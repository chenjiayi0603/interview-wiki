# 字节二面系统设计题：周杰伦发新歌，如何秒级通知2000万粉丝？

> 本质考的是 **Feed流架构** 和 **推送系统设计**，是社交平台最核心的架构问题。

---

## 一、问题分析

### 1.1 核心矛盾：写扩散 vs 读扩散

| 模式 | 做法 | 问题 |
|------|------|------|
| **写扩散（推模式）** | 发动态时写入所有粉丝的收件箱 | 大V瞬间1亿次写入，系统崩溃 |
| **读扩散（拉模式）** | 读的时候去拉所有关注人的发件箱 | 关注2000人，每次查2000次，延迟不可接受 |

⭐ **核心矛盾**：写扩散扛不住大V的写放大，读扩散扛不住用户的读放大。必须推拉结合。

### 1.2 规模估算

| 指标 | 数值 |
|------|------|
| 周杰伦粉丝 | 2000万（题目要求），实际可能上亿 |
| 普通用户关注 | 200~2000人 |
| 写QPS峰值（推模式） | 大V发动态瞬间 → 2000万次写入 |
| 读QPS | Feed流刷新，百万级 |

### 1.3 核心指标

- **延迟**：大V发动态后，粉丝多久能看到？（秒级 vs 分钟级）
- **一致性**：粉丝看到的Feed是否完整、有序？
- **成本**：存储成本、计算成本

---

## 二、三种方案详解

### 方案1：纯推模式（Push / 写扩散）

```
大V发动态 → 遍历粉丝列表 → 写入每个粉丝的Inbox（Redis ZSet）
粉丝读Feed → 直接读自己的Inbox，O(1)极快
```

**适用场景**：微信朋友圈（双向好友，粉丝少）

**致命问题**：
- 周杰伦2000万粉丝 → 瞬间2000万次Redis写入
- 即使Pipeline批量写，也需要几十秒到几分钟
- 期间Redis集群可能因写热点抖动
- 粉丝量更大的大V（1亿），完全不可行

### 方案2：纯拉模式（Pull / 读扩散）

```
大V发动态 → 只写自己的Outbox
粉丝读Feed → 遍历关注的所有人的Outbox → 聚合排序
```

**适用场景**：不适用任何大规模场景

**致命问题**：
- 用户关注2000人 → 每次刷新查2000个Outbox
- 延迟不可接受（秒级 → 几秒甚至十几秒）
- 聚合排序在内存中做，CPU开销大

### 方案3：推拉结合（Hybrid）—— ⭐黄金方案

**核心思路：普通人用推，大V用拉**

```
用户发动态时：
  ├── 普通用户（粉丝 < 50万）→ 推模式：写入所有粉丝Inbox
  └── 大V（粉丝 > 50万）→ 拉模式：只写自己Outbox，不推

用户读Feed时：
  ├── 读取自己的Inbox（普通用户的动态，已推送）
  ├── 读取关注的大V的Outbox（大V的动态，拉取）
  └── 两路数据在内存中归并排序（Merge Sort）→ 返回
```

**为什么有效**：
- 大V发动态只写1次Outbox，解决了写扩散
- 粉丝读Feed时，大V数量通常很少（关注2000人里可能只有5~10个大V），拉取开销可控
- 普通用户的动态已经推送好了，读取极快

⭐ **推拉结合的本质**：用"少量额外拉取"换"海量写入"的释放。

## 三、生产级架构（推拉结合+分层优化）

### 3.1 粉丝分层（解决"推"的精度问题）

不是所有粉丝都需要推：

```
大V的2000万粉丝：
  ├── 铁粉（近7天互动，~300万）→ 推模式，秒级送达
  ├── 活跃粉（近30天登录，~1000万）→ 延迟推送，分钟级
  └── 僵尸粉（超30天未登录，~700万）→ 不推，等用户上线时拉
```

⭐ **粉丝分层将"2000万次写入"降维到"300万即时写 + 1000万延迟写"，峰值降低85%。**

### 3.2 异步削峰（解决瞬时流量洪峰）

```
大V发动态
  │
  ▼
只发1条Kafka事件（不是2000万条！）
  │
  ▼
分组服务消费事件，按粉丝分层生成不同优先级的推送任务
  ├── 高优Topic：铁粉，即时推送
  ├── 中优Topic：活跃粉，延迟1小时推送
  └── 低优Topic：不推送，记录到Outbox
  │
  ▼
推送服务消费各Topic，Pipeline批量写Redis
```

⭐ **大V发动态只产生1次事件写入，由MQ异步分批消化，彻底解耦发布和推送。**

### 3.3 Pipeline批量处理

```go
// 绝不逐条写Redis
func batchPushToInbox(feedID string, fanIDs []uint64) {
    pipe := redisClient.Pipeline()
    for _, fanID := range fanIDs {
        key := fmt.Sprintf("inbox:%d", fanID)
        pipe.ZAdd(key, redis.Z{
            Score:  float64(time.Now().Unix()),
            Member: feedID,
        })
    }
    pipe.Exec(ctx) // 一次网络请求写1000条
}
```

⭐ **Pipeline将N次网络I/O压缩为1次，吞吐提升数十倍。**

### 3.4 存储分层

```
热数据（近7天）：Redis Cluster（ZSet）
  ↓ miss
温数据（近90天）：Redis + 本地SSD缓存
  ↓ miss
冷数据（全量历史）：HBase / ByteKV
```

### 3.5 大V聚合池（优化"拉"的性能）

```
粉丝读Feed时，不是去查每个大V的Outbox，而是查"大V聚合池"：
- 后台异步将所有大V的最新动态聚合到一个索引池
- 粉丝只需要一次I/O就能拿到所有关注大V的动态
- 避免了对N个大V的N次查询
```

⭐ **大V聚合池把"拉N次"变成"拉1次"，彻底解决拉模式的延迟问题。**

## 四、通知推送（App Push）

Feed流更新和App推送通知是两个系统：

| 系统 | 机制 | 场景 |
|------|------|------|
| **Feed流更新** | 写扩散到Inbox | 用户下次打开App时看到 |
| **App推送通知** | APNs（iOS）/ FCM（Android） | 锁屏/通知栏提醒 |

**App推送策略（极度克制，不打扰用户）**：

```
大V发新歌通知：
  ├── 特别关心的粉丝 → 立即推送（APNs/FCM）
  ├── 高互动粉丝 → 延迟5分钟推送
  └── 其他粉丝 → 不推送，只更新Feed流，下次打开App时拉取
```

⭐ **Feed流更新 ≠ App推送通知，这是两个独立系统，面试中必须区分清楚。**

## 五、完整架构图

```
周杰伦发新歌
  │
  ▼
发布服务（只写1条事件）
  ├── 写入大V Outbox（Redis ZSet）
  └── 发送Kafka事件
        │
        ▼
分组服务（粉丝分层）
  ├── 铁粉 → 高优Topic → 即时推送服务 → Pipeline批量写Inbox
  ├── 活跃粉 → 延迟Topic → 延迟推送服务 → Pipeline批量写Inbox
  └── 僵尸粉 → 不推送
        │
        ▼
粉丝打开App
  │
  ├── 读取自己的Inbox（Redis ZSet，已推送的普通用户动态）
  ├── 读取大V聚合池（大V动态，一次I/O）
  ├── Merge Sort → 返回Feed流
  │
  └── （可选）特别关心粉丝 → APNs/FCM推送通知
```

## 六、面试追问

### Q1：Feed流分页怎么做？

- ❌ 不要用 `LIMIT OFFSET`（深分页性能差）
- ✅ 用 Max_ID / 游标分页：上次返回的最后一条时间戳作为游标
- ZSet 的 `ZREVRANGEBYSCORE` 天然支持游标分页

### Q2：如何保证不丢动态？

- **推模式**：Kafka保证 at-least-once，Inbox写入幂等（feedID去重）
- **拉模式**：Outbox是持久化的，不会丢
- **推拉结合**：漏推的动态由拉模式兜底

⭐ **推拉结合天然具备容错能力：推是优化，拉是兜底。**

### Q3：用户取消关注后，Feed里还有TA的动态怎么办？

- **软删除**：读Feed时过滤已取消关注的用户
- **异步清理**：后台任务定期清理Inbox中已取消关注用户的动态

### Q4：Redis挂了怎么办？

- Redis Cluster 多副本
- 降级到拉模式
- 热数据可从MySQL重建

### Q5：2000万扩展到1亿粉丝怎么办？

- 按用户ID地理分区（华北/华东/华南）
- 推送任务分片，多机房并行推送
- 引入MQTT协议替代部分WebSocket（弱网环境）
- QUIC协议替代TCP（解决队头阻塞）

## 七、Go代码示例

### 7.1 Feed流写入

```go
// 大V发动态 - 只写Outbox + 发事件
func PublishFeed(ctx context.Context, userID uint64, content string) error {
    feedID := generateID()

    // 1. 写入大V的Outbox
    err := redis.ZAdd(ctx, fmt.Sprintf("outbox:%d", userID), redis.Z{
        Score:  float64(time.Now().UnixMilli()),
        Member: feedID,
    }).Err()
    if err != nil {
        return err
    }

    // 2. 判断是否大V
    fanCount := getFanCount(userID)

    if fanCount < 500000 {
        // 普通用户：直接推给所有粉丝
        go pushToAllFans(feedID, userID)
    } else {
        // 大V：只发Kafka事件，异步推送
        event := FeedEvent{FeedID: feedID, AuthorID: userID, FanCount: fanCount}
        kafka.Produce("feed-publish", event)
    }

    return nil
}
```

### 7.2 异步推送服务

```go
// 推送服务消费Kafka，批量写Inbox
func StartPushWorker() {
    for msg := range kafka.Consume("feed-push-high") {
        event := parseEvent(msg)
        fans := getActiveFans(event.AuthorID, 7*24*time.Hour) // 铁粉

        // Pipeline批量写，每批1000
        batch := make([]uint64, 0, 1000)
        for _, fanID := range fans {
            batch = append(batch, fanID)
            if len(batch) >= 1000 {
                batchPushToInbox(event.FeedID, batch)
                batch = batch[:0]
            }
        }
        if len(batch) > 0 {
            batchPushToInbox(event.FeedID, batch)
        }
    }
}

func batchPushToInbox(feedID string, fanIDs []uint64) {
    pipe := redisClient.Pipeline()
    score := float64(time.Now().UnixMilli())
    for _, fanID := range fanIDs {
        pipe.ZAdd(ctx, fmt.Sprintf("inbox:%d", fanID), redis.Z{
            Score:  score,
            Member: feedID,
        })
    }
    pipe.Exec(ctx)
}
```

### 7.3 Feed流读取

```go
// 读取Feed流（推拉结合）
func GetFeed(ctx context.Context, userID uint64, cursor int64, limit int) ([]Feed, error) {
    var feeds []Feed

    // 1. 读取Inbox（已推送的普通用户动态）
    inboxFeeds, _ := redis.ZRevRangeByScore(ctx,
        fmt.Sprintf("inbox:%d", userID),
        &redis.ZRangeBy{Min: "0", Max: fmt.Sprintf("%d", cursor), Count: int64(limit)}).Result()

    // 2. 读取关注的大V列表
    bigVs := getFollowedBigVs(userID)

    // 3. 并发拉取大V的Outbox（或从聚合池一次拿）
    bigVFeeds := make([]string, 0)
    var wg sync.WaitGroup
    var mu sync.Mutex
    for _, bv := range bigVs {
        wg.Add(1)
        go func(bvID uint64) {
            defer wg.Done()
            result, _ := redis.ZRevRangeByScore(ctx,
                fmt.Sprintf("outbox:%d", bvID),
                &redis.ZRangeBy{Min: "0", Max: fmt.Sprintf("%d", cursor), Count: 10}).Result()
            mu.Lock()
            bigVFeeds = append(bigVFeeds, result...)
            mu.Unlock()
        }(bv)
    }
    wg.Wait()

    // 4. 合并 + 排序
    allFeeds := mergeAndSort(inboxFeeds, bigVFeeds)

    // 5. 批量获取Feed详情
    feeds = batchGetFeedDetails(allFeeds[:min(len(allFeeds), limit)])

    return feeds, nil
}
```

## 八、面试回答模板

**标准回答结构（3分钟版）**：

> 这个问题本质是Feed流的推拉模式设计。
>
> 核心矛盾是写扩散和读扩散的权衡。纯推模式，大V发一条动态要写2000万次Redis，系统扛不住；纯拉模式，用户刷新时要查所有关注人的发件箱，延迟不可接受。
>
> 所以我采用推拉结合：普通用户（粉丝<50万）用推模式，发动态时写入所有粉丝的Inbox；大V用拉模式，只写自己的Outbox，粉丝读的时候再拉取。
>
> 在此基础上做几个优化：第一，粉丝分层，铁粉即时推、活跃粉延迟推、僵尸粉不推等上线拉；第二，异步削峰，大V发动态只产生1条Kafka事件，由推送服务按优先级分批处理；第三，Pipeline批量写，一次网络请求更新1000个粉丝的Inbox；第四，大V聚合池，粉丝读Feed时一次I/O拿到所有大V动态。
>
> Feed流更新和App推送通知是两个系统，App推送只给特别关心的核心粉丝发，其他用户下次打开App时自然看到。
