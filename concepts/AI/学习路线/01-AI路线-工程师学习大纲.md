# 一、传统后端基础（不能丢）

> 💡 本板块你有深厚基础，重点是查漏补缺和跟进新特性。面试中后端问题仍是基础考察项。

## 1. Go语言进阶

### 1.1 泛型 ⭐⭐⭐ | 面试级 | 建议时间：2天
- **知识点**：类型参数、类型约束（comparable/any/自定义接口）、泛型函数/结构体/方法
- **Go 1.26新特性**：泛型约束自我引用（`type Adder[A Adder[A]] interface{ Add(A) A }`）
- **与你经验关联**：已有Go基础，泛型是1.18后的重点，面试必问
- **学习资源**：
  - [Go Generics官方教程](https://go.dev/doc/tutorial/generics)
  - [Go 1.26 Release Notes](https://go.dev/doc/go1.26)

### 1.2 并发模式（goroutine/channel/context） ⭐⭐⭐ | 实操级 | 建议时间：3天
- **知识点**：
  - goroutine调度模型（GMP模型）
  - channel：无缓冲/有缓冲、select多路复用、方向限定
  - context：取消传播、超时控制、值传递
  - sync包：Mutex/RWMutex/WaitGroup/Once/Pool/Map
  - 并发模式：fan-in/fan-out、pipeline、worker pool、errgroup
- **与你经验关联**：核心优势区，面试中用来展示Go功底
- **学习资源**：
  - 《Go语言高级编程》并发章节
  - [Go Concurrency Patterns (Rob Pike)](https://go.dev/talks/2012/concurrency.slide)

### 1.3 内存管理、GC调优 ⭐⭐⭐ | 原理级 | 建议时间：3天
- **知识点**：
  - Go内存分配器：tcmalloc思想、mspan/mcache/mcentral/mheap
  - GC演进：v1.0 STW → v1.5 三色标记 → v1.8 混合写屏障 → v1.26 Green Tea GC
  - **Go 1.26重点**：Green Tea GC默认启用，GC CPU开销降低10%-40%，AVX向量化加速扫描
  - **Go 2026路线图**：`runtime.free` 显式释放、Specialized malloc、SIMD原生支持
  - GC调优：`GOGC`、`GOMEMLIMIT`、对象池化
  - 逃逸分析：堆/栈分配规则、减少逃逸的技巧
- **与你经验关联**：后端性能优化的核心能力，AI场景中显存+内存双重管理更需要此能力
- **学习资源**：
  - [Go GC Guide](https://go.dev/doc/gc-guide)
  - [Go 1.26 Green Tea GC](https://go.dev/blog/go1.26)
  - [Go 2026路线图](https://blog.csdn.net/bigwhite20xx/article/details/155367574)

### 1.4 错误处理哲学 ⭐⭐ | 面试级 | 建议时间：1天
- **知识点**：error接口、errors.Is/As/Unwrap、panic/recover、sentinel error、wrap error
- **Go 1.26新特性**：`errors.AsType` 泛型错误类型断言
- **与你经验关联**：已有基础，了解1.26新特性即可
- **学习资源**：[Go Blog: Error Handling](https://go.dev/blog/error-handling-and-go)

### 1.5 性能分析：pprof/trace/benchmark ⭐⭐⭐ | 实操级 | 建议时间：2天
- **知识点**：
  - pprof：CPU/Heap/Goroutine/Block/Mutex profiling
  - trace：执行追踪、调度延迟分析
  - benchmark：基准测试、benchstat对比
  - **Go 1.26新特性**：`goroutineleak` profile（实验性）
- **与你经验关联**：已有基础，是AI工程中排查性能瓶颈的关键工具
- **学习资源**：[Go Diagnostics](https://go.dev/doc/diagnostics)

### 1.6 Go 1.26新特性与2026路线图 ⭐⭐ | 面试级 | 建议时间：2天
- **Go 1.26关键特性**：
  - `new(expr)` 指针初始化语法：`new(42)` 替代 `x:=42; &x`
  - 泛型约束自我引用
  - Green Tea GC默认启用
  - cgo开销降低约30%
  - 切片backing store栈分配优化
  - `go fix` 命令重写：基于analysis框架 + modernizers + inline analyzer
  - 实验性：`simd/archsimd` SIMD包、`runtime/secret` 安全擦除、`goroutineleak` profile
  - 新标准库：`crypto/hpke`、`crypto/mlkem/mlkemtest`、`testing/cryptotest`
- **Go 2026路线图**：
  - SIMD high-level API（ARM64 SVE可伸缩向量）
  - `runtime.free` / `runtime.freegc` 显式内存释放
  - Specialized malloc（noscan对象专用分配器）
  - `sync.Sharded` 分片值（减少缓存行争用）
  - Scheduling affinity（调度亲和性）
  - Memory regions（Arena的继任者）
  - 泛型方法（generic method）
  - 联合类型（union type）
  - 无C工具链CGO
- **与你经验关联**：面试加分项，展示技术跟进能力
- **学习资源**：
  - [Go 1.26 Release Notes](https://go.dev/doc/go1.26)
  - [Go 1.26 is released](https://go.dev/blog/go1.26)
  - [Go 2026路线图分析](https://blog.csdn.net/bigwhite20xx/article/details/155367574)

---

#### 1.7.1 Self-RAG：模型自决定是否检索

**核心思想**：让 LLM 自己在生成过程中动态决定"是否需要检索""是否需要重新检索"，而不是每次都固定检索。

**工作机制**：

```
输入Query
    │
    ▼
┌─────────────────────────┐
│   Step 1: 是否需要检索？  │ ← LLM 自判断（IsRetrieveNeeded）
│   - 需要 → 执行检索       │
│   - 不需要 → 直接生成     │
└─────────────────────────┘
    │
    ▼
┌─────────────────────────┐
│   Step 2: 检索并评估      │
│   - 检索结果是否相关？    │ ← LLM 自评估（IsRelevant）
│   - 相关 → 继续生成      │
│   - 不相关 → 忽略检索或重检│
└─────────────────────────┘
    │
    ▼
┌─────────────────────────┐
│   Step 3: 生成回答        │
│   - 基于检索结果生成      │
│   - 每个段落可回溯来源    │
└─────────────────────────┘
```

**关键组件**：

| 组件 | 功能 | 实现方式 |
|------|------|---------|
| **检索决策器** | 判断当前是否需要检索 | 小模型分类器 / LLM 特殊 token 输出 |
| **相关性评估器** | 判断检索结果是否相关 | LLM 打分 / Cross-Encoder |
| **生成器** | 基于检索结果生成回答 | 标准 LLM + 约束解码（citation） |
| **反思标记** | 在输出中标记"有检索支持"或"无检索支持" | 特殊 token 序列（如 `<retrieved><not-retrieved>`） |

**训练方式**：
- 收集"检索-生成"轨迹作为训练数据
- 使用教师强制（Teacher Forcing）训练模型输出反思标记
- 推理时通过反思标记控制检索行为

**优势与劣势**：

| 优势 | 劣势 |
|------|------|
| ✅ 减少不必要的检索（节省成本 + 降低延迟） | ❌ 检索决策可能不准确（假阴性：需要检索但没检） |
| ✅ 提高回答的忠实度（每个段落有来源标记） | ❌ 额外训练成本（需要专有训练数据） |
| ✅ 可解释性强（能看到哪些部分有检索支撑） | ❌ 推理时多一步决策，增加延迟 |
| ✅ 适应不同难度的Query（简单问题不检索） | ❌ 开源实现少，多为论文验证 |

**面试关键**：能讲清楚"为什么 Self-RAG 比朴素 RAG 更接近人类搜索行为——人也是先看是否需要搜索、再评估搜索结果是否靠谱"。

---

#### 1.7.2 CRAG（Corrective RAG）：检索结果评估 + 兜底策略

**核心思想**：对检索结果进行质量评估，根据评估结果采取不同策略——通过、修正或降级。

**工作机制**：

```
输入Query → 检索 → 检索结果
                    │
                    ▼
┌─────────────────────────────────────┐
│         检索结果评估器                │
│  (Relevance Score / Confidence)     │
│                                     │
│  评分 ≥ 阈值高 → ✅ 通过（正常生成）   │
│  阈值低 ≤ 评分 < 阈值高 → 🔄 修正    │
│  评分 < 阈值低 → ❌ 降级             │
└─────────────────────────────────────┘
    │              │              │
    ▼              ▼              ▼
┌─────────┐  ┌────────────┐  ┌──────────┐
│ 直接生成  │  │ 修正策略    │  │ 降级策略  │
│         │  │ - Query改写 │  │ - 网络搜索│
│         │  │ - 多路检索  │  │ - 知识库  │
│         │  │ - 去噪过滤  │  │ - 模型自生成│
└─────────┘  └────────────┘  └──────────┘
```

**评估方法**：

| 评估方式 | 原理 | 适用场景 |
|---------|------|---------|
| **基于分数的评估** | Cross-Encoder 打分 > 阈值 | 精确相关判断 |
| **基于LLM的评估** | 让LLM判断"是否与Query相关" | 灵活、可解释 |
| **基于概率的评估** | 检索模型返回的置信度分数 | 轻量、快速 |
| **基于规则** | 关键词匹配、长度过滤 | 最简单的基线 |

**修正策略详解**：

```
修正（Modify）策略：
  1. Query Rewrite：改写 Query 后重新检索
     "Python内存管理" → "Python garbage collection机制 内存泄漏排查"
  
  2. 多路检索：切换检索源或检索方法
     向量检索 → BM25 / 切换知识库

  3. 去噪过滤：从检索结果中去除不相关的段落
     基于得分阈值截断 / 段落去重

降级（Fallback）策略：
  1. 网络搜索：调用 Google/Bing API 实时搜索最新信息
  2. 备用知识库：切换到另一个知识源
  3. 模型自生成：让 LLM 基于自身知识生成（告知用户无可靠来源）
```

**CRAG vs Self-RAG 区别**：

| 维度 | Self-RAG | CRAG |
|------|----------|------|
| **评估对象** | 是否需要检索（决策前置） | 检索结果的质量（决策后置） |
| **核心机制** | 反思标记控制检索行为 | 评分阈值触发不同策略 |
| **训练需求** | 需要专用训练数据 | 不需要训练，可配置规则 |
| **实现复杂度** | 高（需微调模型） | 中（工程配置即可） |
| **适用场景** | 对延迟和成本敏感的场景 | 对准确率有高要求的场景 |

**面试关键**：能讲出"Self-RAG 和 CRAG 不是互斥的，可以组合使用——先 Self-RAG 决定是否检索，再 CRAG 评估检索结果质量"。

---

#### 1.7.3 Agentic RAG：Agent 主导的多步检索

**核心思想**：将 RAG 流程交给 Agent 自主编排——Agent 可以规划多步检索、选择不同工具、根据中间结果动态调整检索策略。

**工作机制**：

```
用户Query
    │
    ▼
┌──────────────────────────────────────────────────┐
│  Agent (LLM + Tool Registry)                      │
│                                                   │
│  Step 1: 分析Query → 制定检索计划                   │
│    "用户问的是2024年Q3的财报数据"                    │
│    → 计划：① 检索财报库 → ② 检索新闻补充 → ③ 对比   │
│                                                   │
│  Step 2: 按计划执行检索                            │
│    Tool: 向量检索(q, "财报库") → 结果A              │
│    Tool: 向量检索(q, "新闻库") → 结果B              │
│    Tool: Web搜索(q) → 结果C                        │
│                                                   │
│  Step 3: 评估中间结果 → 调整计划                    │
│    结果A不够新 → 增加"网络搜索2024Q3"               │
│    结果B有冲突 → 增加"事实核查"                    │
│                                                   │
│  Step 4: 综合所有结果 → 生成最终回答                │
└──────────────────────────────────────────────────┘
```

**Agent 可用工具库**：

| 工具 | 功能 | 适用场景 |
|------|------|---------|
| **向量检索** | 从知识库语义检索 | 常规知识查询 |
| **BM25检索** | 关键词精确匹配 | 精确命名实体匹配 |
| **Web搜索** | 实时网络信息 | 最新消息、实时数据 |
| **数据库查询** | SQL/NoSQL 查询 | 结构化数据查询 |
| **API调用** | 调用外部服务 | 天气、股票、地图等 |
| **文档解析** | PDF/HTML 解析 | 需要从文档提取信息 |
| **代码执行** | Python 沙箱执行 | 数据分析、计算 |

**多步检索模式**：

```
┌──────────────────────────────────────────────────────────┐
│ 模式1：分解-并行的（Decompose-Parallel）                   │
│   Query: "比较Go和Rust在并发安全方面的设计"                │
│          ↓ 分解                                          │
│   ├─ 子Q1: "Go goroutine 并发安全设计" → 检索 → 结果A     │
│   ├─ 子Q2: "Rust ownership 并发安全设计" → 检索 → 结果B  │
│   └─ 综合A+B → 比较生成                                  │
│                                                          │
│ 模式2：迭代-深化的（Iterative-Deepening）                   │
│   Query: "如何优化Kubernetes集群的网络性能"                │
│          ↓ 初始检索                                       │
│   ├─ 检索 → 结果不够具体 → 细化Query                       │
│   ├─ 细化检索 → 得到CNI插件对比 → 进一步检索               │
│   └─ 检索 → 得到Calico vs Cilium配置对比 → 综合回答       │
│                                                          │
│ 模式3：自省-修正的（Introspect-Correct）                   │
│   Query: "2024年诺贝尔物理学奖得主"                       │
│          ↓ 检索                                           │
│   ├─ 检索 → 得到结果A（可能有幻觉）                        │
│   ├─ 自省: "这个信息可靠吗？" → 发现日期不符               │
│   └─ 重新检索 → 核实 → 得到正确结果                       │
└──────────────────────────────────────────────────────────┘
```

**实现框架**：

| 框架 | 语言 | Agentic RAG 支持 | 特点 |
|------|------|-----------------|------|
| **LangChain/LangGraph** | Python | ✅ 原生支持 | 最成熟的Agent + RAG框架 |
| **LlamaIndex** | Python | ✅ 原生支持 | 检索为中心，Agent工具丰富 |
| **CrewAI** | Python | ✅ 多Agent协作 | 多Agent分工检索 |
| **AutoGen** | Python | ✅ 多Agent协作 | 微软出品，对话式多Agent |
| **Go + MCP** | Go | ⚠️ 手动实现 | 轻量、可控、适合生产 |

**面试关键**：能设计一个 Agentic RAG 的检索计划流程，并解释"为什么需要多步检索而不是一次性检索"——因为复杂Query一次检索可能遗漏关键信息。

#### 1.7.4 Graph RAG：知识图谱增强检索

> Microsoft 在 2024 年提出的方法，通过构建知识图谱来增强 RAG 的检索质量，特别适合处理需要理解实体关系、跨文档连接的问题。

**核心思想**：传统RAG检索的是"文本片段"（chunks），Graph RAG 检索的是"实体 + 关系"（triples）。通过知识图谱连接分散在不同文档中的相关信息。

**架构流程**：

```
文档集
    │
    ▼
┌──────────────────────────────┐
│  1. 知识图谱构建              │
│  ┌────────────────────────┐  │
│  │ a. 实体提取             │  │
│  │   LLM从文档中提取实体     │  │
│  │   "张三" "华为" "工程师" │  │
│  ├────────────────────────┤  │
│  │ b. 关系提取             │  │
│  │   LLM提取实体间关系      │  │
│  │   (张三, 任职于, 华为)   │  │
│  │   (张三, 职位, 工程师)   │  │
│  ├────────────────────────┤  │
│  │ c. 社区检测             │  │
│  │   对实体进行聚类分组      │  │
│  │   "华为团队" "AI行业"    │  │
│  ├────────────────────────┤  │
│  │ d. 社区摘要             │  │
│  │   LLM为每个社区生成摘要   │  │
│  │   "华为AI战略概述"       │  │
│  └────────────────────────┘  │
└──────────────────────────────┘
    │
    ▼
┌──────────────────────────────┐
│  2. 查询阶段                  │
│                              │
│  Query: "华为的AI战略是什么"   │
│         ↓                    │
│  ┌──────────────────────┐   │
│  │ a. Query → 实体提取   │   │
│  │  "华为" "AI战略"      │   │
│  └──────────────────────┘   │
│         ↓                    │
│  ┌──────────────────────┐   │
│  │ b. 图谱检索           │   │
│  │  ├─ 直接相关实体       │   │
│  │  ├─ 一跳邻居实体       │   │
│  │  └─ 相关社区摘要       │   │
│  └──────────────────────┘   │
│         ↓                    │
│  ┌──────────────────────┐   │
│  │ c. 综合生成           │   │
│  │  实体信息 + 关系 +    │   │
│  │  社区摘要 → LLM生成   │   │
│  └──────────────────────┘   │
└──────────────────────────────┘
```

**Graph RAG vs 传统RAG**：

| 维度 | 传统 RAG（向量检索） | Graph RAG |
|------|--------------------|-----------|
| **检索粒度** | 文本片段（chunks） | 实体 + 关系（triples） |
| **跨文档连接** | ❌ 无（chunk之间独立） | ✅ 实体关系连接不同文档 |
| **全局性问题** | ❌ 难以回答"整体概述"类问题 | ✅ 社区摘要提供全局视角 |
| **实现复杂度** | 低 | 高（需图谱构建Pipeline） |
| **构建成本** | 低（一次Embedding） | 高（多次LLM调用提取实体关系） |
| **更新成本** | 低（增量更新） | 高（需要重新提取实体关系） |
| **适用场景** | 事实性问答、单点查询 | 关系分析、综合性/全局性问题 |

**Microsoft Graph RAG 的两种检索模式**：

```
本地检索（Local Search）：
  Query → 实体提取 → 一跳/两跳邻居 → LLM生成
  适用：具体事实查询（"华为的GPU芯片叫什么？"）

全局检索（Global Search）：
  Query → 社区匹配 → 社区摘要 → 多摘要综合 → LLM生成
  适用：综合性问题（"华为在AI领域有哪些布局？"）
```

**实际效果**（Microsoft 论文数据）：

| 指标 | 传统 RAG | Graph RAG | 提升 |
|------|---------|-----------|------|
| 全局性问题准确率 | 42% | 71% | +29% |
| 多步推理准确率 | 55% | 78% | +23% |
| 回答全面性（人工评分） | 3.2/5 | 4.1/5 | +28% |
| 构建成本 | $1/1000文档 | $15/1000文档 | 高15x |

**面试关键**：能讲清楚"Graph RAG 不是替代传统 RAG，而是在需要实体关系理解时的补充——可以混合使用：向量检索搜事实、图谱检索搜关系"。

#### 1.7.5 Modular RAG：模块化组件组合

**核心思想**：将 RAG 流程拆解为可替换的独立模块，根据不同场景灵活组合。这是 RAG 范式的最高层次——从"固定流程"到"乐高积木"。

**模块定义**：

```
┌─────────────────────────────────────────────────────────────────────┐
│                        Modular RAG 组件库                            │
├──────────┬──────────┬──────────┬──────────┬──────────┬──────────────┤
│ 索引模块   │ 检索模块   │ 重排序模块 │ 生成模块   │ 评估模块   │ 控制模块    │
├──────────┼──────────┼──────────┼──────────┼──────────┼──────────────┤
│ ·固定切分 │ ·向量检索  │ ·Cross-  │ ·标准LLM │ ·相关性  │ ·Self-RAG   │
│ ·语义切分 │ ·BM25    │  Encoder │ ·流式输出 │ ·忠实度  │ ·Agent决策  │
│ ·AST切分  │ ·混合检索 │ ·LLM     │ ·结构化   │ ·质量    │ ·路由       │
│ ·滑窗     │ ·图检索   │  Rerank  │  输出    │ ·安全    │ ·缓存       │
│ ·元数据   │ ·SQL查询  │ ·MMR去重 │ ·代码执行 │         │ ·限流       │
└──────────┴──────────┴──────────┴──────────┴──────────┴──────────────┘
```

**常见组合模式**：

```
模式1：朴素 RAG
  Query → [检索] → [生成] → 回答
  最简单，适合知识库精确匹配

模式2：RAG + 重排序
  Query → [检索] → [重排序] → [生成] → 回答
  提升检索结果质量，适合对准确率要求高的场景

模式3：HyDE（假设文档嵌入）
  Query → [LLM生成假设回答] → [用假设回答检索] → [生成] → 回答
  解决Query和文档语义不匹配的问题

模式4：RAG-Fusion
  Query → [多路检索] → [RRF融合] → [重新排序] → [生成] → 回答
  结合不同检索方式的优势

模式5：Self-RAG
  Query → [自判断是否需要检索] → [检索] → [自评估结果] → [生成] → 回答
  动态决定检索行为

模式6：Agentic RAG
  Query → [Agent规划] → [多步检索] → [中间评估] → [调整策略] → [综合生成] → 回答
  最灵活，适合复杂查询

模式7：Graph + Vector 混合
  Query → [实体提取] → [图检索 + 向量检索] → [融合结果] → [生成] → 回答
  同时利用语义检索和关系检索

模式8：完整模块化
  Query → [路由(Router)] → [查询重写] → [多路检索] → [融合] → [重排序] → [过滤] → [参考] → [生成] → [验证] → 回答
  生产级RAG系统
```

**Route（路由）模块详解**：

| 路由策略 | 原理 | 适用场景 |
|---------|------|---------|
| **基于规则** | 关键词/正则匹配 → 指定检索源 | 简单、确定性强 |
| **基于Embedding** | Query向量相似度 → 分类 | 中等复杂度 |
| **基于LLM** | LLM判断Query类型 → 路由 | 最灵活，但成本高 |
| **基于元数据** | 根据Query中的实体类型路由 | 结构化知识库 |

**模块化设计原则**：

```
┌────────────────────────────────────────────┐
│ Modular RAG 设计原则                        │
├────────────────────────────────────────────┤
│ 1. 单一职责：每个模块只做一件事              │
│    检索模块只检索，不负责排序               │
│                                            │
│ 2. 可替换性：模块可独立替换                 │
│    替换检索模块：向量检索→BM25→混合         │
│                                            │
│ 3. 可组合性：模块可自由组合                 │
│    [检索] + [重排序] 或 [检索] + [重写]     │
│                                            │
│ 4. 可扩展性：可新增模块                     │
│    新增"验证模块"→ 在生成后做事实核查       │
│                                            │
│ 5. 透明性：模块间接口清晰                   │
│    输入/输出规范统一、可插拔                │
└────────────────────────────────────────────┘
```

**面试关键**：能根据业务场景选择合适的 RAG 模式组合。给出"如果我是面试官，会让你设计一个RAG系统的模块化架构"的思路。

#### 1.7.6 五种高级 RAG 对比总结

| 维度 | Self-RAG | CRAG | Agentic RAG | Graph RAG | Modular RAG |
|------|----------|------|-------------|-----------|-------------|
| **核心创新** | 自决定是否检索 | 检索结果质量评估 | Agent主导多步检索 | 知识图谱增强检索 | 模块化组件组合 |
| **是否需训练** | ✅ 需要 | ❌ 不需要 | ❌ 不需要 | ❌ 不需要 | ❌ 不需要 |
| **实现复杂度** | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐ |
| **检索质量提升** | 中（减少不必要的检索） | 高（过滤低质量结果） | 很高（多步多策略） | 高（实体关系检索） | 视组合而定 |
| **延迟影响** | 低（减少检索次数） | 中（增加评估步骤） | 高（多步迭代） | 中（图谱检索） | 视组合而定 |
| **成本影响** | 降低（减少API调用） | 中（增加评估调用） | 高（多次LLM调用） | 高（构建+检索） | 视组合而定 |
| **适用Query** | 混合难度 | 中等难度 | 复杂Query | 关系型/全局型 | 任意 |
| **成熟度** | 论文验证 | 论文验证 | 部分生产落地 | Microsoft产品化 | 概念框架 |
| **面试频率** | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐ |

**组合使用建议**：

```
生产级 RAG 系统推荐组合：
  
  简单事实查询 → [朴素RAG] → 快速准确
    不需要高级技术，简单直接

  中等难度Query → [Self-RAG + CRAG]
    先自判断是否需要检索 → 再评估结果质量 → 修正或降级

  复杂多步Query → [Agentic RAG + Graph RAG]
    Agent规划检索 → 图检索找关系 + 向量检索找事实 → 综合生成

  高准确率要求 → [完整Modular RAG]
    路由 → 多路检索 → 重排序 → 验证 → 生成
```

#### 面试追问准备

**Q1：Self-RAG 的检索决策器怎么实现？**
> 两种方案：① 用一个小分类器模型（如 BERT）判断是否需要检索，优点是快，缺点是需要额外训练；② 用 LLM 输出特殊 token（如 `<retrieve>` 或 `<no-retrieve>`），优点是不需要额外模型，缺点是增加生成成本和延迟。实践中更倾向方案①，因为检索决策本身应该轻量。

**Q2：CRAG 的评估阈值怎么设定？**
> 根据业务场景调整：对准确率要求高的场景（如医疗/金融），阈值设高（宁可多修正，不可用错误信息）；对延迟敏感的场景，阈值设低（接受一定错误，但保证响应速度）。通常通过验证集上的 Precision-Recall 曲线确定最优阈值，也可以动态调整——根据用户反馈信号调低/调高。

**Q3：Agentic RAG 怎么防止 Agent "迷路"（多步检索后偏离原始Query）？**
> 三种策略：① **最大步数限制**（如最多5步检索，超时返回已有结果）；② **相关性回溯**（每步检索后判断结果是否仍与原始Query相关，不相关则回溯到上一步）；③ **阶段性验证**（每2-3步让LLM总结当前进展，判断是否已经足够回答Query）。实践中三种策略组合使用。

**Q4：Graph RAG 的构建成本很高，有什么优化方法？**
> ① **增量构建**：新文档只影响局部子图，不需要全量重建；② **分层构建**：高频查询的实体构建完整图谱，低频数据只保留粗粒度关系；③ **按需构建**：不预先构建全量图谱，而是在查询时动态提取实体关系（类似"即时建图"）；④ **用轻量模型**：实体提取用 7B 模型而非 70B 模型，可大幅降低成本。

**Q5：Modular RAG 和传统 Pipeline 有什么区别？**
> 传统 Pipeline 是固定流程（检索→排序→生成），更换组件需要改代码。Modular RAG 将每个组件定义为可插拔的独立模块，通过配置即可组合不同流程。本质上是"策略模式"（Strategy Pattern）在 RAG 上的应用——每个模块是一个策略，运行时可以动态切换。类比：Pipeline 是 for 循环，Modular RAG 是函数式组合。

## 4. 向量检索

### 4.1 向量化流程 ⭐⭐⭐ | 实操级 | 建议时间：1天
- **知识点**：文本 → Tokenization → Embedding模型 → 向量 → 索引

### 4.2 相似度计算 ⭐⭐⭐ | 原理级 | 建议时间：1天
- **知识点**：
  - 余弦相似度：方向相似性、归一化后等价于点积
  - 欧氏距离：空间距离
  - 内积（Dot Product）：未归一化的余弦
  - **选择原则**：归一化向量用余弦/内积，否则用欧氏距离
- **与你经验关联**：基础数学，理解直觉即可

### 4.3 HNSW算法原理 ⭐⭐⭐ | 原理级 | 建议时间：2天
- **知识点**：
  - 多层图结构：底层包含所有向量，上层是稀疏采样
  - 搜索过程：从顶层入口贪心搜索，逐层向下精确
  - 构建过程：逐点插入、启发式选择邻居
  - 参数：M（邻居数）、ef_construction（构建时搜索宽度）、ef_search（查询时搜索宽度）
  - 复杂度：构建O(n·log(n))，查询O(log(n))
- **与你经验关联**：类比跳表（Skip List）——多层索引加速查找
- **学习资源**：[HNSW论文](https://arxiv.org/abs/1603.09320)

### 4.4 ANN vs KNN ⭐⭐ | 面试级 | 建议时间：1天
- **知识点**：
  - KNN：精确搜索，暴力遍历，O(n)
  - ANN：近似搜索，牺牲精度换速度，O(log(n))
  - ANN算法：HNSW、IVF、PQ（乘积量化）、LSH
  - **召回率-延迟权衡**

### 4.5 Qdrant实战 ⭐⭐⭐ | 实操级 | 建议时间：2天
- **知识点**：
  - 集合创建、向量上传、索引构建
  - 搜索API：向量搜索 + 过滤条件
  - Payload索引：支持结构化+向量联合查询
  - 优化：量化配置、分片、别名
- **学习资源**：[Qdrant官方教程](https://qdrant.tech/documentation/)

### 4.6 bge-m3三模式 ⭐⭐⭐ | 实操级 | 建议时间：2天
- **知识点**：
  - Dense：稠密向量，语义相似度
  - Sparse：稀疏向量（类似BM25），关键词匹配
  - ColBERT：交互式向量，token级匹配
  - 三模式联合：混合检索的终极方案
- **与你经验关联**：理解"不同粒度的检索有不同优势"

### 4.7 粗排与精排 ⭐⭐⭐ | 原理级 | 建议时间：1天
- **知识点**：
  - 粗排：向量检索top-K（K大，速度快）
  - 精排：Cross-Encoder/Reranker重排top-K（K小，精度高）
  - 经典漏斗：top-1000 → top-100 → top-10

### 4.8 LLM融合排序 ⭐⭐ | 面试级 | 建议时间：1天
- **知识点**：用LLM对检索结果进行相关性判断和重排序

## 3. 缓存策略

### 3.1 向量缓存 ⭐⭐⭐ | 原理级 | 建议时间：1天
- **知识点**：相同Query的Embedding结果缓存、向量一致性

### 3.2 Prompt缓存 ⭐⭐⭐ | 原理级 | 建议时间：1天
- **知识点**：
  - Anthropic Prompt Caching：标记可缓存的System Prompt/工具定义
  - OpenAI Prompt Caching：自动缓存长prompt前缀
  - 节省：最高90%的输入token成本
- **与你经验关联**：类比HTTP缓存——不变的部分缓存，变化的部分动态

### 3.3 LLM响应缓存 ⭐⭐⭐ | 原理级 | 建议时间：1天
- **知识点**：
  - 精确缓存：相同Query+Context → 相同回答
  - 语义缓存：相似Query → 相似回答（向量相似度判断）
  - 缓存粒度：完整回答 vs 检索片段 vs 单步推理
- **与你经验关联**：🔥 这是最能体现你后端优势的领域

### 3.4 缓存一致性 ⭐⭐⭐ | 原理级 | 建议时间：1天
- **知识点**：
  - 文档更新 → Embedding重算 → 缓存失效
  - 知识库版本管理
  - 增量更新 vs 全量更新
- **与你经验关联**：Redis缓存一致性问题的高级版本

### 3.5 命中率优化 ⭐⭐⭐ | 实操级 | 建议时间：1天
- **知识点**：
  - 语义缓存：Embedding相似度阈值调优
  - 缓存预热：高频Query预加载
  - 缓存淘汰：LRU/LFU/基于重要性
  - 缓存穿透防护：空结果缓存

### 3.6 分层缓存 ⭐⭐⭐ | 原理级 | 建议时间：1天
- **知识点**：
  - L1 内存：最近使用的Prompt/响应，微秒级

  - L3 向量库：语义检索缓存，十毫秒级
- **与你经验关联**：🔥 多级缓存架构设计，后端经典问题
