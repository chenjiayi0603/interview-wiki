# Harness Engineering 详解

> **信息来源**：抖音视频「小哲讲大模型」+ 网络资料扩展

---

## 一句话理解

**Harness Engineering = 给 AI Agent 打造一个「可靠的运行环境」**，让 AI 从「能干活」变成「能稳定、高效、可持续地干活」。

---

## 1. 什么是 Harness Engineering

### 1.1 核心公式

```
Agent = Model + Harness
```

- **Model（模型）**：AI 的「大脑」，负责推理和生成
- **Harness（挽具）**：围绕模型构建的完整运行环境，包括工具、验证、约束、反馈机制

### 1.2 经典比喻

| 角色 | 比喻 |
|------|------|
| Model | 马（动力来源） |
| Harness | 马具（缰绳 + 马鞍） |
| Developer | 骑师（指引方向） |

> "模型是马，Harness 是马具，骑师是开发者。好的马具让普通人也能驾驭烈马。"

### 1.3 提出背景

由 **HashiCorp 联合创始人 Mitchell Hashimoto** 于 2026 年初提出，核心原则：

> *"每当 Agent 犯错，不要只修 Prompt，要设计系统性解决方案让 Agent 永远不再犯同样的错误。"*

### 1.4 OpenAI 的口号

```
"Humans steer. Agents execute."
人类掌舵，Agent 执行。
```

---

## 2. 三次范式跃迁

Harness Engineering 不是替代前两者，而是**分层叠加**：

| 阶段 | 问题 | 核心 |
|------|------|------|
| **Prompt Engineering** | 怎么表达任务？ | 指令设计和措辞优化 |
| **Context Engineering** | 模型工作时该看到什么？ | 信息供给和上下文管理 |
| **Harness Engineering** | 模型运行在什么系统里？ | 完整运行环境和工程保障 |

```
┌─────────────────────────────────┐
│     Harness Engineering         │  ← 新增：系统层保障
├─────────────────────────────────┤
│     Context Engineering         │  ← 2024主流：信息层
├─────────────────────────────────┤
│     Prompt Engineering          │  ← 基础层：表达层
└─────────────────────────────────┘
```

## 3. 为什么 Harness Engineering 重要？

### 3.1 模型趋同，能力之外才是护城河

当各家模型能力趋于一致，**如何在模型之上构建可靠的工程系统**成为核心竞争力。

### 3.2 数据说话

**LangChain 实验**（仅改 Harness，不改模型）：
```
Terminal Bench 2.0: 52.8% → 66.5%
性能提升: +26%
```

**OpenAI 极端案例**：
```
团队规模: 3人
时间跨度: 5个月
代码产量: 100万行
人工手写: 0行
PR数量: 1500个
```

### 3.3 失败率的数学真相

```
多步任务成功率 = 0.95^20 ≈ 36%
```

每一步有 95% 成功率，但 20 步后成功率暴跌到 36%。**AI 失败是系统问题，不是能力问题**。

## 4. 三大支柱

### 4.1 上下文工程（Context Engineering）

让 Agent 看到它需要的一切，但不过载。

| 策略 | 说明 |
|------|------|
| **渐进式披露** | AGENTS.md/CLAUDE.md 作为索引地图（≤100行），指向结构化 docs 目录 |
| **运行时数据接入** | 日志、指标对 Agent 可读 |
| **直接环境感知** | Chrome DevTools 等让 Agent 操作真实环境 |

> **OpenAI 教训**：巨型说明书反而差，100行索引地图效果远好于5000行说明书。

```
# CLAUDE.md 示例结构
## 项目概述
## 技术栈
## 关键文件索引
  - src/api/ → ...
  - tests/ → ...
## 开发规范
## 常用命令
```

### 4.2 架构约束（Architectural Constraints）

用规则引导 Agent 做出正确选择。

| 约束类型 | 示例 |
|----------|------|
| AI友好型 Linter | 错误消息直接包含修复建议 |
| 双轨审计 | 审计 Agent 审查开发 Agent 的代码 |
| 结构化验证规则 | 强制输出满足特定格式/约束 |

> **反直觉真理**：约束解放创造力。限制解决方案空间反而提升质量。

```
# AI-Friendly Linter 示例输出
❌ 错误：变量命名不规范
✅ 建议：将 `x` 重命名为 `user_age`，使用 snake_case
```

### 4.3 反馈回路与熵管理（Feedback Loops & Entropy Management）

对抗「完成即交付」的 Agent 天性。

| 机制 | 作用 |
|------|------|
| **验证闭环** | 输出 → 验证 → 不通过 → 反馈 → 修复 → 再验证 |
| **反熵 Agent** | 定期扫描清理过时文档、漂移代码模式、无效依赖 |
| **Context Rot 管理** | 长时间运行性能退化，需压缩、卸载、分层管理 |

## 5. 六大核心模块

| # | 模块 | 核心问题 | 关键实践 |
|---|------|----------|----------|
| 1 | **上下文/知识** | 信息可可达性 | AGENTS.md、动态注入、知识库 |
| 2 | **工具/权限** | 动作可执行性 | MCP、沙箱、CLI封装、权限白名单 |
| 3 | **验证/约束** | 结果可验证性 | Linter、结构测试、pre-commit hooks、双Agent审计 |
| 4 | **状态/记忆** | 跨步可持续性 | 进度文件、增量提交、检查点恢复 |
| 5 | **可观测/反馈** | 问题可定位性 | 执行追踪、异常检测、质量分级 |
| 6 | **人类接管** | 关键决策可控性 | 暂停点、生命周期钩子、失败恢复 |

## 6. Build-Verify Loop（构建-验证循环）

```
┌─────────────┐
│  规划 & 探索  │  ← 高推理预算
└──────┬──────┘
       ▼
┌─────────────┐
│    构建      │  ← 中等推理预算
└──────┬──────┘
       ▼
┌─────────────┐
│    验证      │  ← 高推理预算
└──────┬──────┘
       ▼
   ┌───────┐
   │ 通过？ │──┐
   └───────┘  │
      │ 否   │ 是
      ▼      ▼
  ┌────────┐ ┌─────────┐
  │  修复   │ │   完成   │
  └────┬───┘ └─────────┘
       │
       └────── 循环 ──────┘
```

**关键洞察**：Agent 天然倾向「完成即交付」，Harness 必须主动施压强制验证。

## 7. 中间件与 Hooks

在 Agent 执行链路中注入干预点：

| Hook 类型 | 触发条件 | 注入内容 |
|-----------|----------|----------|
| **循环检测** | 同一文件编辑 >3 次 | 重新思考提示 |
| **提交前提醒** | Agent 即将退出 | "请运行测试" |
| **时间预算感知** | 任务超时前 | 进度检查提醒 |

> **设计原则**：失败要大声，成功要安静。

## 8. 推理预算策略（Reasoning Sandwich）

不同阶段分配不同的「思考预算」：

```
高推理 → 规划探索（深度分析问题）
    ↓
中推理 → 实现阶段（按计划执行）
    ↓
高推理 → 最终验证（批判性检查）
```

## 11. 实践指南：如何应用到你的场景

> 你之前提到想做一个「可视化流程图 + 每个节点能自动调用工具干活」的全链路自动化工作流。Harness Engineering 就是这套系统的理论框架。

### 对应关系

| 你的需求 | Harness 解决方案 |
|----------|------------------|
| 流程图节点配置 | Context Engineering → 每个节点有独立的 AGENTS.md |
| 节点自动执行工具 | 工具/权限模块 → MCP 协议 + CLI 封装 |
| 执行结果验证 | 验证/约束模块 → Linter + 结构测试 |
| 流程状态保持 | 状态/记忆模块 → 检查点 + 进度文件 |
| 出问题能排查 | 可观测/反馈模块 → 执行追踪 + 日志 |
| 人工干预点 | 人类接管模块 → 暂停点 + 生命周期钩子 |

### 最小可行实现

```yaml
# 示例：节点配置
nodes:
  - id: code_review
    harness:
      context: ./nodes/code_review/AGENTS.md  # 索引文件
      tools: [git, flake8, pytest]            # 可用工具
      verify: ./nodes/code_review/rules.yaml   # 验证规则
      checkpoint: true                         # 启用检查点
      human_override: true                     # 人工干预点
```
