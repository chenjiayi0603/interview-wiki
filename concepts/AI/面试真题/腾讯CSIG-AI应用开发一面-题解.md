## Q1: 手撕LRU

**题目：** 实现一个LRU缓存，要求get和put操作O(1)时间复杂度。

**参考答案：**

核心思路：**哈希表 + 双向链表**。哈希表保证O(1)查找，双向链表保证O(1)的插入/删除/移动到头部。

```go
package lru

import "fmt"

// Node 双向链表节点
type Node struct {
	key   int
	value int
	prev  *Node
	next  *Node
}

// LRUCache LRU缓存结构
type LRUCache struct {
	capacity int
	cache    map[int]*Node
	head     *Node // 哨兵头节点
	tail     *Node // 哨兵尾节点
}

// Constructor 构造函数
func Constructor(capacity int) LRUCache {
	lru := LRUCache{
		capacity: capacity,
		cache:    make(map[int]*Node),
		head:     &Node{},
		tail:     &Node{},
	}
	lru.head.next = lru.tail
	lru.tail.prev = lru.head
	return lru
}

// Get 获取元素，存在则移到头部并返回值，不存在返回-1
func (l *LRUCache) Get(key int) int {
	if node, ok := l.cache[key]; ok {
		l.moveToHead(node)
		return node.value
	}
	return -1
}

// Put 插入/更新元素
func (l *LRUCache) Put(key int, value int) {
	if node, ok := l.cache[key]; ok {
		// key已存在，更新value并移到头部
		node.value = value
		l.moveToHead(node)
		return
	}

	// 新节点
	newNode := &Node{key: key, value: value}
	l.cache[key] = newNode
	l.addToHead(newNode)

	// 超出容量，淘汰尾部
	if len(l.cache) > l.capacity {
		removed := l.removeTail()
		delete(l.cache, removed.key)
	}
}

// moveToHead 将节点移到头部
func (l *LRUCache) moveToHead(node *Node) {
	l.removeNode(node)
	l.addToHead(node)
}

// addToHead 在头部插入节点（哨兵head之后）
func (l *LRUCache) addToHead(node *Node) {
	node.prev = l.head
	node.next = l.head.next
	l.head.next.prev = node
	l.head.next = node
}

// removeNode 从链表中摘除节点
func (l *LRUCache) removeNode(node *Node) {
	node.prev.next = node.next
	node.next.prev = node.prev
}

// removeTail 淘汰尾部节点（哨兵tail之前）
func (l *LRUCache) removeTail() *Node {
	node := l.tail.prev
	l.removeNode(node)
	return node
}
```

**设计要点解析：**

1. **哨兵节点（Dummy Head/Tail）**：避免链表操作时的空指针判断，所有真实节点都在 head 和 tail 之间
2. **双向链表**：O(1) 删除任意节点（需要 prev 指针才能不遍历就删除）
3. **哈希表**：O(1) 定位节点位置，不需要遍历链表查找
4. **淘汰策略**：尾部是最近最少使用的，头部是最近刚访问的

**Go语言特有注意事项：**
- Go没有泛型时用 `interface{}`，Go 1.18+ 可用泛型参数化 key/value 类型
- 实际工程中可结合 `sync.Mutex` 做并发安全版本

⭐ **得分点：**
- 双向链表 + 哈希表组合，说清楚各自职责
- 哨兵节点简化边界处理
- get 和 put 均 O(1) 的时间复杂度证明
- 主动提并发安全改造（体现14年后端经验）

## Q3: 记忆压缩机制

### Q3.1: 了解哪些记忆压缩机制？

**参考答案：**

常见的记忆压缩机制可分为以下几类：

**1. 滑动窗口/截断**
- 保留最近N轮对话，丢弃更早的内容
- 最简单但信息损失最大

**2. 摘要压缩（Summarization）**
- 用LLM将历史对话总结为摘要，替换原文
- Claude Code 的 AutoCompact：9章节结构化摘要（用户请求、技术概念、文件、错误、执行过程、原始消息、待完成任务、当前工作、下一步）
- OpenClaw 的 Memory Flush：压缩前静默写入 MEMORY.md

**3. 分层记忆架构**
- 短期（工作记忆/Context Window）→ 中期（摘要/日志）→ 长期（知识库/MEMORY.md）
- 类似人类的感知记忆 → 短期记忆 → 长期记忆

**4. RAG式记忆检索**
- 将对话历史向量化存入向量库，按需检索
- OpenClaw 混合检索：BM25(30%) + 向量相似度(70%)

**5. 渐进式压缩（Multi-level Compaction）**
- Claude Code 四层压缩：工具结果预算 → MicroCompact → AutoCompact → PartialCompact
- 从零成本到有成本逐级升级

⭐ **得分点：**
- 不只是列举，要说清楚每种方案的适用场景和trade-off
- 主动对比 Claude Code 和 OpenClaw 两种不同思路

### Q3.2: 工作流流程较长，多工具调用返回内容占据大量上下文窗口怎么管理？

**参考答案：**

这是一个非常实际的工程问题，我在后端开发中处理过类似的资源管理问题。核心思路是**分层管理、按需加载**：

**1. 工具结果截断与脱机存储**
- 每个工具设 `maxResultSizeChars` 上限，超出部分写入磁盘/数据库
- 上下文中只保留摘要 + 引用指针
- 类比：后端的大结果集分页，不把全量数据加载到内存

**2. MicroCompact — 用完即清**
- 已被消费的工具结果，直接替换为 `[Old tool result content cleared]`
- 保留最近3个工具结果的原文，其余清除
- 零成本、不调用LLM

**3. 渐进式摘要**
- 当上下文接近阈值时，用LLM生成结构化摘要替换旧历史
- 摘要中必须包含：用户原始请求、当前进度、待完成事项
- 防止"摘要的摘要"导致信息衰减

**4. 关键信息持久化**
- 在压缩前，触发静默写入（Silent Memory Flush），将重要事实持久化到文件
- 下次需要时可按需检索回来

**5. 上下文预算制**
- 给不同类型内容分配token预算
- System Prompt 固定开销 → 工具结果预算 → 对话历史预算
- 超预算就触发对应级别的压缩

⭐ **得分点：**
- 从工程实践角度出发，类比后端资源管理经验
- 强调"渐进式"而非"一刀切"
- 提到Silent Memory Flush这个关键设计

### Q3.3: 短期记忆如何与用户进行关联？比如用户两次询问间隔了好几天如何维护记忆。

**参考答案：**

这是一个跨会话记忆关联的问题，核心挑战是：短期记忆的生命周期是单次会话，但用户期望跨天也能"记住我"。

**三层关联策略：**

**1. 用户ID → 记忆命名空间绑定**
- 每个用户有独立的记忆存储空间（如 `memory/{user_id}/`）
- 防止多用户记忆交叉污染
- 类比：后端Session按用户ID隔离

**2. 跨会话记忆继承**
- 会话启动时，加载该用户的 MEMORY.md（长期记忆）+ 最近2天日志（短期延续）
- OpenClaw 的做法：启动时读取 `SOUL.md`、`USER.md`、今天和昨天的 Daily Log
- 这样即使间隔几天，Agent 也能恢复上下文

**3. 时间衰减 + 重要性提取**
- 日志（Daily Log）按日期存储，默认只加载近2天，自动时间衰减
- 在会话结束或压缩时，提取关键信息（用户偏好、重要决策）写入长期记忆
- 长期记忆无时间衰减，每次会话都加载

**具体流程：**
```
用户第1天对话 → 
  关键信息提取 → 写入 MEMORY.md + daily/2026-05-10.md
  会话结束

用户第5天回来 →
  加载 MEMORY.md（长期记忆，包含第1天的偏好）
  加载 daily/2026-05-10.md（最近日志）
  Agent: "我记得您上次提到偏好用Fetch而不是Axios..."
```

⭐ **得分点：**
- 说清楚"日志=近期上下文延续"和"长期记忆=跨时间不变的事实"的区别
- 提到用户隔离的工程实践
- 用具体例子说明跨天场景下的记忆恢复

### Q3.4: 中期记忆变成长期记忆的标准是什么？

**参考答案：**

中期→长期记忆的升级标准，本质上是判断信息的**持久价值**。可以设以下标准：

**1. 被反复引用（频率标准）**
- 同一条信息在3次以上不同会话中被检索/引用
- 说明这不是临时需求，而是用户的长期偏好

**2. 属于"事实性"而非"过程性"信息（性质标准）**
- ✅ 适合长期记忆：用户偏好、技术约定、API配置、架构决策
- ❌ 不适合长期记忆：临时调试过程、中间状态、一次性的bug修复步骤

**3. 跨会话一致性（稳定性标准）**
- 在多次会话中，该信息保持一致，没有变更
- 如果经常变化（如当前进度），应该留在中期记忆

**4. 独立可用性（上下文无关标准）**
- 该信息无需依赖当时的对话上下文就能被理解
- 例如"项目使用Go语言"是独立的；"他说的那个问题"则不是

**工程实现上的具体做法：**
- **LLM判定法**：在上下文压缩时，让LLM判断哪些信息值得持久化，写入MEMORY.md
- **启发式规则**：用户显式说"记住这个"、Agent主动发现冲突时提取
- **定时任务（Heartbeat）**：OpenClaw 的 Dreaming 机制，定期回顾日志，提取值得长期保留的信息

⭐ **得分点：**
- 给出明确的判定标准，不笼统
- 提到LLM判定和规则判定两种实现路径
- 类比后端开发中的数据生命周期管理（热数据→温数据→冷数据）

### Q3.5: 如果变成了长期记忆就一直呆在数据库中吗？

**参考答案：**

不是。长期记忆也需要**生命周期管理**，类比后端的数据冷热分层和GC机制。

**1. 过期淘汰（TTL机制）**
- 某些长期记忆有天然时效：技术栈选择可能半年后变更、API配置可能迁移
- 给长期记忆加元数据：创建时间、最后引用时间、有效期
- 超过有效期或长期未被引用的，降级或归档

**2. 引用计数 + 冷热分离**
- 每次检索命中时更新引用计数和最后引用时间
- 热数据：常驻内存/SSD，快速访问
- 冷数据：归档到对象存储，需要时再加载
- 类比：Redis 的 LRU 淘汰 + 持久化到磁盘

**3. 冲突检测与更新**
- 当新信息与旧记忆冲突时（如用户从React切换到Vue），需要更新而非保留两份
- OpenClaw 的 Dreaming 机制会做冲突检测
- 类比：数据库的 upsert 语义

**4. 用户主动管理**
- OpenClaw 的设计：用户可以直接编辑 MEMORY.md，删掉过时信息
- "AI记错了？直接删掉那行文字即可"
- 透明性：人类可读、可编辑、可版本控制

**5. 定期压缩（Memory Compaction）**
- 类似JVM的GC，定期扫描长期记忆：
  - 合并重复条目
  - 删除过时信息
  - 重组结构，保持精简
- 文件越精简，AI运行越快，推理越精准

⭐ **得分点：**
- 明确回答"不是"，并给出理由
- 类比后端的数据生命周期管理，体现工程思维
- 提到冲突检测这个容易被忽视的问题

## Q4: ReAct的缺陷

### Q4.1: 讲讲ReAct的缺陷

**参考答案：**

ReAct（Reasoning + Acting）是当前最主流的Agent范式，但有明确的缺陷：

**1. 线性执行效率低**
- ReAct是串行的：Think → Act → Observe → Think → ...
- 无法并行处理独立子任务
- 例如："同时查一下A服务和B服务的状态"，ReAct只能一个一个查

**2. 错误累积与雪崩**
- 早期步骤的错误会传播到后续所有步骤
- 没有自动纠错/回溯机制
- 一旦走错方向，后续推理都在错误前提上展开

**3. 上下文窗口膨胀**
- 每步的 Thought + Action + Observation 都留在上下文中
- 复杂任务可能需要20+轮工具调用，迅速耗尽context window
- 虽然有压缩机制，但频繁压缩导致信息损失

**4. 规划能力弱（短期视野）**
- ReAct是"走一步看一步"，缺乏全局规划
- 对于需要多步协调的复杂任务，容易迷失方向
- 没有显式的任务分解和里程碑检查

**5. 固定循环结构僵化**
- 所有任务都走同一套 Think-Act-Observe 循环
- 无法根据任务类型调整策略（如简单查询不需要推理）
- 导致Token浪费：简单问题也生成冗长的Thought

**6. 工具选择的幻觉问题**
- 在工具较多时，模型可能选错工具或编造不存在的工具
- 工具Schema注入占用大量token
- 工具间的选择缺乏置信度评估

### Q4.2: 说说这些缺陷应该如何优化

**参考答案：**

**1. 线性→并行：引入规划器**
- **Plan-and-Execute**：先让LLM做全局规划（分解子任务），再并行执行独立子任务
- **LATS（Language Agent Tree Search）**：树搜索+蒙特卡洛模拟，支持回溯
- 实际案例：Claude Code 的 Sub-Agent 机制，主Agent可以spawn子Agent并行探索

**2. 错误恢复：引入反思与回溯**
- **Reflexion**：执行失败后，让LLM反思失败原因，修正策略再试
- **SWE-Agent**的回溯机制：保存检查点，失败时回退
- 类比：后端的重试+熔断机制

**3. 上下文管理：分层压缩**
- Claude Code 的四层压缩体系（工具结果预算→MicroCompact→AutoCompact→PartialCompact）
- OpenClaw 的 Silent Memory Flush：压缩前持久化关键信息
- 关键：压缩后的摘要必须包含用户原始意图和当前进度

**4. 增强规划能力：分离规划与执行**
- **Plan-then-Execute**：先生成完整计划，再逐步执行
- 动态重规划：执行过程中根据结果更新计划
- Claude Code 的做法：Plan模式 + Todo列表 + 压缩摘要中的"待完成任务"字段

**5. 自适应策略选择**
- 简单查询：直接One-shot回答，不走ReAct
- 中等复杂度：标准ReAct
- 高复杂度：Plan-and-Execute + Sub-Agent
- 类比：后端请求的路由分发，不同类型走不同处理管道

**6. 工具优化：动态工具发现 + 类型安全**
- MCP协议：按需发现工具，而非一次性注入所有Schema
- CLI模式：利用LLM训练数据中的shell知识，减少额外上下文注入
- 工具分组：根据任务阶段只加载相关工具子集

⭐ **得分点：**
- 每个缺陷对应一个具体优化方案
- 引用实际系统（Claude Code / OpenClaw / LATS）作为佐证
- 主动联系后端工程经验（重试/熔断/路由分发）

## Q5: 多智能体拆分

### Q5.1: 哪些场景适合多智能体拆分？

**参考答案：**

多智能体拆分的核心判断标准：**任务是否有天然的职责边界和隔离需求**。

**适合拆分的场景：**

**1. 专业领域分工（技能隔离）**
- 代码生成Agent + 代码审查Agent + 测试Agent
- 不同领域需要不同的System Prompt和工具集
- 避免"全能Agent"的prompt过于臃肿

**2. 异步长任务（时间隔离）**
- 主Agent负责对话，后台Agent执行耗时分析
- Claude Code 的 Sub-Agent：spawn独立Agent做代码探索
- 类比：后端的异步任务队列

**3. 不同权限等级（安全隔离）**
- 只读Agent + 可写Agent + 管理Agent
- 限制高风险操作只在特定Agent中执行
- 类比：后端的最小权限原则

**4. 多渠道接入（通道隔离）**
- OpenClaw 的设计：不同消息通道（微信/飞书/Discord）各自维护会话状态
- 每个通道的格式、限制、用户群体不同

**5. Pipeline式工作流（阶段隔离）**
- 数据采集 → 清洗 → 分析 → 报告生成
- 每个阶段的输入输出格式明确
- 前一阶段失败不阻塞后续独立阶段

**不适合拆分的场景：**
- 简单问答、单步任务（拆分反而增加协调开销）
- 强依赖顺序且需要共享大量上下文的任务

### Q5.2: 拆分带来的优势和问题

**参考答案：**

| 维度 | 优势 | 问题 |
|------|------|------|
| **专业性** | 每个Agent的Prompt更聚焦，行为更精准 | Agent间知识不共享，可能重复劳动 |
| **并行性** | 独立子任务可并行执行，提升效率 | 并发控制复杂，结果合并困难 |
| **安全性** | 权限隔离，最小权限原则 | 权限传递和委托机制复杂 |
| **可维护性** | 单个Agent可独立迭代 | Agent间接口变更影响面大 |
| **上下文** | 每个Agent的上下文更精简 | 上下文共享需要额外机制（消息传递/共享存储） |
| **容错性** | 单个Agent故障不影响其他 | 跨Agent事务的一致性保证困难 |
| **调试** | 问题定位更明确 | 链路追踪跨Agent困难 |

**核心挑战与解法：**

1. **协调开销**：引入Orchestrator Agent（编排者）负责任务分发和结果汇总
2. **上下文共享**：共享记忆存储（如MEMORY.md），或通过消息传递
3. **结果合并**：子Agent返回摘要而非全量结果（Claude Code的做法）
4. **一致性**：定义清晰的Agent间协议（类似微服务的API契约）
5. **调试**：统一的Trace ID贯穿整个调用链

⭐ **得分点：**
- 用表格清晰对比优劣势
- 类比微服务架构的拆分（后端开发者秒懂）
- 主动提到"不是所有场景都适合拆分"

## Q6: RAG文档排版问题

**题目：** 在做RAG的时候如果遇到文档排版混乱，比如双栏排布或者跨页表格这种问题怎么解决？

**参考答案：**

这是RAG落地中最容易忽视但影响最大的问题——**解析质量决定检索上限**。

### 双栏排布问题

**问题本质：** PDF底层是坐标指令，不包含阅读顺序。双栏文档直接提取会左右栏混排。

**解决方案：**

**1. 版面分析（Layout Analysis）**
- 使用MinerU / Unstructured / PaddleOCR进行版面检测
- 识别标题、正文、侧边栏、表格区域
- 按阅读顺序（先左栏再右栏）重排内容

**2. 多模态大模型解析**
- GPT-4V / Qwen-VL 直接理解版面结构
- 成本较高，适合核心业务文档
- 原生理解图文混排

**3. 分层路由策略**
- 简单文档：PyMuPDF（fitz），性价比最高
- 复杂版面：MinerU，开源最优选择之一
- 扫描件：PaddleOCR + 后处理清洗

### 跨页表格问题

**问题本质：** 表格被分页切断，行列关系丢失。

**解决方案：**

**1. 表格整体提取 + Markdown转换**
- 将完整表格转为Markdown格式保留行列关系
- 检索时整个表格作为上下文送给LLM
- 对于超长表格：表头 + 每行数据组合成独立Chunk

**2. 跨页表格合并**
- 检测表格在分页处的连续性（表头重复、列数一致）
- 自动拼接跨页表格
- MinerU / LlamaParse 支持此功能

**3. 元素级JSON输出**
- 使用MinerU的元素层JSON输出，每个元素包含类型、坐标、页码
- 按元素类型过滤（只保留text + table + formula）
- 按坐标关系合并同版块的连续元素

### 通用最佳实践

```python
# 分层解析Pipeline示例
def parse_document(doc_type, file_path):
    if doc_type == "simple_pdf":
        # 简单文档：PyMuPDF
        return parse_with_pymupdf(file_path)
    elif doc_type == "complex_layout":
        # 复杂版面：MinerU
        return parse_with_mineru(file_path, output="markdown")
    elif doc_type == "scanned":
        # 扫描件：OCR + 后处理
        return parse_with_ocr(file_path)
    else:
        # 兜底：多模态LLM
        return parse_with_vlm(file_path)

# 表格专用处理
def handle_table_chunks(table_markdown):
    # 表头 + 每行数据组合，确保每个Chunk含完整上下文
    header = extract_header(table_markdown)
    for row in extract_rows(table_markdown):
        yield f"{header}\n{row}"
```

⭐ **得分点：**
- 强调"解析质量决定检索上限"
- 分层路由策略（不是一把梭）
- 表格处理给出具体的Chunk策略
- 提到MinerU等实际工具名称

## Q7: 文档去重与缓存

### Q7.1: 用户上传文档如何进行文档去重？

**参考答案：**

文档去重需要在**不同粒度**上处理：

**1. 文件级去重 — 哈希指纹**
```
SHA256(文件内容) → 哈希值比对
```
- 完全相同文件：秒级判定
- 缺点：稍微改一个字，哈希完全不同
- 适合：检测完全重复上传

**2. 内容级去重 — MinHash + LSH**
- 对文档进行Shingling（n-gram切分）
- 用MinHash生成签名，将相似文档映射到相同桶
- LSH（Locality Sensitive Hashing）实现近似O(1)的相似度检索
- Jaccard相似度 > 阈值（如0.8）判定为重复
- 适合：检测改了少量内容的"变种文档"

**3. 语义级去重 — 向量相似度**
- 将文档整体Embedding，计算余弦相似度
- 语义相同但措辞不同的文档也能检出
- 成本较高，适合精准去重
- 可先做MinHash粗筛，再向量精排

**4. 段落级去重 — SimHash**
- 对每个段落计算SimHash
- 海明距离 < 阈值（如3）判定为相似段落
- 适合：同一文档不同版本间的增量更新

**工程实践推荐：**
```
上传文档 → SHA256精确去重 → MinHash近似去重 → 向量语义去重
              ↓ 命中              ↓ 命中           ↓ 命中
           直接引用           提示用户确认      合并/替换
```

### Q7.2: 文档更新了，如何同步更新数据库？

**参考答案：**

**1. 变更检测**
- 文档元数据（修改时间、版本号）比对
- 内容哈希对比（SHA256），快速判断是否变更
- 增量检测：只对变更的页面/段落重新处理

**2. 增量更新策略**
```
原始文档: [Chunk1, Chunk2, Chunk3, Chunk4]
更新文档: [Chunk1, Chunk2', Chunk3, Chunk5]

Diff → Chunk2变更(删除旧Chunk2, 插入Chunk2'), Chunk4删除, Chunk5新增
```
- 对每个Chunk计算指纹，只更新变化的Chunk
- 向量库操作：DELETE旧向量 + INSERT新向量（原子操作）

**3. 版本管理**
- 保留历史版本（软删除），支持回滚
- 向量库中标注文档版本号
- 查询时默认返回最新版本

**4. 一致性保证**
- 更新操作使用事务或两阶段提交
- 先写入新数据，再删除旧数据（避免查询空窗期）
- 类比：数据库的在线DDL，不阻塞读

### Q7.3: 做向量缓存如何保证缓存一致性？

**参考答案：**

向量缓存的一致性核心问题：**查询时的Embedding结果与数据库中的向量是否对齐**。

**1. 缓存Key设计**
- Key = Hash(query + embedding_model_version + model_params)
- 模型升级时，旧缓存自动失效（Key不同）
- 避免模型更新后返回语义不匹配的结果

**2. 缓存失效策略**
- **Write-through**：文档更新时同步清除相关缓存
- **TTL过期**：设置合理的过期时间，兜底保证最终一致
- **版本号比对**：缓存中存储文档版本号，查询时比对

**3. 向量与文档的原子更新**
```
更新流程：
1. 生成新向量
2. 写入向量库（新版本）
3. 更新缓存映射（指向新版本）
4. 删除旧版本向量
5. 清除相关查询缓存
```
- 步骤2-5需保证原子性或最终一致性
- 使用版本号实现双写期间的平滑过渡

### Q7.4: 有没有分析过缓存命中率？

**参考答案：**

**缓存命中率分析维度：**

1. **整体命中率**：命中次数 / 总查询次数
   - RAG场景一般 30%-60%（取决于query分布）
   - 低于20%说明缓存策略有问题

2. **分层分析**：
   - 热点查询命中率（高频query，应>80%）
   - 长尾查询命中率（低频query，天然较低）
   - 按时间段分析（工作时间 vs 非工作时间）

3. **命中率的影响因素**：
   - query归一化：同一意图不同表述 → 命中率低
   - 缓存粒度：太粗→误命中，太细→命中率低
   - 缓存容量：LRU容量不足→频繁淘汰

### Q7.5: 怎么优化key提高命中率？

**参考答案：**

**1. Query归一化**
- 去除停用词、标点、空白差异
- 统一大小写、繁简体
- "什么是RAG？" 和 "rag是什么" → 同一Key

**2. 语义Key（而非精确匹配Key）**
- 用query的Embedding向量作为Key
- 查找时用向量相似度而非精确匹配
- 相似query（余弦相似度>0.95）共享缓存

**3. Query意图分类**
- 先对query做意图分类，同一意图共享缓存
- "查A公司的营收" 和 "A公司去年赚了多少" → 同一意图

**4. 分层缓存**
- L1：精确匹配缓存（最快，命中率低）
- L2：语义相似缓存（稍慢，命中率高）
- L3：回源到向量库（最慢，兜底）

**5. 热点预热**
- 分析高频query，主动预热缓存
- 定期刷新热点缓存，避免过期

⭐ **得分点：**
- 三种去重方法（哈希/MinHash/向量）说清适用场景
- 缓存一致性提到模型版本导致的不一致这个隐蔽问题
- 语义Key和分层缓存体现工程深度

## Q8: CLI与MCP对比

**题目：** 有没有了解过CLI与MCP相比有什么不同？

**参考答案：**

CLI和MCP是AI Agent工具调用的两种范式，核心差异是**设计目标不同**：

### 核心定位差异

| 维度 | CLI | MCP |
|------|-----|-----|
| **设计目标** | 面向人类交互 | 面向AI Agent结构化交互 |
| **通信协议** | 文本流（stdin/stdout/stderr） | JSON-RPC 2.0 |
| **数据格式** | 纯文本（带颜色/表格） | 结构化JSON + Schema |
| **进程模型** | 短生命周期（每次命令新进程） | 长生命周期（Server持久运行） |
| **状态管理** | 无状态 | 有状态（会话、缓存、连接池） |
| **Token开销** | 极低（未调用时几乎为零） | 高（需预加载工具Schema） |
| **发现机制** | SKILL.md / AGENTS.md | tools/list 标准发现协议 |
| **安全性** | 命令注入风险 | 结构化输入 + 权限控制 |

### 关键差异详解

**1. Token效率（CLI碾压MCP）**
- CLI：只在执行后产生输出，未调用时token消耗≈0。LLM训练数据中已包含海量shell命令，几乎零额外上下文
- MCP：每次对话需注入所有工具Schema，50个工具可能消耗上万token
- 据ScaleKit基准测试，MCP比CLI贵10-32倍

**2. 可组合性（CLI天然优势）**
- CLI支持管道组合：`log-fetch | grep "ERROR" | feishu-send`
- MCP需要模型或上层编排逻辑实现组合

**3. 标准化（MCP优势）**
- MCP有统一的工具发现、调用、结果处理协议
- CLI缺乏标准，不同工具接口差异大

**4. 状态管理（MCP优势）**
- MCP Server持久运行，可维护连接池、缓存、会话
- CLI每次命令是新进程，无法保持状态

### 实际选型建议

- **选CLI**：已有成熟CLI工具、高性能低延迟场景、资源受限环境
- **选MCP**：全新工具需要标准化接口、复杂状态管理、跨平台一致性要求
- **混合方案**：MCP包装CLI工具，兼容现有生态 + 提供统一接口

⭐ **得分点：**
- 说清"面向人"vs"面向AI"的根本差异
- Token效率对比有数据支撑
- 给出混合方案，体现工程务实

## Q9: OpenClaw与Claude Code底层

### Q9.1: 有没有了解过OpenClaw和Claude Code的底层？

**参考答案：**

都了解过。两者是同一时代但定位完全不同的Agent系统：

- **Claude Code**：Anthropic官方的CLI编程Agent，绑定单个仓库会话，短生命周期进程
- **OpenClaw**：开源多通道个人助手网关，持久WebSocket守护进程，支持25+消息渠道

底层技术栈高度一致：Node.js + TypeScript，都是ReAct循环，都使用SKILL.md技能系统。

### Q9.2: 你讲讲OpenClaw的agent架构是什么？

**参考答案：**

OpenClaw的架构是一个**嵌入网关的Agent运行时**：

**核心架构：四层 + 心跳**

```
┌─────────────────────────────┐
│   Channel Layer（通道层）     │  WhatsApp/Discord/微信/飞书...
├─────────────────────────────┤
│   Gateway Layer（网关层）     │  WebSocket网关，消息路由，会话管理
├─────────────────────────────┤
│   Agent Runtime（运行时层）   │  Pi-agent Runner，ReAct循环
├─────────────────────────────┤
│   Memory Layer（记忆层）      │  MEMORY.md + Daily Logs + 混合检索
└─────────────────────────────┘
```

**Agent执行循环：**
- 本质是ReAct：LLM推理 → 工具调用 → 观察结果 → 继续推理
- 通过JSON Schema描述工具，LLM输出结构化的tool_use请求
- 运行时解析、执行、将结果格式化喂回

**关键设计：**
- **多通道路由**：不同渠道的消息通过SessionKey路由到正确的Agent
- **子Agent委派**：`sessions_spawn` 创建隔离的子Agent处理耗时任务
- **ACP协议**：可将任务交给专业Agent（如Claude Code）执行
- **插件系统**：Manifest优先，12类能力，中央注册表

### Q9.3: 为什么OpenClaw用ReAct就可以，而Claude Code使用了比较复杂的架构？

**参考答案：**

这是因为两者的**部署环境和任务复杂度**完全不同：

**OpenClaw — 简单ReAct够用的原因：**
1. **任务相对简单**：个人助手场景（发消息、设提醒、查信息），3-5轮工具调用通常完成
2. **单次对话短**：不会产生几十轮的深度推理
3. **用户在环**：每步都可以等人确认，出错可即时纠正
4. **多通道隔离**：每个通道独立会话，不会出现超长对话
5. **网关控制平面**：安全和路由由网关层处理，Agent本身不需要复杂机制

**Claude Code — 必须复杂架构的原因：**
1. **任务深度大**：代码重构可能涉及几十个文件、上百次工具调用
2. **超长对话**：一个复杂任务可能跑几小时，需要四层压缩机制
3. **安全要求极高**：代码修改直接影响生产系统，需要7种权限模式 + ML分类器
4. **自治性强**：很多步骤没有人在环确认，必须靠架构约束
5. **上下文管理挑战大**：大量文件读写、grep结果、错误日志，必须精细管理

**一句话总结：** OpenClaw是"轻量网关+简单推理"，Claude Code是"重度编排+深度推理"。就像Web服务 vs 数据库系统，前者请求-响应就够，后者需要WAL、MVCC、查询优化器。

### Q9.4: 讲讲OpenClaw的记忆模式？

**参考答案：**

OpenClaw采用**文件优先的透明记忆架构**，核心原则：**模型只"记住"被写入磁盘的内容**。

**三层记忆：**

| 层级 | 文件 | 用途 | 加载时机 |
|------|------|------|----------|
| 短期 | `memory/YYYY-MM-DD.md` | 每日日志，记录当天决策和关键对话 | 会话启动时加载今天+昨天 |
| 长期 | `MEMORY.md` | 用户偏好、重要决策、项目约定 | 每次主会话启动 |
| 身份 | `SOUL.md` + `USER.md` + `AGENTS.md` | Agent人格、用户信息、行为规范 | 每次会话启动 |

**核心创新：**

**1. Silent Memory Flush（静默记忆刷新）**
- 当对话接近压缩阈值时，系统先发一条静默指令
- "请迅速把对话中最重要的信息写入MEMORY.md，动作快，别回话"
- 用户无感知，关键信息已安全落地到磁盘
- 每次压缩周期只刷新一次，避免垃圾信息

**2. 混合检索（Vector 70% + BM25 30%）**
- 向量搜索：语义相关但措辞不同（"Mac主机"→"运行macOS的电脑"）
- BM25关键词：精确匹配API名、变量名等
- 加权融合防止任一方法占主导

**3. 文件即事实（File-as-Truth）**
- 人类可直接编辑Markdown文件修改AI记忆
- 可版本控制、可备份、可迁移
- 无供应商锁定

### Q9.5: 你看过Claude Code源码，你讲讲它是如何写prompt的？

**参考答案：**

Claude Code的Prompt不是一段静态字符串，而是**六层优先级动态组装的Prompt Runtime**：

**六层优先级架构：**
```
优先级1: Override Prompt（完全替换，如Simple Mode）
优先级2: Coordinator Prompt（多智能体协调）
优先级3: Agent Prompt（子智能体模式）
优先级4: Custom Prompt（用户 --system-prompt 注入）
优先级5: Default Prompt（7个核心Section）
优先级6: Append Prompt（动态环境信息）
```
高层级完全替换低层级，而非简单拼接——这种"替换优于修改"原则避免了Prompt臃肿。

**缓存边界设计：**
```
可缓存前缀（静态层）:
  - 身份定义 "You are Claude Code"
  - 工具使用规则和安全边界
  - 行为约束（反范围蔓延/反过度防御/反过早抽象）

缓存边界: <|cache_boundary|>

会话特定后缀（动态层）:
  - 工作目录、平台、Shell信息
  - 语言偏好、输出风格
  - MCP工具指令
```
静态层命中Prompt Cache，跨会话复用，显著降低token成本和延迟。

**行为指令的精确编码（不是泛泛的"请认真工作"）：**

1. **反范围蔓延**：Don't add features, refactor code beyond what was asked
2. **反过度防御**：Don't add error handling for scenarios that can't happen
3. **反过早抽象**：Three similar lines of code is better than a premature abstraction
4. **数值化长度锚定**：keep text between tool calls to ≤25 words（研究显示比定性描述"简洁"减少1.2%输出token）

**U型注意力曲线利用：**
- 开头：身份定义 + 安全红线 + 工具路由规则（Primacy Effect）
- 中间：详细工作流和工具参数定义（可遗忘区）
- 结尾：重复关键规则 "Remember: Use Read instead of cat..."（Recency Effect）

### Q9.6: Claude Code做了什么优化保证了它在多轮对话下能做到任务不丢？

**参考答案：**

这是Claude Code最核心的工程能力，靠的是**四层压缩 + 结构化摘要 + 状态恢复**的组合拳：

**1. 四层渐进压缩体系**

| 层级 | 机制 | 成本 | 触发条件 |
|------|------|------|----------|
| L1 | 工具结果预算 | 零 | 单个工具返回超限 |
| L2 | MicroCompact | 零 | 每次API调用前自动执行 |
| L3 | AutoCompact | 一次LLM调用 | 上下文到78%阈值 |
| L4 | PartialCompact | 一次LLM调用 | 用户手动触发 |

- 优先用零成本方案，不到万不得已不调用LLM压缩
- 熔断机制：连续3次压缩失败→停止自动压缩，避免死循环

**2. 九章节结构化摘要（核心）**

AutoCompact不是简单截断，而是用LLM生成9个章节的摘要：
1. 用户主要请求与目标
2. 关键技术/业务概念
3. 涉及文件/数据/标的
4. 遇到的错误与修复
5. 任务执行过程
6. **用户所有原始消息**（最关键！）
7. **待完成任务**
8. **当前正在做什么**（含文件名和代码片段）
9. **下一步计划**（引用最近对话原文）

压缩提示词极其强硬：
```
CRITICAL: 只输出文字！不许调用任何工具！
Do NOT use Read/Bash/Grep/Edit！
Tool calls will be REJECTED！
You have only ONE turn！
```
这样设计是为了复用主Agent的System Prompt + 工具列表，命中Prompt Cache，几万token几乎免费。

**3. 压缩后状态恢复**

压缩完成后，系统自动注入：
- 最近5个文件（每个最多5000 token）
- Todo列表（任务状态）
- Plan文件（如果处于plan模式）
- Hook结果

这保证AI"不丢"——压缩后立刻知道刚才在看什么文件、做到哪一步了。

**4. 会话记忆持久化**

即使整个会话结束：
- 用户偏好、规则、关键事实自动提取存入独立文件
- 下次会话自动注入
- 类比：后端的Session持久化 + 冷启动恢复

⭐ **得分点：**
- 四层压缩从零成本到有成本的渐进设计
- 九章节摘要的具体内容（尤其"用户所有原始消息"和"下一步"）
- 压缩后文件恢复这个关键设计
- 类比后端系统的WAL、检查点机制
