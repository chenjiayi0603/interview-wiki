# C++ 在实时系统中的挑战

## 5.1 动态内存分配

| 问题         | 说明                                               |
|--------------|----------------------------------------------------|
| **非确定性** | `malloc` / `new` 耗时依赖堆状态、碎片、锁，不可预测 |
| **锁与竞争** | 堆实现常用全局锁，多线程分配会相互阻塞             |
| **碎片与 compaction** | 长期运行可能触发 coalescing 等，造成延迟尖峰 |
| **失败处理** | `new` 默认抛异常，异常在实时代码中往往不受欢迎     |

因此，**实时关键路径上应避免 `new`/`delete` 和 `malloc`/`free`**；若必须用，应在初始化阶段完成，或使用自定义池化分配器。

## 5.2 异常与 RTTI

- **异常**：栈展开、查找 catch 等开销难以约束，且可能打断控制流，不利于确定性分析。  
- **RTTI**：`typeid`、`dynamic_cast` 增加运行时开销与二进制体积。  

许多实时/安全规范（如 MISRA C++、某些车载/航空标准）在**关键子系统中禁用异常和 RTTI**。  
若使用 C++，通常采用 **「无异常、无 RTTI」** 的子集，并通过静态分析或编译选项强制落实。

## 5.3 标准库与第三方库

- **STL 容器**（`vector`、`map` 等）：  
  - 扩容、插入可能 `malloc`；  
  - 实现细节（如 `std::string` 的 COW、SSO）因实现和版本而异，可能引入额外不确定性。  
- **iostream**、复杂算法等：可能锁、缓冲、系统调用，不适合在实时路径使用。  

**实践**：  
- 实时路径避免直接使用可能分配或加锁的 STL/第三方 API；  
- 若用，需明确其行为（如 `reserve` 预分配、自定义 allocator），并在非实时阶段完成所有可能分配的操作。

## 5.4 系统调用与阻塞

- 许多 **Linux 系统调用**（如 `read`/`write`、`futex`）可能阻塞；  
- 阻塞会导致调度延迟、优先级反转等，违背「短时、可预测」的实时假设。  

**建议**：  
- 实时关键路径尽量避免阻塞式系统调用；  
- 若必须 I/O，使用非阻塞 + 轮询或独立实时安全通道，或把 I/O 放到非实时线程，通过无锁/锁无关结构与实时线程交互。

## 5.5 编译器与链接时优化

- **-O2/-O3**：提高性能，但代码变换可能增大最坏情况执行时间（WCET）分析的难度。  
- **LTO**：有助于性能，但增加编译时间与工具链复杂度。  
- **-Os**：更小代码体积，有时对 I-cache 友好，可能减少某些场景的抖动。  

实时系统常在 **性能、确定性、可分析性** 之间权衡；有的项目对关键模块使用 **-O2** 并禁用某些激进优化，以便与 WCET 工具配合。
