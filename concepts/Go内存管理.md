# Go内存管理

## 内存逃逸

**逃逸分析**：
- 编译期分析，决定变量分配在栈还是堆
  - **关键点**：这是编译期优化，不是运行期分析，通过静态分析确定变量的生命周期
- 查看逃逸：`go build -gcflags=-m`
  - **调优工具**：通过分析逃逸情况可以优化代码，尽量减少堆分配
- **示例**：对 `func f() *int { x:=1; return &x }` 执行 `go build -gcflags="-m -m"` 输出：
  ```
  ./main.go:3:6: x escapes to heap:
  ./main.go:3:6:   moved to heap: x
  ```

**常见逃逸场景**：
1. **指针逃逸**：局部变量返回指针，函数外部引用
2. **interface{}逃逸**：动态类型，编译期无法确定
3. **栈空间不足**：大对象(如大切片)超出栈限制
4. **slice扩容**：append导致容量变大，重新分配
5. **channel发送指针**：不知道何时被释放
6. **闭包引用**：闭包捕获外部变量

**完整可运行示例（用于逃逸分析）**：
```go
package main

import "fmt"

func newInt() *int { x := 1; return &x } // 1. 指针逃逸：x 逃逸到堆

func printVal() {
	x := 42
	fmt.Println(x) // 2. interface{} 逃逸：x 作为 interface{} 传入
}

func bigSlice() {
	buf := make([]byte, 64*1024) // 3. 栈空间不足：64KB 切片逃逸到堆
	_ = buf
}

func appendSlice() {
	s := []int{}
	s = append(s, 1, 2, 3) // 4. slice 扩容：底层数组可能逃逸
	_ = s
}

func sendPtr(ch chan *int) {
	x := 1
	ch <- &x // 5. channel 发送指针：x 逃逸
}

func closure() {
	x := 0
	go func() { x++ }() // 6. 闭包引用：x 被闭包引用，逃逸
}

func main() {
	n := newInt()
	printVal()
	bigSlice()
	appendSlice()
	ch := make(chan *int)
	go sendPtr(ch)
	<-ch
	closure()
	_ = n
}
```

**查看逃逸**：在项目目录执行 `go build -gcflags="-m -m" . 2>&1 | grep escape`，可看到各变量逃逸到堆的说明。

**逃逸影响**：
- 堆分配比栈分配慢，增加GC压力
  - **性能影响**：堆分配需要调用malloc，还需要GC管理，比栈分配慢很多
  - **示例**：热点循环中 `return &x` 导致每次调用都堆分配+GC标记，性能下降
- 小对象传值可能比传指针更高效(避免逃逸)
  - **优化技巧**：对于小对象(如int、string、小结构体)，传值可能比传指针更快，因为可以避免逃逸
  - **示例**：`func process(u User)` 传值，u在栈上；`func process(u *User)` 可能使u逃逸

## 垃圾回收

**三色标记法**：
1. 初始所有对象为白色
   - **初始状态**：GC开始时，所有对象都是白色(未标记)
   - **示例**：假设有对象A→B→C，初始A/B/C均为白色
2. 从根对象开始，可达对象标记为灰色
   - **根对象**：全局变量、栈上的变量、寄存器中的变量等
   - **示例**：根引用A，A变为灰色，灰色队列=[A]
3. 从灰色对象队列取出，引用的对象标记为灰色，自身标记为黑色
   - **标记过程**：灰色表示待处理，黑色表示已处理且引用的对象都已标记
   - **示例**：取出A，A引用的B变灰，A变黑；取出B，B引用的C变灰，B变黑
4. 重复直到灰色队列为空
   - **终止条件**：灰色队列为空表示所有可达对象都已标记为黑色
   - **示例**：C变黑后灰色队列空，标记结束，A/B/C均为黑色
5. 回收白色对象
   - **回收**：白色对象是不可达的，可以安全回收
   - **示例**：假设还有对象D无引用，D仍为白色，被回收

**写屏障**：
- **插入写屏障**：黑色对象引用白色对象时，白色对象变灰
  - **问题**：需要栈的重新扫描，STW时间长
  - **示例**：标记中A已黑，后执行`A.ref = B`(B白)，插入屏障将B标灰
- **删除写屏障**：删除引用时，被删除对象变灰
  - **问题**：会产生浮动垃圾，但可以增量标记
  - **示例**：`A.ref = nil`删除对B的引用，删除屏障将B标灰(可能已不可达，形成浮动垃圾)
- **混合写屏障(Go 1.8+)**：
  - GC开始扫描栈并标记为黑色
    - **优化**：栈扫描一次即可，不需要重新扫描
  - GC期间栈上新对象为黑色
    - **假设**：假设栈上的对象都是可达的，简化处理
  - 被删除/添加的对象标记为灰色
    - **保证**：确保所有可达对象都能被标记到
  - 避免栈的重新扫描，STW时间<1ms
    - **重大改进**：这是Go GC的重要优化，大幅减少了STW时间
  - **示例**：`obj.field = newVal` 时，newVal标灰；栈上对象直接标黑，无需二次扫描

**GC优化**：
- 减少逃逸，对象尽量在栈上分配
  - **最佳实践**：通过逃逸分析，尽量让对象在栈上分配，减少GC压力
  - **示例**：小结构体传值 `func f(u User)` 不逃逸；传指针 `func f(u *User)` 可能逃逸
- 使用对象池(sync.Pool)复用对象
  - **适用场景**：频繁创建和销毁的对象，如临时buffer、连接等
  - **示例**：`var bufPool = sync.Pool{New: func() any { return make([]byte, 4096) }}`
- 避免频繁创建大对象
  - **注意**：大对象会直接分配在大对象堆上，GC标记成本高
  - **示例**：循环内 `buf := make([]byte, 1<<20)` 每次1MB，改用Pool或复用
