# MySQL 主从复制

> 本文档系统梳理 MySQL 主从复制的核心原理与流程，涵盖**异步复制、传统半同步复制、增强半同步（无损复制）**三种模式的区别、实现机制与流程图。

---

## 一、MySQL 主从复制基础架构

### 1.1 核心组件

```
┌─────────────────────────────────┐     ┌─────────────────────────────────┐
│          Master (主库)           │     │           Slave (从库)            │
│                                 │     │                                 │
│  ┌───────────────────────────┐  │     │  ┌───────────────────────────┐  │
│  │     Client 事务提交        │  │     │  │        客户端读请求        │  │
│  └───────────┬───────────────┘  │     │  └───────────────────────────┘  │
│              │                  │     │                                 │
│  ┌───────────▼───────────────┐  │     │  ┌───────────────────────────┐  │
│  │  Binlog (二进制日志)       │  │     │  │     Relay Log (中继日志)   │  │
│  │  mysql-bin.000001         │  │     │  │     relay-bin.000001       │  │
│  └───────────┬───────────────┘  │     │  └───────────▲───────────────┘  │
│              │                  │     │              │                  │
│  ┌───────────▼───────────────┐  │     │  ┌───────────┴───────────────┐  │
│  │  Dump Thread (推送线程)    ├──┼──┬──┼──►  I/O Thread (IO线程)      │  │
│  │  每个从库对应一个Dump线程   │  │     │  │  拉取并写入Relay Log       │  │
│  └───────────────────────────┘  │     │  └───────────┬───────────────┘  │
│                                 │     │              │                  │
│                                 │     │  ┌───────────▼───────────────┐  │
│                                 │     │  │  SQL Thread (SQL线程)      │  │
│                                 │     │  │  解析Relay Log并重放事件    │  │
│                                 │     │  └───────────┬───────────────┘  │
│                                 │     │              │                  │
│                                 │     │  ┌───────────▼───────────────┐  │
│                                 │     │  │     Slave DB (从库数据库)  │  │
│                                 │     │  └───────────────────────────┘  │
└─────────────────────────────────┘     └─────────────────────────────────┘
```

### 1.2 主从复制三步走

| 步骤 | 线程 | 位置 | 功能 |
|------|------|------|------|
| ① **Binlog 产生** | - | 主库 | 事务提交时将数据变更写入 Binlog |
| ② **日志传输** | Dump Thread → I/O Thread | 主库→从库 | 主库 Dump 线程推送/从库 IO 线程拉取 Binlog 事件 |
| ③ **日志重放** | SQL Thread | 从库 | 从库 SQL 线程解析 Relay Log 并执行 SQL |

### 1.3 Binlog 三种格式

| 格式 | 记录内容 | 优点 | 缺点 |
|------|---------|------|------|
| **STATEMENT** | SQL 语句本身 | 日志量小 | 部分语句（如 UUID()）导致主从不一致 |
| **ROW** | 每行数据的变化 | 精确，保证一致 | 日志量大（UPDATE 全表则非常恐怖） |
| **MIXED** | 混合以上两种 | 折中方案 | 不够纯粹，排查困难 |

> **生产推荐**：ROW 格式，保证数据一致性。

## 二、MySQL 传统主从同步流程图（异步复制）

### 2.1 异步复制流程

```
                   主库 (Master)                          从库 (Slave)
               ┌───────────────────┐             ┌───────────────────┐
               │                   │             │                   │
   ① 客户端提交事务                │             │                   │
      ┌──────▼──────┐             │             │                   │
      │ 执行 DML SQL  │             │             │                   │
      └──────┬──────┘             │             │                   │
             │                    │             │                   │
   ②   ┌────▼─────┐              │             │                   │
       │写 redo log │ (prepare)    │             │                   │
       └────┬─────┘              │             │                   │
            │                    │             │                   │
   ③   ┌────▼─────┐              │             │                   │
       │ 写 Binlog  │ ◄───────────┼──── 两阶段提交                │
       └────┬─────┘              │             │                   │
            │                    │             │                   │
   ④   ┌────▼─────┐              │             │                   │
       │ redo log  │ (commit)     │             │                   │
       └────┬─────┘              │             │                   │
            │                    │             │                   │
   ⑤   ┌────▼─────┐              │             │                   │
       │ 返回客户端 │ 成功         │             │                   │
       └────┬─────┘              │             │                   │
            │                    │             │                   │
            │ ⑥ 主库 Dump Thread  │             │                   │
            │    推送 Binlog 事件  │─────────────┼──►  ⑦ 从库 I/O Thread  │
            │                    │             │      接收并写入       │
            │                    │             │      Relay Log      │
            │                    │             │          │          │
            │                    │             │          ▼          │
            │                    │             │  ⑧ SQL Thread 重放  │
            │                    │             │          │          │
            │                    │             │          ▼          │
            │                    │             │  ⑨ 写入 SlaveDB     │
            │                    │             │                   │
               └───────────────┘             └───────────────────┘
```

### 2.2 关键特点

```
┌────────────────────────────────────────────────────────────────┐
│                      异步复制特点                                │
├────────────────────────────────────────────────────────────────┤
│ ① 主库提交事务后【立即返回】客户端，不等待从库                     │
│ ② Dump Thread 是【异步推送】：主库写 Binlog 后异步发往从库        │
│ ③ 主库故障时，未传输的 Binlog【永久丢失】                         │
│ ④ 从库延迟独立于主库压力，Seconds_Behind_Master 可能较大          │
│ ⑤ 性能最好，主库 TPS 几乎不受从库影响                            │
└────────────────────────────────────────────────────────────────┘
```

### 2.3 异步复制的问题

```
时间线：主库持续写入，Binlog 不断产生
──────────────────────────────────────────────►
  [T1] [T2] [T3] [T4] [T5] [T6] [T7] [T8] ...

  此时从库已同步到 T4：
  ✓ T1 ✓ T2 ✓ T3 ✓ T4

  主库在 T7 时刻宕机     ✗ T5 ✗ T6 ✗ T7
                          ▲
                   ┌──────┴──────┐
                   │  数据丢失！   │
                   │ T5/T6/T7 的  │
                   │ 数据永久丢失  │
                   └─────────────┘
```

## 三、MySQL 传统半同步复制流程图

### 3.1 什么是半同步复制

MySQL 5.5 引入半同步复制（Semi-Synchronous Replication），核心思想：

> **主库提交事务前，必须等待至少一个从库确认收到 Binlog，但不等待从库执行完毕。**

### 3.2 传统半同步复制流程（AFTER_COMMIT）

```
                   主库 (Master)                          从库 (Slave)
               ┌───────────────────┐             ┌───────────────────┐
               │                   │             │                   │
   ① 客户端提交事务                │             │                   │
             │                    │             │                   │
   ② ┌──────▼──────┐              │             │                   │
      │ 执行 DML     │              │             │                   │
      └──────┬──────┘              │             │                   │
             │                    │             │                   │
   ③ ┌──────▼──────┐              │             │                   │
      │ Redo Log    │ (Prepare)    │             │                   │
      │ Prepare     │              │             │                   │
      └──────┬──────┘              │             │                   │
             │                    │             │                   │
   ④ ┌──────▼──────┐              │             │                   │
      │ 写入 Binlog  │              │             │                   │
      └──────┬──────┘              │             │                   │
             │                    │             │                   │
   ⑤ ┌──────▼──────┐              │             │                   │
      │ Redo Log    │ (Commit)     │             │                   │
      │ 引擎层提交    │◄──── 关键！ │             │                   │
      └──────┬──────┘  先在引擎层提交          │                   │
             │         (AFTER_COMMIT)        │                   │
             │                    │             │                   │
   ⑥ ┌──────▼──────────────────────────────────────┐              │
      │  等待从库 ACK (确认收到 Binlog)               │              │
      │  ┌──────────────────────────┐               │              │
      │  │ rpl_semi_sync_master_     │               │              │
      │  │ timeout = 10000ms (默认)   │               │              │
      │  │ 超时则降级为异步           │               │              │
      │  └──────────────────────────┘               │              │
      └──────┬──────────────────────────────────────┘              │
             │                                                    │
             │ ⑦ 发送 Binlog 事件 ─────────────────►  ⑧ 从库 I/O Thread  │
             │                                      接收 Binlog       │
             │                                        │              │
             │                              ┌────────▼───────────┐  │
             │                              │  写入 Relay Log     │  │
             │                              │  (不等待 SQL 线程)  │  │
             │                              └────────┬───────────┘  │
             │                                      │              │
             │ ⑨   ◄───────────────── ACK (确认收到)               │
             │                                      │              │
   ⑩ ┌──────▼──────┐              │             │                   │
      │ 返回给客户端  │ 成功          │             │                   │
      └─────────────┘              │             │                   │
               │                   │             │  ⑪ SQL Thread   │
               │                   │             │     异步重放      │
               │                   │             │     写入 SlaveDB │
               └───────────────┘             └───────────────────┘
```

### 3.3 AFTER_COMMIT 的关键缺陷

传统半同步采用 **AFTER_COMMIT** 模式，存在数据可见性问题：

```
时间线分析（主库宕机场景）：

  T1: 主库 Redo Log Prepare ✓
  T2: 主库写入 Binlog     ✓
  T3: 主库 Redo Log Commit ✓  ◄── 引擎层已提交！
  T4: 主库等待从库 ACK ...
  ──── 主库宕机！─────────── ✗  此时主库引擎层已提交，数据对其他会话可见

  如果从库还没收到 Binlog（未发 ACK），原主库上的事务数据在从库上是没有的。

  故障切换后：
  - 原先在主库上已提交的事务 ← 丢失！
  - 客户可能已经读到数据并做了后续操作 ← 数据不一致！

  ┌─────────────────────────────────────────────────────────────┐
  │  AFTER_COMMIT 问题：                                         │
  │  主库在引擎层提交后、但从库尚未收到 Binlog 时宕机，           │
  │  导致主库"已提交"但从库"未收到"的数据丢失。                  │
  │  数据不一致风险：客户端在主库读到了已提交数据，切换后读不到。 │
  └─────────────────────────────────────────────────────────────┘
```

### 3.4 传统半同步的降级策略

```
主库等待从库 ACK
       │
       ├── 在 rpl_semi_sync_master_timeout 时间内收到 ACK
       │      └── 正常提交，返回客户端成功
       │
       └── 超时未收到 ACK
              └── 自动降级为【异步复制】
                    └── 状态变量 Rpl_semi_sync_master_status = OFF
                    └── 等到从库恢复后，再自动切回半同步
```

## 四、MySQL 主从无损复制流程图（增强半同步）

### 4.1 AFTER_SYNC 无损复制原理

MySQL 5.7 引入增强半同步复制（Lossless Semi-Sync Replication），采用 **AFTER_SYNC** 模式：

> **主库在写入 Binlog 后、引擎层提交前等待从库 ACK。只有收到 ACK 后，才进行引擎层提交。**

```
参数配置：
  rpl_semi_sync_master_wait_point = AFTER_SYNC   -- 默认值（MySQL 5.7.2+）
  rpl_semi_sync_master_wait_point = AFTER_COMMIT -- 传统模式
```

### 4.2 增强半同步（无损复制）完整流程

```
                   主库 (Master)                          从库 (Slave)
               ┌───────────────────┐             ┌───────────────────┐
               │                   │             │                   │
   ① 客户端提交事务                │             │                   │
             │                    │             │                   │
   ② ┌──────▼──────┐              │             │                   │
      │ 执行 DML     │              │             │                   │
      └──────┬──────┘              │             │                   │
             │                    │             │                   │
   ③ ┌──────▼──────┐              │             │                   │
      │ Redo Log    │ (Prepare)    │             │                   │
      │ 写入并刷盘   │              │             │                   │
      └──────┬──────┘              │             │                   │
             │                    │             │                   │
   ④ ┌──────▼──────┐              │             │                   │
      │ 写入 Binlog  │              │             │                   │
      │ 并刷盘       │              │             │                   │
      └──────┬──────┘              │             │                   │
             │                                    │                   │
             │         ★ 关键差异 ★               │                   │
             │    此时 Redo Log 只是 Prepare       │                   │
             │    引擎层尚未提交！！！               │                   │
             │                                    │                   │
             │ ⑤ 发送 Binlog ──────────────────►   │                   │
             │                                    │                   │
   ⑥ ┌──────▼──────────────────────────┐         │                   │
      │  等待从库 ACK (AFTER_SYNC 等待点)│         │                   │
      │                                 │         │                   │
      │  如果所有从库都超时：             │         │                   │
      │    → 降级为异步，引擎层提交       │         │                   │
      │    → rpl_semi_sync_master_       │         │                   │
      │      timeout 默认 10000ms       │         │                   │
      └──────┬──────────────────────────┘         │                   │
             │                                    │                   │
             │                      ⑦  I/O Thread 接收 Binlog          │
             │                      ⑧  写入 Relay Log                  │
             │                      ⑨  发送 ACK ◄──────────────────   │
             │                                    │                   │
   ⑩ ┌──────▼──────┐              │             │                   │
      │ 收到 ACK     │              │             │                   │
      │ Redo Log    │ (Commit)     │             │                   │
      │ 引擎层正式提交 │              │             │                   │
      └──────┬──────┘              │             │                   │
             │                    │             │                   │
   ⑪ ┌──────▼──────┐              │             │                   │
      │ 返回给客户端  │ 成功          │             │                   │
      └─────────────┘              │             │                   │
               │                   │             │  ⑫ SQL Thread   │
               │                   │             │     异步重放      │
               │                   │             │     写入 SlaveDB │
               └───────────────┘             └───────────────────┘
```

### 4.3 AFTER_SYNC vs AFTER_COMMIT 核心区别

```
            AFTER_COMMIT (传统半同步)           AFTER_SYNC (增强半同步/无损)

数据写入流程：
            ┌─────────────────┐               ┌─────────────────┐
            │  Redo Prepare    │               │  Redo Prepare    │
            │       ↓          │               │       ↓          │
            │  Write Binlog    │               │  Write Binlog    │
            │       ↓          │               │       ↓          │
            │  Redo Commit ✓   │               │  等从库 ACK ...   │
            │  (引擎层已提交)    │               │       ↓          │
            │       ↓          │               │  Redo Commit ✓   │
            │  等从库 ACK ...   │               │  (收到ACK后提交)  │
            │       ↓          │               │       ↓          │
            │  返回客户端成功    │               │  返回客户端成功    │
            └─────────────────┘               └─────────────────┘

ACK等待点位：
            在引擎层提交【之后】                 在引擎层提交【之前】

主库宕机后果：
            ┌─────────────────────────┐         ┌─────────────────────────┐
            │ 主库已提交的T5/T6/T7     │         │ 从库没收到Binlog的事务    │
            │ 从库未收到 → 数据丢失    │         │ 主库也【未提交】→ 无丢失  │
            │ 其他会话可能已读到T5    │         │ 所有会话都看不到T5       │
            └─────────────────────────┘         └─────────────────────────┘

数据安全性：
            ★★☆☆☆                             ★★★★★
            可能丢已提交数据                     保证至少一个从库有数据
```

### 4.4 无损复制的核心保障

```
故障切换场景验证：

  场景：主库在等ACK时宕机
  ┌────────────────────────────────────────────────────────────────┐
  │                                                                │
  │   T1: 主库写入 Binlog (事务 T)                                  │
  │   T2: 主库 Redo Log 状态 = Prepare (引擎层未提交！)              │
  │   T3: 主库发 Binlog 给从库                                     │
  │   T4: 从库收到 Binlog，写入 Relay Log                           │
  │   T5: 从库发送 ACK 给主库                                      │
  │   ─── 主库在收到ACK前宕机 ───  (ACK在网络中丢失或尚未发送)     │
  │                                                                │
  │   故障切换后：                                                  │
  │   ├─ 从库有事务 T 的 Binlog/Relay Log                           │
  │   ├─ 主库引擎层事务 T 未提交 (Prepare 状态)                     │
  │   ├─ 新主(从库晋升) 事务 T 可正常提交                            │
  │   └─ 结论：数据零丢失！✓                                        │
  │                                                                │
  └────────────────────────────────────────────────────────────────┘
```

## 五、三种复制模式对比总结

### 5.1 全量对比表

| 维度 | 异步复制 | 传统半同步 (AFTER_COMMIT) | 增强半同步/无损 (AFTER_SYNC) |
|------|---------|--------------------------|------------------------------|
| **ACK 等待点** | 不等 | Redo Commit 之后等 | Redo Commit 之前等 |
| **主库提交时机** | 立即提交 | 立即提交（不等ACK） | 等ACK后再提交 |
| **性能影响** | 无影响 | 中等（网络RTT） | 中等（网络RTT） |
| **数据丢失风险** | 有，丢失所有未传输Binlog | 有，丢失引擎层已提交但未ACK的事务 | 几乎为零 |
| **主从延迟** | 可能较大 | 较小 | 较小 |
| **引入版本** | 所有版本 | MySQL 5.5 | MySQL 5.7.2+ |
| **适用场景** | 读扩展、报表、备份 | 对一致性有要求但可容忍少量丢失 | **金融、交易等强一致场景** |
| **主库宕机时** | 可能大量丢数据 | 可能丢少量已提交数据 | **数据零丢失** |

### 5.2 性能影响分析

```
                    异步复制              增强半同步(无损)

事务提交流程：      ┌──────────┐          ┌──────────────┐
                    │ 执行SQL    │          │ 执行SQL       │
                    │ Write Binlog│          │ Write Binlog  │
                    │ Redo Commit│          │ 等Slave ACK   │ ◄── 额外等待
                    │ Return OK  │          │ Redo Commit  │
                    └──────────┘          │ Return OK    │
                                          └──────────────┘

事务延迟：           ~1ms                 ~1ms + 网络RTT
                   (仅本地磁盘IO)         (本地IO + 网络往返)

每秒事务数影响：    基准                  降低约 10%~30%
                                        (取决于网络延迟)

组提交优化：        ✓                    ✓
                   (多个事务合并等ACK，均摊网络开销)
```

```
需要主从架构？
       │
   ┌───┴───┐
   │ 是     │ 否 → 单机即可
   └───┬───┘
       │
  ┌────┴────┐
  │ 能接受   │
  │ 数据丢失？│
  └────┬────┘
       │
   ┌───┴───┐
   │ 能    │  → 异步复制（性能最优，可能丢数据）
   └───┬───┘
       │
  ┌────┴────────┐
  │ 不能         │
  │ 需要零丢失？ │
  └────┬────────┘
       │
   ┌───┴───┐
   │ 是     │ → 增强半同步 AFTER_SYNC (无损复制)
   └───┬───┘
       │
   ┌───┴───┐
   │ 可容忍  │ → AFTER_COMMIT (传统半同步，极少量丢失风险)
   │ 极少量  │
   └────────┘
```

## 六、配置示例

### 6.1 半同步复制配置

```sql
-- ============ 主库 ============

-- 1. 安装半同步插件
INSTALL PLUGIN rpl_semi_sync_master SONAME 'semisync_master.so';

-- 2. 开启半同步
SET GLOBAL rpl_semi_sync_master_enabled = ON;

-- 3. 设置等待点（MySQL 5.7.2+，默认 AFTER_SYNC）
SET GLOBAL rpl_semi_sync_master_wait_point = AFTER_SYNC;

-- 4. 设置超时时间（ms），超时降级为异步
SET GLOBAL rpl_semi_sync_master_timeout = 10000;

-- 5. 查看状态
SHOW STATUS LIKE 'Rpl_semi_sync%';


-- ============ 从库 ============

-- 1. 安装半同步插件
INSTALL PLUGIN rpl_semi_sync_slave SONAME 'semisync_slave.so';

-- 2. 开启半同步
SET GLOBAL rpl_semi_sync_slave_enabled = ON;

-- 3. 重启 IO 线程使之生效
STOP SLAVE IO_THREAD;
START SLAVE IO_THREAD;

-- 4. 查看状态
SHOW STATUS LIKE 'Rpl_semi_sync%';
```

### 6.2 my.cnf 永久配置

```ini
[mysqld]
# ====== 主库 ======
plugin-load = "rpl_semi_sync_master=semisync_master.so"

gtid_mode = ON
enforce_gtid_consistency = ON
```

### 6.3 关键监控指标

```sql
-- 主库半同步状态
SHOW STATUS LIKE 'Rpl_semi_sync_master_status';         -- ON=正常，OFF=已降级

SHOW STATUS LIKE 'Rpl_semi_sync_master_no_tx';          -- 未成功接收ACK的事务数
```

## 七、面试高频问题

### Q1: 异步复制、半同步、增强半同步（无损复制）的核心区别？

```
时序对比：

异步：    主库写Binlog → 立即Commit → 立即返回客户端 → 异步发往从库
                                                        （主库不关心从库是否收到）

传统半同步：主库写Binlog → 立即Commit(引擎层) → 发Binlog给从库
                  → 等从库ACK → 返回客户端
                  （从库已确认收到，但引擎层早已提交）

增强半同步：主库写Binlog → 发Binlog给从库 → 等从库ACK
（无损）    → 收到ACK后引擎层Commit → 返回客户端
                  （从库已确认收到后，才提交引擎层）
```

### Q2: AFTER_SYNC 为什么叫"无损复制"？

因为 **主库在收到至少一个从库的 ACK 确认后，才在引擎层提交事务**。这意味着：

- 任何在主库上"已提交"的事务，一定已经存在于至少一个从库的 Relay Log 中
- 主库宕机时，不会丢失任何已提交的事务数据
- 切换后新主（原从库）拥有完整数据

### Q3: 半同步复制对性能的影响有多大？

- **增加的延迟** = 一次网络 RTT（通常 < 1ms 同机房，跨机房可能 5~10ms）
- **TPS 下降**：约 10%~30%，取决于事务大小和网络延迟
- **组提交优化**：多个并发事务合并等待，均摊网络开销，高并发下影响更小

### Q4: 半同步复制超时降级后，如何恢复？

MySQL 自动检测：
```
降级触发：等待从库 ACK 超过 rpl_semi_sync_master_timeout
         → Rpl_semi_sync_master_status = OFF
         → 主库继续以异步模式运行

恢复触发：从库 I/O Thread 重新连接，主库收到从库的 ACK 请求
         → Rpl_semi_sync_master_status 自动恢复为 ON
         → 无需人工干预
```

### Q5: 如果一个从库都没有，主库能工作吗？

能。半同步复制策略：
- `rpl_semi_sync_master_wait_for_slave_count = 1`（默认）：只需要1个从库ACK
- 如果没有任何从库，或所有从库都超时，主库降级为异步模式继续工作
- 不会阻塞主库

## 八、并行复制（额外补充）

以上三种复制模式解决了"日志传输"的一致性问题，但均未解决"日志重放"的性能问题。

**并行复制（Parallel Replication）** 是让从库 SQL 线程多线程并行重放 Relay Log，大幅降低主从延迟。

```sql
-- 从库开启并行复制
STOP SLAVE SQL_THREAD;
SET GLOBAL slave_parallel_workers = 8;           -- Worker线程数，建议4~16
SET GLOBAL slave_parallel_type = LOGICAL_CLOCK;  -- MySQL 8.0推荐
SET GLOBAL slave_preserve_commit_order = ON;     -- 保证提交顺序，保持一致性
START SLAVE SQL_THREAD;

-- 查看并行复制状态
SELECT * FROM performance_schema.replication_applier_status_by_worker;
```

| 参数 | 推荐值 | 说明 |
|------|--------|------|
| slave_parallel_workers | 4~16 | 并行worker数，不超过CPU核数 |
| slave_parallel_type | LOGICAL_CLOCK | 基于组提交的事务分组并行 |
| slave_preserve_commit_order | ON | 保证主从事务提交顺序一致 |
