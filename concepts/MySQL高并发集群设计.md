# MySQL 高并发集群设计

> 面向 C++ 后端、采用应用层自路由（无 MyCAT 等中间件）的高 QPS MySQL 集群架构设计总结。

---

## 一、设计原则

| 原则 | 说明 |
|------|------|
| **自路由** | 分片、读写分离在 C++ 框架内实现，不引入 MyCAT/ShardingSphere-Proxy |
| **直连** | 应用直连 MySQL，减少一跳，降低延迟 |
| **C++ 友好** | 适配微信等 C++ 后端的技术栈与性能要求 |
| **可扩展** | 分库分表 + 读写分离，支持数十万级 QPS |

---

## 二、整体架构

```
┌─────────────────────────────────────────────────────────────────────────┐
│                      C++ 业务服务集群（多实例）                            │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │  StorageAccess（存储访问层）                                       │   │
│  │  ├── ShardRouter（分片路由）     ← user_id % N 等                   │   │
│  │  ├── ReadWriteRouter（读写分离）  ← 写主读从                        │   │
│  │  └── ConnPool[]（连接池）        ← 每分片独立主/从池                │   │
│  └─────────────────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────────────────┘
          │                        │ 直连（无中间件）
          ▼                        ▼
┌─────────────────────┐    ┌─────────────────────────────────────────────┐
│  Redis（热点缓存）   │    │  MySQL 分片集群                              │
│  拦截 80%+ 读请求   │    │  分片0: 1主2从 | 分片1: 1主2从 | ...         │
└─────────────────────┘    └─────────────────────────────────────────────┘
```

---

## 三、应用层自路由

### 3.1 自路由 vs MyCAT

| 维度 | 自路由 | MyCAT |
|------|--------|-------|
| 路由位置 | 应用进程内（C++ 框架） | 独立代理进程 |
| 连接路径 | 应用 → MySQL | 应用 → MyCAT → MySQL |
| 网络跳数 | 1 跳 | 2 跳 |
| 部署 | 无额外中间件 | 需部署、维护 MyCAT |
| 适用 | C++、性能敏感场景 | 多语言、希望统一接入 |

### 3.2 自路由核心逻辑

```cpp
// 分片路由
int get_shard_id(int64_t user_id) {
    return user_id % SHARD_COUNT;  // 如 32、64
}

// 读写分离
DBConnection* get_connection(OpType op, int shard_id) {
    if (op == WRITE)
        return conn_pool_[shard_id].get_master();
    else
        return conn_pool_[shard_id].get_slave();  // 轮询/随机
}
```

### 3.3 连接池设计

- 每个进程按**分片 + 主从**拆分连接池
- 每分片：1 个主库池 + N 个从库池
- 配置从 Config Center 拉取，支持主从切换后更新

---

## 四、分库分表策略

### 4.1 分片键选择（以 IM 为例）

| 表类型 | 分片键 | 策略 | 示例 |
|--------|--------|------|------|
| 用户表 | user_id | user_id % 32 | 32 分片 |
| 消息/会话 | conversation_id | conversation_id % 64 | 64 分片 |
| 群组 | group_id | group_id % 32 | 32 分片 |

### 4.2 规模估算

| 指标 | 参考值 |
|------|--------|
| 单表目标行数 | 100 万～500 万 |
| 分片数 | 32～128（按数据量扩展） |
| 每分片 | 1 主 2～3 从 |

### 4.3 QPS 估算

- 单主写：约 5,000 TPS
- 单从读：约 5,000 QPS
- **总 QPS** = 主库 5,000（写）+ N 从 × 5,000（读）
- 例：1 主 3 从 → 写 5,000 + 读 15,000 ≈ **2 万 QPS**
- 32 分片 × 2 万 ≈ **64 万 QPS**（理论值，受网络、应用聚合等限制）

---

## 五、读写分离说明

- **5,000**：主库**写入**能力上限（TPS）
- **2 万**：1 主 3 从场景下**系统总 QPS**（读 + 写）
- 读请求由从库承担，写请求由主库承担；主库是写瓶颈，读可通过加从库扩展

---

## 六、存储层设计

### 6.1 物理存储

| 层级 | 介质 | 用途 |
|------|------|------|
| 主库/从库 | NVMe SSD | 热数据，高 IOPS |
| 归档库 | HDD/对象存储 | 冷数据 |

### 6.2 InnoDB 关键参数（8C16G 示例）

| 参数 | 建议值 |
|------|--------|
| innodb_buffer_pool_size | 物理内存 50%～70% |
| innodb_log_file_size | 1～2GB |
| innodb_flush_log_at_trx_commit | 1 |
| sync_binlog | 1 |
| innodb_io_capacity | 10000～20000 |
| innodb_flush_method | O_DIRECT |

### 6.3 冷热分离

- **热数据**：近期消息、活跃用户，保留在在线 MySQL
- **冷数据**：历史消息定期归档或迁至对象存储
- 可用分区表 + 定期 DROP 老分区控制单表体积

## 七、高可用

| 场景 | 方案 |
|------|------|
| 主库宕机 | MHA/Orchestrator 自动主从切换，配置中心更新主库地址 |
| 从库宕机 | 读流量切至其他从库 |
| 连接失败 | 连接池健康检查、自动剔除故障连接 |

---

## 八、实施要点

1. **统一存储访问层**：所有 DB 访问经同一套接口，分片、读写分离内聚在框架内
2. **连接池按分片+主从拆分**：避免单池过大、热点集中
3. **分片键与业务绑定**：保证大部分查询带分片键，避免跨分片
4. **跨分片查询**：尽量避免；必要时应用层多路查询后聚合
5. **配置外置**：分片拓扑、主从地址从配置中心拉取，便于扩缩容

### 9.4 自建 vs 云服务器

| 方式 | 优点 | 缺点 | 成本参考 |
|------|------|------|----------|
| **云服务器** | 按需扩容、免运维、多 AZ | 长期成本偏高 | 见上表 |
| **自建机房** | 长期成本低、资源可控 | 需运维、采购周期长 | 8C16G 物理机约 1～2 万/台（一次性）+ 机房/电费 |
| **混合** | DB 自建省成本，业务上云 | 架构复杂 | 视业务而定 |

*上述价格为 2024 年前后云厂商活动价参考，实际以各厂商实时报价为准。*

## 十、简要结论

- **自路由**：分片与读写分离在 C++ 框架内完成，无 MyCAT
- **直连 MySQL**：少一跳，适合高性能 C++ 后端
- **分库分表 + 读写分离 + 缓存**：支撑数十万级 QPS
- **存储**：NVMe SSD + 合理 InnoDB 配置 + 冷热分离

## 十一、MySQL 能力边界与微信实际选型

### 11.1 本方案能支撑的规模

| 指标 | MySQL 集群（本方案） | 适用场景 |
|------|---------------------|----------|
| QPS | 数十万级 | 中小型 IM、电商、社交 |
| 消息量级 | 千万～亿级/天 | 日活数百万～千万 |
| 可用性 | 3～5 个 9 | 主从切换有短暂中断 |

### 11.2 微信真实规模与选型

微信技术架构负责人许家滔公开披露：

| 指标 | 微信规模 |
|------|----------|
| 日活用户 | 10 亿 |
| 每日消息量 | 1000+ 亿 |
| 数据存取 | **每分钟超过百亿次** |
| 朋友圈日发表/点赞 | 10+ 亿 |

**微信核心存储：不使用 MySQL，而是自研 PaxosStore**

- 原因：数据敏感、数据量大，**未基于开源存储搭建**，而是自研整套存储
- **PaxosStore**：多主、基于非租约 Paxos Log，无主故障切换带来的 30 秒级中断
- 存储引擎：LSM 树等，单表支持亿行
- 可用性目标：**6 个 9**
- 冷热分级：内存层（热点）→ Paxos 存储层 → 机械盘层（冷数据）

### 11.3 MySQL 能否满足微信需求？

| 场景 | 结论 |
|------|------|
| **核心消息存储** | ❌ 难以支撑。每分钟百亿次存取远超 MySQL 集群常态能力 |
| **用户/账号等元数据** | ✅ 可能用于部分模块，但消息主存储不是 MySQL |
| **中小型 IM（日活数百万）** | ✅ 本方案可行 |

### 11.4 若不用 MySQL，可考虑什么？

| 方案 | 特点 | 适用规模 |
|------|------|----------|
| **TiDB** | 分布式 SQL、兼容 MySQL 协议、水平扩展 | 中大型，替代 MySQL 平滑迁移 |
| **Cassandra / ScyllaDB** | 宽表、最终一致性、写优化 | 海量消息、时序类 |
| **MongoDB 分片** | 文档型、灵活 schema | 非强关系、日志类 |
| **自研（如 PaxosStore）** | 多主、强一致、可控 | 极大规模、有足够团队投入 |
| **混合** | MySQL 存元数据 + 专用存储（如 Kafka+对象存储）存消息体 | 折中方案 |

### 11.5 选型建议

```
规模                    推荐方案
─────────────────────────────────────────────
日活 < 百万、QPS < 10 万     MySQL 集群（本方案）
日活 百万～千万、QPS 数十万   MySQL + Redis + 消息队列
日活 千万～亿、QPS 百万+      TiDB / 分布式 KV / 自研
微信级（10 亿日活）          自研 PaxosStore 类架构
```
