# Redis 存储型方案性能对比

> 本文档对比本地 KeyDB+RocksDB 存储型与华为云、阿里云 Redis 存储型方案，分析各方案优缺点、性能瓶颈及优化方向，并探讨 KeyDB+RocksDB 对接对象存储（如华为 OBS）的可行性、预期性能与瓶颈。

See also: [[KeyDB存算分离项目]], [[OBS对接RocksDB性能分析]], [[RocksDB基础]], [[Redis性能问题]]

## 二、性能测试方式与结果

### 2.1 测试方法

#### 本地 KeyDB 测试

**纯内存模式**：
```bash
keydb-server --daemonize yes --port 6379
keydb-benchmark -h 127.0.0.1 -p 6379 -t set,get -n 100000 -q
```

**FLASH 模式**：
```bash
keydb-server --daemonize yes --port 6379 \
  --storage-provider flash /path/to/keydb_flash \
  --maxmemory 100mb --maxmemory-policy allkeys-lru
keydb-benchmark -h 127.0.0.1 -p 6379 -t set,get -n 100000 -q
```

#### 云厂商测试（阿里云 Tair ESSD 白皮书）

- **工具**：YCSB
- **工作负载**：Load（100% SET）、Uniform-Read（100% GET）、Zipfian-Read（热点读）、Uniform-50%Read-50%Update
- **数据规模**：6.4 亿 ~ 76.8 亿 key（随规格变化）

## 三、各方案优缺点分析

### 3.1 本地 KeyDB+RocksDB 存储型

| 维度 | 优点 | 缺点 |
|------|------|------|
| **性能** | 热数据可达 20 万+ QPS，延迟亚毫秒；无网络存储延迟；可调优空间大 | 冷数据受本地磁盘 IOPS 限制（本环境仅 ~982）；大数据量 SET 预测 2~15 万 |
| **成本** | 无云服务费，硬件一次性投入；存储扩容灵活 | 需自建运维、备份、高可用 |
| **可控性** | 可自定义 RocksDB 参数、compaction 策略、block cache 等 | 需深度理解 LSM、compaction、write stall |
| **存储介质** | 可选用 NVMe 直连获得高 IOPS | 本环境 WSL2 虚拟盘随机 IOPS 极低 |
| **扩展性** | 可横向分片、集群部署 | 需自行实现集群与运维 |

### 3.2 华为云 DCS Redis 存储型

| 维度 | 优点 | 缺点 |
|------|------|------|
| **存储介质** | **本地 NVMe SSD**，非远程对象存储，冷数据延迟 1~10 ms | 较纯内存型仍有数量级差距 |
| **托管** | 免运维、自动备份、主备高可用 | 企业版存储型已限制销售，新购困难 |
| **成本** | 较内存型成本优化，适合大容量冷热分层 | 规格受限，无法按需弹性 |
| **兼容性** | 100% Redis 协议 | 冷数据访问延迟不可控 |

### 3.3 阿里云 Tair ESSD 磁盘型

| 维度 | 优点 | 缺点 |
|------|------|------|
| **性能** | 大数据量下 SET 8~9 万、热点读 13 万+；规格可线性扩展至 13xlarge | 使用**远端 ESSD 云盘**，单次 I/O 延迟高于本地盘 |
| **容量** | 集群最大 32TB 内存、320TB 存储 | 成本随规格上升 |
| **托管** | 全托管、备份恢复、监控告警 | 依赖阿里云生态 |
| **存储** | ESSD 云盘弹性扩容、高可用 | 网络附加存储，极端压力下延迟高于本地 NVMe |

## 四、性能差异原因分析

### 4.1 为何本地小数据量 QPS 远高于云厂商？

| 因素 | 本地（10 万 key，2MB） | 云厂商（数亿 key，数十 GB） |
|------|------------------------|-----------------------------|
| **MemTable** | 2MB << 64MB，永不 flush | 持续写满→flush，产生大量 L0 |
| **Compaction** | 不触发 | L0→L1→… 多层压实，写放大 10~30× |
| **Write stall** | 不触发 | L0 积压时前台写被限流 |
| **Block cache** | 2MB 全命中，零磁盘读 | 数据远超缓存，读穿透磁盘 |
| **存储延迟** | 本地虚拟盘（低延迟） | 云盘网络附加（阿里）或本地 NVMe（华为） |

**结论**：核心差异在于**数据规模差 4 个数量级**，导致 LSM 路径上 flush、compaction、write stall、cache 命中率等环节负载截然不同。

### 4.2 华为云 vs 阿里云存储型差异

| 对比项 | 华为云 DCS 存储型 | 阿里云 Tair ESSD |
|--------|-------------------|------------------|
| **存储位置** | 本地 NVMe SSD | 远端 ESSD 云盘（网络块存储） |
| **是否调用远端对象存储** | **否**，纯本地盘 | **否**，使用块存储（非 OBS） |
| **单次 I/O 延迟** | 本地直连，更低 | 经存储网络，略高 |
| **参考 QPS** | 约 7 万 | 8~9 万（写）/ 5~14 万（读） |
| **规格弹性** | 8~32GB，已限售 | 可扩展至 13xlarge 等大规格 |

### 4.3 本地 KeyDB 大数据量预测与云厂商对齐

修正后本地 KeyDB FLASH 大数据量 SET 预测 **2~15 万**，与阿里云 Tair（8.9 万）、RocksDB 官方 overwrite（8.7 万/NVMe）处于同一量级。本环境磁盘随机 IOPS 仅 ~982，约为云盘 1/50~1/500，故 GET 预测 1,000~3,000，远低于云厂商。

## 五、性能瓶颈与优化方向

### 5.1 本地 KeyDB+RocksDB 瓶颈与优化

#### 写入瓶颈（SET）

| 瓶颈 | 影响 | 优化方向 |
|------|------|----------|
| **Compaction 写放大 (WA)** | 10~30×，每写 1 字节需写 10~30 字节磁盘 | 换用 Universal compaction；增大 write_buffer_size；开启 Snappy/LZ4 压缩 |
| **Write stall 限流** | L0 积压触发 slowdown/stop | 增加 max_background_compactions；调大 level0_slowdown_writes_trigger |
| **顺序写带宽** | WAL + flush + compaction 共享带宽 | WAL 与数据分盘；换用 NVMe |
| **Redis 协议开销** | 相比 db_bench 有 1.3~2× 开销 | 使用 pipeline、MSET；增加 server-threads |

#### 读取瓶颈（GET）

| 瓶颈 | 影响 | 优化方向 |
|------|------|----------|
| **随机 IOPS** | 本环境仅 ~982，直接限制冷数据 GET | **最关键**：换用高 IOPS NVMe（5 万~100 万） |
| **Block cache 容量** | 默认 8MB，命中率低 | 增大 block_cache（可用内存 30~50%） |
| **maxmemory 限制** | 100MB 热数据容量小 | 增大 maxmemory，减少磁盘读 |

#### 优先级排序

1. **换存储介质**：虚拟盘→NVMe 直通，IOPS 提升约 500×
2. **增大 block_cache**：零成本，显著提升读命中率
3. **增大 maxmemory**：更多热数据留 DRAM
4. **调优 compaction**：后台线程、write_buffer_size、压缩
5. **客户端优化**：pipeline、MSET、memtier 多连接

### 5.2 云厂商方案瓶颈（参考）

| 方案 | 主要瓶颈 | 优化建议 |
|------|----------|----------|
| **华为云存储型** | 冷数据 SSD 延迟 1~10 ms；企业版限售 | 热点数据尽量控制在内存内；考虑基础版集群 |
| **阿里云 Tair ESSD** | 远端云盘网络延迟；均匀读 QPS 约 5 万 | 利用热点读优化（Zipfian 可达 13 万+）；选更大规格 |

## 六、KeyDB+RocksDB 对接对象存储分析

### 6.1 技术可行性

**RocksDB 与对象存储**：

- **RocksDB-Cloud**：Rockset 等提供的扩展，支持将持久化状态映射到 S3 等对象存储，适用于云原生、远程 worker 做 compaction 等场景。
- **Environment 插件**：通过自定义 `Env` 实现，可将底层 I/O 重定向到 REST API（如 S3、OBS）。
- **KeyDB FLASH**：当前基于本地 RocksDB，**未原生支持对象存储**；若对接 OBS，需通过 RocksDB 的 `Env` 或 CloudNativeRocksDB 类方案进行改造。

**华为 OBS 内网 API**：内网访问可降低公网延迟，但对象存储的访问模型（Put/Get 大对象、高延迟、高吞吐）与 LSM 的随机小块读写模型存在本质差异。

### 6.2 主要瓶颈

| 瓶颈 | 说明 |
|------|------|
| **延迟** | 对象存储单次请求 5~50 ms，与本地 SSD 亚毫秒级差 1~2 个数量级 |
| **访问模型不匹配** | LSM 需要大量随机小块读写；对象存储适合大对象、顺序/批量访问 |
| **Compaction 成本** | 远程 compaction 需大量 Get/Put，网络与 CPU 开销大，易触发 write stall |
| **一致性** | 分布式对象存储的最终一致性需与 RocksDB 的持久化语义对齐 |
| **成本** | 对象存储按请求次数计费，高 QPS 场景成本可能显著上升 |

### 6.3 适用场景与建议

| 场景 | 是否适合对接 OBS | 建议 |
|------|------------------|------|
| **冷数据归档** | 适合 | 将冷 SST 定期迁移至 OBS，热数据仍留本地 |
| **主存储全量落 OBS** | 不适合 | 延迟与 QPS 无法满足在线缓存需求 |
| **混合架构** | 可考虑 | 本地 SSD 作主存储，OBS 作备份/归档 |
| **RocksDB-Cloud 类方案** | 需评估 | 专为云存储设计，可减少部分适配成本，但性能仍受对象存储特性限制 |

## 七、总结与选型建议

### 7.1 方案对比总结

| 方案 | 存储介质 | 是否远端对象存储 | SET QPS（大数据） | GET QPS（冷数据） | 典型延迟 | 适用场景 |
|------|----------|------------------|-------------------|-------------------|----------|----------|
| **本地 KeyDB+RocksDB** | 本地盘（可升级 NVMe） | 否 | 2~15 万（视磁盘） | 1,000~3,000（本环境）~数万（NVMe） | 亚 ms~ms | 自建、可控、成本敏感 |
| **华为云 DCS 存储型** | 本地 NVMe SSD | 否 | 约 7 万 | 约 7 万 | 1~10 ms（冷数据） | 托管、冷热分层（已限售） |
| **阿里云 Tair ESSD** | 远端 ESSD 云盘 | 否（块存储） | 8~9 万 | 5~14 万（热点更高） | 1~4 ms | 大容量、托管、弹性 |
| **KeyDB+OBS（假设）** | 华为 OBS 内网 | **是** | 500~5,000 | 100~2,000 | 5~50 ms | 仅适合归档/备份，不适合主存储 |

### 7.2 优化本地 KeyDB+RocksDB 的优先建议

1. **更换存储**：WSL2 虚拟盘 → 物理 NVMe 直连，随机 IOPS 从 ~982 提升至 5 万+。
2. **调大缓存**：block_cache 提升至可用内存 30~50%，maxmemory 适当增大。
3. **Compaction 调优**：增加后台线程、write_buffer_size，开启压缩。
4. **客户端**：pipeline、MSET、memtier 多连接压测。

### 7.3 对象存储对接结论

**KeyDB+RocksDB 通过 RocksDB 环境插件对接华为 OBS 内网**：

- **预期性能**：SET 500~5,000 QPS，GET 100~2,000 QPS，延迟 5~50 ms。
- **主要瓶颈**：对象存储高延迟、访问模型与 LSM 不匹配、compaction 远程化成本高。
- **建议**：**不作为主存储**；可作为冷数据归档、备份目标，或采用 RocksDB-Cloud 等专用方案做混合架构评估。
