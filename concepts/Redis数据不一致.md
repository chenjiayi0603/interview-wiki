# Redis 数据不一致

See also: [[MySQL事务与隔离级别]]

## 现象
- 主从数据不一致
- 缓存与 DB 不一致

## 可能原因
- **主从**：主从网络抖动或断连，从节点落后时，主节点会利用 repl_backlog（复制积压缓冲区）将断连期间的增量数据补发给从节点，实现快速增量补同步。但如果从节点落后太多，所需增量数据已被新写指令覆盖（repl_backlog 溢出），此时只能触发全量同步（RDB）。**全量同步的主要问题有：**
  1. 全量同步时主节点会 fork 生成 RDB 文件，占用大量 CPU、内存和磁盘 IO，容易影响主库性能，甚至导致卡顿。
  2. 从节点加载 RDB 时必须清空原有数据重新导入，短时间内不可用或数据不一致，影响线上读写。
  3. 全量数据需要通过网络传输，数据集大时会消耗大量带宽，极易造成网络抖动，对主备在不同地域/机房环境影响尤为显著。
  4. 若主备频繁全量同步，容易连锁导致服务雪崩。
  > 最佳实践是合理增大 repl-backlog-size、优化网络稳定性，并及时发现阻断，避免频繁全量同步。
- **主从**：从节点执行了写命令（未做只读限制）或过期键在主从上的处理差异（惰性删除 vs 定时删除）
- **缓存与 DB**：先更新 DB 再删缓存时，删缓存失败或未执行
- **缓存与 DB**：高并发下“读旧 DB + 写回缓存”导致旧数据覆盖新数据；未设 TTL 或 TTL 过长，长期使用过期数据

## 排查步骤
1. **主从同步状态与偏移量**：`INFO replication` 查看 `master_repl_offset`、`slave_repl_offset`
2. **过期键策略**：主从模式下过期键的传播机制
3. **持久化文件校验**：RDB/AOF 完整性校验

## 解决方案
- 保障主从网络稳定，避免频繁网络抖动
- 设置合理 TTL，避免永久缓存
- 使用延迟双删策略（先删缓存 → 更新 DB → 延迟后再删缓存）

## 根因原理深入分析

### 主从复制的底层机制与不一致根因

**全量同步流程**：
```
1. 从节点发送 PSYNC ? -1（首次同步）
2. 主节点 fork 子进程生成 RDB 快照
3. 主节点将 RDB 发送给从节点（期间新写入命令存入 repl_backlog）
4. 从节点加载 RDB（此时从节点不可用或返回旧数据）
5. 主节点将积压缓冲区的增量命令发送给从节点
6. 进入增量同步：主节点每执行一个写命令，异步传播给从节点
```

**不一致的根本原因是"异步复制"**：
- 主节点写入成功后立即返回客户端 OK，然后**异步**将命令传播给从节点
- 如果此时主节点宕机，已返回客户端但未同步到从节点的数据就丢失了
- 这是 Redis 在**一致性 vs 可用性**之间选择了可用性（AP系统）

**repl_backlog 溢出导致全量同步**：
```
repl_backlog（环形缓冲区，默认1MB）
  ┌─────────────────────────┐
  │ cmd1 cmd2 cmd3 ... cmdN │  ← 写满后覆盖最早的命令
  └─────────────────────────┘
       ↑ master_repl_offset
                ↑ slave_repl_offset（从节点断连，落后了）

如果 master_repl_offset - slave_repl_offset > repl_backlog_size
→ 从节点需要的增量数据已被覆盖
→ 只能进行全量同步（重传 RDB）
→ 全量同步期间从节点数据不一致且可能不可用
```

**处理方式**：
```bash
# 增大 repl_backlog_size，减少全量同步概率
# 建议设为：平均写入速率(MB/s) × 预期最大断连秒数 × 2
repl-backlog-size 256mb

# 使用 min-replicas-to-write 保证至少 N 个从节点确认写入
min-replicas-to-write 1
min-replicas-max-lag 10
# 如果存活从节点 < 1 或延迟 > 10秒，主节点拒绝写入（牺牲可用性换一致性）
```

> #### hash有很多field ，是要分为多个指令来复制过去，造成复制缓冲区过大而失败？原因如下：
当 Redis 的一个大 hash（有很多 field）需要从主库同步到从库时，主节点无法将整个大 hash 直接用一个命令完整复制过去——协议限制，每条命令单次处理元素有限。因此，主节点会将大 hash 拆分成大量的 `hset`（或 `hmset`）命令，逐条同步到从库。这些命令会被暂存到复制缓冲区（`repl_backlog` 或从节点的 socket 输出缓冲）里，等从库逐步消费。

**如果有以下情况就容易失败：**
- 网络慢、从节点处理跟不上，导致这些命令积压在主节点的复制缓冲区。
- 若复制缓冲区配置过小（注意：`repl-backlog-size` 是主节点用来缓存还未同步给从节点的“写命令历史”，用于支持增量复制；`client-output-buffer-limit` 则是针对每个复制从节点连接的输出缓冲区，限制主节点为该从节点暂存未发送数据的大小），则缓冲很快就被塞满。
- `client-output-buffer-limit` 是主节点为每一类客户端分别设置的**每个连接的输出缓冲区上限**，而不是所有从节点或客户端共用一个总量。举例：`client-output-buffer-limit replica 512mb 256mb 60` 代表每个从节点（replica，老版本叫 slave）连接单独有一份 512MB 的硬上限，超过后主节点只会关闭**对应的那个从节点**连接，不会影响其他从节点，各自独立。

-  主节点是主动将写命令推送到从节点的 socket 输出缓冲区，“主节点主动发”这点没错。但这些数据是否能顺利、持续地“发出去”，实际还依赖于从节点消费的速度——只有当从节点及时地从 socket 缓冲区读取（pull）数据，主节点缓冲区才不会堆积。如果从节点处理太慢、网络拥堵导致读取跟不上，主节点缓冲区的数据积压，超出阈值就会断开与对应从节点的连接。因此虽然主节点是主动推送者，但主从同步是否流畅主要卡在从节点能不能“吃得下”，是一个“主节点发得出去、从节点要接得住”的协作过程，而不是主节点无节制的一味输出。

- 主节点负责检测所有连接的缓冲区使用情况并执行断连动作，从节点本身无需关心此参数。所以不是“所有从节点共用”一份缓冲区或者总量限制，而是“每个从节点各自有自己的一份上限”。

**对策建议：**
- 尽量避免超大 hash，单个 key 的 field 数量建议不要过万（实际可承受值与写速率和带宽有关）。
- 调大主从之间的复制缓冲区（`client-output-buffer-limit`、`repl-backlog-size`），但不能无限加大，防止撑爆内存。
- 主从数据迁移时，可以分批迁移、热 key 先行等手段，生产上热 key 分片、分散热点效果更佳。
- 监控 replica/sync 相关慢日志，提前发现慢同步和复同步，避免生产高峰时触发全量同步/频繁断连。

简要结论：**大 hash 在同步时会拆分成多条写命令，消耗大量缓冲区，一旦积压太多就容易导致缓冲区溢出、主从断开，最好避免巨型 key。**

**补充说明：**

- **「缓冲区溢出」指的是哪个缓冲区？**
  指 `client-output-buffer-limit replica` 所限制的**主节点为该从节点准备的 socket 输出缓冲区**。当从节点消费太慢、命令积压超过该上限时，主节点会断开与该从节点的连接。与 `repl_backlog` 不同：repl_backlog 满后只是导致需全量同步，不会直接触发断连。

- **为什么是断开而不是限流？**
  限流需要主节点持续持有积压数据，会继续占用内存甚至导致 OOM，违背 `client-output-buffer-limit` 保护主节点的初衷。限流还可能阻塞主线程，影响所有客户端。断开能立刻释放该从节点的 buffer，主节点继续正常服务；从节点可重连后用 PSYNC 或全量同步恢复。Redis 采用 fail-fast：宁可该从节点断连重同步，也不让慢从节点拖垮主节点。

### 是半同步吗？对延迟有什么影响

不会等从节点响应才返回客户端。
即使设置了 `min-replicas-to-write`，主节点会根据当前和自己保持连接、处于在线状态（`connected`）的从节点数量，并且这些从节点的复制延迟（repl lag）没有超过 `min-replicas-max-lag` 的阈值来判断“足够数量”。这个信息来自主节点和每个从节点之间定期的心跳和 ACK 机制（如PING、REPLCONF ACK等）。只有当满足足够数量的从节点都实时在线且延迟不超过设定阈值，主节点才允许写入；否则会直接拒绝新写入。而一旦条件满足，主节点写成功后**会立即返回客户端**，不会等待所有从节点确认写入完成再响应，所以大部分情况下写操作的延迟不会被显著拉高，只有在从节点全部掉线或延迟远超阈值时才会拒绝写入。

**简要结论：**
该机制可以部分提升数据可靠性，但对服务延迟影响较小，不会像 MySQL 半同步那样每条写都同步等待确认。

可参考官方文档：https://redis.io/docs/management/replication/#data-durability

### 过期键在主从上的不一致
Redis 过期键删除采用两种策略组合：
- **惰性删除**：访问 key 时检查是否过期，过期则删除
- **定时采样删除**：每 100ms 从带 TTL 的 key 中随机采样 20 个，删除过期的，如果过期比例 > 25% 则继续循环

**主从不一致场景**：在 Redis 3.2 之前，从节点不会主动删除过期键（即使已过期），只等主节点发来 DEL 命令。如果主节点还没有触发惰性/定时删除，从节点读到的就是过期但仍存在的脏数据。3.2+ 版本从节点对过期 key 返回空（但物理上仍未删除），解决了读不一致但内存未释放。

### 缓存与 DB 双写不一致的经典问题

**Cache-Aside 模式下并发不一致的根因**：
```
时刻T1：线程A 读缓存 miss → 读DB得到旧值 value_old
时刻T2：线程B 更新DB为 value_new → 删除缓存（成功）
时刻T3：线程A 将 value_old 写入缓存  ← 旧值覆盖！
```

**延迟双删为什么有效**：
```
1. 删缓存
2. 更新DB
3. sleep(N ms)  ← 等待"读旧DB+写缓存"的并发请求完成
4. 再次删缓存  ← 清除可能被并发请求写回的旧值
```
延迟时间 N 应略大于一次"读DB+写缓存"的耗时。缺点是引入了延迟且无法100%保证一致性。

**更可靠的方案——基于 binlog 的异步更新**：
通过 Canal/Debezium 监听 MySQL binlog，异步删除/更新缓存，实现最终一致性。
