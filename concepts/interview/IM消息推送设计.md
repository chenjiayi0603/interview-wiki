# IM消息推送设计

## 5.1 推送架构

**总体流程**:
```
┌─────────────────────┐
│ 业务服务/MsgServer   │  产生消息
└──────────┬──────────┘
           │
           │ 消息入队
           ▼
┌─────────────────────┐
│  消息存储/推送队列    │  异步队列缓冲
└──────────┬──────────┘
           │
           │ PushServer消费
           ▼
┌─────────────────────┐
│    PushServer        │  消息推送服务
└──────────┬──────────┘
           │
           │ 查询用户在线状态
           ▼
    ┌──────┴──────┐
    │             │
    ▼             ▼
┌─────────┐  ┌──────────────┐
│  在线   │  │    离线      │
└────┬────┘  └──────┬───────┘
     │              │
     │              │
     ▼              ▼
┌─────────┐  ┌──────────────────┐
│长连接推送│  │ 离线消息/厂商推送  │
│到客户端 │  │ (APNs/FCM/小米等) │
└─────────┘  └──────────────────┘
```

## 5.2 是否需要独立PushServer

**强烈建议独立PushServer**:
- **服务解耦**: 推送与主消息分离，弹性好，易扩展，易容错
- **多端多通道支持**: 便于集成APNs/FCM/厂商推送及多设备
- **专业限流与重试**: 易做限流、重试、安全隔离
- **独立扩缩容**: 推送侧可单独横向扩展
- **分层处理**: 在线推送和离线消息分层，互不影响

## 5.3 队列与异步推送

**消息推送应采用异步队列**:
- 主线程快速入队，后台线程消费
- 不建议同步串行推送，否则效率极低
- 队列配合限流能抗突发，提升整体吞吐

## 5.4 限流策略

**推荐使用Token Bucket（令牌桶算法）**:
- **核心思想**: 令牌桶按固定速率往桶中加入"令牌"，桶内令牌最多积攒到上限。每来一条推送请求时，若桶内有令牌则取出一个，允许通过；若没有令牌则拒绝/等待/丢弃
- **优势**: 
  - 能更好支持突发高峰
  - 易调节平滑流量，同时优雅"削峰填谷"
  - 业界主流方案（腾讯、字节、阿里等）

**Token Bucket实现**:
```python
初始化：桶容量 = MAX_TOKENS，当前令牌数 = MAX_TOKENS，补充速率 = r（每秒补r个令牌）

请求处理流程：
  now = 当前时间戳
  elapsed = now - 上次补充时间
  补充令牌数 = elapsed * r
  当前令牌数 = min(MAX_TOKENS, 当前令牌数 + 补充令牌数)
  上次补充时间 = now

  如果 当前令牌数 >= 1：
      当前令牌数 -= 1
      允许通过
  否则：
      拒绝/丢弃/排队
```

## 5.5 重发机制

**重发队列设计**:
- 重发机制**并不会直接依赖"旧的主内存推送队列"**，而是采用**单独的重试任务队列（Retry Queue）或持久化存储**
- 推送失败后，将失败消息及重发参数（间隔、下次尝试时间、重试次数等）写入"重发队列"或数据库表
- 定时调度器或后台线程，定期扫描到期重试的消息并重新入主队列或直接投递
- 支持指数退避、定时重试（如1s、3s、10s、1min...）

[src: raw/ingested/3项目/分布式IM-雷漫/数据-leiman_IM系统设计-五、消息推送设计.md]

## 5.6 在线/离线判定

**由PushServer自己判断用户在线状态**:
- PushServer的职责就是"投递各种消息到目标终端"，它天然需要实时掌握用户的在线/离线状态
- 只有PushServer收到新消息、去查目标用户的在线状态，才能决定：
  - 在线则通过长连接直推到终端
  - 离线则投递到厂商推送（小米/华为/APNs/FCM等）或写入离线消息表

[src: raw/ingested/3项目/分布式IM-雷漫/leiman_IM系统设计考点-五、消息推送设计.md]

## 5.7 在线状态缓存策略

**群聊在线状态缓存方案：LRU缓存+Redis兜底**:
- pushserver层可用lru+ttl方式缓存最近访问最频繁或活跃的群（如最近1万~2万群ID）
- 把每个群的"成员在线状态快照"存在本地内存
- 命中本地缓存后可快速判定群成员谁在线，极大提升推送效率并降低Redis压力
- 缓存未命中或过期时再查Redis集群的"群成员在线主表"

**单聊在线状态主流查Redis**:
- 单聊用户分布随机、长尾特性明显，若用本地缓存需复杂同步，一致性难维护
- Redis单机可支撑几十万、百万级QPS，完全满足单聊在线查询需求
- 查询在线状态一般只需亚毫秒到几毫秒，时延极低
- 直接查Redis更简单靠谱

[src: raw/ingested/3项目/分布式IM-雷漫/数据-leiman_IM系统设计-五、消息推送设计.md]

## 5.8 群推送合并&限流

**群推送消息建议pushserver合并同群同消息**:
- 批量高效下发到在线用户，节省带宽和资源
- 推送需要队列+限流（常用令牌桶算法），避免高并发冲垮网关或下游
- 高峰期采取异步处理，保障系统可用性

## 5.9 单聊推送：队列、限流、重发

- 单聊同样需要独立 pushserver 和推送队列。
- 限流常用**Token Bucket（令牌桶）**，支持突发高峰，业界主流。
- 最大队列、QPS超限建议丢弃低优先级消息。
- 重试需用单独的重试队列/表，和主队列解耦，支持按策略重发、自动剔除。

#### 单聊是否需要 PushServer

**结论**：**需要。**

单聊消息同样需要推送能力——即无论发送者与接收者是否在线，都要保障消息及时可靠地通知到目标端。现代 IM 大多采用"独立 pushserver 负责所有在线/离线用户推送"的模式，无论是单聊还是群聊场景。

#### 单聊 PushServer 是否需要队列

**结论**：**需要。**

虽然单聊流量（单点到单点）通常低于群聊，但在高并发/大规模 IM 场景下（如亿级用户、一秒多万并发），也绝不能简单用同步方式去直接推送，否则容易因偶发网络/外部接口抖动而堵住主业务。  
**队列能将瞬时流量缓冲，平滑下游压力，解耦主流程。** 同时能应对下行通道偶发阻塞、推送通路抖动等异常。

#### 队列、限流、重发的详细策略（大厂实践）

##### 队列设计
- **类型**  
  - 通常采用「内存队列+持久化队列」组合。内存队列速度快，用于实时推送；本地磁盘/消息中间件（Kafka/RocketMQ）做持久化备份，防丢失。
  - 单聊/群聊队列可分开，单聊按照用户ID哈希分桶；也有"每worker一队列"并发模型，防止消息跨线程乱序。

- **入队粒度**  
  - 每条待下发消息，都会先写入待推送队列，由后台 worker/线程逐步异步取出下发，主线程立刻返回，极大提升响应能力。

- **容量与降级**  
  - 队列可配置最大容量。达到阈值后，可触发告警、丢弃低优先级消息或做流量降级（如只保留核心告警/系统消息）。

##### 限流策略
- **目标**  
  - 防止突发推送流量压垮后台/厂商下游接口或自身服务，拉平"尖峰"给外部系统的压力。
- **常见模式**  
  - Token Bucket、Leaky Bucket 算法实现微服务限流。
  - 支持"全局限流"与"用户级/通道级限流"两级。
    - 例如每秒单个用户最多推送N条，或 pushserver 总量限流，超限时排队或丢弃。
  - 限流后处理可选：入等待队列（排队）、超时丢弃、主动降级。

#### Token Bucket、Leaky Bucket 选哪个？

**推荐：优先选择 Token Bucket（令牌桶算法）。**

**理由如下：**
  1. **Token Bucket 能更好支持突发高峰。**  
     IM 推送经常遇到短时间的消息激增（如群发/大规模离线补推），Token Bucket 可以"积攒"令牌，允许一定突发流量，保证突发时响应不被硬性截断。Leaky Bucket（漏桶）则更强调严格的平均速率，突发消息会被排队处理，可能导致延迟。
  2. **令牌桶易调节平滑流量，同时优雅"削峰填谷"。**  
     可配置"桶容量"允许多少突发，平时消息较匀速，冲高流量可加速放行、低谷可积攒资源，比较灵活。
  3. **实际 IM/推送/微服务限流业界主流方案**  
     大厂如腾讯、字节、阿里等，服务限流、接口保护几乎都首选 Token Bucket，尤其推送业务突发与平峰交替明显，更适合这种弹性强、实时性高的场景。

- **何时可以选 Leaky Bucket？**  
  如果业务必须"无论如何严格匀速处理"（如带宽计费、流媒体严格平滑），或者流控目标本身就是消峰为主，而不是弹性拥抱突发。此时 Leaky Bucket 更简单、延迟更可控。IM 推送一般不要求如此极端的平滑。

**结论**：IM 推送限流场景**优选 Token Bucket**，既能削峰又能容纳业务常见突发，业界主流实践。

#### Token Bucket 和 Leaky Bucket 实现详解

**1. Token Bucket（令牌桶算法）**

- **核心思想**：  
  令牌桶按固定速率往桶中加入"令牌"，桶内令牌最多积攒到上限。每来一条推送请求时，若桶内有令牌则取出一个，允许通过；若没有令牌则拒绝/等待/丢弃。支持一定的突发速率（桶有积累）。

- **伪代码实现：**

  ```
  初始化：桶容量 = MAX_TOKENS，当前令牌数 = MAX_TOKENS，补充速率 = r（每秒补 r 个令牌）
  // MAX_TOKENS 表示可承受的最大突发流量，建议根据最大QPS和允许突发的秒数设置，如 MAX_TOKENS = 最大QPS × 突发秒数。
  // MAX_TOKENS 太小易丢消息，太大可能堆积延迟。一般设置为1~2秒最大QPS能力即可，具体可根据业务实际监控动态调整。

  请求处理流程：  
    now = 当前时间戳
    elapsed = now - 上次补充时间    // elapsed 没有限定必须是1秒、2秒，可为任意非负数，表示距离上次补充经过了多少秒（或毫秒）
    // elapsed 一般建议小于1秒，这样才能及时响应最大QPS场景。实际越高频补充令牌（如ms级），对高并发突发的响应越丝滑，避免一秒才补一次造成流控不够精细。
    // r 通常是每秒可产生的最大令牌数，对应预计的最大平滑QPS能力。例如最大能1秒处理2000条，则 r=2000。
    补充令牌数 = elapsed * r       // 计算间隔内应生成的令牌数量，elapsed 单位和 r 的单位（如秒）需一致
    当前令牌数 = min(MAX_TOKENS, 当前令牌数 + 补充令牌数)
    上次补充时间 = now

    如果 当前令牌数 >= 1：
        当前令牌数 -= 1
        允许通过
    否则：
        拒绝/丢弃/排队
  ```

- **特性**：允许在短时间内消耗多个令牌（应对突发），平时速率受"令牌生成速率 r"控制，可累计未消费令牌，适合 IM 推送经常性"突发+平稳"并存的流量场景。

---

**2. Leaky Bucket（漏桶算法）**

- **核心思想**：  
  漏桶算法就像一个有出水口的水桶——"进水"可快可慢，但"漏水"永远是恒定速度。消息（请求）先进入桶里排队，按恒定速率排队流出。桶满时新请求溢出丢弃或等待。

- **伪代码实现：**

  ```
  初始化：桶容量 = MAX_QUEUE，出水速率 = r（每秒处理 r 条）
  // MAX_QUEUE 取1-5秒的QPS能力，平衡堆积和丢弃。例如qps=1000，建议 MAX_QUEUE=1000~5000。
  ```

  请求处理流程：
    // 桶队列长度指当前排队待处理的请求数量（即排队队列的元素个数，不是单个请求的数据长度）
    如果 当前队列中的请求数 < MAX_QUEUE：
        把请求加入桶队列
    否则：
        拒绝/丢弃

  处理线程（定期滴漏出水）：
    // 每 1/r 秒（即每隔 1/r 秒处理一次，r 是系统每秒允许处理的最大QPS/速率）
    // 例如 r = 1000，则每 1/1000 = 0.001 秒（即1毫秒）滴一次水，严格匀速；这个 r 就是"QPS"（每秒处理请求数）的设置
    // 换句话说，QPS=r，每 1/r 秒执行一次出队操作
    每 1/r 秒：
        如果 桶队列不为空：
            移除并处理最早加入的请求
  ```

- **特性**：进来的请求被严格匀速输出，无积压能力时超出的会被丢弃。适合需要"甩开突发，只允许匀速"的流控场景，一般不适用于 IM 推送这种需要支持瞬时高峰吞吐的应用，而更适合于限带宽或超强平滑负载场景。

---

**3. 应用场景选择小结**

- **Token Bucket**：IM push（推送）领域主流做法，兼容高突发与平均速率要求，适合高并发、流量波动明显的系统。
- **Leaky Bucket**：更适用于限制严格匀速消耗（比如带宽、流式音视频），对瞬时突发容量需求小。

---

#### 重发机制

**原因**：
- 下游连接异常/网络抖动/对方短暂离线，导致消息未送达，保障最终送达率。

**常见做法**：
- 设置"最大重试次数"和"重试间隔"。
- 支持指数退避、定时重试（如1s、3s、10s、1min...），防止线性放大流量冲击。
- 重试记录入本地队列/数据库，方便监控、排查。
- 单聊业务可自定义重试条件，如强送达（告警、支付消息）与弱送达（促销类可丢弃）。

**重发队列设计**：

重发机制**并不会直接依赖"旧的主内存推送队列"**，而是采用**单独的重试任务队列（Retry Queue）或持久化存储**进行管理。主要原因如下：

1. **解耦主推送与重试任务**：主推送队列主要负责第一次投递、及时处理新消息，在高吞吐时不可被重发消息占用过多资源。
2. **重试任务特性不同**：重发往往有特定时间间隔（如指数退避/定时轮询），与主队列"实时推送"调度机制不同。
3. **容灾与幂等性保证**：重发任务通常要持久化（如写本地磁盘、DB，或 Redis 持久 KV），这样服务重启、不用担心重发丢失或重复投递。
4. **便于精细控制与监控**：比如不同业务/用户设置不同重发策略，监控重发成功率、排查异常等。

**典型实现方式**：
- 推送失败后，将失败消息及重发参数（间隔、下次尝试时间、重试次数等）写入"重发队列"或数据库表（如：push_retry_task）。
- 定时调度器或后台线程，定期扫描到期重试的消息并重新入主队列或直接投递。
- 成功或重试超限后，自动删除重试记录，并做监控告警或人工处理。

**重发流程**：

当一条消息投递（发送）出去后，系统会立即将其相关信息（如消息内容、目标、重试参数等）加入一个独立的重试队列或任务表中（可以是内存队列，也可以持久化存储如 DB、Redis 等）。
- 如果客户端及时响应（比如收到消息确认/ack），系统就会移除该消息在重试队列中的记录，后续无需再重发。
- 如果在设定时间内未收到客户端响应，则由定时调度/后台线程根据重试策略（如重试次数、间隔、指数退避等）尝试再次推送消息，直到收到响应、达到最大重试次数，或业务判定无需继续。

**结论**：重试队列和主推送队列是相互独立的，消息送达且客户端响应后才会从重试队列彻底剔除，否则会持续按照策略进行重发处理。

## 5.10 在线/离线判定归属

**问题**：是pushserver自己查用户在线状态再决定在线推还是离线推？还是在msgserver里面这么做？

**结论**：在主流 IM 设计中，**一般由 PushServer 自己判断用户在线状态，然后决定采用"在线推送"还是走"离线厂商推送"**，而不是在 msgserver 决策。原因和流程详解如下：

1. **PushServer 判断在线状态的主要原因**
    - PushServer 的职责就是"投递各种消息到目标终端"，它天然需要实时掌握用户的在线/离线状态（如每台推送接入网关有用户连接保持，或有在线状态 Redis/内存表同步）。
    - 只有 PushServer 收到新消息、去查目标用户的在线状态，才能决定：
        - 在线则通过长连接直推到终端；
        - 离线则投递到厂商推送（小米/华为/APNS/FCM等）或写入离线消息表。
    - 这样做可以最大化减少依赖链路的延迟，提高推送响应效率，也便于后续推送链路的扩展（批量/合并/重试）。

2. **msgserver 的职责通常仅为：**
    - 负责接入、鉴权、路由和持久化、生成消息ID等，不负责到底怎么推送（消息到 pushserver 后转给谁，由 pushserver 判定）

3. **实际大厂流程举例**
    - 用户上线、掉线时，会触发 pushserver 或其关联的在线状态服务做状态同步（如Redis分布式内存表同步）。
    - pushserver 收到一条新消息，自己查在线表（内存/Redis），大批量时支持批查。
    - 对在线的做长连接直推，离线则写离线表+走三方推送。
    - **只有当多地部署，相互协作时，可能有一个组件专门做在线判断，但依然是推送链路的专属服务，而不是msgserver主业务逻辑。**

4. **这样设计的优点**
    - 使得推送服务与主消息路线解耦，推送链路的异步优化、弹性策略可以独立演进。
    - 在线状态一旦变化，只需同步 pushserver 即可，不用反复通知msgserver/业务服务。
    - 易于扩展各种推送端（PC、手机、小程序等）和接入不同厂商推送通道。

**结论**：绝大多数 IM 架构中，"是否在线"由 pushserver 判定和处理，由其决定采用在线直推还是下发厂商离线通道。msgserver 负责消息鉴权、落库和基本路由，不介入推送决策。

## 5.13 在线状态管理 FAQ

**问题**：心跳是谁发的？同步方式太复杂，能不能以用户为单位，用lru管理"最近活跃群成员"，没有命中的再查redis？

#### 群聊在线状态缓存方案：LRU缓存+Redis兜底

这个方案主要针对**群聊成员在线状态的缓存**。实战工程普遍采用本地 LRU/TTL 缓存最近访问或活跃的群成员在线快照，结合 Redis 群成员在线总表做兜底查询：

- **本地lru缓存（群维度优先）**
  - pushserver 层可用 lru+ttl 方式缓存最近访问最频繁或活跃的群（如最近1万~2万群 ID），把每个群的"成员在线状态快照"存在本地内存。
  - 命中本地缓存后可快速判定群成员谁在线，极大提升推送效率并降低 Redis 压力。
  - 缓存内容以"群ID->成员在线状态map"为主，也可包含设备维度信息。

- **缓存未命中或过期时再查Redis**
  - 缓存对象如果未命中或已过期（如ttl 30秒），则回源查 Redis 集群的"群成员在线主表"拉取全量数据，保证准确。
  - 本地缓存刷新后，只负责加速，不会丢失任何状态。

- **一致性与数据源说明**
  - 本地 lru/ttl 缓存只是加速手段，所有权威状态仍依赖 Redis 的全量主表。
  - 只要未命中走 Redis，推送准确性和一致性不会被破坏。

- **推送节点间无需复杂同步**
  - 各节点缓存群成员状态只做本地层面优化，无需全网分发或广播同步。所有节点直接以 Redis 为真源即可，灵活扩容简单可靠。
  - 群成员上线/下线由 IM 侧心跳或事件驱动，刷新 Redis 在线主表即可。

**结论**：群聊推送场景下，pushserver 常用 lru/ttl 策略缓存最近活跃群的在线快照，不命中或过期查 Redis 群表，高性能兼顾高一致性，适合大流量场景。这是 IM 群聊推送业界标准做法之一。

## 5.14 单聊在线状态主流查 Redis

**单聊在线状态为什么通常直接查 Redis，不做本地缓存？详解如下：**

| 优势         | 说明                                                                                                   |
| ------------ | ------------------------------------------------------------------------------------------------------ |
| 高并发       | Redis 单机可支撑几十万、百万级 QPS，完全满足单聊在线查询需求                                             |
| 低延迟       | 查询在线状态一般只需亚毫秒到几毫秒，时延极低                                                           |
| 本地缓存同步成本高 | 单聊用户分布随机、长尾特性明显，若用本地缓存需复杂同步，一致性难维护，容易出错；直接查 Redis 更简单靠谱    |
| 实时准确     | 状态权威来源于 Redis，杜绝本地过期、站点切换等导致的状态不准确，推送不会遗漏或误发                      |
| 易扩展       | Redis 易集群和分片，适应亿级规模增长，运维简单                                                         |
| 成熟可靠     | 社区方案成熟，配套高可用监控与运维工具丰富，是主流技术选型                                             |

**结论**：单聊推送直接查 Redis 在线状态，无需本地缓存，是最常用且可靠的工程做法。

#### 单聊同步上下线复杂，直接查 Redis 更高效；群聊适合本地缓存

| 场景   | 是否本地缓存 | 主要难点/原因                                     | 适用策略                   |
| ------ | ------------ | ------------------------------------------------ | -------------------------- |
| 单聊   | 否           | 用户分布极度长尾，访问随机且分散，缓存命中率低  | 直接查 Redis               |
|        |              | 在线状态需极高实时性，本地同步难且维护成本高    |                            |
|        |              | Redis 支持极高并发、查询延迟极低               |                            |
|        |              | 用户上线/下线高度分散，频繁波动，需强一致且同步复杂 |                           |
|        |              | 本地若做缓存需同步所有节点，维护和一致性代价高      |                            |
|        |              | Redis 查询高并发高可用，满足实时性，省去同步复杂度  |                            |
·| 群聊   | 是           | 热门群成员上下线更集中，有明显访问热点               | 本地 LRU/TTL 缓存 + Redis  |
|        |              | 群聊批量推送查询，缓存易命中，极大减轻 Redis 压力    |                            |
|        |              | 本地缓存失效兜底查 Redis，简单高效                  |                            |

**总结**：  
- 单聊场景下，用户上下线事件分布极广，若本地缓存则全网同步难度极高且易出错，直接查 Redis 避免复杂同步，符合高并发高一致性 IM 需求。  
- 群聊往往有热点群和活跃批量推送需求，本地缓存提升命中率、减少查询压力，是主流高效做法。
