# MySQL 写入流程（DML 修改）

> 本文档详细解析 MySQL InnoDB 存储引擎的 DML 写入流程，涵盖 Undo Log、Buffer Pool 修改、Redo Log Buffer、两阶段提交（2PC）以及后台刷脏等核心机制。

---

## 写入流程总览

```
                        事务开始 (BEGIN)
                              │
                     ┌────────▼────────┐
                     │   执行 DML SQL   │
                     │ INSERT/UPDATE/   │
                     │ DELETE           │
                     └────────┬────────┘
                              │
          ┌───────────────────┼───────────────────┐
          │                   │                   │
   ┌──────▼──────┐   ┌───────▼───────┐   ┌───────▼───────┐
   │ ① 写 Undo    │   │ ② 修改 Buffer  │   │ ③ 写 Redo     │
   │    Log       │   │    Pool 数据    │   │    Log Buffer  │
   │ (回滚段)     │   │ (内存中的页)   │   │ (记录页修改)   │
   │ 记录修改前   │   │ 标记为脏页     │   │ 顺序追加写入   │
   │ 的值         │   │ (加入FlushList)│   │                │
   └──────┬──────┘   └───────┬───────┘   └───────┬───────┘
          │                   │                   │
          └───────────────────┼───────────────────┘
                              │
                     ┌────────▼────────┐
                     │  COMMIT 提交     │
                     └────────┬────────┘
                              │
              ╔═══════════════╧═══════════════╗
              ║      两阶段提交 (2PC)          ║
              ║                               ║
              ║  Phase 1:                     ║
              ║  ④ Redo Log 刷盘 + Prepare    ║
              ║     fsync ib_logfile          ║
              ║                               ║
              ║  Phase 2:                     ║
              ║  ⑤ 写 Binlog + fsync          ║
              ║  ⑥ Redo Log Commit            ║
              ╚═══════════════════════════════╝
                              │
                     ┌────────▼────────┐
                     │  ⑦ 返回客户端成功 │
                     └────────┬────────┘
                              │
                     ┌────────▼────────┐
                     │  ⑧ 后台异步刷盘  │
                     │ (Page Cleaner)  │
                     │  脏页 → 数据文件 │
                     └─────────────────┘
```

## 各步骤深入分析

### 步骤①：写入 Undo Log

```
为什么需要 Undo Log？
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
 ① 事务回滚：    记录修改前的值，ROLLBACK 时恢复原值
 ② MVCC：       构建版本链，支持非锁定一致性读（快照读）
 ③ 崩溃恢复：   崩溃恢复需要 Undo 来辅助回滚未提交的事务

Undo Log 与 Redo Log 的关系：
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  重要：Undo Log 的修改本身也会产生 Redo Log！
        （为了保证 Undo 的持久性，Undo 页的修改也受 Redo 保护）

  也就是说：写 Undo Log → 产生 Redo Log → 这个 Redo 保护的就是 Undo 页

Undo Log 版本链示例：
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  原始行数据：id=100, name='Tom', age=25

  事务A UPDATE age=26：
    当前版本 (age=26, trx_id=100, roll_ptr →)
    Undo版本  (age=25, trx_id=90, roll_ptr →)
    Undo版本  (age=24, trx_id=80, roll_ptr → null)

  版本链通过 roll_ptr（回滚指针）串联，MVCC 根据 ReadView 选择合适版本
```

### 步骤②：修改 Buffer Pool

```
UPDATE users SET age = 26 WHERE id = 100;

InnoDB 内部操作（以主键更新为例）：

  1. 在 Buffer Pool 中找到或加载 id=100 所在的数据页
  2. 在页内定位到 id=100 的行记录
  3. 将 age 从 25 修改为 26
  4. 把该页标记为"脏页"（Dirty Page）
  5. 将脏页加入 Flush List（等待后台刷盘）

关键概念：
  ┌─────────────────────────────────────────────────────┐
  │ 脏页 (Dirty Page)                                    │
  │  - Buffer Pool 中已被修改，但尚未写入磁盘的数据页     │
  │  - 由 Page Cleaner 线程批量刷盘                      │
  │  - Redo Log 保证脏页的修改在崩溃后可恢复             │
  │                                                      │
  │ 脏页比例（innodb_max_dirty_pages_pct，默认75%）       │
  │  - 超过阈值时强制同步刷盘，可能导致性能骤降          │
  └─────────────────────────────────────────────────────┘
```

### 步骤③：写入 Redo Log Buffer

```
Redo Log (重做日志) 的作用：
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  保证 ACID 中的持久性（Durability）
  记录数据页的物理修改，崩溃后通过重放 Redo Log 恢复未刷盘的脏页

Redo Log 写入流程：
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  修改数据页
       │
       ▼
  ┌──────────────────────┐
  │  Redo Log Buffer      │  ← 内存中，事务执行时实时写入
  │  (innodb_log_buffer_  │
  │   size, 默认16MB)     │
  └──────────┬───────────┘
             │ 触发刷盘时机：
             │ - 事务提交 (prepare阶段)
             │ - Redo Log Buffer 满
             │ - 脏页刷盘前(WAL)
             │ - 每秒定时刷
             ▼
  ┌──────────────────────┐
  │  ib_logfile0          │  ← 磁盘文件，循环写入
  │  ib_logfile1          │     固定大小 (innodb_log_file_size)
  └──────────────────────┘

Redo Log 格式：
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  Redo Log 不是记录"改了哪个字段"，而是记录"哪个页的哪个偏移量，写入什么"

  示例（逻辑表示）：
    页号: 1234, 偏移量: 120, 内容: [将 age 25 改为 26]
    页号: 9999, 偏移量: 88,  内容: [修改 Undo 页，记录旧值]

  LSN (Log Sequence Number)：Redo Log 的全局递增序列号
    - 每次写入 Redo Log，LSN 递增
    - 数据页上记录最新修改的 LSN
    - 恢复时：数据页 LSN < Redo Log LSN → 需要重放
```

### 步骤④-⑥：两阶段提交 (2PC)

```
为什么需要两阶段提交？
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  Redo Log (InnoDB 引擎层) 和 Binlog (Server 层) 是两套独立系统
  必须保证二者一致 → 要么都成功，要么都失败

Phase 1: Prepare
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  ┌──────────────────────────────────────┐
  │  Redo Log Buffer → fsync → ib_logfile │
  │  事务状态标记为 TRX_PREPARED          │
  │  此时数据在 Buffer Pool 已修改        │
  │  但引擎层尚未 Commit                  │
  └──────────────────────────────────────┘

Phase 2: Commit
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  ┌──────────────────────────────────────┐
  │  ① 写 Binlog (Binlog Cache → fsync)   │
  │    包含所有DML语句 + XID event        │
  │                                      │
  │  ② Redo Log 写入 Commit 标记         │
  │    通知 InnoDB 引擎层正式提交         │
  └──────────────────────────────────────┘

Binlog 内容示例 (ROW 格式)：
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  ### UPDATE `test`.`users`
  ### WHERE
  ###   @1=100                   -- id (修改前)
  ### SET
  ###   @1=100                   -- id (修改后)
  ###   @2='Tom'                 -- name
  ###   @3=26                    -- age (修改后)
  ### XID = 12345                -- 事务标识
```

### 步骤⑦-⑧：返回成功 + 后台刷脏

```
数据一致性保障的时间线：
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  提交时 (同步, 安全保证)                    提交后 (异步, 性能优化)
  ┌─────────────────────────┐          ┌─────────────────────────┐
  │ ✓ Redo Log (Prepare)    │          │ ○ 脏页刷入数据文件       │
  │ ✓ Binlog 写入           │          │   Page Cleaner 后台执行  │
  │ ✓ Redo Log (Commit)     │          │   批量刷脏页到磁盘       │
  │   → 返回客户端成功       │          │   包含共享表空间和.ibd   │
  └─────────────────────────┘          └─────────────────────────┘

  崩溃恢复保证：
    只要 Redo Log + Binlog 已刷盘，数据就不会丢失
    即使脏页还没写入数据文件，崩溃后可通过 Redo Log 重放恢复
    这就是 WAL (Write-Ahead Logging) 的核心思想

WAL (预写日志) 原则：
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  在将数据页写入磁盘之前，必须先将对应的 Redo Log 写入磁盘

  目的：
    数据页的写入是"随机写"（不同页分布在不同磁盘位置）
    Redo Log 的写入是"顺序写"（追加写，机械盘/SSD性能都好）
    先写 Redo Log（快），再慢慢刷脏页（慢），兼顾性能和安全性
```
