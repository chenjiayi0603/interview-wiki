# MySQL分库分表

See also: [[MySQL存储引擎]]

## 分库分表的原因
- **数据量过大**：单表数据量达到千万级别，查询性能下降
- **并发过高**：单库无法支撑高并发读写
- **存储空间**：单库存储空间不足

## 分库分表策略

### 水平分表（Sharding）
- **按范围分表**：如按时间、ID范围分表
  - 优点：查询范围明确，易于扩展
  - 缺点：可能存在数据倾斜
- **按哈希分表**：根据某个字段的哈希值分表
  - 优点：数据分布均匀
  - 缺点：范围查询困难
- **按目录分表**：使用一致性哈希等算法

### 垂直分表
- 将大表按列拆分为多个小表
- 将热点字段和冷字段分离

### 分库
- 按业务模块分库（如用户库、订单库、商品库）
- 按数据特征分库（如按地区分库）

## 分库分表带来的问题

### 1. 跨库/跨表查询
- **问题**：需要查询多个库/表的数据
- **解决方案**：避免跨库/跨表查询，在应用层聚合；使用分布式数据库中间件（如ShardingSphere、MyCat）

### 2. 分布式事务
- **问题**：跨库事务难以保证ACID特性
- **解决方案**：使用分布式事务框架（如Seata）；最终一致性方案（如消息队列）

### 3. 主键ID生成
- **问题**：需要保证全局唯一
- **解决方案**：雪花算法（Snowflake）；UUID；数据库自增ID + 分库分表规则

### 4. 数据迁移
- **问题**：分库分表后需要迁移历史数据
- **解决方案**：双写方案（新老系统同时写入）；数据同步工具

## 实践建议
1. **不要过早分库分表**：先通过索引优化、读写分离等方式提升性能
2. **选择合适的分片键**：选择区分度高、查询频繁的字段
3. **考虑扩容**：设计时要考虑未来扩容的便利性
4. **监控和运维**：建立完善的监控和运维体系
