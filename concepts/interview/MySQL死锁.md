# MySQL 死锁

## 一、死锁概述

**死锁**：两个或多个事务相互等待对方释放锁，都无法继续执行。发生死锁的进程无法进行下去，所持资源也无法释放，会导致 CPU 吞吐量下降、浪费系统资源。

---

## 二、死锁的四个必要条件（通用理论）

四个条件**同时满足**时才会发生死锁：

| 条件 | 说明 |
|------|------|
| **互斥** | 资源一次只允许一个进程访问，该进程未释放前其他进程不能访问。 |
| **占有且等待** | 进程已占有部分资源，同时还在等待其他进程释放资源。 |
| **不可抢占** | 已分配给某进程的资源不能被强行抢占。 |
| **循环等待** | 存在进程链：每个进程都占有下一个进程需要的至少一种资源。 |

**解决思路**：破坏其中至少一个条件（互斥通常不能改，主要针对后三个）。

---

## 三、死锁的解决思路（通用）

### 1. 死锁预防

确保系统**永远不会进入**死锁状态。  
做法：从设计上破坏「占有且等待」「不可抢占」「循环等待」中的至少一个（如：一次性申请所有资源、规定资源申请顺序等）。

### 2. 死锁避免

在**分配资源前**做判断，只允许不会导致死锁的申请。  
典型方法：**银行家算法**。

### 3. 死锁检测与解除

允许系统进入死锁，**定期检测**；检测到死锁后，选择代价最小的事务**回滚**以解除死锁。

## 四、MySQL（InnoDB）与死锁

### 4.1 为什么 MySQL 会形成死锁

- 锁要等**事务结束**（commit/rollback）才会释放。
- InnoDB 使用 **两阶段锁协议（2PL）**，加锁阶段没有顺序要求，且不必一次锁住所有要用的数据，因此容易产生**循环等待**，从而死锁。

### 4.2 并发控制：MVCC 与两阶段锁

- **MVCC**：多版本并发控制，用于读一致性和部分隔离级别。
- **两阶段锁协议（2PL）**：  
  - **扩展阶段**（事务开始后、commit 前）：只加锁，不释放。  
  - **收缩阶段**（commit 后）：释放锁，且不再申请新锁。  

两阶段锁保证了可串行化调度，但加锁顺序不固定，故可能死锁。

### 4.3 InnoDB 如何处理死锁

| 方式 | 说明 |
|------|------|
| **等待超时** | `innodb_lock_wait_timeout=50`（默认 50 秒），超时后报错。 |
| **死锁检测（推荐）** | `innodb_deadlock_detect=on`（默认 on），发现死锁后主动回滚**代价最小**的事务，让其他事务继续。 |

**死锁检测原理**：构建「事务为顶点、锁为边」的**有向图**，若存在**环**则判定为死锁。  
**回滚选择**：一般回滚**修改/插入/删除行数最少**的事务，依据 `INFORMATION_SCHEMA.INNODB_TRX` 的 `trx_weight` 等判断。

**Q: 死锁检测有后台线程单独定时检查吗？依据是什么？**

A:  
InnoDB 的**死锁检测**（`innodb_deadlock_detect=on`，默认开启）**不是依靠定时的后台线程**，而是在每次事务加锁（`lock_request`）发生等待（`wait for lock`）时，**由当前加锁线程主动触发死锁检测算法**。

- **实现原理**：  
  当事务因需要等待被其它事务占用的锁而阻塞，InnoDB 会立即沿着等待链构建「等待图」，遍历当前所有锁与事务——
  - 发现存在「环」，即形成**循环等待**，则判定死锁，选择其中一个事务回滚（通常是回滚代价最小的那一个）。
  - 没有环，则正常等待 lock wait timeout。

- **死锁检测的依据**：  
  - **锁依赖（等待图）**：每个阻塞的事务都记录其等待的锁与已持有的锁，系统构建"事务为节点、锁为边"的**有向图**。
  - 在加锁冲突时实时扫描此图，检查是否出现环。
  - 不会定时批量扫描全体事务，只在每次加锁冲突时做「局部」死锁检测。

- **相关提示**：  
  - 对高并发大事务场景，死锁检测遍历所有等待链可能带来额外 CPU 消耗，可根据负载评估是否关闭死锁检测，转而依赖 `innodb_lock_wait_timeout` 管理（但推荐保留检测功能）。
  - 所有死锁信息会记录于 `SHOW ENGINE INNODB STATUS` 及错误日志，便于排查。

**简要总结：**  
MySQL/InnoDB 的死锁检测不是靠周期性线程定时检查，而是每遇到等待锁冲突时，由当前请求线程实时根据锁等待依赖关系（有向图）判断是否死锁。

## 五、MySQL 常见死锁场景与避免

### 5.1 场景一：多表访问顺序不一致

- **现象**：会话 A 锁表 A 再访问表 B，会话 B 锁表 B 再访问表 A → 互相等待。
- **避免**：  
  - 多表操作时**约定相同访问顺序**（如总是先 A 后 B）。  
  - 必须锁多表时，**任何时刻都按同一顺序**加锁。

### 5.2 场景二：同一行上的锁升级冲突

- **现象**：A 对某行持有**共享锁**并要升级为**独占锁**，B 对该行要加**独占锁** → A 等 B、B 等 A。
- **常见原因**：同一按钮被重复点击，同一段代码对同一条记录多次加锁/更新。
- **避免**：  
  - 前端：点击后**立刻禁用按钮**，防止重复提交。  
  - **乐观锁**：基于版本号/时间戳，更新时带条件（如 `WHERE version = ?`）。  
  - **悲观锁**：如 `SELECT ... FOR UPDATE`，注意长事务会放大锁持有时间，需谨慎。

### 5.3 通用避免建议

- **短事务**：操作完尽快 commit，尤其交互式命令行中。
- **统一修改顺序**：修改多表、多行时，**各事务内顺序一致**（例如都按主键或按表名顺序）。
- **合理索引**：减少锁范围，行锁在索引列上，索引合适可减少锁冲突。
- **必要时表锁**：在业务允许时，可对整表加锁（如 `LOCK TABLES t1, t2`）避免死锁，但会降低并发。

## 六、死锁排查与解决（命令速查）

### 6.1 收集死锁信息

```sql
-- 查看最近一次死锁原因
SHOW ENGINE INNODB STATUS;
```

调试时可开启，把**所有**死锁写入错误日志：

```ini
innodb_print_all_deadlocks = 1
```

### 6.2 查看锁与事务

```sql
-- 当前运行的事务（含 trx_weight，用于判断回滚谁）
SELECT * FROM information_schema.INNODB_TRX;
-- trx_rows_locked: 锁定行数  trx_rows_modified: 修改行数

-- 正在持有的锁
SELECT * FROM information_schema.INNODB_LOCKS;

-- 正在等待锁的等待关系
SELECT * FROM information_schema.INNODB_LOCK_WAITS;

-- 是否有表被锁
SHOW OPEN TABLES WHERE In_use > 0;

-- 当前会话/进程列表
SHOW PROCESSLIST;
```

### 6.3 终止会话（需足够权限）

```sql
KILL <process_id>;   -- 例如 KILL 4503;
```

## 七、小结

| 层面 | 要点 |
|------|------|
| **条件** | 互斥 + 占有且等待 + 不可抢占 + 循环等待 → 死锁。 |
| **InnoDB** | 两阶段锁 + 无固定加锁顺序 → 可能死锁；通过超时或死锁检测（默认）解除。 |
| **避免** | 短事务、统一访问/修改顺序、合理索引、前端防重、乐观/悲观锁按需选用。 |
| **排查** | `SHOW ENGINE INNODB STATUS`、`INNODB_TRX/LOCKS/LOCK_WAITS`、`SHOW PROCESSLIST`、`KILL`。 |
