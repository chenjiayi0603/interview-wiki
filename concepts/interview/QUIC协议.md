## 一、QUIC 基础

### 1.1 是「可靠 UDP」吗？

- **底层**：基于 UDP（无连接、不可靠）
- **上层**：在 UDP 之上实现了类似 TCP 的可靠传输
  - 数据确认（ACK）
  - 丢包重传
  - 有序交付
  - 拥塞控制、流量控制
- **结论**：QUIC 是「在 UDP 之上实现的可靠传输协议」，常被称作可靠 UDP

### 1.2 面向连接吗？

- **是**，QUIC 在应用层实现面向连接逻辑：
  - 有握手（1 RTT，0-RTT 恢复）
  - 有连接标识（Connection ID）
  - 有连接状态（流、拥塞控制等）
  - 有显式关闭（CONNECTION_CLOSE 帧）
- **与 TCP**：都用连接；QUIC 用 Connection ID 标识，便于连接迁移（换 IP/端口不断连）

### 1.3 握手与挥手

| 阶段 | TCP | QUIC |
|------|-----|------|
| **握手** | 3 次握手（1 RTT）+ TLS（1～2 RTT）≈ 2～3 RTT | 连接建立 + TLS 1.3 合并，通常 1 RTT；会话恢复可 0 RTT |
| **挥手** | 四次挥手（FIN-ACK 往返） | 任一端发 CONNECTION_CLOSE 帧即可，更轻量 |
| **半关闭** | 支持 | 不支持 |

## 二、有序性与队头阻塞

### 2.1 有序性

| 范围 | 有序性 | 说明 |
|------|--------|------|
| **流内** | 有序 | 同一流内按序交付 |
| **流间** | 无序 | 不同流独立，无顺序要求 |

### 2.2 队头阻塞

- **流内**：有队头阻塞——同一流内若包 2 丢失，包 3、4、5 须等待重传
- **流间**：无队头阻塞——流 A 阻塞不影响流 B、C、D
- **与 TCP 对比**：TCP 单流，任何丢包阻塞整条连接；QUIC 多流，仅阻塞该流

```
TCP:  一个连接 = 一个流 → 任何丢包阻塞整连接
QUIC: 一个连接 = 多个流 → 丢包只阻塞对应流
```

## 三、为什么需要 QUIC（有 TCP 了还要 QUIC）

| 痛点 | TCP 局限 | QUIC 方案 |
|------|----------|-----------|
| 队头阻塞 | 单流，丢包阻塞全连接 | 多流，流间独立 |
| 连接建立慢 | 2～3 RTT 才能发数据 | 1 RTT，0-RTT 恢复 |
| 协议难演进 | 内核实现，升级慢 | 用户态，可快速迭代 |
| 连接迁移 | 换 IP/端口即断连 | Connection ID，支持迁移 |
| 加密 | 需额外 TLS | 内置 TLS 1.3 |
| 拥塞控制 | 内核固定，难换算法 | 用户态可插拔 |

## 四、流量控制

### 4.1 与 TCP 的区别（概念）

| 维度 | TCP | QUIC |
|------|-----|------|
| 粒度 | 连接级，一个窗口 | 连接级 + 流级，每流独立窗口 |
| 机制 | TCP 头部 window 字段 | WINDOW_UPDATE 帧 |
| 优势 | 实现简单 | 流级限速，更细粒度 |

### 4.2 实现层面

| | TCP | QUIC |
|---|-----|------|
| 机制 | 接收方在 ACK 中带 rwnd，16 位（可 scaling） | WINDOW_UPDATE 帧，64 位 offset |
| 发送条件 | inflight ≤ min(cwnd, rwnd) | 同时受连接窗口、流窗口、cwnd 约束 |

## 五、拥塞控制

### 5.1 与 TCP 的区别（概念）

| 维度 | TCP | QUIC |
|------|-----|------|
| 实现位置 | 内核 | 用户态 |
| 算法 | 内核固定（Reno、CUBIC 等） | 可插拔（CUBIC、BBR 等） |
| 演进 | 需内核/系统升级 | 应用层即可更新 |

### 5.2 实现层面

| | TCP | QUIC |
|---|-----|------|
| 位置 | 内核 net/ipv4/tcp_*.c | 用户态库（quiche、Chromium 等） |
| 丢包感知 | 内核处理 ACK、重传 | 库解析 ACK 帧、重传逻辑 |
| 算法 | 编译进内核 | 独立模块，可切换 |

## 六、CUBIC 与 BBR

### 6.1 TCP 支持情况

| 算法 | Linux 内核 | 默认 |
|------|------------|------|
| CUBIC | 2.6.19+ | 多数发行版默认 |
| BBR | 4.9+ | 需手动切换 |

```bash
sysctl net.ipv4.tcp_congestion_control   # 查看
sysctl -w net.ipv4.tcp_congestion_control=bbr  # 切换 BBR
```

### 6.2 CUBIC vs BBR

| | CUBIC | BBR |
|---|-------|-----|
| 类型 | 基于丢包（loss-based） | 基于模型（model-based） |
| 拥塞信号 | 丢包 = 拥塞，降速 | 不依赖丢包，用带宽/RTT 估计 |
| 丢包后 | cwnd 乘 β（如 0.7） | 一般不降速 |
| 窗口增长 | 三次函数恢复 | 按 BtlBw × RtProp 估算 |
| 弱网/随机丢包 | 易误判，吞吐下降 | 更稳健，吞吐更好 |

### 6.3 BBR 实现要点

**核心参数**：BtlBw（瓶颈带宽）、RtProp（传播时延）→ 目标 BDP = BtlBw × RtProp

**带宽估计**：
```
每收到 ACK：delivery_rate = 确认字节数 / 传输时长
BtlBw = 过去约 10 个 RTT 内的 max(delivery_rate)
```

**RtProp 估计**：
```
RtProp = 过去约 10 秒内的 min(RTT)
```

**四个状态**：
| 状态 | 目的 | 行为 |
|------|------|------|
| Startup | 快速探测带宽 | 指数增长直到增速低于阈值 |
| Drain | 排空队列 | 低速发送 |
| ProbeBW | 稳态 | 在 BtlBw 附近周期性探测 |
| ProbeRTT | 刷新 RtProp | 降 cwnd 至 4，测最小 RTT |

**关键公式**：
- pacing_rate = pacing_gain × BtlBw
- cwnd = cwnd_gain × BtlBw × RtProp

**与 CUBIC 本质区别**：不把丢包当拥塞信号，用带宽和 RTT 估计驱动 pacing 与 cwnd。

## 七、QUIC 使用场景

### 7.1 适用场景

| 场景 | 原因 |
|------|------|
| Web/HTTP（HTTP/3） | 多资源并发、短连接多，对建连 RTT、队头阻塞敏感 |
| 视频/直播 | 丢包敏感，流间解耦减少卡顿 |
| 移动 App | 网络切换频繁，连接迁移不断连 |
| 游戏/实时通信 | 0-RTT、低延迟、弱网优化 |
| IoT/弱网 | 高丢包下 BBR 等算法更稳 |

### 7.2 仍适合 TCP 的场景

- 存量系统只支持 TCP
- 设备/网络对 QUIC 支持差（老旧网关、企业策略）
- 简单长连接、对队头阻塞不敏感

## 八、速查小结

| 维度 | 要点 |
|------|------|
| 本质 | 基于 UDP 的可靠、面向连接传输协议 |
| 有序性 | 流内有序，流间无序 |
| 队头阻塞 | 流内存在，流间消除 |
| 流量控制 | 连接级 + 流级，WINDOW_UPDATE |
| 拥塞控制 | 用户态、可插拔，不依赖丢包（如 BBR） |
| 握手 | 1 RTT，0-RTT 恢复 |
| 挥手 | 发 CONNECTION_CLOSE 即可 |
| 典型用途 | HTTP/3、视频、移动、弱网 |
