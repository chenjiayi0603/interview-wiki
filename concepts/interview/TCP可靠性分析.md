# TCP可靠性分析

## 概述

TCP（传输控制协议）作为一种面向连接的协议，天生具备可靠性保障机制，下面从多个维度分析TCP如何实现传输的可靠性：

**1. 数据包有序传输**  
TCP保证字节流按发送顺序到达对端，不会乱序。每个报文段都有顺序号（sequence number），接收端按序号组装数据流。

**2. 丢包重传机制**  
TCP采用超时重传与快速重传机制：  
- 发送方每发送一个报文段就启动一个定时器，如果在超时时间内没收到ACK，会重发该报文段。  
- 若收到多个相同ACK（如3个），表明有数据丢失，立刻进行“快速重传”，无需等待超时。

**3. 数据校验**  
TCP头部包含16位校验和（checksum），对数据和头部字段进行校验。接收端若校验失败直接丢弃，确保数据不会被静默损坏。

**4. 流量控制**  
TCP用滑动窗口协议进行流量控制。接收窗口限制对方发送速率，防止缓冲区溢出或大面积丢包。

**5. 拥塞控制**  
TCP具备多套拥塞控制算法（如慢启动、拥塞避免、快重传、快恢复等），在网络质量变化时自适应调节发送窗口，减轻网络拥堵进一步提升可靠性。

**6. 建立连接与断开保证**  
通过“三次握手”建立连接，“四次挥手”断开连接。确保双方状态一致，避免因旧连接造成数据串扰、切换未完成等异常。

**小结**  
正因具备可靠传输机制（顺序、有确认、有重传、校验、流控/拥控），TCP可支撑金融、电商、文件传输、数据库等对数据正确性和完整性要求极高的业务场景。
但相比UDP多了更多逻辑，延迟和CPU占用略高，因此部分对极致低延迟（游戏、视频、物联网）业务仍选用UDP+业务自定容错。

## 对端关闭探测

### 正常关闭

- **正常关闭（对端调用close/exit，进行“四次挥手”）**：本端只要还在读写socket，很快就能发现（如`read`返回0，表示“对端关闭连接”）。
    - 若本端继续向已关闭的对端写数据，会收到 RST/reset 报文，写操作返回-1并设置`errno=ECONNRESET`。

### 异常关闭

- **异常断电/拔网线/进程kill（未走TCP正常断开流程）**：本端短期内感知不到！只有：
    - 继续发送数据，超时后尝试重传，最后才认为“不可达”，关闭连接。
    - 依赖**TCP保活（keepalive）**机制定期探测，但TCP默认不开启，且机制较慢。

### TCP保活工作机制

- 本端可通过`setsockopt(socket, SOL_SOCKET, SO_KEEPALIVE, ...)`启用keepalive。
- 参数（可调，内核不同略异）：
    - `tcp_keepalive_time`：空闲多久没通信，才开始发送保活探测包（Linux默认7200秒=2小时）。
    - `tcp_keepalive_intvl`：保活包间隔（默认75秒）。
    - `tcp_keepalive_probes`：连续收到多少个ACK无响应后，判定断开（默认9次）。
- **最坏情况下探测到对端已掉线，最快也需 2 小时+9*75=2,675 秒（近45分钟）！**  
  这些参数可通过`sysctl`或`setsockopt`调整（比如降低到10秒，适合敏感业务）。

**tcp_keepalive_time 和 tcp_keepalive_intvl 的区别如下：**

- tcp_keepalive_time（或 TCP_KEEPIDLE）：
    指的是一个连接在“多长时间没有数据通信（发送或接收）后”才开始第一次发送 TCP keepalive 探测包。
    举例：如果设置 tcp_keepalive_time=120，则这条连接空闲120秒后才第一次进行保活探测。

- tcp_keepalive_intvl（或 TCP_KEEPINTVL）：
    指的是“第一次保活探测未收到回应后”，后续每隔多长时间再重复发送一个保活包进行探测（即探测间隔时间）。
    举例：tcp_keepalive_intvl=10 指第一次探测无响应后，10秒后再发第二个，依此类推，直到达到探测次数上限（tcp_keepalive_probes / TCP_KEEPCNT）。

**总结：**
- tcp_keepalive_time（多久没通信后开始探测） → 首次探测时间间隔。
- tcp_keepalive_intvl（探测包重试间隔） → 多次探测之间的间隙。

**举例说明：**假设
  tcp_keepalive_time = 120
  tcp_keepalive_intvl = 10
  tcp_keepalive_probes = 3

则，连接空闲120秒后发送第1个保活探测包，若无响应，10秒后发第2个，再无响应10秒后发第3个，还无响应就认为连接已失效。

### 应用层如何主动感知？

- 定时主动“心跳”包（比如每5~10秒发，若N次收不到回应就判定断线），比TCP内建保活快得多。
- 适用于 IM、推送、业务网关等 **“强在线要求”**场景。

**实践总结**：
- 被动依赖TCP保活探测远端异常关闭，速度很慢，默认场景下通常需几十分钟甚至更久。
- 如果业务对掉线检测有明确时限，**务必应用层做“心跳检测”或调整TCP保活参数（如keepalive=30s）**！
- 不建议仅依赖TCP字段机制感知“死连接”。

**相关代码示例（C/C++）**：
```c
// 启用socket的TCP保活功能，并设定较短的超时时间：
int fd = socket(AF_INET, SOCK_STREAM, 0);
int keepalive = 1;
setsockopt(fd, SOL_SOCKET, SO_KEEPALIVE, &keepalive, sizeof(keepalive));
// 下面这些TCP参数通常需要root权限
int keepidle = 120;    // 2分钟空闲后探测
int keepintvl = 10;    // 探测间隔10秒
int keepcnt = 3;       // 3次失败判为掉线
// TCP_KEEPIDLE 对应的其实就是 Linux 内核参数 tcp_keepalive_time：
// setsockopt 里的 TCP_KEEPIDLE = tcp_keepalive_time，表示空闲多久后开始保活探测。
// 其它两个参数：TCP_KEEPINTVL、TCP_KEEPCNT 分别对应 tcp_keepalive_intvl、tcp_keepalive_probes。

setsockopt(fd, IPPROTO_TCP, TCP_KEEPIDLE, &keepidle, sizeof(keepidle));   // == tcp_keepalive_time
setsockopt(fd, IPPROTO_TCP, TCP_KEEPINTVL, &keepintvl, sizeof(keepintvl));
setsockopt(fd, IPPROTO_TCP, TCP_KEEPCNT, &keepcnt, sizeof(keepcnt));
```

**结论**：TCP能探测到对端关闭，但“异常断开（非正常close）”情况下依赖内建机制非常慢，强在线/IM/推送业务建议应用层心跳+合理设置TCP保活参数。

## TCP保活探测 vs 应用层心跳探测

**区别：**
- **TCP保活（keepalive）**：是操作系统提供的机制，底层自动探测连接对端是否还存活。它仅检测“物理连接是否已失效”——比如网线断开、服务器掉电、进程crash等，主要用于发现“僵尸连接”。但TCP保活一般探测周期较长（默认2小时空闲才开始探测），响应慢，适合“低实时性、物理存活检测”。
- **应用层心跳**：由业务系统主动以固定频率发送心跳数据包，可以自由控制心跳周期（如每隔5s、10s），收到对应ack或数据响应确认对端“业务活跃”。适用于IM、推送等需要“高实时在线感知”的场景。对端只要应用没响应（即使连接物理上还活着），应用层也能较快察觉异常。

**结论：**
- 有了TCP保活，还**需要应用层心跳探测**。TCP保活只保证“网络通”，不能及时发现应用进程假死、程序bug等“应用级掉线”。如果业务敏感（IM、金融、推送等），应**以应用层心跳为主，TCP保活为辅**，提高异常检测速度与在线可靠性。

## 应用层故障检测与TCP保活

**应用层的故障只靠应用层心跳才能发现**。下面详细释义：

- **TCP保活只能检测到“TCP连接的物理层断开”**（如拔网线、宕机、路由异常等极端情形），但**检测周期长**（通常几分钟到两小时），而且**完全感知不到“对方的应用死掉/卡死”等业务层异常**。
- 如果对方的应用进程“卡死”“阻塞”等（TCP连接依然存在），TCP协议栈看不到应用的健康情况，底层不会主动关闭连接，TCP保活机制也无能为力。
- **只有应用层心跳机制**（你主动发心跳包，对方应用正常处理并回包），**才能及时发现“应用级”故障（掉线、假死、网络半断等）**。

**出现故障后的处理**：
- 一般只要多次心跳未响应（如连续3~5次），认为对端已经不可用，可断开连接、切主、告警等。
- 这属于**应用层逻辑的容错与自动恢复**，需要由业务本身来定制，比如 IM 自动重连、推送重新订阅主机等。

**总结：**
- **TCP保活只能发现底层“物理”断链，不能感知业务故障。**
- **实时敏感的IM/推送/金融等，必须用应用层心跳+自定义超时，才能更快检测到“应用级”掉线、假死、缓慢/丢包等各类故障。**
- **实际生产环境，建议应用层主动心跳为主，TCP保活为辅。**

**简明表格举例：**

| 场景                   | 仅TCP保活能否发现 | 应用层心跳能否发现 | 检测速度（典型）|
|------------------------|:-----------------:|:-----------------:|:---------------:|
| 网线/断电/物理宕机     |     是（慢）      |     是（快）      |  >2分钟 vs 5秒  |
| 应用进程挂掉/假死/阻塞 |        否         |        是         |   X    vs 5秒   |
| 路由黑洞/网络半断      |   取决于链路      |        是         |   慢   vs 快    |
| 业务Server踢下线       |        否         |        是         |   X    vs 5秒   |

**代码举例：**

应用层心跳检测常用伪码（简化）：
```c
// 定时发送心跳包，检测N秒未收到响应则判定异常
int fail_cnt = 0;
int max_fail = 3;
while (running) {
    send_heartbeat();
    if (wait_response(timeout)) {
        fail_cnt = 0;
    } else {
        fail_cnt++;
        if (fail_cnt >= max_fail) {
            // 应用级超时，判定连接异常
            handle_disconnect();
            break;
        }
    }
    sleep(5); // 每隔5秒发送一次
}
```

> **结论：TCP保活只能兜底检测物理链路，无法及时发现应用故障。专业业务必须应用层心跳及时感知和处理异常。**

## TCP保活请求的响应方

**Q：对TCP保活（Keepalive）请求的响应是由操作系统完成还是服务应用？**

**答：TCP保活的请求与响应“全部由操作系统（内核协议栈）自动处理”，服务端应用层（如你的服务进程）**根本感知不到**、也无需主动参与。

—— 详细说明如下：

- **发起保活探测**：当一端设置了TCP_KEEPALIVE（保活），达到空闲时间后，操作系统TCP协议栈会自动发送“保活探测包”（Keepalive Probe，通常一个长度为0的ACK包），而不是由你的应用send/recv显式执行。
- **响应保活探测**：收到保活包的对端，响应也是**协议栈自动回一个ACK**，只要内核（网卡）还在、主机网络可达，就会自动完成。
- **应用不会看到任何保活相关事件**。如果对端应用进程挂掉、阻塞，甚至根本没在收/发数据，只要协议栈活着，也会自动响应。
- **只有在协议栈检测N次无响应（如对方断网、物理掉线），才会自动关闭socket，并在下次应用调用read/write时返回错误（如ECONNRESET）**，此时应用才间接被通知。

**总结表：**

| 动作         | 由谁触发/处理       | 应用层能否感知         |
|--------------|--------------------|-----------------------|
| 发送保活探测 | 操作系统TCP协议栈   | 否（应用层看不到）    |
| 处理保活应答 | 操作系统TCP协议栈   | 否                    |
| 连接断开通知 | TCP检测异常后告知   | 是（通过读写错误获知）|

**举例：**  
- 应用层无须关心保活报文包，操作系统自动维护。
- 但应用层可以通过 setsockopt 配置保活参数（探测间隔、次数等）。
- 一旦底层断链，协议栈才会将 socket 标记为异常，用后续数据读写报错的方式通知上层应用。

> **结论：TCP保活机制是内核协议栈级别的，对保活包收发与响应应用完全无感，只有真正连接中断时才通知应用。**

## TCP保活机制不能判断应用故障

**答：不能。TCP保活只能检测物理链路断开或网络不可达，**对于应用本身“卡死、阻塞、无响应”乃至进程挂掉（未立即释放socket），都无法有效探测**。只有当应用进程彻底崩溃且操作系统关闭/回收连接时，对端才能借由保活机制感知真正掉线。  
> 这里的“操作系统关闭/回收连接”，是指：如果应用进程崩溃或被 kill，原先属于该进程的所有 socket 会被操作系统（内核）自动关闭和释放，相关 TCP 连接也会被内核通知对端断开（如发送 FIN 或 RST）。只有在这种情况下，TCP 保活才有机会检测连接真正失效。而如果应用只是“假死”或阻塞，socket 资源还挂在进程下，内核协议栈仍然保持连接，TCP 保活探测依然能正常响应，此时对端检测不到异常。

详细原因说明：

- **TCP保活机制仅发生在操作系统TCP协议栈层面**。即使应用进程已经假死（CPU跑满、死循环、阻塞或崩溃未退出），只要操作系统内核和协议栈还在，底层仍会自动收发保活探测与应答，外部无法感知你的业务是否还能正常提供服务。
    - 例如：应用线程卡死/阻塞，但socket未关闭且内核还回ACK，这条TCP连接表面“存活”，但业务早已不可用。
    - 反之，如果只简单kill应用进程，socket被OS回收关闭，TCP连接才能被远端检测掉线。

- **TCP保活无法探测应用级半开状态**  
  （如监听进程假死但端口未释放，或消息处理逻辑阻塞导致业务完全无响应），此时底层TCP连接依然处于“ESTABLISHED”，无法自动识别“服务不可用”。

- **业务高可用场景下绝不可依赖TCP保活判活。**  
  例如web服务、RPC微服务、推送长连等。如果只等TCP保活超时才判故障，可能需要数分钟甚至更久（很多系统默认2小时才触发），响应极为迟钝。

**为什么？**

- 因为TCP协议栈不关心你的应用读写、业务处理是否活跃，只负责保证“IP链路畅通、数据包能收发”。
- 只有当底层物理断网、主机关机、进程异常导致协议栈释放socket内核资源时，保活机制才会真正起作用，提前关闭“僵尸连接”。

**因此：**
- **探测应用健康、进程存活、业务是否可用——必须在应用层设计心跳、Ping、超时检查等机制，及时断开失联、僵死、不活跃等连接！**
- TCP保活更多是底层补充手段，用于回收网络中已经不可恢复的死连接，而不是业务层可用性探测手段。

> **总结：TCP保活不能检测应用层“假死、阻塞、繁忙”，要及时判活判死，一定要靠“应用层心跳/探针/业务读写超时逻辑”。**
