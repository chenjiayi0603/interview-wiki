# WebSocket网关设计

> 本页涵盖雷漫分布式IM系统的WebSocket网关设计，包括架构设计、WSS协议转换、SSL/TLS握手、Access网关握手协议、WebSocket协议解码、连接复用、限流策略和状态管理。

## 4.1 架构设计

```

│ 客户端(浏览器/APP) │

         ▼

│  Nginx反向代理    │  SSL终止，TLS解密

## 4.2 WSS协议转换原理

**协议转换流程**:
```
┌─────────┐
│  客户端  │
└────┬────┘
     │
     │ WSS (WebSocket Secure)
     │ SSL/TLS加密传输
     │
     ▼
┌─────────────────────────────────┐
│         Nginx反向代理            │
│  ┌───────────────────────────┐  │
│  │  TLS解密/加密              │  │
│  │  协议升级/转换             │  │
│  │  WSS → WS                 │  │
│  └───────────────────────────┘  │
└────┬────────────────────────────┘
     │
     │ WS (WebSocket明文)
     │ 无SSL/TLS加密
     │
     ▼
┌──────────────┐
│ Access网关   │
└──────────────┘

说明：
- 客户端 ↔ Nginx: WSS (全程SSL加密)
- Nginx ↔ Access: WS (明文，内网安全)
- Nginx负责协议转换，业务服务无需处理SSL
```

**关键点**:
- 客户端与Nginx始终是wss（加密WebSocket）
- Nginx到Access始终是ws（明文WebSocket）
- Nginx持续充当协议转换角色，直到WebSocket连接关闭
- 保证公网链路全程加密，提升安全性
- 业务服务只需维护ws，无需感知SSL/TLS

## 4.3 SSL/TLS握手流程

**ECDHE密钥交换流程**（推荐，具备前向安全性）:
完整SSL/TLS ECDHE密钥交换流程图解：

客户端                          Nginx/Access(服务器)
  │                                │
  │─── 1. ClientHello ────────────▶│
  │      (支持的加密算法/版本/随机数) │
  │                                │
  │◀── 2. ServerHello ─────────────│
  │     (选定加密算法/版本/随机数)   │
  │                                │
  │◀── 3. Certificate ─────────────│
  │     (服务器证书，含公钥)        │
  │                                │
  │◀── 4. ServerKeyExchange ───────│
  │     (服务器ECDHE公钥)           │
  │                                │
  │◀── 5. ServerHelloDone──────────│
  │                                │
  │─── 6. ClientKeyExchange ──────▶│
  │      (客户端ECDHE公钥)          │
  │                                │
  │─── 7. ChangeCipherSpec ───────▶│
  │─── 8. Finished ───────────────▶│
  │                                │
  │◀── 9. ChangeCipherSpec ────────│
  │◀──10. Finished ────────────────│
  │                                │
  (客户端和服务器分别通过ECDHE算法，用双方公钥与自己的私钥计算pre-master secret)
  (结合双方的ClientHello和ServerHello随机数，派生session key)

※后续双方进入加密通信（对称加密，安全传输业务数据）

流程概要说明：
1. 客户端发起ClientHello，告知能力和随机数。
2. 服务端回复ServerHello，协商并选定参数，回传自己的证书和ECDHE临时公钥。
3. 客户端收到后验证证书，生成随机ECDHE私钥，并发公钥给服务端。
4. 双方通过各自私钥+对方公钥计算出相同的pre-master secret。
5. 使用协商算法和前期随机数推导session key。
6. 双方切换到加密状态（ChangeCipherSpec/Finished），完成握手，开始数据加密传输。

**RSA密钥交换流程**（不具备前向安全性）:
- 客户端用服务端证书中的公钥加密pre-master secret并发送
- 服务端用私钥解密获取pre-master secret
- 后续流程同ECDHE

## 4.4 Access网关握手协议

**握手和登录是分开的两个步骤**:
- **握手**（如`/hello/shake`）: 仅用于协议能力协商和通道初始化，不涉及正式的用户身份认证
- **登录**: 发生在握手之后，客户端还需主动发送登录消息（携带token、deviceid等），由Access网关联系Login服务进行正式鉴权和session建立

**握手协议流程**:
```
┌──────────────┐      ┌─────────────┐      ┌────────────┐      ┌──────────┐
│   客户端      │      │   Nginx     │      │ Access网关 │      │Login服务  │
│（App/Web等） │      │(代理+转发) │      │ (鉴权/会话)│      │(权限/账户)│
└─────┬────────┘      └─────┬───────┘      └────┬───────┘      └────┬─────┘
      │                        │                    │                    │
      │1. 发送握手请求         │                    │                    │
      │  (协议版本、扩展参数等)│                    │                    │

      │                        │    ├─ 检查协议版本 │                    │
      │                        │    ├─ 协商压缩/心跳│                    │
      │                        │    │ 参数等        │                    │
      │                        │    │               │                    │
      │                        │    4. 身份校验     │                    │
      │                        │    ├─ 解析用户标识 │                    │

## 4.5 WebSocket协议解码

**WebSocket帧结构**:
```
FIN | RSV | opcode | mask | payload length | masking-key | payload data
```

**字段说明**:
- `FIN`（1 bit）: 表示是否为消息的最后一帧，1表示消息结束
- `RSV`（3 bit）: 保留字段，通常为0
- `opcode`（4 bit）: 操作码，定义该帧的类型（0x1文本帧，0x2二进制帧，0x8关闭，0x9 ping，0xA pong等）
- `mask`（1 bit）: 是否有掩码（客户端发服务端时必须为1，服务端到客户端一般为0）
- `payload length`（7/7+16/7+64 bit）: 负载长度
- `masking-key`（32 bit/4字节，可选）: 掩码密钥
- `payload data`: 真实消息内容（业务消息头+业务消息体）

**解码流程**:
```
┌─────────────────────┐
│  网络事件回调         │
│  (原始TCP字节流)      │
└──────────┬──────────┘
           │
           ▼
┌─────────────────────┐
│  1. 接收缓冲         │  将TCP字节流存入缓冲区
│  (字节流缓冲)        │
└──────────┬──────────┘
           │
           ▼
┌─────────────────────┐
│  2. WebSocket帧解析  │  检查缓冲区是否有完整帧
│  ┌─────────────────┐ │
│  │ FIN | RSV | ... │ │  解析帧头字段
│  │ opcode | mask  │ │  提取payload长度
│  │ masking-key    │ │  提取payload data
│  └─────────────────┘ │
└──────────┬──────────┘
           │
           ├─ 帧不完整 → 继续等待数据
           │
           ▼
┌─────────────────────┐
│  3. payload还原     │  使用masking-key还原数据
│  (去除掩码)          │
└──────────┬──────────┘
           │
           ▼
┌─────────────────────┐
│  4. 判断opcode       │  根据opcode分发处理
│  ┌─────────────────┐ │
│  │ 0x1: 文本帧     │ │
│  │ 0x2: 二进制帧   │ │
│  │ 0x8: 关闭帧     │ │
│  │ 0x9: ping帧     │ │
│  │ 0xA: pong帧     │ │
│  └─────────────────┘ │
└──────────┬──────────┘
           │
           ├─ 业务帧(0x1/0x2) → 上层业务处理
           ├─ 控制帧(0x8/0x9/0xA) → 连接管理
           └─ 异常/非法 → 断开连接
```

**IM聊天消息推荐**:
- 普通聊天、通知、信令等业务消息**客户端必须单帧发送**（FIN=1）
- 服务端仅处理单帧业务帧，收到FIN=0或多帧合并的消息时直接拒绝或关闭

## 4.6 连接复用机制

**服务端推送和客户端发消息都复用同一个WebSocket连接**:
- WebSocket协议本身是全双工通道
- 客户端和服务端均可在已建立的同一连接上任意时刻主动发送消息
- 所有类型的下行消息（服务端主动推送/通知/消息同步等）均通过已建立的WebSocket连接直接发送
- 无论客户端发消息，还是服务端推送，均走这唯一的ws/wss通路

## 4.7 限流策略

**多层限流架构**:
```
┌─────────────────────┐
│  iptables (网络层)   │  网络层限流
│  - IP连接数限制      │  - 连接频率限制
│  - 流量控制          │
└──────────┬──────────┘
           │
           ▼
┌─────────────────────┐
│  Nginx (反向代理层)  │  反向代理层限流
│  - 连接数限制        │  - 请求频率限制
│  - 带宽限制          │  - SSL/TLS处理
└──────────┬──────────┘
           │
           ▼
┌─────────────────────┐
│ Access网关 (应用层)  │  应用层限流
│  - 消息频率限制      │  - 消息类型限制
│  - 连接级别限流      │  - 业务逻辑限流
└─────────────────────┘

说明：
- 三层限流逐层过滤，保护后端服务
- 网络层：粗粒度，防DDoS
- 代理层：中粒度，SSL卸载
- 应用层：细粒度，业务限流
```

**限流规则**:
- **IP级别限流**:
  - 连接数限制：每个IP最大连接数（如5-20000）
  - 连接频率限制：每个IP每秒新连接数（如60秒5个）
- **连接级别限流**:
  - 消息频率限制：每个连接每秒发送消息数（如20个/秒）
  - 消息类型限制：特定消息类型（如4501群消息）每秒限制（如3个/秒）
  - 带宽限制：每个连接上传/下载带宽（如200k/s）

**实现算法建议（面试可答）**:
- 连接频率限制（每IP新建连接速率）：优先用**令牌桶**（按IP维度发令牌）
- 消息频率限制（每连接QPS）：优先用**令牌桶**（按连接维度）
- 消息类型限制（如4501群消息）：优先用**令牌桶**（按连接+消息类型维度）
- 带宽限制：通常用按字节计数的**令牌桶**（token=bytes）
- 补充对比：**漏桶**更偏"强平滑匀速"，**令牌桶**更适合IM允许小突发的业务特征

**一句话回答模板**:
- 这块限流主要用令牌桶来做，按IP、连接、消息类型分维度发放令牌，既能控制平均速率，也能容忍短时突发；带宽同理按字节令牌控制，必要时再叠加漏桶做更强平滑。

## 4.8 状态管理

**用户状态字段**（Redis Hash: `1:2:im:status:userid:${userid}`）:
- `logintime:${deviceid}`: 登录时间（秒）
- `status:${deviceid}`: 在线状态 (0/1)
- `loginseq:${deviceid}`: 登录序列号
- `ssidfreshtime:${deviceid}`: 心跳刷新时间
- `sessionid:${deviceid}`: 会话ID
- `sessionkey:${deviceid}`: 加密密钥
- `accnodeidentify:${deviceid}`: 网关定位（格式：ip:port:workIndex）
- `clientip:${deviceid}`: 客户端IP
- `platformtype:${deviceid}`: 平台类型

**状态更新机制**:
- 登录时：更新所有相关字段
- 心跳时：刷新`ssidfreshtime`
- 登出时：更新`status`为0
- 超时时：自动将`status`设为0
