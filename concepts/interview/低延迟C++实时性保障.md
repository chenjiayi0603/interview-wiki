## 7.1 实时调度策略

**SCHED_FIFO / SCHED_RR**：实时调度策略，保证高优先级任务优先执行。

// 高频交易、网络转发等场景通常推荐 SCHED_FIFO：
//  - 高频交易：主撮合环/撮合引擎主循环等对延迟要求极致苛刻的线程，往往设置 SCHED_FIFO 以最大化保证其调度实时性、避免被其他非关键线程打断。
//  - 实时网络包转发、内核旁路DPDK场景：处理主线程也推荐用 SCHED_FIFO，确保网络数据包可被第一时间处理。
//
// 若有多个同等重要的实时线程（如多个报文解包、风控检查、行情等线程）需要合理轮转、防止饥饿，则建议 SCHED_RR，兼顾实时和线程公平轮转。
//
// ⚡ 场景建议小结：
// | 场景         | 推荐调度策略 | 说明                                  |
// | ------------ | ------------ | ------------------------------------- |
// | 高频撮合主循环 | SCHED_FIFO   | 极致延迟、单线程优先保证，永不中断       |
// | 网络DPDK主线程 | SCHED_FIFO   | 需绝对调度优先，不允许被打断             |
// | 多风控/行情轮转 | SCHED_RR     | 需多线程公平获得CPU、定期处理防止饿死   |


```cpp
#include <sched.h>
#include <pthread.h>

// 设置实时调度策略
void set_realtime_priority(int priority) {
    struct sched_param param;
    param.sched_priority = priority;  // 1-99，数字越大优先级越高
    
    // SCHED_FIFO: 先进先出，直到完成
    // SCHED_RR: 时间片轮转
    // 在 SCHED_FIFO 调度策略下，priority 参数（范围 1-99，越大优先级越高）决定线程调度的优先顺序，
    // 优先级高的线程会抢占优先级低的线程，priority 相同则按先来后到（FIFO）调度

    // SCHED_RR 同样受到 priority 的影响，priority 越高调度优先级越高。
    // 区别在于 SCHED_RR 为相同优先级的线程分配时间片，两者公平轮转；
    // SCHED_FIFO 则没有时间片，优先级一致时先调度者先执行，直到自愿让出 CPU。

    // SCHED_FIFO 和 SCHED_RR 选哪个？区别是什么？
    // SCHED_FIFO（先进先出）适合极致低延迟、无干扰、优先级稳定、关键实时任务。只要有高优先级线程未主动让出 CPU，低优先级线程将不会被调度，用于非常严格的实时控制，如高频交易、工业自动化等。
    
    // SCHED_FIFO（先进先出）常用场景：对单线程极致实时响应有极高要求，需全力保证关键线程调度，不允许被其他线程打扰，如：
    // - 高频交易撮合主循环
    // - 实时工业自动化主控环节
    // - 关键实时软中断/硬中断仿真线程
    // - 音视频采集中对极致延迟控制的主线程
    // 此模式下，一旦高优先级线程进入可运行，只有当其主动让出 CPU 或阻塞时，低优先级线程才有机会运行。适合绝对不能容忍“迟到”的任务。


    // SCHED_RR（时间片轮转）则用于需要同等优先级的实时线程之间相对公平轮转的场景，适合有多个“重要线程”协作且都必须定期运行、但对单线程极致延迟并不苛刻，如实时信号处理、多任务控制等。
    
    // 简单总结：只有极少数极端低延迟任务（如关键中断处理、高频交易主循环）推荐 SCHED_FIFO。
        // 绝大多数“实时”场景，建议用 SCHED_RR 保证优先级+线程公平性，防止任务“饿死”。
    // SCHED_RR 适用于有多个同等重要实时线程需要轮流执行、必须周期性获得 CPU 时间片的场景。
    
    // SCHED_RR（时间片轮转）适用于有多个具有相同优先级的重要实时线程协同运行的场景。例如：
    // - 实时音视频处理：解码、编码、网络收发等多个线程需要周期性获得 CPU 时间。
    // - 实时信号处理系统：多个需要周期内响应的采集或处理线程。
    // - 实时控制系统中多个调度要求近似的任务。

// 到底选 SCHED_FIFO 还是 SCHED_RR？
    // - 如果极致低延迟、单一关键线程必须100%优先保证（如主撮合、极端高频中断处理），选 SCHED_FIFO；
    // - 如果有多个同等优先级的重要实时线程都必须公平获得周期性CPU时间（如行情处理+风控等并行线程，防止饥饿），更推荐 SCHED_RR。
    // - 高频交易系统主循环可用 SCHED_FIFO，多个重要模块协同且需轮转时选 SCHED_RR。

    // - 实际选用时建议优先 SCHED_RR，除非需求确实需要独占CPU的不公平极致低延迟。
    // SCHED_RR 可以防止某个线程长期独占 CPU，确保所有同等优先级线程都有公平且周期性的调度机会，特别适合需要“多线程实时且防止饿死”的应用环境。

    // 选择示例：可根据需求替换 SCHED_FIFO 或 SCHED_RR
    pthread_setschedparam(pthread_self(), SCHED_FIFO, &param);  // 或 SCHED_RR
}

// 示例
int main() {
    set_realtime_priority(50);
    // 关键业务逻辑
}
```

**注意事项**：
- 需要 root 权限
- 优先级过高可能导致系统不稳定
- 实时线程不应长时间占用 CPU

## 7.2 内存锁定（Memory Locking）

**原理**：锁定内存页面，避免被交换到磁盘。

```cpp
#include <sys/mman.h>

// 锁定所有内存
void lock_all_memory() {
    if (mlockall(MCL_CURRENT | MCL_FUTURE) != 0) {
        perror("mlockall failed");
    }
}

// 锁定特定内存区域
void lock_memory_region(void* addr, size_t len) {
    if (mlock(addr, len) != 0) {
        perror("mlock failed");
    }
}
```
// 锁定内存的目的是避免关键业务进程的内存被操作系统换出到交换区（swap），从而在访问时导致缺页中断（page fault）、系统等待磁盘 IO，带来不可预测的长延迟。
// 特别是在低延迟、高实时性要求的场景下，任何由于内存换出造成的抖动都难以接受。
// 通过 mlock/munlock，可以保证进程使用的所有或部分物理内存常驻于物理内存，不被 swap，于是内存访问延迟稳态可控。
// 需要注意：锁定过多内存会影响系统整体性能，通常建议只锁定关键内存区域。
//
// 总结：锁定内存是为了减少系统级不可控延迟，提升实时性和确定性。
//
// 举例：金融高频交易、实时工业控制等场景都推荐锁定关键进程内存。
//
// 相关 API：mlock, munlock, mlockall, munlockall


## 7.3 避免页面错误

**策略**：
- 预分配所有内存
- 预热代码路径（touch 所有页面）
- 使用 `mlock` 锁定内存

```cpp
// 预热内存页面
void warmup_memory(void* ptr, size_t size) {
    volatile char* p = (volatile char*)ptr;
    for (size_t i = 0; i < size; i += 4096) {
        p[i] = 0;  // 触发页面错误，加载到内存
    }
}
```
