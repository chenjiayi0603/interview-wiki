# 性能优化-定位套路（按症状）

> 本文总结性能瓶颈定位的常见套路，按症状分类，包含尾延迟高、QPS 上不去、CPU 高但业务量低、内存涨/碎片、上下文切换高等场景的详细定位过程与案例。

See also: [[C++性能调优关键指标]], [[C++代码层性能调优最佳实践]], [[C++多线程与并发]], [[Linux线程调度]]

## 尾延迟高（P99/P999 拖尾）

**分析思路**：尾延迟通常不是“平均变慢”，而是少数请求走了慢路径。重点排查：**排队**（队列积压导致等待）、**锁/条件变量等待**（拿不到锁或等事件）、**GC/内存抖动**（若用 GC 语言或大量分配导致回收/缺页）、**IO 尖刺**（磁盘/网络偶发慢、超时重试）。定位时用 **CPU 火焰图** 看“最慢的那条调用栈”，用 **分布式 Trace** 看请求完整路径上哪一 hop 耗时突增。

---

### 案例一：全局锁导致的等待

**详细定位过程及指令与输出分析：**
1. 现象：某 RPC 服务 P99 延迟突然从 10ms 升到 500ms。
2. 采集关键指标与火焰图：
   - 指令：收集性能火焰图  
     ```shell
     perf record -F 99 -a -g -- sleep 60
     perf script | ./flamegraph.pl > flame.svg
     ```
   - 输出分析：火焰图中大段栈帧集中于 `pthread_cond_wait`，显示大量请求在等待条件变量，存在高并发锁等待问题。
3. 复盘相关锁逻辑，发现“查 DB + 写缓存”操作被全局大锁保护，多数线程阻塞。
4. 日志与监控观察：
   - 锁持有时长和队列长度监控打点（如暴增），业务日志可见 DB 查询慢时锁长时间不释放，导致后续请求堆积。
   - 关键日志片段（示例）：
     ```
     [Warn] DB query cost=250ms, lock hold=300ms, queue wait=200ms
     ```
   - 输出分析：DB query 偶发变慢同步拉长锁时间，后续排队明显延长。
5. 针对性优化措施：将 DB 查询移到加锁之外，仅缓存写操作时持锁，缩小临界区。
6. 优化后效果对比：
   - 观测 P99 延迟回落至 10ms-20ms，锁持有均值与峰值同步下降，火焰图中等待栈帧缩小，队列等待清零。

---

### 案例二：下游 HTTP 重试/超时拉高尾延迟

**详细定位过程及指令与输出分析：**
1. 现象：P999 偶发数秒甚至更长的延迟。
2. 调用链追踪：
   - 使用分布式 Trace 工具（如 jaeger、zipkin）分析  
     指令（以 jaeger 为例）：在 UI 查询尾部高延迟请求的 trace  
   - 追踪输出：trace 显示大部分耗时集中在“等待下游 HTTP 响应”环节。
3. 进一步排查下游重试与超时配置
   - grep 配置/代码（如 `grep -E '(timeout|retry)' config.yml`）
   - 输出示例：`retry: 5`，`timeout: 5s`
   - 输出分析：发现重试次数和超时配置偏高。
4. 网络与日志验证：
   - 使用 tcpdump 抓包/分析：
     ```
     tcpdump -i eth0 host <downstream-ip> and port <port>
     ```
     输出：下游响应延迟大、部分连接多次重试。
   - 查看下游错误日志确认偶发网络抖动、连接短时超时。
5. 结论分析：主服务在下游慢/抖动时反复重试，起到总延迟叠加放大效应。
6. 优化措施：将下游超时收紧如改5s→2s，限制最大重试次数如 5→2，必要时放开熔断进行快速失败。
7. 效果验证：
   - 指标观测：P999 延迟明显降至1s以内，trace中异常长 hop 明显收敛，系统整体尾延迟变平滑。

## QPS 上不去（吞吐到顶）

**分析思路**：先看 **CPU 是否打满**。  
- **CPU 闲**：瓶颈多半在 IO（磁盘/网络）、锁等待、或队列被限（线程池/连接池满、下游限流），请求在“等”而不是在“算”。  
- **CPU 满**：看热点函数（火焰图）、是否锁竞争（lock contention 统计）、分支预测失败（PMU）、以及是否有不必要的重复计算。此外要排除 **网络限速**（带宽、连接数、端口耗尽）和 **下游限流/熔断** 导致的有效 QPS 上限。

---

### 案例一：线程池/队列限制导致 QPS 上不去

**详细定位过程及指令与输出分析：**
1. 现象：压测时 QPS 稳定在 2w，但 CPU 利用仅 40%。
2. 监控线程池队列：
   - 打点监控或拉取现有监控面板，线程池队列长度/等待线程数看齐最大值。
   - 输出示例：队列长度高企，任务长时间未出队。
3. 进一步分析阻塞调用：
   - perf/top  
     ```shell
     top -H -p <pid>
     ```
   - perf 火焰图：
     ```shell
     perf record -F 99 -p <pid> -g -- sleep 30
     ```
   - 输出：大量线程阻塞在`read()`系统调用，呈现 IO 等待。
   - 说明：CPU 大量处于 sleep/blocking 非 CPU 密集型。
4. 检查下游服务指标，发现处理速度偏慢，成为主服务瓶颈。
5. 优化尝试：
   - 扩容下游实例，提升单实例能力。
   - 在主服务使用异步 IO、提升连接池 concurrency。
6. 优化后效果：测试 QPS 抬升至 4w，CPU 利用提升至 70%+，队列长度下降。

---

### 案例二：CPU 热点和数据结构影响吞吐

**详细定位过程及指令与输出分析：**
1. 现象：压测时 CPU 接近 100%，QPS 无法进一步提升。
2. 性能热点采集：
   - 指令：
     ```shell
     perf top
     ```
   - 输出示例：`std::unordered_map::find` 比例高达 40%
   - 输出分析：说明热点集中在 Hash 查找。
3. 源码复查：大 map 高并发频繁访问，偶现 cache miss 和锁冲突。
4. 优化措施：改为分片 sharding hash、热点 key 做本地缓存或 thread local。
5. 优化后指标：QPS 提升 30%，CPU 使用率降至 80%，perf/top 显示热点分散。

---

## CPU 高但业务量低（空转/无效消耗）

**分析思路**：业务请求不多，但 CPU 占用高，说明有“非业务”消耗。常见原因：**空转循环**（忙等、sleep 过短轮询）、**失败重试风暴**（下游不可用导致大量重试/超时）、**锁竞争导致自旋**（多线程抢同一把锁，大量 CPU 花在自旋上）、**无效轮询**（epoll 误用或 wakeup 过于频繁）、**日志过多**（同步写盘、格式化字符串、高并发下日志库锁竞争）。

---

### 案例一：空转循环导致高 CPU

**详细定位过程及指令与输出分析：**
1. 现象：某后台 worker 在无请求时 CPU 仍 30%。
2. 性能采样 & 火焰图：
   - 指令：
     ```shell
     perf top -p <pid>
     ```
   - 输出：大量时间消耗在 `while (!ready) {}` 的 spin loop。
   - 火焰图栈帧高度直观反映忙等占比。
3. 源码回溯发现为 busy-wait 实现阻塞。
4. 优化措施：将 busy-wait 改为条件变量如 `std::condition_variable::wait()` 或使用 eventfd wait。
5. 优化效果：重启服务后 CPU 占用降至 3% 以下，perf/top/火焰图无 busy-wait 热点。

---

### 案例二：重试风暴造成无效 CPU 消耗

**详细定位过程及指令与输出分析：**
1. 现象：下游故障后，本机 CPU 飙高。
2. 分析协程栈与日志追踪：
   - grep 日志/业务代码，看失败后行为  
   - 日志输出示例：
     ```
     [ERROR] call downstream failed, retrying
     [ERROR] call downstream failed, retrying
     ...（极短时间重复）
     ```
   - perf/top 输出：大量 CPU 花在重试相关逻辑和网络等待。
   - 输出分析：短时间内重试欲望极高，大量请求在 busy-loop。
3. 问题确认：没有重试退避与重试次数上限，导致资源风暴。
4. 优化措施：加入指数退避、取有限重试次数，引入熔断。
5. 优化后观测：CPU 降至空闲水平，复现下游故障时主服务无堆积与 CPU 飙高。

---

## 内存涨 / 碎片（RSS 持续升、分配变慢）

**分析思路**：看是 **真实泄漏** 还是 **碎片/缓存未释放**。  
- 用 **arena/碎片率**（如 jemalloc 的 `mallctl` 统计）看碎片是否严重。  
- 查 **对象池/缓存** 是否只增不减（例如按 key 缓存未设 TTL 或上限）、**长寿命容器**（全局 map/vector）是否被业务持续 append、**大块分配未归还**（例如大 buffer 未复用、预分配池未回收）。

---

### 案例一：频繁字符串分配导致内存上涨

**详细定位过程及指令与输出分析：**
1. 现象：进程 RSS 随运行时间单调上涨。
2. 工具定位分配热点：
   - 指令：
     ```shell
     # 以 heaptrack 记录内存分配情况
     heaptrack ./myservice
     # 执行过程中可让业务产生典型负载后 Ctrl+C 终止
     # 分析报告生成（图形界面）
     heaptrack_gui heaptrack.<pid>.gz
     # 命令行汇总函数热点
     heaptrack_print heaptrack.<pid>.gz | head -20
     输出结果举例：

     - heaptrack_print 输出示例（内存分配热点）：
       ```
       Allocations by function:
         1200 MiB  60%  myservice::TraceIdGenerator::Gen()
          300 MiB  15%  myservice::Request::set_trace_id()
           ...
       ```
       说明 TraceId 生成及 set_trace_id 处频繁分配了大量 string。

     - heaptrack_gui 图形界面可直观看到热点函数和调用关系（火焰图或图表）。

     - 优化前后 RSS 曲线对比（假设用监控平台展示）：
       ```
       优化前：RSS 持续增长（单位时间 +20MB）
       优化后：RSS 稳定或波动在较小区间（<1MB/h）
       ```

     - 栈回溯示例（定位调用链）：
       ```
       #0  std::string::_M_construct ...
       #1  myservice::TraceIdGenerator::Gen()
       #2  myservice::Request::set_trace_id()
       ...
       ```

     ```
   - 输出分析：`std::string` 分配数量/字节数居首，callstack 指向 trace/request ID 相关临时对象。
3. 源码定位：ID 生成和使用无对象重用，频繁 new/delete。
4. 优化措施：用 thread_local/std::string_view 复用，或用对象池管理 buffer。
5. 优化后内存走势：RSS 曲线稳定（如由 steady 增长转为平台期）。

---

### 案例二：分配碎片化导致内存膨胀

**详细定位过程及指令与输出分析：**
1. 现象：长时间运行后 RSS>物理需求且分配耗时上涨。
2. jemalloc 统计：
   - 指令（jemalloc）：
     ```shell
     # 具体例子：分析二进制 core dump 内 jemalloc 各函数实际分配、碎片占用
     jeprof --show_bytes myservice core.12345
     # 或分析 heap profile
     jeprof --show_bytes myservice jeprof.heap
     ```
   - mallctl 统计：
     ```
     // mallctl 用于查询分配器内部统计数据。"muzzy_purged" 表示 jemalloc 中 arena 回收/归还给操作系统的未使用内存页的次数；该指标越大，说明内存碎片被主动回收得越多，有助于减少 RSS 膨胀。
     // 为啥是 stats.arenas.0.muzzy_purged？
     // 这是 jemalloc 的内部统计字段，表示当前进程中第 0 号 arena 被主动回收（purge）为“muzzy”状态的内存页次数。
     // "muzzy" 状态的内存页属于已释放但暂未还给操作系统，仍由 jemalloc 管理，可以被快速重新分配，减少分配延迟。
     // 该值越大，说明碎片被主动回收利用的次数较多，有利于降低实际 RSS 占用。
     mallctl("stats.arenas.0.muzzy_purged", &value, &sz, NULL, 0);
     ```
   - 输出分析：碎片率高，大量小块悬挂，无归还。
3. 业务排查：部分对象生命周期极不均衡，导致 free slab 无法合并。
4. 优化：用对象池、切换更优分配器（如 mimalloc——号称碎片少、快，且线程隔离好，能减少 lock contention、提升分配/回收效率）、或合理调整 arena 参数。
5. 优化后指标：碎片率由 12% 降到 3%，RSS 明显下降，分配延迟收敛。


  mimalloc 是一个高性能的通用内存分配器，用于替换系统默认的 malloc/free，以提升内存分配效率并减少碎片。使用 mimalloc 通常有几种方式：

  1. 直接链接替换（推荐）
  只需在链接阶段加上 `-lmimalloc` 即可，无需改动业务代码：
  ```sh
  g++ main.cpp -o myapp -lmimalloc
  ```
  这时所有的 `malloc/free/new/delete` 默认会被 mimalloc 替换（通过 weak symbol 机制）。

  2. 显式包含 mimalloc 头文件
  如果只想在部分模块使用 mimalloc，可以手动包含头文件并用其 API：
  ```cpp
  #include <mimalloc.h>

  void* p = mi_malloc(1024);
  mi_free(p);
  ```
  和标准 malloc/free 接口一致。

  3. LD_PRELOAD 方式（无重新编译场景）
  适用于已有二进制/动态库，仅需在运行时指定环境变量即可：
  ```sh
  LD_PRELOAD=/usr/lib/libmimalloc.so ./myapp
  ```
  这样操作系统会优先用 mimalloc 里的内存分配符号替换 glibc 默认的。

  4. CMake 集成（C++ 项目）
  ```cmake
  find_package(mimalloc REQUIRED)
  target_link_libraries(myapp PRIVATE mimalloc::mimalloc)
  ```

  5. 性能和参数调优
  mimalloc 支持通过环境变量配置行为，如：
  - `MIMALLOC_SHOW_STATS=1`  // 程序退出时打印分配和碎片详细统计
  - `MIMALLOC_VERBOSE=1`     // 输出更多诊断信息

  参考
  - [官方文档](https://github.com/microsoft/mimalloc)
  - 通常能带来更好的内存利用率、更低碎片，推荐场景：服务端高并发、高分配/回收频率的程序。

## 上下文切换高（voluntary / involuntary 都多）

**分析思路**：上下文切换多会导致 CPU 时间浪费在调度而非业务上。常见原因：**线程过多**（远超过核数，且都在 runnable）、**锁争用**（大量线程在锁上 sleep/wake，导致切换）、**频繁唤醒**（条件变量/event 触发过于频繁、epoll 惊群等）。可用 **sched_stat**、**perf sched timehist**、**pidstat -w** 看谁在切换、在等什么。

---

### 案例一：线程数超限导致频繁切换

**详细定位过程及指令与输出分析：**
1. 现象：线程池设置为 500 线程，机器实际 64 核，pidstat 监控每秒上下文切换数极高。
2. 检查线程切换：
   - 指令：
     ```shell
     # 举例：监控进程 12345 的上下文切换情况
     pidstat -w -p 12345

     # 示例输出（部分摘录）：
     #      Time   UID      PID   cswch/s  nvcswch/s  Command
     #   11:32:01  1000   12345    1100.00    800.00  myservice
     # cswch/s  ：每秒自愿(context switch)切换次数（如线程主动等待/睡眠等导致）
     # nvcswch/s：每秒非自愿切换次数（如被抢占）
     ```
   - 输出示例：cswch/s、nvcswch/s 数值极高，runnable/waiting 不断变化、CPU 抖动。
   - 输出分析：通过 ps/top/pidstat 等命令可查看实际线程数，发现线程数远超物理 CPU 核数，导致调度压力大。
3. 优化线程池规模至核数附近，加队列缓冲降波峰。
4. 优化后效果：上下文切换数降 80%以上，吞吐变高且 CPU 抖动消失。

---

### 案例二：锁争用造成切换抖动

**详细定位过程及指令与输出分析：**
1. 现象：perf 统计发现线程频繁切换阻塞在 `futex_wait`/`futex_wake`。  
   - `futex_wait` 其实不会由用户代码直接调用，而是 Linux 内核提供的底层原语，主要用于实现如 `pthread_mutex`、`std::mutex`、`std::condition_variable` 等用户空间锁和条件变量的等待/唤醒。当这些高层同步原语在竞争激烈时，线程会在用户空间自旋一段时间后，进入内核阻塞，最终调用 futex_wait。可通过 perf/top/strace 等工具看到栈帧停留在 `futex_wait`。常见调用链如：  
     ```
     pthread_mutex_lock
       -> futex syscall
          -> futex_wait
     ```
   - 换句话说，频繁发生 futex_wait 多数是由于用户空间的锁竞争、条件变量等待、线程同步等操作导致的。
2. 分析锁热点：
   - perf 火焰图
     ```shell
     perf record -F 99 -p <pid> -g -- sleep 30
     ```
   - 输出分析：futex_wait/wake 热点明显，锁下线程数居高，lock contention 严重。
3. 诊断代码锁分布，发现全局锁下热点冲突。
4. 优化方案：将全局锁分片/按 key 分桶，无锁结构代替部分。
5. 优化后观测：perf/futex_wait conspicuously 降低，pidstat 上切换数同步变低。
