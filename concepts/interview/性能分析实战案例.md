## 4.1 案例 1：定位 CPU 热点函数

**问题**：程序运行缓慢，需要找出 CPU 消耗最多的函数。

**示例代码**：
```cpp
// perf_demo.cpp
void foo() {  // 热点函数1
    volatile long long sum = 0;
    for (long long i = 0; i < 100000000; ++i)
        sum += i;
}

void bar() {  // 热点函数2
    volatile long long prod = 1;
    for (long long i = 1; i < 5000000; ++i)
        prod *= (i % 17 + 1);
}

int main() {
    foo();  // 产生第一个热点
    bar();  // 产生第二个热点
    return 0;
}
```

**操作步骤**：
```bash
# 1. 编译程序（带调试信息）
g++ -O2 -g -o perf_demo perf_demo.cpp

# 2. 采集性能数据（-g 表示记录调用栈）
perf record -g ./perf_demo

# 3. 查看热点函数报告
perf report

// 采集火焰图时建议加上 -g，这样生成的火焰图才有函数名和调用栈信息。如果不加 -g，符号会丢失，不便定位热点。
// 例如：
// 1. 编译时加 -g：
//    g++ -O2 -g -o perf_demo perf_demo.cpp
// 2. 采集时一样：
//    perf record -g ./perf_demo
// 3. 生成火焰图：
//    perf script | flamegraph.pl > flame.svg
```

**输出示例**：
```
Samples: 2K of event 'cycles', Event count (approx.): 1000000000
-  50.00%  perf_demo  perf_demo      [.] foo
   30.00%  perf_demo  perf_demo      [.] bar
   20.00%  perf_demo  perf_demo      [.] main
```

**解读**：`foo()` 函数占用了 50% 的 CPU 时间，是主要热点函数，需要优先优化。

## 4.2 案例 2：识别缓存未命中

**问题**：程序性能不佳，怀疑是缓存未命中导致的。

**操作步骤**：
```bash
# 方法1：使用 perf stat 统计缓存事件
perf stat -e cache-references,cache-misses ./your_program

# 方法2：使用 perf record 采样缓存未命中
perf record -e cache-misses -g ./your_program
perf report
```

**输出示例**：
```
 Performance counter stats for './your_program':

       21,431      cache-references
        5,432      cache-misses       # 25.35% of all cache refs
```

**解读**：缓存未命中率为 25.35%，较高，说明内存访问模式不友好，需要优化数据布局或访问顺序。

## 4.3 案例 3：分析 I/O 性能问题

**问题**：程序涉及大量文件 I/O，需要分析 I/O 操作模式。

**操作步骤**：
```bash
# 1. 使用 strace 统计文件 I/O
strace -c -e trace=file ./your_program
输出结果：

-----------------------------------------------
% time     seconds  usecs/call     calls    errors syscall
------ ----------- ----------- --------- --------- -------------
 80.00    0.004800         192        25           open
 10.00    0.000600          60        10           read
  5.00    0.000300         150         2           write
  5.00    0.000300         150         2           close
------ ----------- ----------- --------- --------- -------------
100.00    0.006000                    39           total
说明：open 调用占用 80% 的 I/O 时间，为主要 I/O 操作瓶颈。

**如何从例子中判断是否已经出现 I/O 瓶颈？**

1. **看 strace -c 的统计分布**：  
   如果 `open`、`read`、`write`、`close` 等 I/O 相关系统调用的耗时加起来远高于 50%，说明程序的大部分时间都消耗在 I/O 上，这很可能就是性能瓶颈。例如上面 `open` 占用 80%，`read`+`write`+`close` 占15%，共95%，表示 CPU 很多时间在等文件操作。

2. **perf stat 输出**：  
   - 如果 `CPU utilization` (CPU 利用率) 很低，但总 wall time（实际运行耗时）很大，则很多时间不是用来计算，而是卡在外部资源访问上（多半是 I/O）。
   - 若 `cycles`、`instructions` 等指标没多少，但程序耗时长，也说明在等 I/O。

3. **time -v 输出**：  
   - 如果 `User time` 明显小于 `Elapsed (wall clock) time`，说明大部分总耗时不是 CPU 计算，而是阻塞或 I/O 等待。

4. **perf report/火焰图热点**：  
   - 主要热点在诸如 `read`、`write`、`fread`、`fwrite`、`pread64` 等系统/库函数，而自己业务代码占比较低时，也常暗示 I/O 已成为瓶颈。

**结论**：  
- 只要 I/O 系统调用的总耗时很高且大大超过了纯计算，或者程序忙于等待文件/网络/外部设备，那么性能瓶颈就在 I/O。此时应考虑文件缓存、批量操作、异步或内存映射等优化方法。
- 典型信号是：I/O syscall 占总耗时远大于 50%；CPU 利用率低、等待高；热点主要在 I/O 函数。

**例子分析：**
- 本例中 `open` 就占了 80%，I/O 总计 95%，说明优化提升程序性能的最大空间就是减少不必要的 I/O 或提升数据访问手段（如缓存或批处理）。


# 2. 详细跟踪文件操作
strace -e trace=open,read,write,close -T ./your_program > io_trace.log

# 3. 分析日志
# 输出结果
# 统计打开文件总次数
grep "open" io_trace.log | wc -l 

# 统计所有 read 操作的总耗时（单位秒）
grep "read" io_trace.log | awk '{sum+=$NF} END {print sum}' 
输出结果：

-----------------------------------------------
分析：
- open("data.txt", O_RDONLY)       = 3 <0.000152>  —— 表示以只读方式打开文件 data.txt，返回文件描述符 3，耗时 0.000152 秒。
- read(3, "abc...", 4096)          = 4096 <0.000035> —— 从文件描述符 3 读取 4096 字节数据，耗时 0.000035 秒（"abc..." 代表实际内容被省略）。
- write(1, "output...", 1024)       = 1024 <0.000012> —— 向文件描述符 1（标准输出）写入 1024 字节，耗时 0.000012 秒。
- close(3)                         = 0 <0.000008> —— 关闭文件描述符 3，耗时 0.000008 秒（约 8 微秒）。
...

可以看出各 I/O 操作及其具体耗时。根据耗时判断瓶颈所在，例如 open 操作（打开文件）的耗时相对较高，若频繁出现，应优化文件打开逻辑或提升缓存策略。

说明：每行记录了系统调用名、参数、返回值和耗时。可据此判断文件操作具体消耗。

**优化建议**：
- 如果频繁打开/关闭文件，考虑保持文件打开
- 使用更大的缓冲区减少系统调用次数
- 考虑使用内存映射文件（mmap）



**如何判断程序存在 I/O 瓶颈？**

可以结合 `perf stat`、`strace -c` 或 `time -v` 等工具的输出，判断 I/O 是否成为性能瓶颈，主要依据如下：

- **strace -c** 输出中，`read`、`write`、`open`、`close` 这类 I/O 相关系统调用的总时间占比很高（比如远高于 50%），说明程序大量时间耗在 I/O 操作上。
- **perf stat** 结果里，`CPU utilization`（CPU 利用率）偏低，同时任务执行时间较长，通常说明大量时间花在等待外部资源（I/O）。
- **time -v** 结果中，`User time` （用户态 CPU 时间）明显小于 `Elapsed (wall clock) time`，意味着程序大部分时间都在等待 I/O 完成，而非纯计算。
- 若 I/O 相关系统调用（如 File system inputs/outputs、socket messages 等）计数和耗时都高于 CPU 计算相关指标，则说明 I/O 已成为性能瓶颈。
- 火焰图或 perf report 采样中，如果大量热点出现在系统调用层（如 `read`、`write`、`fread`、`fwrite` ），而业务代码占比较低，也表明程序主要被 I/O 阻塞。

**典型 I/O 瓶颈输出信号示例：**
- strace -c 报告：
    ```
    % time     seconds  usecs/call     calls    errors syscall
    ------ ----------- ----------- --------- --------- -------------
     70.00    0.007000         100       100           read
     20.00    0.002000          50        40           write
     10.00    0.001000          25        10           open
    ```
    上述表示程序 70% 以上时间消耗在 read（读文件/数据）系统调用上。

- perf stat 输出：
    ```
    1.00 sec task-clock                #    0.10 CPUs utilized
    ...
    ```
    CPU 利用率仅 10%，剩余时间多在等待 I/O。

- time -v 输出：
    ```
    User time (seconds): 0.10
    Elapsed (wall clock) time: 3.00
    Percent of CPU this job got: 3%
    ```
    3 秒挂钟时间，实际只用 0.1 秒 CPU，说明大量时间是 I/O 等待。

**结论**：只要看到 I/O 系统调用的时间消耗占比高，CPU 利用率低、用户态 CPU 时间远小于挂钟时间，即可判定程序有明显的 I/O 瓶颈，应优化 I/O 操作（例如减少读写次数、合并小文件、采用批量 I/O、异步 I/O 或缓存等手段）。

## 4.4 案例 4：综合性能分析流程

**完整分析流程**：
```bash
# 1. 整体性能评估（含 cycles, instructions, IPC 等）
perf stat ./program

# 2. 定位热点函数（配合调用栈）
perf record -g ./program
perf report

# 3. 针对瓶颈逐项分析
perf stat -e cache-misses ./program      # 缓存瓶颈
perf stat -e branch-misses ./program     # 分支瓶颈
perf stat -e instructions,cycles ./program  # 指令与周期效率

# 4. 分析系统调用（I/O 瓶颈）
strace -c ./program

# 5. 生成火焰图（可视化分析）
perf record -F 99 -g ./program
perf script | stackcollapse-perf.pl | flamegraph.pl > flame.svg
```

## 4.5 案例 5：实时监控线上问题

**场景**：线上服务 CPU 使用率突然升高，需要快速定位问题。

**操作步骤**：
```bash
# 1. 找到进程 PID
ps aux | grep your_program

# 2. 实时监控热点函数
perf top -p <pid>

# 3. 如果需要详细分析，采集数据
perf record -p <pid> -g -- sleep 30  # -- sleep 30 的意思是让 perf 对指定进程采样 30 秒
perf report

采集输出火焰图。
perf record -p <pid> -g -- sleep 30
perf script | stackcollapse-perf.pl | flamegraph.pl > flame.svg

# 4. 分析系统调用（如果是 I/O 问题）
strace -p <pid> -c -- sleep 10

```

**输出示例**：
```
Samples: 10K of event 'cycles', Event count (approx.): 1000000000
Overhead  Command       Shared Object     Symbol
  34.56%  your_program  your_program      [.] foo
  22.34%  your_program  your_program      [.] bar
  12.45%  your_program  libc.so.6         [.] malloc
```

**解读**：`foo()` 函数占用 34.56% 的 CPU，是主要热点，需要优先优化。

---
**分析**：

- 如果 `perf top` 发现某个函数占用 CPU 非常高，可以进一步结合 `perf record`+`perf report` 分析其调用路径，或生成火焰图深入剖析调用关系。
- 结合 `strace` 可以快速判别问题是计算型（CPU）、I/O（磁盘/网络）还是锁竞争等系统调用相关。
- 火焰图直观展现调用栈在 CPU 上的分布，便于定位热点和长时间运行的瓶颈代码。
- 在线上分析时，关注进程稳定性，分析命令建议加上 `-- sleep N` 控制采样时长，避免过长影响业务。
- 高 CPU 占用问题常见原因：死循环、频繁内存分配、锁竞争、第三方库 bug、算法复杂度过高等。应结合源码分析逐步定位。

**小结**：实时线上性能问题排查，推荐流程为 `perf top` ——> `perf record/report` ——> 火焰图 ——> strace，辅以源码阅读和测试复现定位根因。

### 监控api
**要是调用某个api的函数的火焰图现实的时间比较长，这个时间是包括调用api的开始到返回的时间的总和，还是说api阻塞时，cpu被切换了的期间的时间不算，只计算cpu在这个函数上的时间？**

在 perf 火焰图（Flamegraph）中，函数所占的“时间”实际上统计的是 **CPU 在该函数（或其调用链）上消耗的时间**，即“CPU 指令周期”（cycles）或者 CPU sample 次数的累计。因此：

- “函数的火焰图高度/宽度”表示 **CPU 真正在该函数/调用栈上运行的时间**，**不会**将线程因阻塞（如等待 IO、系统调用阻塞时）被切换出去的时间算进去。
- 如果你的代码调用了一个阻塞型 API（比如 read、recv、某数据库 RPC），当该线程在内核态等待期间，CPU 会去调度其他线程或任务，perf 不会统计此时该“阻塞”线程上的时间。
- 所以 **火焰图显示的时间是“CPU 活跃时间”，不包含等待 API 响应、IO、sleep 等被调度器挂起的时段**。

**简单理解：**
> 火焰图统计的就是 CPU 实际运行在该函数/调用栈上的消耗，只有当 CPU 在这个函数上执行指令时，才会被 perf sample 到、统计进 flamegraph。阻塞期间（线程没用 CPU）并不会计入。

**例子：**
- 函数 func() 调用 read()，read 阻塞 500ms，CPU 只在 user space 执行 func() 的部分花了 3ms，那么火焰图里 func() 的时间只会显示 3ms。
- 如果你希望看到系统调用花的“墙钟时间”，要用 `strace -T`、bpftrace 等工具分析“函数耗时”而不是“CPU 时长”。

**结论：**
- 火焰图里的“时间”，反映的是 **CPU 活跃在该函数/调用栈的累计时长**，**不会统计阻塞期间被调度出去的等待时间**。

如果想知道包括阻塞等待在内的“端到端延迟”，需要用 `std::chrono`、`gettimeofday` 之类在代码里主动打点测量，或者用 tracing 工具。

**要是调用远程api（例如grpc的接口）出现perf 火焰图 cpu时间比较长的现象，分析下原因是什么？以及优化的方式有哪些？**

调用远程 API（如 gRPC 接口）在 perf 火焰图上出现 CPU 时间较长的情况，说明 CPU 实际消耗主要集中在发起或处理远程调用的相关函数上，而不是线程处于阻塞等待状态。

原因分析：

1. 数据序列化/反序列化耗时  
   远程调用通常基于 protobuf、JSON 等格式进行数据编解码，若数据结构复杂或对象较大，序列化和反序列化过程会明显消耗 CPU。

2. 加解密/压缩等数据处理  
   开启了 TLS/SSL、网络包压缩等功能会导致 CPU 在加解密或压缩解压流程中消耗大量资源。

3. 网络协议栈和拷贝开销  
   gRPC 基于 HTTP/2，需要流控、包组装/拆包和多层 buffer 拷贝，尤其在高并发/大包小包频繁切换时更明显。

4. 回调逻辑或同步等待自旋    
   部分异步 gRPC 客户端/服务端实现会有回调处理、状态轮询、CompletionQueue 事件分发等机制， 若实现有 busy-wait 或自旋锁等问题，会导致无谓 CPU 消耗。

5. 过度频繁的小批量请求    
   如果高并发下每次远程 API 调用数据包很小，导致系统分包、调度、上下文切换频繁，也会在 perf 中体现为较高 CPU 利用。

典型优化方式：

1. 优化序列化模型  
   简化 protobuf 结构或按需选用更高效的编解码库，移除不必要的字段，避免深嵌套和大对象。

2. 批量/合并请求  
   对于可合并的多个小请求，尽可能做 batch 发送/聚合，减少协议处理和上下文切换开销。

3. 合理配置加密/压缩  
   仅对敏感数据或需要远端传输压缩的数据打开加解密/压缩功能，其他场景可根据本地交换区/内网情况酌情关闭，以减少 CPU 压力。

4. 避免自旋和忙等待  
   检查 CompletionQueue、回调线程池等实现，避免无效自旋或高频轮询，优先采用事件或条件变量唤醒。

5. 减少内存拷贝  
   优化网络 buffer，用零拷贝（zero-copy）、池化 buffer 等方式尽量减少数据拷贝次数。

6. 合理调优线程数与并发度  
   根据工作负载调整 gRPC 线程池/CompletionQueue 数量，避免线程竞争和锁争用。

7. 避免频繁创建/销毁 gRPC Channel  
   尽量复用连接而不是每次调用都新建 channel 或过于频繁建连、断连。

通过上述分析和优化，可以有效降低远程 API 调用时 CPU 的实际消耗，提高服务整体吞吐与响应效率。
