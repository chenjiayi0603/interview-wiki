# 远程调用问题（面试高频 — "第三方不可控"怎么处理）

## 3.1 问题本质

你调用别人的接口，别人的代码、机器、网络你全看不见。它突然超时、突然503、突然返回半截数据——你的服务不能跟着挂。

## 3.2 面试答题框架：五层防线

```
第1层：超时控制（不给对方拖死我的机会）
第2层：重试策略（区分可重试/不可重试，退避+抖动）
第3层：熔断降级（快速失败，保护自己）
第4层：隔离（线程池隔离/信号量隔离，防止资源被耗尽）
第5层：兜底（缓存兜底/默认值/降级逻辑，保证核心链路可用）
```

## 3.3 具体话术（口述版）

**"第三方接口突然变慢或不可用，你们怎么处理？"**

> 这个问题我们线上遇到过很多次。核心思路是**不能信任任何外部依赖**，每一层都要有防御。
>
> 第一，所有远程调用必须设超时。我们不是设一个死值，而是根据 P99 动态调整，比如 Redis 调 50ms，HTTP 调 2s。
>
> 第二，重试要非常小心。最大的坑是**重试放大**——A 调 B 超时了重试 3 次，B 又调 C 重试 3 次，一次用户请求变成 9 次下游调用，直接把下游打挂。我们的原则是：只对幂等接口重试、用指数退避加随机抖动、限制最大重试次数。
>
> 第三，熔断是最后防线。我们用的是滑动窗口统计错误率，连续失败超过阈值就打开熔断器，快速失败而不是干等。熔断后定期探测（半开状态），恢复后渐进放量。
>
> 第四，资源隔离。不能让一个慢的远程调用把整个线程池都占满。我们用独立的线程池或连接池，对于特别不稳定的依赖，甚至会做物理隔离。
>
> 第五，兜底逻辑。Redis 挂了能不能走本地缓存？推荐服务挂了能不能返回默认的热门列表？**降级不是不做，而是做"有损但可用"的服务**。

## 3.4 可追问技术细节

**Q: 熔断器的三个状态和参数怎么配？**

- **关闭(Closed)**：正常调用，统计错误率
- **打开(Open)**：错误率达阈值（如 50%），直接快速失败，持续一段冷却时间
- **半开(Half-Open)**：冷却时间到，放少量请求探测，成功则关闭，失败继续打开
- 关键参数：错误率阈值、滑动窗口大小、冷却时间、半开探测数量——都要根据业务压测数据定，不是拍脑袋

**Q: 重试导致的幂等性问题怎么解决？**

- 请求带唯一 idempotent-key（业务唯一 ID 或 UUID）
- 下游用 Redis 记录已处理的 key + 结果，重复请求直接返回缓存结果
- 或者下游业务本身就是幂等的（如"设置状态=已支付"，重复设置无害）

**Q: 连接池满了怎么办？**

- 首先区分是连接泄漏（没归还）还是真的不够用
- 连接泄漏：监控连接池空闲数+活跃时间，主动回收超时空闲连接
- 真不够用：调大 poolSize + 缩短超时 + 评估是否需要扩容下游
- 配置连接池等待队列大小，满时快速失败而非无限排队
