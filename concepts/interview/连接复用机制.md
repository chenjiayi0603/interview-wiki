# 连接复用机制

## 6.1 服务器推送与客户端消息共用连接

**答案：是的，服务端推送和客户端发消息都复用同一个 WebSocket 连接。**

WebSocket 协议本身是全双工通道，客户端和服务端均可在已建立的同一连接上任意时刻主动发送消息，无需新增连接。在 IM 等业务场景中，其特点包括：

- 客户端通过 Nginx（wss）连接，经过反向代理与协议升级，Access 网关始终维护该客户端的唯一长连接
- 所有类型的下行消息（服务端主动推送/通知/消息同步等）均通过已建立的 WebSocket 连接直接发送，无须新建连接通道
- 无论客户端发消息，还是服务端推送，均走这唯一的 ws/wss 通路，由 Access 网关统一分发与格式处理

**主要优势：**

- 节省连接资源：一条连接双向通用，无需多通道
- 推送即时性高：服务端可第一时间将消息直达客户端，无需轮询或额外通道
- 状态管理简化：连接/会话信息仅需一处管理，统一维护

**流程示意：**

```
客户端
  ⇄ WebSocket 长连接（同一条） ⇄ Nginx
                                    ⇄ Access 网关
                                      （可随时主动向在线客户端推送消息）
```

**注意事项：**

- 只要客户端在线且连接未断开，服务端即可主动推送消息
- 推送前，权限与 session 校验需依托 Redis 状态与 sessionKey 等安全机制
- Nginx 负责将客户端发来的 wss（加密 WebSocket）流量转换为 ws（非加密 WebSocket）转发至 Access 网关
- Access 返回的 ws 消息由 Nginx 转封装为 wss，确保传输链路全程加密

**结论：** 服务端所有主动推送和客户端消息，均基于同一 WebSocket 连接双向通信，无需为推送单独建立新通道，协议原生即支持。
