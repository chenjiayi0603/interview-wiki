## CLS vs Go Context

libgo 的 CLS（协程本地存储）和 Go 的 context 并不完全等价，但都能实现“每个协程拥有各自独立副本”的效果。

- Go 的 `context.Context` 是一种跨协程（goroutine）传值的机制，适合用于跨调用链传递请求信息（如 traceID/userID/超时等），但其本身并不是自动每个 goroutine 拥有独立副本，而通常是显式传递 context。

- libgo 的 CLS（Coroutine Local Storage）为每个协程自动分配一份变量副本，这个副本会被拷贝（通常是初始化或赋值时）并与协程生命周期绑定，系统把这些变量副本保存在协程自身的管理结构中。这样每个协程访问的 CLS 变量都完全隔离，不会相互影响，也不需要手动通过函数参数传递或上下文传递，直接在协程体内访问即可，无需额外传参。

这些变量是指通过`CLS(Type, name);`这种方式声明的协程本地变量，其内容可以是任意支持拷贝的类型（如 int、double、结构体、自定义类等）。每声明一个 CLS 变量，例如 `CLS(int, value);`，libgo 就会为每个协程分配一份独立的 `value` 副本。开发者可以在协程内部把数据（比如业务标识、计数器、中间状态、统计信息等）存到 CLS 变量里，这些内容只在当前协程内有效、互不干扰。

也就是要存哪些 CLS 变量，都是自己用 `CLS(Type, name);` 这一句一条条声明的。只要你声明了，libgo 就为每个协程分配独立副本；没写声明的变量就不会自动被存进 CLS，不会漏也不会多存。不会自动把所有的局部数据或临时变量记进“协程本地”，一切以你写的 `CLS(...)` 声明为准，所以管理起来很清晰，并不会出现遗漏。

为啥不把所有局部数据或临时变量都自动保存到 CLS（协程本地存储）里？这是为了让开发者自己明确控制哪些数据需要“协程隔离”。只有你明确用 `CLS(Type, name);` 声明的变量才会单独分配副本，其他的局部变量或临时值不会默认记录进 CLS，这样不会产生多余的内存消耗，也避免把一些无关、临时的数据误存进去。从设计理念上，一切以你手动声明为准，既不会遗漏真正需要的，也不会多存无关内容，管理和调试都非常清晰。

```cpp
CLS(std::string, user_token);
CLS(int, local_count);

// 每个协程内 user_token、local_count 都是独立内容
```
因此，CLS 变量的内容由你声明的类型和值决定，适合存放需要与协程生命周期绑定且仅属于当前协程的数据。

**示例对比：**

Go context:
```go
func handler(ctx context.Context) {
    ctx2 := context.WithValue(ctx, "userID", "abc123")
    go func(c context.Context) {
        userID := c.Value("userID").(string)
        fmt.Println(userID) // "abc123"
    }(ctx2)
}
```
每个 goroutine 接收到同一份 context，只是值通过 context 传递和隔离，依赖传递调用。

libgo CLS:
```cpp
CLS(int, value);

go []{
    value = 1;
    printf("coroutine 1: %d\n", value.get()); // 1
};

go []{
    value = 2;
    printf("coroutine 2: %d\n", value.get()); // 2
};
```
每个协程自动拥有自己的 `value` 副本，互不干扰。

**总结：**
- Go 的 context 通常用于上下文传递、追踪、超时控制等，不自动区分协程副本，要手动传递和维护隔离。
- libgo 的 CLS 是每个协程自动拥有的本地变量，适合存储与协程生命周期绑定的数据，互相独立，无需手动传递。

## 调度效率

```
libgo 调度策略:
- 多线程调度，支持负载均衡
- 线程数可动态伸缩（libgo 通过定时检测任务队列长度、当前活跃线程数、CPU 占用率等信息来动态调节线程池规模。常见做法是：周期性统计队列积压任务数与线程繁忙情况，如果任务数持续高于线程总数阈值（如有大量任务堵塞等待分派），会自动增开线程应对高负载；如果任务量下降，且部分线程较长时间空闲，则逐步释放或休眠多余线程。算法细节可能包括“高水位/低水位”阈值、指数平滑平均队列长度、自适应回收延迟等策略，从而实现线程池的伸缩弹性，并兼顾资源利用率与任务响应效率。）
- 无队头阻塞

Go GMP 调度策略:
- Work Stealing 算法
- 抢占式调度  
  
  Go 的抢占式调度是通过定期在函数调用点插入抢占检查实现的。Go 运行时会周期性地设置抢占标志，当 goroutine 长时间运行
  时，下次函数调用或调用特定调度安全点时，运行时会检测到该标志并主动让出当前协程，切换调度到其他 goroutine。此外，Go 
  1.14 之后，goroutine 即使长时间执行循环，运行时也会在栈溢出检查点等位置自动插入抢占检查，从而避免某个 goroutine 长
  时间独占 CPU，实现真正的“软抢占”。
  
  Go 的抢占检查主要发生在以下几个位置，也称为“调度安全点”或“checkpoint”：

  1. 函数调用点：Go 编译器会在大多数函数调用（函数入口前，调用时）自动插入抢占检查。这意味着只要 goroutine 执行到一次函数调用，就有可能被抢占。
  
  2. 部分运行时操作：如通道操作、select、map 相关操作、内存分配等，都会隐式经过调度点。
  
  3. for 循环（Go 1.14 及以后）：编译器会为长时间运行的循环（尤其是无外部函数调用的循环）定期插入抢占检查，常见于栈溢出检测等位置。
  
  4. 特定的 runtime 检查点：例如内存分配（malloc）、垃圾回收相关以及系统调用返回或者 goroutine 阻塞/唤醒时。

  概括来说，Go 的抢占检查点分布非常广泛，既有自动插入，也有运行时隐式完成，确保任何 goroutine 都不会因为持续运行而长时间霸占 CPU。软抢占通过这些 checkpoint 实现调度公平。
- 系统调用时自动创建新线程
```
