# C++ 性能调优流程（闭环）

> 本文总结 C++ 后台程序性能调优的完整闭环流程，涵盖从问题明确到预防回归的五个阶段。

See also: [[C++性能调优关键指标]], [[C++代码层性能调优最佳实践]], [[C++性能分析常见问题与技巧]]

## 调优流程（闭环）

### 1) 明确问题

指标/现象/范围/时间线/版本差异。

**举例**：记录「P99 从 20ms 升到 150ms、发生在 14:00–15:00、仅华东 region、上周三发版后出现」，便于限定排查范围和做版本对比。

**分析**：问题描述越具体，复现和归因越容易；时间线和版本差异是定位根因的关键线索。

### 2) 基线与复现

基准压测、记录输入与配置、确保可重复。

**举例**：固定 QPS=2 万、请求 body 大小 1KB、同机同配置下连续跑 10 分钟，记录 CPU/内存/P99；之后任何代码或配置改动都在同一基准上对比，避免“换了压测数据导致结论失真”。

**分析**：没有基线就无法量化优化效果；可重复的压测能防止“优化”实为环境波动。

### 3) 观测与定位

采集指标、火焰图、trace、core、内核指标。

**举例**：先看监控确认是 CPU 高还是 IO 高，再用 `perf record` 采 60 秒生成火焰图找热点函数，用分布式 Trace 看慢请求卡在哪一 hop，必要时用 `perf c2c` 看 cache line 争用。

**分析**：先全局指标再局部热点，由面到点；火焰图解决“谁在耗 CPU”，Trace 解决“慢在哪一环节”。

### 4) 假设与验证

小步改动→A/B 或灰度→对比指标。

**举例**：假设“锁竞争是瓶颈”，只做锁分片这一项改动，在相同压测下对比 P99 和 QPS；若改善明显则保留，再做下一项（如对象池），避免多改合并无法归因。

**分析**：单变量实验才能确定因果；A/B 或灰度可在生产上安全验证，避免全量回滚成本。

### 5) 治疗与预防

总结、告警阈值、回归用例与基准、文档化。

**举例**：优化结束后写复盘文档（现象→根因→改动→数据），把 P99>50ms 加入告警，在 CI 中加一条“基准压测 P99 不得高于某阈值”的回归检查，下次发版前自动跑一遍。

**分析**：治疗是单次优化，预防是避免同类问题再现；文档和回归能沉淀经验、防止优化被后续提交“吃掉”。
