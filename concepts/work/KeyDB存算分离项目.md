> 任职：2023.3–2025.3 ｜ 角色：架构主 R
> 一句话：基于 RocksDB 扩展自定义 FileSystem 抽象层，统一 SSD / 元数据 / OBS 三种后端，实现 KeyDB 热数据 SSD + 冷数据对象存储的存算分离架构。

## 1.1 速览卡

**性能**：QPS 10万+，热数据 P99 <1ms，冷数据 P99 ~20ms，存储成本降 70%+，可用性 99.99%（计算面），热缓存命中率 95%+

**提升点**：
- 自研 RocksDB FileSystem 抽象层，统一本地SSD / gRPC元数据 / OBS 三种后端
- 冷热分层存储成本从 ¥0.35 降至综合 ~¥0.17/GB·月

**瓶颈**：
- 冷数据读 OBS 延迟 5–20ms（vs 本地 <1ms），命中率低时 QPS 急跌
- Compaction 抖动期 WAF 10–30x，P99 可达 50–200ms
- 元数据服务单点：gRPC 不可用 → 整体不可用

**优化方向**：异步预读+预热提升命中率；Compaction 限速错峰；元数据服务 Raft 3节点 + 本地TTL缓存降级

## 1.3 架构与关键设计

```
KeyDB 实例
  └─ RocksDB 引擎（持久化层）
       └─ 自定义 FileSystem 抽象层（继承 rocksdb::FileSystem）
            ├─ 热数据：本地 SSD 缓存（P99 <1ms）
            ├─ 元数据：gRPC → 元数据存储服务（Etcd）
            └─ 冷数据：SDK → 华为 OBS 对象存储（P99 ~20ms）
```

**关键设计维度：**

| 调优维度 | 关键设计 | 防御点 |
|---------|---------|-------|
| **FileSystem 抽象层** | 继承 `rocksdb::FileSystem`，重写 `NewSequentialFile/NewRandomAccessFile/NewWritableFile`，按路径前缀分发到 SSD/Meta/OBS | RocksDB 原生设计就是为了换底层 IO，TiKV/Pika 都用过类似手法 |
| **LRU 冷热分层** | SST 文件级粒度，访问时间 + 频次综合打分；后台扫描线程异步迁移 | 与 Cassandra Tiered Storage、HBase HFile 分层同思路 |
| **元数据缓存 + 熔断** | gRPC 同步 + 本地 TTL 缓存 + 熔断降级；元数据高频但变化少 | 与 etcd watch + local cache 模式一致 |
| **多租户隔离** | 每租户独立 KeyDB 进程 + OBS bucket 路径前缀 + cgroup 限 IO/CPU | 物理隔离最简单可靠 |
| **异步迁移** | 后台线程批量迁移，不影响主路径 QPS | 与 RocksDB Compaction 异步合并同思路 |

## 1.4 冷热分层与成本分析

**成本降低 70%+ 的计算推演：**

| 存储类型 | 单价 | 说明 |
|---------|------|------|
| 华为云内存（Redis 类缓存折算） | ~¥2/GB·月 | 内存昂贵 |
| 华为 OBS 标准存储 | ¥0.099/GB·月 | OBS 单价极低 |
| OBS 访问费 | 内网调用，忽略不计 | 内网无流量费 |

**代入 1TB 全量数据，100GB 热内存：**

| 内存单价 P_mem | Cost_old (1TB) | Cost_new | 净节省率 |
|--------------|---------------|----------|---------|
| ¥0.5/GB·月 | ¥500/月 | ¥149/月 | **70%** |
| ¥1.0/GB·月 | ¥1,000/月 | ¥199/月 | **80%** |
| ¥2.0/GB·月 | ¥2,000/月 | ¥299/月 | **85%** |

> 热数据受内存容量限制（~100GB），不随数据总量等比增长 —— **数据量越大，节省比例越高。**

**LRU 冷热分层判断标准：**
- SST 文件级粒度，每个文件维护 `last_access_ts` 和 `access_count`
- 打分公式：`access_count / (now - last_access_ts + 1)` — 单位时间内的访问密度
- 分数低于下四分位数的标记为"冷"，触发异步迁移到 OBS
- 与标准 LRU 区别：批量打分 + 异步迁移，粒度是 SST 文件级而非 key 级

## 1.6 RocksDB Compaction 瓶颈

**为什么 Compaction 在 OBS 上是致命问题：**

| 维度 | 本地 SSD | 远程 OBS | 劣化倍数 |
|------|---------|---------|---------|
| 写放大（WAF） | 10~30× | 同左 | — |
| 单次 IO 延迟 | 0.1~0.5ms | 5~30ms | **50~100×** |
| Compaction 期间 P99 抖动 | 5~20ms | **50~200ms+** | **10×** |
| OBS 单桶 PUT QPS 配额 | — | 500~2,000/s | 硬天花板 |

**Compaction write stall 的级联效应：**
> Compaction 产生的 SST 上传到 OBS 会消耗 PUT 配额。Compaction 高峰期 PUT QPS 打满 OBS 桶配额，触发 503 SlowDown → 上传失败重试 → 更严重的排队 → RocksDB 触发 write stall → 业务写入暂停。这是存算分离架构最核心的矛盾。

**缓解手段：**
- Compaction 限速（`rate_limiter`）+ 错峰调度（业务低峰期触发）
- 大 SST 文件减少 HTTP PUT 次数
- WAL 和 L0 留本地 SSD，只有深层 SST 落 OBS（混合冷热）
- Compaction 输出先写本地 SSD 再异步上传 OBS

## 1.7 调优故事集

**故事 1：Compaction write stall**
- ❌ 问题：Compaction 输出大量 SST PUT → 打满 OBS 单桶配额（500–2,000/s）→ 503 SlowDown → L0 堆积 → write slowdown → 业务写入暂停。
- 🔧 手段：① 限速错峰，Compaction 速率控在配额 70% 内，大 Compaction 放凌晨；② WAL+L0 留本地 SSD；③ 大 SST（256MB）减少 PUT 次数。
- 📊 效果：线上未出现 Compaction 导致的业务中断。
- ⚠️ 代价：Compaction 变慢，L0 堆积量增加。OBS 上 stall 风险是本地 10–50×，无法根除。

**故事 2：元数据服务单点**
- ❌ 问题：元数据服务挂掉 → 文件 open/list 失败 → 存储引擎不可用。
- 🔧 手段：① 本地 TTL 缓存，读路径绕开 gRPC；② 熔断器监控错误率，降级到本地缓存；③ 恢复后异步对账。
- 📊 效果：读路径不受元数据短暂故障影响。
- ⚠️ 代价：缓存不一致窗口期可能读到旧元数据。

**故事 3：冷数据 P99 抖动**
- ❌ 问题：热缓存命中率从 95% 掉到 80% → 冷请求翻 4 倍 → 冷数据 P99 ~20ms 拖垮整体 P99。
- 🔧 手段：① 频次×时间衰减打分 LRU，防一次性扫描 evict 热数据；② 热点 key 预热；③ 冷热分桶监控，命中率 <90% 告警。
- 📊 效果：命中率稳定 95%+，冷请求 <5%。
- ⚠️ 代价：预热消耗额外 OBS 读带宽（低峰可忽略）。

## 1.8 追问预案

**Q：FileSystem 抽象层具体怎么设计的？**
> RocksDB 自带 `rocksdb::Env` 和 `rocksdb::FileSystem` 两个抽象。继承 FileSystem，重写文件读写接口，按路径前缀分发——`/local/...` 走 SSD，`/meta/...` 走元数据 gRPC，`/obs/...` 走 OBS SDK 的 Range Read。

**Q：LRU 冷热分层判断标准？**
> SST 文件级粒度，每个文件维护最后访问时间和访问频次，后台扫描按 `(时间衰减系数 × 频次)` 打分。低于阈值的触发异步迁移。

**Q：元数据服务挂了怎么办？**
> 三层防御：① 本地 TTL 缓存默认命中（命中率 90%+）；② 熔断器开启后降级到本地缓存；③ 熔断恢复后异步对账。最坏情况写入暂不可达，读路径不受影响。

**Q：冷数据 OBS 读 20ms 对总 P99 影响？**
> 冷数据访问是低频路径，业务侧热数据命中率 95%+，冷请求量在总量 5% 以下。监控里冷热分桶统计，主 P99 只看热路径。

**Q：多租户怎么防止 noisy neighbor？**
> 进程级隔离（每租户独立 KeyDB 实例）+ OBS bucket 独立 + cgroup 限 CPU/IO + 网络 QoS。

**Q：99.99% 是 SLA 还是实测？**
> 对外 SLA 承诺计算面 99.99%（纯 KeyDB 计算节点层）。数据面因依赖 OBS（SLA 99.9%），整体可用性在 99.9%+。冷数据路径依赖 OBS 是架构上已知的 trade-off。

**Q：RocksDB 写放大怎么控制？**
> ① 动态 `rate_limiter` 限速，业务高峰放开、低谷收紧；② `max_bytes_for_level_base` 调大 L1 容量；③ 使用 `level_compaction_dynamic_level_bytes`；④ WAL 和 L0 留在本地 SSD，只有深层 SST 才落 OBS，避免 Compaction 输出直接打 OBS 带宽。

**Q：如果重新设计存算分离，会改什么？**
> 三处：① 元数据引入 etcd watch 机制（push 替代 pull）；② Compaction 离线到独立计算集群（Snowflake 模式）；③ 热缓存层用分布式缓存替代 RocksDB Block Cache。

### QPS 10万+

**实际含义：**
读写混合场景下，整个 KeyDB 集群对外提供的总吞吐量。

**测量方式：**
- 工具：`redis-benchmark` 或内部压测工具
- 读写比约 7:3（缓存场景读多写少）
- 测试条件：热数据命中本地 SSD 缓存，绕过远程 OBS

**为什么是这个量级：**
- KeyDB 本身基于 Redis，单实例极限 QPS 约 10–20 万（取决于命令类型）
- 存算分离后热数据走本地缓存，性能与纯本地 KeyDB 接近
- 冷数据走 OBS，读延迟 5–20ms，QPS 会下降到千级以内

**被问到时要补充：**
> "这个 10 万+ 是热数据路径下的数字。冷数据读取因为要走远程 OBS，延迟会到 5–20ms，QPS 相应下降。所以关键是缓存命中率，我们通过 LRU 策略 + 预热保证热数据命中率在 95% 以上。"

### 存储成本降低 70%

**实际含义：**
冷热分层后，把低频访问的 SST 文件从本地 SSD 迁移到 OBS 对象存储，单位存储成本大幅下降。

**架构对比（成本差异的根源）：**

| 架构 | 存储方式 | 说明 |
|------|---------|------|
| 老架构（存算不分离） | 全量数据在内存（RAM） | 所有数据常驻内存，内存贵 |
| 新架构（存算分离） | 热数据留内存 + 全量数据落 OBS | 冷数据从内存迁到磁盘，内存用量大幅缩减 |

> 核心节省来自：把冷数据从昂贵的内存迁移到廉价的 OBS，**不是 SSD vs OBS 的对比**。

**价格基线：**

| 存储类型 | 单价 |
|---------|------|
| 华为云内存（Redis 类缓存服务折算） | ~¥2/GB·月 |
| 华为 OBS 标准存储 | ¥0.099/GB·月 |
| OBS 访问费 | 内网调用，忽略不计 |

**计算公式（通用）：**

```
设：
  N     = 总数据量（GB）
  r_hot = 热数据比例（如 30%）
  P_mem = 内存单价（/GB·月）
  P_obs = OBS 存储单价（¥0.099/GB·月）
  注：内网访问 OBS，无下行流量费

老架构成本：
  Cost_old = N × P_mem

新架构成本：
  Cost_new = N × r_hot × P_mem   （热数据内存）
           + N × P_obs            （OBS 全量存储）

净节省率：
  saving = (Cost_old - Cost_new) / Cost_old
         = 1 - r_hot - P_obs / P_mem
```

**代入数值（全量数据 1TB，热数据（内存上限）100GB，冷数据 900GB）：**

```
设：
  N_total = 1,000 GB   （全量数据，落 OBS）
  N_hot   = 100  GB    （内存容量上限，留 RAM）
  N_cold  = 900  GB    （90% 冷数据，迁 OBS）
  热比例   = 100/1000 = 10%

老架构成本（全内存）：
  Cost_old = 1,000 × P_mem

新架构成本（内存 100GB + OBS 全量）：
  Cost_new = 100 × P_mem + 1,000 × 0.099
           = 100 × P_mem + 99

净节省率：
  saving = (1,000×P_mem - 100×P_mem - 99) / (1,000×P_mem)
         = 0.9 - 0.099/P_mem
```

**节省率随内存单价的变化：**

| 内存单价 P_mem | Cost_old(1TB) | Cost_new(1TB) | 净节省率 |
|--------------|--------------|--------------|---------|
| ¥0.5/GB·月   | ¥500/月       | ¥149/月       | **70%** |
| ¥1.0/GB·月   | ¥1,000/月     | ¥199/月       | **80%** |
| ¥2.0/GB·月   | ¥2,000/月     | ¥299/月       | **85%** |

> 热数据受内存容量限制（~100GB），不随数据总量等比增长，数据量越大节省比例越高。

**被问到时要补充：**
> "核心节省来自把冷数据从内存迁到 OBS 磁盘——内存昂贵、OBS 廉价，OBS 内网访问无流量费。热数据受内存容量限制约 100GB 留在内存，其余 900GB 冷数据落 OBS，热比例约 10%，综合算下来存储成本节省约 **70%**。"

### 冷热分层延迟对比

| 路径 | 延迟 |
|------|------|
| 热数据（本地 SSD） | P50 <0.5ms，P99 <1ms |
