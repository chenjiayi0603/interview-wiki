# 上下文切换高

> 上下文切换（Context Switch）是操作系统在多任务调度时，将 CPU 从当前线程/进程切换到另一个线程/进程的过程。频繁的上下文切换会带来显著的性能开销，包括 TLB 刷新、cache 失效、调度器开销等。本文总结常见的上下文切换高场景及其治理手段。

See also: [[C++多线程与并发]], [[C++并发性能优化]], [[Linux线程调度]], [[C++性能调优关键指标]], [[C++代码层性能调优最佳实践]]

## 绑核、NUMA 亲和与线程池

**要点**：将线程绑定到固定 CPU 核心，可减少 cache 失效和调度迁移；NUMA 亲和则让线程尽量只访问本节点的内存，避免跨 socket 访问带来的高延迟。线程数过多会加剧上下文切换和调度开销，应与物理核数同量级或略少；用线程池复用线程，避免在请求路径上频繁 `std::thread` 创建/销毁。

**举例**：

- pthread 绑核：
  ```cpp
  cpu_set_t cpuset;
  CPU_ZERO(&cpuset);
  CPU_SET(core_id, &cpuset);
  pthread_setaffinity_np(pthread_self(), sizeof(cpu_set_t), &cpuset);
  ```
- numa 绑内存/CPU：
  ```
  numactl --physcpubind=0-7 --membind=0 ./server
  ```
- 线程池伪代码：
  ```cpp
  ThreadPool pool(std::thread::hardware_concurrency());
  ```

## 锁竞争优化

**要点**：锁争用会带来自旋、睡眠和大量上下文切换。手段包括：**细粒度锁**（按 key 或 shard 分桶，缩小临界区）、**读写锁**（读多写少时用 `shared_mutex`）、**无锁结构**（RCU 读多写少、无锁环形队列做生产者-消费者）、**避免在持锁时做 IO**（临界区内只做内存操作，DB/网络移出锁外）。

**举例**：

- 分片锁：
  ```cpp
  std::mutex locks[64];
  std::lock_guard<std::mutex> lk(locks[key % 64]);
  ```
- 读多写少，读写锁：
  ```cpp
  std::shared_mutex mu;
  std::shared_lock rlock(mu);  // 读
  std::unique_lock wlock(mu);  // 写
  ```
- 用无锁环形队列替代 mutex 队列：
  ```cpp
  boost::lockfree::spsc_queue<int, capacity<1024>> queue;
  ```
- 日志写不在锁里写盘：
  ```cpp
  // 锁里写 buffer, 异步线程落地
  ```

- 分析锁争用:
  ```
  perf record -e 'lock:*' -p <pid>; perf report
  ```

## 慢路径异步化

**要点**：磁盘、网络、DB 等 IO 是"慢路径"，若放在主事件循环或请求线程里同步执行，会阻塞整条链路。应把 IO 交给异步接口（如 io_uring、epoll + 非阻塞 fd）或独立 IO 线程/协程，主循环只做就绪事件分发和内存计算，避免"一个慢请求拖住整机"。

**举例**：

- 使用 boost::asio 或 libevent 实现非阻塞异步网络请求。
  ```cpp
  // boost::asio 示例
  boost::asio::async_read(sock, buffer, handler);
  ```
- 自己管理下游 HTTP 任务队列和回调
- 协程库如 libgo 协程异步等待
- 指令观测主线程阻塞可以用 strace:
  ```
  strace -c -p <pid>
  ```

## 异步 IO 与网络参数

**要点**：**异步 IO**：Linux 下 io_uring 或 epoll ET + 非阻塞 fd，单线程可驱动大量连接；**批量收发**：尽量一次 read/write 多包，减少系统调用次数。**TCP 调优**：根据场景调整 Nagle/`TCP_NODELAY`、Delay ACK、RTO、keepalive；大缓冲可设 `SO_RCVBUF`/`SO_SNDBUF` 或 `net.core.rmem_max` 等。

**举例**：

- epoll ET 非阻塞简例：
  ```cpp
  int flags = fcntl(fd, F_GETFL, 0);
  fcntl(fd, F_SETFL, flags | O_NONBLOCK);
  epoll_ctl(epfd, EPOLL_CTL_ADD, fd, ... | EPOLLET);
  ```
- 设 TCP_NODELAY:
  ```cpp
  int flag = 1;
  setsockopt(fd, IPPROTO_TCP, TCP_NODELAY, &flag, sizeof(flag));
  ```
- io_uring 批量发送：
  ```cpp
  io_uring_prep_write(sqe, fd, buf, len, offset);
  io_uring_submit(&ring);
  ```
- sysctl 改 socket 缓冲：
  ```
  sysctl -w net.core.rmem_max=67108864
  ```

## CPU 绑核、cgroup 与隔离

**要点**：**绑核与 NUMA**：关键进程绑定到指定核心，避免被调度到其他核带来的 cache 冷启动。**隔离**：用 cgroup 限制 CPU/内存，避免与 noisy neighbor 争抢；必要时用 isolcpus 将核心专供关键进程。**频率**：关闭频繁的调频（如固定性能模式），减少因频率抖动带来的延迟方差。

**举例**：

- 指定进程绑核：
  ```
  taskset -c 0-7 ./match_engine
  ```
- Cgroup 限定资源：
  ```
  cgcreate -g cpu:tradegroup
  cgset -r cpuset.cpus="0-7" tradegroup
  cgexec -g cpu:tradegroup ./match_engine
  ```
- 容器配置 CPU/内存：
  ```
  docker run --cpuset-cpus="0-7" --memory 8g ...
  ```
- 固定 CPU 频率/关闭低功耗状态
  ```
  cpupower frequency-set -g performance
  ```

## 编译选项：LTO、PGO 与异常

**要点**：**LTO（Link Time Optimization）**：链接期跨编译单元优化，可能带来 5%～15% 性能提升，但链接慢、偶有符号或 ABI 问题，需充分测试。**PGO（Profile-Guided Optimization）**：用典型负载采集 profile，再以该 profile 重新编译，使热点路径更优；需维护 profile 采集与回归流程。**异常**：在允许的前提下，核心路径可考虑 `-fno-exceptions` 或减少异常传播，降低冷路径开销；需与团队规范平衡。

**举例**：

- 加 LTO:
  ```
  # 开启 LTO 优化：在最终链接阶段（如 release 编译）加 -flto，允许编译器跨源文件做全局优化。例如将所有 cpp 编译和链接命令都加上 -flto 参数：
  g++ -O3 -flto main.cpp module1.cpp module2.cpp -o myapp
  ```
- 执行 PGO 流程
  ```
  # 1. 编译时启用 profile 信息采集
  g++ -fprofile-generate -O2 main.cpp -o myapp

  # 2. 用有代表性的生产流量在目标机器上运行，profile 数据会生成在可执行文件所在目录（通常为 `.gcda` 文件）
  ./myapp <生产流量>

  # 3. 用 -fprofile-use 时，需要用到之前 main.cpp 运行后生成的 profile 数据（如 `.gcda` 文件），通常在可执行文件所在目录下。如果目录有变动，需要用 `-fprofile-dir=<path>` 指定加载的 profile 路径，保证编译器用到的就是那次采集到的数据。不需要文件名。编译器会自动读取该目录下的所有 `.gcda` 文件来使用 profile 数据，无需手动指定单个文件。
  g++ -fprofile-use -O2 main.cpp -o myapp
  ```
- 禁止异常展开：
  ```
  g++ -fno-exceptions ...
  ```
- 错误处理用 std::expected:
  ```cpp
  std::expected<T,Err> foo() noexcept;
  ```

- 验证 PGO/LTO 性能提升：
  ```
  perf stat ./myapp
  ```
