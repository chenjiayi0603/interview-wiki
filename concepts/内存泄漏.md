# 内存泄漏

See also: [[内存管理]], [[智能指针]], [[C++高频面试问题]]

## 1. 内存泄漏类型

在 C++ 开发中，内存泄漏是一个需要重视的问题。了解其不同类型有助于更好地预防和排查。

| 类型 | 核心原因 |
|------|---------|
| **堆内存泄漏** | 使用 `new/malloc` 分配内存后，未能使用 `delete/free` 释放 |
| **系统资源泄漏** | 未释放文件句柄、网络套接字（Socket）、GDI 对象等系统资源 |
| **未定义虚析构函数** | 当基类指针指向子类对象时，若基类析构函数非虚，则子类析构函数不会被调用，导致子类资源泄漏 |
| **循环引用（智能指针）** | 主要发生在 `std::shared_ptr` 之间，两个或多个对象相互持有对方的共享指针，导致引用计数永不为零，无法自动释放 |
| **异常安全导致泄漏** | 在分配内存后、释放内存前，若程序因抛出异常而跳出正常执行流，会导致释放代码未被执行 |

## 2. 如何避免和检测内存泄漏

### 2.1 遵循 RAII 原则

RAII 是 C++ 资源管理的核心准则。其核心思想是：
- **在构造函数中获取资源，在析构函数中释放资源**
- 这样，只要对象生命周期结束（例如离开作用域），其析构函数就会被自动调用，从而确保资源被释放
- 使用智能指针（如 `std::unique_ptr`, `std::shared_ptr`）是实践 RAII 来管理内存的最直接方式

### 2.2 善用智能指针并打破循环引用

- 优先使用 `std::unique_ptr`（表示独占所有权）和 `std::shared_ptr`（表示共享所有权）来管理动态内存，避免手动 `new/delete`
- 如果对象间可能存在循环引用，将其中一个成员变量改为 `std::weak_ptr`，它是一个不增加引用计数的"弱引用"，从而打破循环引用

### 2.3 确保基类析构函数为虚函数

- 当一个类设计为会被其他类继承，并且会通过基类指针来操作派生类对象时，务必将基类的析构函数声明为虚函数（virtual）
- 这能确保通过基类指针删除派生类对象时，会正确调用派生类的析构函数，从而完整释放资源

### 2.4 使用工具进行检测

| 工具 | 平台 | 特点 | 适用场景 |
|------|------|------|---------|
| **Valgrind** | Linux | 功能全面，检测准确 | 深度调试，全面检测 |
| **AddressSanitizer** | Linux/Windows | 速度快（2-3倍），集成编译器 | 日常开发，快速检测 |
| **CRT Debug** | Windows | Windows原生支持 | Windows平台开发 |

## 3. Valgrind 在 C++ 内存管理中的使用

Valgrind 是 Linux 平台上最强大的内存调试工具之一。

### 3.1 Valgrind 简介

- Valgrind 是一个用于构建动态分析工具的框架
- 最常用的工具是 **Memcheck**，用于检测内存错误
- 通过模拟 CPU 执行程序，检测内存访问错误

**Valgrind 能检测的问题**：
- ✅ 内存泄漏（Memory Leaks）
- ✅ 使用未初始化的内存（Use of Uninitialized Memory）
- ✅ 读写已释放的内存（Use After Free）
- ✅ 读写越界（Buffer Overflow/Underflow）
- ✅ 重复释放内存（Double Free）
- ✅ 内存对齐问题（Misaligned Memory Access）

### 3.2 基本使用方式

```bash
# 基本语法
valgrind [选项] 程序名 [程序参数]

# 使用 Memcheck 工具（默认）
valgrind --tool=memcheck ./your_program

# 完整的内存泄漏检测
valgrind --leak-check=full --show-leak-kinds=all ./your_program
```

### 3.3 输出解读

- **definitely lost**：确定的内存泄漏，程序结束时仍有指针指向该内存
- **indirectly lost**：间接泄漏，通常由其他泄漏导致
- **possibly lost**：可能泄漏，指针可能指向内存中间位置
- **still reachable**：仍然可达，程序结束时仍有指针指向，但可能不是泄漏

### 3.4 常用 Valgrind 选项

```bash
# 基本选项
--tool=memcheck          # 指定使用 Memcheck 工具（默认）
--leak-check=full        # 完整的内存泄漏检测
--show-leak-kinds=all    # 显示所有类型的泄漏
--track-origins=yes      # 跟踪未初始化值的来源（性能较慢但更详细）
--verbose                # 详细输出

# 输出选项
--log-file=valgrind.log  # 将输出写入文件
--xml=yes                # 输出 XML 格式（便于工具解析）
--xml-file=valgrind.xml  # XML 输出到文件
```

### 3.5 Valgrind 的局限性

**Valgrind 无法检测的问题**：
- ❌ 栈上的数组越界（某些情况下）
- ❌ 静态内存的问题（全局变量）
- ❌ 某些编译器优化后的代码
- ❌ 多线程竞争条件（需要使用 Helgrind 工具）

**性能影响**：
- Valgrind 会使程序运行速度**慢 10-50 倍**
- 仅用于调试，不要在生产环境使用

### 3.6 Valgrind 与其他工具对比

| 工具 | 优点 | 缺点 | 适用场景 |
|------|------|------|---------|
| **Valgrind** | 功能全面，检测准确 | 速度慢（10-50倍） | 深度调试，全面检测 |
| **AddressSanitizer** | 速度快（2-3倍），集成到编译器 | 功能略少 | 日常开发，快速检测 |
| **CRT Debug** | Windows 原生支持 | 仅 Windows | Windows 平台开发 |

**建议**：
- 开发阶段：使用 AddressSanitizer 快速检测
- 深度调试：使用 Valgrind 全面检测
- 持续集成：两者结合使用
