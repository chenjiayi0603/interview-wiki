# C++内存溢出与栈溢出

See also: [[内存管理]], [[C++语言特性]], [[C++高频面试问题]]

## 一、已初始化数据段 / 栈很大时会不会 OOM？

**简短结论**：
- **会不会 OOM，取决于两个东西**：
  - **进程/线程可用的虚拟地址空间 / 配额**
  - **操作系统对段/栈大小的限制（以及链接/编译参数）**

### 1. 已初始化数据段（.data / .bss 很大）的情况
- **.data（已初始化的全局/静态变量）** 和 **.bss（未初始化或零初始化的全局/静态变量）**
  - 编译/链接后，这些段会占用 **可执行文件大小（主要是 .data）和进程虚拟地址空间**。
  - 运行时，如果总大小超过系统允许的范围（比如 32 位进程的 2G/3G/4G 虚拟空间上限），就可能在 **加载阶段就失败（类似 OOM / cannot map segment）**。
- 现代 OS（尤其是 64 位）一般虚拟地址空间非常大，**单纯几 MB、几十 MB 的全局数组一般不会直接 OOM**，但：
  - 如果你放一个 **几百 MB、几 GB 的全局数组**，在 32 位进程里极容易出问题。
  - 在嵌入式/裸机环境中，**物理内存很小**，链接时就可能直接报错（`region overflowed` 之类）。

**经验**：大块数据尽量不要放在全局静态数组里，**用堆（`new` / `std::vector` / `malloc`）按需分配**，便于检查失败与控制生命周期。

#### 示例 1：超大全局数组导致 data 段 / bss 段非常大

```cpp
// 例：1GB 的全局数组（int 4 字节）→ 2.5e8 个元素
// 32 位进程极容易因为地址空间不够在加载阶段就失败
// 注意：很多编译器/链接器在这种极端大小下编译/链接阶段就会报错

// 已初始化（.data）
int g_big_data[250000000] = {1};  // 大约 1GB

// 零初始化（.bss）
int g_big_bss[250000000];         // 也是大约 1GB

int main() {
    // 很可能程序根本起不来，或者一启动就失败
    return 0;
}
```

#### 示例 2：改用堆分配（更可控，也更容易检查失败）

```cpp
#include <vector>
#include <iostream>

int main() {
    try {
        // 改为用堆分配，按需申请。失败会抛出 std::bad_alloc。
        std::vector<int> data;
        data.reserve(250000000);  // 约 1GB

        std::cout << "分配成功，大小 = " << data.capacity() << std::endl;
    } catch (const std::bad_alloc&) {
        std::cerr << "内存分配失败（bad_alloc）" << std::endl;
    }

    return 0;
}
```

### 2. 栈很大的情况
- 每个线程都有一个 **栈大小上限**：
  - Linux 上可通过 `ulimit -s`、`pthread_attr_setstacksize` 等控制。
  - Windows 上通过链接器参数 `/STACK:reserve[,commit]` 指定主线程栈，子线程用 `CreateThread` / `std::thread` 时也可指定。
- **如果单个线程栈预留的虚拟空间太大**（比如几十 MB、几百 MB 甚至更多），可能导致：
  - 进程总体虚拟地址空间不足 → 创建线程失败（类似 OOM）。
  - 部分系统直接拒绝创建这么大的栈，返回错误。
- 栈本身一般是 **按需逐步提交物理页** 的（尤其在现代 OS），但虚拟地址空间得先预留出来，所以栈设得太大仍然会占用虚拟地址空间，**间接导致 OOM/创建线程失败**。

**经验**：
- 普通程序：默认栈一般够用（主线程 1MB～8MB 左右，各平台不同）。
- 深递归/大局部数组时：
  - 优先考虑改为 **迭代 + 堆分配 / `std::vector` / `std::string` 等**。
  - 确实需要大栈时，再去调大线程栈大小，并控制 **线程数量**。

#### 示例 3：大局部数组导致栈溢出（stack overflow）

```cpp
#include <iostream>

void foo() {
    // 如果默认栈只有 1MB 左右，这里直接在栈上放 8MB，很容易栈溢出
    char buf[8 * 1024 * 1024];  // 8MB
    buf[0] = 42;
    std::cout << "buf[0] = " << (int)buf[0] << std::endl;
}

int main() {
    foo();  // 可能直接 stack overflow
    return 0;
}
```

#### 示例 4：改成堆分配，避免栈溢出

```cpp
#include <iostream>
#include <vector>

void foo() {
    // 堆上申请 8MB，比栈安全得多，失败还能检查
    std::vector<char> buf(8 * 1024 * 1024);
    buf[0] = 42;
    std::cout << "buf[0] = " << (int)buf[0] << std::endl;
}

int main() {
    foo();  // 一般不会再因为栈空间不够而崩
    return 0;
}
```

### 3. 实战建议小结
- **全局/静态超大数组**
  - 尽量用堆代替；如果必须用，注意目标平台的 **地址空间 / 内存大小 / 链接脚本** 限制。
- **栈过大**
  - 优先减少栈上大对象、深递归；必要时才调大栈，并限制线程数。
- **64 位桌面/服务器程序** 一般不太容易因为几十 MB 的 .data/.bss 或栈直接 OOM，但在 **32 位、嵌入式、线程很多** 的场景要非常小心。

### 补充：更细一点的分类和建议（按提问整理）

#### 1）已初始化数据段 / BSS 太大会怎样？

- 典型情况：
  - `.data` 或 `.bss` 里放了一个巨大的数组：

    ```cpp
    int big[100000000];  // ~400 MB
    ```

- **链接阶段**：
  - 太离谱时有可能链接器就报错（不同平台限制不一样）。
- **程序加载阶段（OS 加载可执行文件到内存）**：
  - OS 需要为这些全局/静态对象保留虚拟地址空间，并根据需要映射物理页。
  - 如果进程可用的虚拟地址空间不够（尤其是 32 位进程），可能直接加载失败。
- **运行时**：
  - 大的 `.data/.bss` 会长期占用地址空间，后续再申请堆内存时更容易遇到：
    - `new` / `malloc` 返回空指针；
    - C++ 抛 `std::bad_alloc`。
  - 从调用者角度看就是“内存不够（OOM）”。

**总结**：
- 能把进程的虚拟地址空间吃满，从结果上确实可以导致 OOM。
- 在 64 位进程下，只是虚拟空间多得多，你可以声明得“更大”才会出问题，但不是无限。

#### 2）栈太大时会怎样？

常见两种情况：

1. **函数里放了一个巨大的局部数组（自动变量，分配在栈上）**：

    ```cpp
    void foo() {
        int a[100000000]; // 栈上 ~400MB
    }
    ```

    - 当函数被调用时，栈指针一下子跳到很前面，如果超过了线程栈的最大边界：
      - Linux：一般是段错误（`SIGSEGV`）。
      - Windows：通常是 stack overflow 异常。
    - 本质是 **栈溢出（Stack Overflow）**，而不是堆 OOM。

2. **递归层数太深**：

    ```cpp
    void dfs(int x) {
        int tmp[1024];
        dfs(x + 1);
    }
    ```

    - 每一层递归消耗一点栈空间，层数多了同样导致栈溢出。

**特点**：
- 一旦越界，一般是即时崩溃，不会像 `new` 一样“返回失败值”。
- OS 通常会给每个线程一个固定大小的栈（例如 1MB、8MB 等，取决于平台和配置）。
- 你可以在创建线程时显式调整栈大小，但超了就是 stack overflow。

#### 3）OOM vs Stack Overflow 的区别

- **OOM（Out Of Memory）** 多指：
  - 堆内存、或者向 OS 申请地址空间失败。
  - 典型迹象：`malloc` 返回 `NULL`、`new` 抛异常、系统日志记录“内存不足”。
- **Stack Overflow**：
  - 单个线程的栈空间用尽。
  - 典型迹象：程序直接崩溃，signal/exception 提示 `stack overflow` / `segmentation fault` / 访问违例等。

对应“已初始化数据段或者栈要是比较大”：
- **放在数据段 / BSS**：
  - 可能导致地址空间被大量占用 → 后面再申请内存更容易 OOM；
  - 极端时，程序都起不来。
- **放在栈**：
  - 大概率直接栈溢出崩溃，而不是“慢性” OOM。

#### 4）实际开发中的建议（再归纳一遍）

- **尽量不要用巨大的全局 / 静态数组**，尤其是几十 MB 以上的：
  - 优先考虑在堆上动态分配（`new` / `std::vector`），并检查分配是否成功；
  - 或者用内存映射文件等更灵活的方式（如处理超大数据）。
- **避免在栈上放大对象**：
  - 超过几十 KB 就要小心，跨平台库通常建议局部大数组不要超过几 KB～十几 KB；
  - 大块内存放到堆上（`std::vector` / `std::string` / 自己的 `new`）。
- **注意 32 位进程的地址空间上限**：
  - 即使物理内存很多，单进程可用的虚拟地址空间也就 2～3GB 左右（取决于 OS 设置和内核/用户空间划分）。
- **多线程时更要小心栈大小**：
  - 每个线程一个栈，如果一个线程栈配得很大，线程数多了，总地址空间 / 物理内存消耗也会惊人；
  - 同时，函数里仍然不要放上百 KB 的局部数组。

#### 5）如果“OOM”指的是“操作系统直接杀掉进程”

- 在 Linux 上，如果启用了 OOM killer，当**整个系统内存压力极大**时：
  - 你的进程因为占用内存太多，可能被 OOM killer 杀掉；
  - 这不区分是“堆 / 栈 / 数据段”，反正看总占用。
- 大的 `.data/.bss`、大的堆、很多线程的栈，都会叠加成总内存占用。

---

**问：已初始化数据段或者栈要是比较大会 OOM 吗？**
**答**：**有可能**。段/栈太大都会消耗虚拟地址空间或物理内存，在 **地址空间有限（特别是 32 位、嵌入式）或线程很多** 的情况下，确实可能在加载或创建线程时就失败，相当于 OOM；在 64 位常规环境下，合理范围内的一点“大”通常没问题，但不建议滥用，建议把大数据放堆上并控制好内存使用。

## 二、exit 和 _exit 的区别 & 宕机场景

**问：为什么有时候 `exit` 会宕机/卡死，而 `_exit` 却不会？**

**答：核心原因：**
- **`exit` 会做大量“用户态清理工作”**：
  - 调用所有通过 `atexit()` 注册的回调；
  - 刷新并关闭所有 `FILE*` 流（包括 `stdout`、`stderr` 等）；
  - 在 C++ 中还会触发全局/静态对象的析构；
  - 内部可能涉及 malloc/free、加锁/解锁、访问各种全局状态。
- **`_exit` 几乎不做清理，直接让内核结束进程**：
  - 不调用 `atexit` 回调；
  - 不刷新 `stdio` 缓冲，不触发 C++ 析构；
  - 只由内核回收文件描述符等内核资源，用户态不再折腾。

**典型会出现“`exit` 宕机，`_exit` 不会”的场景：**

- **1）信号处理函数/进程已经“半崩溃”时调用**
  - 进程收到致命信号或内部逻辑把堆、栈、全局状态搞坏；
  - 在信号处理函数或错误处理里调用 `exit`：
    - `exit` 去跑 `atexit` 回调、刷新流、析构对象，这些逻辑本身可能不是异步信号安全，而且会再次使用已经损坏的状态；
    - 于是可能在这些清理代码里再次崩溃或死锁，看起来像“退出时宕机”。
  - 换成 `_exit`：
    - 直接从内核层面杀掉进程，不再跑用户态清理逻辑，即使用户态已经乱了，也不会再在这一步卡住或崩溃。

- **2）`fork` 之后的子进程里调用 `exit`**
  - `fork` 之后，子进程继承了父进程的 `atexit` 回调列表、`FILE*` 流及其缓冲区、全局状态等；
  - 子进程里如果调用 `exit`：
    - 会再执行一遍这些来源于父进程的清理逻辑，可能导致：
      - 同一个文件缓冲/偏移被重复 flush，数据写重复；
      - 重复关闭、重复释放，造成未定义行为，甚至崩溃；
      - 某些回调只期望在“唯一一次退出”时执行，在子进程里执行会访问无效/不一致状态。
  - 而子进程里用 `_exit`：
    - 不执行这些回调和清理，不触发父进程那套逻辑，可以“干净利落地只结束当前子进程”，更安全。

- **3）多线程程序退出时**
  - 多线程程序中，C 运行时和各种库内部有复杂锁和全局状态；
  - `exit` 在清理阶段会关闭/flush 流、跑退出钩子、析构单例等，如果这些逻辑没有设计成线程安全，或者某个线程已经把状态搞坏，就可能在退出阶段死锁或崩溃；
  - `_exit` 则跳过整个用户空间清理逻辑，由内核一刀切终止所有线程，避免在“半崩溃状态”下再跑复杂逻辑。

**实践建议：**
- **正常、可控的程序退出**：
  - 用 `return` 从 `main` 返回，或者调用 `exit`，让资源被优雅释放。
- **不可恢复错误 / 信号处理 / `fork` 后的子进程只负责简单收尾就结束**：
  - 用 `_exit`，**不要再相信 C/C++ 运行时的清理逻辑**。
