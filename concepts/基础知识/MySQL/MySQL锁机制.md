# MySQL锁机制

See also: [[MySQL索引]]

## 按锁的粒度分类

| 锁类型 | 粒度 | 并发度 | 开销 | 适用场景 |
|-------|------|--------|------|---------|
| **表级锁** | 锁定整个表 | 低 | 小 | MyISAM引擎，全表操作 |
| **行级锁** | 锁定单行数据 | 高 | 大 | InnoDB引擎，高并发场景 |
| **页级锁** | 锁定数据页 | 中 | 中 | 较少使用 |

## 按锁的类型分类

| 锁类型 | 说明 | 兼容性 |
|-------|------|--------|
| **共享锁 (S锁)** | 读锁，允许其他事务读取，但不允许修改 | 多个事务可以同时持有共享锁 |
| **排他锁 (X锁)** | 写锁，不允许其他事务读取或修改 | 排他锁与其他任何锁都不兼容 |
| **意向共享锁 (IS锁)** | 表级锁，表示事务想要在表中的某些行上设置共享锁 | - |
| **意向排他锁 (IX锁)** | 表级锁，表示事务想要在表中的某些行上设置排他锁 | - |

## InnoDB行锁类型

| 锁类型 | 说明 | 适用场景 |
|-------|------|---------|
| **Record Lock（记录锁）** | 锁定单行记录 | 精确匹配的等值查询 |
| **Gap Lock（间隙锁）** | 锁定索引记录之间的间隙，防止其他事务在间隙中插入 | 防止幻读 |
| **Next-Key Lock（临键锁）** | Record Lock + Gap Lock的组合，锁定记录和记录前的间隙 | InnoDB默认的行锁实现，防止幻读 |

## 死锁

### 死锁产生的4要素（必要条件）

| 要素 | 说明 |
|-----|------|
| **1. 互斥条件** | 资源不能被多个事务同时使用，一次只能被一个事务独占 |
| **2. 请求与保持条件** | 事务在持有至少一个资源的同时，请求获取其他资源 |
| **3. 不剥夺条件** | 已分配给事务的资源不能被强制释放，只能由持有该资源的事务主动释放 |
| **4. 循环等待条件** | 存在一个事务等待链，每个事务都在等待下一个事务持有的资源 |

### 死锁示例
```sql
-- 事务A
BEGIN;
UPDATE users SET name = 'A' WHERE id = 1;  -- 持有id=1的锁
UPDATE users SET name = 'A' WHERE id = 2;  -- 请求id=2的锁（被事务B持有）

-- 事务B
BEGIN;
UPDATE users SET name = 'B' WHERE id = 2;  -- 持有id=2的锁
UPDATE users SET name = 'B' WHERE id = 1;  -- 请求id=1的锁（被事务A持有）
-- 结果：形成循环等待，产生死锁
```

### 死锁的预防
- 按相同顺序访问资源
- 减少事务持有锁的时间
- 使用较低的隔离级别
- 为表添加合理的索引，减少锁的冲突

### 死锁的处理
- InnoDB会自动检测死锁，并回滚其中一个事务
- 可以通过 `SHOW ENGINE INNODB STATUS` 查看死锁信息

## 锁的优化建议
1. **尽量使用索引**：没有索引会导致全表扫描，可能升级为表锁
2. **控制事务大小**：事务越大，持有锁的时间越长，死锁风险越高
3. **避免长事务**：长事务会长时间持有锁，影响并发性能
4. **合理使用隔离级别**：根据业务需求选择合适的隔离级别，不要盲目使用最高级别
