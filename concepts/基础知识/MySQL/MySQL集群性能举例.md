# MySQL 集群性能举例

> 本文档整理自 MySQL 高可用与集群架构中关于主从复制、分库分表性能的详细举例与分析。

## 3.1 主从复制架构

**结构**：1 主 N 从，主写从读。

| 场景 | 单机 | 1主1从 | 1主3从 |
|------|------|--------|--------|
| 读 QPS | ~5000 | ~10000 | ~20000 |
| 写 QPS | ~5000 | ~5000 | ~5000 |
| 延迟 | 0 | 主从延迟 1–100ms | 同左 |

**注意**：写能力仍由主库决定，主从主要解决读扩展。

### 硬件与软件配置详解（QPS 5000/1W 级别）

- **硬件配置举例**：
  - CPU：8 核心（8C16G，如 Intel Xeon 或 AMD EPYC）
  - 内存：16GB
  - 存储：企业级 NVMe SSD（高 IOPS、低延迟）
  - 网络：千兆或更高带宽
- **数据库版本**：MySQL 5.7 或 8.0 推荐
- **重要参数配置**：  
  - `innodb_flush_log_at_trx_commit=1`（确保事务持久性与可靠性）
- **主从标准部署**：
  - 生产环境常见部署为 1 主 1 从（共两台服务器，主库负责写，从库负责读）；高可用或读负载高时可扩展为 1 主多从（如 1 主 2 从、1 主 3 从等），主从数量根据实际业务读写比例和高可用需求灵活配置。
  - 业务量大可选择 1 主多从架构（读扩展）
- **复制与高可用**：
  1. **复制方式**：建议 row 格式（ROW），启用半同步或并行复制（MySQL 5.7+，`slave_parallel_workers` 可设置为逻辑 CPU 数的一半以上）
  2. **主从核心参数**：
     ```ini
     [mysqld]
     server-id = 1
     log_bin = mysql-bin
     binlog_format = ROW
     sync_binlog = 1
     innodb_flush_log_at_trx_commit = 1
     relay_log = relay-bin
     relay_log_recovery = ON
     skip_name_resolve = 1
     gtid_mode = ON
     enforce_gtid_consistency = ON
     log_slave_updates = 1
     read_only = 0
     super_read_only = 0
     slave_parallel_workers = 8
     slave_preserve_commit_order = 1
     master_info_repository = TABLE
     relay_log_info_repository = TABLE
     innodb_buffer_pool_size = 12G
     innodb_log_file_size = 2G
     ```
  3. **高可用**：建议 MHA、Keepalived 等监控主库，备机随时可切换，读流量建议合理分摊
  4. **分库分表支持**：如需扩展，可引入 Sharding-JDBC、MyCAT 等中间件
  5. **负载均衡**：中间件或 VIP 方式实现多从库读流量均衡

### 读写分布与瓶颈分析

- **常见分布参考**：
  - **读密集型（如电商、内容平台）**：读：写 ≈ 8:2 或 9:1
  - **SaaS 业务/交易类**：读：写 ≈ 7:3 或 6:4

- **单机极限下**（假设总 QPS 10000，读写 8:2）：
  - 读 QPS ≈ 8000，写 QPS ≈ 2000
- **主从架构**：
  - 读 QPS = 从库数量 × 单从最大读 QPS（如 1 主 3 从，总读 QPS ≈ 4 × 5000 = 20000）
  - 写 QPS 受限于主库（如单主写 QPS ≈ 5000）

| 架构 | 总写 QPS 上限 | 总读 QPS 上限（理论） |
|------|--------------|------------------------|
| 单机 | 5000～10000 | 5000～10000 |
| 1主1从 | 5000～10000 | 10000～20000（主+从） |

> *写瓶颈由主库决定，读瓶颈可通过加从库线性提升，总读能力 ≈ 从库数 × 单机读 QPS。*

### 分库分表触发信号与优化建议

- 当单表记录量超过 3000 万～5000 万行，且业务持续增长，单表/单库的写入、查询性能会逐步下降（如索引膨胀、查询慢、ALTER 慢等）。
- 但很多中小型业务 QPS 低于 5 千、总数据行数＜几千万，**单机或单库主从分离已可满足**，此时建议优先：
  1. **软硬件优化**：如提升 NVMe SSD、增加内存、升级网络等；调整 innodb_buffer_pool_size、redo/undo buffer 等 MySQL 参数。
  2. **读写分离/主从扩展**：利用多个从库分担只读压力，主库专注写入。
  3. **合理建索引与慢 SQL 优化**：针对热点/慢查询持续优化，避免全表扫描，大事务拆小。
  4. **缓存引入**：用 Redis/Memcached 缓存热点数据，极大减轻数据库压力。
  5. **调整连接池**：合理设置业务层连接池最大数、SQL 超时时间，防止突发流量堆积。
  6. **主从半同步/并行复制**：开启 semi-sync/并行复制减少主从延迟，合理配置 slave_parallel_workers。
- **实际触发分库/分表的典型信号**：
  - 单库的 QPS 达到或超出现有机器或存储能力极限，经调优、扩从、上硬件已无增长空间（写瓶颈不可拆分）。
  - 单表查询、写入、DDL（如加索引、分区）频繁超时影响整体服务。
  - 数据总量按年线性增长明确会突破单库/单表安全线（如历年订单、流水日志等）。
  - 历史表/archive 表持续暴涨，无归档和冷热分离措施。

### 历史表/归档表膨胀处理

1. **在线归档与冷热分离**：定期将冷数据（如超 6/12 个月的订单、流水等）在线归档到专门的历史归档表或单独归档库，主库仅保留近期限活跃数据。
2. **历史库分拆**：将历史数据独立迁移到单独的 MySQL 实例或存储系统（如 ClickHouse、TiDB、HBase、ElasticSearch）。
3. **自动周期归档**：每月、每季度开发自动化归档任务，将老分区/老表批量转存、转移或直接删除。
4. **查询路由与分层**：业务代码中实现“热表优先、本地表优先”逻辑。
5. **分区表设计优化**：历史流水、归档场景建议采用 MySQL 分区表（按时间/ID 范围分区），定期 DROP 老分区。

#### pt-archiver 工具

**pt-archiver** 是由 **Percona** 公司开发和维护的，属于 **Percona Toolkit** 工具集的一部分。

**安装方式**：
- CentOS / RHEL / Rocky Linux:
  ```sh
  sudo yum install perl-DBI perl-DBD-MySQL perl-Time-HiRes perl-TermReadKey
  sudo yum install https://www.percona.com/downloads/percona-toolkit/LATEST/percona-toolkit-latest.noarch.rpm
  sudo yum install percona-toolkit
  ```
- Debian / Ubuntu:
  ```sh
  sudo apt-get update
  sudo apt-get install percona-toolkit
  ```
- macOS (Homebrew)：
  ```sh
  brew install percona-toolkit
  ```

**使用示例**：
```sh
pt-archiver --source h=主库,u=用户,p=密码,D=业务库,t=主表 \
            --dest h=历史库,u=用户,p=密码,D=archive库,t=历史表 \
            --where 'created_at<"2022-01-01"' --limit=10000 --progress=1000
```

### QPS 2 万级别：分库分表、多从、本地高性能服务器

- **硬件配置举例**：
  - 每台服务器推荐 ≥ 8C16G，均为企业级 NVMe SSD，本地部署
- **集群规模参考**：
  - 主库与从库各建议 2–3 台（总4–6台以上），以保证负载均衡和高可用
  - 分库分表后，每个分片/分表独立配 1 主 1 或 2 从
  - 数据库版本建议 MySQL 8.0，充分利用其并行复制能力
- **缓存配合**：
  - 强烈建议将 Redis 等缓存集成到架构中，拦截高频读取（如热点订单、用户状态等）
- **高可用与可扩展性**：
  - 分片数量根据业务量和增长预留
  - 建议结合读写分离和自动路由中间件
- **实践建议**：
  - 采用企业级硬件和完整主从架构负载均衡，能在本地支撑 2 万级 QPS 以上

### “QPS 2 万” 和“5 千”的本质区别

| 指标 | 5 千 QPS | 2 万 QPS |
|------|----------|----------|
| 经验基线 | 按经验线最大推荐 | 理想/极致/部分读压力 |
| 业务复杂度 | 常见中等复杂业务 | 简单/点查/高缓存命中率 |
| 硬件 | 主流配置 | 高配/SSD/NVMe |
| 查询类型 | 范围查/索引查/混合 | 主键查/读为主 |
| 挑战 | 更易遇到瓶颈 | 调优到极致、失之毫厘差千里 |
| 适用场景 | 一般互联网业务 | OLAP/高并发点查/拆分后汇总 |

> **面试/实际建议**：明确“5千是保守经验值”“2万得看业务构成和硬件，有并发优化极致和压力测试经验”。精确容量必须实测，不可死记经验参数！

### 为什么云厂商的 MySQL 官方性能测试（QPS、并发数）这么高？

1. **硬件资源极致优化**
2. **数据模型理想化（压测场景单纯）**
3. **参数调优到极致**
4. **环境无干扰**
5. **主从复制设计优化/只计主库能力**
6. **最佳负载分布**

> **典型理解**：
> “官方压测QPS”是**物理极限/理想状态**；实际生产 QPS 通常因业务 SQL 更复杂、硬件/网络共享、备份负载、冷热点等多维限制，需适度折算（建议以 60~80% 作为带宽规划依据），并预留冗余空间。

### 为什么云数据库/官方标称 QPS 比开源 MySQL 单机的 5000 QPS 高这么多？

1. **硬件资源极致优化但本质上有 CPU/IO/网络极限**
2. **主库 redo log 写入的单线程瓶颈**
3. **分库分表/集群扩展躲过了单点极限**
4. **并行复制和组提交减少主从/主节点压力**
5. **测试场景进一步掩盖主线程瓶颈**

**结论/工程建议：**
- **单机 MySQL 的“极限QPS”**，写入型业务最终受制于 redo log 单线程顺序写盘能力（即主机的 IOPS），多核提升有限，“主节点 commit 队头阻塞”是大并发下常见现象。
- **开源 5000 QPS 是常见服务器+常规业务 SQL的现实值**。读多写少、或大量分库+只读副本时，QPS 才可能做得更高。
- **云 QPS 靠分片/集群/并行复制/高 IOPS 磁盘支撑**，但单主节点 redo log 物理瓶颈依然存在。做到数十万级 QPS，基本靠多节点叠加、实际瓶颈均摊。
- **生产环境下，一定要关注 redo log/IO wait/commit 队列延迟，不能只盯 QPS。**

### QPS 10 万级别及以上：大规模集群、分片与并行写入

- **硬件配置举例**：
  - 服务器：8C16G 及以上，企业级 NVMe SSD，推荐高性能网络
- **部署架构**：
  - 若分片 32 个库，每库 1 主 2 从，需 32 × 3 = 96 台服务器（可多分片合并于同主机以降本增效）
  - 每个分片独立配置主从，整集群横向扩展
- **数据库与参数**：
  - 优选 MySQL 8.0，高并发、并行复制优势突出
  - Group Replication、Semi-Sync、并行复制（`slave_parallel_workers=4~16`）等参数优化写入与延迟
  - Binlog 推荐 RAID10 或 NVMe SSD 提升写入吞吐
- **软件工具链**：
  - 读写流量自动分配、分库分表自动路由、主从失效切换等采用企业常用成熟中间件
- **容量规划与冗余**：
  - 根据业务实际数据量、QPS、单机性能等综合测算所需服务器数量，并适度预留冗余
  - 主库高峰写入和 binlog 吞吐为核心限制环节，需压测调优
- **推荐实践**：
  - MySQL 8.0 原生并行复制为大 QPS 集群首选，本地部署便于伸缩扩容和性能控制

### 并行复制详解

**并行复制（Parallel Replication）**即让从库按库、表或 GTID 组，将 binlog 日志拆分为多个并行 worker 执行。这样可以极大提高从库重放日志的速度，缩短主从延迟、提升整体复制的吞吐能力，尤其在业务分库分表、并发更新场景下效果明显。

- MySQL 8.0 引入更完善的多线程复制（库级/组提交级并行，`slave_parallel_workers` 参数）。
- MariaDB 和 Percona Server 也有类似并行复制方案（略有实现差异）。
- 实测并行复制可将主从延迟从秒级降到毫秒级，保障数据实时性。
- 并行复制不是主库并行写入，而是**加速从库重放并保障高可用性和数据同步时效**。

## 3.2 分库分表

**假设**：订单表 10 亿行，单表 5000 万行时性能明显下降。

**分表策略**：按 `user_id` 取模拆成 32 库 × 32 表 = 1024 分片。

| 指标 | 单表 | 分库分表（1024 分片） |
|------|------|------------------------|
| 单表行数 | 10 亿 | ~100 万 |
| 单次查询扫描 | 全表/大范围 | 单分片 |
| 理论 QPS | 受单库限制 | 接近线性扩展（受机器数限制） |
| 跨分片查询 | 无 | 需应用层聚合或中间件 |

**示例**：
原单库 2 万 QPS 上限，分 32 库后理论可达 32 × 2 万 = 64 万 QPS（实际受网络、应用层聚合等限制）。

## 3.3 读写分离 + 分库分表

**架构**：
- 写：主库（可按分片路由）
- 读：从库（可多从分担读压力）

**示例**：
- 写：1 主 32 分片，每分片 5000 TPS → 总 16 万 TPS
- 读：每分片 3 从，单从 5000 QPS → 总 32 × 3 × 5000 ≈ 48 万 QPS
