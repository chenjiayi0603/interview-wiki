## 一、项目概述

### 1.1 项目目标

在 **Docker（ubuntu:24.04, 12 vCPU）** 环境下，对 C++ 生态中主流的内存分配器、线程池、并行执行策略进行**基准测试（Benchmark）**，回答三个核心问题：

1. **换分配器到底能快多少？** — glibc vs jemalloc vs mimalloc vs tbb::scalable_allocator
2. **哪种线程池调度开销最低？** — TBB vs OpenMP vs std::async vs 手写池
3. **组合优化收益多大？** — 分配器 + 线程池 + 执行策略的全链路加速比

### 1.2 测试环境

| 项目 | 值 |
|------|-----|
| **容器** | Docker, ubuntu:24.04 |
| **编译器** | g++ 13.3.0, -O2 |
| **CPU** | 12 vCPU (Intel Xeon) |
| **glibc** | 2.39 (含 tcache) |
| **TBB** | 2021.11.0 |
| **jemalloc** | 从 apt 安装 (LD_PRELOAD 替换) |
| **mimalloc** | 从 apt 安装 (LD_PRELOAD 替换) |
| **测试时间** | 2026-06-14 |

### 1.3 测试类型

| 测试 | 数据量 | 测量指标 |
|------|--------|---------|
| 分配器顺序模式 | 10M 次 alloc/memset/free × 64B | 总耗时 (ms) |
| 分配器随机模式 | 5M 次，16~256B 随机，16 slot 延迟释放 | 总耗时 (ms) |
| 线程池 | 2M 次 sin 计算 | 总耗时 (ms) |
| 执行策略 | 20M 元素 sort / transform | seq vs par 加速比 |

| Work-Stealing | 12 任务，后半重 50x | 总耗时 (ms) |

## 二、关键技术发现

### 2.1 分配器：老印象 vs 新真相

| 印象 | 旧数据（参考） | 实测（Docker, glibc 2.39） |
|------|--------------|--------------------------|
| glibc 多线程极慢 | 8t = 480ms | 8t = 191ms（tcache 大幅改善） |
| mimalloc 多线程 11.4x | 8t = 42ms | 8t = 163ms（比 glibc 快 ~15%） |
| tbb::scalable 第一梯队 | 8t = 45ms | 8t = 320ms（最慢，抽象层开销高） |
| jemalloc 碎片最优 | 碎片率 3-8% | ✅ 仍成立（长期运行首选） |

**核心结论**：
- glibc 2.26+ tcache 已**彻底改变**了小对象多线程分配的格局
- **简单顺序模式**下 4 种分配器差异 < 20%，glibc 够用
- **随机大小 + 随机生命周期**下 mimalloc/jemalloc 优势显现（快 15-25%）
- **tbb::scalable_allocator** 仅在配合 TBB 任务系统时有集成优势

### 2.2 线程池：std::async 没那么差

| 线程池 | 实测 (2M sin) | 旧参考数据 |
|--------|:------------:|:----------:|
| TBB task_arena | **1.8 ms** | 105 ms |
| std::async | **2.0 ms** | 980 ms |
| OpenMP static | 11.5 ms | 120 ms |
| OpenMP dynamic | 55.2 ms | 135 ms |
| 手写池 (atomic fetch_add) | 55.4 ms | 150 ms |

**核心结论**：
- TBB 调度最轻量（work-stealing 分布式取任务）
- std::async 现代实现线程复用已大幅改善，**不再是最差选择**
- **手写 atomic fetch_add 池在细粒度任务下性能骤降**（cacheline 乒乓）
- OpenMP dynamic 调度开销大，适合负载不均的场景

### 2.3 执行策略

| 算法 | 数据量 | seq | par | 加速比 |
|------|:------:|:---:|:---:|:------:|
| sort（随机整数） | 2×10⁷ | 1095 ms | 134 ms | **8.1x** |
| transform（sin+cos+sqrt） | 2×10⁷ | 145 ms | 16 ms | **9.2x** |

**规律**：计算密集 → 加速比接近核心数；内存密集 → 并行无用（甚至更慢）

### 2.4 组合优化收益

| 链路 | 耗时 | 加速比 |
|------|:----:|:------:|
| glibc + seq（基线） | 87.1 ms | 1.0x |
| glibc + TBB | 11.0 ms | 7.9x |
| mimalloc + seq | 71.2 ms | 1.2x |
| **mimalloc + TBB** | **8.3 ms** | **10.5x** |

**结论**：分配器和线程池**相辅相成**，单独优化任一环节收益有限，同时优化才能最大化加速。

## 三、面试高频问答

### Q1：多线程下为什么要换分配器？

> **答**：glibc malloc（ptmalloc）使用 arena 锁管理多线程分配，早期版本（< 2.26）没有 tcache，高并发下锁竞争严重，8 线程分配吞吐可能比单线程还低。jemalloc 和 mimalloc 通过**每线程独立缓存**避免了锁竞争——分配/释放走本地快路径，无原子操作，跨线程归还时批量搬移。
>
> **但要注意**：glibc 2.26+ 引入了 tcache（per-thread cache），简单顺序分配模式下差异已大幅缩小。只有在**随机大小 + 随机生命周期 + 长期运行**的场景下，jemalloc/mimalloc 的优势才明显（碎片控制 + 15-25% 吞吐提升）。

### Q2：mimalloc、jemalloc、glibc 怎么选？

> **答**：看场景——
> - **通用服务快速上线**：mimalloc（LD_PRELOAD 一键替换，综合吞吐最高）
> - **7×24 数据库/Redis**：jemalloc（碎片率 3-8% 最稳，运行半年内存不涨）
> - **简单批处理/嵌入式**：glibc 够用（零依赖，tcache 下并行不差）
> - **与 TBB 配合**：tbb::scalable_allocator（集成优势，但单独测性能不如 mimalloc）
>
> 实战中常用 **mimalloc 全局 + 局部手写池兜底热点路径**。

### Q3：手写 ObjectPool 和 mimalloc 比谁快？

> **答**：ObjectPool 快 5-10 倍（~5-10 ns vs ~50 ns 每次分配），且**零碎片**。但 ObjectPool 只适用于**固定大小、固定类型**的狭窄场景，且需要侵入式修改代码。mimalloc 虽然慢一些，但**任意大小、任意模式**都适用，LD_PRELOAD 即可部署，维护成本低。
>
> 取舍：**手写池 = 快但窄，mimalloc = 够快且广**。实际项目常用 mimalloc 全局 + ObjectPool 兜底热点路径。

### Q4：TBB work-stealing 比手写线程池好在哪里？

> **答**：work-stealing 让空闲线程自动偷取繁忙线程队列尾部的任务，实现**天然负载均衡**。手写 FIFO 池所有线程从一个全局队列取任务，需要互斥锁保护，且如果任务粒度不均（某些任务重某些轻），重任务的线程会拖慢整体进度。
>
> 但 **work-stealing 有生效条件**：任务数必须 >> 核心数。实测 12 任务 = 12 核时加速比仅 0.98x（无竞争空间），1000+ 任务时优势才显现。另外，手写池如果用 tomic fetch_add 做任务分发，在细粒度任务下 cacheline 乒乓严重（实测比 TBB 慢 30x）。

### Q5：std::async 性能真的很差吗？

> **答**：**老印象是错的**。旧版 std::async 每次调用创建新线程或复用延迟不可控，被诟病为"最差选择"。但现代 glibc 实现（2.39）的线程池复用机制已大幅改进，实测 2M 次 sin 计算仅 2.0ms，接近 TBB 的 1.8ms。对于简单并行任务，std::async 已经够用。
>
> **仍要注意**：std::async 的尾延迟不可控（线程创建策略由实现决定），不适合延迟敏感场景。

### Q6：什么情况下并行反倒更慢？

> **答**：两种典型场景——
> 1. **操作太轻量**（如简单的加法）：线程调度开销 > 并行收益，实测 is_sorted 用 par 比 seq 慢 3x
> 2. **内存带宽饱和**（如 memcpy）：多线程争内存带宽反而降低单线程效率，实测 transform(加法) 慢 1.3x
>
> 经验法则：每个任务的 CPU 耗时 > 1 µs 时并行才有收益，数据量 > 10⁵ 时 par 才有优势。

### Q7：高频交易场景怎么管理内存？

> **答**：HFT 的核心原则是**盘中零分配**。所有内存在启动时预分配好：
> - **SPSC ring buffer**：无锁队列传递订单/行情，启动时分配所有 slot，盘中只移动指针
> - **Arena / Region 分配器**：只 bump pointer 不归还，日终整块重置
> - **ObjectPool**：固定大小对象池，分配 ~5-10 ns
> - **CPU 亲和 + spin-wait**：线程绑核，忙等不进入内核睡眠
>
> 简言之：**开盘前全部分完，盘中不调 malloc**。mimalloc 再快也只是让"本不该发生的分配"变快一点。

### Q8：你们测试过程中踩过什么坑？

> **答**：好几个——
> 1. **编译器优化掉空分配**：TBB benchmark 第一次跑出 0.5ms，后来发现 olatile int x = 0 被 g++ -O2 优化掉了空循环，换成 std::sin() 计算负载才得到真实数据
> 2. **Docker --cpus 误导**：--cpus=12 限制的是 CPU 时间配额而非并发度，真正限制核心数要用 --cpuset-cpus
> 3. **LD_PRELOAD 链接**：Ubuntu 24.04 上 scalable_malloc 符号在 libtbbmalloc 中，需额外链接 -ltbbmalloc
> 4. **小规模测试看不差异**：1M 次分配下 glibc vs mimalloc 几乎没区别，放大到 10M + 随机模式才显化差异
> 5. **work-stealing 需要规模**：12 任务 = 12 核时 steal 无效果，需要 1000+ 任务

### Q9：你们用什么工具做性能分析？

> **答**：这次测试主要用**计时 benchmark（std::chrono）** 做宏观对比。更细粒度的分析会用：
> - **perf stat**：看 cache miss、branch miss、IPC
> - **perf c2c**：检测 cacheline 竞争（HFT 场景）
> - **火焰图**：看热点函数和调度开销
> - **valgrind / heaptrack**：检测内存碎片和泄漏
>
> 面试被追问时可以说：这次的重点是**宏观选型对比**（哪个分配器/线程池更适合什么场景），微观调优会用 perf 进一步分析。
