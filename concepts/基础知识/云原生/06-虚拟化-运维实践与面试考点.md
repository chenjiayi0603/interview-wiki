### 1.3 数据库备份自动化

```bash
#!/bin/bash
# backup-cron.sh —— 配合 crontab 使用
# 0 2 * * * /opt/scripts/backup-cron.sh

BACKUP_DIR="/data/backups"
DATE=$(date +%Y%m%d)
KEEP_DAYS=30

# MySQL 备份
docker compose exec -T mysql mysqldump -u root -p"$MYSQL_ROOT_PASSWORD" --all-databases \
  | gzip > "$BACKUP_DIR/mysql_${DATE}.sql.gz"

# Redis 备份
docker compose exec -T redis redis-cli -a "$REDIS_PASSWORD" BGSAVE
docker cp $(docker compose ps -q redis):/data/dump.rdb "$BACKUP_DIR/redis_${DATE}.rdb"

# 上传到对象存储
ossutil cp "$BACKUP_DIR/mysql_${DATE}.sql.gz" oss://my-backup/mysql/
ossutil cp "$BACKUP_DIR/redis_${DATE}.rdb" oss://my-backup/redis/

# 清理过期备份
find "$BACKUP_DIR" -type f -mtime +$KEEP_DAYS -delete

echo "[$(date)] 备份完成" >> /var/log/backup.log
```

## 二、安全最佳实践

| 实践 | 说明 |
|-----|------|
| 不使用 root 用户 | Dockerfile 中用 `USER appuser` |
| 使用 Alpine/scratch 基础镜像 | 减少攻击面，体积更小 |
| 敏感信息用 Secrets / 环境变量 | 不硬编码到镜像中 |
| 定期更新基础镜像 | `docker pull` 获取安全补丁 |
| 限制容器资源 | 防止单个容器耗尽主机资源 |
| 使用 `.dockerignore` | 避免将 `.git`、`node_modules` 等打入镜像 |
| 镜像扫描 | 使用 `docker scout` 或 Trivy 扫描漏洞 |
| 使用只读文件系统 | `read_only: true` 防止容器内写文件系统 |

## 三、Docker Compose vs 纯 Shell 脚本

### 场景：部署 Nginx + API + Redis + MySQL

#### Shell 脚本方式（80+ 行）

```bash
#!/bin/bash
docker network create myapp-net 2>/dev/null || true

docker run -d --name myapp-mysql --network myapp-net \
  -e MYSQL_ROOT_PASSWORD=secret123 -e MYSQL_DATABASE=mydb \
  -v /data/mysql:/var/lib/mysql \
  --memory 1g --cpus 1.0 \
  mysql:8.0

until docker exec myapp-mysql mysqladmin ping -h localhost --silent; do sleep 2; done

docker run -d --name myapp-redis --network myapp-net \
  -v /data/redis:/data --memory 512m \
  redis:7-alpine redis-server --requirepass redispwd

docker run -d --name myapp-api --network myapp-net \
  -e DB_HOST=myapp-mysql -e REDIS_HOST=myapp-redis \
  -p 8080:8080 --memory 512m \
  myregistry/api:latest

docker run -d --name myapp-nginx --network myapp-net \
  -p 80:80 -p 443:443 -v /opt/nginx/conf.d:/etc/nginx/conf.d:ro \
  nginx:1.25-alpine
```

还需额外 stop.sh / restart.sh / update.sh / status.sh / logs.sh 脚本。

#### Docker Compose 方式（45 行 YAML）

```yaml
services:
  nginx:
    image: nginx:1.25-alpine
    ports: ["80:80", "443:443"]
    volumes: ["./nginx/conf.d:/etc/nginx/conf.d:ro"]
    depends_on: [api]
    restart: always

  api:
    image: ${REGISTRY}/api:${TAG:-latest}
    ports: ["8080:8080"]
    environment:
      DB_HOST: mysql
      REDIS_HOST: redis
    depends_on:
      mysql: { condition: service_healthy }
      redis: { condition: service_started }
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8080/health"]
      interval: 15s
    restart: always

  redis:
    image: redis:7-alpine
    command: redis-server --requirepass ${REDIS_PASSWORD} --maxmemory 256mb
    volumes: ["redis-data:/data"]
    restart: always

  mysql:
    image: mysql:8.0
    environment:
      MYSQL_ROOT_PASSWORD: ${DB_PASSWORD}
      MYSQL_DATABASE: mydb
    volumes: ["mysql-data:/var/lib/mysql"]
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost"]
      interval: 30s
    restart: always

volumes:
  redis-data:
  mysql-data:
```

#### 逐项对比

| 维度 | 纯 Shell 脚本 | Docker Compose |
|------|--------------|----------------|
| **代码量** | 80+ 行 + 额外脚本 | 1 个 YAML ≈ 45 行 |
| **启动顺序** | 手写 `sleep`/`until` 轮询 | `depends_on` + `condition: service_healthy` |
| **网络管理** | 手动 `docker network create` | 自动创建，服务名即主机名 |
| **服务发现** | 容器名硬编码 | 自动 DNS 解析 |
| **更新服务** | stop → rm → run | `docker compose up -d --no-deps api` |
| **回滚** | 记住旧版本和所有参数 | 改 TAG 后 `up -d` |
| **扩缩容** | 手动起多个容器管端口 | `--scale api=3` |
| **幂等性** | 二次执行报"容器名已存在" | 天然幂等，只更新变化 |
| **配置即文档** | 脚本可读性差 | YAML 声明式，结构清晰 |

#### 最佳分工

```
Shell 脚本（编排层）：  备份数据库、拉取代码、通知、回滚逻辑
Docker Compose（容器层）：定义和运行容器
```

```bash
#!/bin/bash
# deploy.sh —— Shell 调 Compose，各司其职
git pull origin main                     # Shell 擅长的
./scripts/backup-db.sh                   # Shell 擅长的
docker compose pull                      # 交给 Compose
docker compose up -d --no-deps --build api  # 交给 Compose
curl -X POST "$WEBHOOK" -d '{"text":"部署完成"}'  # Shell 擅长的
```

## 四、Docker vs 直接运行二进制

### 全维度对比

| 维度 | 直接运行二进制 | Docker |
|------|--------------|--------|
| **安装依赖** | 每个软件不同方式，经常冲突 | `docker pull` 自带依赖 |
| **环境一致性** | "在我机器上能跑" | 镜像即环境，100% 一致 |
| **多版本共存** | Node 16 和 20 共存？痛苦 | 不同容器跑不同版本 |
| **资源隔离** | 共享宿主机，OOM 拖垮整机 | cgroup 隔离 |
| **服务迁移** | 重新装一遍环境（一整天） | `docker compose up -d`（5 分钟） |
| **回滚** | 希望做了备份 | `docker run image:v1.0` 秒回 |
| **安全** | 入侵后可访问整个系统 | namespace 隔离 |

### Docker 的代价

| 代价 | 严重程度 | 说明 |
|------|---------|------|
| **性能损耗** | ⭐ 极低 | Linux 容器 < 2% |
| **磁盘占用** | ⭐⭐ 低 | Alpine 基础镜像仅 5MB |
| **学习成本** | ⭐⭐ 低 | 三个命令就能上手 |
| **调试复杂度** | ⭐⭐ 低 | `docker exec -it` 进入容器 |

### 什么时候不需要 Docker？

| 场景 | 原因 |
|------|------|
| 只有一个简单的静态网站 | Nginx 直接装即可 |
| 嵌入式/IoT 设备 | 资源极度受限 |
| 直接访问硬件（GPU 密集计算） | 增加复杂性 |
| 遗留系统，不值得改造 | 跑了十年没出过问题 |
| 内核开发/系统级开发 | 需要直接操作内核 |

## 五、面试高频问题

### Q1: K8s 和 Docker 的区别？

**A**：Docker 是容器运行时，单机管理；K8s 是容器编排平台，跨主机集群管理。Docker 是 K8s 的底层实现之一（CRI）。

### Q2: Pod 和 Container 的区别？

**A**：Pod 是 K8s 最小调度单元，可包含多个容器（sidecar 模式），共享网络/存储/UTS 命名空间。容器是实际运行的进程。

### Q3: Service 类型有哪些？

| 类型 | 访问范围 | 说明 |
|------|---------|------|
| **ClusterIP** | 集群内部 | 默认类型 |
| **NodePort** | 集群外（节点端口） | 测试用 |
| **LoadBalancer** | 公网 | 云厂商负载均衡 |
| **ExternalName** | CNAME 映射 | 外部服务别名 |
| **Headless** | 无头服务 | 自主选择 Pod |

### Q4: K8s 如何实现服务发现？

**A**：CoreDNS 解析 Service 名，或 kubelet 注入环境变量 `SERVICE_HOST`。推荐 DNS。

### Q5: Deployment 更新策略？

- **RollingUpdate**（默认）：逐步替换 Pod，`maxSurge`/`maxUnavailable` 控制速率
- **Recreate**：先删所有旧 Pod，再建新 Pod

### Q6: Istio Sidecar 注入原理？

**A**：自动注入通过 MutatingAdmissionWebhook，手动注入 `istioctl kube-inject`。注入后 init 容器设置 iptables 规则，流量全部经过 Sidecar。

### Q7: Envoy 如何做熔断？

```yaml
circuit_breakers:
  thresholds:
  - max_connections: 100
    max_pending_requests: 100
    max_requests: 100
    max_retries: 10
```

- 连接数熔断、请求数熔断
- 熔断后快速失败，避免级联故障

### Q8: gRPC vs HTTP/REST？

| 特性 | gRPC | HTTP/REST |
|------|------|-----------|
| 协议 | HTTP/2 | HTTP/1.1/2 |
| 序列化 | Protobuf（二进制） | JSON（文本） |
| 代码生成 | 自动 | OpenAPI |
| 流式 | 双向流 | 单向 |
| 性能 | 高 | 中 |

### Q9: 如何排查 Pod 问题？

1. `kubectl describe pod` 查看事件
2. `kubectl logs` 查看日志
3. `kubectl exec` 进入容器
4. `kubectl get events` 查看集群事件
5. `kubectl top` 查看资源使用

### Q10: HPA 工作原理？

**A**：HorizontalPodAutoscaler 基于 CPU/内存/自定义指标，周期性检查当前指标，计算目标副本数 `ceil(current * desired / current)`，更新 Deployment 副本数。

## 六、项目深挖问题

### Q1: 服务网格如何选型？

| 方案 | 特点 |
|------|------|
| **Istio** | 功能全，复杂 |
| **Linkerd** | 轻量，简单 |
| **Envoy** | 灵活，自主集成 |

考虑因素：学习成本、资源开销、功能需求、团队规模。

### Q2: 为什么用 Envoy Wasm 插件？

**A**：扩展能力强、动态加载、沙箱隔离、多语言实现（Rust/C++/Go）。

### Q3: 微服务如何做蓝绿部署/金丝雀？

- **蓝绿**：两套环境，切换流量
- **金丝雀**：逐步增加流量比例
- Istio VirtualService 支持权重路由
- 配合 Prometheus 监控

```
## 八、面试高频追问

### Q1: 自建 K8s vs 托管 K8s 怎么选？
| 对比 | 自建 K8s | 托管 K8s（ACK/EKS/AKS） |
|:----:|:--------:|:----------------------:|
| 运维成本 | 极高（master HA/etcd/升级） | 极低（云厂商托管 master） |
| 可控性 | 完全控制 | 部分受限 |
| 版本升级 | 手动 | 一键或自动 |
| 成本 | 低（只需 worker 节点） | 高（master 管理费） |
| **建议** | 除非有专业团队，否则选托管 |

### Q2: P99 延迟排错的排查思路？
1. 看监控（CPU/内存/网络/IO 指标异常）
2. 抓日志（应用层错误、慢查询）
3. 链路追踪（Jaeger/Zipkin 定位具体服务）
4. Profiling（perf/pprof 定位热点函数）
5. 对拍测试（隔离可疑模块做对比验证）

### Q3: CI/CD 流水线中集成安全扫描的层次？
1. **代码扫描**：SonarQube 静态分析
2. **依赖扫描**：Snyk / Trivy 检测漏洞库
3. **镜像扫描**：Trivy / Clair 扫描镜像层漏洞
4. **运行时安全**：Falco 检测异常行为 + 网络策略
5. **合规扫描**：kube-bench 检测 CIS 基准
```

**核心建议**：把精力放在业务上，等真正遇到瓶颈时再演进。
