## 1. KeyDB 存算分离 — 华为云

> 任职：2023.3–2025.3 ｜ 角色：架构主 R
> 一句话：基于 RocksDB 扩展自定义 FileSystem 抽象层，统一 SSD / 元数据 / OBS 三种后端，实现 KeyDB 热数据 SSD + 冷数据对象存储的存算分离架构。

### 1.1 速览卡

**性能**：QPS 10万+，热数据 P99 <1ms，冷数据 P99 ~20ms，存储成本降 70%+，可用性 99.99%（计算面），热缓存命中率 95%+

**提升点**：
- 自研 RocksDB FileSystem 抽象层，统一本地SSD / gRPC元数据 / OBS 三种后端
- 冷热分层存储成本从 ¥0.35 降至综合 ~¥0.17/GB·月

**瓶颈**：
- 冷数据读 OBS 延迟 5–20ms（vs 本地 <1ms），命中率低时 QPS 急跌
- Compaction 抖动期 WAF 10–30x，P99 可达 50–200ms
- 元数据服务单点：gRPC 不可用 → 整体不可用

**优化方向**：异步预读+预热提升命中率；Compaction 限速错峰；元数据服务 Raft 3节点 + 本地TTL缓存降级

### 1.2 核心性能指标表

| 指标 | 数值 | 业界对标 / 出处 |
|------|------|--------------|
| **QPS** | **10万+** | KeyDB 多线程单实例公开 benchmark 8-15 万；热数据路径压测，读写比 7:3 |
| **热数据 P50 / P99** | **<0.5ms / <1ms** | 本地 SSD 路径，Redis 官方 SLA P99 <1ms |
| **冷数据 P50 / P99** | **~10ms / ~20ms** | OBS 长连接 + 同 AZ；华为 OBS / AWS S3 公开 GET P99 在 10-30ms |
| **OBS 单次延迟（最优）** | **3–12ms** | 同 AZ + 长连接 + 小对象 + 低负载 |
| **OBS 单次延迟（含建连）** | **8–25ms** | 含 TCP/TLS 建连 + IAM 鉴权 + 元数据查找 |
| **热缓存命中率** | **95%+** | LRU 在业务热点局部性下的典型水平 |
| **存储成本降低** | **70%+**（实际 ~70–85%，OBS ¥0.099/GB·月 vs 内存 ~¥2/GB·月）|
| **可用性** | **计算面 99.99% (SLA)**，数据面 99.9%+ | 计算层独立 SLA，依赖 OBS 链拉低整体可用性；年停机计算面 <52min |
| **Compaction 期间 P99** | **50–200ms** | write stall 期间写入暂停；本地 SSD 仅 5-20ms |
| **OBS 单桶 PUT 配额** | **500–2,000/s** | 硬天花板，Compaction 高峰期触发 503 SlowDown 限流 |
| **数据规模** | PB 级 | 多租户累计，OBS 对象存储端 |
| **服务模式** | 每租户独立 KeyDB 实例 | 进程级隔离 |

### 1.3 架构与关键设计

```
KeyDB 实例
  └─ RocksDB 引擎（持久化层）
       └─ 自定义 FileSystem 抽象层（继承 rocksdb::FileSystem）
            ├─ 热数据：本地 SSD 缓存（P99 <1ms）
            ├─ 元数据：gRPC → 元数据存储服务（Etcd）
            └─ 冷数据：SDK → 华为 OBS 对象存储（P99 ~20ms）
```

**关键设计维度：**

| 调优维度 | 关键设计 | 防御点 |
|---------|---------|-------|
| **FileSystem 抽象层** | 继承 `rocksdb::FileSystem`，重写 `NewSequentialFile/NewRandomAccessFile/NewWritableFile`，按路径前缀分发到 SSD/Meta/OBS | RocksDB 原生设计就是为了换底层 IO，TiKV/Pika 都用过类似手法 |
| **LRU 冷热分层** | SST 文件级粒度，访问时间 + 频次综合打分；后台扫描线程异步迁移 | 与 Cassandra Tiered Storage、HBase HFile 分层同思路 |
| **元数据缓存 + 熔断** | gRPC 同步 + 本地 TTL 缓存 + 熔断降级；元数据高频但变化少 | 与 etcd watch + local cache 模式一致 |
| **多租户隔离** | 每租户独立 KeyDB 进程 + OBS bucket 路径前缀 + cgroup 限 IO/CPU | 物理隔离最简单可靠 |
| **异步迁移** | 后台线程批量迁移，不影响主路径 QPS | 与 RocksDB Compaction 异步合并同思路 |

### 1.4 冷热分层与成本分析

**成本降低 70%+ 的计算推演：**

| 存储类型 | 单价 | 说明 |
|---------|------|------|
| 华为云内存（Redis 类缓存折算） | ~¥2/GB·月 | 内存昂贵 |
| 华为 OBS 标准存储 | ¥0.099/GB·月 | OBS 单价极低 |
| OBS 访问费 | 内网调用，忽略不计 | 内网无流量费 |

**代入 1TB 全量数据，100GB 热内存：**

| 内存单价 P_mem | Cost_old (1TB) | Cost_new | 净节省率 |
|--------------|---------------|----------|---------|
| ¥0.5/GB·月 | ¥500/月 | ¥149/月 | **70%** |
| ¥1.0/GB·月 | ¥1,000/月 | ¥199/月 | **80%** |
| ¥2.0/GB·月 | ¥2,000/月 | ¥299/月 | **85%** |

> 热数据受内存容量限制（~100GB），不随数据总量等比增长 —— **数据量越大，节省比例越高。**

**LRU 冷热分层判断标准：**
- SST 文件级粒度，每个文件维护 `last_access_ts` 和 `access_count`
- 打分公式：`access_count / (now - last_access_ts + 1)` — 单位时间内的访问密度
- 分数低于下四分位数的标记为"冷"，触发异步迁移到 OBS
- 与标准 LRU 区别：批量打分 + 异步迁移，粒度是 SST 文件级而非 key 级

### 1.5 OBS 冷数据路径延迟详细拆解

| 延迟构成 | 内网典型值 | 备注 |
|----------|-----------|------|
| 网络 RTT（同 AZ） | 0.5~1ms | 跨 AZ 1~3ms |
| TCP/TLS 建连 | 2~6ms | 连接池复用可避免 |
| OBS 内部鉴权 & 路由 | 1~5ms | 网关层 IAM 校验 |
| 元数据查找 | 0.5~2ms | KV 引擎查对象位置 |
| 数据定位 + 磁盘 IO | 0.5~3ms | 取决于对象冷热 |
| **合计（长连接，同 AZ，小对象）** | **3~12ms** | 理想条件 |
| **合计（首包，含 TCP/TLS）** | **8~25ms** | 冷启动场景 |
| **高负载/大对象** | **20~100ms+** | 突发流量 |

### 1.6 RocksDB Compaction 瓶颈

**为什么 Compaction 在 OBS 上是致命问题：**

| 维度 | 本地 SSD | 远程 OBS | 劣化倍数 |
|------|---------|---------|---------|
| 写放大（WAF） | 10~30× | 同左 | — |
| 单次 IO 延迟 | 0.1~0.5ms | 5~30ms | **50~100×** |
| Compaction 期间 P99 抖动 | 5~20ms | **50~200ms+** | **10×** |
| OBS 单桶 PUT QPS 配额 | — | 500~2,000/s | 硬天花板 |

**Compaction write stall 的级联效应：**
> Compaction 产生的 SST 上传到 OBS 会消耗 PUT 配额。Compaction 高峰期 PUT QPS 打满 OBS 桶配额，触发 503 SlowDown → 上传失败重试 → 更严重的排队 → RocksDB 触发 write stall → 业务写入暂停。这是存算分离架构最核心的矛盾。

**缓解手段：**
- Compaction 限速（`rate_limiter`）+ 错峰调度（业务低峰期触发）
- 大 SST 文件减少 HTTP PUT 次数
- WAL 和 L0 留本地 SSD，只有深层 SST 落 OBS（混合冷热）
- Compaction 输出先写本地 SSD 再异步上传 OBS

### 1.7 调优故事集

**故事 1：Compaction write stall**
- ❌ 问题：Compaction 输出大量 SST PUT → 打满 OBS 单桶配额（500–2,000/s）→ 503 SlowDown → L0 堆积 → write slowdown → 业务写入暂停。
- 🔧 手段：① 限速错峰，Compaction 速率控在配额 70% 内，大 Compaction 放凌晨；② WAL+L0 留本地 SSD；③ 大 SST（256MB）减少 PUT 次数。
- 📊 效果：线上未出现 Compaction 导致的业务中断。
- ⚠️ 代价：Compaction 变慢，L0 堆积量增加。OBS 上 stall 风险是本地 10–50×，无法根除。

**故事 2：元数据服务单点**
- ❌ 问题：元数据服务挂掉 → 文件 open/list 失败 → 存储引擎不可用。
- 🔧 手段：① 本地 TTL 缓存，读路径绕开 gRPC；② 熔断器监控错误率，降级到本地缓存；③ 恢复后异步对账。
- 📊 效果：读路径不受元数据短暂故障影响。
- ⚠️ 代价：缓存不一致窗口期可能读到旧元数据。

**故事 3：冷数据 P99 抖动**
- ❌ 问题：热缓存命中率从 95% 掉到 80% → 冷请求翻 4 倍 → 冷数据 P99 ~20ms 拖垮整体 P99。
- 🔧 手段：① 频次×时间衰减打分 LRU，防一次性扫描 evict 热数据；② 热点 key 预热；③ 冷热分桶监控，命中率 <90% 告警。
- 📊 效果：命中率稳定 95%+，冷请求 <5%。
- ⚠️ 代价：预热消耗额外 OBS 读带宽（低峰可忽略）。

### 1.8 追问预案

**Q：FileSystem 抽象层具体怎么设计的？**
> RocksDB 自带 `rocksdb::Env` 和 `rocksdb::FileSystem` 两个抽象。继承 FileSystem，重写文件读写接口，按路径前缀分发——`/local/...` 走 SSD，`/meta/...` 走元数据 gRPC，`/obs/...` 走 OBS SDK 的 Range Read。

**Q：LRU 冷热分层判断标准？**
> SST 文件级粒度，每个文件维护最后访问时间和访问频次，后台扫描按 `(时间衰减系数 × 频次)` 打分。低于阈值的触发异步迁移。

**Q：元数据服务挂了怎么办？**
> 三层防御：① 本地 TTL 缓存默认命中（命中率 90%+）；② 熔断器开启后降级到本地缓存；③ 熔断恢复后异步对账。最坏情况写入暂不可达，读路径不受影响。

**Q：冷数据 OBS 读 20ms 对总 P99 影响？**
> 冷数据访问是低频路径，业务侧热数据命中率 95%+，冷请求量在总量 5% 以下。监控里冷热分桶统计，主 P99 只看热路径。

**Q：多租户怎么防止 noisy neighbor？**
> 进程级隔离（每租户独立 KeyDB 实例）+ OBS bucket 独立 + cgroup 限 CPU/IO + 网络 QoS。

**Q：99.99% 是 SLA 还是实测？**
> 对外 SLA 承诺计算面 99.99%（纯 KeyDB 计算节点层）。数据面因依赖 OBS（SLA 99.9%），整体可用性在 99.9%+。冷数据路径依赖 OBS 是架构上已知的 trade-off。

**Q：RocksDB 写放大怎么控制？**
> ① 动态 `rate_limiter` 限速，业务高峰放开、低谷收紧；② `max_bytes_for_level_base` 调大 L1 容量；③ 使用 `level_compaction_dynamic_level_bytes`；④ WAL 和 L0 留在本地 SSD，只有深层 SST 才落 OBS，避免 Compaction 输出直接打 OBS 带宽。

**Q：如果重新设计存算分离，会改什么？**
> 三处：① 元数据引入 etcd watch 机制（push 替代 pull）；② Compaction 离线到独立计算集群（Snowflake 模式）；③ 热缓存层用分布式缓存替代 RocksDB Block Cache。

### 1.9 讲解话术

**30 秒版：**
> "华为云 KeyDB 存算分离项目，我是架构主 R。核心是基于 RocksDB 扩展 FileSystem 抽象层，把热数据放本地 SSD（P99 <1ms），冷数据迁移到华为 OBS（P99 ~20ms），通过 LRU 冷热分层支撑 PB 级多租户数据。最终 QPS 10 万+，存储成本降 70%+，计算面可用性 99.99%。"

**2 分钟版：**
> 30 秒版 + 展开 4 个亮点：① FileSystem 抽象设计 ② LRU 分层策略 ③ 元数据熔断降级 ④ 多租户隔离。加成本推演和 Compaction 瓶颈说明。

## 2. Redis 可观测性 — 华为云

> 任职：2023.3–2025.3 ｜ 与 KeyDB 项目同期
> 一句话：在 Redis 命令处理路径插入异步统计钩子，实现万级实例的大 Key / 热 Key 实时检测。

### 2.1 速览卡

**性能**：万级实例，定位效率提升 50%（平均 2h → 1h），插件主线程开销 <1μs，布隆过滤器 100万Key 仅占 1.2MB

**提升点**：
- 离线 bigkeys 扫描（阻塞Redis）→ 实时插入式监控，告警直接带Key名
- 布隆过滤器 FPR 1% 过滤低频Key，减少无效计数器写入

**瓶颈**：
- 布隆过滤器 FPR 1% 产生误报，且不支持删除需周期重建
- 大Key DEL 同步删除阻塞主线程（大Hash/List 可达数秒）
- 三模式实例并存（主从/哨兵/集群），故障处理逻辑各异

**优化方向**：Cuckoo Filter 替代布隆支持删除；大Key 改 UNLINK 异步删除；告警按集群模式分类路由

### 2.2 核心性能指标表

| 指标 | 数值 | 业界对标 / 出处 |
|------|------|--------------|
| 实例规模 | **万级** | 主从 / 哨兵 / 集群三模式 |
| 主线程开销 | **<1μs** | Redis 命令本身耗时 1-10μs，<1μs ≈ 增加 1-10% |
| 布隆过滤器 FPR | **1%** | 通用配置（10 hash, 10 bits/key）|
| 100万 Key 内存 | **1.2MB** | 数学：100万 × 10 bits / 8 = 1.25MB |
| CPU 额外开销 | **<10%** | 分析模块整体 |
| 告警时间 | **2h → <1h** | 离线扫描 → 实时检测 |
| 定位效率提升 | **+50%** | 插件上线前后对比 |

### 2.3 大Key/热Key检测原理

**大Key检测：**
- 在 Redis 命令处理路径中插入统计钩子，记录每个 Key 的 value 大小
- 超过阈值（String > 10KB 或 集合 > 10000 元素）写入统计 Redis / 上报监控
- 异步统计，不阻塞主线程

**热Key检测：**
- 滑动窗口计数器，统计单位时间内 Key 的访问频次
- 超过阈值上报热Key告警，建议业务层做本地缓存或 Key 打散
- 布隆过滤器用于快速过滤低频 Key，减少计数器内存占用

**关键设计：**
- 主线程只做一次内存 enqueue（纳秒级），写入无锁 SPSC ring buffer
- 统计 worker 独立线程消费，主线程零阻塞
- 降采样：高 QPS 时 1/N 抽样

### 2.4 性能瓶颈与已知问题

**布隆过滤器误判：**
- FPR 1% 意味着低频 Key 有 1% 概率被误判为热Key
- 因为统计本身是采样聚合的，最终输出 top N 时低频 Key 自然被过滤掉，整体准确率不受 FPR 影响
- 不支持删除，周期性重建（滚动布隆过滤器 / Cuckoo Filter）

**大Key处理建议：**
- String 大Key：value 分片存储，上层组装
- Hash/List/Set 大Key：按 field 范围分桶，拆分为多个 Key
- 删除大Key用 `UNLINK`（异步删除）而非 `DEL`

**万级实例运维复杂度：**
- 主从/哨兵/集群三种模式并存，故障处理脚本需分类处理
- 集群模式下 slot 迁移期间的读写路由需特别处理（MOVED/ASK 重定向）

### 2.5 调优故事集

**故事 1：主线程零阻塞**
- ❌ 问题：`processCommand` 路径直接统计 → 每个命令多 5-10μs → 高 QPS 下 P99 恶化。
- 🔧 手段：主线程只做一次内存 enqueue（纳秒级），写入无锁 SPSC 队列，统计 worker 独立消费。
- 📊 效果：主线程额外开销 **<1μs**，P99 无影响。
- ⚠️ 代价：统计有秒级延迟（异步消费滞后），worker 卡住丢弃统计不影响主业务。

**故事 2：布隆过滤器降内存**
- ❌ 问题：热 Key 全量建计数器 → 万级实例 × 10万 Key → 内存爆炸。
- 🔧 手段：布隆过滤器前置过滤，FPR 1%，仅命中的分配计数器。100万 Key 仅占 1.2MB。
- 📊 效果：计数器数量从 100万 → ~1万（热 Key 实际占比 ~1%），内存节省 99%。
- ⚠️ 代价：1% 低频 Key 被误判为热 Key → 在 top N 聚合时自然被过滤。

### 2.6 追问预案

**Q：异步统计怎么避免阻塞主线程？**
> lock-free SPSC ring buffer 入队，主线程纳秒级 push。统计 worker 单独线程消费。即使 worker 卡住，主线程最多丢统计，不影响业务。

**Q：布隆过滤器假阳性怎么处理？**
> FPR 1%，但因为统计本身是采样聚合的，最终输出 top N 时低频 Key 自然被过滤掉。整体准确率不受 FPR 影响。

**Q：钩子怎么避免影响 Redis 内核行为？**
> 钩子只读不写，不持有锁，且 enqueue 失败时降级（丢弃统计而不是阻塞）。

**Q：大Key / 热Key 阈值怎么定？**
> 大Key：String > 10KB；List/Hash/ZSet > 10000 元素。热Key：单位时间访问频次排前 N。阈值业务侧可配。

### 2.7 讲解话术

**30 秒版：**
> "Redis 大 Key / 热 Key 实时统计插件。在命令处理路径插入异步统计钩子，主线程开销 <1μs；布隆过滤器过滤低频 Key，100 万 Key 只占 1.2MB 内存。从原来 redis-cli --bigkeys 离线扫描的 2 小时定位时间，优化到实时检测、1 小时内定位根因，效率提升 50%。支撑万级实例。"

### 3.3 Sidecar 延迟详细拆解

```
请求链路：
客户端 → Envoy(in) → 应用 → Envoy(out) → 下游服务

开销组成：
```

### 3.4 Wasm 自适应熔断插件

**熔断参数配置：**

| 参数 | 默认值 | 说明 |
|------|--------|------|
| 滑动窗口大小 | 10s | 统计窗口内错误率和延迟 |
| 错误率阈值 | 50% | 窗口内错误率 >50% 触发熔断 |
| P99 延迟阈值 | 1s | 超阈值也触发（独立条件） |
| 熔断持续时间 | 3s | 期间所有请求直接 503 |
| half-open 探针间隔 | 1s | 周期性放行少量请求 |
| half-open 成功次数 | 2 次 | 连续成功后关闭熔断 |

**最短恢复路径：** 熔断 3s → 第 1 次探针 (1s) → 第 2 次探针 (1s) → 恢复 = **<5s**

**自适应熔断算法：**
- 公式：`k × accepts < total - protection` 则概率性熔断
- k 默认 1.5（越小越敏感，范围 1.1-2），window 默认 10s
- protection 默认 5（请求数 ≤ protection 不触发熔断）
- 熔断概率 = `(((total - protection) - (k × accepts)) / (total + 1)) × 100`

**Wasm vs Native C++ Filter 深度对比：**

| 维度 | Wasm Filter | Native C++ Filter |
|------|-----------|-------------------|
| 热更新 | ✅ `istioctl apply` 即生效 | ❌ 需重新编译 Envoy + 重启 |
| 安全隔离 | ✅ 沙箱执行，崩溃不影响 Envoy | ❌ 同进程，bug 可导致 Envoy 挂掉 |
| 性能 | 慢 ~20%（沙箱 + 跨 VM 调用） | 原生性能 |
| 开发语言 | Go / Rust / AssemblyScript / C++ | 仅 C++ |
| 文件系统访问 | ❌ 不允许（沙箱限制） | ✅ 可访问 |
| 网络出站 | 仅通过 Envoy Host API | 可直接调用 |
| 共享数据 | SharedData API（跨 VM CAS） | 直接内存共享 |

> 选 Wasm 的核心逻辑：熔断逻辑本身很轻量，Wasm 的 20% 性能损失在绝对延迟上是纳秒级，不是瓶颈。但热更新和安全沙箱带来的运维收益是实打实的。

### 3.5 性能瓶颈

**1. 控制平面扩展性（istiod）：**
- istiod 需向所有 Sidecar 下发配置（xDS 协议），规模大时下发延迟增加
- 100 个服务时配置下发 <1s，1000 个服务时可能 >10s（配置爆炸问题）
- 应对：DiscoverySelector 限制 istiod 关注的命名空间

**2. 流量镜像和可观测性开销：**
- 开启 Tracing（Jaeger/Zipkin）有约 5% 的性能损耗
- 采样率调低（1–10%）可降低开销，但会丢失部分链路信息

**3. 延迟敏感服务不适合接入：**
- 原生 <10ms 的服务接入 Sidecar 后 P99 可能翻倍
- 极端延迟敏感服务考虑 eBPF 替代 Sidecar

### 3.6 追问预案

**Q：为什么选 Wasm 不用 Native C++ Filter？**
> 三个原因：① Wasm 支持热更新，改逻辑不重启 Envoy；② Wasm 沙箱执行，插件 bug 不影响 Envoy 主进程；③ Wasm 跨语言。代价是比原生慢 ~20%，但熔断逻辑本身轻量，不是瓶颈。

**Q：Sidecar 5ms 延迟怎么测的？**

**Q：QPS 5 万+ 这个量级 Istio 控制面能撑吗？**
> 撑得住。Pilot 配置推送是周期性 + 增量的，5 万 QPS 是数据面流量，跟控制面压力关系不大。

**Q：Istio 控制面和高频配置变更怎么处理？**
> Wasm 插件升级用 EnvoyFilter 的 `workloadSelector` 按 namespace 和 label 灰度匹配，先在 canary 环境验证 24 小时。配置 `fail_open`——如果 Wasm 加载失败，熔断逻辑降级为关闭，业务不受影响。

### 4.3 单机百万连接实现

**调优四层结构（面试按这个顺序讲）：**

#### 第一层：内核参数

| 调优点 | 调优前 → 调优后 | 原理 |
|-------|---------------|------|
| **TCP 收发 buffer** | `tcp_rmem/wmem` min 4KB → **1KB** | 默认 1M 连接吃 100GB 内存；IM 多为小包 |
| **文件描述符** | `ulimit -n` 1024 → **1048576+** | 同步改 `fs.file-max`、systemd `LimitNOFILE` |
| **accept 队列** | `net.core.somaxconn` → **65535** | 配合 `tcp_max_syn_backlog` |
| **TIME_WAIT** | `tcp_max_tw_buckets` 调大 | 长连接场景影响小，弱网重连关键 |
| **conntrack 表** | `nf_conntrack_max` 调大 | 易被忽略，百万连接下不调会丢包 |

#### conntrack 深挖（最容易讲赢的细节）

Linux 内核的连接追踪子系统（netfilter），记录每个 TCP/UDP 连接状态。`iptables` 的 stateful firewall 和 NAT 都依赖它。

| 项 | 默认值 | 百万连接需求 |
|----|--------|-------------|
| `nf_conntrack_max` | 65,536 / 262,144（视发行版）| **2,097,152+** |
| 每 entry 内存 | ~300 字节 | 100 万 ≈ 300MB |

表满时内核直接丢 SYN 包，`dmesg` 刷：`nf_conntrack: table full, dropping packet`。

**生产标准配置（/etc/sysctl.d/99-conntrack.conf）：**
```
net.netfilter.nf_conntrack_max=2097152
net.netfilter.nf_conntrack_buckets=524288
net.netfilter.nf_conntrack_tcp_timeout_established=600
net.netfilter.nf_conntrack_tcp_timeout_time_wait=30
```

**压测故事**：
> 压测到 50 万连接出现偶发 SYN drop，查 socket buffer 和 fd 都正常，最后 `dmesg` 看到 `nf_conntrack: table full`。调大 max 到 200 万、缩短 established 超时从 5 天到 10 分钟，后续压到 100 万，表使用率才 60%。

#### 第二层：网络模型

| 调优点 | 关键设计 |
|-------|---------|
| **epoll ET + 非阻塞** | while-EAGAIN 循环读，比 LT 减少 60%+ 系统调用 |
| **多进程 Worker + SO_REUSEPORT** | 内核负载均衡，避免 accept 锁竞争和惊群（参考 Nginx）|
| **零拷贝 / writev** | 多消息合并写，减少系统调用 |
| **心跳 30s + 滑窗判活** | 平衡功耗和断线感知 |

#### 第三层：业务架构（核心亮点）

| 调优点 | 调优前 → 调优后 | 说明 |
|-------|---------------|------|
| **群消息扇出聚合** | **3000 次 RPC → ~10 次** | 按 `accnodeidentify(ip:port:workIndex)` 聚合 |
| **在线状态查询** | **5-20ms → <1ms** | 一致性哈希路由 PushServer + LRU 缓存 + RocketMQ 主动失效 |
| **msgseq 高并发分配** | 纯 Redis INCR 瓶颈 → **99.99% <1ms 不碰 MongoDB** | Redis Lua + MongoDB 预分配批次（每 1 万 FINDANDMODIFY）|
| **未读数方案** | 避免 Redis INCR/DECR 一系列问题 | 已读点存 msgId + 登录/重连查 MongoDB countDocuments |
| **消息可靠性** | 推送失败丢失 → **指数退避 + 离线兜底** | ZSet score=μs 时间戳，1s/2s/4s，超时转 APNs/FCM |

### 4.4 群消息扇出核心架构

**职责分离设计**：MsgServer 只做校验+落库+获取成员列表，通过 MQ 把任务交给 PushServer。在线状态查询和扇出在 PushServer 完成。

**完整流程：**
```
发送方 App → Nginx(SSL) → Access网关 → MsgServer
  ├─ 生成 msgId（Snowflake）
  ├─ 异步写 MongoDB（msg_c2g，分片键=groupId）
  ├─ 查 Redis 群成员缓存
  └─ 发布到 MQ（按 groupId 分区保序）
        ↓
PushServer（按 groupId 一致性哈希路由）
  ├─ 查群成员在线状态
  │    命中本地 LRU → <1ms
  │    未命中 → Redis pipeline HMGET → 5–20ms
  ├─ 按 accnodeidentify 分组聚合（同网关合并）
  ├─ 向各 Access 网关批量下发 cmd=4503
  │    Access 网关本地遍历连接表推送
  └─ 推送失败 → 指数退避重试(1s/2s/4s) → 超时转 APNs/FCM
```

**性能数字拆解：**

| 维度 | 数据 | 说明 |
|------|------|------|
| 万人群在线成员 | 约 30%，即 3000 人 | 典型 DAU/注册比 |
| 单条消息大小 | ~1KB | 含协议头、消息体、签名 |
| 单条群消息出口带宽 | 3000 × 1KB = **3MB/条** | 按在线 3000 人算 |
| 万人全在线极端情况 | 1万 × 1KB = **10MB/条** | 带宽爆炸临界点 |
| 网关节点分组后 RPC 次数 | 网关节点数（如 10 个） | 从 1万次降为 10 次 |

**为什么在线状态查询必须在 PushServer 而不在 MsgServer？**

| 对比点 | 在 MsgServer 查 | 在 PushServer 查 |
|--------|-----------------|------------------|
| 职责清晰度 | MsgServer 耦合推送拓扑 | 关注点分离，各司其职 |
| LRU 缓存有效性 | 无法利用 PushServer 本地 LRU | 一致性哈希保证同群命中同实例 |
| 扩展性 | MsgServer 扩容影响推送逻辑 | 独立扩缩容 |
| 在线状态时效 | 查完到推送有时间差 | 紧邻推送，时效更准 |

### 4.5 msgseq 预分配机制

**核心设计：**
- 正常路径：Redis Lua 原子 INCR，<1ms，99.99% 消息走此路径
- 批次耗尽（每 10000 条）：MongoDB FINDANDMODIFY 预分配 5–20ms
- 冷启动（首条消息）：MongoDB INSERT 初始化 10–30ms

**seq 分配性能数字：**

| 路径 | 触发条件 | 延迟 | 频率 |
|------|----------|------|------|
| 正常分配（Redis INCR Lua） | 99.99% 的消息 | < 1ms | 每条消息 |
| 批次预分配（MongoDB FINDANDMODIFY） | 每 10000 条消息 1 次 | 5–20ms | 极低 |
| 冷启动（首条消息） | 会话第一条 | 10–30ms | 极低 |
| 并发竞争（SETNX 失败） | 多节点同时触发预分配 | 额外 1 次 Lua | 极低 |

**seq 断号问题与处理：**

| 场景 | 后果 | 处理 |
|------|------|------|
| 服务重启（预分配段未用完） | seq 浪费 0~10000 个，产生断号 | 客户端检测到 seq gap → 触发补拉请求 |
| 节点扩缩容 | MongoDB 换 nodeId 分配新段 | seq 整体单调，无影响 |
| 批量补拉 | seq gap 大时客户端补拉请求增加 | MongoDB 读压力瞬时增大 → 优化：活跃群动态加大批次到 50000 |

### 4.6 未读数方案：为什么放弃 Redis INCR

| 方案 | 写入路径 | 撤回处理 | 故障恢复 | 大群影响 |
|------|---------|---------|---------|---------|
| **Redis INCR** | 每发一条消息，N 个成员各 INCR 1次 → N 次写 | 需 DECR，异步流程可能 DECR 丢失 | Redis 故障重连 → 计数器清零 → 未读数全丢失 | 大群 1 条消息 → N 次 Redis 写扩散 |
| **已读点 + count**（本项目） | 仅在登录/重连时查 MongoDB 一次 `countDocuments` | 统计 SQL 自然排除 `msgState=4`（撤回） | Redis 故障不影响（已读点丢失最多重算一次） | 大群无写扩散，仅 1 次 MongoDB count |

**为什么不用 Redis INCR 的详细分析：**

| 场景 | 为什么 Redis INCR 失效 | 具体后果 |
|------|----------------------|---------|
| 撤回消息（msgState=4） | INCR 写入容易，DECR 靠异步写回，服务挂掉时漏 DECR | 未读数永久偏高，红点不消 |
| 删除自己（msgState=5） | 只影响自己视图，客户端本地扣减；离线期间本地计数丢失 | 重新登录后无法从 Redis 还原准确值 |
| seq 断号 | 用 `max_seq - read_seq` 估算未读，断号号段无真实消息 | 结果偏大，红点虚高 |
| Redis 故障/重启 | Codis 重启后 INCR 计数器清零 | 消息还在 MongoDB，计数归零，未读全丢 |
| 大群写扩散 | 1 条消息 → N 个成员各 INCR 一次 | 万人群每条消息触发万次 Redis 写 |

**MongoDB countDocuments 性能数据：**

| 索引条件 | 延迟 | 说明 |
|---------|------|------|
| 联合索引 `{sessionId, msgId}` + `fromId` / `msgState` 过滤 | 正常 <5ms | 有索引覆盖或索引扫描 |
| 长时间离线（未读数 >10万条） | 10~50ms | K 值大但仍在 O(log M+K) 内 |
| 极端（半年未登录，百万级未读） | >100ms | 需引入快照辅助 |

### 4.7 消息可靠性保障

**推送状态 ZSet 生命周期：**
1. 消息产生 → ZADD key score=μs 时间戳 member=msgId
2. 推送到客户端 → PushServer 启动本地定时器（3s 后触发）
3. 正常路径：客户端回 ACK → ZREM → 定时器取消
4. 异常路径：3s 内未 ACK → 指数退避重试（1s→2s→4s）→ 超时 30s 转 APNs/FCM

**重发机制底层实现（Libev 定时器）：**
- `ev_timer`（一次性）：每次推送后注册，timeout=3s，检查是否 ACK
- `ev_periodic`（周期性）：全局 ZSet 扫描，interval=30s
- ZSet Key TTL=1 天：Redis 自身事件循环兜底清理，不触发重发

### 4.8 调优故事集

**故事 1：TCP buffer 调优**
- ❌ 问题：默认 `tcp_rmem/wmem` min=4KB → 百万连接内核 buffer ~8GB + 内核元数据 ~4GB + 应用 ~2GB = 14GB+，16G 机器扛不住。
- 🔧 手段：min 调到 1KB，内核 buffer → ~2GB。配合 conntrack 调优。
- 📊 效果：单机百万连接 ~8GB，CPU 空闲 5-10%。
- ⚠️ 代价：大包（>1KB）拥塞窗口偶发收缩，IM 99% 小包，能接受。

**故事 2：conntrack 表满（详见 §4.3 conntrack 深挖）**

**故事 3：群消息扇出聚合**
- ❌ 问题：万人群在线 ~3000 人 → 每条消息 3000 次 RPC → PushServer CPU 打满。
- 🔧 手段：按 `accnodeidentify` 分组合并，同网关节点成员合并成 1 次 RPC，网关本地 fanout。
- 📊 效果：推送从成员数量级压到网关节点数量级。
- ⚠️ 代价：网关需本地解包分发，CPU 多 5-10%。网关是 IO 密集型，余量充足。

**故事 4：msgseq 预分配**
- ❌ 问题：每次发消息 MongoDB FINDANDMODIFY（5-20ms）→ 消息路径不可用。纯 Redis INCR 重启丢 seq。
- 🔧 手段：Redis Lua 原子 INCR（<0.1ms）做主路径；额度耗尽时 MongoDB 预分配 10000 条（5-20ms）。99.99% 消息走 Redis。
- 📊 效果：消息路径延迟 5-20ms → <1ms，seq 会话内严格递增。
- ⚠️ 代价：重启浪费未用完段（最多 10000 seq 断号），客户端补拉瞬时增加 MongoDB 读压力。

**故事 5：未读数方案**
- ❌ 问题：Redis INCR 三个致命缺陷——大群写扩散、撤回 DECR 丢失、Redis 故障清零。
- 🔧 手段：已读点存 Redis `read_msgid`，登录/重连时 MongoDB count，在线客户端本地维护。
- 📊 效果：零写扩散，撤回自然排除，Redis 故障不影响。count <5ms。
- ⚠️ 代价：长离线（>10万未读）count 10-50ms，登录稍慢。离线时长远低于此，可接受。

**故事 6：消息可靠性**
- ❌ 问题：推送失败直接丢弃 → 用户收不到；重试风暴 → 打垮推送服务。
- 🔧 手段：ZSet 记录推送状态（score=μs），指数退避重试（1s→2s→4s），超时 30s 转 APNs/FCM，SETNX 防重发。
- 📊 效果：到达率 >99.9%，重试不风暴。
- ⚠️ 代价：ZSet 定期清理已 ACK 记录，每条消息额外一次 ZADD（微秒级可忽略）。

### 4.9 追问预案

**Q：百万连接 8GB 内存怎么算出来的？拆一下？**
> 内核层 ~4-5GB（TCP socket 元数据 3-4KB × 100万 + conntrack entry 300B × 100万）+ TCP buffer 层 ~2GB（tcp_rmem/wmem min=1KB, 100万×2KB）+ 用户态 ~2-3GB（Connection 对象 1-2KB/连接 + epoll 事件数组）= 8-10GB。实际压测 16G 机器跑到 100 万连接时 free 还能剩 6-7GB。

**Q：epoll ET vs LT 怎么选的？**
> 用 ET（边缘触发）。长连接场景下如果用 LT，只要 socket buffer 有数据，每次 epoll_wait 都返回该 fd——100 万连接哪怕只有 1% 有数据，也要处理 1 万个重复事件 CPU 空转。ET 的坑：必须 while-EAGAIN 读完，非阻塞 fd 是强制要求，EPOLLOUT 用完立即摘掉防惊群。

**Q：群消息扇出从 3000 压到 ~10 的具体流程？**
> MsgServer 只做校验+落库 → MQ → PushServer 消费 → 按 accnodeidentify 分组聚合 → 同网关合并 1 次 RPC → 网关本地 fanout。代价是增加一级 MQ 延迟（+5-10ms），但 RPC 从成员数量级压到网关节点数量级，PushServer CPU 大幅下降。

**Q：为什么放弃 Redis INCR 做未读数？**
> 三个致命缺陷：① 大群写扩散（万人群一条消息 1 万次 Redis 写）；② 撤回需要 DECR，异步流程下 DECR 可能丢失；③ Redis 故障计数器清零。我们选的是已读点 + MongoDB count，看起来"重"（登录时要 count），但在线时才最轻的，离线才查一次。

**Q：conntrack 表满怎么发现的？**
> 压测到 50 万连接出现间歇性 SYN 丢包。排查：socket buffer 正常 → fd 正常 → listen 队列正常 → `dmesg` 看到 `nf_conntrack: table full` → `/proc/sys/net/netfilter/nf_conntrack_count` 打满默认 65536。调大 max 到 200 万、缩短 ESTABLISHED 超时到 10 分钟，再压 100 万连接时表使用率 60%。

**Q：消息撤回怎么实现？**
> 撤回是发一条特殊的控制消息（type=revoke + 引用 msgId），客户端收到后本地 mark 那条消息为已撤回。服务端不删原消息（保留审计），只在拉取时打 revoke 标志。这也是为啥 Redis INCR 未读数会有问题——撤回 DECR 容易出错。

**Q：seq 断号怎么处理？**
> seq 断号是设计上知道会发生的 trade-off。好处是 99.99% 正常消息不碰 MongoDB。客户端检测到 seq gap 会触发补拉请求，活跃群动态加大批次到 50000。服务重启前写回最大已分配 seq 减少浪费。

**Q：百万连接数字是单机实测还是集群聚合？**
> 单机实测。8 核 16G 单台压测打到 100 万长连接，~8GB 内存。集群层面是水平扩展，多台叠加。

### 4.10 讲解话术

**30 秒版：**
> "雷漫 IM 系统，我是后台架构负责人。自研基于 Libev 的 C++ 异步框架，单机 8 核 16G 撑百万连接（内存 ~8GB）、服务端处理 P99 <50ms。亮点是群消息扇出优化：万人群推送从 3000 次 RPC 压到 ~10 次（按网关节点聚合），在线状态查询从 5-20ms 优化到 <1ms（一致性哈希 + LRU 缓存 + RocketMQ 失效），msgseq 设计让 99.99% 消息 <1ms 不碰 MongoDB。"

### 5.3 5000 QPS 容量规划与正推分析

**硬件基线（2015-2019 典型配置）：** 4-5 台服务器，8C16G，SATA SSD，1Gbps

**部署拓扑：**
```
Server 1-2：网关 + IM 业务（C++ 异步 epoll）
Server 3：  MySQL 主库（写，SATA SSD）
Server 4：  MySQL 从库 + Redis
Server 5：  MongoDB + 智能客服
```

**正推第一步：MySQL 主库 fsync 是最终瓶颈**

| 要素 | 具体配置 | 说明 |
|------|---------|------|
| **CPU** | Intel Xeon E5-2620 v3，8核 2.4GHz | 2016 年主流配置 |
| **内存** | 32GB DDR4，buffer pool 20GB | 留 12GB 给 OS + 连接线程 |
| **磁盘** | Intel S3520 SATA SSD，1-3ms fsync，18000 IOPS | 企业级 SATA SSD |
| **MySQL 版本** | 5.7 InnoDB | group commit 成熟 |
| **`innodb_flush_log_at_trx_commit`** | `= 1` | 每次提交 fsync redo log |
| **`sync_binlog`** | `= 1` | 每次提交 fsync binlog |
| **半同步复制** | `rpl_semi_sync_master_enabled=1` | AFTER_SYNC 模式 |
| **实测上限** | 单主 **3000-5000 事务/s** | 半同步下吞吐不变 |
| **集群总吞吐** | **10000+ QPS**（1写2读） | 读写分离后总 QPS 轻松过万 |

**为什么是 3000-5000 事务/s？**
```
SATA SSD 瓶颈不在 IOPS（18000 IOPS 远大于 5000 事务/s），
瓶颈在 fsync 延迟：Intel S3520 单次 fsync ≈ 1-3ms。
InnoDB group commit 合并多事务 redo log + binlog → ≈ 3000-5000 tx/s。
换 NVMe（fsync 0.1ms）→ 天花板直接提到 10000-50000 tx/s。
```

**正推第二步：每消息消耗事务数 → 最大消息吞吐**
```
每条消息：INSERT 消息体(1事务) + UPDATE 会话 last_msgid(1事务) = 2 事务/消息
最大消息吞吐 = 3000÷2 = 1500 msg/s（保守）~ 5000÷2 = 2500 msg/s（乐观）
```

**正推第三步：消息占总 QPS 比例 → 最大总 QPS**
```
消息发送是唯一必然穿透 MySQL 主库的请求类型。
社交金融 IM 消息占比约 10-15%：
最大总 QPS = 1500÷0.15 = 10000 ~ 2500÷0.10 = 25000
取中值 ≈ 15000 QPS
```

**正推第四步：验证其他层不会先于 MySQL 触顶**

| 层 | 上限 | 15000 QPS 时负载 | 是否先于 MySQL 触顶 |
|----|------|----------------|------------------|
| C++ 异步服务（2实例） | ~10000-11000 QPS | 15000 | ⚠️ 可能先到顶 |
| MySQL 从库读 | 5000-10000 读/s | ~3600 读/s | ✅ 不会 |
| TCP 连接 | 140万（内存） | <10万 | ✅ 不会 |
| Redis | 10万+ QPS | ~11000 QPS | ✅ 不会 |
| 网络带宽 | 1Gbps(125MB/s) | ~45MB/s | ✅ 不会 |

**结论：**
```
正推最大 QPS ≈ 10000-12000（C++ 2 实例时，C++ 服务先到顶）
              ≈ 15000（C++ 3 实例时，瓶颈回到 MySQL fsync）
当前真实 5000 QPS → 5000÷10000 = 50%，在安全区内，还有约一倍余量，合理。
```

| 维度 | 关键设计 |
|------|---------|

| **并发模型** | 多进程 Worker，规避 GIL，每 Worker 独立事件循环 |

**Raft 选主关键参数：**
- 选举超时（election timeout）：太小容易频繁选举，太大故障恢复慢；通常 150–300ms
- 心跳间隔：选举超时的 1/10，约 15–30ms
- 日志复制延迟：写入需要 quorum（N/2+1）确认，三节点下需 2 个节点确认

**动态库插件的坑：**
- 问题：如果旧插件的函数还在执行，卸载会导致 SEGFAULT
- 应对：引用计数保护，旧 .so 只有所有请求处理完毕后才真正卸载（RCU 机制）

### 6.4 追问预案

**Q：跟 brpc / sofa-pbrpc 比有什么区别？**
> Thunder 不是为了取代成熟框架。主要目的是把 C++20 协程 + Raft + 插件化串起来深度实践，学习性质大于生产性质。生产环境建议用 brpc。

**Q：Raft 选举超时为啥 150-300ms？**
> Raft 论文推荐值，平衡选举延迟和心跳开销。太短触发不必要选举，太长故障恢复慢。etcd 默认 1000ms，TiKV 默认 100ms，我们取中间值。

**Q：协程怎么对接 Libev？**
> Libev 注册 fd 事件回调，回调里 resume 对应协程；协程内 IO 操作 yield 出来，等下次事件触发。本质是用协程替代回调函数——同步语义、异步执行。

**Q：Raft 日志压缩 / Snapshot 实现了吗？**
> MVP 版本没实现 Snapshot，定位是教学型。生产化需要补 InstallSnapshot RPC + 日志截断逻辑。没做的诚实承认比硬编安全。

### 6.5 讲解话术

**30 秒版：**

## 一、KeyDB 存算分离 — 性能数字全解

---

### `QPS 10万+`

**实际含义：**
读写混合场景下，整个 KeyDB 集群对外提供的总吞吐量。

**测量方式：**
- 工具：`redis-benchmark` 或内部压测工具
- 读写比约 7:3（缓存场景读多写少）
- 测试条件：热数据命中本地 SSD 缓存，绕过远程 OBS

**为什么是这个量级：**
- KeyDB 本身基于 Redis，单实例极限 QPS 约 10–20 万（取决于命令类型）
- 存算分离后热数据走本地缓存，性能与纯本地 KeyDB 接近
- 冷数据走 OBS，读延迟 5–20ms，QPS 会下降到千级以内

**被问到时要补充：**
> "这个 10 万+ 是热数据路径下的数字。冷数据读取因为要走远程 OBS，延迟会到 5–20ms，QPS 相应下降。所以关键是缓存命中率，我们通过 LRU 策略 + 预热保证热数据命中率在 95% 以上。"

---

### `存储成本降低 70%`

**实际含义：**
冷热分层后，把低频访问的 SST 文件从本地 SSD 迁移到 OBS 对象存储，单位存储成本大幅下降。

**架构对比（成本差异的根源）：**

| 架构 | 存储方式 | 说明 |
|------|---------|------|
| 老架构（存算不分离） | 全量数据在内存（RAM） | 所有数据常驻内存，内存贵 |
| 新架构（存算分离） | 热数据留内存 + 全量数据落 OBS | 冷数据从内存迁到磁盘，内存用量大幅缩减 |

> 核心节省来自：把冷数据从昂贵的内存迁移到廉价的 OBS，**不是 SSD vs OBS 的对比**。

**价格基线：**

| 存储类型 | 单价 |
|---------|------|
| 华为云内存（Redis 类缓存服务折算） | ~¥2/GB·月 |
| 华为 OBS 标准存储 | ¥0.099/GB·月 |
| OBS 访问费 | 内网调用，忽略不计 |

**计算公式（通用）：**

```
设：
  N     = 总数据量（GB）
  r_hot = 热数据比例（如 30%）
  P_mem = 内存单价（/GB·月）
  P_obs = OBS 存储单价（¥0.099/GB·月）
  注：内网访问 OBS，无下行流量费

老架构成本：
  Cost_old = N × P_mem

新架构成本：
  Cost_new = N × r_hot × P_mem   （热数据内存）
           + N × P_obs            （OBS 全量存储）

净节省率：
  saving = (Cost_old - Cost_new) / Cost_old
         = 1 - r_hot - P_obs / P_mem
```

**代入数值（全量数据 1TB，热数据（内存上限）100GB，冷数据 900GB）：**

```
设：
  N_total = 1,000 GB   （全量数据，落 OBS）
  N_hot   = 100  GB    （内存容量上限，留 RAM）
  N_cold  = 900  GB    （90% 冷数据，迁 OBS）
  热比例   = 100/1000 = 10%

老架构成本（全内存）：
  Cost_old = 1,000 × P_mem

新架构成本（内存 100GB + OBS 全量）：
  Cost_new = 100 × P_mem + 1,000 × 0.099
           = 100 × P_mem + 99

净节省率：
  saving = (1,000×P_mem - 100×P_mem - 99) / (1,000×P_mem)
         = 0.9 - 0.099/P_mem
```

**节省率随内存单价的变化：**

| 内存单价 P_mem | Cost_old(1TB) | Cost_new(1TB) | 净节省率 |
|--------------|--------------|--------------|---------|
| ¥0.5/GB·月   | ¥500/月       | ¥149/月       | **70%** |
| ¥1.0/GB·月   | ¥1,000/月     | ¥199/月       | **80%** |
| ¥2.0/GB·月   | ¥2,000/月     | ¥299/月       | **85%** |

> 热数据受内存容量限制（~100GB），不随数据总量等比增长，数据量越大节省比例越高。

**被问到时要补充：**
> "核心节省来自把冷数据从内存迁到 OBS 磁盘——内存昂贵、OBS 廉价，OBS 内网访问无流量费。热数据受内存容量限制约 100GB 留在内存，其余 900GB 冷数据落 OBS，热比例约 10%，综合算下来存储成本节省约 **70%**。"

---

### `可用性 99.99%`

**实际含义：**
全年停机时间 < 52 分钟（8760h × 0.01% = 0.876h ≈ 52min）。

**保障机制：**
- KeyDB 多副本（主从复制）
- 元数据服务 Raft 集群（3节点，容忍1节点故障）
- OBS 服务本身 SLA 99.99%
- 熔断降级：元数据服务异常时返回本地缓存，避免全量不可用

**被问到时要补充：**
> "99.99% 是华为云平台整体 SLA 目标，我们的代码层面主要保障是：WAL 本地保留、元数据 Raft 高可用、本地缓存 fallback。单点故障不会导致整体不可用。"

---

### `冷热分层延迟对比`

| 路径 | 延迟 |
|------|------|
| 热数据（本地 SSD） | P50 <0.5ms，P99 <1ms |
| 元数据查询（gRPC） | P50 ~1ms，P99 ~5ms |
| 冷数据（OBS） | P50 ~10ms，P99 ~20ms+ |
| Compaction 抖动期间 | P99 可达 50–100ms |

## 二、Redis 可观测性 — 性能数字全解

---

### `问题定位效率提升 50%`

**实际含义：**
大Key/热Key 插件上线前后，从告警触发到定位根因的平均耗时对比。

**测量方式：**
- 上线前：靠 `redis-cli --bigkeys` 离线扫描，耗时长且不实时，平均定位时间约 2 小时
- 上线后：监控系统实时展示 Top N 大Key/热Key，告警 → 定位 < 1 小时，效率提升约 50%

**被问到时要补充：**
> "之前发现大Key问题要人工跑 bigkeys 命令，串行扫描整个实例会阻塞 Redis，通常是出了问题才去扫。上线插件后是实时监控，告警直接带 Key 名，不需要再扫描，定位时间从平均 2 小时降到 1 小时以内。"

---

### `万级实例`

**实际含义：**
华为云 Redis 云服务托管的 Redis 实例总数，包含主从、哨兵、集群三种模式。

**运维复杂度拆解：**
- 万级实例下每秒心跳包约 1–2 万次，注册中心需专门优化
- 故障率即使只有 0.01%/天，每天也有约 1–2 个实例需要人工介入
- 插件的统计数据上报量：1万实例 × 平均 10 万 Key × 采样率 0.01% = 每秒约 100 个统计上报，可控

**被问到时要补充：**
> "万级实例不是我一个人管，是平台层面的规模。我的工作是在每个实例内部嵌入统计插件，上报到集中监控。单实例的插件开销极小（异步上报，<1μs/次），对业务无感知。"

---

### `布隆过滤器误判率 1%`

**参数推导：**
- 布隆过滤器 FPR 公式：`p = (1 - e^(-kn/m))^k`
- 其中 k = 哈希函数个数，n = 元素数，m = 位数组大小
- 1% FPR 时，最优 k ≈ 7，m/n ≈ 9.6 bits/元素
- 100 万 Key 的布隆过滤器约占内存 1.2MB，代价极低

**被问到时要补充：**
> "1% FPR 是默认配置，意味着 100 个低频 Key 里有 1 个会被误判为热Key产生误报。对于告警场景可以接受，业务运维收到告警后会二次确认。如果误报率影响使用，可以调整 m/n 到 14 把 FPR 降到 0.1%，内存增加 50%。"

## 三、服务网格 — 性能数字全解

---

### `QPS 5万+`

**实际含义：**
所有业务服务通过 Istio Sidecar 代理的总流量，不是单个服务的 QPS。

**测量方式：**
- Prometheus 采集 Envoy 的 `envoy_cluster_upstream_rq_total` 指标
- 10+ 个业务服务的 QPS 之和，单个服务约 1000–10000 QPS

**被问到时要补充：**
> "5万是平台总流量，每个服务的流量差异很大。压测时我们重点测的是 Sidecar 引入的额外延迟，结论是 P50 额外增加 5ms，P99 额外增加 15ms，业务方都在可接受范围内。"

---

### `Sidecar 引入延迟 5–15ms`

**延迟来源拆解：**

```
请求路径额外开销：
  客户端 Sidecar 出站处理：~1–3ms
    ├─ iptables 流量劫持（本机 loopback）：~0.1ms
    ├─ Envoy 路由匹配 + 负载均衡：~0.5ms
    └─ Wasm 插件处理：~1–2ms
  服务端 Sidecar 入站处理：~1–3ms（同上）
  合计：~2–6ms（无 Wasm），~5–15ms（含 Wasm）
```

**被问到时要补充：**
> "5–15ms 主要来自两次 iptables 劫持和两次 Envoy 处理。没有 Wasm 插件时约 2–6ms，加了自适应熔断 Wasm 后到 5–15ms。对于 P50 延迟 50ms 以上的服务影响不大，对延迟敏感的服务（<10ms）不建议接入服务网格。"

---

### `故障恢复时间 <5s`

**实现原理：**
```
熔断触发 → 熔断期（拒绝所有请求）→ half-open 探针（每2s发一次）→ 连续2次成功 → 恢复
最短恢复路径：2s + 2s = 4s < 5s
```

**参数配置：**
- 错误率阈值：50%（10秒窗口内）
- 熔断持续时间：3s
- half-open 探针间隔：1s
- 连续成功次数：2次方可恢复

**被问到时要补充：**
> "<5s 是在熔断持续时间 3s + 探针验证 2 次（各 1s）的配置下得到的。可以根据业务容忍度调整，延迟敏感业务可以配置更短的熔断窗口和更快的探针频率。"

---

## 四、分布式 IM — 性能数字全解

---

### `单机百万连接`

**内存完整推算：**

```
每个 TCP 连接内存开销：
  内核态：
    tcp_rmem 最小值（调优后）：1KB
    tcp_wmem 最小值（调优后）：1KB
    socket 元数据结构：~1KB
    合计内核态：~3KB/连接
  用户态（应用层连接对象）：
    连接状态、UID、心跳时间戳等：~1–2KB/连接

百万连接总内存：
  内核态：3KB × 100万 = 3GB
  用户态：2KB × 100万 = 2GB
  合计：~5GB（调优后）
  默认配置（不调优）：~10GB+
```

**系统参数调优清单：**

| 参数 | 默认值 | 调优值 | 作用 |
|------|--------|--------|------|
| `ulimit -n` | 1024 | 1048576 | 文件描述符上限 |
| `fs.file-max` | 100000 | 1048576 | 系统级 fd 上限 |
| `net.ipv4.tcp_rmem` min | 4KB | 1KB | 接收缓冲最小值 |
| `net.ipv4.tcp_wmem` min | 4KB | 1KB | 发送缓冲最小值 |
| `net.core.somaxconn` | 128 | 65535 | accept 队列长度 |

**被问到时要补充：**
> "百万连接的核心挑战不是 epoll 的性能，而是内存。默认配置下每个连接约 10KB，百万连接就是 10GB。调优后 socket buffer 最小值从 4KB 降到 1KB，实际压测约 5GB 内存可以承载百万连接。压测用多台客户端机器，每台机器绑多个 IP 避免端口耗尽。"

---

### `消息延迟 <50ms（P99）`

**端到端链路拆解：**

```
发送端设备
  ↓ 移动网络/Wi-Fi（不可控，通常 10–50ms）
网关层（<1ms，本地处理）
  ↓ 内网（<0.5ms）
消息服务（<3ms，路由 + 权限校验）
  ↓ 内网（<0.5ms）
MongoDB 写入（<5ms，WriteConcern=1，Primary 写）
  ↓ 异步推送（不等待存储完成）
推送服务 → 接收端网关（<2ms）
  ↓ 长连接推送（<1ms）
接收端设备
```

**为什么能做到 P99 <50ms：**
- 关键优化：**先推送再落库**（异步写存储），推送路径不等 MongoDB 返回
- 代价：极端情况（MongoDB 写入失败）消息丢失，靠补偿机制（ACK + 重试）补救
- 测量环境：同机房内网测试，不含移动网络延迟

**被问到时要补充：**
> "这个 50ms 是服务端端到端的数字，测试环境在同机房内网。移动端用户实际体验会加上无线网络延迟，通常 50–200ms。服务端能控制的是尽量压缩，所以我们做了先推送再落库的优化，把存储 IO 从关键路径上摘除。"

---

### `可用性 99.99%`

**故障时间分配：**
- 年允许停机 52 分钟
- 单次发布滚动更新：约 30s（多实例轮换）
- 全年发布约 50 次：50 × 30s = 25 分钟
- 剩余故障预算：27 分钟/年，约每次故障 < 5 分钟

**保障手段：**
- Nacos 健康检查：实例故障 5–10s 内摘除
- 消息补偿：发送失败自动重试 3 次，间隔指数退避
- 多机房部署：跨机房流量切换（切换期间有短暂不可用）

## 五、社交 IM（你我金融）— 性能数字全解

---

### `线上 5000 QPS`

**容量分析：**

```
5000 QPS 对应的资源消耗：
  C++ 异步服务（单实例 2000 QPS）→ 需要 3 实例 + LB
  Redis：5000 QPS 对 Redis 毫无压力（Redis 上限 10万+）
  MySQL：5000 QPS 中写操作约 1000–2000/s，需要读写分离
  MongoDB（地理查询）：地理查询约 500 QPS，延迟 10–50ms，是真正瓶颈
```

**被问到时要补充：**
> "5000 QPS 对 C++ 服务来说是轻载，整体架构有足够余量。实际运行时 CPU 使用率约 20–30%。瓶颈在地理查询，附近的人功能并发量高时 MongoDB 2dsphere 查询会成为热点，我们加了查询结果缓存（TTL 30s）来降低 MongoDB 压力。"

### `注册用户 1000万+，实际线上 5000 QPS`

**活跃度换算：**
- 假设 DAU = 注册量的 5%（金融类 App 典型值）= 45万 DAU
- 高峰期 2 小时集中在 45 万用户活跃
- 每个用户高峰期平均 0.08 次请求/s → 45万 × 0.08 = 3.6万 QPS（理论上限）
- 实际 IM 消息频率远低于普通 App，5000 QPS 合理

## 六、Thunder 框架 — 性能数字全解

---

### Raft 关键时间参数

| 参数 | 配置值 | 含义 |
|------|--------|------|
| Election timeout | 150–300ms | 随机，避免同时选举 |
| Heartbeat interval | 15–30ms | Leader 定期发心跳 |
| 日志复制延迟 | <10ms | 3节点内网 |
| Leader 切换时间 | <500ms | Election timeout 上限 |
| 写入确认延迟 | <20ms | quorum 确认（2/3节点） |

**被问到时要补充：**
> "Election timeout 设 150–300ms 随机是为了避免所有节点同时超时触发选举导致选票分裂。心跳间隔是 timeout 的 1/10，确保 Leader 活着时能及时续命。三节点集群写入需要 2 节点确认，内网 RTT < 1ms，所以写入延迟主要是处理时间，约 10–20ms。"

---

### 多进程 Worker 内存隔离

```
Master 进程（管理 Worker 生命周期）
  ├─ Worker 1（独立地址空间，独立 epoll）
  ├─ Worker 2（独立地址空间，独立 epoll）
  └─ Worker N（独立地址空间，独立 epoll）

Worker 间通信：Unix Domain Socket（共享内存可选）
崩溃隔离：Worker 挂掉，Master 重新 fork，其他 Worker 不受影响
```

**性能数据：**
- 进程间通信（Unix Socket）吞吐量：约 1–5GB/s，延迟约 0.01ms
- 相比线程共享内存（>10GB/s），有约 5–10% 的通信开销
- 对于网络 I/O 密集型服务，这点开销可以忽略

## 汇总：面试中所有数字的"标准答法"

| 数字 | 一句话解释 | 追问时补充的关键点 |
|------|-----------|-----------------|
| **QPS 10万+** | KeyDB 热数据路径压测值，读写比 7:3 | 冷数据路径 QPS 下降到千级，命中率是关键 |
| **成本降低 70%** | 内存 vs OBS 差价扣除附加成本后的净节省 | 热数据受内存容量限制，冷数据落廉价 OBS |
| **效率提升 50%** | 告警→定位耗时从 2h 降到 1h 以内 | 从离线扫描改为实时监控，不是靠优化算法 |
| **QPS 5万+** | 服务网格平台 10+ 服务的总流量 | 单服务约 1000–10000，Sidecar 加 5–15ms |
| **恢复时间 <5s** | 熔断 3s + 探针 2 次（各 1s）= 4s | 参数可配置，取决于业务容忍度 |
| **单机百万连接** | 调优后约 5GB 内存，epoll 非瓶颈 | 关键是 fd 上限 + socket buffer 调小 |
| **延迟 <50ms P99** | 先推送再落库，摘除存储 IO 出关键路径 | 仅服务端内网，移动端要加网络延迟 |
| **可用性 99.99%** | 年停机 <52 分钟，滚动发布 + 快速故障摘除 | 不含计划维护窗口（部分 SLA 定义不同） |
| **5000 QPS** | 社交 IM 峰值，对 C++ 服务轻载 | 真正瓶颈是 MongoDB 地理查询 |
| **1000万+注册用户** | 历史累计，DAU 约 10-15%（金融类典型） | 与 5000 QPS 对应，用户活跃度偏低属正常 |
