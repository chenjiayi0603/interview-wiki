## 一、GMP 模型

```
G (Goroutine): 栈 2KB 起步，动态伸缩
M (Machine):   OS 线程，默认 GOMAXPROCS 核数
P (Processor): 本地调度器，持有 G 队列

调度:
  1. P 从本地队列取 G 运行
  2. 本地空 → 偷取其他 P（Work Stealing）
  3. G 阻塞（syscall）→ M 与 P 解绑 → 新 M 接管

对比 C++ 线程:
  ├── Go: 隐式调度，不关心线程数
  └── C++: 显式控制，性能可控
```

### GMP 高频追问

```
Q: GMP 最大数量限制？
   G: 无硬限制（受内存制约，~1e4 量级稳定）
   M: 最大 10000（runtime 硬限制），默认休眠复用
   P: 默认 = GOMAXPROCS（通常 = CPU 核数）

Q: G0 和 M0 是什么？
   ├── M0: 程序启动时的第一个 OS 线程（主线程）
   └── G0: 每个 M 绑定的特殊 G，负责调度、GC 等系统任务

Q: 全局 G 队列的作用？
   ├── P 本地队列满（256）→ G 放入全局队列
   └── P 长时间未从全局队列取 G → 批量取一批

Q: 自旋线程是什么？
   ├── M 找不到 G 时进入自旋（spinning）状态
   └── 避免频繁线程切换，但占用 CPU
```

### 实例: GOMAXPROCS 与并行控制

```go
// 查看/修改 GOMAXPROCS
fmt.Println(runtime.GOMAXPROCS(0))     // 当前 CPU 核数
runtime.GOMAXPROCS(1)                  // 限制为单核（所有 G 串行）
runtime.GOMAXPROCS(runtime.NumCPU())   // 全核

// runtime.Gosched(): 主动让出 P
func worker(id int) {
    for i := 0; i < 5; i++ {
        runtime.Gosched() // 让出 P，给其他 goroutine 机会
        fmt.Printf("worker %d: %d\n", id, i)
    }
}
// 面试问: 不加 Gosched() 会怎样？
// 答: 单核下，一个 for 循环可能独占 P 导致其他 G 饥饿
//     Go 1.14+ 引入了基于信号的异步抢占解决此问题

// NumGoroutine: 监控 goroutine 数量
go func() {
    for {
        fmt.Println("goroutines:", runtime.NumGoroutine())
        time.Sleep(time.Second)
    }
}()
```

## 二、Channel 和 Goroutine 通信

```
有缓冲 channel: 异步，缓冲区满则阻塞
无缓冲 channel: 同步，必须配对收发

select: 多路复用监听多个 channel
  select {
  case <-ch1: ...
  case <-ch2: ...
  default: ...  // 非阻塞
  }
```

### 实例: channel 通信模式

```go
// 1. 无缓冲 channel（同步握手）
ch := make(chan int)
go func() {
    ch <- 42  // 阻塞直到主 goroutine 接收
}()
val := <-ch  // 阻塞直到 goroutine 发送
fmt.Println(val) // 42

// 2. 有缓冲 channel（异步队列）
ch := make(chan int, 3)
ch <- 1  // 不阻塞
ch <- 2  // 不阻塞
ch <- 3  // 不阻塞
// ch <- 4  // 阻塞！缓冲区满
close(ch)
for v := range ch {
    fmt.Println(v) // 1 2 3（通道关闭后 range 自动退出）
}

// 3. 通知退出（done channel 模式）
done := make(chan struct{})
go func() {
    // do work
    close(done) // 广播通知
}()
<-done // 等待完成

// 4. 生产者-消费者（并发安全队列）
jobs := make(chan int, 100)
done := make(chan bool)

// 消费者
go func() {
    for j := range jobs {
        fmt.Println("consume:", j)
    }
    done <- true
}()

// 生产者
for i := 0; i < 10; i++ {
    jobs <- i
}
close(jobs) // 关闭通知消费者退出
<-done      // 等待消费完成
```

### Channel 深度考点

```
Q: 关闭 channel 后还能读写吗？
   ├── 读: 可读，读到零值 + false（已关闭标志）
   └── 写: panic（closed channel）

Q: nil channel 读写会怎样？
   ├── 读 nil channel: 永久阻塞
   ├── 写 nil channel: 永久阻塞
   └── close(nil): panic

Q: Channel 底层数据结构？
   ├── hchan 结构体: buf、sendx/recvx 环形队列、sendq/recvq 等待队列
   ├── 无缓冲: 直接唤醒另一个 goroutine 进行数据拷贝
   └── 有缓冲: 先写入环形缓冲区，唤醒等待的接收者

Q: 如何优雅关闭 channel？
   ├── 只在发送端关闭（接收端关闭 → panic）
   └── 多个发送者 → 用 done channel + sync.Once 控制

Q: select 底层实现？
   ├── 随机化 case 顺序（避免饥饿）
   ├── 注册所有 channel 到 poll 数组
   ├── 如果无 case 就绪 → 挂起当前 G
   └── 有 case 就绪 → 执行对应逻辑
```

### 实例: select 多路复用

```go
// 1. 超时控制
ch := make(chan int)
select {
case v := <-ch:
    fmt.Println(v)
case <-time.After(time.Second):
    fmt.Println("timeout")
}

// 2. 非阻塞尝试收发
ch := make(chan int, 1)
ch <- 1
select {
case v := <-ch:
    fmt.Println("got:", v)
default:
    fmt.Println("not ready")
}

// 3. 合并多个 channel（fan-in）
func merge(cs ...<-chan int) <-chan int {
    out := make(chan int)
    var wg sync.WaitGroup
    for _, c := range cs {
        wg.Add(1)
        go func(c <-chan int) {
            for v := range c {
                out <- v
            }
            wg.Done()
        }(c)
    }
    go func() { wg.Wait(); close(out) }()
    return out
}

// 4. nil channel 禁用 case
var ch chan int
select {
case <-ch: // nil channel 永远选不到
default:
    fmt.Println("nil channel blocked")
}
```

## 三、interface 和 断言

```
interface{} 底层: (type, value) 二元组
类型断言: value.(Type) / value.(type) 在 switch 中
```

### interface 高频坑

```
Q: nil interface 和 nil pointer 的区别？
   ├── var a interface{} = nil           → (type=nil, value=nil)  → a == nil true
   ├── var p *int = nil; var a interface{} = p  → (type=*int, value=nil) → a == nil false ❌
   └── 常见坑: error 返回 nil 指针，外层检查 err != nil 永远为 true

Q: 底层结构？
   ├── eface (empty interface):   _type + unsafe.Pointer
   └── iface (非空 interface):   tab(itab) + data
       └── itab 缓存: 全局哈希表，按 (interface type, concrete type) 做 key
```

### 实例: interface 断言与坑

```go
// 1. 类型断言 switch
var v interface{} = "hello"
switch val := v.(type) {
case string:
    fmt.Println("string:", val)
case int:
    fmt.Println("int:", val)
default:
    fmt.Println("unknown")
}

// 2. 安全断言（comma-ok）
s, ok := v.(string)
if ok {
    fmt.Println("is string:", s)
}

// 3. nil interface 经典坑
type MyError struct{ Msg string }
func (e *MyError) Error() string { return e.Msg }

var err error = nil
fmt.Println(err == nil) // true

var p *MyError = nil
err = p
fmt.Println(err == nil) // false ← 坑！interface type 不为 nil

// 修复: 返回 error 时显式 return nil
func getError(flag bool) error {
    if flag { return &MyError{Msg: "bad"} }
    return nil
}

// 4. 接口值比较
type Animal interface{ Speak() string }
type Dog struct{}
func (d *Dog) Speak() string { return "woof" }
var a1, a2 Animal = &Dog{}, &Dog{}
fmt.Println(a1 == a2) // false（指针不同）
```

## 四、垃圾回收

```
并发三色标记+清扫
STW 时间 < 500μs（Go 1.19+）
```

### GC 进阶

```
Q: 三色标记流程？
   1. GC 开始时: 所有对象白色
   2. 根对象（全局、栈）→ 灰色
   3. 遍历灰色 → 引用的白色变灰色 → 当前变黑色
   4. 结束时: 黑色存活，白色回收

Q: 写屏障 (Write Barrier)？     ← 必考
   ├── 混合写屏障（Go 1.8+）
   ├── 插入屏障: 对象 A 引用 B，B 被标记为灰色
   ├── 删除屏障: 对象 A 不再引用 B，B 仍被视为存活
   └── 目的: 在并发标记时保证三色不变性

Q: 辅助标记 (Mark Assist)？
   ├── G 分配内存太快 → 协助 GC 标记
   └── GC 压力大 → 分配变慢 → 反馈调节

Q: GC 触发时机？
   ├── 主动: runtime.GC()
   ├── 阈值: 堆大小到达上次 GC 后的目标值（GOGC=100 翻倍）
   └── 定时: 2 分钟未触发则强制触发
```

## 五、内存管理

```
⛓ 内存分配器: tcmalloc 变体

分级分配 (Size Classes):
  ├── Tiny (<16B): 微对象分配器，mcache 直接分配
  ├── Small (16B~32KB): 对应 size class，从 mspan 分配
  └── Large (>32KB): 直接 mheap 分配

四层结构:
  mcache → mcentral → mheap → OS (mmap)

  ├── mcache:  每个 P 独享，无锁分配（≈25 个 size class）
  ├── mcentral: 全局，按 size class 管理，需加锁
  ├── mheap:    管理所有 mspan，大页分配
  └── OS:       通过 mmap 向系统申请

内存释放:
  ├── scavenger: 后台回收物理内存
  └── 内存不立即归还 OS，供复用
```

## 六、逃逸分析

```
编译器决定对象分配在栈上还是堆上

常见逃逸场景:
  ├── 返回局部变量指针
  ├── 闭包引用外部变量
  ├── interface{} 传参（动态类型 → 堆分配）
  ├── 变量过大超过栈帧限制
  └── 切片扩容后在堆上分配

查看方式:
  go build -gcflags='-m'         // 逃逸分析日志
  go build -gcflags='-m -m'      // 详细日志
  
Q: 为什么逃逸到堆不好？
   └── 堆分配 + GC 开销 > 栈分配（栈分配只需 SP 移动）
```


### 实例: 逃逸分析实战

```go
// -gcflags='-m' 查看编译器逃逸分析决策

// 例1: 返回指针 → 逃逸到堆
func f() *int {
    x := 42
    return &x // x 逃逸到堆（因为函数返回后栈帧释放但指针仍被引用）
}

// 例2: 闭包 → 逃逸
func g() func() int {
    x := 0
    return func() int { // x 被闭包引用 → 逃逸
        x++
        return x
    }
}

// 例3: interface 传参 → 逃逸
func h(v interface{}) { fmt.Println(v) }
// h(42) → 42 逃逸到堆（动态类型需要堆分配）

// 例4: 不逃逸（栈分配优先）
func sum() int {
    nums := make([]int, 3) // 大小固定 → 栈分配
    nums[0] = 1
    nums[1] = 2
    nums[2] = 3
    return nums[0] + nums[1] + nums[2]
}

// 例5: 变量过大 → 逃逸
func large() {
    a := [1000000]int{} // > 栈帧限制 → 堆分配
    _ = a
}
```

## 七、sync 包深度

```
Mutex:
  ├── 正常模式: 自旋 + CAS + 信号量（公平）
  └── 饥饿模式: 等待 > 1ms 切换到饥饿，直接排队

RWMutex:
  ├── 写优先（写等待时，新读不能获取锁）
  └── 底层: Mutex + readerCount + readerWait

WaitGroup:
  ├── Add() 必须发生在 Wait() 之前，或与 Done() 并发
  └── Wait() 返回后不可重用（可重用建议用 errgroup）

Once:
  ├── doSlow 用 atomic 做 double-check
  └── 死锁: Once 内部调 Once → fatal error

Pool:
  ├── 临时对象池，GC 时清空
  ├── Get: 私有 > 共享 > 其他 P 偷取 > New()
  └── 适用: 频繁分配的对象（如 json 解析 buffer）

Cond:
  ├── Wait() 必须持有锁，内部释放锁 + 挂起，唤醒后重新获取
  └── Signal/Broadcast 唤醒等待者
```

### 实例: sync 包实战

```go
// 1. Mutex 保护共享资源
type SafeCounter struct {
    mu    sync.Mutex
    count int
}

func (c *SafeCounter) Inc() {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.count++
}

// 2. RWMutex: 读多写少场景
type Cache struct {
    mu    sync.RWMutex
    data  map[string]string
}

func (c *Cache) Get(key string) string {
    c.mu.RLock()
    defer c.mu.RUnlock()
    return c.data[key]
}

func (c *Cache) Set(key, val string) {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.data[key] = val
}

// 3. WaitGroup 等待并发完成
func crawlWeb(urls []string) {
    var wg sync.WaitGroup
    for _, url := range urls {
        wg.Add(1)
        go func(u string) {
            defer wg.Done()
            fetch(u)
        }(url)
    }
    wg.Wait() // 等待所有请求完成
}

// 4. Once 单次初始化（单例）
var (
    config   *Config
    configOnce sync.Once
)

func GetConfig() *Config {
    configOnce.Do(func() {
        config = loadConfig() // 只执行一次
    })
    return config
}

// 5. Pool 复用对象
var bufPool = sync.Pool{
    New: func() interface{} {
        return new(bytes.Buffer)
    },
}

func writeJson(w io.Writer, v interface{}) error {
    buf := bufPool.Get().(*bytes.Buffer)
    defer bufPool.Put(buf)
    buf.Reset()
    if err := json.NewEncoder(buf).Encode(v); err != nil {
        return err
    }
    _, err := io.Copy(w, buf)
    return err
}

// 6. Cond 条件通知
type Queue struct {
    items []int
    cond  *sync.Cond
}

func NewQueue() *Queue {
    return &Queue{
        cond: sync.NewCond(&sync.Mutex{}),
    }
}

func (q *Queue) Push(item int) {
    q.cond.L.Lock()
    defer q.cond.L.Unlock()
    q.items = append(q.items, item)
    q.cond.Signal() // 唤醒消费者
}

func (q *Queue) Pop() int {
    q.cond.L.Lock()
    defer q.cond.L.Unlock()
    for len(q.items) == 0 {
        q.cond.Wait() // 等待生产者
    }
    item := q.items[0]
    q.items = q.items[1:]
    return item
}
```


### 实例: Context 实战

func doWork(ctx context.Context) {
    for {
        select {
        case <-ctx.Done():

            return
        default:

// 2. WithTimeout: 超时控制
func queryDB(ctx context.Context) (string, error) {
    done := make(chan string, 1)
    go func() {
        // 模拟慢查询
        time.Sleep(3 * time.Second)
        done <- "result"
    }()
    select {
    case r := <-done:
        return r, nil
    case <-ctx.Done():
        return "", ctx.Err() // context deadline exceeded
    }
}
// 使用:
// ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
// defer cancel()
// result, err := queryDB(ctx)

// 3. WithValue: 传递 trace-id
type ctxKey string
const TraceKey ctxKey = "trace_id"

func middleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        traceID := r.Header.Get("X-Trace-ID")
        if traceID == "" {
            traceID = uuid.New().String()
        }
        ctx := context.WithValue(r.Context(), TraceKey, traceID)
        next.ServeHTTP(w, r.WithContext(ctx))
    })
}

// 4. 优雅关闭服务（signal + context）
func gracefulShutdown() {
    ctx, stop := signal.NotifyContext(context.Background(), syscall.SIGINT, syscall.SIGTERM)
    defer stop()
    srv := &http.Server{Addr: ":8080"}
    go srv.ListenAndServe()
    <-ctx.Done() // 等待信号
    shutdownCtx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
    defer cancel()
    srv.Shutdown(shutdownCtx)
}

## 八、Context 包

```
context.Background(): 根 Context（最外层）
context.TODO():       不确定用途时占位
context.WithCancel():  手动取消
context.WithDeadline(): 绝对超时
context.WithTimeout():  相对超时
context.WithValue():   传值（key 用自定义类型防冲突）

最佳实践:
  ├── Context 作为函数第一个参数
  ├── 链式传递，不要存 struct
  ├── 超时/取消控制: 请求级生命周期
  └── WithValue 仅传请求级元数据（trace id 等）

典型场景:
  ├── HTTP 请求取消 → 所有下游 goroutine 退出
  ├── 数据库查询超时 → context.WithTimeout
  └── 优雅关闭: signal.NotifyContext
```


### 实例: defer / slice / map 实战

```go
// ===== defer 坑 =====
func exampleDefer() {
    // defer 参数在注册时求值
    i := 1
    defer fmt.Println(i) // 输出: 1（i 的当前值已拷贝）
    i = 2

    // defer + 闭包捕获外部变量
    i = 1
    defer func() {
        fmt.Println(i) // 输出: 2（引用外部 i）
    }()
    i = 2

    // defer 修改命名返回值
    func f() (r int) {
        defer func() { r++ }()
        return 0
    } // 返回 1

    // defer 执行顺序: LIFO
    for i := 0; i < 3; i++ {
        defer fmt.Print(i) // 2 1 0
    }
}

// ===== slice 陷阱 =====
func exampleSlice() {
    // 共享底层数组
    s := []int{1, 2, 3, 4, 5}
    s1 := s[1:3]      // [2,3], len=2, cap=4
    s1[0] = 99        // s 也变: [1,99,3,4,5]

    // append 不超过 cap → 共享
    s2 := s[1:3]      // cap=4
    s2 = append(s2, 6) // s 变: [1,99,3,6,5] ← 改了第四个元素！
    fmt.Println(s)     // [1,99,3,6,5]

    // append 超过 cap → 新分配，不再共享
    s3 := s[1:3]      // cap=4
    s3 = append(s3, 7, 8, 9) // len=5 > cap=4 → 新数组
    s3[0] = 88        // 不影响 s（s 仍=[1,99,3,6,5]，s3=[88,99,3,7,8,9]）
    fmt.Println(s)     // [1,99,3,6,5] ← s 不受影响！

    // 传参: slice header 拷贝但底层数组共享
    func modify(s []int) {
        s[0] = 100     // 会影响外部
        s = append(s, 200) // 不会影响外部（len/cap 只在函数内变）
    }
}

// ===== map 并发安全 =====
// 错误写法（并发读写 fatal crash）:
// var m map[string]int
// go func() { for { m["a"] = 1 } }()
// go func() { for { _ = m["a"] } }()
// → fatal error: concurrent map read and map write

// 正确做法 1: sync.RWMutex
var (
    m   = make(map[string]int)
    mu  sync.RWMutex
)
func read(k string) int { mu.RLock(); defer mu.RUnlock(); return m[k] }
func write(k string, v int) { mu.Lock(); defer mu.Unlock(); m[k] = v }

// 正确做法 2: sync.Map（读多写少场景）
var sm sync.Map
func useSyncMap() {
    sm.Store("key", 42)
    val, ok := sm.Load("key")
    sm.LoadOrStore("key", 100)     // 存在则返回，不存在则写入
    sm.Range(func(k, v interface{}) bool { // 遍历
        fmt.Println(k, v)
        return true // 继续遍历
    })
}

// ===== string 转换 =====
// string → []byte（有拷贝）
s := "hello"
b := []byte(s)      // 分配新内存拷贝
s2 := string(b)     // 再次拷贝

// 零拷贝转换（不安全但高效，go 1.20+)
// unsafe 方式: s[:] → string 转 []byte 免拷贝
```

## 九、常见考点

```
defer:
  ├── LIFO 执行，return 前执行
  ├── 参数在 defer 注册时求值（非执行时） ← 高频坑
  ├── 闭包引用: defer func() { 引用外部变量 }()
  └── defer recover: 必须在 panic 发生的 goroutine 内直接调用

panic/recover:
  ├── panic 沿调用栈传播
  ├── recover 只在 defer 中有用
  └── recover 后返回当前 goroutine 的控制权

slice:
  ├── 底层: unsafe.Pointer + len + cap
  ├── 扩容: <1024 → 2x, ≥1024 → 1.25x
  ├── 共享底层数组陷阱:
  │   s1 := s[0:1]  // 修改 s1 影响 s
  │   扩容后分裂: 超出 cap 新分配，不再共享
  └── 传 slice 是传 header 副本，但底层数组共享

map:
  ├── 底层: 哈希表（bmap + tophash）
  ├── 无序: 每次遍历随机起点（防依赖）
  ├── 并发读写: fatal error（不是 panic）→ 用 sync.Map
  ├── 非线程安全: 检测到并发读写直接 crash
  └── 扩容: 渐进式（每次写操作搬一部分 bucket）

string:
  ├── 底层: unsafe.Pointer + len（不可变）
  ├── string ↔ []byte: 隐式转化触发拷贝（除非优化）
  ├── string 拼接 +=: 每次创建新字符串（大量用 strings.Builder）
  └── range string: 按 rune 遍历，非 byte

for range 陷阱:
  ├── 迭代变量复用: for i, v := range { go func() {使用 v}() } → 全取最后一个
  │   解决: v := v / 或传参给闭包
  └── map range 中增删元素: 可能遍历到也可能遍历不到

nil 的妙用:
  ├── nil slice: 可 append（底层 cap=0）
  ├── nil map: 可读（返回零值），不可写（panic）
  ├── nil channel: 永久阻塞（select 中可用来禁用 case）
  └── nil interface ≠ nil pointer（经典坑）

make vs new:
  ├── make: 只用于 slice/map/channel（返回初始化后的值）
  └── new: 分配零值内存，返回指针（*T）
```

### 实例: 并发安全与 data race

```go
// 1. data race 示例（go run -race 检测）
var counter int
// 错误: 多个 goroutine 无锁并发写
for i := 0; i < 1000; i++ {
    go func() { counter++ }() // data race!
}

// 修复 1: Mutex
var mu sync.Mutex
for i := 0; i < 1000; i++ {
    go func() { mu.Lock(); counter++; mu.Unlock() }()
}

// 修复 2: atomic
var atomicCounter int64
for i := 0; i < 1000; i++ {
    go func() { atomic.AddInt64(&atomicCounter, 1) }()
}

// 2. happens-before 关系
var msg string
var done bool

func setup() {
    msg = "hello"     // (1)
    done = true       // (2) → happens-before (3)
}

func main() {
    go setup()
    for !done {       // (3) 空循环等待（无同步 → 不确定能否看到 msg）
        runtime.Gosched()
    }
    fmt.Println(msg)  // 理论上可能空！无 happens-before 保证
}
// 修复: 用 channel 或 sync.Mutex 建立 happens-before

// 3. 正确同步
func correctSync() {
    ch := make(chan struct{})
    var msg string
    go func() {
        msg = "hello"   // (1) happens-before (2)
        close(ch)       // (2) send happens-before receive
    }()
    <-ch                // (3) happens-after (2)
    fmt.Println(msg)    // 保证看到 "hello"
}
```

## 十一、Go 内存模型（happens-before）

```
核心原则:
  ├── 同一个 goroutine: 顺序一致性（代码执行顺序）
  ├── mutex: Unlock() happens-before 另一个 Lock()
  ├── channel: send happens-before receive
  ├── close(ch) happens-before 从 ch 收到零值
  └── WaitGroup: Done() happens-before Wait() 返回

常见的 data race 场景:
  ├── map 并发写（直接 fatal）
  ├── slice 并发 append（数据丢失）
  ├── 变量读写在 goroutine 间无同步
  └── 检测: go run -race，线上用 GODEBUG=race=1

## 十六、错误处理（errors 包）

```
Go 错误处理哲学: 显式处理，不抛异常

错误创建:
  ├── errors.New("msg")          // 简单错误
  ├── fmt.Errorf("wrap: %w", err) // 包装错误（%w 表示 wrap）
  └── fmt.Errorf("ctx: %v", err)  // 不包装，只带上下文

错误链:
  ├── errors.Is(err, target)     // 递归解包，判断是否为目标错误
  ├── errors.As(err, &target)    // 递归解包，转为指定类型
  └── errors.Unwrap(err)         // 获取被包装的下一层

自定义错误:
  type MyError struct { Msg string; Code int }
  func (e *MyError) Error() string { return e.Msg }

最佳实践:
  ├── 底层错误用 sentinel error: var ErrNotFound = errors.New("not found")
  ├── 需要额外信息用自定义 struct
  ├── 错误只处理一次，不要同时 log + return
  └── 关键路径用 fmt.Errorf("%w") 保留错误链

     └── As: 类型断言，适合自定义 error struct
  Q: %w 和 %v 区别？
     ├── %w: 保留 Unwrap 关系，可被 Is/As 追踪
     └── %v: 仅拼接字符串，不保留链

// 1. 泄漏: channel 永远收不到数据
func leak() {
    ch := make(chan int)
    go func() {
        <-ch // 永远阻塞，没人发数据 → goroutine 泄漏
    }()
}

// 修复: select + 超时
func fixed() {
    ch := make(chan int)
    go func() {
        select {
        case <-ch:
        case <-time.After(5 * time.Second):
            fmt.Println("timeout, exit")
        }
    }()
    // 或者用 context 控制
}

// 2. 泄漏: for-select 永不退出
func leakyWorker() {
    ch := make(chan int)
    go func() {
        for {
            select {
            case v := <-ch:
                fmt.Println(v)
            // 没有退出条件 → goroutine 永远卡在这里！
            }
        }
    }()
    // leakyWorker 返回后，ch 没有 close，goroutine 无法退出
}

// 修复: 加退出 channel 或 context
func fixedWorker(ctx context.Context, ch <-chan int) {
    for {
        select {
        case <-ctx.Done():
            fmt.Println("worker exiting:", ctx.Err())
            return  // ← 优雅退出
        case v := <-ch:
            fmt.Println(v)
        }
    }
}
// ★ select 执行顺序:
//   1. ctx 未取消 → ctx.Done() = nil 通道 → 永久阻塞，不会选中
//   2. ctx 取消 + ch 无数据 → 只有 ctx.Done() 就绪 → 确定走退出 ✅
//   3. ctx 取消 + ch 同时有数据 → 两个都就绪 → Go 随机选一个！
//      （多 case 就绪时 uniform random，防饥饿）
// 使用:
// ctx, cancel := context.WithCancel(context.Background())
// go fixedWorker(ctx, ch)
// cancel()  // 关闭 ctx.Done()，ch 无数据 → 确定执行退出，不会随机

// ★ 随机例子: 两个 channel 同时就绪 → select 随机选
func demoRandomSelect() {
    // 每轮重新创建 channel，确保两个都有数据
    for i := 0; i < 10; i++ {
        ch1 := make(chan string, 1)
        ch2 := make(chan string, 1)
        ch1 <- "来自 ch1"
        ch2 <- "来自 ch2"
        // 此时两个 channel 都有数据，select 会随机选一个
        select {
        case v := <-ch1:
            fmt.Println("选中 ch1:", v)
        case v := <-ch2:
            fmt.Println("选中 ch2:", v)
        }
    }
    // 输出示例（每次运行可能不同）:
    // 选中 ch2: 来自 ch2
    // 选中 ch1: 来自 ch1
    // 选中 ch2: 来自 ch2  ← 随机！无固定顺序
    // 选中 ch1: 来自 ch1
    // ...
}
// 运行: demoRandomSelect()
// 多次运行结果不同 → 证明 select 在多个就绪 case 间随机选择

// ★ 随机例子2: ctx 取消 + ch 同时有数据 → 也是随机选！
func demoCancelVsData() {
    for i := 0; i < 10; i++ {
        ctx, cancel := context.WithCancel(context.Background())
        ch := make(chan string, 1)
        ch <- "业务数据"
        cancel() // 此时 ctx.Done() 关闭（就绪）+ ch 有数据（就绪）
        select {
        case <-ctx.Done():
            fmt.Println("ctx 取消了")
        case v := <-ch:
            fmt.Println("读到数据:", v)
        }
        // 输出随机: 有时 "ctx 取消了"，有时 "读到数据: 业务数据"
        // 多次运行可观察到两种输出交替出现
    }
}
// 关键在于: cancel() 后 ctx.Done() 关闭 + ch 已有数据 = 双就绪 → 随机
// 这解释了为什么生产代码中要先检查 ctx.Done() 再读 ch:
// select {
// case <-ctx.Done(): return
// case v := <-ch:             // ctx 取消了 + ch 有数据 → 仍可能走这里！
// }
// 但这里有个隐含问题：step 1 → step 2 之间可能有 cancel() 插入，
// 此时 ctx.Done() + ch 同时就绪 → step 2 的 select 仍然随机，还是可能读到 ch！
// 所以"先非阻塞检查"只解决"ctx 已取消时不阻塞等 ch"，不保证不读脏数据。
// 真正的严谨写法: 读完后二次确认 ctx 状态

// ★ 真正严谨: 读 ch + 二次检查 ctx
func demoRigorousSelect(ctx context.Context, ch <-chan string) {
    select {
    case <-ctx.Done():
        fmt.Println("ctx 已取消，直接返回")
        return
    case v := <-ch:
        // 读出数据了，但在处理前再确认 ctx 是否刚取消
        select {
        case <-ctx.Done():
            fmt.Println("读到数据但 ctx 刚取消，丢弃")
            return
        default:
        }
        fmt.Println("安全读到:", v)
    }
}
// 调用:
// ctx, cancel := context.WithTimeout(context.Background(), 100*time.Millisecond)
// defer cancel()
// demoRigorousSelect(ctx, ch)
// 优势: 读 ch 后二次确认 ctx，杜绝处理"脏数据"（代价是极短暂的额外检查）

## 十八、goroutine 泄漏与防护

```
泄漏场景:
  ├── channel 一直没数据，接收者永远阻塞
  │   修复: select + timeout 或用 context 控制
  ├── 无缓冲 channel，发送者无接收者
  │   修复: 改为有缓冲或用 select + default
  ├── timer 未 Stop
  │   修复: defer timer.Stop()
  ├── goroutine 在 for-select 中永远不退出
  │   修复: 用 done channel 或 context 做退出信号
  └── 第三方包启动 goroutine 不暴露停止接口

## 十九、错误恢复与 panic 处理

```
panic 恢复原则:
  ├── 只在 package 边界 recover（如 HTTP handler 顶层）
  ├── 不要 recover 未知 panic（可能破坏内部状态）

  func safeGo(fn func()) {
      go func() {
          defer func() {
              if err := recover(); err != nil {

              }
          }()
          fn()
      }()
  }

  Q: panic 后还能 recover 什么？
     └── runtime 错误（nil pointer、index out of range）也能 recover

### 2. Worker Pool（工作池）
```go
// 固定数量 goroutine 从 channel 取任务执行，控制并发度
type Pool struct {
    work chan func()
    wg   sync.WaitGroup
}

func New(size int) *Pool {
    p := &Pool{work: make(chan func())}
    for i := 0; i < size; i++ {
        p.wg.Add(1)
        go func(id int) {
            defer p.wg.Done()          // worker 退出时减一
            for fn := range p.work {   // channel 关闭后自动退出
                fn()
            }
        }(i)
    }
    return p
}

// 提交任务（可能会阻塞，如果所有 worker 都在忙）
func (p *Pool) Submit(fn func()) {
    p.work <- fn
}

// 关闭 Pool，等待所有 worker 退出
func (p *Pool) Shutdown() {
    close(p.work)  // 通知所有 worker 退出
    p.wg.Wait()    // 等待所有 worker 结束
}

// 使用示例:
pool := New(5)                         // 启动 5 个 worker
for i := 0; i < 100; i++ {
    i := i                             // 捕获循环变量
    pool.Submit(func() {               // 提交 100 个任务
        fmt.Println("task", i)
    })
}
pool.Shutdown()                        // 等待全部完成
fmt.Println("all done")
// 对比: 直接 go func() 开 goroutine 不做控制 → 并发爆炸
```

### 3. Options Pattern（函数选项）
```go
// 解决"构造函数参数太多"的问题，替代 builder 模式
type Config struct {
    Addr    string
    Timeout time.Duration
    MaxConn int
}

// Option 是函数类型：接收 *Config，修改其字段
type Option func(*Config)

func WithTimeout(t time.Duration) Option {
    return func(c *Config) { c.Timeout = t }
}
func WithAddr(addr string) Option {
    return func(c *Config) { c.Addr = addr }
}
func WithMaxConn(n int) Option {
    return func(c *Config) { c.MaxConn = n }
}

func defaultConfig() *Config {
    return &Config{
        Addr:    ":8080",
        Timeout: 30 * time.Second,
        MaxConn: 100,
    }
}

type Server struct{ cfg *Config }

func New(opts ...Option) *Server {           // 返回指针
    cfg := defaultConfig()                   // ① 先给默认值
    for _, opt := range opts { opt(cfg) }    // ② 逐一执行选项函数修改 cfg
    // 机制: opt 是 func(*Config) 类型（即 Option）
    // opt(cfg) 调用闭包，例如 WithTimeout(5s) 返回的闭包内执行 cfg.Timeout = 5s
    // 相当于: 调用方说"加辣"→ 店员(循环)执行"加辣"操作修改订单(cfg)
    return &Server{cfg: cfg}
}
// 问: 返回 *Server → 逃逸到堆？答: 是的，因为指针要传到函数外，不能分配在栈上（栈帧回收后指针就悬空了）。逃逸是编译器行为，不是「用了指针就逃逸」：
//   ├── 返回 &Server{} → 逃逸到堆 ✅（外部要用）
//   ├── 局部变量 &x 不外传 → 不逃逸，仍在栈 ✅（编译器能证明不会泄露）
//   ├── 值传递给 fmt.Println(x) → 可能逃逸（fmt 用 interface{} 接收）
//   └── 结论: 按语义写代码，不用过早优化逃逸。编译器逃逸分析很智能

// 使用场景 1: 只传需要的参数
s1 := New(WithTimeout(5 * time.Second))
// 结果: Addr=":8080"(默认), Timeout=5s, MaxConn=100(默认)

// 使用场景 2: 全自定义
s2 := New(
    WithAddr(":9090"),
    WithTimeout(10*time.Second),
    WithMaxConn(500),
)
// 结果: Addr=":9090", Timeout=10s, MaxConn=500

// 使用场景 3: 零参数 = 全默认
s3 := New()

// 优势: 
//   - 新增选项只需加 WithXxx 函数，无需改 New 签名
//   - 调用方只关注关心的参数，不传 nil 或空值
//   - 编译期类型安全（传错类型编译不过）
```

### 5. Fan-Out / Fan-In（扇出/扇入）
```go
// Fan-Out: 多个 goroutine 从同一个 channel 读（分发任务）
func fanOut(in <-chan int, workers int) {
    for i := 0; i < workers; i++ {
        go func(id int) {
            for v := range in {
                fmt.Printf("worker %d: %d\n", id, v)
            }
        }(i)
    }
}

// Fan-In: 多个 channel 合并到一个（汇聚结果）
func fanIn(chs ...<-chan int) <-chan int {
    out := make(chan int)
    var wg sync.WaitGroup
    for _, ch := range chs {
        wg.Add(1)
        go func(c <-chan int) {
            defer wg.Done()
            for v := range c { out <- v }
        }(ch)
    }
    go func() { wg.Wait(); close(out) }()  // 所有输入 channel 关闭后才关 out
    return out
}
// 典型场景: 生产者多路 → fanIn 汇聚 → 统一消费
```

## 二十五、Go 代码规范与 lint

```
命名规范:
  ├── 驼峰: export 首字母大写，unexport 小写
  ├── 缩写: 全大写或全小写（HTTP, URL, ID → 不写 HttpUrl）

  ├── gofmt: 格式强制标准
  ├── go vet: 静态分析可疑构造
  ├── staticcheck: 业界最强静态检查
  ├── revive: golint 替代品
  └── golangci-lint: 多 lint 集成

有效 Go 建议:
  ├── 零值有用: var s []int 可直接 append
  ├── 不要用内联 error:  if err != nil { ... }
  ├── 接口尽量小: 1~2 方法
  └── "Accept interfaces, return structs"
```

// 1. 并发安全计数器（atomic 版本）
type Counter struct {
    v int64
}
func (c *Counter) Inc()  { atomic.AddInt64(&c.v, 1) }
func (c *Counter) Dec()  { atomic.AddInt64(&c.v, -1) }
func (c *Counter) Val() int64 { return atomic.LoadInt64(&c.v) }

// 2. SingleFlight 并发缓存（防止缓存击穿）
type Call struct {
    val interface{}
    err error
    wg  sync.WaitGroup
}
type Group struct {
    mu    sync.Mutex
    calls map[string]*Call
}
func (g *Group) Do(key string, fn func() (interface{}, error)) (interface{}, error) {
    g.mu.Lock()
    if c, ok := g.calls[key]; ok {
        g.mu.Unlock()
        c.wg.Wait()
        return c.val, c.err
    }
    c := new(Call)
    c.wg.Add(1)
    g.calls[key] = c
    g.mu.Unlock()
    c.val, c.err = fn()
    c.wg.Done()
    g.mu.Lock()
    delete(g.calls, key)
    g.mu.Unlock()
    return c.val, c.err
}

// 3. Token Bucket 限流器
type Limiter struct {
    rate   float64
    burst  int
    tokens float64
    last   time.Time
    mu     sync.Mutex
}
func (l *Limiter) Allow() bool {
    l.mu.Lock()
    defer l.mu.Unlock()
    now := time.Now()
    elapsed := now.Sub(l.last).Seconds()
    l.tokens += elapsed * l.rate
    if l.tokens > float64(l.burst) {
        l.tokens = float64(l.burst)
    }
    l.last = now
    if l.tokens < 1 { return false }
    l.tokens--
    return true
}

// 4. Fan-Out 任务分发器
func FanOut(jobs <-chan int, numWorkers int) {
    var wg sync.WaitGroup
    for i := 0; i < numWorkers; i++ {
        wg.Add(1)
        go func(id int) {
            defer wg.Done()
            for job := range jobs {
                fmt.Printf("worker %d: job %d\n", id, job)
            }
        }(i)
    }
    wg.Wait()
}

// 5. 优雅关闭 HTTP 服务（完整版）
func gracefulShutdown() {
    srv := &http.Server{Addr: ":8080"}
    go func() {
        if err := srv.ListenAndServe(); err != nil && err != http.ErrServerClosed {
            log.Fatalf("listen: %s\n", err)
        }
    }()
    quit := make(chan os.Signal, 1)
    signal.Notify(quit, syscall.SIGINT, syscall.SIGTERM)
    <-quit
    ctx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
    defer cancel()
    srv.Shutdown(ctx)
}

// 6. 并发安全的 LRU Cache
type LRUCache struct {
    mu       sync.Mutex
    capacity int
    cache    map[string]*list.Element
    lru      *list.List
}
type entry struct{ key, value string }
func NewLRU(cap int) *LRUCache {
    return &LRUCache{
        capacity: cap,
        cache:    make(map[string]*list.Element),
        lru:      list.New(),
    }
}
func (c *LRUCache) Get(key string) (string, bool) {
    c.mu.Lock()
    defer c.mu.Unlock()
    if elem, ok := c.cache[key]; ok {
        c.lru.MoveToFront(elem)
        return elem.Value.(*entry).value, true
    }
    return "", false
}
func (c *LRUCache) Set(key, value string) {
    c.mu.Lock()
    defer c.mu.Unlock()
    if elem, ok := c.cache[key]; ok {
        c.lru.MoveToFront(elem)
        elem.Value.(*entry).value = value
        return
    }
    if c.lru.Len() >= c.capacity {
        back := c.lru.Back()
        if back != nil {
            delete(c.cache, back.Value.(*entry).key)
            c.lru.Remove(back)
        }
    }
    c.lru.PushFront(&entry{key, value})
    c.cache[key] = c.lru.Front()
}
