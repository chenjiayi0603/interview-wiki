# 系统设计 · IM 系统

> 面试频率：⭐⭐⭐⭐⭐（字节/中小公司必考）

---

## 一、需求

```
日活 1 亿，日消息量 10 亿
群聊最大 5000 人，消息延迟 P99 < 100ms
消息不丢不重
```

---

## 二、整体架构

```
客户端(TCP/WS) → Nginx(SSL终止) → Access网关 → gRPC → 服务层
                                                          ↓
                                   存储层: MySQL/Redis/MongoDB/RocketMQ
```

---

## 三、核心设计点

### 3.1 连接管理

```
Access 网关（自研 C++，epoll ET 模式）:
  ├── 单机 120 万连接（每连接 12KB）
  ├── 多 Worker 模型: acceptor → N 个 worker（epoll_wait）
  ├── 连接分配: accept 后按 fd % N 分发
  └── CPU 绑定 + 对象池

内核调优:
  ├── ulimit -n 1048576
  ├── tcp_mem/wmem/rmem 调大
  └── tcp_tw_reuse / fin_timeout 优化
```

### 3.2 消息推送（核心）

```
单聊:
  发消息 → 写 DB → MQ → PushServer → 查在线 → 推网关 → 客户端

群聊（关键优化）:
  1000 人群:
    优化前: 推 999 次（每人 1 次）
    优化后: 按网关合并，1000人/10网关 = 10 次推送

  ACK:
    网关 TCP 确认 → ACK MQ（不等客户端 ACK）
    网关推送失败 → RECONSUME_LATER 阶梯重试
    重试 > 16 次 → 死信队列人工补偿
```

### 3.3 消息有序性

```
每个群独立 seq: Redis INCR session_msgseq
客户端按 seq 排序展示（不管到达顺序）
批次预分配: 每 10000 条一次 INCRBY（减少 Redis 压力）
```

### 3.4 未读数

```
❌ Redis INCR: 撤回 DECR 可能丢失，大群写扩散
✅ MongoDB count: count(msgId > lastReadMsgId AND msgState != 4)
   精确、无写扩散、撤回简单
```

### 3.5 离线消息

```
离线消息存 MongoDB 30 天，上线后拉取
首次只拉最近 20 条概要，详情点击再加载
```

### 3.6 多端同步

```
每端独立 TCP 连接，不同 deviceId
每设备独立维护 lastReadMsgId
消息按 userId 推送至所有在线设备
```

### 3.7 消息不丢不重

```
不丢: WAL + MongoDB + MQ ACK + 离线收件箱
不重: 客户端 msgId 去重（exactly-once = at-least-once + 去重）
```

## 四、存储方案

| 数据 | 存储 | 分片 |
|------|------|------|
| 消息 | MongoDB 分片集群 | user_id % 32 |
| 用户/好友/群组 | MySQL 分库分表 | 32 库 × 64 表 |
| 在线/路由 | Redis/Codis | 一致性哈希 |
| 历史消息(冷) | MongoDB 归档 | 30 天后转冷 |

---

## 五、推拉模式选择

```
写扩散（存 N 份，读快）: 小群 < 500 人
读扩散（存 1 份，写快）: 大群 > 500 人

混合策略:
  ├── 在线成员: 推送到网关 → 内存
  └── 离线成员: 不写收件箱，上线后拉取群消息
```

## 六、追问应对

```
Q: "为什么不用 Kafka？"
A: "RocketMQ 延迟更低（长轮询），内置重试+死信，运维简单"

Q: "WebSocket 还是自研 TCP？"
A: "App 端自研 TCP（4字节头），第三方用 WebSocket"

Q: "怎么保证消息不重？"
A: "客户端 uuid msgId，服务端去重表"

Q: "心跳怎么设计？"
A: "30s 发一次，90s 超时判离线，指数退避重连"
```
