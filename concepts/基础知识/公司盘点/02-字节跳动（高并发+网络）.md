## 二、字节特色面试题

### Q1: epoll ET/LT 区别？百万连接为什么用 ET？

```
LT（水平触发）: 数据没读完 → 下次还会通知（编程简单，性能略低）
ET（边缘触发）: 只通知一次 → 必须循环读到 EAGAIN（编程难，性能高）

百万连接选 ET:
  ├── 减少 epoll_wait 返回次数
  ├── 搭配非阻塞 IO + 循环读写
  └── 系统调用更少
```

#### ET 模式完整代码

```c
// epoll ET 模式服务端核心（C 语言）
#define MAX_EVENTS 1024
#define READ_BUF_SIZE 4096

void handle_connection(int epfd, struct epoll_event *events, int nfds) {
    for (int i = 0; i < nfds; i++) {
        int fd = events[i].data.fd;

        if (events[i].events & EPOLLIN) {
            // ET 模式: 循环读到 EAGAIN
            char buf[READ_BUF_SIZE];
            int offset = 0;

            while (1) {
                ssize_t n = read(fd, buf + offset, sizeof(buf) - offset);
                if (n > 0) {
                    offset += n;
                    if (offset >= sizeof(buf)) {
                        // 缓冲区满，处理已有数据
                        process_data(fd, buf, offset);
                        offset = 0;
                    }
                    continue;
                }
                if (n == -1) {
                    if (errno == EAGAIN || errno == EWOULDBLOCK) {
                        break; // 数据读完
                    }
                    if (errno == EINTR) {
                        continue; // 被中断重试
                    }
                    close(fd);
                    break;
                }
                if (n == 0) {
                    close(fd); // 对端关闭
                    break;
                }
            }
            if (offset > 0) {
                process_data(fd, buf, offset);
            }
        }

        if (events[i].events & EPOLLOUT) {
            // ET 模式写: 循环写到 EAGAIN
            send_buffered_data(fd);
            // 如果写完了，取消 EPOLLOUT 事件
            struct epoll_event ev;
            ev.data.fd = fd;
            ev.events = EPOLLIN | EPOLLET; // 只等读
            epoll_ctl(epfd, EPOLL_CTL_MOD, fd, &ev);
        }

        if (events[i].events & (EPOLLERR | EPOLLHUP)) {
            close(fd);
        }
    }
}
```

```
面试话术:
  Q: "ET 模式要注意什么坑？"
  A: "ET 必须循环读写直到 EAGAIN，否则数据会丢。
      而且搭配非阻塞 IO，用阻塞 IO 的话 ET 退化成 LT。
      还有一个坑: accept 也要用 ET + while 循环，
      不然多连接同时到来时只 accept 一次就漏了。"
```

### Q2: select / poll / epoll / io_uring 演进？

| 维度 | select | poll | epoll | io_uring |
|------|--------|------|-------|----------|
| 最大 fd | 1024 | 无上限 | 无上限 | 无上限 |
| 效率 | O(n) 遍历 | O(n) 遍历 | O(1) 就绪回调 | O(1) 异步完成 |
| 模式 | LT | LT | LT+ET | 异步 |
| 内核版本 | 全 | 全 | Linux 2.6+ | Linux 5.1+ |

**io_uring**: 共享内存环(SQ/CQ)，减少 syscall，适合高吞吐网络/存储场景

```
面试话术:
  Q: "实际项目用 epoll 还是 io_uring？"
  A: "目前 epoll 是主流，Linux 5.1+ 才支持 io_uring。
      io_uring 优势在减少 syscall 次数，适合高吞吐场景（如 Redis、Nginx）。
      如果内核版本够新、性能要求极致，可以考虑 io_uring。
      通用业务用 epoll 完全够。"
```

### Q3: Go GMP 模型 vs C++ 线程池？

```
Go GMP:
  G(Goroutine) → 栈 2KB 起步，动态伸缩
  M(Machine)   → OS 线程，默认 GOMAXPROCS
  P(Processor) → 本地调度器，持有 G 队列

调度:
  1. P 从本地队列取 G 运行
  2. 本地空 → 偷取(Work Stealing)
  3. G 阻塞 → M 与 P 解绑 → 新 M 接管

C++ 线程池对比:
  ├── Go: 隐式调度，开发不关心线程数
  ├── C++: 显式控制，性能更可控（适合中间件）
  └── 字节: 业务用 Go，中间件用 C++
```

#### GMP 面试话术（结合项目）

```go
// 雷漫 IM 项目中，Goroutine 处理每个 WebSocket 连接
// 100 万连接 = 100 万 Goroutine？不行！

// 错误做法: 每个连接一个 Goroutine 读写
// 问题: 100 万 Goroutine → 栈 2KB × 100 万 = 2GB 起步
//       调度开销巨大，GC 压力暴增

// 正确做法: Goroutine Pool + Reactor 模型
type ConnectionPool struct {
    workers   int               // 固定 worker 数量（CPU 密集型 = GOMAXPROCS）
    connChan  chan *Connection  // 连接事件通道
}

func NewConnectionPool(workers int) *ConnectionPool {
    cp := &ConnectionPool{
        workers:  workers,
        connChan: make(chan *Connection, 1024),
    }
    for i := 0; i < workers; i++ {
        go cp.worker(i)
    }
    return cp
}

func (cp *ConnectionPool) worker(id int) {
    for conn := range cp.connChan {
        // 非阻塞循环读写（类似 epoll ET）
        conn.SetReadDeadline(time.Now().Add(30 * time.Second))
        for {
            msg, err := conn.ReadMessage()
            if err != nil {
                if netErr, ok := err.(net.Error); ok && netErr.Timeout() {
                    break
                }
                conn.Close()
                break
            }
            // 解析、路由消息
            Router().Dispatch(conn, msg)
        }
    }
}

// 关键权衡:
// Go: 1000 个 Goroutine 处理 10 万连接（每个 Goroutine epoll_wait 管理一组 fd）
// C++: 8 个线程处理 100 万连接（每个线程 epoll 管理一组 fd）
// Go 的优势: 开发效率高，GC 对 Goroutine 栈友好
// C++ 的优势: 零 GC 停顿，极致性能
```

#### 追问: GOMAXPROCS 设置多少合适？

```
Q: GOMAXPROCS 设多少？
A: 默认 = CPU 核心数。
   - IO 密集型（IM/WebSocket）: GOMAXPROCS = CPU 核心数 × 2（更多 P 让 M 阻塞时快速切换）
   - CPU 密集型（计算/加密）: GOMAXPROCS = CPU 核心数（避免线程切换开销）

   字节内部: Go 业务服务一般设 8-16，配合 P 数量控制 Goroutine 调度粒度
```

### Q4: 怎么保证消息时序一致性？

```
挑战: 同群消息 A 先发但后到，多设备收到顺序不一
```

#### 完整方案（Go 实现）

```go
// 消息序号服务
type SeqService struct {
    rdb *redis.Client
}

// NextSeq 获取单调递增 seq（群维度）
func (s *SeqService) NextSeq(ctx context.Context, groupID string) (int64, error) {
    // Redis INCR 保证单调递增、不重复、不回拨
    seq, err := s.rdb.Incr(ctx, "group_seq:"+groupID).Result()
    if err != nil {
        return 0, err
    }
    return seq, nil
}

// 消息发送
func (s *SeqService) SendMessage(ctx context.Context, msg *Message) error {
    // 1. 分配 seq（此时即可排序）
    seq, err := s.NextSeq(ctx, msg.GroupID)
    if err != nil {
        return err
    }
    msg.Seq = seq
    msg.Timestamp = time.Now().UnixMilli()

    // 2. 存储消息（RocksDB / MySQL）
    if err := s.storeMessage(msg); err != nil {
        return err
    }

    // 3. 推送给群成员（MQ 广播）
    return s.pushToGroup(msg)
}

// 客户端排序（Go 伪代码）
type MessageList struct {
    msgs      []*Message
    maxWait   time.Duration // 最大等待时间
    waitStart time.Time
}

func (ml *MessageList) AddMessage(msg *Message) {
    // 按 Seq 插入排序（插入排序，消息量不大）
    idx := sort.Search(len(ml.msgs), func(i int) bool {
        return ml.msgs[i].Seq >= msg.Seq
    })
    ml.msgs = append(ml.msgs, nil)
    copy(ml.msgs[idx+1:], ml.msgs[idx:])
    ml.msgs[idx] = msg
}

// Seq 缺失检测: 发现不连续时等待（最多 5s）
func (ml *MessageList) CheckSeqGap() {
    for i := 1; i < len(ml.msgs); i++ {
        if ml.msgs[i].Seq != ml.msgs[i-1].Seq+1 {
            // 有 gap，等待
            if time.Since(ml.waitStart) > ml.maxWait {
                // 超时，强制展示（可能有乱序，但概率低）
                return
            }
            // 继续等待缺失的消息
            time.Sleep(100 * time.Millisecond)
            i-- // 重新检查这个位置
        }
    }
}
```

```
面试话术:
  Q: "Redis INCR 做 seq 有什么风险？"
  A: "Redis 宕机或主从切换可能导致 seq 丢失或跳号。
      方案: ① Redis 持久化（AOF）防止重启丢 seq；
      ② 用 Redis Cluster 保证高可用；
      ③ seq 丢失影响不大，客户端检测到 gap 超时后强制展示，
      只是个别消息可能乱序，不影响整体体验。"
```

### Q5: 缓存穿透/击穿/雪崩 的区别？

```
缓存穿透（查不存在的数据）:
  → 布隆过滤器 / 空值缓存

缓存击穿（热点 key 过期）:
  → 互斥锁重建 / 逻辑永不过期

缓存雪崩（大量 key 同时过期）:
  → 过期时间随机化 / 多级缓存 / 降级
```

```
面试话术:
  Q: "这三种情况分别适合什么场景？"
  A: "穿透: 适合恶意请求拦截，布隆过滤器误判率要调到<1%。
      击穿: 适合热点新闻/爆款商品，用互斥锁防止所有请求同时打 DB。
      雪崩: 适合缓存初始化或重启场景，过期时间加随机偏移
      防止同时过期。三者的共同点是: 最终要保护 DB 不被冲垮。"
```

### Q6: Redis 大 Key 怎么发现和解决？

```
发现: redis-cli --bigkeys / 慢查询日志 / 可观测性插件

解决:
  ├── 大 Hash → 多个小 Hash（Hash 分片）
  ├── 大 Value → 压缩存储
  └── 删除 → UNLINK 替代 DEL（异步）
```

```
面试话术:
  Q: "大 Key 有什么危害？"
  A: "三个危害: ① 读写慢，单次操作 O(n)；
      ② 阻塞 Redis，DEL 大 key 会让 Redis 卡住几秒；
      ③ 网络带宽打满，一个 key 几 MB，高并发时带宽爆了。
      解决方案: 大 Hash 分成多个小 Hash（比如 user:1001:friends 分片），
      大 Value 考虑压缩或存到其他存储（OSS），删除用 UNLINK 异步。"
```

### 字节跳动故事

```
S（情境）: 雷漫 IM 需要支撑 900 万注册用户，高峰期单机 120 万并发连接
T（任务）: 消息延迟 < 100ms P99，资源消耗可控，不 OOM
A（行动）:
  ├── 网络层: epoll ET + 非阻塞 IO（C++ 网关，8 线程管理 100 万连接）
  ├── 业务层: Go Goroutine Pool（32 个 worker 处理所有连接事件）
  ├── 消息合并: 群发消息 → 按群聚合 → 一次 RPC 推全群（3000 次 → 10 次）
  │     └── 实现: map[groupID][]targetUser, 每 20ms flush 一次
  ├── 时序保障: Redis INCR 单调 seq + 客户端 cache & sort
  └── 内存优化: 连接对象池（sync.Pool 复用），零拷贝读缓冲区

R（结果）:
  ├── P50 延迟 0.8ms，P99 延迟 50ms，吞吐 5 万条/秒
  ├── 群消息 RPC 合并后降低 99.7% 的调用量
  ├── 单机内存稳定在 4GB，GC 停顿 < 10ms
  └── 全链路压测 120 万连接无掉线

追问层层递进:
  Q1: 100 万 Goroutine 不行，那 1 万个呢？
  A: 也不行。每个 Goroutine 占用 2KB 栈，1 万 = 20MB 还能接受，
     但调度开销和 GC 扫描是 O(n) 的。Go 的 GC 是标记-清扫，
     扫描 1 万个栈肯定比 32 个栈慢。所以用 Goroutine Pool 固定数量。

  Q2: 合并推送怎么保证不丢消息？
  A: 合并只是"攒一批发"，不是丢弃。消息先写 RocksDB 持久化，
     再进合并队列。如果合并推送失败，消费者会重试，保证 at-least-once。

  Q3: 单机 120 万连接，TCP 端口够吗？
  A: 服务端 accept 不消耗端口，只消耗 fd（每个连接 1 个 fd）。
     Linux 默认 ulimit -n 1024，需要调大到 1048576。
     epoll 的 eventpoll 结构体内存约 200B，120 万 ≈ 240MB。
```

### Q7: 零拷贝（Zero-Copy）怎么实现？mmap 和 sendfile 区别？

#### 原理对比

```
传统读+写（4次拷贝，4次上下文切换）:
  磁盘 → 内核缓冲区(read) → 用户缓冲区 → 内核缓冲区(write) → 网卡

mmap（3次拷贝，4次上下文切换）:
  磁盘 → 内核缓冲区(mmap) → 用户共享 → 内核缓冲区(write) → 网卡
  ├── 优点: 省 1 次内核→用户的拷贝
  └── 缺点: 内存映射占用虚拟地址空间

sendfile（2次拷贝，2次上下文切换）:
  磁盘 → 内核缓冲区 → 网卡（DMA 直接到网卡）
  ├── 优点: 完全在内核态完成，最少的拷贝
  └── 适用: 静态文件传输（Nginx/静态资源）

io_uring + 注册缓冲区（真正的 0 拷贝）:
  共享内存环，应用和内核共用缓冲区
  连内核→用户的拷贝都省了
```

#### Go 中的零拷贝

```go
// Go 中 sendfile 的使用
import "net/http"
import "os"

func serveFile(w http.ResponseWriter, r *http.Request) {
    file, _ := os.Open("large_file.bin")
    defer file.Close()

    fileInfo, _ := file.Stat()
    // Go 的 http.ServeContent 内部使用 sendfile（Linux）
    http.ServeContent(w, r, "large_file.bin", time.Now(), file)
    // 输出: 仅 2 次拷贝（磁盘 → 内核缓冲 → 网卡）
    // 对比: io.Copy 是 4 次拷贝
}

// 手动使用 sendfile（Go 1.20+）
import "golang.org/x/sys/unix"

func sendFileDirect(dst int, src int, count int64) (int64, error) {
    // 直接系统调用 sendfile
    n, err := unix.Sendfile(dst, src, nil, int(count))
    return int64(n), err
}
```

#### 面试话术

```
字节/头条场景: 视频/图片文件传输
  用 sendfile 比 read+write 快 2-3 倍
  100GB 视频= 用户态 100GB 拷贝 VS 内核态零拷贝
  网卡支持 DMA 时，CPU 完全不参与数据搬运

对比:
  mmap 适合: 频繁读写的小文件（如配置文件、索引文件）
  sendfile 适合: 大文件传输（图片、视频、静态资源）
  io_uring 适合: 极致性能场景（中间件、网关）
```
