## 二、存储方向特色面试题

### Q1: 存算分离 vs 存算一体？

| 维度 | 存算一体（原生 Redis） | 存算分离（KeyDB） |
|------|---------------------|------------------|
| 延迟 | 微秒级 | 毫秒级（冷数据） |
| 成本 | 高（全内存） | 低（冷数据上 OBS） |
| 弹性 | 困难（需迁移数据） | 灵活（加计算节点即可） |

```
面试话术:
  "存算分离的核心是'让计算和存储独立扩缩'。
   原生 Redis 存算一体，加节点 = 同时加 CPU 和内存，
   但电商场景可能 CPU 不够内存有剩，浪费。
   存算分离后计算节点无状态，秒级扩缩容，
   冷数据放 OBS（成本降 60%），热数据在内存。
   代价是冷数据读延迟从微秒级变成毫秒级，但命中率 95% 以上就没影响。"
```

### Q2: LSM-Tree vs B+Tree 优缺点？

| 维度 | LSM-Tree (RocksDB) | B+Tree (InnoDB) |
|------|-------------------|----------------|
| 写入 | **快**（顺序写，无随机 IO） | 慢（随机写页分裂） |
| 读取 | 慢（需查多层） | **快**（路径固定） |
| 写放大 | 高 10-20x | 低 ~2x |
| 适用 | 写入密集、SSD 友好 | 读取密集、OLTP |

```
面试话术:
  "LSM-Tree 用顺序写换随机写，适合写多读少场景。
   B+Tree 用随机写换读性能，适合 OLTP 场景。
   面试常问: 为什么 RocksDB 写放大高？
   因为 LSM-Tree 每一层 compaction 都要重写 SST 文件，
   默认 10 倍写放大 = 应用写 1MB，磁盘实际写 10MB。
   SSD 寿命有限，写放大是 RocksDB 的核心优化目标。"
```

### Q3: RocksDB Compaction 策略对比？

| 策略 | 写放大 | 读放大 | 适用场景 |
|------|--------|--------|---------|
| **Leveled**（默认） | 10-20x | 低 | 通用 |
| **Universal** | ~2x | 高 | 写入极密集 |
| **FIFO** | 无 | 高 | TTL 过期 |
| **Leveled + TTL** | 10-20x | 低 | 冷热分层 |

#### RocksDB 核心配置（C++）

```cpp
#include <rocksdb/db.h>
#include <rocksdb/options.h>

// KeyDB 项目中的 RocksDB 调优配置
rocksdb::Options GetKeyDBOptions() {
    rocksdb::Options opts;
    opts.create_if_missing = true;

    // === 内存相关 ===
    opts.write_buffer_size = 256 * 1024 * 1024;      // 256MB memtable
    opts.max_write_buffer_number = 4;                 // 最多 4 个 memtable
    opts.min_write_buffer_number_to_merge = 2;        // 最少 2 个才合并

    // === LSM-Tree 层级 ===
    opts.level0_file_num_compaction_trigger = 4;      // L0 4 个文件触发 compaction
    opts.level0_slowdown_writes_trigger = 20;         // L0 20 个文件时减慢写入
    opts.level0_stop_writes_trigger = 36;             // L0 36 个文件时停写
    opts.max_bytes_for_level_base = 512 * 1024 * 1024; // L1 基准大小 512MB
    opts.max_bytes_for_level_multiplier = 10;          // 每层 10 倍增长
    opts.num_levels = 4;                               // 4 层（减少写放大）

    // === Compaction ===
    opts.compaction_style = rocksdb::kCompactionStyleLevel;  // Leveled
    opts.level_compaction_dynamic_level_bytes = true;

    // === 缓存 ===
    opts.block_cache = rocksdb::NewLRUCache(1 * 1024 * 1024 * 1024LL); // 1GB
    opts.compression = rocksdb::kSnappyCompression;

    return opts;
}

// 写放大计算
// WAL(1x) + Flush(1x) + Compaction(level_ratio × num_levels)
// = 1 + 1 + (10 × 3) = 32x（优化前）
// 优化后: write_buffer=256MB, level_ratio=5, num_levels=3
// = 1 + 1 + (5 × 2) = 12x
```

#### 追问: Compaction 抖动怎么优化？

```
问题: RocksDB Compaction 时 IO 暴增，导致 P99 延迟飙升 50%

优化方案（KeyDB 实战）:
  1. 限速: 设置 compaction_rate_limit = 200MB/s
  2. 预创建: 提前做 minor compaction，避免峰值合并
  3. 拆分 SST 文件大小: target_file_size_base = 64MB（减少单次合并量）
  4. 关闭 direct IO: use_direct_io_for_flush_and_compaction = false

结果: Compaction 抖动从 50% 降到 < 10%
```

### Q4: 写放大怎么计算和优化？

```
定义: 实际写入磁盘量 ÷ 应用写入量

组成:
  ├── WAL: 1x
  ├── Flush: 1x
  └── Compaction: 10-20x

优化:
  ├── 增大 write_buffer_size (64MB→512MB)
  ├── 减小 level_ratio (10→5)
  └── 减少层级 (4→3层)
```

```
面试话术:
  "写放大是 LSM-Tree 的天生缺陷。
   比如你写 1KB 数据到 RocksDB，可能引起 compaction，
   最终磁盘写了 20KB，写放大 = 20x。
   优化的核心思路是: 减少 compaction 次数。
   增大 write_buffer_size 让 memtable 更大再 flush，
   减小 level_ratio 让每层增长更慢，
   减少层级直接减少 compaction 链路长度。
   我们项目从 4 层减到 3 层，写放大从 32x 降到 12x。"
```

### Q5: 存算分离怎么保证数据不丢？

```
1. 本地 WAL 双写（RocksDB 默认）
2. 元数据事务（OBS 写入成功后 Etcd 事务更新）
3. OBS 多版本控制
4. 跨 AZ 复制 + Etcd Raft 多数派
5. 定期 Checksum 校验
```

```
面试话术:
  "存算分离的'不丢'分两层:
   第一层: 写入先写本地 WAL 保证不丢（RocksDB 默认）。
   第二层: OBS 有 99.999999999% 持久性，多版本控制防误删。
   真正难的是元数据一致性:
   Etcd 事务保证 'OBS 写入成功' 和 '元数据更新' 原子完成。
   如果只写了 OBS 但 Etcd 没更新完就宕机，
   重启后扫描 OBS 恢复元数据。"
```

### Q6: Redis 和 KeyDB 的区别？

| 维度 | 原生 Redis | KeyDB（华为云） |
|------|-----------|----------------|
| 存储 | 全内存 | 热内存 + 冷 OBS |
| 成本 | 高 | 降 30% |
| 弹性 | 慢 | 快（加计算节点） |
| 一致性 | 主从异步复制 | Etcd + OBS 强一致 |

```
面试话术:
  "KeyDB 不是替代 Redis，而是拓展 Redis 的能力边界。
   Redis 场景: 全内存，微秒级延迟，适合缓存/会话等热数据。
   KeyDB 场景: 内存+OBS，毫秒级延迟，适合冷热混合。
   选哪个？有钱上 Redis，要省钱上 KeyDB。
   关键 trade-off: KeyDB 的冷数据多 10-50ms 延迟，
   但成本降 30%+，弹性秒级，一致性更强（Etcd 强一致 vs Redis 异步复制）。"
```

## 三、面试故事框架（STAR 格式）

### 华为云 KeyDB 故事

```
S（情境）: 华为云 Redis 服务使用纯 SSD，成本高（全内存），利用率不均
T（任务）: 实现存算分离，冷数据上 OBS，成本降 30% 以上，性能不降太多

A（行动）:
  ├── 存储引擎: RocksDB 作为本地缓存（热数据），OBS 作为持久层（冷数据）
  ├── 读流程: 先查 RocksDB → 没命中查 OBS → 回填 RocksDB（LRU 淘汰）
  │     └── 优化: 异步预取（发现读 OBS 时，预取相邻 key）
  ├── 写流程: 先写 RocksDB WAL → 异步写 OBS（WriteBatch 合并）
  │     └── 优化: 双写 + Etcd 事务保证元数据一致
  ├── Compaction 调优:
  │     ├── write_buffer_size: 64MB → 256MB（减少 flush 次数）
  │     ├── level_ratio: 10 → 5（减小写放大）
  │     └── num_levels: 4 → 3（减少层级）
  └── OBS 延迟优化:
        ├── 连接池（100 个连接复用）
        ├── 预取（发现读 OBS 时预取相邻 key）
        └── 多级缓存（RocksDB + 本地 LRU + OBS，三层穿透保护）

R（结果）:
  ├── QPS 10 万+（全内存 15 万，存算分离 10 万，差距可接受）
  ├── 成本降 30%（冷数据存 OBS 比 SSD 便宜 60%）
  ├── 可用性 99.99%（OBS 跨 AZ + Etcd 多数派）
  ├── Compaction 抖动从 50% 降到 < 10%
  └── 内存从 16GB 降到 8GB（冷数据不占内存）

追问从容应对:
  Q1: OBS 延迟变大怎么办？
  A: 多级缓存兜底。RocksDB 是 L1 缓存（毫秒级），本地 LRU 是 L2（微秒级），
     OBS 是冷存储（几十毫秒）。命中率 95%+ 在 L1，OBS 访问很少。

  Q2: OBS 数据一致性怎么保证？
  A: Etcd 事务记录元数据 + OBS 多版本控制。写入先写 RocksDB 本地，
     再异步写 OBS 并同步更新 Etcd。Etcd Raft 保证多数派一致。

  Q3: 和原生 Redis 比差距在哪？
  A: 热数据性能几乎一样（微秒级），冷数据多 10-50ms 的 OBS 延迟。
     但成本降 30%+，弹性扩缩容秒级（加计算节点即可，不用迁移数据）。
```

### 腾讯云 Tendis 故事

```
S（情境）: 腾讯云 CKV（Redis）集群冷热数据混合，成本高
T（任务）: 实现冷热分离 + 跨 AZ 容灾

A（行动）:
  ├── 热数据存 Redis（内存），冷数据存 RocksDB（SSD）
  ├── 冷热自动迁移（访问频率判断，7 天无访问下沉）
  ├── 跨 AZ 复制（WAL 实时同步 + 异步复制）
  └── 容灾切换（30s 自动检测 + 10s 切换）

R（结果）: 内存成本降 50%，AZ 故障 RTO < 60s
```
