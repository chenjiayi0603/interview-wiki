### 你简历上的核心项目

1. 华为云 KeyDB/Redis 开发

Q: Redis为什么快？
- 内存操作：所有数据在内存，读写延迟在纳秒级，避免磁盘IO瓶颈
- 单线程处理命令：无锁竞争，无线程上下文切换，CPU缓存命中率高
- IO多路复用：epoll监听大量连接，一个线程处理数万并发请求
- 高效数据结构：SDS、跳表、压缩列表等均针对场景精心设计

Q: KeyDB多线程和Redis单线程的区别？为什么要多线程？
- Redis 6.0之前命令处理完全单线程，IO也在主线程；6.0+引入多线程IO但命令执行仍单线程
- KeyDB是Redis的多线程fork，采用多个主线程（multi-master），每个线程独立处理命令，线程间通过锁同步共享数据
- 为什么要多线程：单线程无法充分利用多核CPU；当网络IO成为瓶颈时（高并发小对象），多线程IO可显著提升吞吐量；KeyDB实测在多核下性能可达Redis的2-5倍
- 代价：引入锁竞争和上下文切换，代码复杂度大幅增加，调试难度高

Q: 持久化方案对比（RDB vs AOF）
| 对比项 | RDB | AOF |
|--------|-----|-----|
| 原理 | fork子进程做内存快照写文件 | 记录每条写命令追加到文件 |
| 文件大小 | 小，压缩二进制 | 大，文本命令 |
| 恢复速度 | 快，直接加载 | 慢，需要重放命令 |
| 数据安全 | 差，可能丢失最后一次快照后的数据 | 好，最多丢1秒（everysec配置） |
| 性能影响 | fork时内存翻倍风险（COW） | 每次写命令追加，everysec影响小 |
| 适用场景 | 备份、可接受少量数据丢失 | 高数据安全要求 |
- 混合持久化（4.0+推荐）：AOF重写时前半段用RDB格式，后半段追加增量AOF，兼顾恢复速度和数据安全

Q: 集群方案（主从、哨兵、Cluster）
- 主从复制：主写从读，异步复制（SYNC/PSYNC），主宕机需手动切换，单点写瓶颈
- 哨兵（Sentinel）：在主从基础上，Sentinel进程监控主从健康，自动故障转移（选新主），提供服务发现；Sentinel本身也需要奇数部署防脑裂
- Cluster（分片集群）：16384个哈希槽，每个节点负责部分槽，支持水平扩展；客户端通过MOVED/ASK重定向；多主多从，可用性更高；不支持多key跨槽操作

Q: 缓存穿透/击穿/雪崩怎么解决？
- 穿透：查询不存在的key，每次都穿透缓存打到DB
  - 布隆过滤器：拦截一定不存在的key（允许极低false positive）
  - 缓存空值：将DB查询结果为空也缓存，设置短过期时间（如60秒）
- 击穿：单个热点key过期，瞬间大量并发请求打DB
  - 互斥锁（setnx）：只允许一个请求重建缓存，其他等待
  - 热点key永不过期：逻辑过期（value里存过期时间，后台异步更新）
- 雪崩：大量key同时过期，或Redis宕机，流量全部打DB
  - 过期时间加随机抖动：避免同时失效
  - Redis高可用：主从+哨兵或Cluster
  - 服务降级+限流：DB扛不住时返回降级数据

2. 服务网格（Istio）

Q: 服务网格解决了什么问题？
- 传统微服务将服务治理逻辑（重试、限流、熔断、链路追踪、mTLS）耦合在业务SDK里
- 服务网格将这些能力下沉到基础设施层（Sidecar代理），业务代码零感知
- 解决：跨语言治理（Java/Go/C++统一策略）、SDK升级困难、治理逻辑分散难运维

Q: Sidecar模式原理
- 每个Pod注入一个Envoy代理容器（Sidecar），与业务容器共享网络命名空间
- Istio控制面（Pilot）下发xDS配置给Envoy（路由、负载均衡、熔断策略）
- 所有入站/出站流量都经过Envoy，Envoy透明处理：认证、加密、遥测、流量管理
- 业务代码只需访问localhost，完全无感知

Q: Envoy如何拦截流量？（iptables + 透明代理）
- init容器启动时配置iptables规则：将所有出站流量（OUTPUT链）重定向到15001端口（Envoy出站监听），入站流量重定向到15006端口
- iptables使用REDIRECT目标，透明代理无需业务代码感知
- Envoy通过SO_ORIGINAL_DST socket选项获取原始目标地址，正确转发
- 特殊处理：Envoy自身流量、健康检查流量通过UID/GID规则排除（避免死循环）

Q: 和传统微服务框架的区别？
| 对比项 | 传统框架（Spring Cloud/Dubbo） | 服务网格（Istio） |
|--------|-------------------------------|-------------------|
| 治理位置 | 应用内SDK | 基础设施Sidecar |
| 语言限制 | 绑定特定语言/框架 | 语言无关 |
| 升级方式 | 需重新发布业务服务 | 运维侧滚动更新Sidecar |
| 性能开销 | 低（进程内） | 稍高（本地回环网络） |
| 运维复杂度 | 低 | 高（需要Kubernetes支持） |

3. 分布式IM系统

Q: 消息可靠性如何保证？（ACK机制+重试+持久化）
- 发送确认（ACK）：客户端发消息后等待服务端ACK；超时未收到则按指数退避重试（防刷）
- 服务端去重：消息携带client_msg_id（客户端生成唯一ID），服务端用Redis/DB记录已处理ID，幂等处理重复消息
- 消息持久化：写入MQ（Kafka）再写DB，MQ宕机时有DB兜底；使用消息序号(seq)标识顺序
- 接收确认：服务端向接收方推送消息后，等待接收方ACK；接收方上线时拉取离线消息

Q: 消息顺序如何保证？（单队列+顺序写入）
- 单会话单队列：同一个会话（chatID）的消息路由到同一个MQ分区（Kafka按chatID分区），保证单会话内顺序
- 服务端分配序号：服务端为每条消息分配全局递增序号（seq），客户端按seq排序展示
- 客户端乱序处理：客户端发现seq不连续时，请求补全缺失消息再展示
- 群消息：群ID作为路由key，同一群消息进同一分区

Q: 如何处理海量连接？（epoll + 连接池）
- 长连接+epoll：使用TCP长连接，服务端用epoll（Linux）实现IO多路复用，单机可维持10W+连接
- 连接分层：接入层（Gateway）专门维护连接，逻辑层（Business）处理业务，通过内部RPC通信
- 连接信息存Redis：userID -> gatewayID + connID，推送消息时先查Redis定位接入节点
- 心跳保活：客户端定时发心跳（30s），服务端检测超时断开，释放资源

Q: 在线状态如何维护？（心跳+Redis）
- 用户连接时在Redis写入 `online:{uid}` = `{gateway_id, conn_id, login_time}`，设置TTL（如60s）
- 客户端每30s发心跳，服务端收到后刷新Redis TTL
- 断线检测：心跳超时未到，Redis key自动过期，用户变为离线
- 查询在线状态：直接查Redis，O(1)；批量查询用MGET
- 多端在线：key改为 `online:{uid}:{device_type}`，支持手机/PC同时在线

## 三、高频八股文速记（必背清单）

### C++ 核心必背（20题）

1. 智能指针
- `unique_ptr`：独占所有权，不可拷贝，可移动（move转让），析构时自动释放，零开销
- `shared_ptr`：引用计数（控制块），多个指针共享同一对象，引用计数归零时释放；线程安全指计数本身，不保护对象访问
- `weak_ptr`：不增加引用计数，通过`lock()`获取`shared_ptr`（可能失败返回空），专门解决循环引用导致的内存泄漏

2. 虚函数原理
- 每个含虚函数的类有一张虚函数表（vtable），存储虚函数指针数组，编译期生成
- 每个对象头部有一个虚表指针（vptr），指向对应类的vtable，构造时初始化
- 调用虚函数：通过vptr找vtable，再按偏移找函数指针，间接调用 → 运行时多态
- 纯虚函数：`= 0`，vtable对应项为nullptr，含纯虚函数的类为抽象类，不可实例化

3. 内存布局
- 栈区：局部变量、函数参数，由编译器自动管理，地址从高到低增长，大小有限（默认几MB）
- 堆区：`new`/`malloc`分配，程序员手动管理（或RAII），地址从低到高，大小受限于物理内存
- 全局/静态区：全局变量、static变量，程序整个生命周期存在，BSS段（未初始化）+ Data段（已初始化）
- 代码区：存储程序指令，只读，多进程可共享同一代码段
- 常量区：字符串字面量等，只读，尝试修改会段错误

4. new/delete vs malloc/free
- `malloc`/`free`是C库函数；`new`/`delete`是C++运算符
- `new`：分配内存 + 调用构造函数；`delete`：调用析构函数 + 释放内存
- `malloc`失败返回`NULL`；`new`失败抛出`std::bad_alloc`异常
- `new`/`delete`支持运算符重载，可自定义内存管理策略（如内存池）
- 不可混用：`new[]`分配的必须用`delete[]`释放（否则只析构第一个元素）

5. 移动语义
- 右值引用（`T&&`）：绑定到临时对象（右值），不延长其生命周期
- 移动构造函数：从右值"偷取"资源（如指针直接赋值），将原对象置空，避免深拷贝，O(1)开销
- `std::move()`：将左值强转为右值引用，告诉编译器"这个对象可以被移走"
- 完美转发：`std::forward<T>`在模板中保持值类别（左值/右值）不变

6. RAII（Resource Acquisition Is Initialization）
- 构造函数中获取资源（内存、文件句柄、锁），析构函数中释放
- 异常安全：栈展开时析构函数一定被调用，资源不会泄漏（比手动try-catch可靠）
- 典型例子：`unique_ptr`（内存）、`lock_guard`/`unique_lock`（互斥锁）、`fstream`（文件）
- C++ Core Guidelines：几乎所有资源管理都应通过RAII

7. 指针 vs 引用
| 特性 | 指针 | 引用 |
|------|------|------|
| 是否可空 | 可以为nullptr | 必须绑定合法对象 |
| 重新绑定 | 可以随时改变指向 | 初始化后不可重绑定 |
| 算术运算 | 支持（+/-/++/--） | 不支持 |
| sizeof | 指针自身大小（4/8字节） | 所绑定对象的大小 |
| 底层实现 | 独立存储地址的变量 | 编译器通常用指针实现，但对程序员透明 |
- 优先用引用（更安全），必要时用指针（可空、可重绑定）

8. static作用
- 全局静态变量/函数：限制在本文件内可见（内部链接），防止与其他文件命名冲突
- 局部静态变量：只在第一次执行时初始化，生命周期到程序结束；C++11起线程安全（编译器加锁）
- 静态成员变量：属于类，所有对象共享，必须在类外定义并初始化
- 静态成员函数：没有`this`指针，只能访问静态成员，可通过类名直接调用

9. const作用
- `const int a`：常量，值不可修改
- `const int* p`：指向常量的指针，`*p`不可改，`p`可以改指向（顶层const在右）
- `int* const p`：常量指针，`p`不可改指向，`*p`可改（底层const在左）
- `const int* const p`：既不能改指针也不能改值
- `const`成员函数：`void foo() const`，`this`是`const`指针，不能修改成员，可被`const`对象调用

10. volatile
- 防止编译器将变量优化缓存到寄存器，确保每次访问都从内存读取
- 使用场景：内存映射IO寄存器、信号处理器修改的变量、多线程中某些标志位
- 注意：`volatile`不保证原子性，也不提供内存屏障，线程同步仍需`mutex`或`atomic`
- C++11后多线程场景推荐用`std::atomic`代替`volatile`

11. lambda原理
- 编译器将lambda表达式转换为匿名类（仿函数），`operator()`实现函数体
- 捕获列表对应构造函数参数：`[=]`值捕获（复制为成员），`[&]`引用捕获
- `std::function`使用类型擦除存储lambda，有虚函数调用开销；直接传lambda给模板函数零开销
- 注意悬空引用：引用捕获局部变量后，lambda生命周期不能超过变量

12. vector扩容
- `push_back`时若`size == capacity`则触发扩容：分配新内存（通常2倍）→ 移动/拷贝元素 → 释放旧内存
- 扩容导致所有迭代器/指针/引用失效（内存地址变了）
- `reserve(n)`：预分配容量，避免多次扩容；`shrink_to_fit()`释放多余容量
- 插入中间元素也会使插入点后的迭代器失效（元素移动）

13. map vs unordered_map
| 对比项 | map | unordered_map |
|--------|-----|---------------|
| 底层 | 红黑树 | 哈希表（链表法解决冲突） |
| 查找/插入/删除 | O(log n) | 平均O(1)，最坏O(n) |
| 元素顺序 | 按key有序 | 无序 |
| key要求 | 需要`<`运算符 | 需要hash函数和`==`运算符 |
| 内存 | 每节点独立分配，碎片多 | 哈希表+桶数组 |
- 需要有序遍历/范围查询用`map`；高频随机查找用`unordered_map`

14. 内存泄漏检测
- Valgrind（Linux）：`valgrind --leak-check=full ./program`，运行时检测，无需重编译，慢约10-50倍
- AddressSanitizer（ASan）：编译时加`-fsanitize=address`，运行时检测，速度比Valgrind快，推荐开发阶段使用
- LeakSanitizer（LSan）：比ASan更专注泄漏，可单独使用`-fsanitize=leak`
- 自定义：重载`new`/`delete`记录分配，程序结束时输出未释放列表

15. 死锁条件（四个必要条件）
- 互斥：资源一次只能被一个进程使用
- 占有等待：进程持有已获得资源，同时等待新资源
- 不可抢占：已分配的资源只能由持有者主动释放
- 循环等待：进程间存在资源等待环（A等B、B等A）
- 预防：按固定顺序获取锁（破循环等待）、超时`try_lock`（破占有等待）、一次性获取所有锁

16. 线程同步
- `mutex`：互斥锁，同时只有一个线程持有；配合`lock_guard`（RAII，不可中途解锁）或`unique_lock`（可中途解锁，配合条件变量）
- `condition_variable`：条件变量，`wait(lock, pred)`原子释放锁并阻塞，`notify_one`/`notify_all`唤醒；解决生产者-消费者问题
- `atomic<T>`：原子操作，无锁，底层CAS或特定CPU指令，适合简单计数器/标志
- `shared_mutex`（C++17）：读写锁，多读单写，`shared_lock`读，`unique_lock`写

17. CAS原理
- Compare-And-Swap：`if (*addr == expected) { *addr = new_val; return true; } else { expected = *addr; return false; }`
- 硬件原子指令：x86的`CMPXCHG`，ARM的`LDREX/STREX`
- ABA问题：值从A→B→A，CAS认为未变化但实际已改变；解决：加版本号（`AtomicStampedReference`）
- 自旋：CAS失败后循环重试；高竞争时CPU浪费，低竞争时比mutex快
- C++的`std::atomic::compare_exchange_weak/strong`

18. 内存序（Memory Order）
- relaxed：只保证操作本身原子性，不限制重排，适合独立计数器
- acquire：读操作，之后的所有操作不得重排到此读之前（配合release同步）
- release：写操作，之前的所有操作不得重排到此写之后（配合acquire同步）
- seq_cst：顺序一致，最强保证，所有线程看到相同的全局操作顺序，是默认值，性能最低
- 典型用法：producer用release写，consumer用acquire读，建立happens-before关系

19. 设计模式
- 单例（双重检查锁定）：先判空→加锁→再判空→创建；C++11更简单：局部静态变量线程安全（推荐）
- 工厂模式：将对象创建与使用分离，客户端通过工厂接口创建对象，新增类型只需新增工厂，符合开闭原则
- 观察者模式：Subject维护Observer列表，状态变化时`notify()`遍历调用所有Observer的`update()`，发布-订阅的基础
- 策略模式：将算法封装为独立类（Strategy接口），运行时通过组合切换算法，避免大量if-else

20. STL容器底层实现
- `vector`：动态数组，连续内存，随机访问O(1)，尾部操作摊销O(1)，中间插入O(n)
- `list`：双向链表，非连续内存，随机访问O(n)，任意位置插入删除O(1)，不支持随机访问迭代器
- `deque`：分段连续内存（页表），头尾操作O(1)，中间插入O(n)，`stack`/`queue`的默认底层容器
- `map`/`set`：红黑树（自平衡BST），所有操作O(log n)，元素有序
- `unordered_map`/`unordered_set`：哈希表，平均O(1)，负载因子超1时rehash

### Go 核心必背（15题）

1. GMP模型
- G（Goroutine）：Go的轻量级协程，初始栈2KB（可动态增长），由Go runtime管理，可创建百万级
- M（Machine）：操作系统线程，真正在CPU上执行G，数量默认不超过10000
- P（Processor）：逻辑处理器，维护本地G队列（runq），M必须绑定P才能执行G，数量由`GOMAXPROCS`决定（默认=CPU核数）
- 调度流程：G优先从P的本地队列取，没有则从全局队列或其他P偷（work-stealing）

2. Channel原理
- 底层是`hchan`结构：环形缓冲区（buf）+ 发送等待队列（sendq）+ 接收等待队列（recvq）+ 互斥锁
- 无缓冲：发送方必须等待接收方就绪（同步），反之亦然
- 有缓冲：buf未满时发送不阻塞，buf非空时接收不阻塞
- `close(ch)`后仍可读取残留数据；再读返回零值和`false`；向已关闭channel发送会`panic`

3. Slice底层
- `SliceHeader`：`{ptr *array, len int, cap int}`，是数组的视图
- 多个切片可共享底层数组，子切片修改会影响原切片
- `append`超过cap时：分配新数组 → 复制数据 → 返回指向新数组的切片，不影响原切片
- `copy(dst, src)`：安全拷贝，避免共享底层数组的副作用

4. Map底层
- `hmap`结构：桶数组（每桶8个kv对）+ 溢出桶链表 + 元数据（count、B、flags）
- 扩容条件：负载因子 > 6.5（翻倍扩容）或溢出桶过多（等量扩容整理碎片）
- 渐进式扩容：写操作时每次迁移最多2个旧桶，避免一次性迁移阻塞；迁移未完成时读写两个桶
- 并发不安全：并发读写会panic，需用`sync.RWMutex`或`sync.Map`

5. Defer执行
- 函数返回前按LIFO（后进先出）顺序执行所有defer
- defer参数在defer语句执行时立即求值（值拷贝），函数体延迟执行
- 通过闭包可以访问并修改命名返回值（实现defer修改返回值的技巧）
- `panic`时defer仍会执行，可以在defer中用`recover()`捕获panic

6. Panic/Recover
- `panic`：触发运行时错误，开始栈展开（unwind），依次执行当前goroutine各层函数的defer
- `recover()`：只在`defer`中有效，调用后捕获panic值，阻止程序崩溃，函数正常返回
- 跨goroutine：panic只在当前goroutine传播，子goroutine的panic无法被父goroutine recover
- 最佳实践：库函数内部panic转为error返回；HTTP handler的顶层defer recover防止单请求crash整个服务

7. Interface原理
- `eface`（空接口`interface{}`）：`{_type *_type, data unsafe.Pointer}`，仅存类型描述符和数据指针
- `iface`（非空接口）：`{tab *itab, data unsafe.Pointer}`，`itab`包含接口类型、具体类型、方法指针数组（缓存加速）
- 接口判nil的坑：`var p *MyStruct = nil; var i interface{} = p`，`i != nil`为true（接口有类型信息）
- 类型断言：`v, ok := i.(T)`；类型switch：`switch v := i.(type)`

8. GC算法
- 三色标记：白色（未访问，初始全白）→ 灰色（已发现，子节点未处理）→ 黑色（已完全处理）；GC结束后白色对象回收
- 混合写屏障（go1.14+）：对象赋值时触发，保证标记期间新建/修改的引用不丢失，减少STW时间
- 并发执行：标记阶段与用户程序并发，只有STW（Stop The World）极短暂（通常<1ms）
- 触发GC：堆内存达到上次GC后2倍 or 距上次GC超2分钟 or 手动`runtime.GC()`

9. 内存分配
- 类tcmalloc思想：对象按大小分级（tiny/small/large），不同级别不同策略
- mcache：每个P持有，本地span缓存，无锁分配，对应不同size class
- mcentral：全局按size class管理span列表，mcache耗尽时从此申请，需加锁
- mheap：直接向OS申请内存页，管理大对象（>32KB）和给mcentral补充span

10. Goroutine泄露
- channel阻塞：goroutine等待永远不来的数据或向无人接收的channel发送
- 定时器泄露：循环中用`time.After()`，每次创建新Timer，应改用`time.NewTimer()`+Reset
- WaitGroup误用：`Add`/`Done`数量不匹配，`Wait()`永久阻塞
- 检测工具：`pprof` goroutine profile（`go tool pprof`）；线上用`runtime.NumGoroutine()`监控增长趋势

11. Context用途
- 超时/截止时间：`WithTimeout`/`WithDeadline`，子goroutine通过`ctx.Done()`感知超时取消
- 主动取消：`WithCancel`返回cancel函数，调用cancel后所有子context的Done关闭
- 请求作用域值：`WithValue`存储请求ID、traceID等，不应存业务数据（无类型安全）
- 约定：context作第一个参数，命名`ctx`，不要存入struct字段，传递而非存储

12. Sync包
- `Mutex`：互斥锁；正常模式（FIFO+自旋）和饥饿模式（等待超1ms直接获得锁）自动切换
- `RWMutex`：读写锁，多goroutine可同时持有读锁，写锁独占；写锁优先（防饥饿）
- `WaitGroup`：`Add(n)`→启动n个goroutine各自`Done()`→主goroutine`Wait()`阻塞直到全Done
- `Once`：`Do(f)`保证f只执行一次，即使并发调用；常用于懒初始化单例
- `Pool`：临时对象池，GC时可能回收；减少频繁分配/GC压力，如`bytes.Buffer`池

13. Go调度
- 工作窃取（work-stealing）：P本地队列空时，随机选其他P偷一半G，充分利用多核
- 协作式抢占（go1.14前）：只在函数调用时检查抢占标志，死循环无法被抢占
- 基于信号的异步抢占（go1.14+）：`SIGURG`信号强制抢占，解决无函数调用时的CPU占用问题
- 全局队列：当本地队列满（256个）时放入全局队列；M启动时也检查全局队列

14. 切片扩容规则
- go1.18之前：期望容量 < 1024时，新cap = 旧cap×2；≥1024时，新cap = 旧cap×1.25（循环直到足够）
- go1.18+：新算法，阈值改为256，增长更平滑（防止256附近突变）
- 扩容后进行内存对齐，实际cap可能比计算值大（如期望5，实际分配8）
- 扩容产生新底层数组，原切片不受影响（两者独立）

15. make vs new
- `new(T)`：为T分配零值内存，返回`*T`指针；适用于任何类型；类似C的`calloc`
- `make(T, args)`：仅用于slice/map/channel，初始化内部数据结构（如map的哈希桶），返回T本身（非指针）
- `make([]int, 5, 10)`：长度5容量10的切片，元素初始化为0
- `make(map[K]V)`：必须make后才能赋值，否则nil map赋值会panic

### 数据库必背（10题）

1. MySQL索引
- B+树：内节点只存key，叶子节点存完整数据（聚簇索引）或主键（非聚簇），叶子节点双向链表，高效范围查询
- 聚簇索引：以主键建立，叶子节点是完整行数据，InnoDB必须有且只有一个
- 非聚簇索引（二级索引）：叶子节点存主键值，查找数据需回表（再查聚簇索引）
- 覆盖索引：查询所需列都在索引中，无需回表（explain中Extra显示`Using index`）
- 最左前缀原则：复合索引(a,b,c)，查询必须从a开始，中间不能断，否则右侧索引失效

2. 事务隔离级别
| 级别 | 脏读 | 不可重复读 | 幻读 |
|------|------|-----------|------|
| 读未提交 | ✓ | ✓ | ✓ |
| 读已提交（Oracle默认） | ✗ | ✓ | ✓ |
| 可重复读（MySQL默认） | ✗ | ✗ | ✓（InnoDB通过MVCC+间隙锁解决） |
| 串行化 | ✗ | ✗ | ✗ |

3. MVCC原理
- 每行有隐藏字段：`trx_id`（最后修改的事务ID）、`roll_pointer`（指向undo log的指针）
- 版本链：undo log通过roll_pointer串联历史版本，形成链表
- ReadView：记录当前活跃事务ID列表（未提交的），用于判断哪个版本对当前事务可见
  - RC（读已提交）：每次SELECT生成新ReadView → 能看到其他事务已提交的修改
  - RR（可重复读）：只在事务第一次SELECT时生成ReadView → 整个事务内读到一致的快照

4. 锁类型
- 行锁（Record Lock）：锁定一条索引记录，InnoDB支持，并发性高
- 间隙锁（Gap Lock）：锁定索引间的区间（不含记录本身），防止幻读，RR级别生效
- 临键锁（Next-Key Lock）：行锁+前面的间隙锁，InnoDB RR级别的默认锁，范围查询时使用
- 表锁：MyISAM/DDL操作，并发极低，偶尔无索引时InnoDB也会退化为表锁
- 死锁：InnoDB自动检测，回滚代价较小的事务；`innodb_lock_wait_timeout`超时也会回滚

5. 慢查询优化
- EXPLAIN分析：重点看`type`（最好ref/eq_ref，避免ALL全表扫描）、`key`（是否用到索引）、`rows`（扫描行数）、`Extra`（Using filesort/temporary要优化）
- 加索引：WHERE/JOIN ON/ORDER BY/GROUP BY的字段；注意选择性（区分度）要高
- 避免索引失效：索引列上不做函数/计算/类型转换；不用`!=`/`NOT IN`/前缀`%like`
- 分页优化：大OFFSET用游标分页（`WHERE id > last_id LIMIT 20`）或延迟关联

6. Redis数据类型
| 类型 | 底层编码 | 典型场景 |
|------|---------|---------|
| String | SDS（int/embstr/raw） | 缓存、计数器、分布式锁 |
| List | ziplist（小）/quicklist（大） | 消息队列、最新列表 |
| Hash | ziplist（小）/hashtable（大） | 对象存储、购物车 |
| Set | intset（整数小集合）/hashtable | 标签、去重、交并差集 |
| ZSet | ziplist（小）/skiplist+hashtable（大） | 排行榜、延迟队列 |

7. Redis持久化
- RDB：`BGSAVE`fork子进程做快照（COW机制不阻塞主进程），文件紧凑恢复快，但可能丢失最后一次快照后的数据
- AOF：记录每条写命令，`appendfsync`配置：`always`（每条都fsync，最安全）、`everysec`（每秒，最多丢1秒，推荐）、`no`（OS决定）
- AOF重写（BGREWRITEAOF）：将内存当前状态转为最小命令集，压缩AOF文件
- 混合持久化（4.0+）：AOF重写时前部分为RDB二进制，后部分追加增量命令，兼顾文件小+安全性高

8. Redis集群
- 主从复制：`SYNC`全量 → `PSYNC`增量（断线重连时）；异步复制，主宕机需手动干预；读写分离降低主节点压力
- 哨兵（Sentinel）：≥3个Sentinel监控主从，主观下线→客观下线（多数派确认）→选举新主自动故障转移；客户端通过Sentinel获取主节点地址
- Cluster：16384槽按CRC16(key)%16384分配；`MOVED`错误重定向到正确节点；每个主节点可有从节点，支持水平扩展；不支持跨槽多key操作

9. 缓存问题
- 穿透（key根本不存在）：布隆过滤器拦截（允许极低误判率）；或缓存空值+短TTL
- 击穿（热点key过期，并发重建）：互斥锁（`SET lock NX PX`）只允许一个请求重建，其他等待；逻辑过期（key永不过期，value存过期时间，后台异步更新）
- 雪崩（大量key同时过期或Redis宕机）：TTL加随机抖动；Redis高可用集群；请求限流+服务降级；多级缓存（本地缓存兜底）

10. Redis为什么快
- 内存操作：读写内存，纳秒级延迟，比磁盘快10万倍
- 单线程命令处理：无锁竞争，无线程切换开销，CPU缓存局部性好（go1.6前，6.0+引入多线程IO）
- IO多路复用：epoll事件驱动，单线程监听数万连接，只处理就绪事件
- 高效数据结构：SDS避免strlen遍历，跳表O(logn)有序操作，ziplist节省内存减少缓存miss

### 分布式必背（10题）

1. CAP理论
- C（Consistency）：所有节点同时看到相同的最新数据
- A（Availability）：每次请求都得到响应（不保证是最新数据）
- P（Partition Tolerance）：网络分区（节点间通信失败）时系统继续运行
- 网络分区不可避免，实际系统选择CP或AP：Zookeeper选CP（一致性优先，分区时拒绝服务）；Eureka选AP（可用性优先，可能读到旧数据）

2. BASE理论
- 对强一致性CAP的妥协，适用于大规模分布式系统
- BA（Basically Available）：系统出现故障时，允许部分功能不可用（如降级、限流），核心功能仍可用
- S（Soft State）：允许系统存在中间状态，不同节点数据可以暂时不一致
- E（Eventually Consistent）：不要求实时一致，但最终（通常秒级）会达到一致；比强一致性更高的可用性和性能

3. 一致性算法
- Paxos：提案者(Proposer)/接受者(Acceptor)/学习者(Learner)；两阶段：Prepare阶段获得承诺+Accept阶段提交值；难理解难实现
- Raft：比Paxos更易理解，分为三个子问题：
  - Leader选举：term任期+随机超时，Follower超时未收心跳发起选举，获多数票成为Leader
  - 日志复制：Leader接收请求，AppendEntries同步到多数Follower后提交（commit），返回客户端
  - 安全性：选举限制（只有日志最新的节点才能成为Leader）保证已提交日志不丢失

4. 分布式锁
- Redis：`SET key value NX PX timeout`，value用UUID防误删；问题：主从切换时锁可能丢失
  - Redlock：向N个独立Redis节点申请锁，多数（N/2+1）成功才算获锁，解决单点问题
- Zookeeper：创建临时顺序节点，序号最小的节点获得锁；客户端宕机会话超时自动释放（临时节点删除）；Watch前一个节点避免惊群效应
- etcd：基于Raft强一致，租约（lease）机制自动过期，revision保证公平；比ZK API更简洁

5. 分布式事务
- 2PC（两阶段提交）：协调者Prepare→各参与者回复yes/no→协调者Commit/Rollback；问题：协调者故障时参与者阻塞，性能低
- TCC：Try（预留资源）→Confirm（确认提交）→Cancel（回滚），业务层实现补偿，需保证幂等
- Saga：长事务拆为多个本地事务，每步有对应补偿操作，失败时逆序执行补偿；最终一致
- 本地消息表：业务操作+写消息表在同一本地事务，MQ消费消息表实现异步最终一致，经典可靠方案

6. 消息队列
| 特性 | Kafka | RocketMQ | RabbitMQ |
|------|-------|----------|---------|
| 吞吐量 | 极高（百万/s） | 高（十万/s） | 一般（万/s） |
| 特色 | 顺序写磁盘+Page Cache，流处理 | 事务消息、延迟消息、消息追踪 | AMQP协议，Exchange路由，可靠 |
| 适用 | 日志收集、流计算 | 金融业务、订单 | 传统企业集成 |
- 消息不丢：生产者ACK确认 + broker刷盘 + 消费者手动ACK + 幂等消费

7. 服务发现
- etcd：基于Raft强一致，Watch机制实时感知变化，Kubernetes默认使用，适合对一致性要求高的场景
- Consul：内置健康检查（HTTP/TCP/gRPC），支持多数据中心，提供DNS接口，生态成熟
- Nacos：阿里开源，可在AP/CP模式切换（临时实例AP/持久实例CP），同时提供配置中心功能，国内使用广泛

8. 负载均衡
- 轮询：简单均匀，适合无状态同质服务
- 加权轮询：按配置权重分配，适合异构服务器（高配多分流量）
- 一致性哈希：相同key路由到相同节点，适合有状态服务（会话保持）；虚拟节点解决数据倾斜；节点增减只影响相邻区间（最小化数据迁移）
- 最少连接：选当前活跃连接数最少的节点，适合长连接、处理时间不均匀的场景

9. 限流算法
- 令牌桶：以固定速率向桶中放入令牌，请求消耗令牌；桶满时令牌溢出（允许短暂突发流量）；Guava `RateLimiter`
- 漏桶：请求进入漏桶队列，以固定速率处理（流出）；超出容量丢弃；严格平滑输出，不允许突发
- 滑动窗口：维护时间窗口内的请求计数，精度比固定窗口高（固定窗口有边界突刺问题）
- 实现：Redis+Lua原子脚本（防竞态）；Nginx的`limit_req_zone`；Sentinel的QPS控制

10. 熔断降级
- 熔断器状态机：
  - Closed（关闭）：正常，统计错误率
  - Open（打开）：错误率/响应时间超阈值，直接拒绝请求，快速失败
  - Half-Open（半开）：Open一段时间后，放入少量探测请求，成功则回到Closed，失败则回Open
- 降级策略：返回默认值/兜底数据；返回缓存旧数据；返回错误提示+引导重试
- Hystrix：线程池隔离（每个服务独立线程池，互不影响）或信号量隔离
- Sentinel：阿里开源，基于流量控制，轻量级，支持规则动态推送，更适合微服务

### 必会手写题（10道）

#### 1. 单例模式（双重检查锁定）⭐⭐⭐

```cpp
// 方法一：双重检查锁定（C++11需要加volatile或atomic）
class Singleton {
    static atomic<Singleton*> instance;
    static mutex mtx;
    Singleton() = default;
public:
    static Singleton* getInstance() {
        Singleton* p = instance.load(memory_order_acquire);
        if (!p) {
            lock_guard<mutex> lock(mtx);
            p = instance.load(memory_order_relaxed);
            if (!p) {
                p = new Singleton();
                instance.store(p, memory_order_release);
            }
        }
        return p;
    }
};

// 方法二：C++11局部静态（推荐，更简洁，线程安全由编译器保证）
class Singleton {
    Singleton() = default;
public:
    static Singleton& getInstance() {
        static Singleton instance;  // 第一次调用时初始化，线程安全
        return instance;
    }
    Singleton(const Singleton&) = delete;
    Singleton& operator=(const Singleton&) = delete;
};
```

```cpp
    vector<thread> workers;

    mutex mtx;
    condition_variable cv;
    bool stop = false;

public:
    explicit ThreadPool(size_t n) {
        for (size_t i = 0; i < n; i++) {
            workers.emplace_back([this] {
                while (true) {
                    function<void()> task;
                    {
                        unique_lock<mutex> lock(mtx);
                        cv.wait(lock, [this] { return stop || !tasks.empty(); });
                        if (stop && tasks.empty()) return;
                        task = move(tasks.front());
                        tasks.pop();
                    }
                    task();
                }
            });
        }
    }

    template<typename F>
    void submit(F&& f) {
        {
            lock_guard<mutex> lock(mtx);
            tasks.emplace(forward<F>(f));
        }
        cv.notify_one();
    }

    ~ThreadPool() {
        { lock_guard<mutex> lock(mtx); stop = true; }
        cv.notify_all();
        for (auto& w : workers) w.join();
    }
};
```

#### 3. LRU缓存 ⭐⭐⭐

```cpp
class LRUCache {
    int cap;
    list<pair<int, int>> cache;  // {key, val}，头部是最近使用
    unordered_map<int, list<pair<int, int>>::iterator> mp;

public:
    LRUCache(int capacity) : cap(capacity) {}

    int get(int key) {
        if (!mp.count(key)) return -1;
        // 移动到头部（最近使用）
        cache.splice(cache.begin(), cache, mp[key]);
        return mp[key]->second;
    }

    void put(int key, int val) {
        if (mp.count(key)) {
            mp[key]->second = val;
            cache.splice(cache.begin(), cache, mp[key]);
        } else {
            if ((int)cache.size() == cap) {
                // 淘汰尾部（最久未使用）
                mp.erase(cache.back().first);
                cache.pop_back();
            }
            cache.push_front({key, val});
            mp[key] = cache.begin();
        }
    }
};
```

```cpp
template<typename T>
class BlockingQueue {
    queue<T> q;
    mutex mtx;
    condition_variable not_empty, not_full;
    int cap;

public:
    explicit BlockingQueue(int capacity) : cap(capacity) {}

    void push(T item) {
        unique_lock<mutex> lock(mtx);
        not_full.wait(lock, [this] { return (int)q.size() < cap; });
        q.push(move(item));
        not_empty.notify_one();
    }

    T pop() {
        unique_lock<mutex> lock(mtx);
        not_empty.wait(lock, [this] { return !q.empty(); });
        T item = move(q.front());
        q.pop();
        not_full.notify_one();
        return item;
    }

    int size() {
        lock_guard<mutex> lock(mtx);
        return q.size();
    }
};
```

```cpp
void quickSort(vector<int>& arr, int l, int r) {
    if (l >= r) return;
    int pivot = arr[l + rand() % (r - l + 1)];
    int i = l, j = r, k = l;
    while (k <= j) {
        if (arr[k] < pivot) swap(arr[i++], arr[k++]);
        else if (arr[k] > pivot) swap(arr[k], arr[j--]);
        else k++;
    }
    quickSort(arr, l, i - 1);
    quickSort(arr, j + 1, r);

void merge(vector<int>& arr, vector<int>& buf, int l, int m, int r) {
    for (int i = l; i <= m; ++i) buf[i] = arr[i];
    int i = l, j = m + 1, k = l;  // i 左(在 buf) j 右(在 arr) k 写回头
    while (i <= m && j <= r)
        arr[k++] = (buf[i] <= arr[j]) ? buf[i++] : arr[j++];

    // 若左先耗尽：必有 k==j，右段 arr[j..r] 未动部分已在位，无第三段 while
}

    if (l >= r) return;

    mergeSort(arr, buf, m + 1, r);
    merge(arr, buf, l, m, r);
```

```cpp
void adjust(vector<int>& a, int l, int r) {
  // pi 暂存当前父节点的值，k 记录当前“洞”位置
  int pi = a[l], k = l;
  // 从当前父节点的左孩子开始下滤
  for (int i = 2 * l + 1; i <= r; i = 2 * i + 1) {
    // 如果右孩子存在且比左孩子大，指向右孩子
    if (i < r && a[i] < a[i + 1]) i++;
    // 如果父节点比最大的孩子还大，说明调整完成，直接break
    if (pi >= a[i]) break;
    // 否则，用较大的孩子填补父节点的位置
    a[k] = a[i];
    k = i; // “洞”移动到孩子节点
  }
  // 将最初暂存的父节点值放到最终的“洞”位置
  a[k] = pi;
}
void heapSort(vector<int>& a) {
  int n = (int)a.size();
  // 初始化构建大顶堆（从最后一个非叶子节点向上调整）
  for (int i = n / 2; i >= 0; --i) adjust(a, i, n - 1);
  // 每次取出堆顶（最大值）放到末尾，然后调整剩余部分为大顶堆
  for (int i = n - 1; i > 0; --i) {
    swap(a[0], a[i]);
    adjust(a, 0, i - 1);
  }
}
```

```cpp
int minRemoval(vector<vector<int>>& a) {
  if (a.empty()) return 0;
  sort(a.begin(), a.end(), [](const auto& x, const auto& y) {
    return x[1] < y[1];
  });
  int keep = 1, e = a[0][1];
  for (size_t i = 1; i < a.size(); ++i) {
    if (a[i][0] >= e) { ++keep; e = a[i][1]; }
  }
  return (int)a.size() - keep;
}
```

##### 二分查找 · 搜索旋转排序数组

```cpp
// 无重复
int search(vector<int>& a, int t) {
  int l = 0, r = a.size() - 1;
  while (l <= r) {
    int m = l + (r - l) / 2;
    if (a[m] == t) return m;
    if (a[l] <= a[m]) {
      if (a[l] <= t && t < a[m]) r = m - 1; else l = m + 1;
    } else {
      if (a[m] < t && t <= a[r]) l = m + 1; else r = m - 1;
    }
  }
  return -1;
}
```

##### 二分查找 · 寻找峰值

```cpp
// 任一侧比中间大就爬坡
int findPeakElement(vector<int>& a) {
  int l = 0, r = a.size() - 1;
  while (l < r) {
    int m = l + (r - l) / 2;
    if (a[m] < a[m + 1]) l = m + 1; else r = m;
  }
  return l;
}
```
