## 二、外企特色面试题

### Q1: C++20 协程 promise_type 机制？

```
promise_type 必须实现:
  ├── get_return_object() → 返回协程句柄包装
  ├── initial_suspend() → 创建后是否挂起
  ├── final_suspend() noexcept → 结束前挂起
  ├── return_void() / return_value() → co_return
  └── unhandled_exception() → 异常处理

执行流程:
  构造 → initial_suspend 挂起
    ↓ resume
  协程体 → co_await 挂起 → resume → 继续
    ↓
  final_suspend → 析构时 handle.destroy()
```

#### 完整协程示例（Thunder 框架）

```cpp
#include <coroutine>
#include <iostream>
#include <optional>

// 一个简单的 Task 协程类型
template<typename T>
struct Task {
    struct promise_type {
        std::optional<T> result_;
        std::coroutine_handle<> continuation_;

        Task get_return_object() {
            return Task{std::coroutine_handle<promise_type>::from_promise(*this)};
        }

        // 创建后立即执行（不挂起）
        std::suspend_never initial_suspend() { return {}; }

        // 结束后挂起（让调用方通过 handle 取结果）
        std::suspend_always final_suspend() noexcept {
            // 如果有 continuation，恢复它
            if (continuation_) continuation_.resume();
            return {};
        }

        void return_value(T value) {
            result_ = std::move(value);
        }

        void unhandled_exception() {
            std::terminate();
        }
    };

    using handle_type = std::coroutine_handle<promise_type>;
    handle_type handle_;

    T get_result() {
        if (!handle_.done()) handle_.resume();
        return std::move(*handle_.promise().result_);
    }

    ~Task() { if (handle_) handle_.destroy(); }
};

// 使用协程
Task<int> async_fetch_data() {
    std::cout << "协程开始执行...\n";
    co_await std::suspend_always{};  // 主动让出
    std::cout << "协程恢复执行...\n";
    co_return 42;
}

// Thunder 框架中的协程调度器
struct CoroutineScheduler {
    // 协程切换开销 < 50ns（对比线程切换 ~1μs）
    template<typename T>
    void schedule(Task<T>& task) {
        while (!task.handle_.done()) {
            task.handle_.resume();
        }
    }
};

// 使用
// int main() {
//     Task<int> task = async_fetch_data();
//     std::cout << "结果: " << task.get_result() << "\n";
// }
```



#### 面试话术

```
C++20 协程是无栈协程，切换开销 < 50ns，比线程切换快 20 倍。
promise_type 是编译器和用户代码的契约接口，必须实现：
get_return_object、initial_suspend、final_suspend、
return_value/return_void、unhandled_exception 五个方法。
关键设计决策：initial_suspend 返回 suspend_never 还是 suspend_always
决定了协程是"热启动"还是"冷启动"。
```

### Q2: std::move vs std::forward？

```
move:     无条件左值→右值引用 (T→T&&)
forward:  条件转换（保持原始值类别）

完美转发:
  template<typename T>
  void wrapper(T&& arg) {          // T&& 万能引用
      target(std::forward<T>(arg)); // 保持左右值属性
  }
```



#### 面试话术

```
std::move 是 unconditional cast，把左值变右值，
告诉编译器"你可以偷走我的资源"。
std::forward 是 conditional cast，在完美转发中
保持参数的原始左右值属性。区别很简单：
move 用于已知要转移的场景，forward 用于模板泛型场景。
错误使用 move 会阻止 RVO 优化。
```

### Q3: virtual 函数原理？vptr 初始化时机？

```
vptr 初始化: 构造函数开始时（成员初始化列表之前）
  按基类→派生类顺序

性能开销: 8 字节 vptr + 间接跳转（分支预测失败有惩罚）
```



#### 面试话术

```
虚函数通过 vptr 和 vtable 实现动态分发。
vptr 在构造函数开始时初始化，按基类到派生类的顺序。
注意：构造/析构函数中调用虚函数不会触发多态，
因为此时派生类部分还没构造好或已经销毁了。
性能开销：8 字节 vptr + 间接跳转（分支预测失败时惩罚大）。
高频调用的虚函数考虑用 CRTP 静态多态替代。
```

### Q4: shared_ptr 线程安全？

```
控制块引用计数: 线程安全（原子操作）
shared_ptr 对象本身: 多线程同时写不安全
指向的对象: 不保证线程安全（需外部加锁）

make_shared 优点:
  ├── 1 次分配（对象+控制块连续）
  ├── 异常安全
  └── 缓存友好
```



#### 面试话术

```
shared_ptr 的线程安全分三层：
1. 引用计数安全（原子操作）；
2. shared_ptr 本身不安全（多线程同时写同一个 shared_ptr 会崩）；
3. 指向的对象不安全（需要自己加锁）。
推荐用 make_shared，一次分配对象+控制块，缓存友好且异常安全。
但注意：weak_ptr 存活时对象内存不释放，可能内存占用比预期高。
```

### Q5: 异常安全级别？

```
1. No Guarantee: 可能泄漏
2. Basic: 资源不泄漏，状态不确定
3. Strong: 回滚到操作前（copy-and-swap）
4. Noexcept: 永不抛

实践: 析构 noexcept / move noexcept / swap noexcept
```



#### 面试话术

```
异常安全四级别：No Guarantee、Basic、Strong、Noexcept。
实践中最常用的是 Strong Guarantee（copy-and-swap 模式），
先操作副本，最后无异常时 swap 替换。
noexcept 很重要：移动构造、swap、析构都应该标记 noexcept，
否则 STL 容器在扩容时宁愿拷贝也不移动。
```

### Q6: 内存序 (memory_order)？

```
relaxed: 仅原子性，无顺序保证
acquire: 之后读不能重排到之前
release: 之前写不能重排到之后
seq_cst: 全局顺序一致（默认，最安全但慢）

典型: Producer(store release) → Consumer(load acquire)
```

#### 完整示例

```cpp
#include <atomic>
#include <thread>
#include <cassert>

// 生产-消费模型（acquire-release 语义）
std::atomic<bool> ready{false};
std::atomic<int> data{0};

void producer() {
    data.store(42, std::memory_order_release);  // #1
    ready.store(true, std::memory_order_release); // #2
    // release barrier: #1 不会重排到 #2 之后
}

void consumer() {
    while (!ready.load(std::memory_order_acquire)); // #3
    // acquire barrier: #3 之后的读不会重排到 #3 之前
    assert(data.load(std::memory_order_relaxed) == 42); // #4 一定成立
}

// Sequentially Consistent（默认，最慢但最安全）
std::atomic<int> x{0}, y{0};
int r1, r2;

void thread1() {
    x.store(1, std::memory_order_seq_cst);
    r1 = y.load(std::memory_order_seq_cst);
}

void thread2() {
    y.store(1, std::memory_order_seq_cst);
    r2 = x.load(std::memory_order_seq_cst);
}

// seq_cst 保证: r1==0 && r2==0 不可能同时发生
// relaxed 可能: 两个线程同时读到 0

// 性能对比（单次原子操作）:
//   relaxed:  ~1-2ns
//   acquire/release: ~2-5ns
//   seq_cst: ~5-15ns（需要内存屏障指令）
```

---



#### 面试话术

```
内存序的核心是控制指令重排和可见性。
relaxed 只保证原子性，不保证顺序，适合计数器。
acquire-release 建立 happens-before 关系，
典型用法：写线程 store release、读线程 load acquire。
seq_cst 全局一致最安全但最慢（需要内存屏障指令）。
性能参考：relaxed ~1-2ns，acquire/release ~2-5ns，seq_cst ~5-15ns。
大部分场景用 acquire/release 就够了。
```
