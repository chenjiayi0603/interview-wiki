## 二、中小公司常问通用题

### Q1: 从浏览器输入 URL 到页面展示？

#### 完整流程（7 步）

```
1. DNS 解析: 浏览器缓存 → OS 缓存 → hosts → DNS 递归查询
2. TCP 三次握手: SYN → SYN+ACK → ACK
3. TLS 握手（HTTPS）: ClientHello → ServerHello → 证书 → 密钥交换
4. HTTP 请求: GET /index.html HTTP/1.1 → 请求头 → 请求体
5. 服务端处理: 反向代理 → 应用层 → 数据库 → 响应
6. HTTP 响应: 状态码 200 → 响应头 → 响应体（HTML）
7. 浏览器渲染: HTML 解析 → DOM 树 → CSSOM → 布局 → 绘制
```

#### 追问细节

```
Q: DNS 用了 UDP 还是 TCP？
A: 标准查询用 UDP 53 端口，响应 > 512B 自动切 TCP。
   区域传输（Zone Transfer）用 TCP。

Q: 输入 URL 后按回车到 DNS 查询前发生了什么？
A: 浏览器先判断是 URL 还是搜索词。
   若是 URL，检查 HSTS 列表（强制 HTTPS），再开始 DNS 查询。

Q: 浏览器的渲染是单线程吗？
A: 主线程是单线程（处理 DOM/CSS/布局/绘制），
   Worker 线程处理 JS/定时器/网络请求。
   重排（Reflow）和重绘（Repaint）的区别:
   - Reflow: 布局变化（宽高/位置），代价大
   - Repaint: 样式变化（颜色/背景），代价小
```

#### 面试话术

```
从输入 URL 到页面展示是面试必考题，核心考察知识广度。
我习惯按网络分层讲：应用层 DNS → 传输层 TCP → 网络层 IP ->
应用层 HTTP 请求 -> 服务端处理 -> HTTP 响应 -> 浏览器渲染。
每个环节都可以深挖，比如 DNS 用 UDP 还是 TCP、
TLS 握手过程、浏览器渲染是单线程还是多线程。
关键是讲清楚整个链路，让面试官觉得你基础扎实。
```



### Q2: HTTP 状态码 301/302/304/401/403/500/502/503？

```
301=永久重定向  302=临时重定向  304=缓存有效
401=未认证     403=无权限     404=不存在
500=服务端错    502=网关错     503=过载
```

#### 面试话术

```
状态码不用死记，理解分类就行。
2xx 成功、3xx 重定向、4xx 客户端错、5xx 服务端错。
常问的是 301 vs 302（永久 vs 临时）、
304（缓存有效，配合 If-Modified-Since）、
502 vs 503（网关问题 vs 过载）。项目中最常见的是
排查 502，一般是上游服务挂了或超时。
```



### Q3: MySQL 索引什么时候失效？

```
LIKE '%xxx' / 函数包裹 / 隐式类型转换 / 不满足最左前缀 / OR 非索引
```

#### 详细案例

```sql
-- 失效场景 1: 前模糊匹配
EXPLAIN SELECT * FROM user WHERE name LIKE '%张%';  -- 全表扫描
EXPLAIN SELECT * FROM user WHERE name LIKE '张%';    -- 走索引（后模糊可用）

-- 失效场景 2: 函数包裹
EXPLAIN SELECT * FROM user WHERE DATE(create_time) = '2024-01-01';  -- 不走索引
EXPLAIN SELECT * FROM user WHERE create_time >= '2024-01-01' AND create_time < '2024-01-02';  -- 走索引

-- 失效场景 3: 隐式类型转换
EXPLAIN SELECT * FROM user WHERE phone = 13800138000;  -- phone 是 varchar，不走索引
EXPLAIN SELECT * FROM user WHERE phone = '13800138000'; -- 走索引

-- 失效场景 4: 不满足最左前缀（联合索引 idx(a,b,c)）
EXPLAIN SELECT * FROM t WHERE b = 1 AND c = 2;   -- 不走
EXPLAIN SELECT * FROM t WHERE a = 1 AND c = 2;   -- 走 a 部分
EXPLAIN SELECT * FROM t WHERE a = 1 AND b = 2;   -- 全走索引

-- 失效场景 5: OR 条件非索引
EXPLAIN SELECT * FROM user WHERE name = '张三' OR status = 1;  -- status 无索引 => 全表
-- 优化: UNION 拆成两个查询
EXPLAIN SELECT * FROM user WHERE name = '张三'
        UNION
        SELECT * FROM user WHERE status = 1;
```

#### 追问: 怎么发现索引失效？

```
1. EXPLAIN 看 type 字段（ALL=全表扫描，ref/range=走索引）
2. slow_query_log 开启，抓取慢 SQL
3. 查看 rows 扫描行数，远大于预期就是索引失效
```

#### 面试话术

```
索引失效是 SQL 优化的核心痛点。
记住五种场景：前模糊匹配、函数包裹列、隐式类型转换、
不满足最左前缀、OR 条件含非索引列。
排查方法：EXPLAIN 看 type 字段，ALL 就是全表扫描。
优化建议：写 SQL 时养成好习惯，字段保持原样不包函数，
参数类型与字段类型一致，联合索引按顺序写条件。
```



### Q4: MVCC 怎么实现？

#### 核心原理

```
每行有隐藏字段:
  DB_TRX_ID  (6B): 最后修改的事务 ID
  DB_ROLL_PTR (7B): 回滚指针（指向 undo log）
  DB_ROW_ID  (6B): 自增行 ID（无主键时使用）

Read View 可见性判断:
  ├── trx_id < min(m_ids)  → 已提交，可见
  ├── trx_id in m_ids      → 未提交，不可见
  ├── trx_id > max(m_ids)  → 未来事务，不可见
  └── trx_id == 自己的 trx_id → 可见

隔离级别:
  RC (Read Committed): 每次查询都生成新的 Read View
  RR (Repeatable Read): 事务开始时生成 Read View，复用到底
```

#### 面试话术

```
MySQL 的 MVCC 靠 undo log 实现。
每行数据有 DB_TRX_ID 记录最后修改的事务 ID。

当 SELECT 时，InnoDB 根据当前事务的 Read View 判断可见性:
- 如果 row 的 DB_TRX_ID 在当前事务开始前已提交，直接可见
- 如果 row 的 DB_TRX_ID 是当前事务自己的修改，也可见
- 否则，通过 DB_ROLL_PTR 找到 undo log 中的历史版本

RR 解决"不可重复读": Read View 事务开始时就固定了
RC 解决"脏读": 每次查询都生成新的 Read View，但会有"不可重复读"

MySQL 的 MVCC 只对 READ COMMITTED 和 REPEATABLE READ 生效。
READ UNCOMMITTED 直接读最新版本，SERIALIZABLE 全部加锁。
```

### Q5: Redis 过期策略和淘汰机制？

```
过期: 被动(访问时检查) + 主动(每100ms抽20个)
淘汰: allkeys-lru(推荐缓存) / noeviction(推荐存储)
```

#### 面试话术

```
Redis 过期策略是被动+主动结合。
被动：访问时检查是否过期，过期就删。
主动：每秒 10 次，每次抽 20 个 key 检查。
淘汰机制推荐 allkeys-lru（缓存场景）或 noeviction（存储场景）。
注意：大量 key 同时过期会导致性能抖动，
所以过期时间应该加随机偏移。
```



### Q6: 分布式锁 Redis vs ZK？

```
Redis: 性能高(10万+/s)，主从切换可能丢锁
ZK: 强一致(ZAB)，性能稍低(几千/s)
选型: 业务锁→Redis，配置协调→Etcd
```

#### 代码对比

```go
// Redis 分布式锁（高性能）
func RedisLock(rdb *redis.Client, key, value string, ttl time.Duration) bool {
    ok, err := rdb.SetNX(context.Background(), key, value, ttl).Result()
    return ok && err == nil
}

// ZK 分布式锁（强一致，Java 示例）
// CuratorFramework client = CuratorFrameworkFactory.newClient("zk:2181", retryPolicy);
// InterProcessMutex lock = new InterProcessMutex(client, "/lock/order");
// lock.acquire(10, TimeUnit.SECONDS);
// try { /* 业务逻辑 */ } finally { lock.release(); }

// Etcd 分布式锁（强一致，Go 示例，推荐）
func EtcdLock(client *v3.Client, key, value string, ttl int64) error {
    // 使用 etcd 的 Lease + Txn 实现
    lease, _ := client.Grant(context.Background(), ttl)
    txn := client.Txn(context.Background())
    txn.If(v3.Compare(v3.CreateRevision(key), "=", 0)).
        Then(v3.OpPut(key, value, v3.WithLease(lease.ID))).
        Else()
    resp, err := txn.Commit()
    if err != nil {
        return err
    }
    if !resp.Succeeded {
        return ErrLockAlreadyHeld
    }
    return nil
}

// 选型建议
// +----------+---------+----------+
// |          | Redis   | Etcd     |
// +----------+---------+----------+
// | 性能     | 10万+/s | 几千/s   |
// | 一致性   | 最终    | 强一致   |
// | 锁超时   | TTL     | Lease    |
// | 适用     | 业务锁  | 配置协调 |
#### 面试话术

```
Redis 和 ZK/Etcd 的分布式锁选型看场景。
Redis 性能高（10万+ QPS），适合业务锁、秒杀、防重复提交。
但主从切换可能丢锁，所以重要场景加补偿机制。
Etcd 强一致，适合配置协调、选主、服务注册。
选型原则：业务锁用 Redis，配置锁用 Etcd。
实际项目 Redis 锁都会配合幂等性做补偿。

### Q7: 死锁 4 条件 + 排查方法？

```
互斥 + 持有等待 + 不可剥夺 + 循环等待
排查: MySQL SHOW ENGINE INNODB STATUS / gdb bt / pprof goroutine
```

#### 面试话术

```
死锁四个条件：互斥、持有等待、不可剥夺、循环等待。
只要破坏任何一个就能预防死锁。
实际排查：MySQL 用 SHOW ENGINE INNODB STATUS 看最近死锁，
Go 用 pprof goroutine 看协程阻塞状态，
Linux 用 gdb bt 看线程堆栈。
最常见的死锁是加锁顺序不一致，
解决方法是所有线程按相同顺序加锁。
```



### Q8: 微服务 vs 单体？

```
前期单体(快速迭代) → 中期垂直拆分 → 后期微服务(需DevOps支撑)
不要为了微服务而微服务
```

#### 面试话术

```
微服务不是银弹，前期单体 + 后期按需拆分是务实路线。
拆分时机：团队 > 10 人、代码库 > 50 万行、部署频率冲突时才拆。
拆分原则：按业务领域垂直拆分，每个服务独立数据库。
微服务带来的挑战：分布式事务、服务发现、链路追踪、配置管理，
没有 DevOps 支撑上微服务是自找麻烦。
```



### Q9: 服务降级和熔断？

```
降级: 开关降级/限流降级/超时降级
熔断(Hystrix): 关闭→打开→半开 三状态
```

#### 面试话术

```
降级和熔断都是保护系统的手段。
降级是主动行为：开关降级（关闭非核心功能）、限流降级（超过阈值返回默认值）。
熔断是被动行为：Hystrix 三状态（关闭→打开→半开），
失败率达到阈值就熔断，过一段时间半开试探。
区别：降级是人工决策，熔断是自动决策。
项目中降级常用于大促保障，熔断用于服务依赖保护。
```



### Q10: Linux 查日志/查进程/查端口/查磁盘？

#### 常用命令大全

```bash
# ======== 查日志 ========
tail -f /var/log/app.log                  # 实时跟踪日志
tail -n 100 /var/log/app.log              # 看最后 100 行
grep "ERROR" /var/log/app.log             # 搜索错误
grep "ERROR" app.log | awk '{print $1}' | sort | uniq -c  # 按错误类型统计
journalctl -u myapp.service --since "1 hour ago"  # systemd 日志

# ======== 查进程 ========
ps aux | grep nginx                       # 查 nginx 进程
ps -ef --sort=-%cpu | head -10            # CPU 前 10
ps -ef --sort=-%mem | head -10            # 内存前 10
top -b -n 1 | head -20                    # 系统资源概览
htop                                      # 交互式（需安装）
pstree -p                                 # 进程树

# ======== 查端口 ========
netstat -tlnp | grep :8080                # 查 8080 端口（-t tcp, -l listen, -n 数字, -p 进程）
ss -tlnp | grep :8080                     # 现代版 netstat（更快）
lsof -i :8080                             # 谁在占用 8080
fuser -k 8080/tcp                         # 强制释放端口

# ======== 查磁盘 ========
df -h                                     # 磁盘分区使用率
du -sh /var/log/                          # 目录总大小
du -sh * | sort -rh | head -10            # 当前目录下最大的 10 个
ncdu /var                                 # 交互式磁盘分析（需安装）
iostat -x 1 3                              # 磁盘 IO 性能（每秒显示，3 次）

# ======== 查网络 ========
curl -w "@format.txt" -o /dev/null -s http://localhost:8080/api  # 接口耗时分析
ping -c 5 google.com                      # 网络连通性
traceroute google.com                     # 路由追踪
mtr google.com                            # 持续追踪（需安装）
tcpdump -i eth0 port 80                   # 抓包分析
```

#### 面试话术

```
Linux 命令是基本功，但面试官更看重你用过哪些。
日志查错用 grep | awk | sort 组合；
进程排查用 ps aux、top、strace；
端口用 ss -tlnp（比 netstat 快）；
磁盘用 df -h 和 du -sh。
套路是：发现问题 -> 确定范围 -> 工具定位 -> 解决。
面试官问这个主要是确认你真有线上问题排查经验。
```



### Q11: Git Merge vs Rebase？

```
merge: 保留完整历史（团队协作）
rebase: 线性历史（个人开发）
公共分支不要 rebase
```

#### 面试话术

```
Merge 和 Rebase 的区别是面试高频题。
Merge 保留完整分支历史，适合团队协作，缺点是历史图复杂。
Rebase 让历史线性干净，适合个人开发，缺点是改写历史。
公共分支严禁 rebase。我的习惯：开发分支 rebase 保持整洁，
合并到主分支时用 merge --no-ff 保留合并节点。
```



### Q12: 排序算法复杂度？

```
快排 O(nlogn)/O(n²) ❌稳定 | 归并 O(nlogn) ✅稳定
堆排 O(nlogn) ❌稳定 | 冒泡 O(n²) ✅稳定
```

#### 面试话术

```
排序算法问的是复杂度理解和稳定性。
快排平均 O(nlogn) 但最差 O(n2)，不稳定，实际最快。
归并稳定 O(nlogn)，需要额外 O(n) 空间。
堆排 O(nlogn) 但不稳定。
实际开发中语言标准库的排序基本够用（Go 的 sort、C++ 的 std::sort），
面试考排序主要是看你能不能分析算法优劣。
```

### 组合 1: KeyDB + 雷漫 IM（业务后端推荐）

```
"我有两个核心项目：KeyDB 存算分离和雷漫 IM..."

KeyDB 项目:
  ├── 背景: 华为云 Redis 全内存成本高，利用率不均
  ├── 方案: RocksDB + OBS 存算分离，热数据内存/冷数据 OBS
  ├── 结果: 成本降 30%，QPS 10万+，Compaction 抖动从 50%→<10%
  ├── 技术栈: C++/RocksDB/OBS/Etcd
  └── 体现能力: 存储调优、系统设计、性能分析

雷漫 IM 项目:
  ├── 背景: 百万级并发即时通讯，消息延迟敏感
  ├── 方案: Go + WebSocket + Redis INCR seq + Goroutine Pool
  ├── 结果: 120 万并发连接，P50 0.8ms，群消息合并降 99.7% RPC
  ├── 技术栈: Go/Redis/WebSocket/Kafka
  └── 体现能力: 高并发、分布式、消息时序

一句话总结:
  "两个项目覆盖了存储和网络两个方向，KeyDB 体现底层 C++ 存储优化能力，
   雷漫 IM 体现 Go 高并发业务架构能力，面试时可以根据岗位侧重切换讲解。"
```
