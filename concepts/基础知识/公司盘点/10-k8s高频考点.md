# Kubernetes (K8s) 高频考点速查

> 全行业通用（字节/阿里/腾讯/美团/快手/百度/小厂 均高频覆盖）

## 一、核心概念

```
集群架构:
  ├── Control Plane (Master):
  │   ├── kube-apiserver:    所有组件通信入口（REST API）
  │   ├── kube-scheduler:    Pod 调度到 Node
  │   ├── kube-controller-manager: 控制器集合（Deployment, Node, 等）
  │   └── etcd:              分布式键值存储（集群状态）
  └── Worker Node:
      ├── kubelet:           节点代理，管理 Pod 生命周期
      ├── kube-proxy:        网络代理（iptables/IPVS 转发规则）
      └── container runtime: containerd / CRI-O / Docker

核心资源:
  ├── Pod: 最小调度单位（1+N 容器，共享网络/存储）
  ├── Service: 稳定网络端点，负载均衡到 Pod
  ├── Volume: 存储卷（emptyDir, hostPath, PVC, ConfigMap, Secret）
  ├── Namespace: 虚拟集群隔离
  └── Ingress: 七层 HTTP 路由（外部流量进入集群）

面试高频:
  Q: kube-apiserver 高可用怎么实现？
     └── 多实例 + 负载均衡 + etcd 集群
  Q: etcd 是什么？
     └── 分布式一致性 KV 存储（Raft 协议），存所有集群状态
```

## 二、Pod 详解

```
Pod 生命周期:
  Pending → ContainerCreating → Running → Succeeded/Failed → Unknown

重启策略 (restartPolicy):
  ├── Always:       默认，始终重启
  ├── OnFailure:    非正常退出时重启
  └── Never:        永不重启

健康检查:
  livenessProbe:   存活检查（失败 → 重启容器）
  readinessProbe:  就绪检查（失败 → 从 Service 端点移除）
  startupProbe:    启动检查（慢启动容器，成功前禁用其他探针）

  探测方式:
  ├── httpGet:  HTTP GET 请求
  ├── tcpSocket: TCP 端口检查
  └── exec:      容器内执行命令

资源限制:
  resources.requests: 调度保证（最小需求）
  resources.limits:   运行时上限（超限 → OOMKill / Throttle）
  Quality of Service:
  ├── Guaranteed: 所有容器 requests == limits
  ├── Burstable:  部分容器 requests < limits
  └── BestEffort:  无 requests/limits（优先级最低）

Init Containers:
  ├── 在应用容器之前运行
  ├── 串行执行，每个成功才到下一个
  └── 用于初始化、等待依赖、权限配置

Sidecar 模式:
  ├── 同一 Pod 中多个容器共享网络/存储
  ├── 典型: 日志采集（Fluentbit）、代理（Envoy）、配置热更新
  └── 1.29+ 原生支持 sidecar 生命周期控制

面试高频:
  Q: Pod 如何分配到指定节点？
     ├── nodeSelector: 简单标签匹配
     ├── nodeAffinity: 复杂调度规则（preferred/required）
     └── podAffinity / podAntiAffinity: Pod 间亲和/反亲和
  Q: 静态 Pod 是什么？
     └── kubelet 直接通过文件创建（不经过 apiserver）
```

## 三、控制器 (Controller)

```
Deployment（无状态应用）:
  ├── 声明式更新: spec.replicas 期望副本数
  ├── 滚动更新: maxSurge + maxUnavailable 控制速率
  ├── 回滚: rollout undo / revision history
  ├── 暂停/恢复: rollout pause / resume
  └── 自愈: Pod 故障自动重建

StatefulSet（有状态应用）:
  ├── 唯一网络标识: pod-name-0, pod-name-1（稳定 DNS）
  ├── 顺序部署/伸缩/删除
  ├── 稳定存储: PVC 模板（每个 Pod 独立卷）
  └── 适用: 数据库（MySQL 主从）、ZooKeeper、Kafka

DaemonSet（每个节点运行一个副本）:
  ├── 典型: 日志收集（Fluentd）、监控（Prometheus Node Exporter）
  ├── 网络插件（Calico, Cilium）
  └── 新节点加入自动部署，节点删除自动回收

Job / CronJob（批处理）:
  ├── Job: 运行到成功完成
  ├── CronJob: 定时触发（cron 表达式）
  └── 并行: completions, parallelism 参数

面试高频:
  Q: Deployment 滚动更新策略？
     ├── maxSurge:   最大超过期望数（默认 25%）
     ├── maxUnavailable: 最大不可用（默认 25%）
     └── 过程: 先创建新 Pod → 老 Pod 逐步缩容
  Q: StatefulSet 如何保证顺序？
     └── podManagementPolicy: OrderedReady（默认）/ Parallel
  Q: Deployment vs StatefulSet 选择？
     └── 无状态用 Deployment，需稳定 ID/存储用 StatefulSet
```

## 四、Service 与网络

```
Service 类型:
  ├── ClusterIP:     集群内部虚拟 IP（默认）
  ├── NodePort:      每个节点开放固定端口（30000-32767）
  ├── LoadBalancer:  云厂商 LB（自动创建外部负载均衡器）
  └── ExternalName:  DNS CNAME 别名

Service 实现:
  ├── iptables:  随机选择后端 Pod（默认模式）
  ├── IPVS:      更高效的负载均衡（支持更多调度算法）
  └── 内部: kube-proxy watch apiserver → 更新转发规则

DNS 解析:
  ├── <svc>.<ns>.svc.cluster.local
  ├── headless Service: clusterIP=None → 返回所有 Pod IP
  └── Pod DNS: pod-ip.<ns>.pod.cluster.local

Ingress:
  ├── 七层 HTTP/HTTPS 路由
  ├── 需要 Ingress Controller（nginx-ingress, traefik, ALB）
  ├── 支持: 路径路由、虚拟主机、TLS 终止
  └── Ingress 资源定义规则，Controller 实现

网络策略 NetworkPolicy:
  ├── 默认: 所有 Pod 互通（扁平网络）
  ├── 隔离: 通过 labelSelector 控制 ingress/egress 流量
  └── 需要 CNI 插件支持（Calico, Cilium, Weave）

CNI 插件:
  ├── Calico:   BGP 网络策略（性能好，功能全）
  ├── Flannel:  简单 overlay（VXLAN），不支 NetworkPolicy
  ├── Cilium:   eBPF 技术（高性能，可观测性）
  └── Weave:    加密 mesh 网络

面试高频:
  Q: Service 如何实现负载均衡？
     └── iptables DNAT 规则 → 随机选择 Endpoint
  Q: NodePort 和 LoadBalancer 关系？
     └── LoadBalancer = NodePort + 外部 LB 转发到 NodePort
  Q: headless Service 应用场景？
     └── StatefulSet 稳定 DNS、自建服务发现
```

## 五、存储

```
Volume 类型:
  ├── emptyDir:    Pod 内临时存储（Pod 删除即消失）
  ├── hostPath:    宿主机目录（通常用于 DaemonSet）
  ├── configMap:   配置文件注入 Pod
  ├── secret:      敏感数据注入
  └── PVC:         持久卷声明（动态/静态绑定 PV）

PV / PVC / StorageClass:
  ├── PV (PersistentVolume):    集群级存储资源
  ├── PVC (PersistentVolumeClaim): 用户存储请求
  ├── StorageClass:             动态 PV 模板（provisioner + 参数）
  └── 绑定流程: PVC 请求 → StorageClass 创建 PV → 绑定 PVC

存储访问模式:
  ├── ReadWriteOnce (RWO): 单节点读写（块存储）
  ├── ReadOnlyMany (ROX):  多节点只读
  ├── ReadWriteMany (RWX): 多节点读写（NFS）
  └── ReadWriteOncePod:     单 Pod 读写（CSI 1.0+）

ConfigMap / Secret:
  ├── 注入方式: 环境变量 / 挂载卷
  ├── ConfigMap: 明文配置（最大 1MB）
  ├── Secret:    base64 编码敏感数据，支持加密（KMS）
  └── 更新: 挂载卷方式会热更新，环境变量方式需重启 Pod

面试高频:
  Q: PV 回收策略？
     ├── Retain:    手动回收（保留数据）
     ├── Delete:    自动删除（动态 PV 默认）
     └── Recycle:   清空后重用（已弃用）
  Q: 如何让多个 Pod 共享同一存储？
     └── 使用 RWX 的 PVC（如 NFS, CephFS, GlusterFS）
```

## 六、配置与安全

```
RBAC (Role-Based Access Control):
  ├── Role / ClusterRole: 权限规则集合
  ├── RoleBinding / ClusterRoleBinding: 绑定到用户/SA
  └── 最佳实践: 最小权限原则

ServiceAccount:
  ├── Pod 的身份标识
  ├── 自动挂载 Token (/var/run/secrets/kubernetes.io/serviceaccount)
  └── 1.24+: 不再自动创建 Secret，使用 TokenRequest API

Pod Security:
  ├── PodSecurityPolicy (PSP): 已废弃（1.25 删除）
  ├── Pod Security Admission (1.23+):
  │   ├── Privileged:  宽松
  │   ├── Baseline:    最小限制
  │   └── Restricted:  最严格
  └── securityContext: Pod/容器级别安全设置
      ├── runAsNonRoot: true
      ├── runAsUser: 1000
      ├── capabilities: drop: ['ALL']
      └── seccompProfile: type: RuntimeDefault

网络策略:
  apiVersion: networking.k8s.io/v1
  kind: NetworkPolicy
  spec:
    podSelector: matchLabels: {app: web}
    policyTypes: [Ingress]
    ingress:
    - from:
      - podSelector: matchLabels: {role: frontend}
      ports: [port: 80]
```

## 七、调度器 (Scheduler)

```
调度流程:
  1. 过滤 (Predicates):  筛选满足条件的节点
  2. 打分 (Priorities):  对候选节点打分
  3. 绑定: 选择最优节点，更新 Pod 的 nodeName

过滤条件:
  ├── PodFitsResources: 资源足够
  ├── PodMatchNodeSelector: nodeSelector/affinity
  ├── PodFitsHostPorts: 端口不冲突
  ├── CheckNodeCondition: 节点健康
  └── NoDiskConflict: 卷不冲突

打分维度:
  ├── LeastRequestedPriority: 资源利用率低的节点优先
  ├── BalancedResourceAllocation: CPU/内存均衡
  ├── NodeAffinityPriority: 亲和性匹配
  └── ImageLocalityPriority: 镜像已存在的节点优先

调度策略:
  ├── nodeSelector:          标签匹配
  ├── nodeAffinity:          requiredDuringScheduling / preferredDuringScheduling
  ├── podAffinity:           与某类 Pod 同节点
  ├── podAntiAffinity:       与某类 Pod 不同节点
  ├── taints + tolerations:  污点与容忍（Pod 只能调度到容忍的节点）
  └── topologySpreadConstraints: 拓扑分布约束

面试高频:
  Q: Taints 和 Tolerations 作用？
     ├── Taint 标记节点 `kubectl taint node x key=value:NoSchedule`
     ├── Pod 需对应 Toleration 才能调度到该节点
     └── 用途: 独占节点（GPU）、系统节点、故障隔离
  Q: Pod 优先级和抢占？
     └── PriorityClass → 高优 Pod 可抢占低优 Pod
```

## 八、集群部署与升级

```
安装方式:
  ├── kubeadm:        官方工具，快速搭建生产集群
  ├── kind:           本地开发（Docker in Docker）
  ├── minikube:       单节点本地测试
  ├── k3s:            边缘/轻量级 K8s
  └── 云托管: EKS, AKS, GKE, TKE, ACK

升级流程:
  1. 升级 kubeadm: kubeadm upgrade plan / apply
  2. 升级节点: 先 drain → 升级 kubelet → uncordon
  3. 先升级 Control Plane，再升级 Worker

高可用:
  ├── Control Plane: 3 或 5 节点（奇数）
  ├── etcd: 3/5/7 节点集群
  ├── apiserver: 多实例 + LB（nginx/haproxy）
  └── 注意: etcd 性能依赖磁盘 IOPS（推荐 SSD）

面试高频:
  Q: 集群证书过期如何处理？
     └── kubeadm certs renew all → 重启 kubelet
     └── 控制面证书 1 年，kubelet 证书自动轮换
  Q: etcd 备份和恢复？
     ├── 备份: etcdctl snapshot save
     └── 恢复: etcdctl snapshot restore + 更新 apiserver 配置
```

```
监控体系:
  ├── metrics-server:   基础资源指标（CPU/内存）
  ├── kube-state-metrics: 集群对象指标
  ├── node-exporter:    节点级指标

事件监控:
  kubectl get events --watch
  kubectl describe pod xxx
  ├── 事件自动清理（etcd 中 1 小时过期）

告警规则:
  ├── Pod 频繁重启
  ├── 节点 NotReady
  ├── 持久卷使用率 > 85%
  ├── API Server 延迟高
  └── etcd leader 切换频繁
```

## 十、排障实战

```
Pod 排障:
  ├── Pod Pending: 资源不足/节点选择器不匹配/PVC 未绑定
  ├── Pod CrashLoopBackOff: 应用崩溃（kubectl logs / describe）
  ├── Pod ImagePullBackOff: 镜像拉取失败（仓库认证/地址错误）
  ├── Pod OOMKill: limits 过小（kubectl describe 查看 OOM）
  ├── Pod 未就绪: readinessProbe 失败（kubectl describe）
  └── Pod Unknown: 节点失联 / kubelet 故障

节点排障:
  ├── kubectl describe node <node>
  ├── 查看 Condition: Ready/DiskPressure/MemoryPressure
  ├── 查看事件: LastHeartbeatTime
  └── 排查: kubelet 状态、docker 进程、磁盘、网络

网络排障:
  ├── 跨 Pod 不通: 检查 CNI 插件 / NetworkPolicy
  ├── Service 不通: iptables -L / kube-proxy 日志
  ├── DNS 解析失败: CoreDNS Pod 状态 / ConfigMap
  └── 外部无法访问: Ingress Controller / Service Type

常用排障命令:
  kubectl get pods -o wide -n <ns>
  kubectl logs -f <pod> -c <container>
  kubectl exec -it <pod> -- /bin/sh
  kubectl describe pod <pod>
  kubectl get events --sort-by='.lastTimestamp'
  kubectl top pod / node
```

## 十一、HPA 与自动伸缩

```
HPA (Horizontal Pod Autoscaler):
  ├── 基于 CPU/内存/Prometheus 指标自动扩缩
  ├── 算法: desiredReplicas = ceil(currentUsage / targetUsage)
  ├── 冷却: --horizontal-pod-autoscaler-downscale-stabilization
  └── 聚合: 多个指标取最大值

VPA (Vertical Pod Autoscaler):
  ├── 自动调整 Pod requests/limits（需要重启）
  └── 适合: 资源需求变化大的有状态应用

Cluster Autoscaler:
  ├── 节点不够时自动扩容云服务器
  ├── 空闲节点缩容
  └── 依赖云厂商（AWS ASG, GCP MIG, 阿里云 ESS）

面试高频:
  Q: HPA 工作原理？
     ├── 周期（默认 15s）采集 metrics
     ├── 计算目标副本数 = ceil(当前利用率 / 目标利用率)
     └── 更新 Deployment replicas → 滚动更新
  Q: HPA 与 Cluster Autoscaler 配合？
     └── HPA 增加 Pod → 资源不足 → Pod Pending → CA 扩容节点
```

## 十二、Helm 包管理

```
Helm 三要素:
  ├── Chart:   应用包（模板 + 配置）

注意事项:
```

## 十三、Operator 模式

```
Operator = 自定义控制器 + CRD (Custom Resource Definition)

核心思想:
  ├── 将运维知识编码为代码
  ├── 控制器 watch 自定义资源状态
  └── 不断调谐 (Reconcile) 到期望状态

CRD 定义:
  apiVersion: apiextensions.k8s.io/v1
  kind: CustomResourceDefinition
  metadata: name: etcdclusters.example.com
  spec:
    group: example.com
    names: {kind: EtcdCluster, plural: etcdclusters}
    scope: Namespaced
    versions: [{name: v1, schema: ...}]

常用框架:
  ├── kubebuilder:   官方推荐（Go）
  ├── operator-sdk:  Red Hat 方案（Go, Ansible, Helm）
  ├── Kopf:          Python 框架
  └── Charmed Operator: Canonical（Python）

典型 Operator:
  ├── etcd-operator
  ├── prometheus-operator
  ├── kafka-operator (Strimzi)
  ├── postgres-operator (Zalando / Crunchy)
  └── tidb-operator (PingCAP)

面试高频:
  Q: Operator 和 Helm 区别？
     ├── Helm: 模板化部署，静态配置
     └── Operator: 动态运维（备份、扩缩、恢复）
  Q: 什么时候需要写 Operator？
     └── 管理复杂有状态应用（数据库、消息队列）
```

## 十五、K8s 面试场景题

```
1. 设计一个高可用 Web 服务
   ├── Deployment: replicas=3, rolling update
   ├── Service: ClusterIP（内部）or LoadBalancer（外部）
   ├── ConfigMap: 配置文件
   ├── Ingress: 域名 + TLS 终止
   └── HPA: CPU > 70% 自动扩容

2. 数据库部署方案
   ├── StatefulSet: 稳定网络标识（mysql-0, mysql-1）
   ├── headless Service: 主从自动发现
   ├── PersistentVolumeClaim: 独立存储
   ├── readinessProbe: SQL 查询检查
   └── Operator: 自动备份/恢复/故障转移

3. 微服务通信与治理
   ├── 服务间: Service 名称 DNS 解析
   ├── 熔断/限流: Istio 或 HPA
   ├── 灰度发布: Istio VirtualService + DestinationRule
   └── 链路追踪: Jaeger/Zipkin

4. 日志收集方案
   ├── Filebeat/Fluentd: DaemonSet 采集节点日志
   ├── 输出: Elasticsearch / Loki
   ├── 可视化: Kibana / Grafana
   └── 结构化日志: JSON 格式 + 标准输出

5. 限流与反压
   ├── Ingress 限流: nginx.ingress.kubernetes.io/limit-rps
   ├── Service mesh: Istio 配额控制
   ├── HPA: 根据 QPS/CPU 自动扩容
   └── Pod 反压: readinessProbe 失败 → 从 Service 移除

6. 集群安全加固
   ├── RBAC: 最小权限，不用 cluster-admin
   ├── Pod Security: Restricted 策略
   ├── 网络策略: 默认拒绝所有入站
   ├── Secret: 加密存储（KMS）
   └── 镜像: 数字签名 + 漏洞扫描
```
