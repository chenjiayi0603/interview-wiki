## 一、GMP 调度器深度

### Q1: Goroutine 的栈管理

```
Goroutine 栈初始 2KB，动态伸缩（Go 1.3 前是分段栈，1.3+ 是连续栈）

连续栈:
  1. 栈空间不足时 -> 分配新栈（通常是 2 倍大小）
  2. 拷贝旧栈内容到新栈
  3. 更新所有指向栈的指针（需要 GC 配合）
  4. 释放旧栈

触发扩容的时机:
  - 调用 morestack（函数序言中检查）
  - 栈使用超过当前栈大小的阈值

栈缩容:
  - GC 时检查，栈使用率 < 25% 且栈大小 > 4KB 时缩容
  - 缩容到 2 倍实际使用大小

栈大小上限:
  - Go 1.19 前: 1GB（64-bit）
  - Go 1.19+: 1GB 不变，但大栈的 goroutine 会被调度器标记为"不抢占"

对比:
  - OS 线程栈: 通常 1-8MB，固定大小
  - Goroutine 栈: 2KB 起步，动态伸缩，百万 goroutine 只需 GB 级内存

面试话术:
  "Goroutine 轻量的核心是栈可伸缩。2KB 起步对比线程 1MB，
   100 万 Goroutine 只要 2GB 栈内存，100 万线程需要 1TB。
   连续栈的指针更新是性能关键，Go 用了栈复制 + GC 写屏障来保证安全。"
```

### Q2: sysmon - 后台监控线程

```
sysmon 是 Go runtime 的后台监控线程（M），不依赖 P，一直运行。

职责:
  1. 抢占调度: 检测运行超过 10ms 的 G，发送抢占信号
  2. 网络轮询: 检查 netpoller 是否有就绪的 fd
  3. 系统监控: GC 超时触发、堆大小检查
  4. 释放闲置的 M（超过空闲时间阈值）
  5. 处理未决的信号

抢占流程:
  Go 1.14 前: 协作式抢占（G 主动让出）
    - G 在函数调用、chan 操作、锁等时机检查抢占标志
    - 死循环 G 无法被抢占 -> 导致 STW 时间过长

  Go 1.14+: 异步抢占（基于信号）
    - sysmon 发送 SIGURG 信号给目标 M
    - 信号处理函数中设置抢占标志
    - 在函数序言（morestack）中检查并让出
    - 彻底解决了死循环 G 阻塞调度的问题

面试话术:
  "Go 1.14 的异步抢占是一个里程碑。以前 for { select {} } 能卡死所有 P，
   现在 sysmon 发 SIGURG 信号强制抢占。代价是信号处理有额外开销，
   但对绝大多数场景影响可忽略。"
```

### Q3: goroutine 状态机

```
Goroutine 状态转换:

     ┌───────────┐
     │   Idle    │ ← 空闲 G（复用，避免频繁创建）
     └─────┬─────┘
           │
     ┌─────▼──────┐
     │  Runnable   │ ← 等待被 P 执行
     └─────┬──────┘
           │
     ┌─────▼──────┐
     │  Running    │ ← 正在执行
     └──┬──────┬──┘
        │      │
        ▼      ▼
  ┌────────┐ ┌─────────┐
  │ Waiting│ │ Syscall │
  │(chan/  │ │ (block) │
  │ lock/  │ └────┬────┘
  │ sleep) │      │
  └───┬────┘      │
      │           │
      └───────┬───┘
              ▼
        ┌──────────┐
        │ Runnable │
        └────┬─────┘
             │
        ┌────▼─────┐
        │  Dead    │ → 进入 P 的 free 队列复用
        └──────────┘

Syscall 特殊路径:
  1. G 进入系统调用 -> M 阻塞
  2. P 与 M 解绑，P 寻找新的 M 或创建新 M
  3. syscall 返回 -> G 进入 Runnable，尝试绑定原来的 P

#### 面试话术详解: "M 与 P 解耦"到底啥意思？

```
问题场景: 一个 Goroutine 调了 os.ReadFile / 加锁 / 写日志等阻塞 syscall
          → 整个 M（OS 线程）被内核挂起
          → 如果没有解耦 → 这个 P 上的其他 G 全被卡死
          → GOMAXPROCS=8 时 1 个 G 阻塞 = 损失 12.5% 的 CPU！

解耦过程（handoff 机制）:
  ① G1 在 P1 上运行，调了 syscall → M1 阻塞
  ② Go runtime 检测到 M1 进入 syscall
  ③ P1 立即与 M1 解绑（handoff）
  ④ P1 从空闲 M 池中拿 M2 绑定，或者新建 M2
  ⑤ P1 带着 M2 继续执行 P1 本地队列中的其他 G
  ⑥ M1 的 syscall 返回后，G1 重新进入 Runnable
  ⑦ G1 尝试绑回原来的 P1；如果 P1 忙，就去全局队列

类比理解:
  就像厨房里的厨师（M）和灶台（P）：
  - 厨师 M1 正在用灶台 P1 炒菜（执行 G1）
  - 突然 M1 需要去仓库搬货（syscall 阻塞）
  - M1 大喊"灶台空出来了！"（释放 P）
  - 厨师 M2 立刻接手灶台 P1 继续炒菜
  - M1 搬完货回来，排队等下一个空灶台

为什么这是 Go 的核心优势？
  C++ 线程池:
    1 个线程阻塞 → 线程池里少 1 个线程 → 其他任务排队等
    如果线程池只有 4 线程，1 个阻塞 = 只剩 3 个干活

  Go GMP:
    1 个 M 阻塞 → P 被释放 → 其他 M 顶上
    GOMAXPROCS=8，1 个阻塞 = 还有 7 个 P 在干活
    阻塞不减少并行度！

面试原话:
  "GMP 的精髓是 M 和 P 的解耦。P 代表'执行权'，M 代表'执行者'。
   执行者阻塞了，执行权不会浪费，立刻转交给下一个执行者。
   这就是 Go 能把阻塞 syscall 的开销降到最低的原因。
   对比 C++ 线程池，线程阻塞就是真阻塞，而 Go 的阻塞只是 M 阻塞，
   P 和 G 的调度不受影响。"
```

### Q4: 网络轮询器（netpoller）

```
netpoller 是对 epoll/kqueue/IOCP 的封装，让 Goroutine 以同步风格写网络代码。

原理:
  1. Goroutine 调用 net.Read -> 底层 fd 无数据 -> G 挂起
  2. netpoller 将 fd 注册到 epoll
  3. epoll_wait 检测到 fd 就绪 -> 唤醒等待的 G
  4. G 恢复执行，继续读取数据

关键点:
  - netpoller 在 M 上运行，不占用额外线程
  - goroutine 数量可以远大于 OS 线程，每个 G 等待网络时不占 M
  - 对比传统 epoll 编程: 无需手动管理事件回调

源码路径:
  - runtime/netpoll.go
  - runtime/netpoll_epoll.go (Linux)
  - runtime/netpoll_kqueue.go (macOS)

面试话术:
  "netpoller 让 Go 的网络编程体验远超 C++。
   C++ 需要手写 epoll + 事件循环 + 状态机，
   Go 只需要一个 for 循环 + goroutine per connection。
   性能方面，Go netpoller 的 goroutine 切换成本 ~100ns，
   C++ 的事件回调是零切换，但开发成本高得多。"
```

### GMP 一图总结

```
┌──────────────────────────────────────────────────────────────┐
│                    GMP 调度模型（M:N 线程模型）                │
├───────────┬──────────────────────────────────────────────────┤
│    G      │ Goroutine，轻量级"协程"，2KB 栈可伸缩，百万级    │
│ (Goroutine)│ 状态机: Idle → Runnable → Running → Waiting/   │
│            │        Syscall → Runnable → Dead               │
├───────────┼──────────────────────────────────────────────────┤
│    M      │ Machine，OS 内核线程，和 C++ std::thread 一样   │
│  (Machine) │ 区别: 不直接执行代码，只执行 G                │
│            │ 阻塞时 handoff 让出 P，不浪费 CPU              │
├───────────┼──────────────────────────────────────────────────┤
│    P      │ Processor，逻辑处理器，数量 = GOMAXPROCS        │
│ (Processor)│ 持有本地 G 队列（256），M 必须有 P 才能干活   │
│            │ 核心: 解耦了 M 和 G，让阻塞不影响并行度        │
├───────────┴──────────────────────────────────────────────────┤
│ 调度策略:                                                    │
│   ① P 优先从本地队列取 G（无锁）                            │
│   ② 本地空 → 从全局队列取（加锁）                           │
│   ③ 全局也空 → Work Stealing（偷别的 P）                   │
│   ④ 都空 → M 自旋 → 休眠                                   │
├──────────────────────────────────────────────────────────────┤
│ 阻塞处理:                                                    │
│   syscall 阻塞 → M 让出 P → 别的 M 顶上 → 并行度不降       │
│   channel/锁阻塞 → G 进 Waiting → M 继续干别的             │
│   C++ 线程阻塞 = 真阻塞，Go 的阻塞 = 只是 G 阻塞           │
├──────────────────────────────────────────────────────────────┤
│ 抢占: 1.14+ 异步抢占（sysmon 发 SIGURG 信号强抢）          │
│ 网络: netpoller 封装 epoll，同步写法异步执行                │
└──────────────────────────────────────────────────────────────┘

一句话：GMP = M 个内核线程跑 N 个 goroutine。P 是中间调度层，解耦了 M 和 G，让 syscall 阻塞不再浪费 CPU 核心。
```

#### 阻塞时到底发生了什么？（简化版）

```
原来的 M 和 P 绑定在一起干活 → G 做 syscall → M 陷入内核阻塞
        ↓
P 检测到 M 阻塞 → P 与 M 解绑（handoff）
        ↓
P 带着本地队列里剩下的 G → 绑定到另一个空闲 M → 继续调度
        ↓
原来的 M 等 syscall 返回 → G 醒来 → 重新进调度队列等 P

结论: 阻塞的是 M（内核线程）和 G（协程），
      P（调度权）没有被阻塞，立刻转移给了别的 M。
      所以"并行度不降"——干活的人（M）换了，灶台（P）没闲着。
```

#### P 到底是啥？调度器又是谁在跑？

```
P = 逻辑处理器 = 调度上下文（struct p），不是线程也不是调度器。

  P 的核心字段:
    ├── runq [256]guintptr    // 本地 G 队列
    ├── runnext guintptr       // 下一个要执行的 G
    ├── m       *m            // 当前绑定的 M
    ├── mcache *mcache         // 内存缓存（per-P 独享）
    └── status                // _Pidle / _Prunning / _Psyscall

关键区分:
  ├── M = OS 内核线程（真正干活的人）
  ├── P = 执行许可证 + 本地任务队列（GOMAXPROCS 个槽位）
  └── 调度器 = runtime.schedule() 那套代码逻辑

调度器是谁执行的？
  → 调度器是 Go runtime 里的代码（函数），
  → 由当前正在运行的 G 来执行调度逻辑。
  → 具体说: G 主动让出（加锁/chan/sleep）或被动抢占时，
     会调用 schedule()，由当前 M 上正在跑的 G 来完成调度决策。
  → 所以: 调度算法是 G 自己执行的，不是某个独立的调度线程。

类比:
  厨师（M）炒菜累了 → 自己看菜单（schedule()）决定下一道菜（G）
  不是有个"调度员"站在旁边帮他选菜
```

## 二、内存管理深度

### Q5: 内存分配器（tcmalloc 变体）

```
Go 内存分配器基于 tcmalloc，但做了 Go 特有的优化。

四层结构:

  mcache (per-P) → mcentral (全局) → mheap (堆) → OS (mmap)

  1. mcache: 每个 P 独享，无锁分配
     - 每个 size class 有两个 mspan（一个已扫，一个未扫）
     - 小对象直接从 mcache 分配，零锁竞争

  2. mcentral: 全局，按 size class 管理
     - 每个 size class 一个 mcentral
     - mcache 不够时从 mcentral 取
     - 需要加锁，但粒度细（per size class）

  3. mheap: 管理所有 mspan
     - 大页分配（arenas）
     - 从 OS 申请/归还内存

  4. OS: 通过 mmap 向操作系统申请

Size Classes:
  - Tiny: < 16B（微对象分配器，放在超大 span 中）
  - Small: 16B ~ 32KB（精确的 size class，67 种）
  - Large: > 32KB（直接 mheap 分配）

零碎优化:
  - Tiny allocator: 把多个微对象合并到一个 16B 槽位
  - 对象对齐: 按 size class 对齐，减少碎片
  - 内存归还: scavenger 后台定期归还闲置内存

面试话术:
  "Go 的 mcache 是性能关键。每个 P 独享无锁分配，
   亿级 QPS 场景下锁竞争几乎为零。
   只有 mcache 不足时才去加锁取 mcentral。
   这也是为什么 GOMAXPROCS 通常等于 CPU 核数。"
```

### Q6: GC 实现深度 - 三色标记 + 写屏障

```
Go GC 是并发三色标记 + 清扫。

标记阶段:
  1. 所有对象初始为白色
  2. 根对象（全局变量、goroutine 栈）标记为灰色
  3. 遍历灰色对象 -> 引用的白色变灰色 -> 当前变黑色
  4. 结束时: 黑色 = 存活，白色 = 可回收

写屏障（混合写屏障，Go 1.8+）:
  - 插入屏障: 对象 A 引用 B 时，B 标记为灰色
  - 删除屏障: 对象 A 不再引用 B，B 仍视为存活（本轮不回收）
  - 目的: 保证并发标记时的三色不变性

GC 阶段:
  1. Mark Setup (STW): 开启写屏障，所有 P 参与
  2. Marking (并发): 三色标记，GC 工作线程 + Mark Assist
  3. Mark Termination (STW): 关闭写屏障，完成标记
  4. Sweep (并发): 清扫白色对象

GC 触发:
  - 主动: runtime.GC()
  - 阈值: 堆大小到达上次 GC 后的目标值（GOGC 控制）
  - 定时: 2 分钟未触发则强制触发

GC 调优:
  GOGC=100  (默认: 堆翻倍触发 GC)
  GOGC=off  (关闭 GC，不推荐)
  GOGC=50   (更频繁的 GC，更低的内存峰值)

面试话术:
  "Go 的 GC 在 1.8 之后 STW 稳定在 < 500us，
   对绝大多数业务来说已经够用了。
   写屏障的开销在 5-15% 之间，主要在 GC 期间。
   用 sync.Pool 复用对象、减少指针嵌套，能显著降低 GC 压力。"
```

## 三、Channel 与 Select 内部

### Q7: hchan 结构体深度分析

```go
// channel 底层结构（简化）
type hchan struct {
    qcount   uint           // 缓冲区中元素个数
    dataqsiz uint           // 缓冲区大小（环形队列）
    buf      unsafe.Pointer // 缓冲区指针
    elemsize uint16         // 元素大小
    closed   uint32         // 是否关闭
    elemtype *_type         // 元素类型
    sendx    uint           // 发送索引
    recvx    uint           // 接收索引
    recvq    waitq          // 接收等待队列（sudog 链表）
    sendq    waitq          // 发送等待队列（sudog 链表）
    lock     mutex          // 保护所有字段
}

// 关键数据结构: sudog（等待 goroutine）
type sudog struct {
    g        *g
    elem     unsafe.Pointer // 收发数据的地址
    isSelect bool          // 是否在 select 中
    next     *sudog
    prev     *sudog
    parent   *sudog        // select 的 goroutine 的 sudog
}
```

#### 收发流程

```
无缓冲 channel:
  发送: G1 发送 -> 发现没有接收者 -> G1 封装为 sudog 入 sendq -> G1 挂起
  接收: G2 接收 -> 发现 sendq 有等待者 -> 直接复制数据 -> 唤醒 G1

有缓冲 channel:
  发送: buf 未满 -> 写入环形队列 -> 返回
      buf 已满 -> G 入 sendq 等待
  接收: buf 非空 -> 从环形队列读 -> 唤醒 sendq 中的 G
       buf 空 -> G 入 recvq 等待

关闭 channel:
  - 关闭所有等待的 sudog 中的 goroutine
  - 它们收到零值 + false
  - 再次发送 -> panic
```

### Q8: select 实现原理

```
select 的实现分几个步骤:

1. 随机化 case 顺序（防止饥饿）
   - 遍历所有 case，打乱顺序
   - 保证每个 case 有公平的机会被选中

2. 快速路径: 检查是否有就绪的 channel
   - 遍历所有 case，非阻塞检查
   - 若发现有 case 就绪 -> 执行并返回

3. 慢路径: 都没有就绪 -> 挂起当前 G
   - 创建 sudog，注册到所有 case 的 channel
   - 当前 G 进入等待状态
   - 当某个 channel 就绪 -> 唤醒 G

4. 唤醒后: 锁定 channel，确认是哪个 case 就绪
   - 遍历所有 channel 取锁
   - 确定就绪的 case
   - 清理其他 channel 上的 sudog

select 核心:
  - 所有 case 的 channel 加锁（按地址排序防死锁）
  - 注册 sudog 到每个 channel
  - 释放锁，挂起 G
  - 唤醒后重新加锁，清理未选中的 case
```

## 四、Map 内部与并发安全

### Q9: map 底层结构

```go
// map 底层（简化）
type hmap struct {
    count     int            // 元素个数
    flags     uint8          // 标志位（B=正在写，I=正在扩容等）
    B         uint8          // bucket 数 = 2^B
    buckets   unsafe.Pointer // bucket 数组
    oldbuckets unsafe.Pointer // 旧 bucket（扩容时使用）
    nevacuate uintptr        // 扩容迁移进度
    extra     *mapextra      // 溢出桶
}

type bmap struct {
    tophash [8]uint8  // 高 8 位 hash（快速比较）
    keys    [8]keyType    // 8 个 key
    values  [8]valueType  // 8 个 value
    overflow *bmap    // 溢出桶指针
}
```

#### 扩容机制

```
负载因子 = count / 2^B
触发扩容条件: 负载因子 > 6.5（或者溢出桶过多）

等量扩容（sameSizeGrow）:
  - 溢出桶过多但负载因子不高
  - 重新排列，减少溢出桶

翻倍扩容:
  - 负载因子 > 6.5
  - B = B + 1 -> bucket 数翻倍
  - 渐进式: 每次写操作搬一部分 bucket
  - oldbuckets 保留旧数据，直到全部迁移完成

渐进式扩容流程:
  1. 创建新 bucket 数组（2 倍大小）
  2. 设置 oldbuckets = 旧数组
  3. 每次写操作时（mapassign），搬迁 1-2 个 bucket
  4. 读操作时（mapaccess），先查 oldbuckets，再查 buckets
  5. 迁移完成后: oldbuckets = nil

并发安全:
  - map 不是并发安全的！并发读写 = fatal error
  - 检测: runtime.throw("concurrent map read and map write")
  - 修复: sync.Map / 读写锁 / 分片锁
```

### Q14b: Go 的 M（Machine）是用户线程还是内核线程？和 C++ std::thread 一样吗？

`
M 是内核线程（OS 线程），和 C++ std::thread 底层完全一样。
在操作系统眼里，M 和 std::thread 没有区别——都是内核调度单位。

关键区别不在 M 本身，在 Go 怎么用它：
`

| 维度 | Go M | C++ std::thread |
|------|------|-----------------|
| 类型 | 内核线程 | 内核线程 |
| 创建代价 | ≈4KB 栈 + 8KB 线程结构 | ≈1MB 栈 + 线程结构 |
| 数量控制 | 默认 GOMAXPROCS，很少超过几千 | 几百个就可能扛不住 |
| 使用者 | M 执行 G（goroutine），不直接跑代码 | 直接执行线程函数 |
| 阻塞时 | M 与 P 解绑，换另一个 M 接管 P | 线程卡住，资源浪费 |

`
M 的本质是一个"执行工人"，不是"代码载体":

  M = 工厂里的工人（内核线程）
  G = 流水线上的任务单（goroutine）

  C++ 是一个工人只干一个任务（1:1 模型），
  Go 是一个工人可以干很多任务（M:N 模型）。

M 做的事情:
  1. 从 P 的本地队列取一个 G
  2. 执行 G 的代码
  3. G 阻塞（syscall/IO）→ M 把 P 让出去，自己继续等
  4. 另一个 M 接管 P，继续取 G 执行
`

#### M 阻塞时到底发生了什么？

`
Goroutine 做 syscall（如 read 文件）:
  1. G 进入 Syscall 状态
  2. M 阻塞在内核态等 IO
  3. M 和 P 解绑 → P 去找别的 M
  4. 另一个空闲 M 或新建 M 绑定 P
  5. 继续执行其他 G

结果:
  虽然这个 M 卡住了，但 CPU 核心（P）没闲着
  → 这就是 Go 能把阻塞 syscall 开销降到最低的原因
`

对比 C++:

`cpp
// C++: 线程卡住，没法复用
std::thread t([&] {
    read(fd, buf, size);  // 线程卡在这里
    // 其他工作没法做，这个线程就是浪费了
});
`

`go
// Go: G 阻塞，M 让出 P，不浪费 CPU
go func() {
    data, _ := os.ReadFile(path)  // G 阻塞，M 让出 P
    // 其他 G 继续在这个 M（或者另一个 M）上执行
}()
`

`
面试话术:
  "M 是内核线程，跟 C++ 的线程底层一样。
   但 Go 用 M:N 模型，一个 M 可以执行多个 G，
   阻塞时自动让出 P，不会浪费 CPU 核心。
   C++ 是你得自己搞线程池才能达到类似效果。"
`

## 九、高并发场景实战

### Q17: SingleFlight 实现

```go
// 防止缓存击穿: 多个并发请求只查一次 DB
type Call struct {
    val interface{}
    err error
    wg  sync.WaitGroup
}

type Group struct {
    mu    sync.Mutex
    calls map[string]*Call
}

func (g *Group) Do(key string, fn func() (interface{}, error)) (interface{}, error) {
    g.mu.Lock()
    if c, ok := g.calls[key]; ok {
        g.mu.Unlock()
        c.wg.Wait()
        return c.val, c.err
    }
    c := new(Call)
    c.wg.Add(1)
    g.calls[key] = c
    g.mu.Unlock()

    c.val, c.err = fn()
    c.wg.Done()

    g.mu.Lock()
    delete(g.calls, key)
    g.mu.Unlock()
    return c.val, c.err
}
```

### Q18: 限流器（Token Bucket）

```go
type Limiter struct {
    rate   float64
    burst  int
    tokens float64
    last   time.Time
    mu     sync.Mutex
}

func (l *Limiter) Allow() bool {
    l.mu.Lock()
    defer l.mu.Unlock()
    now := time.Now()
    elapsed := now.Sub(l.last).Seconds()
    l.tokens += elapsed * l.rate
    if l.tokens > float64(l.burst) {
        l.tokens = float64(l.burst)
    }
    l.last = now
    if l.tokens < 1 {
        return false
    }
    l.tokens--
    return true
}
```

#### WithCancel 源码简化

```go
// 简化版 WithCancel 实现
func WithCancel(parent Context) (ctx Context, cancel CancelFunc) {
    c := newCancelCtx(parent)
    // 关键: 将新 context 挂到父 context 的 children 链表
    propagateCancel(parent, &c)
    return &c, func() { c.cancel(true, Canceled) }
}

type cancelCtx struct {
    Context
    mu       sync.Mutex
    done     chan struct{}
    children map[canceler]struct{}  // 子 context 列表
    err      error
}

func (c *cancelCtx) cancel(removeFromParent bool, err error) {
    c.mu.Lock()
    if c.err != nil { return }  // 只取消一次
    c.err = err
    close(c.done)              // 核心: close channel 通知所有监听者
    // 递归取消所有子 context
    for child := range c.children {
        child.cancel(false, err)
    }
    c.mu.Unlock()
    if removeFromParent {
        removeChild(c.Context, c)
    }
}
```

   所以 WithTimeout 的场景，超时后所有派生 context 自动取消。

### Q29: Go 内存模型（Happens-Before）

```
Go 内存模型定义了在什么条件下一个 goroutine 的写操作
能被另一个 goroutine 的读操作看到。

核心规则:
  ├── 同一 goroutine 内: 顺序一致性（Sequential Consistency）
  ├── 锁: sync.Mutex 的 Unlock happens-before 另一个 goroutine 的 Lock
  ├── Channel: 发送 happens-before 接收完成
  ├── WaitGroup: Wait 返回 happens-before Done 调用返回
  └── atomic: 较弱的保证，需要配合 memory order

Channel 保证:
  ┌── 无缓冲: 接收 happens-before 发送 goroutine 唤醒
  └── 有缓冲: 发送 happens-before 接收（缓冲满时相反）

示例:
  var a string
  var c = make(chan int, 10)

  func f() {
      a = "hello"
      c <- 0  // 发送 happens-before 接收
  }

  func main() {
      go f()
      <-c           // 接收在发送之后
      print(a)      // 一定输出 "hello"
  }
```
