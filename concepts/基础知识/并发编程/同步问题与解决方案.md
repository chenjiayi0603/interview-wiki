## 1. 死锁

### 死锁条件（四个必要条件）
1. **互斥**：资源不能共享
2. **持有并等待**：持有资源同时等待其他资源
3. **不可抢占**：资源不能被强制释放
4. **循环等待**：存在循环等待链

### 死锁预防

```cpp
// 方法1: 锁排序
std::mutex mtx1, mtx2;

void safe_operation() {
    // 总是按固定顺序加锁（如按地址）
    std::mutex* first = &mtx1 < &mtx2 ? &mtx1 : &mtx2;
    std::mutex* second = &mtx1 < &mtx2 ? &mtx2 : &mtx1;
    
    std::lock_guard<std::mutex> lock1(*first);
    std::lock_guard<std::mutex> lock2(*second);
}

// 方法2: 使用std::lock
void safe_operation2() {
    std::lock(mtx1, mtx2);
    std::lock_guard<std::mutex> lock1(mtx1, std::adopt_lock);
    std::lock_guard<std::mutex> lock2(mtx2, std::adopt_lock);
}

// 方法3: 使用scoped_lock (C++17)
void safe_operation3() {
    std::scoped_lock lock(mtx1, mtx2);
}

// 方法4: 超时锁
void safe_operation4() {
    std::timed_mutex mtx;
    if (mtx.try_lock_for(std::chrono::milliseconds(100))) {
        // 获得锁
        mtx.unlock();
    } else {
        // 超时处理
    }
}
```

## 2. 活锁

```cpp
// 活锁示例：两个线程相互谦让
class Account {
    std::mutex mtx;
    int balance;
public:
    // 可能导致活锁的转账
    bool transfer_livelock(Account& to, int amount) {
        while (true) {
            if (mtx.try_lock()) {
                if (to.mtx.try_lock()) {
                    // 成功获取两个锁
                    balance -= amount;
                    to.balance += amount;
                    to.mtx.unlock();
                    mtx.unlock();
                    return true;
                }
                mtx.unlock();
            }
            // 两个线程可能同时释放锁又同时尝试获取，导致活锁
        }
    }
    
    // 解决方案：随机退避
    bool transfer_safe(Account& to, int amount) {
        std::random_device rd;
        std::mt19937 gen(rd());
        std::uniform_int_distribution<> dis(1, 100);
        
        while (true) {
            if (mtx.try_lock()) {
                if (to.mtx.try_lock()) {
                    balance -= amount;
                    to.balance += amount;
                    to.mtx.unlock();
                    mtx.unlock();
                    return true;
                }
                mtx.unlock();
            }
            std::this_thread::sleep_for(
                std::chrono::microseconds(dis(gen)));
        }
    }
};
```

## 3. 优先级反转

```cpp
// 问题：低优先级线程持有锁，高优先级线程等待
// 解决方案：优先级继承

#include <pthread.h>

pthread_mutex_t mutex;
pthread_mutexattr_t attr;

void init_priority_inheritance_mutex() {
    pthread_mutexattr_init(&attr);
    // 设置优先级继承协议
    pthread_mutexattr_setprotocol(&attr, PTHREAD_PRIO_INHERIT);
    pthread_mutex_init(&mutex, &attr);
}
```

## 4. 虚假唤醒

```cpp
std::condition_variable cv;
std::mutex mtx;
bool ready = false;

void waiter() {
    std::unique_lock<std::mutex> lock(mtx);
    
    // 错误：可能虚假唤醒导致问题
    // cv.wait(lock);
    
    // 正确：使用谓词版本或循环检查
    cv.wait(lock, []{ return ready; });
    // 或
    while (!ready) {
        cv.wait(lock);
    }
}
```

## 5. Lost Wake-up

```cpp
// 问题：通知发生在等待之前
// 解决方案：总是在持有锁时检查条件

void correct_wait() {
    std::unique_lock<std::mutex> lock(mtx);
    // 即使在wait之前收到通知，条件也会被检查
    cv.wait(lock, []{ return ready; });
}

void correct_notify() {
    {
        std::lock_guard<std::mutex> lock(mtx);
        ready = true;
    }
    cv.notify_one();
}
```

## 6. 惊群问题（条件变量）

**问题**：`pthread_cond_broadcast()` 会唤醒所有等待线程，导致它们同时竞争 mutex 和资源，产生上下文切换和锁争用，称为**惊群效应（Thundering Herd）**。

**解决思路**：
1. ** prefer signal 而非 broadcast**：若无必要唤醒全部线程，用 `pthread_cond_signal()` 只唤醒一个。
2. **合理使用 broadcast**：仅当多个条件共享同一条件变量，或资源数量变化较大、需要让所有等待者重新评估时，才用 broadcast。
3. **设计层面规避**：让每个线程有独立"能处理"的逻辑，减少无意义唤醒；或用单一条件变量对应单一事件。
4. **内核层面**：Linux futex 实现已优化 broadcast 的批量唤醒和迁移，减轻惊群影响。
