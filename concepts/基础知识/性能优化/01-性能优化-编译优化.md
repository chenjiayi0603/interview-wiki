# 编译优化

## 一、编译器优化选项

### 1.1 GCC/Clang 优化级别

| 级别 | 说明 | 典型场景 |
|------|------|----------|
| `-O0` | 无优化，编译最快 | 调试阶段 |
| `-O1` | 基本优化，减小代码体积 | 开发测试 |
| `-O2` | 大多数优化（不含向量化） | 常规发布 |
| `-O3` | 最高优化，含自动向量化 | 性能敏感场景 |
| `-Os` | 侧重代码体积优化 | 嵌入式/空间受限 |
| `-Ofast` | `-O3` + `-ffast-math`，可能损失精度 | 数值计算，慎用于交易系统 |

### 1.2 关键编译选项

```bash
# CPU 架构优化
-O3 -march=native -mtune=native
# -march=native：针对当前 CPU 指令集生成代码（自动检测）
# -mtune=native：优化调度策略适配当前 CPU

# 链接时优化（LTO）
-flto -fuse-linker-plugin
# LTO 允许跨编译单元进行内联、常量传播、死代码消除

# 数学优化（慎用）
-ffast-math          # 快速数学运算（可能违反 IEEE 754 标准）

# 循环与内联
-funroll-loops       # 循环展开（增加代码体积换取速度）
-finline-functions   # 函数内联
-fomit-frame-pointer # 省略帧指针（节省寄存器）

# 完整推荐
g++ -O3 -march=native -mtune=native -flto -fomit-frame-pointer -DNDEBUG -o program program.cpp
```

### 1.3 PGO (Profile-Guided Optimization)

**原理**：根据实际运行数据优化代码分支、内联决策。

```bash
# 第一步：使用 -fprofile-generate 生成插桩版本
g++ -O3 -fprofile-generate -o program program.cpp

# 第二步：使用具有代表性的输入运行程序，生成 profile 数据
./program < typical_input
# 生成 .gcda 文件

# 第三步：使用 profile 数据重新编译
g++ -O3 -fprofile-use -o program_optimized program.cpp
```

**PGO 收益**：
- 分支预测优化：将热点分支布局到更优位置
- 内联决策：根据热点选择性地内联
- 代码布局：热代码聚合，提升指令缓存命中

### 1.4 静态链接 vs 动态链接

```bash
# 完全静态链接
g++ -static -o program program.cpp

# 选择性静态链接（仅静态链接特定库）
g++ -Wl,-Bstatic -lmylib -Wl,-Bdynamic -lpthread -o program program.cpp
```

**对比**：

| 特性 | 静态链接 | 动态链接 |
|------|----------|----------|
| 启动速度 | 快（无需加载共享库） | 慢（需 ld.so 解析） |
| 二进制体积 | 较大 | 较小 |
| 部署 | 单一文件，方便 | 需携带 .so |
| 安全更新 | 需重新编译 | 替换 .so 即可 |
| ASLR 兼容 | 部分受限 | 完全支持 |
| 低延迟推荐 | 推荐（减少启动抖动） | 常规场景 |

## 二、内联与分支预测

### 2.1 函数内联

```cpp
// 强制内联（仅建议在性能热点使用）
inline __attribute__((always_inline))
int fast_add(int a, int b) {
    return a + b;
}

// C++11+ 方式
inline int fast_add(int a, int b) __attribute__((always_inline));
```

**注意事项**：
- 过度内联导致指令缓存（I-Cache）膨胀，可能适得其反
- 编译单元间内联需要 LTO 或 `-flto`
- 虚函数无法内联（除非 devirtualization）

### 2.2 branch 分支预测优化

```cpp
// likely/unlikely 宏定义
#define likely(x)   __builtin_expect(!!(x), 1)
#define unlikely(x) __builtin_expect(!!(x), 0)

// 优化前：编译器无法判断哪个分支更常见
int process(int value) {
    if (value > 0) {
        return value * 2;  // 99.9% 走这里
    } else {
        return 0;          // 仅异常时
    }
}

// 优化后：告知编译器主分支
int process(int value) {
    if (likely(value > 0)) {
        return value * 2;
    } else {
        return 0;
    }
}
```

**量化影响**：
- 分支预测命中：延迟 1~5ns
- 分支预测失败：延迟 60~150ns（流水线冲刷）
- likely/unlikely 可带来 10%~40% 延迟优化（极度倾斜分支场景）

**注意**：错误使用（将低频分支标记为 likely）比不使用更糟糕。

### 2.3 减少分支：查找表替代 switch/if

```cpp
// 优化前：多个 if/switch
int get_value(int type) {
    if (type == 0) return 10;
    if (type == 1) return 20;
    if (type == 2) return 30;
    return 0;
}

// 优化后：查找表（无分支）
int get_value(int type) {
    static const int values[] = {10, 20, 30};
    if (type >= 0 && type < 3) {
        return values[type];
    }
    return 0;
}

// 条件移动指令（编译器自动优化）
int max(int a, int b) {
    return a > b ? a : b;  // 可能编译为 CMOV，无分支
}
```

## 三、指令级并行优化

### 3.1 减少数据依赖

```cpp
// 优化前：每次循环依赖前一次结果
int sum = 0;
for (int i = 0; i < n; ++i) {
    sum += data[i];  // 串行依赖链
}

// 优化后：循环展开，多条独立链
int sum1 = 0, sum2 = 0, sum3 = 0, sum4 = 0;
for (int i = 0; i < n; i += 4) {
    sum1 += data[i];
    sum2 += data[i+1];
    sum3 += data[i+2];
    sum4 += data[i+3];
}
int sum = sum1 + sum2 + sum3 + sum4;
```

### 3.2 SIMD 向量化

```cpp
#include <immintrin.h>

// 向量化累加求和（data 需 32 字节对齐）
void vectorized_sum(const int* data, size_t n, int& result) {
    __m256i sum_vec = _mm256_setzero_si256();  // 256 位向量寄存器
    for (size_t i = 0; i < n; i += 8) {        // 一次处理 8 个 int
        __m256i vec = _mm256_load_si256((__m256i*)&data[i]);
        sum_vec = _mm256_add_epi32(sum_vec, vec);
    }
    int sum[8];
    _mm256_store_si256((__m256i*)sum, sum_vec);
    result = sum[0] + sum[1] + sum[2] + sum[3] +
             sum[4] + sum[5] + sum[6] + sum[7];
}

// 自动向量化：编译器 -O3 可自动向量化简单循环
// #pragma omp simd 可辅助编译器
#pragma omp simd
for (int i = 0; i < n; ++i) {
    a[i] = b[i] * c[i];
}
```

### 3.3 IPC（每周期指令数）优化

**优化方向**：
- IPC < 0.5：存在严重流水线停顿（内存等待、分支预测失败）
- IPC 0.5~1.0：有优化空间
- IPC > 1.0：流水线利用较好（现代 CPU 可达到 2~4）

**提升 IPC 的方法**：
1. 减少数据依赖（循环展开）
2. 减少分支预测失败（查找表、likely/unlikely）
3. 减少缓存未命中（SoA、热冷分离、预取）
4. 使用 SIMD 指令

## 四、编译器属性与辅助优化

### 4.1 热/冷属性标记

```cpp
// 标记热函数（优化更积极）
__attribute__((hot))
int hot_function() { ... }

// 标记冷函数（优化不积极，减少 I-Cache 占用）
__attribute__((cold))
int cold_function() { ... }
```

### 4.2 对齐控制

```cpp
// 控制对齐（配合 SIMD 或缓存行优化）
struct alignas(64) AlignedStruct {
    int data[16];
};

// 变量对齐
alignas(64) int buffer[1024];
```

### 4.3 NDEBUG 的作用

```cpp
// 发布版本必须定义
#define NDEBUG
// - 禁用 assert()
// - 禁用某些标准库的调试检查（如 std::vector::at() 的 boundary check）
// - 减少分支和异常路径
```

## 五、编译优化注意事项

### 5.1 优化顺序建议

1. 先加 `-O2`（常规发布）
2. 确认正确性后加 `-O3 -march=native`
3. 如有多文件优化需求，加 `-flto`
4. 对特定热点做 PGO
5. 最后尝试 `-ffast-math`（需验证精度符合要求）

### 5.2 可能带来的问题

- **`-ffast-math`**：违反 IEEE 754，可能导致 NaN/Inf 处理不一致，交易场景慎用
- **`-O3`**：增加代码体积，可能 I-Cache miss 增加
- **`-flto`**：编译时间显著增加，需要更多内存
- **PGO**：profile 数据需有代表性，否则可能反向优化

### 5.3 面试高频追问

**Q：-O2 和 -O3 的差异到底多大？**
- 实测（CPU 密集场景）：-O2 → -O3 提升 10-30%，主要来自自动向量化和循环优化
- 但 -O3 会增加代码体积，可能 I-Cache miss 增加
- **建议**：先 -O2，只有确认热点后局部 -O3

**Q：LTO 的原理和代价？**
- 原理：编译器生成中间表示（IR），链接时跨编译单元优化（内联、常量传播、死代码消除）
- 代价：编译时间增加 20-50%，内存消耗翻倍
- **收益**：跨文件的 inline、模板实例化合并、虚拟调用去虚拟化

**Q：PGO 什么时候值得做？**
- 收益最明显：分支预测倾斜严重的程序、频繁调用的热点函数
- 需要：有代表性的输入数据（profile 数据偏差会导致反向优化）
- **典型收益**：5-20% 性能提升

**Q：`likely/unlikely` 真的有用吗？**
- 在预测极度倾斜（>99%）且分支在热点路径上有用
- GCC/Clang 认可，LLVM 不一定
- 错误标记比不标记更糟糕

### 5.4 调试 vs 优化

```bash
# 调试版本（关闭优化，保留符号）
g++ -g -O0 -o program_debug program.cpp

# 优化版本（保留部分调试信息）
g++ -g -O2 -o program_opt program.cpp  # 变量可能被优化掉，调试体验稍差
```
