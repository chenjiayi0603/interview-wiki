# 瓶颈诊断与治理

## 一、症状诊断速查

| 症状 | 可能原因 | 首要工具 |
|------|----------|----------|
| CPU 高但延迟高 | 锁竞争、上下文切换 | `perf record -e sched:sched_switch` |
| CPU 低但延迟高 | I/O 等待、系统调用 | `strace -c`, `iostat` |
| 内存不断增长 | 内存泄漏、容器膨胀 | AddressSanitizer, Massif |
| P99 突增 | GC/THP/中断抖动 | `cyclictest`, `perf stat -I` |
| 吞吐上不去 | 线程过多/过少、锁竞争 | `perf stat`, `vmstat` |
| 服务偶发超时 | 调度延迟、swap | `vmstat 1`, `cat /proc/interrupts` |

## 二、详细诊断流程

### 2.1 建立基线

**必须做的第一步**：固定版本/配置/数据集，记录关键指标。

```bash
# 基线记录模板
cat > baseline.csv << EOF
date,version,qps,p50,p99,p999,cpu%,rss,context_switches
2026-06-01,v2.3.0,50000,1.2ms,5.8ms,15.3ms,65%,2.1GB,15000/s
EOF

# 每次优化后对比
# 无基线 = 无法证明优化有效
```

### 2.2 症状分类

#### 症状 A：尾延迟高（P99/P999 恶化）

**排查步骤**：
1. 检查是否有锁竞争：`perf record -e sched:sched_switch -g -p <pid>`
2. 检查是否有 THP 抖动：查看 `/sys/kernel/mm/transparent_hugepage/enabled`
3. 检查是否发生 swap：`vmstat 1` 查看 si/so 列
4. 检查中断是否干扰业务 CPU：`cat /proc/interrupts`
5. 检查 CPU 频率是否稳定：`cat /sys/devices/system/cpu/cpu*/cpufreq/scaling_cur_freq`

**解决方案**：
- 锁分拆/无锁
- 禁用 THP
- `mlockall()` 锁内存
- CPU 隔离 + 中断绑定
- performance governor

#### 症状 B：QPS 上不去（吞吐瓶颈）

**排查步骤**：
1. `perf stat` 看 CPUs utilized 是否低
2. 低 → I/O 瓶颈，高 → CPU/锁瓶颈
3. 检查线程数是否合适（`ps -eLf | grep program | wc -l`）
4. 检查系统调用频率：`strace -c -p <pid>`

**解决方案**：
- I/O 瓶颈 → 批量化、异步、零拷贝
- 线程过多 → 减到核心数或略少
- 锁竞争 → 分片锁、无锁队列、局部队列

#### 症状 C：高 CPU 但低吞吐

**排查步骤**：
1. `perf record -g` 生成火焰图
2. 看最宽的栈是什么
3. 检查 IPC：`perf stat` 的 insn per cycle

**典型根因**：
- 自旋锁（spinlock）忙等
- 无效的轮询
- 大量上下文切换
- cache-misses 过高

#### 症状 D：内存增长/泄漏

**排查步骤**：
1. `top` 看 RES 持续增长
2. `pmap -x <pid>` 看哪段内存增长
3. AddressSanitizer 检测泄漏
4. Massif 分析分配时序

**解决方案**：
- 查泄漏源修复
- 限制容器大小（LRU 淘汰）
- 改用对象池/内存池

## 三、优化清单（按优先级执行）

### 3.1 建立压测基线

固定版本、配置、数据集，记录 CPU/内存/延迟/吞吐。

**做法**：专用压测机，固定 QPS/body 大小/并发数，跑 10 分钟记录 P50/P99/CPU%/RSS，保存为 `baseline.csv`。

### 3.2 采集火焰图

```bash
perf record -F 99 -g -p <pid> -- sleep 60
# 生成火焰图，找最宽栈
```

### 3.3 减少锁/同步

| 技术 | 说明 |
|------|------|
| 分片锁 | 全局 map 一把锁 → 64 分片 |
| 缩短临界区 | 锁内只入队，不写盘 |
| 读写锁 | `shared_mutex` 读多写少 |
| 无锁 | SPSC 队列、CAS 原子操作 |

### 3.4 减少分配

- 对象池：热点路径对象复用
- `string_view`：替代字符串拷贝
- `reserve()`：容器预分配
- PMR：`monotonic_buffer_resource`

### 3.5 减少拷贝与序列化

- Protobuf 替代 JSON
- FlatBuffers 零拷贝解析
- readv/writev 批量收发

### 3.6 改善调度

- 线程数 = 核心数或略少
- 绑定 NUMA，避免跨节点访问
- 减少 wakeups

### 3.7 IO 路径

- 异步化/批量化
- 顺序写取代随机写
- 网络参数调优

### 3.8 编译与指令级

- `-O3 -march=native`
- LTO/PGO
- SIMD 热点

### 3.9 观测与防回退

- 尾延迟告警
- 每次发版前回归基线压测
- P99 > 阈值则阻断发布

## 四、典型案例

### 4.1 案例：CPU 不满但 QPS 低

**症状**：CPU 30%，延迟 P99 100ms，QPS 不到预期 30%。

**排查**：
```
1. perf stat → CPUs utilized 0.3 → 大量时间在等待
2. strace -c → read 系统调用占 70%
3. 检查代码 → 每次处理消息都 read 4K 小包
```

**根因**：网络读取频繁小系统调用。

**优化**：
```
1. 改用 readv 批量读取 → QPS 提升 2x
2. 增大 socket 缓冲区 → 减少系统调用次数
3. 最终效果：CPU 提升到 70%，QPS 达到预期
```

### 4.2 案例：P99 抖动严重

**症状**：P50 正常 1ms，但 P99 偶尔跳到 50ms。

**排查**：
```
1. cyclictest → 最大延迟 200μs，但无 RT 内核
2. cat /proc/interrupts → 业务线程所在 CPU 处理大量中断
3. 检查 THP → enabled
```

**根因**：网卡中断干扰 + THP 抖动。

**优化**：
```
1. 禁用 THP
2. 中断绑定到非业务 CPU
3. mlockall 锁定内存
4. 安装 PREEMPT_RT 内核
5. 最终效果：P99 稳定在 2ms
```

### 4.3 案例：内存持续增长

**症状**：RSS 从 2GB 增长到 8GB，最终 OOM。

**排查**：
```
1. Massif → 某 map 容器不断插入新 key
2. 业务逻辑 → 缓存了所有历史查询结果
3. 无淘汰机制
```

**根因**：缓存无限增长。

**优化**：
```
1. 添加 LRU 淘汰
2. 限制缓存最大条目数
3. 最终效果：RSS 稳定在 2.5GB
```

## 五、优化优先级矩阵

```
                    影响范围
                   大      小
               ┌──────┬──────┐
          高   │ 锁优  │ SIMD │
               │ 化    │      │
  收益        ├──────┼──────┤
          低   │ I/O  │ 小功 │
               │ 优   │ 能优 │
               │ 化    │ 化   │
               └──────┴──────┘
```

**现实优先级建议**：
1. ✅ 锁优化（分片、无锁）：收益最高，风险中等
2. ✅ 减少分配（对象池、预分配）：收益高，风险低
3. ✅ 减少拷贝（零拷贝、批量）：收益高，风险低
4. ✅ 调度优化（绑核、NUMA）：收益高，风险低
5. ✅ I/O 批量化：收益中，风险低
6. 🔶 编译优化（-O3、LTO）：收益中，需回归
7. 🔶 SIMD 手写：收益看场景，复杂度高
8. ❌ 过早优化无基线的微优化：风险大，不可靠
