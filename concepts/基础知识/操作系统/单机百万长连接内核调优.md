## 数据支撑

**机器配置**：单机 8 核 16G，千兆网卡，Linux 4.x（CentOS 7）

**内存拆解**（100万连接 ~8GB 总内存）：

| 层 | 内存 | 说明 |
|----|------|------|
| TCP 内核元数据 | ~3–4GB | `tcp_sock` 结构体 + `sk_buff` 队列，约 3–4KB/连接 |
| conntrack entries | ~300MB | 每 entry ~300 字节，100万 × 300B |
| TCP buffer（调优后） | ~2GB | `tcp_rmem/wmem` min=1KB，100万 × 2KB |
| 用户态应用层 | ~2–3GB | 每连接 `Connection` 对象（fd + 读写 buffer 各 512B + 状态机）~1–2KB |
| **总计** | **~8–10GB** | 16G 机器跑 100 万连接，`free` 剩 6–7GB |

**核心调优参数**：

| 参数 | 默认值 → 调优值 | 作用 |
|------|----------------|------|
| `tcp_rmem/wmem` min | 4KB → **1KB** | 每连接 buffer 从 8GB 降到 2GB |
| `ulimit -n` | 1024 → **1,048,576** | 文件描述符上限 |
| `net.core.somaxconn` | 128 → **65535** | listen 队列 |
| `nf_conntrack_max` | 65,536 → **2,097,152** | conntrack 表容量（百万连接的隐藏雷） |
| `nf_conntrack_tcp_timeout_established` | 5天 → **600s** | 僵尸连接清理 |

## 理论支撑

百万连接最容易忽略的 conntrack：netfilter 连接追踪子系统记录每条 TCP 连接状态，`nf_conntrack_max` 默认 65536 远不够。表满时内核直接丢 SYN 包，业务侧表现为间歇性连接失败，`dmesg` 才能看到 `nf_conntrack: table full, dropping packet`。四条参数协作调优（max + buckets + established timeout + time_wait timeout）缺一不可，只调 max 不调 timeout 会导致僵尸 entry 越积越多。

SO_REUSEPORT 绑定多进程，内核按 4 元组哈希均匀分发，避免 accept 队列成为单点瓶颈。

## 追问预案

**Q：conntrack 表满为什么不直接用 NOTRACK？**
> 网关层有 iptables 限流和 ACL 规则，依赖 stateful 连接追踪，不能全局 NOTRACK。但内部 RPC 端口（不需要状态追踪的）做了 NOTRACK 跳过 conntrack，优化了内部 RPC 的建连开销。

**Q：压测是自研工具还是开源工具？**
> 单机模拟 50 万连接用自研压测客户端（同套 Libev 框架），多机叠加打满 100 万。辅助 HTTP 网关压测用 wrk，性能瓶颈定位用 perf + FlameGraph 火焰图，协议栈错误统计用 `ss -s` / `nstat`。
