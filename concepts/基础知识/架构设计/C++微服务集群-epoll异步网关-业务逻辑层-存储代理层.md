# C++ 微服务集群（epoll 异步网关 + 业务逻辑层 + 存储代理层）

## 简历原文
自研 C++ 微服务集群（epoll 异步网关 + 业务逻辑层 + 存储代理层），基于注册中心的服务发现，全链路自建监控

## 数据支撑

| 指标 | 值 | 说明 |
|------|----|------|
| 注册用户 | 900 万 | |
| 峰值 QPS | 5,000 | 社交金融 IM，DAU 百万级 |
| 持续运营 | 4 年（2015–2019） | 生产稳定性验证 |
| 服务层次 | 3 层（网关 / 业务 / 存储代理） | 职责分离 |

**5000 QPS 合理性**：1000万+注册 × 10–15% DAU ≈ 100–150万 DAU，同时在线 ~5万，人均 0.1 QPS，峰值 ~5000 QPS。金融类社交用户活跃度低于娱乐类，同类产品（脉脉、虎扑）DAU 百万级 QPS 在 3000–8000 区间。

**MySQL 容量上限推导**（被追问"架构能跑多少 QPS"）：
- 硬件：单机 8C16G，SATA SSD，InnoDB fsync ~1–3ms
- `innodb_flush_log_at_trx_commit=1` + `sync_binlog=1` + 半同步复制
- 单主事务吞吐：3000–5000 tx/s（InnoDB group commit 合并 fsync）
- 每条消息 2 事务（msg INSERT + session UPDATE）→ 最大消息吞吐 1500–2500 msg/s
- 消息占总 QPS ~12%，最大总 QPS ≈ 10000–20000 QPS（MySQL 是瓶颈天花板）
- 实际峰值 5000 QPS 远低于上限，系统有充足余量

## 理论支撑

三层架构职责：
- 网关层（epoll 异步）：连接管理、协议解析、路由转发，无业务逻辑
- 业务逻辑层：消息处理、好友关系、群组管理，依赖缓存
- 存储代理层：MySQL + Redis + MongoDB 的统一访问封装，连接池管理、读写分离路由

注册中心服务发现：服务节点启动时向注册中心（ZK/Etcd）注册，消费方实时订阅节点列表变化。相比硬编码 IP 地址，支持动态扩缩容和故障摘除。

## 业界对标

- **微信后台架构（公开分享）**：三层 epoll 网关 + 业务逻辑 + 存储代理的架构是 IM 系统的经典模式
- **美团 IM 后台**：同样 C++ epoll 异步框架 + 多层服务分离
