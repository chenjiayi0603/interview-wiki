# 布隆过滤器预筛（FPR 1%，100万 Key → 1.2MB）

**简历原文**：布隆过滤器预筛，替代原有在线阻塞式 Key 扫描，实现大规模实例大 Key / 热 Key 实时检测

## 数据支撑

| 指标 | 值 | 计算来源 |
|------|----|---------|
| FPR（假阳性率） | 1% | 10 个哈希函数 × 10 bits/key 的标准配置 |
| 100万 Key 布隆过滤器内存 | 1.2MB | 100万 × 10 bits / 8 = 1.25MB |
| 不用布隆过滤器（全量计数器） | 100MB+ | 每 Key ~100 字节计数器 × 100万 |
| 内存节省 | 99%+ | 实际热 Key 约 1% 数量级，计数器仅分配给热 Key |

布隆过滤器周期性重建（每 N 分钟全量重建），防止历史低频 Key 长期占用误报位。

## 理论支撑

布隆过滤器是 m bit 数组 + k 个独立哈希函数，插入时将 k 个哈希位置置 1，查询时检查 k 个位置是否全为 1。假阳性率公式：`FPR = (1 - e^(-kn/m))^k`，取 k=10, m/n=10 时 FPR ≈ 1%。不存在假阴性（false negative）——实际的大 Key / 热 Key 一定会被检测到。

1% 假阳性在业务层面可接受：被误判为热 Key 的低频 Key，在 top N 统计聚合时会因为计数器值极低而自然被过滤，不影响最终输出结果。

## 业界对标

- **Redis 4.0+ RedisBloom 模块**：官方布隆过滤器实现，算法与本方案完全一致
- **BigTable / LevelDB 中的 Bloom Filter**：用于 SST 文件中快速判断 key 是否存在，同样避免不必要的磁盘访问
- **Cassandra 行级 Bloom Filter**：每个 SST 文件携带 bloom filter，读路径优化

## 追问预案

**Q：布隆过滤器 FPR 1% 对结果准确性有什么影响？**
> FPR 1% 意味着低频 Key 有 1% 概率被误判为候选 Key，分配计数器。但因为这些低频 Key 的实际访问计数很低，在 top N 聚合输出时会被真正的热 Key 淘汰。整体大 Key / 热 Key 检测准确率不受 FPR 影响。

**Q：布隆过滤器不支持删除，怎么处理过期 Key？**
> 周期性全量重建（如每 30 分钟），避免历史 Key 长期占用假阳性位。重建期间短暂多分配少量计数器（FPR 略高），不影响业务。如果需要支持删除，可以用 Counting Bloom Filter（每个 bit 改为计数器），内存代价约 4×，但对本场景不必要。
