# 网络协议 · 面试考点汇总

> 涵盖 TCP/UDP/QUIC 协议、拥塞控制、内核调优、网络编程、延迟优化等 120+ 面试题。

---

## 一、TCP 协议基础

### Q1: TCP 三次握手为什么需要三次？
- 防止已失效的连接请求到达服务端，造成资源浪费
- 两次无法确认双方收发能力（服务端不知道客户端能否接收 SYN+ACK）
- 第一次：服务端确认客户端发送正常
- 第二次：客户端确认服务端收发正常
- 第三次：服务端确认客户端接收正常

### Q2: TCP 四次挥手为什么需要四次？
- TCP 全双工，关闭需要双方各自发 FIN
- 被动方收到 FIN 后可能还有数据要发，先回 ACK，等数据发完再发 FIN
- 延迟确认可使 ACK 与 FIN 合并（抓包常见"三次挥手"）

### Q3: TIME_WAIT 为什么是 2MSL？
- MSL（Maximum Segment Lifetime）：报文最大生存时间（Linux 默认 30s，2MSL=60s）
- 保证最后的 ACK 可重传（若丢失，对端会重发 FIN）
- 让本连接产生的所有报文从网络中消失，避免影响新连接

### Q4: TCP 如何保证可靠性？
序号+确认、超时重传、快速重传（3 重复 ACK）、SACK、校验和、流量控制（滑动窗口）、拥塞控制

### Q5: 什么是半连接队列？全连接队列？
- 半连接队列（SYN Queue）：SYN_RCVD 状态的连接，收到 SYN 后放入
- 全连接队列（Accept Queue）：ESTABLISHED 状态的连接，收到第三次 ACK 后放入
- 满队列处理：syncookies 防 SYN Flood；tcp_abort_on_overflow 控制全连接队列溢出行为

### Q6: 为什么说 TCP 是字节流？
- 无边界，发送方写入的数据和接收方读取的数据没有对应关系
- 有序，按序交付，乱序包暂存
- 自动去重，丢弃重复报文

### Q7: TCP 粘包问题如何解决？
- 固定长度报文
- 特殊分隔符（如 `\r\n`）
- 长度字段 + 数据（TLV 编码）
- 应用层协议包含消息边界

### Q8: 同时关闭会发生什么？
- 双方都发 FIN，都收到对方的 FIN 后进入 CLOSING 状态
- 回复 ACK 后都进入 TIME_WAIT

### Q9: SYN Flood 攻击原理与防御？
- 攻击者伪造源 IP 发大量 SYN，耗尽服务端半连接队列
- 防御：
  - SYN Cookie（推荐，默认开启）
  - 减少 `tcp_synack_retries` 加速超时
  - 增大 `tcp_max_syn_backlog`

## 二、UDP 协议

### Q10: UDP 和 TCP 的区别？
无连接 vs 面向连接；不可靠 vs 可靠；无流控/拥控 vs 有；8 字节 vs 20+ 字节；面向报文 vs 字节流；一对多 vs 一对一

### Q11: 为什么 DNS 用 UDP？
请求小（一个包），响应快；丢包重试成本低；无连接节省服务器资源。
DNS 用 TCP 的场景：响应超 512 字节（EDNS 扩展）、区域传输（AXFR/IXFR）。

### Q12: UDP 如何实现可靠传输？
应用层实现：序号、确认（ACK）、超时重传、校验（CRC/MD5）、流控。或使用 QUIC。

### Q13: UDP 有粘包吗？
UDP 面向报文，每个 sendto 对应一个独立报文，有边界，不存在 TCP 的粘包问题。但应用层需自己处理报文边界。

### Q14: UDP 单包最大多大？
理论 65507 字节（65535 - 20 IP - 8 UDP）。超 MTU 会 IP 分片，建议 ≤ 1472 避免分片。

### Q15: UDP 校验和是必须的吗？
IPv4 中可选（为 0 表示未计算）；IPv6 中必选。

### Q16: UDP connect 的作用？
- 指定默认目标地址，之后可用 send/recv 替代 sendto/recvfrom
- 过滤非预期源的包
- 可收到 ICMP 错误（如端口不可达）

## 三、QUIC 协议

### Q17: QUIC 和 TCP 的主要区别？
- 握手：QUIC 1 RTT（0-RTT 恢复），TCP + TLS 2~3 RTT
- 队头阻塞：QUIC 多流解耦，TCP 单流阻塞整连接
- 连接迁移：QUIC 用 Connection ID，换 IP 不断连
- 拥塞控制：QUIC 用户态可插拔，TCP 内核固定
- 加密：QUIC 内置 TLS 1.3，TCP 需额外 TLS

### Q18: QUIC 为什么解决队头阻塞？
TCP 单连接 = 单流，一个丢包导致后续所有包被阻塞。QUIC 单连接 = 多个独立流，一个流丢包只阻塞该流，其他流不受影响。

### Q19: QUIC 流量控制与 TCP 有何不同？
TCP 连接级单窗口，QUIC 连接级 + 流级双窗口，更细粒度。

### Q20: QUIC 适合什么场景？不适合什么场景？
适合：HTTP/3、视频直播、移动 App、弱网环境。不适合：存量 TCP-only 系统、老旧网关环境。

## 四、拥塞控制与流量控制

### Q21: 流量控制与拥塞控制的区别？
| 对比 | 流量控制 | 拥塞控制 |
|------|----------|----------|
| 目标 | 保证接收方来得及处理 | 避免网络过载 |
| 范围 | 端到端 | 全局 |
| 机制 | 滑动窗口（rwnd） | 拥塞窗口（cwnd） |
| 信号 | ACK 中 window 字段 | 丢包 / RTT |

### Q22: 滑动窗口的工作原理？
- 发送方在未收到确认前可连续发送窗口内数据
- 接收方通过 ACK 中的 Window 字段通告缓冲区剩余空间
- 发送窗口 = min(rwnd, cwnd)
- 窗口为 0 时停止发送（Zero Window），发送 Window Probe

### Q23: 拥塞控制的四个算法？
1. **慢启动**：cwnd 指数增长（1→2→4→8...），直到 ssthresh
2. **拥塞避免**：cwnd 线性增长（每 RTT + 1 MSS）
3. **快速重传**：收到 3 个重复 ACK 触发重传
4. **快速恢复**：重传后 cwnd 减半，随后线性增长

### Q24: 超时重传 vs 快速重传？
| | 超时重传 | 快速重传 |
|---|---------|---------|
| 触发 | RTO 超时 | 3 个重复 ACK |
| 拥塞程度 | 严重 | 轻度 |
| cwnd | 重置为 1 | 减半 |
| 后续 | 重新慢启动 | 快速恢复 |

### Q25: CUBIC 和 BBR 的区别？
- **CUBIC**：基于丢包，丢包即降速，弱网随机丢包吞吐下降
- **BBR**：基于模型（带宽+RTT），不依赖丢包，弱网更稳健

### Q26: SACK 的作用？
选择性确认，告诉发送方具体收到哪些段，只重传丢失部分，提升丢包恢复效率。

### Q27: D-SACK 的作用？
判断是包丢了还是 ACK 丢了、网络是否乱序、重传是否过度。

### Q28: Nagle 算法和延迟 ACK 的交互问题？
Nagle 等 ACK 才能发下一包，延迟 ACK 等更多包才回 ACK，相互等待导致延迟增大。实时场景建议关闭 Nagle（TCP_NODELAY）。

## 五、TCP 调优与内核参数

### Q29: 如何优化 TIME_WAIT？
- `tcp_tw_reuse = 1`（出站连接复用）
- `tcp_fin_timeout = 15~30`（加速 FIN_WAIT_2）
- 增大 `tcp_max_tw_buckets`
- 注意：`tcp_tw_recycle` 已从 Linux 4.12 移除，不要使用

### Q30: 如何优化连接队列？
- 增大 `listen(fd, backlog)`、`somaxconn`、`tcp_max_syn_backlog`
- 开启 `tcp_syncookies`
- `ss -lnt` 查看队列状态（Recv-Q 排队数，Send-Q 总大小）

### Q31: Keepalive 能检测应用假死吗？
**不能**。TCP Keepalive 由内核协议栈处理，即使应用假死，内核也会自动回复保活探测。应用级假死必须用**应用层心跳**检测。

### Q32: 应用层心跳和 TCP Keepalive 的区别？
- TCP Keepalive：内核实现，检测物理链路，速度慢（默认 2 小时）
- 应用层心跳：业务层实现，可检测应用假死，速度快（秒级）

### Q33: epoll 的 LT 和 ET 模式区别？
LT 持续通知，ET 仅变化通知一次。ET 必须循环读到 EAGAIN，需配合非阻塞 I/O。

### Q34: SO_REUSEPORT 的作用？
多进程绑定同一端口，内核负载均衡。消除惊群，提高多核利用率，支持不停服更新。

### Q35: TCP_NODELAY 的作用？
关闭 Nagle 算法。适用于实时性要求高的场景（游戏、实时通信），避免小包延迟。

### Q36: TFO（TCP Fast Open）的作用？
允许在 SYN 包中携带数据，重连时减少 1 RTT。配合 TLS 1.3 0-RTT 可做到理论 0 RTT。

### Q37: TLS 1.2 vs 1.3？
TLS 1.3 握手仅 1 RTT，支持 0-RTT 恢复（PSK），取消不安全的 RSA 密钥交换，强制前向安全。

## 六、网络编程

### Q38: select/poll/epoll 区别？
select：1024 fd 上限，O(n) 遍历；poll：无上限，O(n) 遍历；epoll：红黑树管理，O(1) 就绪获取，支持 ET。

### Q39: 如何设计高性能服务器？
1. epoll ET + Reactor
2. 线程池分离 I/O 与业务
3. 无锁数据结构
4. 零拷贝（sendfile/mmap）
5. 内存池
6. 连接池
7. 异步日志
8. 应用层心跳

### Q40: HTTP/1.1、HTTP/2、HTTP/3 区别？
- **HTTP/1.1**：持久连接、管道化、队头阻塞严重
- **HTTP/2**：二进制分帧、多路复用、HPACK 头部压缩、服务器推送、TCP 级队头阻塞
- **HTTP/3**：基于 QUIC（UDP），0-RTT，流间无队头阻塞，连接迁移

### Q41: WebSocket 握手过程？
客户端发 Upgrade: websocket + Sec-WebSocket-Key，服务端回 101 状态码 + Sec-WebSocket-Accept。

### Q42: gRPC vs libev+protobuf 选型？
微服务/RPC 用 gRPC（开发效率高），极致性能/自定义协议用 libev+protobuf。

### Q43: Reactor 模型有哪几种？
- 单 Reactor + 单线程（Redis）
- 单 Reactor + 线程池
- 多 Reactor + 线程池（Netty、Nginx、gRPC）

## 七、延迟与性能

### Q44: 同机房 RPC 延迟大概多少？
纯 RPC 一跳 0.5~2ms（优化后 <1ms），含 Nginx 代理 1~3ms。

### Q45: CPU 100% 时延迟会恶化多少倍？
10~100 倍（取决于瓶颈位置和链路复杂度）。

### Q46: 微信 RPC 过载阈值是多少？
队列等待 > 20ms 触发限流，默认超时 500ms。

### Q47: Nagle + 延迟 ACK 为什么导致延迟？
Nagle 攒包等 ACK，延迟 ACK 等包才回 ACK，死锁式等待。解决方法：关闭 Nagle 或关闭延迟 ACK。

### Q48: TCP 连接的建立和关闭各需多少 RTT？
建立：1 RTT（三次握手），关闭：1 RTT（四次挥手，ACK 与 FIN 可能合并）。

### Q49: TLS 1.3 相比 TLS 1.2 减少了多少 RTT？
完整握手：2 RTT → 1 RTT；重连：1 RTT → 0 RTT。

## 八、HTTP / 协议扩展

### Q50: 什么是正向代理和反向代理？
- 正向代理：代理客户端（如翻墙 VPN）
- 反向代理：代理服务端（如 Nginx、负载均衡）

### Q51: Nginx 负载均衡算法？
轮询（rr）、加权轮询（wrr）、最少连接（lc）、IP hash（iphash）、最短响应时间

### Q52: LVS 的三种模式？
NAT（网络地址转换）、DR（直接路由）、TUN（隧道）。

### Q53: HTTP/2 为什么还慢？
虽然 HTTP/2 解决了 HTTP 层队头阻塞，但 TCP 层仍有一个连接一个流的队头阻塞。HTTP/3 通过 QUIC（UDP多流）彻底解决。

### Q54: HTTP 长连接和短连接的区别？
短连接：每次请求都新建 TCP 连接（HTTP/1.0 默认）。长连接：复用 TCP 连接（Connection: keep-alive），减少握手开销。

### Q55: DNS 解析过程？
1. 浏览器缓存 → 2. 系统缓存（hosts）→ 3. 本地 DNS 服务器 → 4. 根 DNS → 5. 顶级域 DNS → 6. 权威 DNS → 7. 返回 IP

## 九、综合设计

### Q56: 如何设计一个分布式 IM 长连接系统？
- 连接管理：长连接池、心跳保活
- 消息路由：一致性 hash 或发布订阅
- 多端同步：seq 号 + 拉取
- 断线重连：指数退避重试
- 状态同步：在线状态广播

### Q57: 如何设计一个 RPC 框架？
- 服务注册与发现（Consul/etcd）
- 负载均衡（加权轮询 / 一致性 hash）
- 序列化（protobuf / thrift）
- 传输层（TCP/HTTP2）
- 心跳与健康检查
- 超时与重试策略
- 限流熔断

### Q58: 如何排查 TCP 连接问题？
- `netstat -anp`：查看连接状态
- `ss -lnt`：查看队列积压
- `tcpdump + Wireshark`：抓包分析
- `strace -p <pid>`：跟踪系统调用
- `cat /proc/net/tcp`：内核 TCP 信息

### Q59: 四元组 vs 五元组？
- 四元组：源IP、源端口、目的IP、目的端口（标识连接）
- 五元组：协议 + 四元组（标识一条 socket 连接）

### Q60: 什么是惊群？如何解决？
多进程在同一个 listen fd 上 accept，新连接到来时所有进程被唤醒。解决：SO_REUSEPORT（每个进程独立 listen socket）或使用 `EPOLLEXCLUSIVE`。
