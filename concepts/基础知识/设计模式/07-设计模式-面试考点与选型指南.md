## 一、高频面试 Q&A

### Q1: 单例模式的线程安全实现？

**参考答案**：
- **饿汉**：程序启动时创建，线程安全，但启动慢、浪费资源
- **懒汉双检锁**：`std::atomic` + `mutex`，防指令重排与重复创建
- **C++11 局部静态（Meyers）**：标准保证线程安全，日常最省事

```cpp
// C++11 局部静态（推荐）
struct Singleton {
    static Singleton& inst() {
        static Singleton s;
        return s;
    }
};
```

详见 `03-创建型模式.md`。

### Q2: 工厂方法和抽象工厂的区别？

**参考答案**：
- **工厂方法**：一个创建接口 → **一种**产品类型，子类决定具体类
- **抽象工厂**：一个工厂接口 → **一族**配套产品（产品族），换工厂换整套风格

```cpp
// 工厂方法：只产一种 Button
struct ButtonFactory {
    virtual std::unique_ptr<Button> create() = 0;
};
struct WinButtonFactory : ButtonFactory {
    std::unique_ptr<Button> create() override { return std::make_unique<WinButton>(); }
};

// 抽象工厂：一次产一族控件
struct GuiFactory {
    virtual std::unique_ptr<Button> createButton() = 0;
    virtual std::unique_ptr<Checkbox> createCheckbox() = 0;
};
struct WinGuiFactory : GuiFactory {
    std::unique_ptr<Button> createButton() override { return std::make_unique<WinButton>(); }
    std::unique_ptr<Checkbox> createCheckbox() override { return std::make_unique<WinCheckbox>(); }
};
```

### Q3: 装饰器 vs 继承？

**参考答案**：
- **装饰器**：运行时**嵌套包装**，按需叠加能力
- **继承**：编译期固定超类，每种组合导致类爆炸
- 装饰器减轻「每种组合一个子类」的问题

```cpp
struct VisualComponent { virtual void draw() = 0; };
struct Text : VisualComponent { void draw() override { /* 纯文字 */ } };

struct Decorator : VisualComponent {
    VisualComponent& inner;
    explicit Decorator(VisualComponent& i) : inner(i) {}
};
struct BorderDec : Decorator {
    using Decorator::Decorator;
    void draw() override { /* 画边框 */ inner.draw(); }
};
struct ScrollDec : Decorator {
    using Decorator::Decorator;
    void draw() override { /* 滚动条 */ inner.draw(); }
};
// 运行时组合：BorderDec(ScrollDec(text))
```

### Q4: 代理 vs 装饰器？

**参考答案**：
- **代理**：**控制访问**（延迟加载、权限、远程、缓存），对外尽量**像本体**
- **装饰器**：**增强行为**（加功能），调用方知道包了一层也无妨
- 比喻：代理「替你挡事」，装饰器「替你加料」

```cpp
struct Image { virtual void display() = 0; };

// 代理：延迟加载
struct ProxyImage : Image {
    std::unique_ptr<Image> real;
    std::string file;
    void display() override {
        if (!real) real = loadFromDisk(file);  // 访问时才加载
        real->display();
    }
};

// 装饰器：额外日志
struct LoggingImage : Image {
    Image& inner;
    void display() override { log("show"); inner.display(); }
};
```

### Q5: 观察者 vs 发布-订阅？

**参考答案**：
- **观察者**：`Subject` **直接持有** `Observer` 列表，一对多推送
- **发布-订阅**：发布者与订阅者**不互相认识**，中间 **Broker** 按主题分发
- 发布-订阅更松耦合、可跨进程

详见 `05-行为型模式.md` §1.2。

### Q6: 策略 vs 状态？

**参考答案**：
- **策略**：客户端**主动注入**算法，策略间**通常无转移关系**
- **状态**：对象内部状态变化 → 行为变化，状态对象常**知道下一状态**

```cpp
// 策略：外部随时替换「怎么算」
struct PayContext {
    struct Strategy { virtual int calc(int n) = 0; };
    Strategy* s;
    void set(Strategy* ns) { s = ns; }
    int checkout(int n) { return s->calc(n); }
};

// 状态：内部 request 触发迁移
struct Turnstile {
    struct State { virtual void coin(Turnstile& m) = 0; };
    State* st;
    void coin() { st->coin(*this); }
};
```

### Q7: 什么是依赖注入（DI）？

**参考答案**：
- 依赖注入（DI）是实现控制反转（IoC）的一种方式
- 把对象需要的依赖通过构造/接口/属性**从外部传进来**，对象不用自己 new
- 利于解耦、单元测试和灵活扩展

```cpp
struct UserRepo { virtual User load(int id) = 0; };
struct UserService {
    UserRepo& repo;  // 不在内部 new SqlRepo()
    explicit UserService(UserRepo& r) : repo(r) {}
    User get(int id) { return repo.load(id); }
};
// 测试注入 FakeRepo；生产注入 SqlRepo —— 同一套 UserService
```

### Q8: 如何选择设计模式？

**参考答案**：
1. 先写清**变化点**（需求里哪块最常改、哪块需要扩展）
2. 用 **SOLID** 衡量：是否单一职责、是否依赖抽象、开闭是否友好
3. **能函数/组合解决就不上模式**；重复三次再抽象
4. 对照"坏味道"：if-else 链 → 策略/状态；频繁 new 族对象 → 工厂

```cpp
// 分支爆炸时优先考虑策略
int price(const Order& o, const std::string& userType) {
    if (userType == "vip") return (int)(o.amount * 0.8);
    if (userType == "svip") return (int)(o.amount * 0.7);
    return o.amount;
}
// → 每种用户一个 PricingStrategy
```

## 二、模式对比速查

| 对比项 | 模式 | 核心区别 |
|--------|------|---------|
| 创建对象 | Factory vs Abstract Factory | 一种 vs 一族 |
| 扩展行为 | Decorator vs Inheritance | 运行时 vs 编译期 |
| 控制访问 | Proxy vs Decorator | 控制 vs 增强 |
| 通知机制 | Observer vs Pub-Sub | 直接持有 vs Broker |
| 行为变化 | Strategy vs State | 外部注入 vs 内部转移 |
| 请求处理 | Chain of Resp. vs Command | 链式传递 vs 封装为对象 |

## 三、设计模式选型清单

| 需求/问题 | 推荐模式 |
|-----------|---------|
| 全局唯一实例 | Singleton |
| 不知道具体类，要由子类决定 | Factory Method |
| 需要换整套产品族 | Abstract Factory |
| 复杂对象分步构建 | Builder |
| 接口不兼容 | Adapter |
| 运行时按需叠加能力 | Decorator |
| 控制对对象的访问 | Proxy |
| 为子系统提供统一接口 | Facade |
| 一对多通知 | Observer |
| 算法族互换 | Strategy |
| 请求封装/撤销/排队 | Command |
| 算法骨架固定，步骤可定制 | Template Method |
| 状态决定行为 | State |
| 请求链式处理 | Chain of Responsibility |
