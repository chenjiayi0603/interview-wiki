## 4.1 主要延迟来源

| 来源           | 说明                                     | 缓解思路                         |
|----------------|------------------------------------------|----------------------------------|
| 内核不可抢占   | 持 spinlock、关抢占等                    | PREEMPT_RT、减少持锁时间         |
| 中断与下半部   | 硬中断、softirq、tasklet 在 CPU 上执行   | 线程化中断、隔离核、降低负载     |
| 上下文切换     | 进程/线程切换、模式切换                  | 降低切换频率、绑核、实时调度     |
| 缺页、swap     | 访问未驻留内存触发页故障                 | mlock、禁用 swap、预分配         |
| Cache 抖动     | 多任务共享 cache、迁移                   | CPU 亲和、避免跨核共享热数据     |
| 电源管理       | C-state、P-state 等                      | 关闭深 C-state、固定频率等       |

## 4.2 cyclictest 测量调度延迟

**cyclictest**（来自 `rt-tests`）是衡量**调度延迟**的常用工具：周期性唤醒，测量从预期唤醒到实际运行之间的延迟。

```bash
# 运行 60 秒，每 1000 微秒周期，默认使用 SCHED_FIFO
cyclictest -t1 -n -m -p99 -i1000 -l100000

# 多线程、绑核
cyclictest -t4 -n -m -a -p99 -i1000 -l100000
```

**输出关注**：  
- Min / Avg / Max 延迟（us）；  
- 直方图、百分位（如 P99、P99.9）。  

Max 和高端百分位反映**最坏情况**，对硬实时评估更重要。

#### 基本测试命令

- 单线程，以 1 毫秒周期、99 优先级运行 10 万次：

```bash
sudo cyclictest -t1 -n -m -p99 -i1000 -l100000
```
参数解析：
- `-t1`        只启用 1 线程
- `-n`         使用高精度时钟（clock_nanosleep）
- `-m`         使用锁定内存，避免换页延迟
- `-p99`       实时调度优先级 99
- `-i1000`     每 1000 微秒（1ms）唤醒一次
- `-l100000`   共测试 10 万次

- 多线程、绑核测试，每个线程绑定 1 CPU：

```bash
sudo cyclictest -t4 -a -n -m -p95 -i1000
```
- `-t4`    启动 4 个 realtime 线程
- `-a`    每线程自动绑定一个 CPU（CPU affinity）

```
**结果解释：**

用 cyclictest 或上述自编 C 程序运行后，会输出每次周期唤醒/响应的延迟统计，典型如：

```
Min:      8  Avg:   12  Max:     27
```

- **Min/min** 表示所有循环中测到的最小调度延迟（微秒）。
- **Avg/平均** 是 N 次测量的平均响应延迟（通常代表常态负载下延迟水平）。
- **Max/最大** 显示一次测试过程中的“最坏情况”延迟，是实时系统最重要的观测指标——如果高于业务容忍阈值（如 50μs/100μs），说明系统存在实时性隐患。

**怎么看结果：**

- **实时性关键系统（如工业控制、HFT）一般关注 Max 值**，期望单核单线程 max 延迟始终 < 50~100 微秒，1ms 以上属于严重异常。
- 若 *Min* 很小、*Avg* 很低，但 *Max* 偶尔很大，说明有“延迟抖动/尖峰”（如页面换入、软/硬中断、驱动抢占等），影响确定性。
- 多线程绑核测试时，也要观察多核间 max 差异——若有个别绑核线程 max 明显偏高，可能该核 IRQ 压力更大或者共享资源竞争。

**应该如何排查高延迟尖峰？**

- 可用 `ftrace` 记录调度、中断、内核延迟区段（latency tracer），定位是哪段代码抢占实际运行权。
- 用 `perf top/record` 看测试进程运行时的系统热点。
- 检查是否有后台任务抢占 CPU、内存回收、频繁上下文切换、未锁内存导致的 page fault 等。
- 若发生在虚拟机，可排查宿主机噪声（其他 VM、硬件 IRQ 绑定等）。

**cyclictest vs 自编测延迟程序？**

- cyclictest 功能全面，线程池化、实时优先级、各种参数可调，也可同时绑多 CPU；
- 自编程序便于定制（如特殊业务负载下测两类延迟），调试透明，便于嵌入业务代码观测；
- 两者测到的 *绝对延迟数值* 在相似参数下通常很接近，说明自测方法具备对比、参考与业务自定义监测场景下的实战价值。

**总结要点：**

- 关注 *Max*（最大延迟）；如果偶发高延迟，需配合内核跟踪工具进一步分析根因。
- 常态（Avg/Min）很小但 Max 偶尔极高，是抢占或内核 bug 引起的真实隐患。
- 优化时可从调度策略、内存锁定、CPU 隔离、IRQ 亲和等方向着手，具体请查阅内核/IO/中断优化专题。
```

#### 编写一个等价于 cyclictest 的简单延迟测量 C 程序、编译与运行测试

下面给出一个用 C 语言实现简单周期唤醒与调度延迟统计的示例代码，并说明如何编译、运行与对比 cyclictest。

**test_cyclic.c 示例代码：**

```c
#include <stdio.h>
#include <stdint.h>
#include <unistd.h>
#include <sys/mman.h>
#include <time.h>
#include <sched.h>
#include <string.h>
#include <errno.h>

#define LOOPS 100000
#define CYCLE_US 1000
#define REALTIME_PRIO 99

static int set_realtime_priority(int prio) {
    struct sched_param sp;
    sp.sched_priority = prio;
    return sched_setscheduler(0, SCHED_FIFO, &sp);
}

static void set_cpu_affinity(int cpu) {
    cpu_set_t set;
    CPU_ZERO(&set);
    CPU_SET(cpu, &set);
    sched_setaffinity(0, sizeof(set), &set);
}

uint64_t timespec_to_us(const struct timespec *ts) {
    return (uint64_t)ts->tv_sec * 1000000ull + ts->tv_nsec / 1000;
}

int main() {
    mlockall(MCL_CURRENT | MCL_FUTURE); // 锁定内存，避免换页带来延迟
    set_realtime_priority(REALTIME_PRIO); // 提升调度优先级
    // set_cpu_affinity(0); // 如需绑核可取消注释

    struct timespec ts, next;
    uint64_t delays[LOOPS];
    memset(delays, 0, sizeof(delays));

    // 获取当前的单调递增时钟时间，初始化 next 变量为当前时间点
    clock_gettime(CLOCK_MONOTONIC, &next);

    for (int i = 0; i < LOOPS; ++i) {
        // 本段用于计算下一个周期的绝对唤醒时间：
        // 每次循环让 next 的纳秒值递增一个周期长度（CYCLE_US * 1000 纳秒），
        // 如果纳秒累计满1秒（10^9 ns），则进位到秒域，保证 next 始终是合法的 timespec 结构体，表示下次绝对唤醒点。

        // 这里的时间是：每次循环递增的下一个定时唤醒的绝对时间戳，以 timespec 结构体表达。
        // CYCLE_US * 1000 是本次周期需增加的纳秒数（如 CYCLE_US=1000，则为1,000,000ns，即1ms）。
        // 如果纳秒部分累计到1秒或以上，则进位到秒，保证 next 仍是合法的 timespec。
        next.tv_nsec += CYCLE_US * 1000;
        while (next.tv_nsec >= 1000000000) {
            next.tv_nsec -= 1000000000;
            next.tv_sec++;
        }
        // 这行的作用：让线程精确休眠到 next 设定的绝对时间戳（单位纳秒），即“等到指定时刻再继续执行”。
        // CLOCK_MONOTONIC：使用单调递增时钟，不受系统时间调整影响，TIMER_ABSTIME：绝对时间模式
        // 这样可以精确实现周期性调度，不因循环代码运行时间累积漂移
        // 使用 clock_nanosleep 进行绝对时间休眠，让线程精确等待到 next 设定时刻再被调度唤醒。
        // 这种写法能显著降低因“代码执行耗时”导致的时序漂移，实现高精度的周期性调度。也能很好地评估内核调度延迟，因为理想状态下线程应恰好在 next 时间点被唤醒，任何延后都反映了调度/内核延迟。
        clock_nanosleep(CLOCK_MONOTONIC, TIMER_ABSTIME, &next, NULL);

        // clock_gettime 记录被真正唤醒的实际时间。二者求差即可得到该周期调度延迟。
        clock_gettime(CLOCK_MONOTONIC, &ts);
        uint64_t scheduled_us = timespec_to_us(&next);
        uint64_t actual_us = timespec_to_us(&ts);
        delays[i] = (actual_us > scheduled_us) ? (actual_us - scheduled_us) : 0;
    }

    // 统计 Min/Avg/Max
    uint64_t min = delays[0], max = delays[0], sum = 0;
    for (int i = 0; i < LOOPS; ++i) {
        if (delays[i] < min) min = delays[i];
        if (delays[i] > max) max = delays[i];
        sum += delays[i];
    }
    printf("Loops: %d, Cycle: %dus, Priority: %d\n", LOOPS, CYCLE_US, REALTIME_PRIO);
    printf("Latency (us): Min: %lu  Avg: %.1f  Max: %lu\n", min, (double)sum/LOOPS, max);
    return 0;
}
/*
本程序是一个用于测试 Linux 用户态实时调度延迟的简单循环程序，其主要功能和流程如下：

1. 通过 mlockall(MCL_CURRENT | MCL_FUTURE) 锁定进程内存，防止页换入/换出带来不可控延迟；
2. 调用 set_realtime_priority(REALTIME_PRIO) 设置当前进程为最高实时优先级（SCHED_FIFO），以确保调度优先权；
3. 可选调用 set_cpu_affinity(0) 将进程绑到 CPU0，排除多核调度影响（源码留有注释可选启用）；
4. 使用 timespec 结构体记录循环周期的目标绝对时间（基于 CLOCK_MONOTONIC），每次循环递增“下一次唤醒目标时间”；
5. 通过 clock_nanosleep(TIMER_ABSTIME) 精确等待到目标绝对时间，实现周期性任务调度；
6. 醒来后用 clock_gettime 获取实际被唤醒的时间戳，和目标时间求差，统计调度延迟（us级）；
7. 循环执行 LOOPS 次，记录每次延迟值，最终统计并输出最小/最大/平均调度延迟。

实现思路类比 cyclictest 测试工具，综合评估实时进程在不同负载下的调度实时性，适合验证内核、调度器、CPU 绑定、锁页/内存管理等配置对最坏时延的影响。

典型输出如:
Loops: 100000, Cycle: 1000us, Priority: 99
Latency (us): Min: 7  Avg: 12.5  Max: 35

说明该环境下（绑核、锁页、最高优先级）实时调度最坏延迟不超过35微秒，系统实时表现良好。

// 实时调度延迟的计算方式（见上述 main 循环核心代码）如下：
// 1. 先用 clock_gettime 记录本次循环应被唤醒的目标绝对时间 scheduled_us（取 next 变量）
// 唤醒操作发生在 clock_nanosleep 返回之后，此时线程被内核唤醒，随即用 clock_gettime 记录当前实际时间（ts 变量，actual_us）
// 3. 两者作差：delay = actual_us - scheduled_us
//    - 若实际被唤醒早（理想状态），delay 为0
//    - 若被“迟唤醒”，delay 为正值，单位为微秒（us）
// 4. 每次循环记录该 delay，最终统计循环中的最小、最大、平均延迟，反映实时性的整体状况
//
// 总结：调度延迟 = 本应被唤醒时间点（理论值）与实际被内核调度唤醒时间点（现实值）的差值


*/

```

## 4.3 使用 trace / perf 分析延迟

### 1. 使用 ftrace 定位关键延迟代码段

**说明**：ftrace 支持使用不同的 tracer（如 `irqsoff`、`preemptoff`、`preemptirqsoff`）来捕捉长时间关闭中断、关闭内核抢占等情况，有助于找出导致实时延迟的代码路径。

**举例指令**：
```bash

echo 1 > /sys/kernel/debug/tracing/tracing_on             # 开始跟踪
```

### 3. 利用 BPF/eBPF 自定义实时延迟分析

**说明**：BPF/eBPF 支持自定义脚本，灵活统计线程唤醒延迟、关键路径持锁时间等，适合复杂或细粒度的实时性分析。

**举例代码（bpftrace 脚本统计调度延迟）**：
```bash
sudo bpftrace -e '
tracepoint:sched:sched_wakeup,
tracepoint:sched:sched_wakeup_new
{
    @start[args->pid] = nsecs;
}
tracepoint:sched:sched_switch
/@start[args->next_pid]/
{
    printf("PID %d delay: %d us\n", args->next_pid, (nsecs-@start[args->next_pid])/1000);
    delete(@start[args->next_pid]);
}
'
```
