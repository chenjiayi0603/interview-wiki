# 替代在线阻塞式 redis-cli --bigkeys

**简历原文**：替代原有在线阻塞式 Key 扫描，实现大规模实例大 Key / 热 Key 实时检测

## 数据支撑

| 方案 | 执行方式 | 对主业务影响 | 实例规模 |
|------|---------|------------|---------|
| `redis-cli --bigkeys` | 在线 SCAN 全量 Key，阻塞主线程（Redis 单线程） | 执行期间每次 SCAN 命令占用主线程，P99 上升 | 单实例 |
| 本项目同步插桩 | 命令路径内嵌统计，<1μs 开销 | 无阻塞，主线程额外开销可忽略 | 万级实例 |

`redis-cli --bigkeys` 底层使用 `SCAN` + `OBJECT ENCODING` + `DEBUG OBJECT`，每次 SCAN 批次是一次阻塞，对于 1 亿 Key 的实例可能需要数分钟，期间命令延迟明显上升。

## 理论支撑

Redis 单线程模型：所有命令（包括 SCAN）都在主事件循环中串行执行。`SCAN` 命令每次返回一批 key（count 参数控制批次大小），但每次调用都占用主线程时间片。百万 Key 实例的完整 SCAN 需要数千次调用，总计对主线程的干扰时间可达分钟级。

在线实时检测的核心优势：命令执行完成时 Key 的 value 大小和访问频次天然已知，无需额外扫描。插桩成本 = 一次哈希表查找 + 一次计数器更新，远低于 SCAN 的全量遍历。

## 业界对标

- **阿里云 Redis 控制台**：提供大 Key 分析功能，底层使用 RDB 离线分析（重启后分析 dump 文件），非在线
- **Datadog Redis 监控**：通过 `INFO`, `CLIENT LIST` 等命令采样，非命令级别实时统计
- **美团 Redis 监控**：公开分享中提及在命令路径插桩统计的方案，与本项目思路一致

## 追问预案

**Q：大 Key 的定义是什么？**
> 按类型：String value > 10KB；List/Hash/ZSet/Set 元素数 > 10,000。热 Key：单位时间（如 1s 内）访问频次排前 N（N 可配）。阈值业务侧可配置。
