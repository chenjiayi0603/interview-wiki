边车（客户端、服务器增加边车）增加30%左右的延迟，降低40%左右的QPS。

|------|---------|-----|------|

## Wasm自适应熔断

### 熔断算法

- **protection**：请求数小于等于protection则不会触发熔断，默认5
- **k**：熔断敏感系数，在1.1到2之间，默认1.5，越小越容易熔断

**熔断条件**：
- `k * accepts >= total - protection` 则不会熔断
- `k * accepts < total - protection` 则概率性熔断
- 概率百分比为 `(((total - protection) - (k * accepts)) / (total + 1)) * 100`

### 熔断测试数据

| 指标 | 数值 | 说明 |
|------|------|------|
| 错误率阈值 | 50% | 超过即熔断 |
| 熔断时间 | 30s | 默认配置 |
| 半开试探 | 1个请求 | 试探是否恢复 |
| 恢复时间 | < 5s | 从熔断到正常 |

**熔断过程时间线**：
```
T+0s    错误率升至60%
T+0.5s  熔断触发，返回503
T+30s   进入半开，试探请求
T+30.5s 试探成功，恢复
T+31s   正常服务

总恢复时间：31s
优化后（自适应阈值）：5s内恢复
```

### Wasm熔断压测数据

service 501 cpp wasm 自适应熔断(k=1.5 window=10s)：

| conns | ms | qps | code |
|-------|-----|------|------|
| 200 | 26.729 | 7458.1 | Code 501 : 188 (0.5%) Code 504 : 37209 (99.5%) |

**本地压测结论**：
- 在QPS较低时，调节系数k和统计窗口，对于一直返回错误的场景，影响较大
- k系数越小熔断概率越高
- 统计滑动窗口越大，熔断概率越高，越接近预期概率
- 压测请求数会产生影响，因为算法是反馈型的，在开始时未有采样数据
- 请求数越多和压测时间越长，则压测结果数据越准确，熔断也越接近预期概率
- 最长统计时长越长，计算结果数据越准确，但同时也会可能增加熔断生效时延
- 参考：go-zero使用基于滑动窗口，10s/40窗口

### 故事二：Envoy自适应熔断插件

**面试官问**：自适应熔断是怎么实现的？

**回答模板**：

> "传统熔断是固定阈值，比如错误率超过50%就熔断。但实际场景中，不同服务能承受的错误率不同，固定阈值不合理。
> 
> **自适应熔断思路**：
> - 根据历史数据动态调整阈值
> - 用滑动窗口统计最近的成功率
> - 成功率下降时逐步降低阈值，自动恢复时逐步放开
> 
> **实现**：
> - Envoy Wasm插件（Rust语言）
> - 在filter层面统计请求结果
> - 超过阈值直接返回503，不转发到后端
> 
> **效果**：
> - 异常流量自动隔离
> - 恢复时间 < 5秒
> - 不需要人工干预"

### 常问问题

**Q: Istio和传统微服务框架的区别？**

> 传统框架（如Spring Cloud）是把治理逻辑写在业务代码里，服务网格是把治理逻辑抽到Sidecar，业务代码无感知。好处是业务开发不需要关心治理细节，坏处是多一层代理，有一定性能开销。

**Q: Wasm插件是什么？为什么用Rust？**

> Wasm是WebAssembly，Envoy支持用Wasm写插件，可以在请求处理过程中注入自定义逻辑。用Rust是因为性能好，内存安全，编译成Wasm后体积小。

**Q: 性能开销大吗？**

> 有开销，大约增加1-2ms延迟。但对于业务服务，这个开销可以接受。我们做过压测，QPS影响在5%以内。

## 参考：开源代理性能对比

### Apache APISIX vs Envoy

| 进程数 | APISIX QPS | APISIX Latency | Envoy QPS | Envoy Latency |
|--------|-----------|----------------|-----------|---------------|
| 1 worker | 18608.4 | 0.96 | 15625.56 | 1.02 |
| 2 workers | 34975.8 | 1.01 | 29058.135 | 1.09 |
| 3 workers | 52334.8 | 1.02 | 42561.125 | 1.12 |

**总结**：APISIX在响应延迟和QPS层面都略优于Envoy，由于nginx的多worker协作方式在高并发场景下更有优势。但两者并不冲突，Envoy的总线设计使它在处理东西向流量上有独特优势，APISIX在性能和延迟上的表现使它在处理南北向流量上具有海量的吞吐能力。

### nginx、kong、envoy代理转发性能对比

**网关资源估算方法**（假设网关总共32核，仅做代理）：

| 网关 | TPS上限估算 |
|------|-----------|
| nginx | 338k |
| kong | 157k |
| envoy | 230k |

**估算公式**：
- nginx: 36k * (32/3.4) = 338.8k
- kong: 36k * (32/7.3) = 157.8k
- envoy: 36k * (32/5.0) = 230.4k

只要所有upstream的TPS上限值累加起来的数值，低于网关的上限，就是安全的。

**业务服务资源估算示例**：
- 假设业务服务单核TPS上限平均为1.5k
- Kubernetes集群共有2000 CPU
- 理论上限 = 3000k
- 网关分别需要：284 CPU（nginx）、611 CPU（kong）、417 CPU（envoy）
- 若业务服务CPU使用率平均为30%，网关资源可缩减为：94 CPU、203 CPU、139 CPU
- 分别是集群CPU总数的5%、10%、7%

### 3. 高频面试问题与答题框架

#### 3.1 Istio 流量管理原理是什么？

**答题主线：控制面 + 数据面 + 配置对象**

- 控制面（Istiod）将策略配置转换为 xDS，下发给数据面 Envoy
- `VirtualService` 定义路由规则（按 path/header/权重）
- `DestinationRule` 定义目标版本策略（subset、LB、连接池、熔断）
- 请求进入 Sidecar 后，按路由与目标策略执行，完成灰度、金丝雀、故障转移

[src: raw/ingested/3项目/服务网格-即构/服务网格平台-面试考点文档.md]

#### 3.2 Wasm 插件和原生 Envoy Filter 怎么选？

**答题主线：灵活性/安全性/性能权衡**

- Wasm 优势：沙箱隔离、安全边界清晰、支持动态加载、语言更灵活
- 原生 Filter 优势：性能更高、生态更成熟、调试链路更直接
- 选择 Wasm 的原因：需要快速迭代治理逻辑，避免频繁改 Envoy 主体和重启
- 风险控制：核心链路保持轻量逻辑，复杂逻辑下沉到后端服务

[src: raw/ingested/3项目/服务网格-即构/服务网格平台-面试考点文档.md]

#### 3.3 Sidecar 开销到底有多大？

**答题主线：给区间 + 说明影响因素 + 给优化手段**

- 常见区间：CPU 增加约 5%~10%，延迟增加约 1~3ms（取决于流量模型）
- 影响因素：QPS、包大小、连接复用、TLS、过滤器数量、日志级别
- 优化手段：连接池参数调优、精简过滤器链、降采样日志、启用协议复用

### 5. K8s 相关知识补充（面试高频）

#### 5.1 Service、Ingress、Istio Gateway 有什么区别？

- `Service`：集群内服务发现与负载均衡（L4）
- `Ingress`：K8s 原生七层入口资源，通常由 Ingress Controller 实现
- `Istio Gateway`：网格入口/出口流量管理对象，和 `VirtualService` 配合实现细粒度路由

[src: raw/ingested/3项目/服务网格-即构/服务网格平台-面试考点文档.md]

#### 5.2 Deployment、StatefulSet 怎么选？

- `Deployment`：无状态服务，副本可替换，滚动更新常用
- `StatefulSet`：有状态服务，需要稳定网络标识和持久化存储
- 网格控制面、业务服务多用 Deployment；数据库/中间件常见 StatefulSet

[src: raw/ingested/3项目/服务网格-即构/服务网格平台-面试考点文档.md]

#### 5.3 Readiness 和 Liveness 的区别？

- `Readiness`：是否可接收流量（不通过会被 Service 摘流）
- `Liveness`：进程是否存活（失败会触发重启）
- 网格场景下 Readiness 更关键，避免未就绪实例接流

[src: raw/ingested/3项目/服务网格-即构/服务网格平台-面试考点文档.md]

#### 5.4 HPA 如何与网格治理协同？

- HPA 根据 CPU/自定义指标扩缩容
- 网格提供每个实例的流量与错误指标，辅助扩容决策
- 扩容后需考虑连接预热与渐进放量，避免冷实例瞬时压垮

[src: raw/ingested/3项目/服务网格-即构/服务网格平台-面试考点文档.md]

#### 5.5 Pod 被驱逐/重建时如何保证平滑？

- 配置 `preStop` + 合理 `terminationGracePeriodSeconds`
- 先让实例变为 NotReady 并摘流，再执行优雅退出
- 配合 PDB（PodDisruptionBudget）避免同时驱逐过多副本

[src: raw/ingested/3项目/服务网格-即构/服务网格平台-面试考点文档.md]

#### 5.6 常见故障排查路径（K8s + Istio）

- 先看 Pod 状态和事件：`Pending/CrashLoopBackOff/OOMKilled`
- 再看 Service Endpoint 是否就绪
- 再查 Istio 路由对象（VirtualService/DestinationRule）是否匹配
- 最后看 Envoy 配置与指标（xDS 下发、5xx、upstream reset）

## 性能数据重点说明（面试专用）

> 以下内容来自面试准备文档，专门拆解每个性能数字的来源、含义和回答策略。

[src: raw/ingested/3项目/面试准备/性能数据重点说明-三、服务网格-—-性能数字全解.md]

### QPS 5万+

**实际含义：**
所有业务服务通过 Istio Sidecar 代理的总流量，不是单个服务的 QPS。

**测量方式：**
- Prometheus 采集 Envoy 的 `envoy_cluster_upstream_rq_total` 指标
- 10+ 个业务服务的 QPS 之和，单个服务约 1000–10000 QPS

**被问到时要补充：**
> "5万是平台总流量，每个服务的流量差异很大。压测时我们重点测的是 Sidecar 引入的额外延迟，结论是 P50 额外增加 5ms，P99 额外增加 15ms，业务方都在可接受范围内。"

[src: raw/ingested/3项目/面试准备/性能数据重点说明-三、服务网格-—-性能数字全解.md]

### Sidecar 引入延迟 5–15ms

**延迟来源拆解：**

```
请求路径额外开销：
  客户端 Sidecar 出站处理：~1–3ms
    ├─ iptables 流量劫持（本机 loopback）：~0.1ms
    ├─ Envoy 路由匹配 + 负载均衡：~0.5ms
    └─ Wasm 插件处理：~1–2ms
  服务端 Sidecar 入站处理：~1–3ms（同上）
  合计：~2–6ms（无 Wasm），~5–15ms（含 Wasm）
```

**被问到时要补充：**
> "5–15ms 主要来自两次 iptables 劫持和两次 Envoy 处理。没有 Wasm 插件时约 2–6ms，加了自适应熔断 Wasm 后到 5–15ms。对于 P50 延迟 50ms 以上的服务影响不大，对延迟敏感的服务（<10ms）不建议接入服务网格。"

[src: raw/ingested/3项目/面试准备/性能数据重点说明-三、服务网格-—-性能数字全解.md]

### 故障恢复时间 <5s

**实现原理：**
```
熔断触发 → 熔断期（拒绝所有请求）→ half-open 探针（每2s发一次）→ 连续2次成功 → 恢复
最短恢复路径：2s + 2s = 4s < 5s
```

**参数配置：**
- 错误率阈值：50%（10秒窗口内）
- 熔断持续时间：3s
- half-open 探针间隔：1s
- 连续成功次数：2次方可恢复

**被问到时要补充：**
> "<5s 是在熔断持续时间 3s + 探针验证 2 次（各 1s）的配置下得到的。可以根据业务容忍度调整，延迟敏感业务可以配置更短的熔断窗口和更快的探针频率。"
