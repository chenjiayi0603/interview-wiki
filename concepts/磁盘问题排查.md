# 磁盘问题排查

## 7.1 磁盘过载的表现

- `iostat -x 1` 看到 `%util` 接近 100%
- `await`（平均等待时间）飙升，特别是 `w_await`
- 系统 load 高但 CPU 不高（大量进程在 D 状态等待 IO）
- Redis 的 `latency` 监控显示 `aof-write`、`rdb-save` 延迟突增

## 7.2 排查与处理（口述版）

> "磁盘突然坏了或过载了怎么办？"
>
> 这是最严重的问题之一，因为数据可能在丢。处理分几个层次：
>
> **第一层：确认严重程度。**
> - `dmesg` 看有没有 I/O error、文件系统错误
> - `smartctl` 看磁盘健康状态（是否有坏道、重映射扇区）
> - 如果 `dmesg` 里有 `Buffer I/O error`，说明磁盘已经在物理层面出问题了
>
> **第二层：如果是过载而非物理损坏。**
> - 查是谁在大量写：`iotop`、`pidstat -d` 找元凶
> - 如果是 Redis 的 RDB 快照或 AOF 重写导致的，调整触发条件（错峰、限速）
>   - RDB：设置 `rdb-save-incremental-fsync`、错开保存时间
>   - AOF：`auto-aof-rewrite-percentage` 调大、`aof-rewrite-incremental-fsync` 开启
> - 如果是 RocksDB Compaction 导致的，限速或错峰
> - 如果是日志疯狂写入，紧急关闭 debug 日志或切换日志级别
>
> **第三层：如果是物理损坏。**
> - 这台机器不能再依赖了。立即执行故障转移
> - Redis 集群：先做主从切换，把故障机器的 role 摘掉
> - KeyDB 集群：类似，利用多副本快速切主
> - 如果数据损坏且无法从副本恢复，从备份恢复（RDB/AOF 文件 + 增量日志）
>
> **第四层：恢复后做什么。**
> - 如果是文件系统损坏，`fsck` 修复但风险很大（可能丢数据）
> - 更安全的做法：从健康副本重新同步
> - 事后：检查同批次磁盘是否有同样隐患，提前更换

## 7.3 数据损坏恢复策略

| 场景 | 处理方式 |
|------|---------|
| **RDB 文件损坏** | 从其他副本同步，或回退到上一个有效 RDB + 增量 AOF |
| **AOF 文件损坏** | `redis-check-aof --fix` 修复，会截断损坏部分（可能丢少量数据） |
| **RocksDB SST 文件损坏** | RocksDB 有 checksum，自动跳过损坏的 SST；如果大量损坏，从副本全量同步 |
| **元数据损坏** | 这是最严重的。必须从备份恢复+重放日志。关键在于元数据要做多副本和定期备份 |
| **磁盘完全不可读** | 踢掉故障节点→新节点从副本全量同步（基于 RDB 文件传输） |
