## 5.1 速览卡

**性能**：1000万+注册用户，线上峰值 5000 QPS，AC 自动机敏感词过滤 <1ms/条（10万词典，O(n)）

**提升点**：
- 敏感词从朴素匹配 O(n×m) 升级为 AC 自动机 O(n)
- MongoDB 2dsphere + TTL 缓存降低地理查询热点压力

**瓶颈**：
- MongoDB 地理查询 10–50ms，高并发时成热点
- DAU/MAU 比偏低（金融类典型），活跃度有限

**优化方向**：GeoHash 替代 2dsphere（字符串前缀索引更高效）；查询结果 TTL 缓存 30s

## 5.3 5000 QPS 容量规划与正推分析

**硬件基线（2015-2019 典型配置）：** 4-5 台服务器，8C16G，SATA SSD，1Gbps

**部署拓扑：**
```
Server 1-2：网关 + IM 业务（C++ 异步 epoll）
Server 3：  MySQL 主库（写，SATA SSD）
Server 4：  MySQL 从库 + Redis
Server 5：  MongoDB + 智能客服
```

**正推第一步：MySQL 主库 fsync 是最终瓶颈**

| 要素 | 具体配置 | 说明 |
|------|---------|------|
| **CPU** | Intel Xeon E5-2620 v3，8核 2.4GHz | 2016 年主流配置 |
| **内存** | 32GB DDR4，buffer pool 20GB | 留 12GB 给 OS + 连接线程 |
| **磁盘** | Intel S3520 SATA SSD，1-3ms fsync，18000 IOPS | 企业级 SATA SSD |
| **MySQL 版本** | 5.7 InnoDB | group commit 成熟 |
| **`innodb_flush_log_at_trx_commit`** | `= 1` | 每次提交 fsync redo log |
| **`sync_binlog`** | `= 1` | 每次提交 fsync binlog |
| **半同步复制** | `rpl_semi_sync_master_enabled=1` | AFTER_SYNC 模式 |
| **实测上限** | 单主 **3000-5000 事务/s** | 半同步下吞吐不变 |
| **集群总吞吐** | **10000+ QPS**（1写2读） | 读写分离后总 QPS 轻松过万 |

**为什么是 3000-5000 事务/s？**
```
SATA SSD 瓶颈不在 IOPS（18000 IOPS 远大于 5000 事务/s），
瓶颈在 fsync 延迟：Intel S3520 单次 fsync ≈ 1-3ms。
InnoDB group commit 合并多事务 redo log + binlog → ≈ 3000-5000 tx/s。
换 NVMe（fsync 0.1ms）→ 天花板直接提到 10000-50000 tx/s。
```

**正推第二步：每消息消耗事务数 → 最大消息吞吐**
```
每条消息：INSERT 消息体(1事务) + UPDATE 会话 last_msgid(1事务) = 2 事务/消息
最大消息吞吐 = 3000÷2 = 1500 msg/s（保守）~ 5000÷2 = 2500 msg/s（乐观）
```

**正推第三步：消息占总 QPS 比例 → 最大总 QPS**
```
消息发送是唯一必然穿透 MySQL 主库的请求类型。
社交金融 IM 消息占比约 10-15%：
最大总 QPS = 1500÷0.15 = 10000 ~ 2500÷0.10 = 25000
取中值 ≈ 15000 QPS
```

**正推第四步：验证其他层不会先于 MySQL 触顶**

| 层 | 上限 | 15000 QPS 时负载 | 是否先于 MySQL 触顶 |
|----|------|----------------|------------------|
| C++ 异步服务（2实例） | ~10000-11000 QPS | 15000 | ⚠️ 可能先到顶 |
| MySQL 从库读 | 5000-10000 读/s | ~3600 读/s | ✅ 不会 |
| TCP 连接 | 140万（内存） | <10万 | ✅ 不会 |
| Redis | 10万+ QPS | ~11000 QPS | ✅ 不会 |
| 网络带宽 | 1Gbps(125MB/s) | ~45MB/s | ✅ 不会 |

**结论：**
```
正推最大 QPS ≈ 10000-12000（C++ 2 实例时，C++ 服务先到顶）
              ≈ 15000（C++ 3 实例时，瓶颈回到 MySQL fsync）
当前真实 5000 QPS → 5000÷10000 = 50%，在安全区内，还有约一倍余量，合理。
```

## 5.4 敏感词过滤与地理服务

**AC 自动机敏感词：**
- 算法：Aho-Corasick（trie + fail 指针），多模式匹配 O(n)
- 10 万词典对一条消息 <1ms，聊天无感知
- 热更新：构建新 AC tree → 原子替换指针 → 旧 tree 延迟回收
- 词典更新不实时（重建周期内新词不生效），紧急词手动触发立即重建

**MongoDB 2dsphere 地理查询：**
- GeoJSON 点集，球面距离 haversine 公式，B-tree 索引
- `$nearSphere` 查询走索引，10–50ms
- TTL 缓存 30s 大幅降低地理查询 QPS（缓存命中 90%+）
- TTL 30s 内用户移动有偏差，社交场景可接受

## 5.5 追问预案

**Q：千万级用户峰值才 5000 QPS，量级合理吗？**
> 5000 QPS 是社交 IM 高峰值，对应日活百万级。社交场景 DAU/MAU 约 10-15%，1000 万+注册对应 100-150 万 DAU，5 万同时在线，人均 0.1 QPS。类似产品对标：什么值得买 ~3000-5000、脉脉 ~3000-5000、知识星球 ~2000-3000。金融用户偏低频使用，5000 QPS 完全合理。

**Q：这套架构正推最大能跑多少 QPS？**
> MySQL 主库 fsync 是最终天花板（SATA SSD 3000-5000 事务/s → 1500-2500 msg/s → 10000-25000 总 QPS）。当前 5000 QPS 在安全区内，约 50% 利用率。扩容路径：加 C++ 实例 → UPDATE 批量合并 → SATA→NVMe SSD。

**Q：AC 自动机怎么动态更新词典？**
> 周期性重建（10 万词典构建几百毫秒），原子替换指针。紧急词手动触发立即重建。

**Q："附近的人"怎么实现？**
> MongoDB 2dsphere 索引 + `$near` 查询，TTL 缓存 30s。深度分页用 last_distance 作 cursor 优化。
