# 端到端加密单聊设计

## 端对端加密单聊流程图

1. 用户A本地生成一次性临时会话密钥（对称随机数 keyX）
2. 用户A从CA服务获取用户B的公钥（PubB），校验有效性
3. 用户A用自己的私钥(PrivA)和B的公钥(PubB)通过ECDH算法计算出共享密钥 sessionKey
4. 用户A用sessionKey加密keyX等密钥数据，计算HMAC
5. 用户A将密文与HMAC、密钥版本号等通过服务器发送给用户B
6. 服务器收到信息：
   - a. 如发现双方已有密钥且未过期，直接返回现有密钥信息
   - b. 如会话密钥已过期或首次通信，转发A加密信息给B的所有设备（并保存入库）
7. 用户B收到密钥消息，读取A的公钥（PubA），校验有效期
8. 用户B用自己的私钥(PrivB)和A的公钥(PubA)通过ECDH算法计算出sessionKey
9. 用户B用sessionKey解密获得keyX，对HMAC校验
10. 成功后A与B本地保留当前会话对称密钥keyX，后续收发单聊消息都用keyX（对称加密+签名），并标注密钥版本号

【备注】
- 每个密钥版本大约一周内有效，到期由任意一方发起密钥协商重建
- 其它设备可同步此密钥过程
- 公钥管理、认证流程均通过CA中心完成

## keyX 存储与转发说明

### 1. 本地安全存储（客户端设备）
- 协商完成后，A/B 双方将 keyX（临时对称会话密钥）**仅保存在各自设备的安全存储区**（如 Keychain、加密本地数据库等）。
- **不得上传明文 keyX 到服务器**，仅本地用于消息加/解密。
- 多端（同一账号多台设备）同步时，推荐用端对端加密信道（比如用老密钥加密keyX），同样不经由明文服务器。

### 2. 服务端只中转/保存加密密钥消息
- 服务端**不保存明文 keyX**，仅作为密钥协商消息的转发中转站，以及加密密钥（如 encrypted_keyX）和元数据的临时存储库。
- 入库的仅包含已加密的密钥内容及其元信息，**服务端不能解密获取明文keyX**。

### 3. 离线/多端场景支持
- 当用户A生成keyX并用sessionKey加密后，通过服务器转发，服务端保存已加密密钥交换消息及元数据（用于可靠投递，防止丢失）。
- **推送优先**：如果B在线，服务端立即推送协商消息到B所有在线设备。
- **拉取兜底**：B不在线时，服务端持久化保存加密密钥消息，等B上线时主动推送或B设备主动拉取，确保密钥传递完整可靠。

### 4. 客户端密钥销毁策略
- 超过密钥有效期、切换密钥或退出登录后，客户端应**自动销毁本地历史keyX**（如从本地安全区彻底删除），避免明文遗留风险。

### 5. 解密与本地存储
- 用户B收到keyX密钥消息后，通过 A 公钥 + B 私钥（ECDH 算法）得到 sessionKey，再解密获得keyX，然后**只在本地安全存储保留明文**。
- B实际拿到的不是直接传递的随机数，而是双方协商出的结果解密得出。
- 后续所有消息的端对端加解密都用本地安全保存的 keyX，服务端一无所获。

### 6. 安全原则总结
- keyX 只在客户端安全存储，服务端绝不持有明文。
- 服务端仅存储、转发密钥协商的**加密内容**和必要元数据。
- 多端同步必须也走加密通道，保证密钥不会因多设备问题泄漏。
- 离线场景下服务端只做加密密钥的可靠消息存储/转发，不影响密钥安全。
- 客户端须定期清理、销毁过期密钥，确保历史无残留。

> **核心：密钥只在两端本地生成、协商、解密和储存，服务端永远无法获得明文密钥，任何情况下不会造成密钥泄漏。**

## CA中心服务公钥管理

### 1.1 用户密钥信息管理

- CA服务保存用户的主要信息：
    - 用户唯一标识
    - 公钥（客户端生成，RSA2048或ECDH），包含有效期、类型、版本
- 用户首次上传公钥场景：
    - 注册时：
        1. 客户端随机生成一对公钥（ecdh）
        2. 注册提交公钥，服务端CA保存用户信息
    - 登录时：
        - 第一次登录/满足重置条件时，登录成功后保存最新公钥

### 1.2 公钥更新流程

1. 客户端生成新的密钥对，计算公钥SHA哈希，用原有私钥签名
2. 客户端上传新公钥、有有效期和签名给CA服务
3. CA服务验证签名（用旧公钥），通过则更新新密钥
4. 客户端开始使用新密钥，老密钥对短期保留后删除（避免密钥协商遗留问题）

## 单聊端对端加密方案（ECDH）

### 2.1 密钥产生与更新（ECDH）

- 每用户每次仅提交一个公钥版本，每个版本有效期一周
- 相互拉取对方公钥，结合本地私钥通过ECDH算法协商出对称密钥

#### 步骤

1. 用户A拉取用户B的CA公钥（本地可缓存）
2. 校验用户B的公钥有效性
3. 用户A生成随机数，做为对称加密密钥
4. 用户A使用B的公钥和本地私钥，产生加密密钥、对消息密钥加密，并计算相关HMAC（SHA256）
    - 若无版本号，`old_version=0`，否则取本地老版本号
5. 用户A将加密结果和签名发往服务器
    - 若会话密钥未过期（7天），且双方公钥有效，服务器返回现有密钥
    - A收到后解密使用，新消息不再转发
    - 若密钥过期，服务器身份验证、消息拆分后转发到A、B所有设备并保存入库
6. 用户B拉取A的公钥信息
7. 校验A公钥有效性
8. 用户B收到密文，解密结果及HMAC，结合本地私钥和A的公钥解密，完成SHA校验
9. A的其他设备同理

#### 消息收发与密钥存储

- A/B端收发消息时用当前端对端密钥加解密内容
- 对称密钥可本地数据库持久化，以便历史消息解密
- 双方任一收到服务端响应均可更新密钥，只需按规则重新协商提交

## 微服务获取端对端公钥流程

### 6.1 通信与密钥协商流程

- 客户端使用会话密钥(AES)加密请求正文
- 请求内容（POST/json）包括加密密文、userId、devoiceId、lang（语言）
    - 例如：
        - Header:  
            - userId: 1281485267400331265
            - devoiceId: ffffffff-b553-fd03-0000-00003e3eb66a
            - lang: zh-CN
        - Body:
            - data: 加密内容 (base64)
    - 未加密内容需登录，需传accessToken
- 服务端加解密与校验流程：
    1. 验证参数完整性
    2. 判断URL放行
    3. 判断是否需要加密
    4. 用userId+设备号查本地LRUCache
    5. 若缓存无则查Redis（如"sessionkey:{devoiceId}"）
    6. 密钥不存在或解密失败响应异常
    7. 成功则密钥加缓存
    8. 核查token登录有效性
- 应答时响应结构（加密）示例：
    ```json
    {
      "code": 0,
      "codeMsg": "success",
      "data": "GKiUyJ9nBKMv76R2qnMvOQ=="
    }
    ```
- 客户端用本地会话密钥解密，解密失败自动新建密钥请求
