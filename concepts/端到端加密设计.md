## 6.1 端对端加密单聊流程  

**端对端加密密钥协商完整流程**:

```
┌──────────┐         ┌──────────┐         ┌──────────┐         ┌───────┐
│  用户A   │         │  服务端   │         │  用户B   │         │  CA  │
└────┬─────┘         └────┬─────┘         └────┬─────┘         └──┬────┘
     │                    │                    │                   │
     │ 1. 生成临时会话密钥keyX                                        │
     │    (对称随机数)                                             │
     │                    │                    │                   │
     │ 2. 从CA服务获取B的公钥(PubB)（每台设备独立密钥，一机一钥，需指定目标设备）│
     │ ──────────────────────────────────────请求(pubB)───────▶    │
     │                    │                    │                   │
     │                    │                    │     3. CA向服务端返回用户B公钥（PubB）
     │                    │   ◀─────响应(PubB)───────│
     │                    │
     │                    │ 4. 服务端把PubB转发给用户A
     │   ◀───响应(PubB)─── │                    │
     │ 4. 获得PubB，校验其有效性                                  │
     │    ECDH计算: sessionKey = ECDH(PrivA, PubB)                │
     │                    │                    │                   │
     │ 5. 用sessionKey加密keyX                                    │
     │    计算HMAC签名                                            │
     │──────────────── 发送密钥协商消息 ────────────────▶         │
     │    (加密keyX + HMAC + 密钥版本号)                           │
     │                    │                    │                   │
     │                    │ 6. 服务端检查双方密钥状态              │
     │                    │    ├─ 已有且有效 → 返回现有密钥        │
     │                    │    └─ 过期/首次 → 转发给B所有设备       │
     │                    │                    │                   │
     │                    │───────────────── 推送密钥消息 ────▶    │
     │                    │                    │                   │
     │                    │                    │ 7. B收到密钥消息   │
     │                    │                    │    → 从CA获取A的公钥(PubA)
     │                    │                    │  ────────────请求(pubA)─▶│
     │                    │                    │                   │
     │                    │                    │    CA校验并返回PubA   │
     │                    │                    │ ◀─────响应──────      │
     │                    │                    │ 8. 校验PubA有效性
     │                    │                    │    ECDH计算: sessionKey = ECDH(PrivB, PubA)
     │                    │                    │
     │                    │                    │ 9. 用sessionKey解密keyX
     │                    │                    │    校验HMAC
     │                    │                    │ 10. 本地保存keyX（安全存储区）
     │                    │                    │
     │════════════════════════════════════════════════════════════════════════════│

     │════════════════════════════════════════════════════════════════════════════│

**备注**:
- 每个密钥版本大约一周内有效，到期由任意一方发起密钥协商重建
- 其它设备可同步此密钥过程
- 公钥管理、认证流程均通过CA中心完成

**CA中的保存的数据表**

CA（证书授权/密钥管理中心）作为整个端到端加密信任锚点，需安全存储和管理各用户各设备的公私钥、证书等关键信息。主要表结构如下：

1. **用户公私钥表（tb_ca_user_key/ca_user_key）**
   - `id`：主键，自增
   - `user_id`：用户ID
   - `device_id`：设备ID（多端一机一钥）
   - `identity_key_pub`：身份公钥（用于身份认证）
   - `identity_key_pri`：身份私钥（受加密保护，仅本地存储/或安全硬件托管）
   - `signed_key_pub`：签名公钥（短周期，每周轮换）
   - `signed_key_pri`：签名私钥（受加密保护，仅本地存储/或硬件托管）
   - `key_version`：密钥版本号
   - `create_time`：生成时间
   - `expire_time`：过期时间
   - `status`：状态（1：有效，0：过期/吊销）

**补充说明：**
- CA中心设计的核心原则是密钥**只出公钥、不泄私钥**，私钥如有存储须软/硬件加密保护或分布式托管，极力防止泄露。
- 对于会话密钥交换，仅管理和分发公钥，不存储用户间的会话对称密钥（如keyX）。
- 表结构可根据实际CA实现技术（如HSM、云KMS、分布式PKI系统等）进行拓展和强化安全措施。

**典型数据流**
- 设备注册/轮换：生成或上传公钥，由CA签发认证证书，存储到上述表；
- 密钥查询：服务或客户端按(user_id, device_id, version)查询目标公钥/证书；

**A生成的keyX，B如何获取？**

答：A和B通过端到端密钥协商协议来安全传递keyX，流程如下：

1. **A生成keyX**（如新的聊天会话/密钥轮换时）：
   - A本地生成一个临时对称会话密钥 keyX，用于后续与B端到端加密通信。

2. **A加密keyX**：
   - A获取B的最新公钥（B的设备公钥，来自CA中心等权威来源，并校验证书合法性）。
   - A与B设备的公钥、自己设备的私钥进行ECDH（椭圆曲线 Diffie-Hellman）密钥协商，计算出"会话密钥 sessionKey"。
   - 用该 sessionKey 对 keyX 进行加密（通常采用对称加密算法如AES等）。
   - 可对加密后的内容再加入完整性校验（如HMAC）与key版本等元信息，防止篡改和重放。

3. **A发送加密的keyX给B**：
   - 将【A设备id、B设备id、加密后的keyX、会话/密钥版本号、完整性保护信息等】封装成消息，通过IM服务器中转发给B。
   - 服务器仅中转该加密内容、不解密、不保存明文，仅为可靠投递与兜底存储。

4. **B收到密钥协商消息**：
   - B收到后，取出A的设备公钥（从CA验证/拉取），并用自己的私钥执行ECDH协商，计算出正确的sessionKey（与A侧的ECDH结果一致）。
   - 用协商出来的sessionKey解密keyX，并校验完整性。
   - 校验通过后，将明文keyX本地保存于本端的安全存储区。至此，A和B都拿到了相同的keyX，可以用它对会话消息进行端到端加解密。

**核心要点总结：**
- B无法直接获取明文keyX，必须通过A用ECDH派生的共同密钥加密后下发。
- 密钥交换的加密、认证和完整性依赖于双方各自设备的公钥对与私钥，密钥交换全程端到端加密，服务端不知明文。
- 多设备时A需为B的每一个目标设备（对应公钥）分别加密keyX单独投递。
- 客户端本地丢失密钥需靠新一轮密钥协商生成新keyX，历史密钥不可恢复。

## 6.2 keyX存储与转发说明

**本地安全存储（客户端设备）**:
- 协商完成后，A/B双方将keyX（临时对称会话密钥）**仅保存在各自设备的安全存储区**（如Keychain、加密本地数据库等）
- **不得上传明文keyX到服务器**，仅本地用于消息加/解密
- 多端（同一账号多台设备）同步时，推荐用端对端加密信道（比如用老密钥加密keyX），同样不经由明文服务器

**服务端只中转/保存加密密钥消息**:
- 服务端**不保存明文keyX**，仅作为密钥协商消息的转发中转站，以及加密密钥（如encrypted_keyX）和元数据的临时存储库
- 入库的仅包含已加密的密钥内容及其元信息，**服务端不能解密获取明文keyX**

**离线/多端场景支持**:
- 当用户A生成keyX并用sessionKey加密后，通过服务器转发，服务端保存已加密密钥交换消息及元数据（用于可靠投递，防止丢失）
- **推送优先**: 如果B在线，服务端立即推送协商消息到B所有在线设备
- **拉取兜底**: B不在线时，服务端持久化保存加密密钥消息，等B上线时主动推送或B设备主动拉取

**安全原则总结**:
- keyX只在客户端安全存储，服务端绝不持有明文
- 服务端仅存储、转发密钥协商的**加密内容**和必要元数据
- 多端同步必须也走加密通道，保证密钥不会因多设备问题泄漏
- 离线场景下服务端只做加密密钥的可靠消息存储/转发，不影响密钥安全

**问题：如果重装后，没了keyX，原来的会话怎么办？**

答：keyX（端到端加密的临时会话密钥）**只存在于各自设备本地安全存储区**。若用户卸载/重装 app 或清除数据，设备本地的 keyX 就会丢失，导致无法解密之前会话收到的加密消息（历史密钥无法恢复——这是端到端加密系统的重要设计原则）。

处理方式：

1. **新设备/重装后，如何恢复安全通信？**
   - 新安装的客户端**需主动与对方重新协商 session key（keyX）**。这就像一台全新设备加入聊天，需要重新建立安全信任链。此时双方重新完成 ECDH 密钥协商，产生可用的新 keyX，后续消息重新恢复可用。
   - 原来用旧密钥加密的历史消息，新 keyX **无法解密**，需要提示"无法读取历史加密消息"；只有重装后的新 keyX 可解密之后产生的新消息。

2. **历史消息可用性与安全性权衡**
   - 端到端加密系统默认**不支持服务端恢复历史密钥**，端的丢失即不可逆丢失密钥。这是为了最大限度防止密钥泄漏（即使服务器被攻破也无法获取密钥解锁历史记录）。
   - 可以设计"多端同步密钥"（如 iOS/Android 密钥同步、扫码迁移密钥等），但也仅通过端到端安全通道传递（比如用老设备扫码新设备，安全转移密钥），**绝不上传明文密钥到服务器**。
   - 若无备份措施，**重装/换机/换端=失去旧密钥=失去历史解密能力**，即历史加密消息将永久无法读取。

3. **用户体验建议**
   - UI上应明确提示："你已重装应用，无法解密历史加密消息。如遇重要信息请提前做好备份/多端同步"。
   - 如有扫码迁移/多端同步方案，可引导用户先做密钥迁移备份再换机。

4. **总结**
   - **安全优先原则**：服务端从不保存明文keyX，丢失后不可恢复
   - **恢复机制**：需端到端新协商密钥，后续新会话正常，历史消息无法恢复解密

## 6.3 CA中心服务公钥管理

**用户密钥信息管理**:
- CA服务保存用户的主要信息：
  - 用户唯一标识
  - 公钥（客户端生成，RSA2048或ECDH），包含有效期、类型、版本
- 用户首次上传公钥场景：
  - 注册时：客户端随机生成一对公钥（ecdh），注册提交公钥，服务端CA保存用户信息
  - 登录时：第一次登录/满足重置条件时，登录成功后保存最新公钥

**公钥更新流程**:
```
┌──────────┐                            ┌──────────┐
│  客户端   │                            │  CA服务   │
└────┬─────┘                            └────┬─────┘
     │                                        │
     │ 1. 生成新密钥对                        │
     │    (RSA2048或ECDH)                     │
     │                                        │
     │ 2. 计算新公钥SHA哈希                    │
     │                                        │
     │ 3. 用旧私钥签名                        │
     │    (签名 = Sign(旧私钥, 新公钥哈希))     │
     │                                        │
     │─────────── 上传新公钥 ────────────────▶│
     │    (新公钥 + 有效期 + 签名)             │
     │                                        │
     │                                        │ 4. 验证签名
     │                                        │    用旧公钥验证签名
     │                                        │    ├─ 验证失败 → 拒绝更新
     │                                        │    └─ 验证成功 → 继续处理
     │                                        │
     │                                        │ 5. 更新公钥
     │                                        │    保存新公钥到数据库
     │                                        │    更新版本号
     │                                        │
     │◀────────── 更新成功响应 ────────────────│
     │                                        │
     │ 6. 开始使用新密钥                       │
     │                                        │
     │ 7. 老密钥对短期保留                     │
     │    (避免密钥协商遗留问题)                │
     │                                        │
     │ 8. 删除老密钥对                         │
     │    (保留期过后)                         │
```

## 6.4 数据结构设计

**端对端加密密钥表（MongoDB: keys_c2c）**:
- `userId`: 用户id,分片键
- `dstId`: 接收用户id
- `dstType`: 1:用户 2:群 3:系统
- `content`: 密钥消息内容
- `msgPb`: pb序列化内容
- `keyVersion`: 密钥版本号(snowflake)

**公钥信息表（MySQL: tb_ca_info）**:
- `user_id`: 用户id
- `identity_key_pub`: hex身份公钥
- `identity_key_pri`: hex身份公私钥（aes加密）
- `signed_key_pub`: hex签名后公钥
- `signed_key_pri`: hex签名后私钥（aes加密）
- `version`: 公私钥更新版本号
- `state`: 1:正常 0:无效

**加密对称密钥存储表 (tb_encrypted_symmetric_key)**:
- `session_id`: 会话ID
- `sender_id`: 发送方用户ID
- `receiver_id`: 接收方用户ID或设备ID
- `encrypted_key`: 加密后的对称密钥密文
- `key_version`: 密钥版本号
- `key_type`: 对称密钥类型或用途标识
- `expire_time`: 过期时间
- `status`: 状态（1:有效，2:已使用，3:过期/撤销）
