# 系统化排障方法论

> 来源：生产环境故障排查面试考点文档

## 8.1 不要凭直觉，要建立排障SOP

```
1. 定位：什么时间、什么范围、什么症状？（用监控回答）
2. 隔离：是不是只有我们？是不是只有这个机房？是不是只有这个接口？
3. 止损：先恢复服务，再查根因（切流、降级、重启、回滚、扩容）
4. 复现：是稳定复现还是偶发？找到最小复现条件
5. 根因：找到根本原因（不只是表面现象）
6. 根治：改代码/改配置/改架构，让同类问题不再发生
7. 复盘：出 Report，同步团队，沉淀到排障手册
```

## 8.2 可观测性三层模型

```
┌─────────────────────────────────────────────┐
│  第3层：业务指标（订单量、消息到达率、延迟）  │
│  → 告诉你"用户受到影响了"                    │
├─────────────────────────────────────────────┤
│  第2层：应用指标（QPS、错误率、RT分位、熔断） │
│  → 告诉你"哪个服务/接口出了问题"             │
├─────────────────────────────────────────────┤
│  第1层：基础设施（CPU、内存、磁盘IO、网络、GC）│
│  → 告诉你"底层资源出了什么问题"              │
└─────────────────────────────────────────────┘
```

**面试口播**：
> 我做运维体系的核心思路是"三每"——每层有指标、每层有告警、每层有看板。出问题的时候，从上往下收敛：先看业务指标有没有异常→定位到具体接口→看该接口的底层资源。这样效率最高，不会像无头苍蝇一样到处查。

## 8.3 排障工具链

| 工具 | 用途 | 体现功力的话 |
|------|------|-------------|
| `perf top / perf record` | CPU 瓶颈分析、火焰图 | "线上一个接口突然变慢，我用 perf 发现 60% 的 CPU 耗在 malloc 上，最后定位到是 jemalloc 的 arena 竞争" |
| `strace` | 系统调用追踪 | "用 strace 看一个卡住的 Redis 进程，发现一直卡在 fsync，定位到磁盘有问题" |
| `tcpdump` | 网络抓包分析 | "tcpdump 抓包发现大量 TCP 重传，确认是网络丢包导致的问题" |
| `bcc/bpftrace` | eBPF 动态追踪 | "用 bpftrace 追踪内核函数，不侵入代码就能分析 IO 延迟" |
| `gdb` | 进程调试、coredump 分析 | "线上 coredump 了，用 gdb 看 backtrace 定位到空指针，结合日志找到触发条件" |
| `valgrind/memcheck` | 内存泄漏检测 | "怀疑有内存泄漏，valgrind 跑一下确认，找到未释放的位置" |
| `jeprof` (jemalloc) | 内存分配分析 | "Redis 内存碎片高，用 jeprof 看内存分配热点，找到碎片根因" |
