# 群消息扇出聚合

**简历原文**：群消息扇出：按网关分组聚合推送，将跨节点 RPC 数量级降低

## 数据支撑

| 场景 | RPC 次数 | CPU 消耗 |
|------|---------|---------|
| 老方案（逐成员推送） | 3000 次/条（万人群在线 ~3000） | PushServer CPU 打满 |
| 新方案（按网关节点聚合） | ~10 次/条（网关节点数 ~10） | CPU 大幅下降 |

在线率约 30%（万人群 ~3000 人在线）。网关节点约 10 台，按 `accnodeidentify`（`ip:port:workIndex`）分组后，等效 3000 → 网关节点数（~10）。每条跨节点 RPC 节省 ~0.5–1ms（gRPC 同 DC 1–3ms），总节省 ~1.5–3s CPU 时间/消息。

## 理论支撑

扇出优化的本质是把 **O(N) 跨进程 RPC** 转为 **O(G) RPC + O(N) 本地内存操作**（N=在线成员数，G=网关节点数）。网关本地遍历连接表是纯内存操作（哈希表查找 ~ns），相比跨进程 gRPC（~ms）快 3 个数量级。

新架构：MsgServer 落库 → 写 RocketMQ → PushServer 消费 → 按 `accnodeidentify` 分组 → 批量 RPC 到每个网关 → 网关本地 fanout。引入 MQ 增加约 5–10ms 延迟，但换来的是 PushServer CPU 量级下降。

## 业界对标

- **微信公开架构**：群消息采用"拉模式"（客户端感知到新消息后主动拉取）在超大群，与本方案"推模式"各有适用场景
- **美团实时消息系统**（公开分享）：按接入层节点聚合推送，思路与本项目完全一致
- **Slack 消息路由**：频道消息通过中间 broker 聚合，避免 O(N) 直推

## 追问预案

**Q：如果某个网关节点挂了，这批成员的消息怎么办？**
> 网关心跳检测（10s），挂掉后成员状态从 Redis 中清除（RocketMQ 下线事件）。PushServer 在聚合时跳过这批成员；这批成员在重连到新网关后，会触发拉取离线消息。
