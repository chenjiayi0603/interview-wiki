# 长连接认证和链路加密方案

## 一、整体流程说明

1. 客户端使用 RSA 公钥加密临时生成的 `aeskey`、`userid`、`ecdh_pubkey` 等信息，作为登录请求包。
2. 登录请求包中，使用 protobuf 封装数据，拆分为 `rsaData` 与 `aesData` 两部分。`rsaData` 用 RSA 加密，`aesData` 用临时 AES 密钥加密。
3. 服务器收到请求包后，依次用私钥解密获得临时 AES 密钥，用 AES 解密获得 token 等敏感数据。
4. 双方通过 ECDH 算法交换密钥协商，生成后续通信 session key，设置通信过程中对称加密与消息认证算法（AES256、HMAC-SHA256）。

### RSA 公钥获取与变更说明

- **RSA 公钥获取来源**：
    - 客户端首次发起长连接登录/认证时，需要使用服务器的 RSA 公钥对敏感信息进行加密。
    - 该 RSA 公钥通常由服务端运维同学在上线前统一生成一次（如 2048bits），并通过以下方式分发/获取：
        - **方式一：随 APP/SDK 一起内置**（推荐）  
          APP 发布前，将 RSA 公钥编码（如 PEM/Base64/Hex，去掉私钥）固化在客户端代码或配置中。这样攻击者无法获知私钥，客户端可直接调用进行加密，无需每次拉取。
        - **方式二：登录前拉取**  
          客户端首次运行时，向服务端的公开 HTTP(S) 接口请求当前 RSA 公钥，校验服务端证书有效性后本地化保存。此方法适合密钥可能轮换的场景。
        - **方式三：结合动态热点分发/CA下发**  
          若安全要求极高,可以和 CA 中心或可信链路下发方式结合使用，客户端按需动态拉取或者周期自动更新。

- **RSA 公钥是否需要变更**：
    - **一般情况下**，RSA 公钥可长期使用不变，只有以下场景要考虑更换：
        1. 运维主动轮换密钥对（如定期或密钥泄露风险时）。
        2. 私钥疑似泄漏、算法升级（如2048升级到3072），或安全策略要求强制轮换。
    - 若公钥需要变更，建议：
        - 确保新公钥下发到所有客户端（APP升级、拉取 API 或热更新分发）。
        - 服务端需要在一段时间内同时兼容老公钥和新公钥登录（灰度平滑切换）。
        - 公钥指纹等信息可随接口返回，客户端可校验合法性/完整性。

- **补充说明**：
    - RSA 公钥只用于保护第一次登录/认证过程（临时 AES key、用户身份等），实际链路密钥协商后业务数据全部用对称通信密钥（如 sessionKey）加密。
    - 公钥通常无需频繁更换，但应定期检查安全性和管理权限，推荐密钥管理制度与自动告警机制。

**总结**：  
RSA 公钥推荐随 APP 内置，或登录前通过安全接口拉取；如需变更则采用平滑切换和版本管理机制，避免业务中断。

### 概要流程简图

以下为“长连接认证和链路加密方案”流程图（采用文本字符画，不使用 Mermaid）。

```
┌─────────────┐
│   客户端    │
└──────┬──────┘
       │ 1. 生成随机 AES key, ECDH 公钥，用户参数，封包发送
       ▼
┌─────────────┐
│  Access/网关│
└──────┬──────┘
       │ 2. 转发请求（或本地解密）
       ▼
┌─────────────┐
│   Login服务 │
└──────┬──────┘
       │ 3. 用 RSA 私钥解密获得 AES key、ECDH 公钥、用户ID信息
       │ 4. 用 AES key 解密进一步参数（token、时间、设备id 等）
       │ 5. 服务器已有 ECDH 密钥对，协商生成通信共享密钥 signalKey
       │ 6. 生成 sessionKey（后续主通信加密密钥）
       ├─► 用 signalKey 加密 sessionKey 
       │
       │ 7. 将服务器 ECDH 公钥、加密的 sessionKey 回包封装
       │ 8. 用临时 AES key 加密整个应答并下发
       ▼
┌─────────────┐
│   客户端    │
└──────┬──────┘
       │ 9. 解密服务器应答，提取服务器 ECDH 公钥
       │    用自己的 ECDH 私钥和服务器 ECDH 公钥协商 signalKey
       │    signalKey 解密拿到 sessionKey
       │
       │ 10. 之后所有业务通信 payload，如下加密：
       │    - AES256/CBC 加密数据
       │    - HMAC-SHA256 校验
       │    - 使用 sessionKey/AUTH_KEY 作为密钥
       ▼

    <--- 长连接安全链路建立完毕，后续所有消息全程加密 ---> 
```

注：
- 关键交互步骤均已标注。
- 双向箭头表示双方协商密钥与数据传递。
- SessionKey 用于后续所有数据对称加密和完整性校验。
- 若解密失败需重新发起协商，或提示登录过期。

## 二、通信包结构

### 登录请求包（LoginReq）

- **包头**：略  
- **包体（protobuf）**：

```
message LoginReq {
    bytes rsaData = 1; // RSA 加密
    bytes aesData = 2; // AES 加密
}
```

#### rsaData（RSA 加密 ProtoBuf 包含）

- `userId`: 用户ID
- `ecdh_pubkey`: 客户端 ECDH 公钥 (32字节)
- `aeskey`: 临时 AES 密钥 (32字节)

#### aesData（AES 加密 ProtoBuf 包含）

- `token`: 客户端 token，字符串
- `clientTime`: 客户端时间戳 (4字节，1970起)
- `devid`: 设备唯一标识，字符串
- `loginseq`: 登录流水号 (8字节，每次自增)
- **deviceInfo**（嵌套）:
    - `clientType`: 客户端类型（1:ios, 2:android, 3:mac, 4:pc）
    - `pushToken`: 离线推送 token

## 三、认证流程

### 步骤1：服务器端解密获取客户端参数

1. 用 RSA 私钥解密 `rsaData`，得到 `userId`、`ecdh_pubkey`、`aeskey`。
2. 用获得的临时 AES 密钥解密 `aesData`，还原 token、时间戳等敏感数据。

```cpp
// 1. 反序列化收到的 login 请求包（protobuf）
if (!m_pAppLoginData->m_loginReq.ParseFromArray(
        m_oReqMsgBody.body().c_str(), m_oReqMsgBody.body().size()))
{
    // 解析 Protobuf 出错
    return ERR_PARASE_PROTOBUF;
}

// 2. 用服务器 RSA 私钥解密 loginReq 里的 rsadata，获得客户端公钥（ecdh_pubkey）、userId、临时 AES 密钥等
std::string strRsaData;
if (!Rsa2048Decrypt(m_pAppLoginData->m_loginReq.rsadata(), strRsaData, m_pLoginSession->GetRsaPrivateKey()))
{
    // RSA 解密失败
    return ERR_RSADECRYPT_ERROR;
}

// 3. 反序列化 RsaData，客户端公钥（ecdh_pubkey）、aeskey、userid 都包含在这里
if (!m_pAppLoginData->m_pbRsaData.ParseFromString(strRsaData))
{
    // RsaData 解析失败
    return ERR_PARASE_PROTOBUF;
}
// 客户端公钥在 m_pAppLoginData->m_pbRsaData.ecdhpubkey() 字段中

// 4. 用上一步获得的临时 aeskey 解密 aesdata，得到实际的 token、时间戳等
std::string strAesData;
if (!Aes256Decrypt(m_pAppLoginData->m_loginReq.aesdata(), strAesData, m_pAppLoginData->m_pbRsaData.aeskey()))
{
    // AES 解密失败
    return ERR_AESDECRYPT_ERROR;
}

// 5. 反序列化 AesData，提取 token、devid、clientTime 等登录参数
if (!m_pAppLoginData->m_pbAesData.ParseFromString(strAesData))
{
    // AesData 解析失败
    return ERR_PARASE_PROTOBUF;
}
```

### 步骤2：服务端返回 session 加密信息

1. 服务器启动/维护自己的 ECDH 公私钥对。
2. 服务器通过客户端 ECDH 公钥与服务端私钥计算共享密钥（ECDH）。
3. 随机生成本次 Session 的 AES 密钥 `m_aesSessionKey`。
4. 用前面协商所得 ECDH 共享密钥对 Session AES 密钥加密，连同服务端公钥一同返回客户端。

```cpp
// 生成服务器 ECDH 公私钥
generate_key_pair_public_private_ecdh_string(m_ecdhServerPubkey, m_ecdhServerPrivateKey);

// 计算 ECDH 共享秘钥
uint8_t* signalKey = calculate_ecdh_share_key(
    m_pAppLoginData->m_pbRsaData.ecdhpubkey().c_str(),
    m_pLoginSession->GetEcdhServerPrivateKey().c_str()
);

// 用 ECDH 共享密钥加密 “session key”
if (!Aes256Encrypt(m_pAppLoginData->m_aesSessionKey,
                   strEncryptSessionkey,
                   std::string((char*)signalKey, ECDHKEY_LEN)))
{
    // 处理加密失败
}

// 写入 response 部分
m_pAppLoginData->m_loginRsp.set_ecdhserverpubkey(m_pLoginSession->GetEcdhServerPubkey());
m_pAppLoginData->m_loginRsp.set_sessionkey(strEncryptSessionkey);

// 用临时 AES key 加密整个应答包下发
if (!Aes256Encrypt(m_pAppLoginData->m_loginRsp.SerializeAsString(),
                   strEncryptLoginRsp,
                   m_pAppLoginData->m_pbRsaData.aeskey()))
{
    // 处理应答加密失败
}
```

## 四、后续通信密钥与加密方式

- **SessionKey = AES 解密(协商 ECDH 密钥, sessionkey 字符串)**
- 之后所有通信：
    - 加密算法：AES256 CBC
    - 校验算法：HMAC-SHA256
    - 使用协商得到的 SessionKey 作为加密/校验密钥
    - `Auth_key = SessionKey`
