## 一、项目复盘与架构设计

**考察点**：业务理解深度 & 架构设计能力

### 背景：项目定位与目标

我独立开发的项目是 **InterviewPro——一款 AI 驱动的面试练习 App**（iOS / Android / H5），用户可以通过语音或文字回答 AI 面试官的问题，获得实时评分和反馈。

**业务痛点：**
- **面试准备成本高**：传统模拟面试需要预约真人面试官，¥200-500/小时，普通人练不起
- **反馈不即时**：面试结束后等几天才有反馈，难以针对性提升
- **缺少量化维度**：市面上产品只给个总分，没有发音、流利度、语法、词汇、内容五个维度的拆解
- **场景单一**：无法自由切换岗位、角色、难度

**项目目标：**
> 做一个 AI 面试教练：用户选择岗位和难度，AI 面试官出题、评分、反馈、出下一题，7 秒一轮循环。成本仅 ¥0.15/次，定价 ¥5/次，毛利率 97%。

### 难点：技术上的核心挑战

#### 挑战 1：端到端延迟 —— 7 秒完成一轮面试对话

一轮完整的面试交互链路：**AI 出题（3s）→ TTS 语音合成（1s）→ 用户回答 → STT 语音识别（0.5s）→ AI 评分（2s）→ 下一题**。加起来约 7 秒，业务要求用户无等待感。

**方案：**
1. **AI 流式响应（首字 0.5s）**：DeepSeek API 开启 `stream=true`，服务端边接收 token 边通过 WebSocket 推送，用户感知首字从 2s 降到 0.5s
2. **Eino Parallel 并行编排**：评分 Agent + 出题 Agent + 发音评测三路并行，延迟从串行的 18s 降到并行的 8s
3. **TTS 引擎预热**：服务启动时预加载 TTS 模型，首次合成从 2s 降到 1s
4. **STT 流式上传**：客户端边录音边上传，阿里云实时流识别，端到端 510ms

#### 挑战 2：AI 评分准确性 —— 4B 模型打败 236B 模型

评分是产品的核心价值。我们对比了 DeepSeek-V3（236B）、Qwen2.5-7B、Qwen3-4B 等模型，发现**参数量不决定评分准确率**。

**方案：**
- 选型 Qwen3-4B-Instruct-2507（4B 本地模型），评分准确率 92%，超过 DeepSeek-V3 的 50%
- 核心原因：该模型有显式思维链（CoT），会逐维度推理 + 自校验，而不是靠整体感觉打分
- 关键配置：`temperature=0.1`、`n-predict ≥ 3000`（思维链消耗 1000-2000 tokens）
- DeepSeek 系统性低估 7-11 分（训练偏好导致"不过度夸赞"），不适合评分场景

#### 挑战 3：高并发 WebSocket —— 单机支持 1 万并发连接

面试是实时双向通信，WebSocket 长连接，可能同时有大量用户在线。

**方案：**
- **Hub + Client Actor 模型**：每个连接独立 ReadPump / WritePump / saveLoop 三个 goroutine，注册/注销通过 channel 串行处理
- **每连接仅 50KB**：通过对象池复用、缓冲区精细控制，1 万连接 = 500MB
- **读写分离**：WritePump 单一消费者模式 + 缓冲 channel（256 容量），非阻塞 send
- **CAS 幂等保护**：`atomic.CompareAndSwap` 防止重复评估
- **上下文树**：用户断开时 `context.WithCancel` 级联取消所有子操作，无 goroutine 泄漏

#### 挑战 4：题库系统 —— 混合检索 + 去重 + AI 补充

题库需要量大、不重复、场景匹配。纯靠 LLM 生成成本高、质量不稳。

**方案：**
- **混合检索（RRF）**：Qdrant 向量检索 + PostgreSQL LIKE 关键词检索 → RRF 融合排序
- **三源题目**：预置题（curated）+ 用户贡献 + AI 实时生成
- **跨会话去重**：30 天窗口内出过的题不再出
- **冷启动加权**：新题（7 天内）权重 2x，线性衰减
- **QualityScore 动态更新**：使用次数越多，排序越靠后，保证题目轮转

### 收益：最终交付的业务/技术价值

|------|:-----:|:------:|:----:|
| AI 首字延迟 | 2s | **0.5s** | -75% |
| TTS 合成延迟 | 2s | **1s** | -50% |
| STT 识别延迟 | 800ms | **500ms** | -37.5% |

| 评分准确率（Qwen3-4B） | — | **92%** | 超过 DeepSeek-V3 |

### 反思：当前系统设计的缺陷与优化方向

#### 缺陷 1：AI 评分在 good/fair 边界有系统性偏差
**问题**：Qwen3-4B-Instruct 在 good 档（75-89）有 -4.7 分的系统性偏低。处于 good/fair 边界的回答容易误判。

**优化方向**：引入 few-shot 校准。在 prompt 中加入 2-3 个边界案例的评分示例，微调模型的分数映射。或者用回归模型对 LLM 输出做二次校准（如 linear correction: `calibrated_score = raw_score + 4.7`）。

#### 缺陷 2：WebSocket 写缓冲区无背压
**问题**：`send` channel 缓冲区 256，满时直接 drop 消息。高并发场景下 `audio_response` 或 `evaluation_result` 可能丢失，客户端收不到反馈。

**优化方向**：改为加权丢弃策略——`five_dimension_evaluation` 和 `feedback_ready` 等高优事件不能被丢弃，`typing_indicator` 等低优事件可以丢。或者改用有界优先队列。

#### 缺陷 3：Eino Graph 运行时缺少超时传播
**问题**：Eino `compose.Parallel` 的三个分支各有独立超时（30s），但 merge 节点没有超时。如果某个分支 hang 住（如 LLM 不返回），merge 会一直等待，导致整个 evaluateAndRespond goroutine 泄漏。

**优化方向**：在 merge lambda 中加 context timeout，`max(30s, 30s, 30s) + 5s` 兜底。超时后对未返回的分支执行降级（如返回"评分暂不可用"）。

#### 缺陷 4：RAG 出题链路缺少 A/B 测试能力
**问题**：混合检索的权重参数（RRF k=60、向量阈值 0.6、冷启动权重 2x）是硬编码的，无法快速实验调优。

**优化方向**：参数配置化 + 实验平台。将 RRF k、向量阈值、AI 补充率等参数做成可动态配置的，支持按用户 ID hash 做 A/B 实验，自动统计各参数组合下的出题满意度。

## 二、性能优化与平滑迁移

**考察点**：性能优化 & 不停机迁移能力

### 场景说明

InterviewPro 经历了两次架构演进：
1. **V1（单体）**：单一 Go 服务 + SQLite + 阿里云语音，所有逻辑在 if-else 中串联
2. **V2（分层架构）**：按职责拆分为 Handler / Service / Agent 三层，引入 Eino 编排引擎
3. **V3（高可用）**：WebSocket 并发优化 + 多 Provider Fallback + 可观测性

### 拆分思路：按职责+领域拆分

> 面试话术："拆分的核心是'单一职责'——让每一层只做一件事，且做好。"

**拆分维度：**

| 维度 | V1 单体 | V2/V3 拆分后 |
|------|:-------:|:----------:|
| **网络层** | 混在业务逻辑中 | 独立 Handler + WebSocket Hub |
| **AI 编排** | if-else 串联 | Eino compose.Parallel 三路并行 |
| **语音服务** | 阿里云硬编码 | 8 STT + 7 TTS Provider，策略模式 |
| **AI 模型** | DeepSeek 硬编码 | 工厂模式，支持 DeepSeek / Qwen 切换 |
| **题库** | 无 | 混合检索 + QuestionPool + SessionDeck |
| **可观测性** | 无 | Prometheus + 结构化日志 + 调用追踪 |

### 集群扩容策略

#### 弹性伸缩设计

```
由于 InterviewPro 是独立全栈项目，当前是单机部署（Docker Compose）。
如果是大厂生产环境，我会这样设计：

水平扩容（Per-Connection 无状态）:
├── KeyDB 计算节点是无状态的（所有会话状态在 Client 内存中）
├── 关键痛点：WebSocket 连接有状态，需要 Session Affinity
├── 方案：LVS + Nginx 四层转发，基于源 IP hash 做会话保持
├── 或：K8s Ingress Controller + sticky sessions
└── 扩容触发：CPU > 70% 或连接数 > 8000

垂直扩容（单机资源规划）:
├── 当前指标：2 核 4GB → 1 万连接，500MB Go 进程 + 500MB WebSocket
├── 瓶颈预判：4GB 机器上限约 2 万连接（3GB 应用 + 1GB 系统）
├── 升级到 4 核 8GB → 预估 3 万连接
└── 8 核 16GB → 预估 6 万连接（线性增长有边际递减）
```

#### 容量规划

```
单节点容量计算（2 核 4GB）:
├── WebSocket 连接上限: min(10,000, 内存_上限 / 每连接_50KB)
│   = min(10,000, 3GB/50KB) = min(10,000, 60,000) = 10,000
├── 并发评估上限: 
│   ├── 每轮面试 ~7s，每个用户约 30% 时间在等待 AI（活跃连接）
│   ├── 10,000 连接 × 30% ≈ 3,000 活跃评估中
│   └── AI API 并发限流 10 → 队列等待，瓶颈在 API 不在服务端
└── 数据库连接池: max(50, 2 × CPU_cores) = 4
```

#### 瓶颈定位方法

| 瓶颈类型 | 定位手段 | 典型阈值 |
|---------|---------|---------|
| **Goroutine 泄漏** | `pprof goroutine` + `curl /debug/vars` | goroutine 数持续增长 |
| **WebSocket 缓冲区满** | 日志 `send buffer full` 频次 | > 1 次/分钟 |
| **AI API 超时** | Prometheus `ai_request_duration_ms` | P99 > 15s |
| **DB 连接池耗尽** | `db.Stats().OpenConnections` | 达到 max_open_conns |
| **内存泄漏** | `pprof heap` 对比 | RSS 持续增长不回落 |
| **GC 抖动** | `pprof trace` STW 时长 | STW > 10ms/次 |

**压测踩过的坑：**
1. **WebSocket 连接泄漏**：用户断网后服务端未触发 close handshake，Client 一直残留在 Hub 中。修复：ReadPump 读到 EOF 时确保调用 `hub.unregister` 和 `cancel()`
2. **SQLite 写冲突**：并发的 `saveMessage` 导致 `database is locked` 错误。修复：saveLoop 串行化 + WAL 模式
3. **Ollama 显存溢出**：Qwen Local 模型并发请求导致 GPU OOM。修复：信号量限流 `maxConcurrent=2` + 请求排队

#### 阈值设定

| 指标 | 警告水位 | 熔断水位 | 动作 |
|------|:-------:|:-------:|------|
| P99 AI 响应延迟 | > 10s | > 20s | 降级：切到本地 Qwen 模型 |
| STT 错误率 | > 5% | > 20% | 降级：切换到下一个 Provider |
| TTS 错误率 | > 5% | > 20% | 降级：切到 Edge TTS（免费兜底） |
| WebSocket 连接数 | > 8,000 | > 10,000 | 限流：拒绝新连接 |
| AI API 错误率 | > 5% | > 15% | 熔断：停止新 AI 请求，返回缓存 |
| 内存使用率 | > 70% | > 85% | 告警 + 对象池清理 |

### 双写双读切换流程（迁移场景）

InterviewPro 的场景是从 **V1 单体 SQLite → V2 PostgreSQL** 的数据库迁移。

#### 阶段 1：全量同步

```
旧库（SQLite）──► 导出全量 SQL ──► 导入新库（PostgreSQL）
                                        │
                                   校验：行数 + 最近 100 条记录采样对比
```

#### 阶段 2：双写

```
写路径:
  客户端请求 → V2 服务 → 双写 SQLite + PostgreSQL
               ├── 同步写 PostgreSQL（主库，返回客户端）
               └── 异步写 SQLite（兜底，失败只记日志不阻塞）

校验:
  ├── 每次写入后对比两库的 affected rows
  └── 差异 > 0.1% 告警
```

#### 阶段 3：灰度切读

```
Step 1: 10% 读流量切到 PostgreSQL（观察 1 小时）
Step 2: 50% 读流量切到 PostgreSQL（观察 1 小时）
Step 3: 100% 读流量切到 PostgreSQL

灰度策略:
├── 按用户 ID 末位 hash
├── 新用户默认走新库
└── 支持 header 强制指定（X-Use-New-DB: true）
```

#### 阶段 4：回滚

```
触发条件: P99 读延迟 > 2x 基线 或 错误率 > 1%
回滚: Proxy 层 100% 切回 SQLite（< 1s）
事后: 排查 PostgreSQL 连接池 / 索引 / 慢查询
```

## 三、复杂故障与分层止损

**考察点**：复杂故障处理 & 架构根治能力

### 场景适配：InterviewPro 的 AI + 语音链路

模板场景是 `Kafka → Flink → Redis → DB`，对应到 InterviewPro 的链路是：

```
客户端 → WebSocket → AI 评分/出题 → STT/TTS 语音服务 → DB
                          ↓
                     Eino Agent 编排
                     (ScorerAgent + InterviewerAgent)
```

这条链路上最典型且影响最大的故障是：**AI API 超时导致整个面试流程卡住**。下面以此场景展开。

---

### 分层止损预案（即时应对）

#### 第 1 层：客户端侧 —— 用户体验保护

```
问题现象：用户提交回答后，等 10s+ 没收到评分，页面卡死

止损动作:
├── 前端超时兜底
│   ├── WebSocket 消息超时 15s → 显示"评分处理中，请稍候"
│   ├── 30s 仍无响应 → 显示"网络异常，请重试"
│   └── 不阻塞用户操作（用户可继续下一题）
│
├── 指数退避重试
│   ├── 发消息失败 → 1s → 3s → 10s 重试
│   └── 重试 3 次放弃，提示用户检查网络
│
└── 本地缓存兜底
    ├── 缓存的面试题本地展示（无 AI 评分，但有题目可以练习）
    └── 联网恢复后同步
```

#### 第 2 层：WebSocket 层 —— 请求分级 & 熔断

```
问题现象：AI API 超时导致服务端大量 goroutine 阻塞在等待响应

止损动作:
├── 并发限流（信号量）
│   ├── `sem := make(chan struct{}, maxConcurrent)`  // max=10
│   ├── 超过 10 个并发 AI 请求 → 排队等待
│   └── 队列 100 满 → 直接返回 RATE_LIMIT
│
├── 请求超时控制
│   ├── 评分请求：30s 超时
│   ├── 出题请求：30s 超时
│   ├── TTS 请求：15s 超时
│   └── 超时 → cancel context → 释放 goroutine → 返回 fallback
│
├── CAS 幂等保护（防止重复评估）
│   ├── `c.isEvaluating.CompareAndSwap(false, true)`
│   ├── 同用户同时只能有一个评估中
│   └── 重复请求直接返回已有结果
│
└── 熔断器（自研轻量版）
    ├── 统计窗口：30s
    ├── 错误阈值：AI API 失败率 > 30% → 熔断开启 60s
    ├── 熔断期间：AI 评分为 "暂不可用"，直接返回下一题
    └── 半开恢复：60s 后放 1 个请求探测
```

#### 第 3 层：Eino Agent 层 —— 分支降级

```
问题现象：ScorerAgent（评分）分支超时，但 InterviewerAgent（出题）正常

止损动作:
├── 分支隔离
│   ├── compose.Parallel 三路独立 goroutine
│   ├── 评分失败 → 降级返回基础分（如 overall=5.0）
│   ├── 出题失败 → 降级从题库取下一题（纯本地操作）
│   └── 发音评测失败 → 跳过发音维度
│
├── merge 超时兜底
│   ├── merge lambda 设置 overall timeout = 35s
│   ├── 超时 → 取已返回的分支结果
│   └── 未返回的分支用默认值填充
│
└── fallback 链（语音服务）
    ├── STT 主 Provider（bailian）失败 → 自动切到 whisper → 再失败切到 xunfei
    ├── TTS 主 Provider（aliyun）失败 → 切到 edge（免费兜底）
    └── 所有 Provider 失败 → 返回错误提示
```

#### 第 4 层：数据持久化层 —— 写保护 & 降级

```
问题现象：大量 AI 结果写入 DB，DB 连接池耗尽

├── saveLoop 串行化
│   ├── 所有 DB 写入通过 saveCh channel 串行
│   ├── 避免并发 INSERT 冲突

├── 连接池保护
│   ├── GORM `SetMaxOpenConns(20)`

│   └── `SetConnMaxLifetime(30m)`

└── 降级到内存队列
    ├── DB 不可用 → 写入内存队列（最大 1000 条）
    ├── DB 恢复后回刷
    └── 队列满 → 丢弃非关键数据（如 typing_indicator）
```

#### 根因定位方法论

```
定位 AI API 超时根因的步骤：

├── 案例 3：Ollama GPU OOM

│   证据：Ollama 日志 "CUDA out of memory" + 服务端 AI 调用全部超时

└── 案例 4：题库 AI 补充导致链式超时
```

##### 根治 1：AI API 调用优化

```
问题：AI API 延迟波动大，排队机制不完善

根治方案:
├── 动态并发控制
│   ├── 正常：maxConcurrent=10
│   ├── 低延迟时（P99 < 3s）：自动提升到 15
│   └── 高延迟时（P99 > 10s）：自动降到 5

├── 请求优先级调度
│   ├── P0（评分请求）：优先分配 AI 资源

│   └── P2（AI 题库补充）：低优先级，可被 P0/P1 抢占

└── 双 Provider 热备
    ├── DeepSeek（主）+ Qwen Local（备）
    ├── DeepSeek 失败 3 次 → 切到 Qwen

```

##### 根治 2：WebSocket 消息通道重构

```
问题：单一缓冲 channel 满时丢消息

根治方案:
├── 分级缓冲通道
│   ├── highPriChan（cap=64）：评分、反馈、错误通知 → 永不丢弃
│   ├── medPriChan（cap=128）：AI 响应、下一题 → 丢弃时降级
│   └── lowPriChan（cap=256）：typing_indicator、心跳 → 可丢弃
│
├── WritePump 优先处理
│   ├── select 先检查 highPriChan → medPriChan → lowPriChan
│   ├── 高优消息永远先发
│   └── 低优消息在缓冲区满时直接 drop
│
└── 消息确认机制（关键消息）
    ├── evaluation_result 和 feedback_ready 要求客户端 ACK
    ├── 15s 未收到 ACK → 重推
    └── 重试 3 次失败 → 记日志 + 客户端下次连接时补推
```

##### 根治 3：数据一致性兜底

```
问题：异步 DB 写入失败导致数据丢失

根治方案:
├── 写操作日志（WAL-like）
│   ├── 每次 save 请求先写 Redis list（RPUSH）
│   ├── saveLoop 处理完后 DEL
│   └── 重启时扫描 Redis 中的未处理记录，补偿写入
│
├── 幂等写入
│   ├── 每条消息有全局唯一 ID（snowflake）
│   ├── DB 层 UPSERT（ON CONFLICT DO NOTHING）
│   └── 重复写入不会产生重复数据
│
└── 定期对账
    ├── 每天凌晨对比 Redis 中消息数和 DB 中消息数
    ├── 差异 > 0.1% → 自动补偿
    └── 补偿日志供审查
```

```
│   ├── stt_request_duration_ms

└── 健康检查端点
```

### 🔁 幂等性设计

```
场景：用户可能重复提交回答（网络重试、双击按钮），导致重复 AI 评估

幂等方案:
├── CAS 原子锁
│   └── `c.isEvaluating.CompareAndSwap(false, true)`
│       ├── 同一用户同时只能有一个评估
│       └── 重复请求直接忽略
│
├── 消息去重（客户端生成消息 ID）
│   ├── 前端每次消息生成 UUID（message_id）
│   ├── 服务端 check `message_id` 是否已处理（Redis Set, TTL=1h）
│   └── 已处理 → 返回缓存结果
│
├── DB 写入幂等
│   ├── UPSERT 语义：`INSERT ... ON CONFLICT (id) DO NOTHING`
│   ├── 重复写入不会产生重复记录
│   └── 消息序列号（messageSeq）在 saveLoop 中严格递增
│
└── 反馈生成幂等
    └── `c.feedbackGenerated.CompareAndSwap(false, true)`
        ├── 会话结束时只能生成一次反馈报告
        ├── 同时触发两次（WebSocket + HTTP）→ 只执行一次
        └── 避免重复的 AI 调用（节省成本）
```

### 💥 节点宕机

```
场景：InterviewPro 是单节点部署，但假设扩展到多节点：

单节点宕机 -> 该节点上所有 WebSocket 连接断开

止损方案:
├── 客户端自动重连
│   ├── 断线检测：WebSocket onclose
│   ├── 退避重连：1s → 3s → 10s → 30s
│   ├── 重连后恢复会话状态：
│   │   ├── 发送 resume_session(session_id)
│   │   ├── 服务端查询 DB 中的会话记录
│   │   └── 重新推送未确认的消息
│   └── 最多重试 10 次，放弃后提示用户
│
├── 无状态重启
│   ├── 服务端进程重启时间 < 10s（Go 二进制启动快）
│   ├── 重启后从 DB 恢复所有活跃会话
│   └── 客户端重连后继续面试（不丢进度）
│
└── 跨节点会话迁移（多节点场景）
    ├── 会话状态存 Redis（JSON: session_id → ClientState）
    ├── 节点宕机 → 客户端重连到其他节点
    ├── 新节点从 Redis 恢复会话状态
    └── 面试继续，用户无感知
```

### ⚔️ 资源抢占

```
场景：AI API 配额有限，多个评分/出题任务竞争

方案:
├── 任务优先级调度
│   ├── P0（紧急）：付费用户评分请求 → 优先分配 AI 资源
│   ├── P1（正常）：普通用户评分/出题 → 正常排队
│   ├── P2（后台）：AI 题库补充 / 会话摘要生成 → 低优先级
│   └── P3（定时）：数据统计 / 模型预热 → 空闲时执行
│
├── 资源配额管控
│   ├── 全局并发 AI 调用：max=10（信号量控制）
│   ├── 付费用户：并发上限 3，排队插队权重 2x
│   ├── 免费用户：并发上限 1，排队插队权重 1x
│   ├── Provider Token 配额：按分钟统计
│   └── 超配额 → 排队等待或降级
│
├── 动态降级策略
│   ├── 高峰期（白天 9-21点）：关闭题库 AI 补充
│   ├── 低峰期（凌晨）：批量处理后台任务 + 模型预热
│   ├── AI 繁忙时：出题降级为纯题库模式（零 AI 调用）
│   └── 评分繁忙时：返回基础分 + 题库预存反馈
│
└── 公平调度
    ├── 任务按优先级入队（P0/P1/P2/P3 四个队列）
    ├── 同一优先级内 FIFO
    ├── P0 可抢占 P2 资源（P2 出队，标记为"被抢占"）
    └── 避免 P0 饿死 P1（P0 最多连续处理 5 个后，处理 1 个 P1）
```

### 📊 编排方式对比：DAG 编排 vs. 事件驱动编排

我们当前使用的是 **Eino DAG 编排（`compose.Parallel` + `compose.Chain`）**。

| 维度 | DAG 编排（我们的方案） | 事件驱动编排 |
|:-----|:-------------------:|:----------:|
| **架构** | 编译时定义有向无环图，Invoke 时执行 | 无固定拓扑，通过消息总线异步触发 |
| **数据结构** | 图：节点 + 边 + 状态传递 | 消息队列 + 事件回调 |
| **执行方式** | Invoke(request) → 等待返回完整结果 | 发布事件 → 各消费者独立执行 |
| **超时控制** | 每个节点可设置超时，整体总超时 | 依赖事件超时机制 |
| **错误处理** | 节点级 error 传递，merge 可降级 | 每个消费者独立处理失败 |
| **适用场景** | 请求-响应模式：用户提交 → 等待完整结果 | 流式/异步：数据持续流入，逐步处理 |
| **扩展性** | 节点内部可并发（Parallel），但整体是同步 | 天然异步，每个消费者独立扩缩 |
| **调试难度** | 低：一次调用一个 trace | 高：事件流跨多个消费者，难追踪 |
| **我们的选择** | ✅ DAG（Eino compose.Parallel） | ❌ 不适用于实时面试场景 |

**为什么面试场景选 DAG 编排？**

```
1. 请求-响应模式
   ├── 用户提交回答 → 等待评分 + 下一题 → 显示结果
   ├── 这是一个同步请求应答模式，不是异步流处理
   └── DAG 天然适合：输入 → 处理 → 输出

2. 强一致性要求
   ├── 评分、出题、发音三者需要"同时返回"
   ├── 缺任何一个维度都对用户展示不完整
   └── DAG 的 merge 节点可以等待所有分支完成

3. 超时可控
   ├── 每个分支 30s 超时，总超时 35s
   ├── 超时后可降级（"评分暂不可用"）
   └── 事件驱动下超时更难管理

4. Eino 框架优势
   ├── compose.Parallel 三路并行
   ├── merge 自动合并
   ├── 进程内调用（~0ms 延迟）
   └── 纯 Go 实现，单二进制部署
```

**如果扩展到异步场景（如批量面试报告生成），我会改事件驱动：**

```
事件驱动编排示例：
┌──────────┐ 事件(Kafka) ┌──────────┐
│ 面试完成 ├───────────► │ 摘要生成  │
│ (Session) │            │ Agent    │
└──────────┘            └────┬─────┘
                             │ 事件
                        ┌────▼─────┐
                        │ 报告生成  │
                        │ Agent    │
                        └──────────┘

优点：面试完成 → 异步生成报告，不阻塞下一轮面试
缺点：报告可能延迟 1-2 分钟，需状态轮询或推送
```

### 常见追问准备

| 追问 | 回答思路 |
|------|---------|
| "为什么 4B 模型比 236B 准确？" | 分布对齐问题。Qwen3-4B-Instruct 的思维链 + 训练分布恰好对齐评分标准，DeepSeek 训练偏好导致系统性低估 |
| "Eino 比 LangGraph 好在哪？" | Go 原生、单二进制、进程内调用 0ms 延迟、团队零学习成本 |
| "WebSocket 并发瓶颈在哪？" | 目前是 AI API（信号量排队），服务端 1 万连接没问题。未来瓶颈在 DB 写入 |
| "混合检索的 RRF k 为什么设 60？" | 经验值。k 越大越平滑，k 越小越偏向排名靠前的结果。60 在测试集上效果最好 |
| "STT 多 Provider fallback 切换时间？" | bailian 失败 → 5s 内切换到 whisper → 再失败切到 xunfei。总切换 < 15s |
| "Ollama GPU OOM 怎么解决？" | 信号量限流 maxConcurrent=2 + 请求排队。或用批处理（accumulate 多个请求一起推理） |
| "如果用户量到 10 万，哪里先崩？" | AI API 配额先崩（10 并发 × 7s/轮 × 100 轮/分钟 ≈ 85 次/分钟，已接近 DeepSeek 免费配额上限） |
| "为什么自研不用 gRPC？" | 小项目 HTTP REST + WebSocket 足够。gRPC 增加 protobuf 管理、流控复杂度 |
