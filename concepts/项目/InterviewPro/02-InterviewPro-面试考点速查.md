## 一、性能数据

### 1.1 WebSocket 并发能力

| 指标 | 数值 | 说明 |
|------|------|------|
| 单机最大并发 | 10,000 | 2 核 4GB |
| 每连接内存 | ~50KB | 含缓冲和状态 |
| 连接建立速度 | 1,000/秒 | 持续 30 秒 |
| 心跳间隔 | 30 秒 | 客户端发送 |
| 超时断开 | 90 秒 | 无心跳断开 |
| CPU 占用（空闲） | 20% | 1 万连接心跳 |

**每连接开销**：
```
WebSocket 握手状态：2KB
读缓冲区：          16KB（音频流）
写缓冲区：          16KB（AI 响应）
Goroutine 栈：      2KB
连接对象：          4KB
Redis Session：     2KB
其他：              8KB
合计：              50KB
1 万连接 = 50KB × 10,000 = 500MB
```

## 二、STAR 故事

### 背景 (Situation)

独立开发的 AI 面试练习 App，后端 Go + Gin + WebSocket，前端 React Native，AI 集成 DeepSeek + 阿里云语音。

### 任务 (Task)

- 实现 1 万并发 WebSocket 连接
- AI 问答端到端延迟 < 5 秒
- 语音识别延迟 < 600ms
- 内存控制在 4GB 以内

### 行动 (Action)

1. **WebSocket 架构**：Hub + Client Actor 模型，ReadPump/WritePump 分离
2. **流式响应**：DeepSeek 流式输出，首字 0.5s
3. **信号量限流**：控制并发 AI 请求不超过 10
4. **幂等保护**：CAS 原子操作防止重复评估
5. **异步 DB 写入**：saveLoop 串行化，避免并发 INSERT

### 结果 (Result)

| 指标 | 结果 |
|------|------|
| 并发连接 | 10,000 |
| 端到端延迟 | 510ms（STT）/ 4.5s（问答） |
| 内存 | 3GB |
| AI 首字 | 0.5s |

## 三、高频 Q&A

### Q1: AI 响应慢怎么优化？

> 流式响应：DeepSeek API 支持流式输出，服务端边接收边转发，用户感知首字从 2s 降到 0.5s。

### Q2: 语音识别延迟怎么优化？

> 音频批量上传 + 实时流上传 + 结果缓存。瓶颈在阿里云 API（300ms），本地优化空间有限。

### Q3: 为什么自研不用 gRPC？

> 小项目保持简单：HTTP REST + WebSocket 足够，gRPC 增加复杂度。

### Q4: 手工 DI 比框架好在哪？

> 依赖关系一目了然，编译期检查，调试链路清晰，无第三方 IoC 容器黑盒。

### Q5: WebSocket 并发怎么测试？

> 自研 Go 压测工具：同时建立 1 万连接，每秒发心跳，观察 CPU/内存/延迟。

### Q6: DeepSeek vs Qwen 怎么切换？

> 策略模式 + 工厂方法：`GetModelProviderFromConfig` 根据配置返回不同实现，调用方只依赖 `ModelProvider` 接口。
