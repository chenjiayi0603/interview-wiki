## 一、llama.cpp 服务端参数（docker-compose `command`）

### `-m <path>`　模型文件

加载的 GGUF 模型文件路径。

| 当前值 | 推荐值 |
|---|---|
| `qwen2.5-7b-ins-v3-Q4_K_M.gguf` | `Qwen3-4B-Instruct-2507-Q4_K_M.gguf` |

推荐换成 Qwen3-4B-Instruct-2507，评分准确率 92% vs 当前 58%，且参数量更小（4B vs 7B），显存占用更低、速度更快。

---

### `--temp`　温度（输出随机性）

控制每个 token 的概率分布"扁平化"程度：

```
temp → 0   完全确定，每次输出完全一样（greedy）
temp = 0.1 极低随机性，结果高度稳定可复现
temp = 0.7 中等随机性，适合对话/创意场景
temp = 1.0 高随机性，多样性最大
```

| 当前值 | 推荐值 | 原因 |
|---|---|---|
| `0.7` | **`0.1`** | 评分任务需要稳定复现；0.7 会导致同一答案不同次评分偏差 ±5 分；测试中 92% 准确率是在 0.1 下测出的 |

---

### `--n-predict`　单次最大输出 token 数

模型这次回复最多生成多少个 token，超出后强制截断。

**Qwen3-4B-Instruct 有思维链（Chain of Thought）**，回复格式是：

```
<think>
  ...推理过程，通常 1000–2000 tokens...
</think>
{"overall_score": 95, "dimensions": {...}}
```

思维链必须跑完才能输出 JSON。若截断发生在思维链中：

```
n-predict = 512 (默认)  → 思维链被截断 → 直接输出 → 准确率 ~75%
n-predict = 3000        → 思维链完整 → 正常 JSON → 准确率 92%
```

| 当前值 | 推荐值 | 原因 |
|---|---|---|
| 未设置（服务端默认 -1，但 API 层 QWEN_MAX_TOKENS=512 会覆盖） | **`3000`** | 给思维链足够空间；完整 JSON 输出约 800–1200 tokens，加思维链共 2000–3000 tokens |

> 注意：服务端 `--n-predict` 是上限，实际截止取 `min(--n-predict, API请求的max_tokens)`。两处都要改。

---

### `--parallel`　并发槽位数

服务端同时处理的请求数。每个槽位独立维护一份 KV Cache（显存占用 ∝ 槽位数 × 上下文长度）。

```
--parallel 1   串行，显存最省，但并发请求需排队
--parallel 4   4个请求并行处理
--parallel 8   8个并行，显存占用约 2×
```

| 当前值 | 推荐值 | 原因 |
|---|---|---|
| `4` | **`4`** | RTX 4070 SUPER 12GB，Qwen3-4B + ctx=8192 × 4 槽约占 10GB，刚好合适；换 Qwen3-4B 后显存反而更宽裕（4B < 7B） |

**必须与 `.env` 的 `QWEN_MAX_PARALLEL` 保持一致**，否则 Go 后端并发限制与实际槽位数不匹配。

---

### `--gpu-layers`　GPU 卸载层数

将模型的多少层加载到 GPU 显存。

```
--gpu-layers 0     纯 CPU 推理（极慢，RTX 4070 SUPER 约 60s/次）
--gpu-layers 999   全部层加载到 GPU（超过实际层数时自动取全部，约 7s/次）
```

| 当前值 | 推荐值 | 原因 |
|---|---|---|
| `999` | **`999`** | 保持全 GPU 推理；Qwen3-4B 约 35 层，全部放入显存速度最快 |

---

### `--flash-attn auto`　Flash Attention

优化注意力计算的内存访问模式：

- 显存减少约 30–50%（长上下文时效果更明显）
- 速度提升约 10–20%
- `auto`：自动检测硬件是否支持，支持则开启

| 当前值 | 推荐值 |
|---|---|
| `auto` | **`auto`**（保持） |

---

### `--cache-type-k q8_0` / `--cache-type-v q8_0`　KV Cache 量化

Key/Value Cache 的存储精度：

```
f16    全精度，显存占用最大
q8_0   8-bit 量化，显存减少约 50%，精度损失极小（< 0.1% 差异）
q4_0   4-bit 量化，显存减少约 75%，精度损失稍大
```

| 当前值 | 推荐值 |
|---|---|
| `q8_0` / `q8_0` | **`q8_0`**（保持）|

评分任务对 KV Cache 精度不敏感，q8_0 是显存效率和精度的最优平衡点。

---

### `--batch-size` / `--ubatch-size`　批处理大小

- `--batch-size 512`：prompt 处理阶段（prefill）的最大批次 token 数，影响 **首 token 延迟**
- `--ubatch-size 128`：微批次大小，影响 GPU 利用率和显存峰值

这两个参数对本项目影响较小（单次评分的 prompt 约 300–500 tokens，一次 prefill 即可完成）。

| 当前值 | 推荐值 |
|---|---|
| `512` / `128` | **保持**，无需调整 |

---

### `-c`　上下文窗口大小（Context Size）

模型一次能看到的最大 token 数（prompt + 输出之和）。

```
-c 4096   最多处理 4096 tokens（含输入和输出）
-c 8192   翻倍，显存占用约 +15%
-c 16384  当前值，显存占用较大，对本项目浪费
```

评分任务的典型 prompt 约 500 tokens，输出 3000 tokens，合计 3500 tokens。

| 当前值 | 推荐值 | 原因 |
|---|---|---|
| `16384` | **`8192`** | 评分任务不需要超长上下文；缩小到 8192 可释放约 1–2GB 显存，给 KV Cache 和并发槽位留余量 |

## 二、API 层参数（`backend/.env`）

这些参数在 Go 后端发起请求时传给 llama.cpp，会覆盖服务端默认值。

### `QWEN_MAX_TOKENS`

对应请求体的 `n_predict`，限制**单次请求**的最大输出 token 数。

| 当前值 | 推荐值 | 原因 |
|---|---|---|
| `512` | **`3000`** | 与服务端 `--n-predict 3000` 一致；512 会截断 Qwen3-4B-Instruct 的思维链 |

### `QWEN_TEMPERATURE`

对应请求体的 `temperature`，覆盖服务端 `--temp`。

| 当前值 | 推荐值 | 原因 |
|---|---|---|
| `0.7` | **`0.1`** | 评分稳定性；与测试环境一致 |

### `QWEN_MAX_PARALLEL`

Go 后端的并发限制，控制同时发出多少个 llama.cpp 请求。

| 当前值 | 推荐值 | 原因 |
|---|---|---|
| `4` | **`4`** | 与服务端 `--parallel 4` 一致；超出槽位数会导致请求排队 |

## 三、推荐配置汇总

### `docker-compose.yml` command（切换到 Qwen3-4B-Instruct-2507 后）

```yaml
command: [
  "-m", "/models/Qwen3-4B-Instruct-2507-Q4_K_M.gguf",
  "--port", "8080",
  "--host", "0.0.0.0",
  "--gpu-layers", "999",
  "--parallel", "4",
  "--flash-attn", "auto",
  "--cache-type-k", "q8_0",
  "--cache-type-v", "q8_0",
  "--batch-size", "512",
  "--ubatch-size", "128",
  "-c", "8192",
  "--temp", "0.1",
  "--n-predict", "3000"
]
```

### `backend/.env`（切换到 qwen_local 后）

```env
AI_PROVIDER=qwen_local
QWEN_LOCAL_URL=http://localhost:8083/completion
QWEN_TEMPERATURE=0.1
QWEN_MAX_TOKENS=3000
QWEN_MAX_PARALLEL=4
```
