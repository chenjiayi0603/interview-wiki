# 项目深挖 · KeyDB 存算分离

> 适用面试：华为云 / 腾讯云 / 基础架构 / 存储方向

---

## 一、一句话介绍

**KeyDB** 是华为云的 Redis 兼容存储服务。我负责存算分离架构的存储引擎改造：基于 **RocksDB** 扩展自定义文件系统（Env 插件），数据从本地 SSD 迁移到远程 **OBS** 对象存储。

---

## 二、关键性能数据（必须背熟）

### 多级存储性能对比

| 维度 | 纯内存 (KeyDB) | 内存+SSD (KeyDB存算一体) | **内存+OBS (KeyDB存算分离)** |
|------|:---:|:---:|:---:|
| **持久化方式** | 无（纯内存，掉电丢） | AOF/RDB（写本地SSD） | **RocksDB LSM-Tree → SST → OBS（无 AOF/RDB）** |
| **底层引擎** | 纯内存 | 纯内存 + AOF/RDB | **RocksDB + 自定义 Env 插件** |
| **写路径** | 写内存 | 写内存 → 异步刷 AOF/RDB 到 SSD | **写 WAL(本地) → MemTable → SST → Env → OBS** |
| **读延迟 P99** | 0.1-0.5ms | 0.1-0.5ms | **热 1.2ms / 冷 8ms** |
| **写延迟 P99** | 0.1-0.3ms | 0.5-2ms（AOF 刷盘开销） | **2ms** |
| **混合读写 QPS** | 15-20万 | 12-15万 | **10万+** |
| **每 GB 成本** | 高（DRAM ≈ ¥30/GB） | 中（SSD ≈ ¥2/GB） | **低（OBS ≈ ¥0.12/GB/月）** |
| **数据容量** | 受单机内存限制 | 受本地 SSD 限制 | **近乎无限（OBS 对象存储）** |
| **弹性扩缩** | 需迁移数据，慢 | 需迁移数据，慢 | **加/减计算节点即可，快** |
| **适用场景** | 热缓存，可丢数据 | 中小容量，需要持久化 | **温冷大容量，成本敏感** |
| **性能消耗（相对于纯内存）** | — | 写 +0.4~1.7ms，QPS -20% | **读热 +0.7~1.1ms，读冷 +7.5~7.9ms，写 +1.7~1.9ms，QPS -30~50%** |
| **换来什么** | — | 数据不丢（AOF/RDB 持久化） | **成本降 30%、容量近乎无限、扩缩容秒级** |

**KeyDB 存算一体 vs 存算分离** — 本质区别不在存储介质，而在**引擎层**：
- 存算一体 = **纯内存 + AOF/RDB**，和 Redis 一样
- 存算分离 = **RocksDB + 自定义 Env 插件 + OBS**，AOF/RDB 砍掉，写路径走 LSM-Tree

### KeyDB 实测数据

| 场景 | QPS | P99 延迟 | 说明 |
|------|-----|--------|------|
| 纯读（热数据） | **15万** | 1.2ms | 命中 Block Cache，内存访问 |
| 纯读（冷数据） | **5万** | 8ms | OBS 网络拉取，RTT 约 2ms |
| 纯写（SET） | **8万** | 2ms | 异步批量提交，攒 100 条 |
| 混合读写 (8:2) | **10万+** | 5ms | 生产环境典型 |

**延迟分布**: P50 0.8ms / P90 2ms / P99 5ms / P999 15ms  
**存储成本**: 降 **30%**（纯 SSD vs 存算分离）  
**可用性**: 99.99%（年停机 < 53 分钟）

## 三、架构

```
KeyDB → RocksDB → 自定义 Env 插件 → [Etcd + OBS 对象存储]
```

| 分层 | 组件 | 延迟 |
|------|------|------|
| 热数据 | 本地 RocksDB（Block Cache + MemTable） | < 1ms |
| 冷数据 | OBS 对象存储 | 5-20ms |
| 元数据 | Etcd（文件位置、分片信息、版本号） | gRPC < 1ms |
| 文件分类 | SSTable (.ldb) → 自定义 Env → OBS | WAL (.log) → 本地 | MANIFEST → Etcd |

## 四、优化历程（STAR 话术）

| 问题 | 现象 | 优化手段 | 效果 |
|------|------|---------|------|
| **冷数据延迟高** | 8ms | 异步预取 + 连接池 | **3ms** |
| **Compaction 抖动** | QPS 掉 50% | 分时段限速 (RateLimiter) | **< 10%** |
| **内存占用** | 16GB | 分层 LRU 缓存淘汰 | **8GB** |
| **gRPC 断连** | 空闲超时 | keepalive 心跳 30s | **自动重连** |
| **写放大** | 10x | 增大 MemTable 256MB→512MB | **5x** |

## 五、关键技术深度

### RocksDB 写入流程

```
用户线程 Put → CAS 竞争 newest_writer_（JoinBatchGroup）
  Leader: 批量合并 Follower → 写 WAL → 写 MemTable
  Follower: 在 AwaitState 阻塞 → Leader 通知唤醒
```

### 存算分离一致性

```
写 OBS 成功 → Etcd 事务更新元数据（版本号自增）
读: 查 Etcd 获最新版本 → 从 OBS 读取 → 本地点校验
缓存: 本地命中需校验 Etcd 版本号
```

### 冷热分层判断

```
时间: 超过 7 天未访问 → 冷
频次: 滑动窗口 < threshold → 冷
大小: > 10KB 优先下沉
```

## 六、核心面试题

| 问题 | 一句话回答 |
|------|-----------|
| "存算分离和存算一体区别？" | 存算一体全内存贵，存算分离冷数据上 OBS 成本降 30% |
| "LSM-Tree vs B+Tree？" | LSM 顺序写适合写密集，B+Tree 读快适合 OLTP |
| "写放大怎么算？" | WAL 1x + Flush 1x + Compaction 10-20x |
| "怎么保证一致性？" | 先写 OBS 成功再更新 Etcd，版本号校验 |
| "Compaction 怎么限速？" | 低峰期 500MB/s，高峰期 100MB/s，降低线程数 |
| "Etcd 还是 ZK？" | Etcd: gRPC+JSON 现代，运维简单，写 10000+/s |

## 七、追问应对

```
Q: "OBS 延迟变大了怎么办？"
A: "多级缓存（本地+远端）、异步预取、连接池预热"

Q: "如果本地磁盘坏了？"
A: "从 OBS 加载 + Etcd 元数据重建"

Q: "Redis 和 KeyDB 怎么选？"
A: "看数据层级：纯内存 Redis 适合热数据（P99<0.5ms），KeyDB 存算分离覆盖温冷数据（P99 1-8ms）。华为云的方案是用 Redis 做热缓存层，KeyDB 做温冷持久化层，一套完整的存算分离方案——既有极速又有容量，成本还降了 30%。类比 AWS 就是 ElastiCache（内存）→ MemoryDB（持久化）→ S3（对象存储）三层。"

Q: "监控什么指标？"
A: "Block Cache命中率 / Write Stall次数 / L0文件数 / P99延迟"
```
