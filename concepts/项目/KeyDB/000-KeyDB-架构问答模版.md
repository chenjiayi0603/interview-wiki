## 一、项目复盘与架构设计

**考察点**：业务理解深度 & 架构设计能力

### 背景：项目定位与目标

我参与的项目是 **华为云 KeyDB 存算分离存储引擎**。KeyDB 是华为云自研的 Redis 兼容服务，定位是 **"大容量、低成本、强一致的 Redis 替代方案"**。

**业务痛点：**
- **成本问题**：原生 Redis 纯内存架构，1TB 数据月费高达 ¥2,000。大客户（如电商、游戏）数据量在 10TB+ 级别，成本难以承受。
- **弹性问题**：Redis Cluster 扩缩容需要迁移数据，一个 64 节点的集群扩缩容耗时 2-4 小时，无法应对秒级流量波峰。
- **容量瓶颈**：单机内存容量受限（最大 512GB），对大容量场景不友好。

**项目目标：**
> 实现存算分离架构——热数据在内存（微秒级），冷数据在 OBS 对象存储（毫秒级），成本降 70%，弹性扩缩容秒级，对上层 Redis 协议完全兼容。

### 难点：技术上的核心挑战

#### 挑战 1：RocksDB 文件系统拦截 —— 对上层无感
存算分离的核心是把数据从本地磁盘搬到远端 OBS。但 KeyDB 底层用的是 RocksDB 存储引擎，RocksDB 所有文件操作都走本地文件系统（`open`/`read`/`write`/`fsync`）。我们要在不改 RocksDB 一行代码的前提下，把文件操作重定向到 OBS。

**方案：** RocksDB 提供了 `Env` 抽象接口，所有文件 I/O 都通过这个接口完成。我们继承 `EnvWrapper` 实现了 `RemoteStorageEnv`，重写了 `NewWritableFile`、`NewRandomAccessFile`、`NewSequentialFile`、`DeleteFile` 等核心方法。按文件类型走不同的存储策略：
- **SSTable（.ldb/.sst）**→ 写入 OBS 对象存储
- **WAL（.log）**→ 本地 + OBS 双写（保证数据不丢）
- **MANIFEST（.manifest）**→ 存入元数据中心（Etcd/MySQL）

对 RocksDB 内部完全透明，相当于在文件系统层面做了一层"存储虚拟化"。

#### 挑战 2：冷数据延迟 —— 从微秒级到毫秒级的跨越
纯内存读延迟 P99 < 0.5ms，OBS 远端读取 P99 达到 8-20ms。如果每次读冷数据都去 OBS 拉，性能完全不可接受。

**方案：三级缓存 + 异步预取**
- **L1：Block Cache（内存）**—— RocksDB 内置的块缓存，命中率 90%+，延迟 < 0.5ms
- **L2：本地 SSD 缓存（文件级）**—— 整个 SSTable 文件缓存到本地磁盘，延迟 ~1ms
- **L3：OBS 远端存储**—— 延迟 8ms，仅穿透到这一层

**预取优化：** 当检测到连续 OBS 读取时，异步提前拉取相邻 Block。我们实现了 ReadAhead 窗口，默认 256KB，如果连续命中 OBS 且偏移量递增，自动扩展到 1MB。

#### 挑战 3：一致性 —— 存算分离下的强一致保证
存算分离后，数据在远端 OBS，元数据在 Etcd，本地只有缓存。节点宕机后重启，怎么保证数据不丢、不重复、一致？

**方案：**
1. **WAL 双写**：每次写操作先写本地 WAL（异步），同时同步写 OBS WAL。同步成功才返回客户端。
2. **Etcd 事务提交**：SSTable 上传 OBS 完成后，通过 Etcd 事务原子更新元数据（版本号自增）。确保"文件已上传"和"元数据已更新"要么同时成功，要么同时失败。
3. **版本号校验**：本地缓存命中时，需通过 Etcd 对比版本号，如果版本过期则重新从 OBS 拉取。
4. **恢复流程**：节点重启时，先扫描本地 WAL 恢复未刷盘的写入，然后从 Etcd 拉取 MANIFEST 重建 SSTable 视图，最后从 OBS 加载必要数据。

### 收益：最终交付的业务/技术价值

| 指标 | 优化前（纯内存） | 优化后（存算分离） | 提升 |
|------|:--------:|:----------:|:----:|
| 存储成本（1TB） | ¥2,000/月 | ~¥300/月 | **降 85%** |
| 热数据读 P99 | < 0.5ms | 1.2ms | 略增，可接受 |
| 冷数据读 P99 | — | 8ms | 新增能力 |
| 混合 QPS | 15 万 | 10 万+ | 略降，但容量无限 |
| 数据容量 | 单机 512GB 上限 | **近乎无限**（OBS） | 质的飞跃 |
| 扩缩容 | 2-4 小时（需迁移数据） | **秒级**（加计算节点） | 质的飞跃 |
| Compaction 抖动 | 50% QPS 下降 | < 10% | 稳定 5x |

### 反思：当前系统设计的缺陷与优化方向

#### 缺陷 1：Etcd 作为元数据中心的容量瓶颈
**问题**：我们最初用 Etcd 存储文件元数据。当集群文件数量超过 100 万时，Etcd 的 key 数量导致性能明显下降——Raft 提案速率受限（单集群约 1000-2000 ops/s），watch 事件堆积。

**优化方向**：架构上应该将元数据拆成两层——**Etcd 做协调层**（锁、选主、配置下发），**MySQL 集群或 TiDB 做数据层**（文件元数据、MANIFEST 版本管理）。MySQL 支持复杂查询、二级索引、水平扩展，更适合海量文件元数据的场景。

#### 缺陷 2：冷数据回热的粒度太粗
**问题**：当前冷数据回热以整个 SSTable 文件为粒度。如果一个 64MB 的 SSTable 中只有一个 Key 被访问，也要下载整个文件。

**优化方向**：改为 Block 粒度的按需加载。RocksDB 的 SSTable 本身按 Block（默认 4KB-16KB）组织，我们可以只拉取需要的 Block。代价是实现更复杂，需要维护 Block 级别的缓存索引。

#### 缺陷 3：Compaction 的写放大仍有优化空间
**问题**：当前写放大 ~12x（优化前 32x），相比纯内存方案仍有较大差距。在写密集场景下，写放大会导致磁盘寿命缩短、CPU 消耗增加。

**优化方向**：
- **BlobDB**：对大 Value（>1KB）启用 BlobDB 分离存储，避免大 Value 在 Compaction 中被反复搬运
- **Tiered Storage**：冷数据 SSTable 不参与 Compaction，直接下沉到 OBS 只读
- **更激进的 MemTable 配置**：write_buffer_size 从 256MB 提升到 512MB，减少 Flush 频率

#### 缺陷 4：缺乏自适应冷热分层
**问题**：当前冷热判断策略是静态规则（7 天未访问 + 频次滑动窗口），在流量模式突变的场景下（如秒杀、热点事件）响应滞后。

**优化方向**：引入**基于机器学习的冷热预测**。采集访问模式特征（时间序列、频次变化率、Key 前缀分布），用轻量级模型（如 LR、XGBoost）预测哪些 Key 即将被访问，提前预取。

#### 二、热读延迟退化详解（纲表第 1 行）

> OBS 热读 P99 2ms，比纯内存的 0.3ms 多 1.7ms。这 1.7ms 是怎么一步步加上去的？

**退化步骤拆解：**

```
纯内存基线                                      0.27ms
  └─ 命令解析(0.05) + 1次哈希查找(0.02) + 返回(0.2) = 0.27ms
     1次逻辑读 = 1次哈希表查找，O(1)，路径最短

① + RocksDB 读放大                              0.02ms → 0.29ms
  └─ 纯内存 1次哈希命中，RocksDB 要查 MemTable → Immutable → L0 → L1 → ...
     Bloom Filter 拦截 99% 无效层 → 通常只穿透 2-3 层
     每层 +0.005ms（Bloom判定 + Index二分）
     全 Cache 命中时 0.018ms → 实际增加 0.02ms
     对应架构代价：LSM-Tree 多层结构本身的查询开销

② + Etcd 版本校验（gRPC 调用）                    0.8ms → 1.1ms
  └─ 确认本地 Cache 的 SSTable 没被远端 Compaction 淘汰
     本地元数据缓存命中率 99%+ → 0.01ms（几乎无感）
     1% 穿透 → gRPC 0.8ms → 1.1ms
     对应架构代价：存算分离的一致性保证

③ + 并发调度 & P99 抖动                          0.9ms → 2ms
  └─ gRPC 连接复用等待、线程调度
     P50 ≈ 0.3ms，P99 受尾延迟影响 ≈ 2ms

= OBS 热读 P99 ≈ 2ms ✓
```

> **面试一句话**："热读多出来的 1.7ms，RocksDB 读放大只贡献 0.02ms（1%），Etcd 版本校验贡献 0.8ms（47%），P99 抖动贡献 0.9ms（52%）。核心代价是**一致性校验**——为了让 Cache 不读到 stale 数据，多跑了一趟 gRPC。"

#### 三、冷读延迟退化详解（纲表第 2 行）

> 纯内存没有"冷数据"概念。OBS 模式下新增冷读路径，P99 8-20ms。核心原因是 **OBS 读放大：1 次逻辑读 = 2 次 HTTP GET**。

**OBS 冷读完整路径：**

```
Cache Miss 判定                              0.05ms
  ├── 热读命中率 92%，8% 请求进入此路径
  │
② 元数据查询——定位 SSTable 在 OBS 的 key + 偏移   0.01ms（缓存命中）/ 0.5ms（穿透 Etcd）
  ├── 这一步是本地 SSD 没有的——SSD 寻址由文件系统完成
  │
③ OBS 读放大 第1次：Index Block GET             2.1ms（RTT 2ms + 传输 0.1ms）
  └─ 必须先拉 Index Block 才知道 Key 在 Data Block 的哪个偏移
     └─ OBS 是对象存储，没有 seek() 语义，定位 → 必须拉 Index
  │
④ Bloom Filter 判定（Index Block 内含）          0.0001ms
  │
⑤ OBS 读放大 第2次：Data Block GET              2.2ms（RTT 2ms + 传输 0.2ms）
  └─ 如果 Key 跨多个 Block → N × 2.2ms（大 Value/范围扫描）
     并行 GET：max(2.2ms) ≈ 3ms（含 HTTP 开销）
  │
⑥ Block 内查找 + CRC 校验                       0.015ms
  │
⑦ 连接池排队（P99）                             2-6ms
  └─ 读放大让连接消耗翻倍：每次冷读吃掉 2 个连接 slot
     150个读连接 ÷ 2 = 仅 75 个并发冷读 → 更容易耗尽
  │
= 单 Block：4.8ms（无排队）
  多 Block：7-12ms
  P99：8-20ms（含排队） ✓
```

**OBS 读放大的根因：**

```
为什么 1 次逻辑读 = 2 次 OBS HTTP GET？

  闪存/本地 SSD 的冷读路径：
    read(file_fd, offset, size) → 内核文件系统 → 驱动 → SSD → 返回
    1 次系统调用完成所有工作（文件系统知道 Index Block 在哪、Data Block 在哪）

  OBS 的冷读路径：
    没有文件系统！OBS 只认识 object key + byte range
    Step 1: GET /bucket/000123.sst?Range=0-4096     → 拉 Index Block
    Step 2: 解析 Index → 找到 Data Block 偏移
    Step 3: GET /bucket/000123.sst?Range=4096-20480 → 拉 Data Block
    2 次 HTTP RTT，每次 2ms，共 4ms → 这是本地 SSD 读放大 2x 的根因
```

> **面试一句话**："OBS 冷读的核心瓶颈不是传输（4KB+16KB 只传 0.3ms），而是 **OBS 读放大**——对象存储没有文件系统的 seek 能力，1 次逻辑读被迫拆成 2 次 HTTP GET，多跑一趟 RTT。"

#### 四、写延迟退化详解（纲表第 3 行）

> OBS 写 P99 3-8ms，比纯内存的 < 1ms 退化 3-8x。根因有三：WAL 串行写、组提交攒批、网络 RTT。

**退化步骤拆解：**

```
纯内存基线                                     < 1ms（P99）
  └─ 命令解析(0.005) + 哈希插入(0.008) + 返回(0.005) ≈ 0.02ms
     无 WAL、无 IO、无写放大

① + WAL 串行等待（前一个 batch 正在 OBS PUT）      1ms → 2ms（P50）
  └─ 纯内存无 WAL。OBS 的 WAL 每个分片只有 1 条流，串行顺序写
     前一个 batch 在上传 OBS（4ms）→ 你等半个周期 ≈ 2ms
     对应架构代价：WAL 必须顺序写保证崩溃恢复

② + 组提交攒批等待                                2ms → 4ms（P50）
  └─ 触发条件：Buffer 满 1MB 或 超时 10ms
     请求正好落在周期开头 → 等近 10ms
     平均等待 5ms → P50 约 2-3ms
     对应架构代价：吞吐换延迟（攒 40 条共享一次 OBS PUT）

③ + OBS 网络 RTT                                2ms → 6ms（P50）
  └─ OBS PUT 网络往返 2ms，物理极限无法消除
     对应架构代价：数据跨越网络到远端的物理延迟

④ − 组提交摊销（40 条共享一次 PUT）                -3ms → 3ms（P50）
  └─ 单条摊销 = (5ms等待 + 2ms RTT + 1ms处理) / 40 ≈ 0.2ms
     P50 ≈ 1-2ms（用户感受到的值）

⑤ + Write Stall 对 P99 的影响                     3ms → 3-8ms（P99）
  └─ 写放大 12x → MemTable 更快写满 → Flush 到 OBS(5s)
     5s 内所有写排队 → P99 飙到 5000ms（极少发生，< 0.5%）
     但把 P99 从 2ms 拉到 3-8ms
     对应架构代价：写放大 12x 的 Compaction 副作用
```

> **面试一句话**："OBS 写延迟 P50 约 2ms（组提交摊销后），P99 3-8ms（尾延迟受攒批等待 + Write Stall 影响）。核心代价是 **WAL 必须同步落远端 OBS**——闪存的 WAL 落本地 NVMe 只要 0.8ms，我们多跑了 2ms 网络 RTT。"

#### 五、读 QPS 退化详解（纲表第 4 行，含读放大系数）

> OBS 读 QPS 从纯内存的 18 万降到 10 万（-44%）。每一步减法都是可追溯的。

**退化推导链：**

```
纯内存基线                                                  18 万
  └─ 单核 6.7 万 × 8 核 × 利用率 85% = 18 万
     1次逻辑读 = 1次哈希 O(1)，读放大系数 = 1x

① − RocksDB 读放大（LSM-Tree 多层查询）                     −2 万 → 16 万
  └─ 纯内存 1次哈希查找
     RocksDB 要查多层 SSTable：MemTable → Imm → L0 → L1 → ...
     Bloom Filter 拦截 99% 无效层 → 通常穿透 2-3 层
     每层 +0.005ms → 全 Cache 命中时单请求 0.015→0.021ms(+40%)
     读放大系数 ≈ 1.4x（RocksDB 读放大）
     对应架构代价：LSM-Tree 换来的写入性能提升（代价是读路径变长）

② − Etcd 版本校验（一致性代价）                              −2 万 → 14 万
  └─ 92%热读命中后必须 gRPC 查 Etcd确认版本
     本地缓存命中 99%+ → 几乎无感（+0.01ms）
     1% 穿透 gRPC → +0.8ms → 加权单请求 0.029ms
     → QPS = 1/0.029 × 8 × 0.85 ≈ 14 万
     对应架构代价：存算分离的一致性保证

③ − OBS 读放大（1次逻辑读 = 2次 HTTP GET）                   −2 万 → 12 万
  └─ 冷读 8% 穿透到 OBS：每次需要 2 次 HTTP GET（Index + Data）
     150 个读连接 ÷ 2 = 有效并发仅 75 个 slot
     75 × 600 QPS/slot ≈ 4.5 万（冷读路径）
     加上 92% 热读不耗连接 → 整体 ~12 万
     OBS 读放大系数 = 2x（每次冷读 2 次 HTTP GET）
     对应架构代价：OBS 无文件系统 seek 能力

④ − 连接池排队（突发流量余量）                               −2 万 → 10 万
  └─ 150 连接 × 600 QPS/连接 = 9 万理论值
     热读命中不耗连接 → +1 万余量 → 保守 8-10 万
     对应架构代价：OBS 连接配额限制（云资源管控）

= OBS 读 QPS ≈ 10 万 ✓
─────────────────────────────────────────────
退化分配：RocksDB读放大(11%) + Etcd(11%) + OBS读放大(11%) + 排队(11%) = 44%
```

**读放大系数对比：**

| | 纯内存 | 闪存 | OBS |
|:--|:----:|:---:|:---:|
| 逻辑读 → 物理读（RocksDB 层） | 1x | ~1.4x | ~1.4x |
| 物理读 → HTTP 调用（OBS 层） | — | — | **2x** |
| **总读放大** | **1x** | **~1.4x** | **~2.8x** |

> **面试一句话**："OBS 读 QPS 降 44% = LSM-Tree 读放大吃 11% + 一致性校验吃 11% + OBS HTTP 读放大吃 11% + 连接池吃 11%。"
> "最大可优化点是OBS读放大——如果能一次 HTTP 拉 Index+Data，读 QPS 可以回到 12 万。"

#### 六、写 QPS 退化详解（纲表第 5 行，含写放大 + WAL 串行推导）

> OBS 写 QPS 从纯内存的 12 万降到 5-7 万（-50%）。最大杀手是 **WAL 串行天花板**。

**退化推导链：**

```
纯内存基线                                                  12 万
  └─ 单核 5 万 × 8 核 × 利用率 85% = 12 万
     无 WAL、无 IO、无写放大

① − 写放大（Compaction 抢 CPU）                             −2 万 → 10 万
  └─ 写放大 12x：1MB 逻辑写 → 12MB 物理磁盘 IO
     Compaction 线程吃 1-2 核 CPU
     → 业务写可用 CPU 从 8 核降到 ~7 核 → QPS 降 15-25%
     对应架构代价：LSM-Tree Compaction 的必要代价

② − WAL 串行天花板（OBS 写 QPS 硬上限）                      −3 万 → 7 万
  └─ 纯内存无 WAL。OBS 每条写必须走 WAL → OBS PUT
     WAL 每个分片只有 1 条流，顺序写，不可并行
     ┌─────────────────────────────────────────────┐
     │ 写 QPS 上限 = 分片数 × (1000ms / 周期) × 每周期写入数 │
     │           = 8 × (1000 / 5) × 40              │
     │           = 8 × 200 × 40 = 6.4 万            │
     │                                             │
     │ 为什么是 5ms？→ 平均攒批 2.5ms + OBS RTT 2ms  │
     │ 为什么是 40条？→ 5ms × 8分片 × 1000QPS/分片   │
     └─────────────────────────────────────────────┘
     对应架构代价：WAL 必须串行保证崩溃恢复 + OBS PUT 物理延迟

③ − OBS 写放大（SSTable 上传抢带宽）                        −1 万 → 6 万
  └─ 写放大 12x：1MB 写入 → 12MB SSTable 上传
     单节点 OBS 上行 ~100MB/s，SSTable 上传占满带宽
     → WAL 上传排队 → WAL 周期拉长(5ms→8ms) → 有效 QPS 再降
     对应架构代价：存算分离下 SSTable 上传挤占 WAL 带宽

④ − Write Stall 余量                                        −1 万 → 5-7 万
  └─ MemTable 写满等 Flush(5s) → 瞬时写 QPS 归零
     生产占比 < 0.5%，年报扣 10-15% 余量
     对应架构代价：Flush SSTable 到 OBS 的 5s 阻塞窗口

= OBS 写 QPS ≈ 5-7 万 ✓
─────────────────────────────────────────────
退化分配：写放大(17%) + WAL串行(25%) + OBS写放大(8%) + Stall(8%) = 58%
最大杀手：WAL 串行天花板 → 物理定律，除非增加分片否则无法绕过
```

**写放大系数对比：**

| | 纯内存 | 闪存 | OBS |
|:--|:----:|:---:|:---:|
| RocksDB 本地写放大 | 1x | 12x | 12x |
| OBS 上传放大（SSTable 挤占 WAL 带宽） | — | — | 额外 -15% 有效写 QPS |
| Write Stall 占比 | 0% | 5-15% | < 0.5% ← 存算分离红利 |
| **总写放大对 QPS 影响** | **0%** | **~20%** | **~25%**（去 WAL 串行后看） |

> **面试一句话**："OBS 写 QPS 最大杀手不是写放大，是 **WAL 串行天花板**——8分片 × 200次/s × 40条 = 6.4 万，这个物理上限除非加更多 WAL 分片否则无法打破。写放大 12x 吃掉 17% 的 QPS 反而排第二。"

#### 七、成本退化详解（纲表第 6 行）

> 1TB 数据，OBS 存算分离只要 ¥289/月，比纯内存 ¥2,000/月降 85%。

#### 八、弹性退化/收益（纲表第 7 行）

> 这是唯一一行 OBS 不是"退化"而是"收益"的指标。

```
为什么纯内存扩缩容要 2-4 小时？

  扩容流程：新节点加入 → 槽位迁移 → 数据全量拷贝
  64节点集群，每节点 16GB → 总数据 1TB
  迁移 100 个槽位（约 16GB）→ 网络传输 + 目标节点加载到内存
  16GB / 1Gbps 网络 = 128 秒（纯传输）+ 加载索引 = 2-4 小时
  而且迁移期间 QPS 抖动（CPU 被数据拷贝占用）

为什么 OBS 扩缩容是秒级？

  计算节点完全没有本地数据（Block Cache 不算，丢了也能从 OBS 拉）
  新节点启动 → 注册到 Etcd → 接管分片 → 即可服务
  不需要等数据迁移 → 启动即 ready
  代价：冷读 8ms（首次访问需从 OBS 拉数据）
  这就是"无本地 SSD 缓存"的架构意义——换取真正的弹性
```

> **面试一句话**："OBS 扩缩容秒级的代价是冷读 8ms。'去本地 SSD'不是技术做不到，而是**架构取舍**——宁可有 8ms 冷读，也要守住计算节点完全无状态的底线。"

#### 十一、面试追问——10 个必背推导

| 追问 | 一句话回答（含推导） |
|:----|:-------------------|
| "OBS 为什么 QPS 低一半？" | **写路径 0.3ms→5ms(+16x)，读路径 0.3ms→2.6ms(+9x)，瓶颈从 CPU 转到 OBS 连接数 + WAL 串行天花板**。 |
| "OBS 热读为什么也要 2ms？" | **RocksDB 读放大(0.02) + Etcd 版本校验(0.8) + P99抖动(0.9)。Etcd 校验是最大头——一致性代价**。 |
| "冷数据 8ms 能接受？" | **92% 请求在 2ms 返回，只有 8% 感受到 8ms。而且靠预取+请求合并已优化到 P99 5ms 以内**。 |
| "85% 成本节省真实吗？" | **纯存储省 85%，加请求费+流量费后实际省 70-80%。关键变量是冷热比——热数据越多越不省**。 |
| "Compaction 抖动真的 < 5%？" | **OBS 侧异步执行，但 Write Stall（MemTable Flush）仍在本地发生，占比 < 0.5%。比闪存的 5-15% 轻 10-30x**。 |
| "为什么去本地 SSD？" | **计算无状态 = 秒级扩缩容的代价。有 SSD → 扩容要预热 30 分钟，无 SSD → 即开即用，冷读代价 8ms**。 |
| "10Gbps 带宽够吗？" | **10 万 QPS × 1KB = 1Gbps，利用率 10%。SSTable 上传期短时占满 → 瓶颈在突发带宽而非均值**。 |
| "纯内存 vs 闪存，20% QPS 差距在哪？" | **WAL fsync(+1ms) + Compaction 抢 CPU(20%) + 读放大(1.4x)**。 |
| "闪存 30% 抖动怎么降到 15%？" | **限速(高峰100MB/s) + 增大 MemTable(256→512MB) + Leveled Compaction(写放大 32x→12x)**。 |
| "OBS 写延迟能优化吗？" | **WAL Buffer 1→4MB（攒更多条一次 PUT），P99 从 3-8ms 降到 2-4ms。代价：低流量时等更久**。 |
| "WAL 串行天花板能突破吗？" | **增加分片数(8→16)，写 QPS 从 6.4万 → 12.8万。代价：OBS 连接池翻倍 + Etcd 元数据翻倍**。 |

## 三、平滑迁移（存算分离热升级）

**考察点**：不停机迁移 & 灰度切流能力

> **面试主动引导**："KeyDB 从纯内存迁移到存算分离架构，本质上是一个在线存储引擎热升级问题。核心挑战是：存量数据怎么搬？增量数据怎么同步？切换时怎么保证业务无感且可回滚？"

### 场景说明

KeyDB 服务从纯内存架构迁移到存算分离架构，是一个典型的"在线存储引擎热升级"场景。涉及：
1. 老旧节点（纯内存 KeyDB）→ 新节点（RocksDB + OBS）
2. 数据全量迁移 + 增量同步
3. 不停服平滑切换

### 拆分思路：按数据分层拆分

> 面试话术："存算分离本质上就是一种'垂直拆分'——把存储从计算中拆出来独立演进。"

**拆分维度：**

| 维度 | 拆分前（单体） | 拆分后（存算分离） |
|------|:------------:|:--------------:|
| **计算层** | 无状态 + 有状态混部 | 纯无状态计算节点（KeyDB 进程） |
| **热数据层** | 全量在内存 | 本地 RocksDB + Block Cache |
| **冷数据层** | 无 | OBS 对象存储 |
| **元数据层** | 无（依赖 Redis Cluster） | 独立元数据中心（Etcd + MySQL） |
| **管控层** | 无原生管控 | 独立的管控面（调度、监控、迁移） |

**拆分后各组件职责：**

```
┌─────────────────────────────────────────────────────┐
│                    控制面（管控层）                    │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌────────┐ │
│  │ 弹性伸缩  │ │ 配置管理  │ │ 监控告警  │ │ 迁移调度│ │
│  └──────────┘ └──────────┘ └──────────┘ └────────┘ │
└─────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────┐
│                    数据面（计算层）                    │
│  ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐    │
│  │ KeyDB │ │ KeyDB │ │ KeyDB │ │ KeyDB │ │ KeyDB │  ← 无状态，水平扩展
│  │节点1  │ │节点2  │ │节点3  │ │节点4  │ │节点N  │
│  └──┬───┘ └──┬───┘ └──┬───┘ └──┬───┘ └──┬───┘    │
```

### 集群扩容策略

#### 弹性伸缩设计

| 场景 | 策略 | 具体做法 |
|------|------|---------|
| **流量波峰**（秒杀、大促） | 水平扩容 | 自动检测 CPU > 70% 或 QPS > 阈值 → k8s HPA 触发 → 新节点注册到集群 → 槽位自动均衡 |
| **流量波谷**（凌晨） | 缩容 | 检测利用率 < 20% 持续 30 分钟 → 触发缩容 → 槽位迁出 → 节点下线 |
| **节点故障** | 自动替换 | 心跳超时 10s → Etcd Lease 过期 → 触发重新调度 → 新节点接管分片 |
| **数据倾斜** | 槽位重平衡 | 监控各节点存储量标准差 > 20% → 触发槽位拆分/迁移 |

**容量规划公式：**
```
所需节点数 = max( QPS_target / 单节点QPS,  内存_target / 单节点内存,  连接数_target / 单节点连接数 )
其中单节点 QPS = 10 万（混合读写），单节点内存 = 16GB（含 RocksDB 缓存），单节点连接数 = 10000
```

#### 负载均衡设计
- **Proxy 层**：LVS + Nginx 四层转发，一致性哈希路由
- **客户端侧**：Smart Client 直连模式，本地缓存槽位信息，减少 Proxy 跳数
- **热点 Key 打散**：自动识别热点 Key（访问频次 > 1000/s），加随机后缀打散到多个分片

#### 瓶颈定位方法

| 瓶颈类型 | 定位手段 | 典型指标阈值 |
|---------|---------|------------|
| **CPU 瓶颈** | perf top + /proc/stat | user > 80% |
| **内存瓶颈** | /proc/meminfo + ROCKSDB 内存统计 | Block Cache 命中率 < 85% |
| **磁盘 IO 瓶颈** | iostat + iotop（本地缓存） | await > 10ms，%util > 90% |

**压测过程中我们踩过的坑：**
1. **OBS 连接池耗尽**：默认 10 个连接，并发 50 个读请求时大量超时。修复：连接池扩到 100，加连接预热。
2. **gRPC 空闲断连**：元数据中心 gRPC 连接 60s 无流量自动断开，导致频繁重连。修复：keepalive 心跳 30s。
3. **Buffer Pool 写放大**：SSTable 上传缓冲区 4MB，小文件多时碎片化。修复：动态调整缓冲区大小，按文件大小匹配。

| P99 写延迟 | > 5ms | > 20ms | 限流：拒绝写入请求 |
| CPU 利用率 | > 70% | > 90% | 扩容：新增计算节点 |
| Block Cache 命中率 | < 85% | < 70% | 扩容：增加内存配额 |
| OBS 延迟 P99 | > 20ms | > 50ms | 降级：切到本地降级模式 |
| Compaction 排队 | > 10 pending | > 30 pending | 限速：降低 Compaction 线程数 |

### 集群迁移流程（存量 Redis → KeyDB 存算分离）

这是存量 Redis/KeyDB 纯内存集群迁移到 KeyDB 存算分离架构的核心环节，做到**业务无感、可灰度、可回滚**。

> ⚠️ **关键澄清**：KeyDB 存算分离底层使用 RocksDB 存储引擎，通过 Env 插件将所有文件（SSTable、WAL）直接写入 OBS。**整个链路中没有 RDB/AOF 文件**——RocksDB 的 LSM-Tree 结构天然持久化到 OBS，不需要传统 Redis 的 RDB 快照或 AOF 日志。因此迁移不走"导出 RDB → 导入 RDB"路径，而是利用 **Redis 复制协议（REPLICAOF）** 做增量同步。

#### 整体迁移架构

```
                    ┌──────────────────┐
                    │   客户端 / Proxy   │
                    └────────┬─────────┘
```

#### 阶段 0：新集群部署（OBS 数据面就绪）

新集群的计算节点启动后，直接对接 OBS 作为持久化层：

```
新节点启动流程:
1. 启动 KeyDB 进程（加载 RocksDB + Env 插件）
2. Env 插件初始化 OBS 客户端（连接池 200、内网 Endpoint）
3. RocksDB 通过 Env 插件在 OBS 上创建初始目录结构
   └─ bucket/im-cluster-xxx/
       ├── MANIFEST-000001      ← 元数据文件（同时记录到元数据中心）
       ├── CURRENT              ← 当前 MANIFEST 指针
       ├── OPTIONS-000001       ← RocksDB 配置
       └── WAL/                 ← WAL 日志目录
4. 元数据中心（Etcd）记录集群拓扑，标记节点为 "ready"
5. Readiness Probe 通过 → 接入流量
```

**新集群的存储路径（面试必问）**：

```
写入路径：
  Client → KeyDB → RocksDB WAL → Env → OBS (bucket/im-cluster/WAL/xxx.log)    ← 同步写，确认后返回
                   RocksDB MemTable → Flush → SSTable → Env → OBS (bucket/im-cluster/*.sst)  ← 异步

读取路径：
  Client → KeyDB → Block Cache (DRAM) 命中？→ 返回
                    │ 未命中
                    └─→ Env → OBS 拉取 SSTable → 加载到 Cache → 返回
```

#### 阶段 1：全量数据同步（REPLICAOF 自动完成）

利用 Redis 复制协议，新集群作为 Replica 挂到旧集群 Master 下，**不需要人工导出 RDB 文件**：

```
步骤:
1. 新集群执行命令：REPLICAOF old-cluster-host 6379
2. 旧集群（Master）触发 BGSAVE（在其本地生成 RDB 快照）
   └─ ❗ 注意：这是旧集群的 RDB，不是新集群的。新集群从未使用 RDB 文件。
3. 旧集群通过 TCP 连接将 RDB 传输给新集群（全量同步）
4. 新集群 RocksDB 接收数据，解析后写入 MemTable → Flush 成 SSTable → Env → OBS
5. RDB 传输完成后，新集群开始增量同步（接收旧集群的实时写命令）
6. 判定依据：新集群复制偏移量 = 旧集群复制偏移量（差距 < 100 条命令）
```

**全量同步关键指标**：

| 指标 | 数值 | 说明 |
|------|------|------|
| **全量同步速度** | ~2GB/min（受 OBS 写入带宽限制） | 新集群收到 RDB 数据后，需写入 RocksDB 并上传 OBS |
| **100GB 数据预估时间** | ~50 分钟 | 实际受旧集群 BGSAVE 速度 + 网络带宽 + OBS 上行带宽影响 |
| **全量期间旧集群影响** | 内存 +10-20%（BGSAVE fork 进程） | 需提前预留内存余量 |
| **新集群 OBS 写入量** | ~原始数据 × 写放大（~3-5x） | RocksDB 写入 SSTable 的写放大 |

#### 阶段 2：增量同步 + 灰度切流

```
                    ┌──────────────────┐
                    │   客户端 / Proxy   │
                    └────────┬─────────┘
                             │
                ┌────────────┼────────────┐
                │ 灰度比例    │            │
           ┌────▼──────┐     │     ┌──────▼──────┐
           │ 旧集群     │     │     │  新集群      │
           │ (纯内存)   │     │     │ (RocksDB+OBS)│
           │ Master    │◄────┘     │  Replica     │
           └───────────┘           └──────────────┘
                │                        ▲
                └── REPLICAOF 增量同步 ───┘
                     (实时复制，延迟 < 100ms)
```

灰度切流步骤（通过 Proxy 层控制，按 Key hash 百分比）：

```
阶段 2.1：只读流量灰度（1% → 5% → 20% → 50% → 100%）
  ├── 1%  读流量切到新集群 → 观察 10 分钟
  │   ├── P99 延迟 < 基线 1.5x
  │   ├── 错误率 < 0.1%
  │   ├── Block Cache 命中率 > 80%（新集群刚开始 Cache 是冷的）
  │   └── 复制延迟 < 500ms
  ├── 5%  读流量 → 观察 10 分钟（同上检查项）
  ├── 20% 读流量 → 观察 10 分钟
  ├── 50% 读流量 → 观察 10 分钟
  └── 100% 读流量 → 观察 30 分钟 → 进入阶段 2.2

阶段 2.2：写流量灰度（50% → 100%）
  ├── 条件：读流量 100% 已切完，稳定运行 30 分钟以上
  ├── 50% 写流量切到新集群
  │   ├── 此时新集群同时承担写 + 从旧集群复制
  │   ├── 检查写 P99 延迟（目标 < 5ms，OBS 写确认延迟）
  │   └── 观察 15 分钟
  └── 100% 写流量切到新集群
      └── ⚠️ 旧集群不再接收写入，只作为备份

灰度策略（通过 Proxy 层控制）:
├── 按 Key hash 百分比灰度（确保同一 Key 的读写路由到同一集群）
├── 支持按业务 Key 前缀灰度（特定业务先切）
└── 支持白名单（内测租户先切）
```

**为什么读流量和写流量分开灰度**：

| 原因 | 说明 |
|------|------|
| 读流量灰度验证延迟 | 新集群 Block Cache 需要预热，先切读流量观察 Cache 命中率是否达标 |
| 写流量灰度验证一致性 | 写流量切到新集群后，需确认 OBS 写入延迟、数据一致性 |
| 风险隔离 | 如果读延迟有问题，只影响读，不影响写。缩小爆炸半径 |

#### 阶段 3：数据一致性校验

在灰度全程持续校验，不是一次性动作：

```
实时增量校验（每 10 秒）:
├── 对比旧集群复制偏移量和新集群已应用偏移量
├── 差值 < 100 条命令 → 正常
└── 差值持续增长 → 复制链路存在瓶颈

定时全量校验（每天凌晨低峰期）:
├── 新集群 SCAN 遍历全量 Key → 计算 CRC64 校验和
├── 旧集群 SCAN 遍历全量 Key → 计算 CRC64 校验和
├── 对比 CRC 是否一致
└── 不一致 → 记录差异 Key → 以旧集群为准修复

随机采样校验（灰度期间实时）:
├── 每次灰度步骤切换前，随机采样 10000 个 Key
├── 对比新、旧集群的 Value 是否一致
├── 对比 TTL 是否一致（允许 ±1s 误差）
└── 通过后才允许进入下一灰度步骤
```

#### 阶段 4：旧集群下线

```
条件（全部满足才下线）:
├── 100% 读写流量已切到新集群
├── 稳定运行 72 小时无异常
├── 无 P99 延迟告警
├── 无数据一致性差异
└── 全量校验通过至少 3 次

下线步骤:
1. 旧集群停止接受写入（Proxy 层摘除）
2. 保留旧集群数据 7 天（快照备份至 OBS）
3. 7 天后确认无问题 → 释放旧集群资源
4. 更新 CMDB / 配置中心，标记迁移完成
```

#### 回滚机制

```
触发条件（任一满足立即回滚）:
├── P99 延迟飙升 > 2x（持续 3 分钟）
├── 错误率 > 1%
├── 复制延迟 > 5s（持续 1 分钟）
├── 数据校验不一致 Key > 100
└── OBS 写入延迟 > 10s（持续 30 秒）

各阶段的回滚策略:

│ 阶段          │ 回滚动作                      │ 影响范围   │
│───────────────│───────────────────────────────│───────────│
│ 阶段 1（全量） │ 停止同步，旧集群无影响          │ 无         │
│ 阶段 2.1（读） │ Proxy 切回 100% 旧集群         │ 秒级       │
│ 阶段 2.2（写） │ Proxy 切回 100% 旧集群         │ 毫秒级     │
│               │ + 确认旧集群数据未丢失           │            │
│ 阶段 3（校验） │ 停止校验，保留新集群数据         │ 无         │
│ 阶段 4（下线） │ 旧集群还在，重新接入流量         │ 分钟级     │

回滚后保障:
├── 旧集群数据完整性 100%（从未停止写入，灰度期间双写）
├── 业务无需修改配置
└── 新集群保留现场，用于事后分析
```

## 四、复杂故障与分层止损

**考察点**：复杂故障处理 & 架构根治能力

### 场景适配：KeyDB 存算分离链路中的故障

模板题目是 `Kafka → Flink → Redis → DB`，对应到 KeyDB 的场景，我们可以类比为一条**完整的读写链路**：

```
客户端 → [Proxy/LVS] → KeyDB 计算节点 → [RocksDB / 自定义 Env 插件]
                                          ├── 本地 Block Cache（热）
                                          ├── 本地 SSD（温）
                                          ├── OBS 对象存储（冷）→ 元数据中心 Etcd
                                          └── WAL 双写 → 本地 + OBS
```

这条链路上任意一环出问题，都会导致端到端超时。下面我以 **OBS 存储链路故障导致写入超时** 为场景，展开分层止损和架构根治方案。

---

### 分层止损预案（即时应对）

#### 第 1 层：客户端侧 —— 快速失败 & 优雅降级

```
问题现象：客户端请求 KeyDB，P99 延迟从 2ms 飙升到 20ms+

止损动作:
├── 熔断器（Hystrix 模式）
│   ├── 统计窗口：10s，请求数 > 100
│   ├── 错误阈值：50% 请求超时（> 5s）→ 熔断开启
│   ├── 熔断动作：直接返回 fallback 响应（如缓存的值或空）
│   └── 半开恢复：5s 后放 1 个请求探测，成功则关闭熔断
│
├── 客户端限流（Guava RateLimiter / Sentinel）
│   ├── QPS 阈值 = 正常峰值的 80%
│   ├── 超出直接拒绝（返回 TOO_MANY_REQUESTS）
│   └── 客户端自行重试（指数退避：100ms、500ms、1s、5s）
│
└── 本地缓存兜底
    ├── 热 Key 本地缓存 TTL = 30s（即使 KeyDB 挂掉也能读）
    └── 缓存命中率下降但业务不中断
```

#### 第 2 层：Proxy / 网关层 —— 流量调度 & 超时控制

```
问题现象：多个客户端超时，Proxy 层连接数暴涨

止损动作:
├── 连接池限流
│   ├── 后端 KeyDB 连接数上限 = 10000
│   ├── 超出排队（队列深度 1000，超出拒绝）
│   └── 快速失败（Fail Fast）：队列满直接返回 503
│
├── 超时分层控制
│   ├── 客户端→Proxy：连接超时 500ms，读超时 3s
│   ├── Proxy→KeyDB：连接超时 200ms，读超时 2s
│   └── 超时链路断开，释放资源
│
├── 熔断隔离
│   ├── 按分片维度熔断：某个分片 P99 > 10s → 仅熔断该分片
│   ├── 按业务维度熔断：高优业务（支付）限流宽松，低优（日志）强硬拒绝
│   └── 防止级联雪崩：熔断后快速清空等待队列
│
└── 降级策略
    ├── 写入降级：写失败 → 异步写入 Kafka（补偿队列），高峰期过后回放
    ├── 读降级：冷数据降级 → 只返回热数据，冷数据返回 stale cache
    └── 功能降级：关闭大 Key 分析、热 Key 统计等高 CPU 功能
```

#### 第 3 层：KeyDB 计算节点 —— 资源隔离 & 分级处理

```
问题现象：OBS 延迟 8ms → 500ms+，大量请求在等 OBS 返回

止损动作:
├── OBS 客户端限流
│   ├── 最大并发 OBS 请求 = 200（超过排队）
│   ├── 队列满 → 直接返回 ERR_OBS_BUSY
│   └── 连接池隔离：读写分离连接池，读 OBS 不影响写 WAL
│
├── Write Stall 保护（RocksDB 内置）
│   ├── L0 文件数 > 20 → 减慢写入（level0_slowdown_writes_trigger）
│   ├── L0 文件数 > 36 → 停止写入（level0_stop_writes_trigger）
│   └── MemTable 数量 > 4 → 阻挡写入，等待 Flush
│
├── 请求分级（优先级队列）
│   ├── P0（支付、交易）：严格保障，限流阈值最高
│   ├── P1（用户查询）：普通限流
│   └── P2（后台分析）：限流阈值最低，可全部降级
│
└── 快速失败（Fail Fast）
    ├── OBS 请求等待 > 5s → 取消请求，返回错误
    ├── 释放 goroutine/thread 资源
    └── 不阻塞后续请求
```

#### 第 4 层：OBS / 元数据中心 —— 故障隔离 & 容错

```
问题现象：OBS 服务降级 / 网络分区 / 元数据 Etcd 抖动

止损动作:
├── OBS 多 AZ 部署
│   ├── 主 AZ OBS 故障 → 自动切到备 AZ（延迟增加 1-2ms）
│   ├── 跨 AZ 重试：默认 3 次重试，每次间隔 500ms
│   └── OBS SDK 内置退避策略
│
├── 元数据中心容错
│   ├── Etcd 多数派存活即可服务（3 节点容忍 1 节点宕机）
│   ├── 元数据查询超时 → 使用本地缓存的元数据（stale read 允许）
│   └── 元数据写入失败 → 写入本地 WAL 标记，待恢复后重试
│
├── 降级到本地模式（终极兜底）
│   ├── 当 OBS 延迟 > 10s 持续 30s → 自动进入"本地降级模式"
│   ├── 降级期间写入只写本地 WAL + 本地 SSTable
│   ├── 降级期间读取只读本地缓存（冷数据不可用）
│   └── OBS 恢复后 → 异步回刷 OBS + 合并 WAL
│
└── 雪崩防护
    ├── 新请求速率限制（Connection Limiter）
    ├── 拒绝非核心请求（业务降级）
    └── 健康检查：/healthz 端点不查 OBS，只查本地进程状态
```

### 事后的架构根治方案（长期修复）

#### 根因定位方法论

```
定位链路超时根因的步骤：

Step 1：现场保留（第一时间）
├── dump 所有 goroutine/thread 堆栈（pprof）
├── 记录最近 1 分钟的全量请求日志（请求 ID、耗时、路径）
├── 导出 RocksDB 内部统计（STATISTICS / perf_context / iostats_context）
└── 保持 OBS 客户端连接池现场（不重启）

Step 2：分层排查
├── 客户端侧：是否超时配置不合理？重试策略导致请求放量？
├── 网络侧：是否带宽打满？TCP 重传率 > 1%？
├── KeyDB 侧：RocksDB Write Stall？Block Cache Miss 飙升？GC 抖动？
├── OBS 侧：OBS 服务端延迟？DNS 解析变慢？连接池耗尽？
└── 元数据侧：Etcd 写性能瓶颈？gRPC 连接断开？

Step 3：根因确认
├── 案例 1：OBS 连接池耗尽
│   根因：OBS 默认最大连接数 10，并发 50 个冷数据读取时，大量请求等待空闲连接
│   证据：OBS 客户端统计 active_connections=10, pending_requests=40
│
├── 案例 2：gRPC 连接空闲断开
│   根因：元数据服务 gRPC keepalive 未配置，60s 无流量后被 nginx 断开
│   证据：gRPC 错误日志 "transport: connection closing"，伴随大量重连
│
├── 案例 3：Compaction 导致写放大
│   根因：MemTable 太小（64MB），频繁 Flush 和 Compaction 吃满 IO
│   证据：RocksDB STATISTICS 中 write_stall_microseconds > 10s
│
└── 案例 4：热点 Key 导致单分片过载
     根因：单个 Key QPS 5 万，打满单线程处理能力
     证据：CPU 单核 100%，其他核空闲
```

#### 架构根治方案

##### 根治 1：OBS 连接池 & 重试策略优化

```
问题：OBS 连接数不足，大量请求排队等待连接

根治方案:
├── 连接池扩容：10 → 200（按 CPU 核数 × 25 计算）
├── 连接预热：启动时创建 50 个连接（避免冷启动建连慢）
├── 连接健康检查：每 30s 探测一次（ping OBS endpoint）
├── 动态连接数：根据 pending 请求数动态伸缩连接（5-200）
├── 独立读写连接池：写 WAL 高优连接池（50 个），读 SSTable 低优（150 个）
└── 重试策略改造：
    ├── 指数退避：100ms → 500ms → 1s → 3s → 放弃
    ├── 最大重试次数：3 次（避免重试风暴）
    └── 快速失败：对 P99 > 10s 的请求不重试
```

##### 根治 2：异步化 + 缓冲层

```
问题：OBS 同步等待导致请求阻塞

根治方案:
├── 写入异步化
│   ├── 写 WAL 在本地（同步 fsync，< 1ms）→ 立即返回客户端
│   ├── SSTable 上传 OBS 异步进行（后台线程池）
│   └── 客户端收到写入成功 → 数据已在本地 WAL 落盘，OBS 上传异步完成
│
├── 引入缓冲队列（RingBuffer）
│   ├── OBS 上传请求放入无锁 RingBuffer（大小 10000）
│   ├── 消费者批量聚合（攒够 100 条或 100ms 触发一次）
│   ├── 批量上传 OBS（减少 RTT，吞吐提升 5x）
│   └── 队列满 → 反压到写入路径（减慢写入速度，不丢数据）
│
├── 请求级缓存（写合并）
│   ├── 相同 Key 的写入在内存缓存中合并（如 counter 自增）
│   ├── 合并后只写一次 RocksDB，减少写放大
│   └── 适用场景：计数器、时间序列、日志聚合
│
└── 预读 + 预取（读优化）
    ├── 冷数据读取时预取相邻 Block（ReadAhead 256KB-1MB）
    ├── 热 Key 访问模式学习（记录 Key 访问序列，预测下一个）
    └── 后台预热：根据访问日志提前加载冷 SSTable
```

##### 根治 3：熔断 + 限流的标准化

```
问题：熔断/限流策略混乱，各组件不统一

根治方案:
├── 统一熔断框架（自研 Sentinel-Go 轻量版）
│   ├── 滑动窗口（10s 窗口，100 个 bucket，每个 100ms）
│   ├── 错误率阈值：50% → 熔断
│   ├── 慢调用阈值：P99 > 5s → 熔断
│   └── 半开恢复：5s 后探测 1 个请求
│
├── 多维度限流
│   ├── QPS 限流（单节点 10 万 QPS 上限）
│   ├── 并发限流（最大 1000 个并发请求）
│   ├── OBS 连接数限流（最大 200 个 OBS 连接）
│   └── 热点 Key 限流（单 Key 最多 5000 QPS）
│
├── 请求优先级调度
│   ├── P0（支付）：不限流，直接走优化路径
│   ├── P1（用户侧）：限流 80%，降级读 stale cache
│   ├── P2（非核心）：限流 50%，超时直接返回
│   └── P3（后台任务）：限流 20%，可完全降级
│
└── 容量规划自动化
    ├── 基于历史流量预测（Prophet / ARIMA 模型）
    ├── 提前 30 分钟预测流量波峰，自动扩容
    └── 每秒上报指标到监控系统（Prometheus + Grafana）
```

##### 根治 4：数据一致性兜底

```
问题：故障恢复后数据可能不一致

根治方案:
├── OBS 多版本控制
│   ├── 每个 SSTable 保留最近 3 个版本
│   ├── 误删或覆盖可快速恢复
│   └── 定期清理过期版本（TTL = 7 天）
│
├── 定期全量校验（Checksum）
│   ├── 计算层每天凌晨对全量数据做 CRC 校验
│   ├── 对比 OBS 上的数据和元数据中心记录
│   └── 不一致 → 自动修复（以 OBS 为准或拉取副本）
│
├── WAL 补偿机制
│   ├── 记录所有写操作到审计日志（Write-Ahead Audit Log）
│   ├── 恢复时对比 WAL 和 SSTable，补偿缺失的写入
│   └── 最多回放 24 小时内的 WAL（过期清理）
│
└── 主备切换时的数据追齐
    ├── 新主节点先拉取最新 MANIFEST
    ├── 对比本地 SSTable 和 MANIFEST 差异
    ├── 差异 SSTable 从 OBS 下载
    └── 下载完成后才能接受写入（Readiness Probe）
```


### 常见追问准备

| 追问 | 回答思路 |
|------|---------|
| "OBS 延迟变大了怎么办？" | 三级缓存兜底：Block Cache → 本地 SSD → OBS。命中率 90%+ 在 L1，OBS 访问很少。 |
| "OBS 挂了怎么保证服务可用？" | 本地降级模式：写入本地 WAL + SSTable，OBS 恢复后异步回刷。 |
| "怎么保证 Etcd 和 OBS 数据一致？" | Etcd 事务：写 OBS 成功后才更新 Etcd。宕机后扫描 OBS 恢复元数据。 |
| "Compaction 抖动怎么解决？" | 分时段限速 + 增大 MemTable + Leveled Compaction + TTL 下沉。 |
| "和 TiKV 比怎么样？" | TiKV 用 Raft 做分布式一致性，我们更专注 Redis 协议兼容。 |
| "为什么用 RocksDB 不用 WiredTiger？" | RocksDB LSM-Tree 适合写密集场景，WiredTiger B+Tree 适合读密集。KeyDB 是写密集的。 |
| "扩缩容具体怎么做？" | 槽位迁移（虚拟节点），一次迁移 100 个槽位，增量同步，业务无感。 |
