## 一、性能数据

### 1.1 三种部署模式

KeyDB 有三种部署模式，按存储后端区分：

| 维度             | ①写内存（纯内存 KeyDB）          | ②写Flash/SSD（本地 SSD KeyDB）              | ③写OBS（存算分离 KeyDB） ⭐本项目         |
|:-----------------|:--------------------------------:|:-------------------------------------------:|:------------------------------------------:|
| **设备规格**     | 8C16GB                           | 8C16GB                                      | 8C16GB                                     |
| **线程数**       | 8 workers                        | 8 workers                                   | 8 workers                                  |
| **存储引擎**     | KeyDB 原生内存（无 RocksDB）     | KeyDB + RocksDB（本地文件系统）              | KeyDB + RocksDB（自定义 Env → OBS）        |
| **数据存放**     | 全量 DRAM                        | DRAM（热）+ 本地 SSD（全量）                | DRAM（热）+ OBS（冷）                      |
| **读 QPS**       | ~150,000                         | ~100,000（受 SSD 读 IOPS 限制）             | 热 150,000 / 冷 50,000                     |
| **读延迟 P99**   | < 1ms                            | ~3ms（SSD 随机读）                          | 热 1.2ms / 冷 8ms                          |
| **写 QPS**       | ~80,000                          | ~50,000（受 RocksDB compaction 影响）       | 80,000                                     |
| **写延迟 P99**   | < 2ms                            | ~5ms（含 WAL 刷盘）                         | 2ms                                        |
| **持久化**       | 无（类 Redis 纯内存）            | RocksDB 本地持久化                          | WAL 双写本地+OBS + SSTable 异步刷 OBS      |
| **成本/月/TB**   | ¥2,000                           | ~¥560（100GB 内存 + 900GB SSD）             | ~¥289（100GB 内存 + 900GB OBS）            |

> **说明：** 模式①②的数据为 KeyDB 公开 benchmark 参考值，非本项目实测；模式③为本项目存算分离架构实测值（来源：项目自述，无独立验证）。

### 1.2 写入路径对比（三种模式各自的主路径）

| 模式       | 写入路径                                                              | 同步/异步        | 关键延迟          |
|:-----------|:----------------------------------------------------------------------|:----------------:|:-----------------:|
| ①写内存    | KeyDB 命令解析 → 直接写内存数据结构                                   | 同步（无磁盘 IO） | < 0.1ms           |
| ②写Flash   | MemTable → WAL（本地 SSD）→ SSTable flush（本地 SSD）                 | WAL 同步 / SSTable 异步 | 0.1-2ms（WAL 刷盘）   |
| ③写OBS     | MemTable → WAL 双写（本地+OBS）→ SSTable flush（OBS）                 | WAL 同步 / SSTable 异步 | 0.5-2ms（WAL 同步 OBS） |

### 1.3 延迟分布（模式③存算分离 混合读写）

```
P50   0.8ms
P90   2ms
P99   5ms
P999  15ms

热数据：P99 < 1ms
冷数据：P99 ≈ 8ms
写入：  P99 < 3ms
```

### 1.4 存储成本对比

| 方案 | 100GB 成本 | 1TB 成本 |
|------|-----------|---------|
| ①纯内存 | ¥200/月 | ¥2,000/月 |
| ②本地 SSD | ~¥240/月（100GB 内存 + 本地 SSD） | ~¥560/月（100GB 内存 + 900GB SSD） |
| ③存算分离 | ~¥209/月（100GB 内存 + OBS） | ~¥289/月（100GB 内存 + 900GB OBS） |
| **③ vs ① 节省** | **~85%** | **~70%**（含附加成本） |

**成本计算**：
```
①纯内存：    1TB × ¥2/GB·月 = ¥2,000/月
②本地 SSD：  100GB × ¥2 + 900GB × ¥0.4 = ¥560/月
③存算分离：  100GB × ¥2 + 900GB × ¥0.099 = ¥289/月
节省：(2000-289)/2000 ≈ 85%（纯存储），综合 ~70%（含 OBS 访问费）
```

### 1.5 优化方向

| 问题 | 现状 | 方案 | 预期 |
|------|------|------|------|
| 冷数据延迟（③） | 8ms | 异步预取 + 连接池 | 降到 3ms |
| Compaction 抖动（②③） | QPS 掉 50% | 分时段限速 | 抖动降到 10% |
| 内存占用（③） | 16GB | 智能缓存淘汰 | 降到 8GB |
| 写放大（②③） | 10 倍 | 增大 MemTable | 降到 5 倍 |

## 二、STAR 故事

### 背景 (Situation)

华为云 KeyDB 团队，负责存储引擎开发。Redis 纯内存方案成本高，1TB 数据月费 ¥2000。客户数据量大时成本难以接受。

### 任务 (Task)

设计存算分离方案：热数据在内存，冷数据在廉价 OBS 对象存储，兼容 Redis 协议，对上层应用透明。

### 行动 (Action)

1. **RocksDB 存储引擎**：基于 RocksDB 的 LSM-Tree 架构，数据分层存储
2. **Env 插件开发**：继承 EnvWrapper 重写文件操作，SSTable→OBS、WAL→双写、MANIFEST→Etcd
3. **元数据中心**：Etcd 集群管理文件位置和元数据，gRPC 接口交互
4. **本地缓存**：Block Cache + 智能淘汰策略，热数据本地加速
5. **大 Key/热 Key 分析**：减少内存开销的采样算法

### 结果 (Result)

| 指标 | 优化前 | 优化后 |
|------|--------|--------|
| 存储成本（1TB） | ¥2,000/月 | ~¥300/月 |
| 热数据读延迟 | 0.3ms | 0.3ms（不变） |
| 冷数据读延迟 | — | 8ms |
| 写入 QPS | — | 80,000 |
| 混合 QPS | — | 100,000 |

## 三、高频 Q&A

### Q1: 存算分离核心原理？

> RocksDB Env 插件拦截文件操作。SSTable 数据文件写 OBS，WAL 双写本地+远程，MANIFEST 存 Etcd。RocksDB 内部不感知底层存储。

### Q2: 冷数据延迟 8ms 怎么优化？

> 异步预取：预测即将访问的冷数据提前加载到本地缓存。OBS 连接池复用减少建连开销。

### Q3: WAL 双写怎么保证一致性？

> 先同步写远程，成功后再异步写本地。恢复时优先从远程拉取 WAL 进行数据恢复。

### Q4: 大 Key 分析 CPU 高怎么解决？

> 计算内存占用时遍历哈希桶，大量空桶消耗 CPU。优化：用 field 数量替代内存占用计算，减少 O(n) 遍历。

### Q5: 热 Key 分析内存增加多少？

> 每个 robj 增加 8 字节访问计数，总内存增加 < 5%，最多 < 10%。

### Q6: Compaction 抖动怎么处理？

> 分时段限速：高峰时段限制 Compaction 带宽，低谷时段加速。配合 MemTable 增大减少 Compaction 频率。
