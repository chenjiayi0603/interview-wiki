## 一、项目复盘与架构设计

**考察点**：业务理解深度 & 架构设计能力

### 背景：项目定位与目标

我自研的项目是 **Thunder——一个基于 C++20 stackless 协程的高性能分布式异步框架**，整合了 RPC 通信、Raft 共识算法、动态插件热加载三大核心能力。

**项目动机：**
- 业界主流 RPC 框架（gRPC / brpc / Thrift）存在共性问题：
  - **性能瓶颈**：gRPC 基于 HTTP/2 + Protobuf，协议头大（~50B）、序列化慢（500ns/1KB）、内存占用高（50KB/连接）
  - **协程支持弱**：C++ 领域缺乏原生协程 RPC 框架，brpc 的 bthread 是 stackful 协程，栈 64KB-1MB 浪费内存
  - **Raft 不内置**：gRPC/brpc 需要额外集成 Raft 库，增加了系统复杂度和集成成本
- C++20 标准引入了原生协程支持（`co_await` / `co_return` / `co_yield`），但业界缺少一个"把协程、RPC、Raft 整合在一起"的高性能基础框架

**项目目标：**
> 自研一个 C++20 stackless 协程驱动的分布式框架：单进程 50 万连接、RPC QPS 200 万、Raft 选主 < 50ms、内存效率比 gRPC 高 2.5 倍。

### 难点：技术上的核心挑战

#### 挑战 1：协程调度器设计 —— 50ns 切换 vs 10μs 线程切换

C++20 协程是 stackless 的，编译器把协程变换为状态机。但要让协程在大规模并发下高效运行，需要自研调度器。

**方案：**
- **Work-Stealing 调度器**：每个 Worker 线程绑定一个 CPU 核心，拥有 lock-free SPSC 本地队列和独立 epoll 实例
- **窃取策略**：本地队列空 → 随机窃取其他 Worker 的任务（均匀分布）→ 窃取失败则休眠（eventfd 唤醒）
- **切换开销 50ns**：stackless 协程只需保存/恢复约 10 个寄存器，不需要 Cache Miss + TLB Flush + 内核调度（线程切换 ~10μs，200 倍差距）
- **栈内存 2KB-8KB**：vs 线程 8MB 栈，50 万连接场景下内存从 500GB+ 降到 ~2.5GB

#### 挑战 2：高性能 RPC 协议 —— 自研 vs Protobuf

**方案：**
- **自研 Binary 协议**：头部仅 22B（gRPC ~50B），序列化 250ns/1KB（gRPC 500ns/1KB）
- **零拷贝设计**：基于 `writev` 合并小包发送，io_uring 支持直接读写用户缓冲区
- **长连接复用**：多个请求复用同一 TCP 连接，通过 Request ID 匹配响应（支持乱序响应）
- **共享内存 IPC**：Manager-Worker 进程间通过 mmap + ring buffer 通信，零 syscall（除 semaphore），延迟 0.15ms，QPS 150 万

**为什么自研不是用 Protobuf？**
```
核心原因不是"Protobuf 慢"，而是三个维度综合考量：
1. 性能：自研 header 22B vs Protobuf varint 平均 10B/int32，小请求时协议开销占比高
2. 编译：自研用 C++ 模板元编程，编译期生成序列化代码，免去 protoc 编译步骤
3. 精简：自研只实现需要的类型（int/string/bytes/vector），没有 Protobuf 的反射等重量级特性

代价是向前兼容需要手动处理——这是可以被接受的 trade-off。
```

#### 挑战 3：Raft 共识算法优化 —— 从 200ms 到 45ms 选主

标准 Raft 选举需要 200ms+，主要瓶颈在心跳检测超时和串行投票。

**方案：**
- **批量日志复制**：攒够 100 条或等待 5ms 后批量发送 AppendEntries RPC，QPS 从 1 万提升到 10 万（100 倍）
- **预投票（Pre-Vote）**：发起选举前先探测多数节点可达，防止网络分区时的无效选举
- **异步投票**：RequestVote 异步发送，不阻塞选举流程
- **ReadIndex 优化**：Leader 记录当前 commit_index，Follower 可以直接提供线性一致性读，不需要走 Raft 日志

#### 挑战 4：IO 引擎选型 —— epoll vs io_uring

**方案：**
- **三引擎架构**：通过统一 `IoBackend` 接口抽象，支持 libev(epoll)、原生 io_uring、Asio io_uring 三种后端
- **嵌入而非替代**：io_uring 嵌入 libev 主循环，通过 `ev_prepare/ev_check/ev_io(ring_fd)` 三路驱动，零锁、零线程跳
- **实测数据**：小包场景 epoll 和 io_uring 吞吐持平，大包（64KB）场景 io_uring 延迟低 86%，尾延迟降至 1/50
- **降级策略**：低版本内核（< 5.1）自动降级到 epoll，无需修改业务代码

### 反思：当前系统设计的缺陷与优化方向

#### 缺陷 1：io_uring 集成尚不完整
**问题**：当前 io_uring 后端中，写操作仍使用同步 writev（实测小包同步写效率足够），没有充分利用 io_uring 的异步写能力。对于大包写入场景，同步写会短暂阻塞 Worker 线程。

**优化方向**：实现完全的异步读写路径。写操作也通过 io_uring SQE 提交，CQE 完成后恢复协程。代价是需要处理 write 部分完成的复杂情况（short write），以及 SQE 队列满时的背压策略。

#### 缺陷 2：协程栈预分配浪费
**问题**：当前为每个协程固定预分配 8KB 栈空间。大部分 RPC 请求实际使用 < 1KB 栈，但少量请求（如深度嵌套的 RPC 调用）可能需要超过 8KB。

**优化方向**：引入动态扩容栈（分段分配）。初始 2KB，当协程栈溢出时通过 `sigaltstack` 信号处理机制动态扩展。类似 goroutine 的 2KB 初始栈 + 动态扩容方案。

#### 缺陷 3：Raft 日志存储缺乏 compaction 的智能调度
**问题**：当前快照触发基于固定阈值（10000 条日志或 1 小时），没有考虑写入速率和磁盘空间使用率的动态变化。在写高峰期间触发快照可能导致 IO 抖动。

**优化方向**：引入自适应快照调度。根据日志增长速度、磁盘 IO 利用率、写入 QPS 动态调整快照阈值。快照生成和日志 compact 也做 IO 限速（类似 RocksDB 的 `rate_limiter`）。

#### 缺陷 4：缺少生产级可观测性
**问题**：当前框架的监控和追踪能力薄弱。除了基础的日志和性能计数器外，缺乏分布式追踪、链路级别的延迟分解、协程级别的 Profile 能力。

**优化方向**：
- 在 RPC 请求和 Raft 日志复制路径中嵌入 OpenTelemetry 追踪
- 实现协程级别的火焰图：记录每个协程的创建、挂起、恢复、完成时间线
- 集成 Prometheus 指标暴露（QPS、延迟分布、协程数、内存池水位）

## 二、性能优化与平滑迁移

**考察点**：性能优化 & 不停机迁移能力

### 场景说明

Thunder 作为一个基础框架，其"迁移"场景通常是将**基于线程模型的旧服务迁移到基于协程的新框架**。下面以一个典型的**高并发网关服务**为例，阐述从线程模型到协程模型的迁移方案。

```
旧架构（线程模型）:
  每个连接一个线程 → 1 万连接 = 1 万线程
  ├── 线程栈: 8MB × 10,000 = 80GB（不可行）
  └── 实际: 线程池 + epoll 多路复用，但业务代码是阻塞式

新架构（协程模型）:
  每个连接一个协程 → 1 万连接 = 1 万协程
  ├── 协程栈: 2KB × 10,000 = 20MB ✅
  └── 代码: 线性编写，co_await IO 操作
```

### 拆分思路：按 IO 类型拆分

> 面试话术："框架层面的拆分不是微服务拆分，而是'IO 类型拆分'——把阻塞 IO、计算 IO、网络 IO 分离到不同的协程调度域。"

| 维度 | 线程模型（旧） | 协程模型（新） |
|:-----|:-----------:|:-----------:|
| **网络 IO** | epoll 回调 + 状态机 | `co_await EpollAwaiter` 线性代码 |
| **磁盘 IO** | 线程池 + 异步回调 | `co_await UringAwaiter` 协程化 |
| **业务逻辑** | 回调嵌套、Lambda 地狱 | 顺序代码、try-catch 异常处理 |
| **并发控制** | mutex + condition_variable | channel + 协程安全队列 |
| **定时器** | 时间轮回调 | `co_await SleepFor(100ms)` |

**框架分层架构：**

### 集群扩容策略

```
Thunder 作为框架，支持两种集群部署模式：

模式一：Manager-Worker 单机多进程（共享内存 IPC）
┌─────────────────────────────────────────┐
│  Manager（管理进程）                      │
│  ├── 共享内存 ring buffer ←→ Worker 0   │
│  ├── 共享内存 ring buffer ←→ Worker 1   │
│  ├── 共享内存 ring buffer ←→ Worker N   │
│  └── 负责：路由、负载均衡、服务发现       │
├─────────────────────────────────────────┤
│  Worker（工作进程，每 CPU 核心一个）      │
│  ├── 独立 epoll + 协程调度器             │
│  ├── CPU 亲和绑定                        │
│  └── 无状态，可随意增删                  │
└─────────────────────────────────────────┘

模式二：多节点分布式集群
├── 节点间通过 RPC 通信
├── Raft 集群管理配置和元数据（3/5 节点）
├── 水平扩容：新节点加入 → 通知注册中心
├── 负载均衡：一致性哈希 / 轮询 / 最小连接
└── 故障转移：健康检查 5s 间隔 → 标记下线 → 客户端重连

扩容步骤（以分布式集群为例）：
1. 新增节点启动，注册到管理面
2. 管理面更新路由表，通知已有节点
3. 客户端渐近感知（路由表版本号 + 增量更新）
4. 新节点开始接收请求（无数据迁移，纯计算节点）
5. 缩容同理：节点离线前排空连接→优雅退出
```

#### 瓶颈定位方法

| 瓶颈类型 | 定位手段 | 典型阈值 |
|:---------|:---------|:--------|
| **协程调度瓶颈** | 自研 Profile：协程切换次数/秒 | > 100 万次/秒需要优化 |
| **Work-Stealing 冲突** | steal 成功率 < 80% | 负载不均衡，调整窃取策略 |
| **epoll 事件堆积** | epoll_wait 返回 > 500 事件/次 | 单次事件处理变慢，需拆分 |
| **RPC 序列化瓶颈** | perf top | `BinaryWriter::WriteString` > 10% |
| **Raft 日志复制瓶颈** | RTT + 批量等待时间 | 批量等待 > 5ms 需调整阈值 |
| **内存池耗尽** | 对象池分配次数 | 分配 > 释放，内存持续增长 |

**压测踩过的坑：**
1. **共享内存 ABA 问题**：ring buffer 的 head/tail 指针在无锁环境下出现 ABA。修复：加入 64 位版本号标记
2. **epoll 惊群**：多个 Worker 监听同一个 listen_fd，accept 时多 Worker 被唤醒。修复：SO_REUSEPORT + 每个 Worker 独立 listen_fd
3. **协程栈溢出**：某些 RPC handler 有深度递归，8KB 栈不够用。修复：编译期检测 + 侵入式检测（编译期标记需要大栈的函数）

#### 阈值设定

| 指标 | 警告水位 | 熔断水位 | 动作 |
|:-----|:-------:|:-------:|:-----|
| RPC P99 延迟 | > 5ms | > 20ms | 降级：切到本地处理 |
| 协程调度延迟 | > 100μs | > 1ms | 告警：检查 Worker 负载 |
| Raft 选主失败 | > 1 次/小时 | > 5 次/小时 | 告警：检查网络/节点状态 |
| 内存占用 | > 80% | > 90% | 告警 + 触发内存池清理 |
| 连接数增长率 | > 1000/s 持续 1min | > 5000/s | 限流：新连接排队 |
| 日志复制批量率 | < 50 条/批 | < 10 条/批 | 调优批量等待时间 |

### 双写双读切换流程（迁移场景）

Thunder 框架的迁移场景是：将**基于线程模型/回调模型的旧服务**迁移到**Thunder 协程框架**。

#### 阶段 1：适配层封装（并行存在期）

```
旧代码（线程/回调）        Thunder 适配层（协程封装）
─────────────────          ─────────────────────

// 旧的回调风格 EPoll Server
void OnReadable(int fd) {          // Thunder 协程风格
    char buf[1024];                 Task<> HandleRead(int fd) {
    int n = read(fd, buf, ...);         char buf[1024];
    Process(buf, n);                    int n = co_await AsyncRead(fd, buf);
}                                       co_await Process(buf, n);
                                    }
```

#### 阶段 2：增量迁移（灰度切流）

```
Step 1: 20% 流量走 Thunder
├── 通过配置中心下发路由比例
├── 旧服务与新服务并行运行
└── 对比两端延迟+错误率

Step 2: 50% 流量走 Thunder
├── 持续观察 24 小时
├── 确认无回归
└── 旧服务保留作为 fallback

Step 3: 100% 流量走 Thunder
├── 旧服务保留只读（兜底）
└── 一个月后清理旧服务
```

#### 阶段 3：回滚

```
触发条件：P99 延迟 > 2x 基线 或 错误率 > 1%
回滚：配置中心一键切回 100% 旧服务（< 1s）
事后：分析 Thunder 性能瓶颈（协程调度/序列化/网络）
```

## 三、复杂故障与分层止损

**考察点**：复杂故障处理 & 架构根治能力

### 场景适配：Thunder RPC + Raft 分布式链路

模板题目是 `Kafka → Flink → Redis → DB`，对应到 Thunder 的场景是一条**分布式 RPC 调用链路**：

```
客户端 → [Thunder 网关节点] → [RPC 调用] → [Thunder 服务节点] → [Raft 集群写入]
                                                                  ├── Leader 处理
                                                                  ├── 日志复制到 Follower
                                                                  └── WAL 磁盘写入
```

这条链路上最典型的故障是：**RPC 调用超时，导致客户端请求堆积，最终级联雪崩**。

---

### 分层止损预案（即时应对）

#### 第 1 层：客户端侧 —— 超时控制 & 快速失败

```
问题现象：客户端调用 RPC 等待 10s+ 无响应

止损动作:
├── 请求超时控制
│   ├── 默认 RPC 超时：连接超时 500ms + 请求超时 3s
│   ├── 可自定义 per-request 超时（如 SQL 查询设 30s）
│   └── 超时 → 取消协程（cancel context）→ 释放资源
│
├── 熔断器（自研轻量版）
│   ├── 统计窗口：10s
│   ├── 错误阈值：50% 请求超时 → 熔断开启 30s
│   ├── 熔断期间：直接返回 fallback（缓存/空）
│   └── 半开恢复：30s 后放 1 个请求探测
│
├── 指数退避重试
│   ├── 失败后等待：100ms → 500ms → 1s → 3s → 放弃
│   ├── 最大重试次数：3 次
│   └── 幂等请求可重试，非幂等请求不重试
│
└── 连接池保护
    ├── 最大连接数 100，空闲连接 5
    ├── 连接泄漏检测：空闲超时 300s 自动断开
    └── 报错连接自动标记、移除
```

#### 第 2 层：网关/路由层 —— 流量调度 & 过载保护

```
问题现象：大量 RPC 超时导致网关层 Goroutine/协程堆积

止损动作:
├── 并发限流
│   ├── 网关层最大并发请求数 = CPU 核数 × 1000
│   ├── 超过 → 请求排队（队列深度 10000）
│   └── 队列满 → 直接返回 SERVER_BUSY
│
├── 请求分级
│   ├── P0（强一致写）：有限重试，不降级
│   ├── P1（最终一致写）：可降级为异步写入
│   ├── P2（读请求）：可返回缓存/stale 数据
│   └── P3（后台任务）：可完全降级
│
├── 连接隔离
│   ├── 不同服务使用独立连接池
│   ├── 某个后端服务故障 → 只影响该服务的连接池
│   └── 防止级联雪崩到其他服务
│
└── 优雅降级
    ├── P2/P3 请求直接返回降级响应（快速失败）
    ├── 释放协程和连接资源给 P0/P1 请求
    └── 降级比例动态调整（错误率越高，降级越多）
```

#### 第 3 层：RPC 服务节点 —— 协程级隔离

```
问题现象：服务节点内大量协程在等待下游 Raft 集群

止损动作:
├── 协程调度隔离
│   ├── 每个服务实例有独立协程调度域
│   ├── 某个调度域阻塞 → 不影响其他调度域
│   └── Worker 线程通过 Work-Stealing 平衡负载
│
├── RPC 请求超时传播
│   ├── 上游超时 → `co_await` 抛出 `TimeoutException`
│   ├── 协程捕获异常后立即释放资源（连接/内存）
│   └── 不继续向下游发送已超时的请求
│
├── 服务端限流
│   ├── 最大并发请求数 = Worker 数 × 500
│   ├── 信号量控制（`semaphore.acquire()`）
│   └── 超过 → 直接返回 RATE_LIMITED
│
└── 健康检查端点
    ├── /healthz → 检查协程调度器存活
    ├── /metrics → Prometheus 暴露 QPS/延迟/协程数
    └── /debug → 协程堆栈 dump（类似 pprof）
```

#### 第 4 层：Raft 共识层 —— 选主保护 & 日志复制限流

```
问题现象：Raft Leader 负载过高或宕机

止损动作:
├── Leader 限流
│   ├── 写入 QPS 超过阈值 → 拒绝部分写入请求
│   ├── 日志复制 backlog > 1000 → 减慢接受写入
│   └── 保护 Follower 不被淹没
│
├── 快速选主
│   ├── PreVote 探测 → 确认多数节点可达再选举
│   ├── 心跳间隔 50ms → 故障检测 < 150ms
│   └── 选主恢复时间 < 50ms（3 节点）
│
├── 日志复制背压
│   ├── Follower 复制落后 > 10000 条 → Leader 减慢推送
│   ├── Follower 落后 > 50000 条 → 触发快照安装
│   └── 避免 Follower OOM
│
└── Follower 只读降级
    ├── Follower 与 Leader 失联 → 自动切为只读模式
    ├── 读请求走本地状态机（可能 stale，但可用）
    └── 重新连接后追齐日志 → 恢复读写
```

#### 根因定位方法论

```
定位 RPC 超时根因的步骤：

Step 1：现场保留
├── dump 所有协程堆栈（框架内置 debug 接口）
├── 导出 RPC 调用链时间线（请求 ID、每跳耗时）
├── 导出 Raft 状态（term/commit_index/log_length/peer_state）
├── 保存系统日志和内核日志（dmesg）
└── 保存网络抓包（tcpdump，如有必要）

Step 2：分层排查
├── 客户端侧：超时配置？重试策略导致请求放量？
├── 网络侧：带宽打满？TCP 重传率 > 1%？网卡丢包？
├── 服务端侧：协程调度延迟？序列化瓶颈？GC（如果有）？
├── Raft 侧：Leader 过载？Follower 日志落后？磁盘 IO 瓶颈？
└── 系统侧：CPU 饥饿？内存不足导致 OOM？内核参数不合理？

Step 3：根因确认（真实案例）
├── 案例 1：epoll 惊群导致连接建立变慢
│   根因：多 Worker 共享 listen_fd，accept 时多 Worker 同时唤醒
│   证据：epoll_wait 返回 EPOLLIN 频次 > accept 成功数 10 倍
│
├── 案例 2：批量日志复制延迟失准
│   根因：攒批等待时间（5ms）在网络延迟（2ms RTT）下比例过高
│   证据：日志复制 P99 7ms，其中攒批等待占 5ms
│
├── 案例 3：共享内存 ring buffer 头尾指针不同步
│   根因：无锁队列在弱内存序架构（ARM）上缺少 memory barrier
│   证据：IPC 偶发数据损坏，x86 不出现，ARM 频繁出现
│
└── 案例 4：协程栈内存泄漏
     根因：协程完成时未正确释放 promise 对象
     证据：内存持续增长 + pprof 显示大量未析构协程帧
```

#### 架构根治方案

##### 根治 1：RPC 超时链路的确定性超时

```
问题：超时配置分散在各层，不同层超时不一致导致资源浪费

根治方案:
├── 统一 RPC 超时策略
│   ├── 请求发起时确定总超时 T（默认 3s）
│   ├── 每跳消耗 T/N（N 为预估跳数）
│   ├── 剩余超时在 Response header 中回传
│   └── 超时到 → 立即取消协程，不继续转发
│
├── 优先级队列
│   ├── P0：超时 5s，最多重试 2 次
│   ├── P1：超时 3s，最多重试 1 次
│   ├── P2：超时 1s，不重试
│   └── 调度器优先执行 P0 协程
│
└── 自适应超时
    ├── 基于历史 P99 延迟动态计算超时
    ├── 公式：`timeout = max(p99 × 3, 500ms)`
    └── 每分钟更新一次，避免配置重启
```

##### 根治 2：协程调度器的过载保护

```
问题：协程数量无限制增长，调度延迟飙升

根治方案:
├── 协程数量限流
│   ├── 最大协程数 = Worker 数 × 10000
│   ├── 超过 → 创建协程时挂起，等待其他协程完成
│   ├── 实现：全局协程计数器 + semaphore
│   └── 防止协程无限增长耗尽内存
│
├── 协程调度延迟监控
│   ├── 每个协程创建时记录时间戳
│   ├── 协程等待调度时间 > 1ms → 打印告警日志
│   └── 协程等待调度时间 > 10ms → 触发熔断
│
└── Work-Stealing 优化
    ├── 当前：随机窃取 → 可能窃取到正在执行热任务的 Worker
    ├── 优化：窃取前先检查目标 Worker 队列的"平均等待时间"
    ├── 只从等待时间 > 阈值 的 Worker 窃取
    └── 减少不必要的 cache miss
```

##### 根治 3：Raft 日志复制的动态批量

```
问题：固定批量策略（100 条/5ms）在低负载下延迟高，高负载下吞吐不足

根治方案:
├── 动态批量阈值
│   ├── 低负载（QPS < 1000）：攒 10 条或 2ms → 低延迟优先
│   ├── 正常负载（QPS 1000-10000）：攒 50 条或 3ms → 平衡
│   ├── 高负载（QPS > 10000）：攒 200 条或 5ms → 高吞吐优先
│   └── 阈值自动调整，无需人工干预
│
├── 流水线复制（Pipeline Replication）
│   ├── 当前：发一批 → 等 Ack → 发下一批
│   ├── 优化：发一批 → 不等 Ack 继续发下一批
│   ├── 使用 sliding window 控制并发（窗口大小 = 10）
│   └── 吞吐提升 30%，实现复杂度中高
│
└── WAL 分组提交（Group Commit）
    ├── 多个日志条目合并一次 fsync
    ├── 攒够 64KB 或 1ms 触发一次
    └── 减少 fsync 次数，提升吞吐
```

##### 根治 4：可观测性增强

```
问题：故障发生时缺乏有效数据定位根因

根治方案:
├── 协程级链路追踪
│   ├── 每个 RPC 请求携带 trace_id
│   ├── 记录协程在每个阶段的耗时：
│   │   ├── 协程创建 → 调度执行 → IO 等待 → 完成
│   │   └── 精度：微秒级
│   └── 通过 debug 接口导出（/debug/traces）
│
├── 关键指标监控（Prometheus）
│   ├── thunder_rpc_requests_total (labels: service, method, status)
│   ├── thunder_rpc_latency_ms (histogram: 0.1ms-10s)
│   ├── thunder_coroutines_active
│   ├── thunder_raft_leader_changes_total
│   ├── thunder_raft_log_entries_per_batch
│   └── thunder_worker_steal_ratio
│
└── 主动健康检查
    ├── 协程调度器存活检查：每 5s 心跳探测
    ├── RPC 端点健康检查：/healthz
    ├── Raft 集群健康检查：/raft/status
    └── 依赖组件检查：/dependencies（检查下游服务可达性）
```

### 🔁 幂等性设计（Raft 天然幂等）

```
场景：RPC 请求重试可能导致 Raft 日志重复写入

幂等方案:
├── Raft 日志幂等
│   ├── 每条日志有唯一 index + term
│   ├── 日志追加前检查 index 是否已存在
│   └── 重复的 AppendEntries 请求被忽略
│
├── RPC 请求幂等
│   ├── 请求 ID（UUID）全局唯一
│   ├── 服务端缓存最近 10000 个已处理的请求 ID
│   └── 重复请求直接返回缓存结果
│
└── 状态机幂等
    ├── 状态机操作是确定性的（相同输入 → 相同输出）
    ├── 重复 Apply 相同日志产生相同结果
    └── 天然幂等，不需要额外去重
```

### 💥 节点宕机（Raft 自动恢复）

```
场景：Raft 集群节点宕机

故障检测:
├── 心跳超时 150ms（3 × 50ms 心跳间隔）
├── 2 次心跳未收到 → 标记节点可能宕机
└── 3 次心跳未收到 → 发起 Leader 选举

Leader 宕机恢复:
├── Follower 检测到选举超时 → 发起 PreVote
├── PreVote 通过 → 发起正式选举
├── 获得多数票 → 成为新 Leader
├── 新 Leader 追加 No-Op 日志 → 提交之前 term 的日志
├── 业务恢复时间：< 50ms（3 节点，1ms 网络）
└── 客户端重连（连接池自动排除旧 Leader）

Follower 宕机恢复:
├── Leader 检测到 Follower 心跳超时
├── 标记 Follower 为 unreachable
├── 停止向该 Follower 发送日志复制
├── Follower 重启后重新加入集群
├── 从快照或日志追齐数据
└── 恢复正常复制
```

### ⚔️ 资源抢占（协程优先级调度）

```
场景：P0 请求和 P3 后台任务争抢 CPU 和 IO 资源

方案:
├── 协程优先级（3 级）
│   ├── High（P0 请求）：抢占式调度
│   │   ├── 调度器优先执行 High 队列中的协程
│   │   └── High 协程可抢占 Low 协程的 Worker 线程
│   ├── Normal（P1/P2 请求）：正常调度
│   └── Low（P3 后台任务）：空闲时执行
│
├── 资源配额管控
│   ├── 每个优先级有最大协程数配额
│   │   ├── High: max = Worker 数 × 100
│   │   ├── Normal: max = Worker 数 × 500
│   │   └── Low: max = Worker 数 × 2000
│   ├── 超过配额 → 创建协程时挂起
│   └── 防止低优任务耗尽系统资源
│
└── IO 带宽分配
    ├── Raft 日志复制（P0）：带宽不限制
    ├── 快照传输（P2）：限速 100MB/s
    └── 后台任务（P3）：限速 10MB/s
```

### 📊 编排方式对比：协程 DAG 编排 vs 事件驱动编排

| 维度 | 协程 DAG 编排（Thunder） | 事件驱动编排 |
|:-----|:---------------------:|:----------:|
| **模型** | 协程 A `co_await` 协程 B → 等待 B 返回 | 发布 Event → 注册 Callback → Event 到达时触发 |
| **代码风格** | 线性顺序代码，try-catch 异常 | 回调嵌套，promise.then().catch() |
| **同步原语** | `co_await` / `sync_wait` / `when_all` | 事件循环 + 状态机 |
| **错误处理** | try-catch，协程栈 unwind | 错误回调，容易遗漏 |
| **资源管理** | RAII → 协程退出自动释放 | 手动释放，容易泄漏 |
| **调试难度** | 低（正常 stack trace） | 高（callback hell） |
| **适用场景** | 请求-响应、DAG 任务 | 状态机、流处理、UI 事件 |
| **Thunder 的选择** | ✅ C++20 协程 | ❌ 不适用于 RPC 场景 |

**为什么 Thunder 选协程 DAG 编排？**

```
1. RPC 是天然的请求-响应模式
   ├── 客户端发送请求 → 等待响应 → 处理结果
   ├── 协程的 co_await 恰好对应：挂起→等待→恢复
   └── 代码写起来像同步调用，但实际上是异步的

2. 错误处理统一
   ├── 网络超时 → co_await 抛出异常
   ├── 序列化失败 → 抛出异常
   ├── Raft 复制失败 → 抛出异常
   └── 统一在一个 try-catch 中处理，不会遗漏

3. 资源管理自动化
   ├── 协程栈（RAII 对象）在 co_return 时自动析构
   ├── 连接池的借用/归还通过协程生命周期管理
   └── 没有 callback 场景下的"资源何时释放"问题

4. 性能
   ├── 协程切换 50ns（vs 事件回调虚函数调用 ~20ns）
   ├── 虽然回调略快，但可维护性收益远大于性能损失
   └── 在毫秒级 RPC 延迟中，50ns 切换可以忽略
```

**如果实现流式数据处理，我会用事件驱动编排：**

```
事件驱动模式示例（Thunder 的流式 RPC 场景）：
┌──────────┐  CQE 事件  ┌──────────┐
│ 网络 IO   ├───────────► │ 事件循环  │
│ (io_uring)│            │ (libev)  │
└──────────┘            └────┬─────┘
                             │ 事件分发
                        ┌────▼─────┐
                        │ 连接/数据  │
                        │ 事件处理   │
                        └──────────┘

优点：天然适配 IO 多路复用，每个事件处理时间极短（< 1μs）
缺点：复杂业务逻辑下代码可维护性差
```

```
4. 展示反思能力
   ❌ "Thunder 的设计没有缺陷"

   ❌ "我们选了 epoll"
   ✅ "我们保留了 epoll + io_uring 两个后端。原因：小包场景两者接近，大包（64KB）场景 io_uring 延迟低 86%。内核 < 5.1 自动降级到 epoll"
```

### 常见追问准备

| 追问 | 回答思路 |
|:-----|:---------|
| "C++20 stackless 协程的切换开销为什么只有 50ns？" | 编译器变换为状态机，只保存/恢复寄存器（~10 个），不需要 Cache Miss + TLB Flush + 内核调度 |
| "自研 RPC 协议头 22B 怎么实现的？" | Magic(1) + Version(1) + Type(1) + Flags(1) + RequestID(4) + ServiceID(4) + MethodID(4) + BodyLen(4) = 22B |
| "Raft 选主怎么优化到 45ms 的？" | 心跳 50ms + 异步投票 + PreVote 预检测 + 3 节点多数派 = 45ms |
| "批量复制攒多少条最优？" | 取决于延迟目标：低延迟场景攒 10 条/2ms，高吞吐场景攒 200 条/5ms。我们做了动态自适应 |
| "共享内存 ring buffer 怎么解决 ABA 问题？" | 64 位版本号标记 + memory barrier（ARM 架构必须） |
| "50 万连接每连接 20KB 怎么算的？" | 协程控制块 2KB + 读缓冲 8KB + 写缓冲 8KB + 连接对象 1KB + epoll 0.5KB + 其他 0.5KB = 20KB |
| "和 brpc 比差距在哪？" | brpc 工业级成熟度更高。Thunder 优势在 C++20 协程原生支持、stackless 内存效率、Raft 内置 |
| "io_uring 比 epoll 好在哪？" | 大包场景优势明显（64KB 延迟低 86%），小包场景差距不大。io_uring 减少 syscall 次数，但需要内核 5.1+ |
