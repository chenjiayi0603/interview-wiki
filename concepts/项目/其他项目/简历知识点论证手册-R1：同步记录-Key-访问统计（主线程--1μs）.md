# R1：同步记录 Key 访问统计（主线程 <1μs）

**简历原文**：在命令处理路径中同步记录 Key 访问统计（规避异步拷贝引发内存暴涨）

## 数据支撑

| 指标 | 值 | 说明 |
|------|----|------|
| 主线程额外开销 | <1μs | Redis 命令本身耗时 1–10μs，<1μs ≈ 增加 1–10% |
| 支撑实例规模 | 万级 | 主从 / 哨兵 / 集群三模式全覆盖 |
| 插桩位置 | `processCommand` 入口/出口 | 与 Redis 模块化设计一致 |

**为什么不用异步拷贝**：异步方案需要将 Key 的 value 数据拷贝到独立队列（或后台线程），大 Key（value 可达 MB 级别）的拷贝会使内存暴涨。同步记录只需记录 Key 名称（字符串引用）+ value 大小（整数），不复制数据本体，开销极低（一次内存写入 ~纳秒级）。

## 理论支撑

Redis 单线程架构（主线程处理所有命令），在 `processCommand` 路径插桩是最直接的方式。同步记录在命令执行完成后立即更新统计结构（哈希表计数器），整个操作是纯内存读写，无锁需要（主线程单线程，天然无竞争）。

布隆过滤器前置：先用布隆过滤器判断 Key 是否有可能是大 Key / 热 Key 候选，命中后才分配计数器，避免为每个 Key 维护状态导致的内存膨胀。

## 业界对标

- **`redis-cli --bigkeys`**（被替代的方案）：遍历全量 Key 的离线扫描，执行期间占用大量 CPU + IO，影响主业务（实测会引起主线程延迟上升）
- **Redis 4.0+ OBJECT FREQ 命令**：LFU 模式下记录访问频次，思路相似但仅限 value 淘汰策略，不支持实时大 Key 检测
- **阿里云 Redis 大 Key 检测**：阿里云 DCS 内置大 Key / 热 Key 统计，实现机制与本方案类似

## 追问预案

**Q：为什么不用 Redis Module 实现？**
> Module 需要独立 .so 加载，每个命令回调会有 Module API 调用的额外开销，且与 Redis 主代码解耦后维护版本兼容性复杂。直接在命令路径插桩是最低侵入、最低开销的方式。

**Q：同步记录会不会因为统计结构本身的内存问题影响 Redis？**
> 布隆过滤器控制内存：100万 Key 仅占 1.2MB（参见 R2）。计数器只为布隆过滤器命中的 Key 分配，实际热 Key 数量远小于全量 Key，计数器总内存可控。
