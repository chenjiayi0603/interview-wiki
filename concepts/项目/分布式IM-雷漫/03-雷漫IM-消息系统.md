## 一、消息推送流程

### 1.1 总体流程

```
┌──────────────┐
│ 业务服务/    │
│ MsgServer产生│
│   消息       │
└─────┬────────┘
      │
      ▼
┌──────────────┐
│ 消息入存储/  │
│  推送队列    │
└─────┬────────┘
      │
      ▼
┌──────────────┐
│ PushServer   │
│ 消费队列     │
└─────┬────────┘
      │
      ▼
┌──────────────────────┐
│ 判断用户在线/离线状态  │
├────────┬─────────────┤
│  在线   │    离线     │
│  直接推  │  离线存储   │
│  送网关  │  + 第三方推  │
└────────┴─────────────┘
```

### 1.2 为什么在线推送也要走队列？

消息路径 `MsgServer → **队列** → PushServer → 在线推送` 看起来多绕了一步，但这是有意为之：

**原因一：MsgServer 不持连接，无法直接推**

MsgServer 是业务逻辑层，**它不知道用户连在哪台 Access 网关上**。连接信息（accnodeidentify）存在 Redis 的状态 Hash 里，只有 PushServer 负责查这个路由。MsgServer 如果自己做推送，就要同时持有业务逻辑 + 路由逻辑 + 连接管理，职责耦合。

**原因二：统一在线/离线路径，避免状态竞态**

如果不走队列，在线推送有两种做法：

| 做法 | 问题 |
|------|------|
| MsgServer 直接调 PushServer RPC | MsgServer 查时用户在线，RPC 到达前用户断了，消息谁负责？ |
| MsgServer 自己查路由直接推 | 推一半宕机，消息丢了没人知道 |

统一走队列后，**MsgServer 只做一件事：写 MongoDB + 扔队列**。PushServer 消费时才查 Redis 状态，这时候的状态才是准确的，不会出现"查到在线但推时已离线"的竞态。

**原因三：削峰填谷 + 容灾**

| 场景 | 无队列 | 有队列 |
|------|--------|--------|
| 瞬间消息量暴增（如群聊 @所有人） | PushServer 被打满，消息超时丢弃 | 队列缓冲，PushServer 按能力消费 |
| PushServer 宕机重启 | 推送中的消息全部丢失 | 消息留在队列中，重启后继续消费 |
| 后端维护灰度发布 | 需停服或做复杂的流量控制 | 队列天然解耦，PushServer 逐个重启无损 |

**原因四：批量推送优化**

PushServer 从队列批量拉取消息后，**按目标网关分组**，同一网关的消息合并发送。如果没有队列，MsgServer 逐条调 PushServer，就失去了聚合推送的机会。

```
无队列：MsgServer → PushServer(单条) → Access × 999次
有队列：MsgServer → [队列] → PushServer(批量拉取→分组→合并) → Access × N次(网关数)
```

### 1.3 队列的代价与选型

#### 1.3.1 引入队列的代价

| 代价 | 说明 | 影响程度 |
|------|------|---------|
| **增加时延** | 消息多经过一次序列化/网络/反序列化，内存队列 ~0.1ms，磁盘队列（如 Kafka）~2-5ms | 低（相对 DB 写入 5ms+，可接受） |
| **部署复杂度** | 多维护一个中间件集群，需配置、监控、扩缩容 | 中 |
| **硬件成本** | 队列集群需要额外的机器和内存，Kafka/RocketMQ 至少 3 节点起 | 中 |
| **运维成本** | 需关注堆积告警、消费延迟、磁盘水位、Rebalance 等 | 中 |
| **故障排查** | 出问题时多了一层链路：是 MsgServer 生产慢还是 PushServer 消费慢？ | 低 |

**是否需要队列，取决于场景**：
- 如果系统规模小（单机万级连接），用 Redis List 做轻量队列就够了，无需引入 Kafka/RocketMQ
- 千万级系统，队列带来的稳定性和削峰能力远大于其代价

#### 1.3.2 RocketMQ vs Kafka 选型

IM 推送场景对队列的要求：

| 需求 | IM 推送要求 |
|------|------------|
| 延迟 | ≤ 5ms（端到端 30ms 内，队列不能吃掉太多预算） |
| 吞吐 | 万级 TPS |
| 可靠性 | 不能丢消息（用户发消息丢了不能接受） |
| 有序性 | 同一会话的消息最好有序 |
| 重试 | 推送失败需要自动重试 |

| 维度 | Kafka | RocketMQ |
|------|-------|---------|
| **延迟** | ~2-5ms（依赖 fsync + page cache） | ~1-2ms（优化了实时性） |
| **吞吐** | 百万级 TPS（更高） | 十万级 TPS（够用） |
| **消息可靠性** | 依赖 ack 配置，需谨慎调优 | 同步刷盘 + 主从同步，可靠性更高 |
| **重试机制** | 需自行实现死信队列 | 内置重试队列 + 死信队列 |
| **消息有序** | 单 partition 内有序 | 单队列内有序，支持全局顺序 |
| **运维复杂度** | ZooKeeper/KRaft + broker | NameServer + broker，更轻量 |
| **社区活跃度** | 极高 | 高（阿里主导，国内 IM 场景多） |

**IM 推送场景推荐 RocketMQ**：

原因：
1. **延迟更低**：RocketMQ 的实时消息延迟通常比 Kafka 低 1-3ms，IM 场景对延迟敏感
2. **内置重试机制**：推送失败后 RocketMQ 自动重试，不需要额外开发死信队列
3. **消息轨迹**：内置消息轨迹能力，排查"消息发了但没收到"的问题更方便
4. **事务消息**：如果后续需要"消息入库 + 入队列"的事务一致性，RocketMQ 原生支持

**选 Kafka 的场景**：
- 消息量极大（百万 TPS 以上）
- 同时承担日志/监控/大数据管道职责（复用集群）
- 团队 Kafka 运维经验更丰富

> **实际项目中选型的考量**：如果团队已经有 Kafka 基础设施（如用于日志收集），复用 Kafka 做推送队列可以节省运维成本，加 1-2ms 延迟可以接受。如果是从零搭建，RocketMQ 更适合 IM 场景。

### 1.4 RocketMQ 存储与配置详解

#### 1.4.1 存储模型：内存 + 磁盘混合

RocketMQ **不是纯内存也不是纯磁盘**，而是 **内存映射文件（MappedByteBuffer）+ 磁盘持久化**：

```
写入路径：
  生产者 → Broker → MappedByteBuffer(内存映射) → 异步/同步刷盘 → CommitLog(磁盘)

读取路径：
  消费者 → Broker → ConsumeQueue(磁盘) → 定位 offset → MappedByteBuffer 读 CommitLog → 返回
```

| 组件 | 存储位置 | 作用 |
|------|---------|------|
| **CommitLog** | 磁盘（顺序写） | 消息本体，所有消息写入同一个文件，顺序追加 |
| **ConsumeQueue** | 磁盘（固定大小） | 索引文件，记录每条消息在 CommitLog 中的 offset + size + tag hash |
| **IndexFile** | 磁盘 | 可选索引，按 key 或时间查询消息 |

**关键特性**：
- CommitLog **顺序写**（比随机写快 10 倍），这是 RocketMQ 高吞吐的核心
- **MappedByteBuffer** 映射 CommitLog，读写都在内存中完成，刷盘异步进行
- 消费时先读 ConsumeQueue（轻量索引），再通过内存映射读 CommitLog，**大部分场景下等价于内存读写**

#### 1.4.2 刷盘策略

| 策略 | 写入路径 | 可靠性 | 吞吐 | 适用场景 |
|------|---------|--------|------|---------|
| **ASYNC_FLUSH**（异步刷盘） | 写入 PageCache 即返回，后台刷盘 | 可能丢毫秒级数据（Broker 宕机） | **最高** | IM 消息可接受（业务层有重传） |
| **SYNC_FLUSH**（同步刷盘） | 写入 CommitLog 落盘才返回 | 不丢消息 | 较低（约 1/3） | 金融、交易类 |

> IM 场景通常用 **ASYNC_FLUSH**，因为消息可靠由业务层保证（MsgServer 存 MongoDB + 客户端 ACK 重传），队列层不需要同步刷盘。

#### 1.4.3 主从同步

| 同步模式 | 说明 | 适用 |
|---------|------|------|
| **SYNC_MASTER** | Master 写入后等待 Slave 确认才返回 | 不丢消息，延迟稍高 |
| **ASYNC_MASTER** | Master 写入即返回，Slave 异步复制 | 高吞吐，主切从可能丢少量消息 |

#### 1.4.4 整体架构流程

```
                            ┌──────────────────────────────────────────────────────────┐
                            │                     RocketMQ Broker                      │
                            │                                                          │
                            │  ┌──────────────────────────────────────────────────┐     │
  MsgServer ──生产──▶       │  │                 CommitLog (磁盘)                  │     │
   (单聊/群聊)              │  │   [msg1][msg2][msg3][msg4][msg5]...[msgN]         │     │
                            │  │    ↑ 顺序写 (MappedByteBuffer 内存映射)            │     │
                            │  └──────────────────────┬───────────────────────────┘     │
                            │                         │                                │
                            │                         ▼                                │
                            │  ┌──────────────────────────────────────────────────┐     │
                            │  │              ConsumeQueue (磁盘)                   │     │
                            │  │   [offset1][offset2][offset3]...[offsetN]         │     │
                            │  │   每个队列独立一个文件，定长条目                      │     │
                            │  └──────────────────────────────────────────────────┘     │
                            │                         │                                │
                            │                         ▼                                │
                            │  ┌──────────────────────────────────────────────────┐     │
                            │  │           主从同步 (Master → Slave)               │     │
                            │  │   Master: 处理生产+消费，异步/SYNC 复制给 Slave    │     │
                            │  │   Slave: 只读副本，Master 宕机后自动切换          │     │
                            │  └──────────────────────────────────────────────────┘     │
                            └──────────────────────────────────────────────────────────┘
                                         │
                            ┌────────────┴────────────┐
                            ▼                         ▼
                    消费成功                     消费失败
                         │                         │
                         ▼                         ▼
                  PushServer 推送            ┌──────────────────────┐
                  在线→网关→客户端            │  重试队列 (RETRY)      │
                  离线→存储+APNs             │  重试 1→2→4→...→16 次  │
                         │                  │  延时等级逐步递增       │
                         │                  └──────────┬───────────┘
                         │                             │
                         │                    重试耗尽仍失败
                         │                             │
                         │                             ▼
                         │                     ┌──────────────────────┐
                         │                     │ 死信队列 (DLQ)       │
                         └─────────────────────│  %DLQ%PushServerGroup│
                                               │  人工排查 + 补偿      │
                                               └──────────────────────┘
```

**生产路径**（MsgServer → CommitLog）：
1. MsgServer 生产消息，Broker 写入 **MappedByteBuffer**（内存映射，等价于写内存）
2. 后台线程异步刷盘到 **CommitLog**（顺序写磁盘，速度 ≈ 600MB/s）
3. 同时生成 **ConsumeQueue** 索引条目（定长 20 字节：offset + size + tag hash）
4. Master 将消息同步/异步复制到 **Slave**

**消费路径**（MQ → PushServer → 客户端）：

```
纠正：MongoDB 是 MsgServer 写的，不是 PushServer

MsgServer 收到客户端消息
  │
  ├─①─ 写 MongoDB（持久化，此时 msgState=0）
  │
  └─②─ 入 MQ 队列（消息投递给 PushServer）
              │
              ▼
         PushServer 消费 MQ
              │
              ├─③─ 拉取消息（RocketMQ 底层是长轮询 Pull，API 包装成 Push）
              │
              ├─④─ 查 Redis 用户在线状态（accnodeidentify）
              │
              ├─⑤─ 判断在线/离线
              │
              ├─ 在线 ──⑥─→ 推送 Access 网关
              │                 │
              │                 ├─ 网关确认收到 → ⑦ ACK MQ ⭐
              │                 │
              │                 └─ 网关推客户端 → ⑧ 客户端回业务 ACK
              │                                   （更新 msgState=2）
              │
              └─ 离线 ──→ ⑨ 标记离线 + APNs/FCM → ⑩ ACK MQ
```

**关于"拉取还是推送"**：RocketMQ 的 API 叫 `pushConsumer`，但底层实现是 **长轮询 Pull**——PushServer 不断向 Broker 发拉取请求，如果没有消息就 hold 住连接等待（默认 15s 长轮询）。对业务代码来说表现为"推送"效果，本质是 Pull。Kafka 同理。

**ACK 的时机——核心问题**：

```
PushServer 拉取到消息
  │
  ├─ 查在线 → 在线 → 推送 Access 网关
  │                   ├─ 网关 TCP 确认收到 → ACK MQ  ✓
  │                   │   （网关确认 = 网关已接管投递责任）
  │                   │
  │                   └─ 网关拒绝/超时（用户断连）
  │                         → RECONSUME_LATER，MQ 重试
  │                         → 重试几次仍失败 → 标记离线
  │                         → ACK MQ + 走 APNs
  │
  └─ 查在线 → 离线 → 直接 ACK MQ + 走 APNs/FCM
```

| ACK 时机 | 效果 | 问题 |
|---------|------|------|
| ❌ 拉取消息后立即 ACK | 不等推送结果 | PushServer 推送前宕机，消息无人处理，MQ 已标记完成 |
| **✓ 网关确认后 ACK** | **网关已接收，投递责任从 MQ 转移到网关** | **最佳平衡点** |
| ❌ 等客户端确认后 ACK | 确保客户端真收到 | 离线用户卡整条队列，群聊 999 人不可行 |

**为什么网关确认后 ACK 是最佳时机**：
- 网关确认 = PushServer 到 Access 网关的 TCP 写入成功，**网关已接管推送责任**
- 网关到客户端的投递由网关负责（重试 + 离线检测）
- 即使网关到客户端失败，消息在 MsgServer 的 MongoDB 中已持久化，客户端重连后拉取补齐
- MQ 的职责是"MsgServer → PushServer → 网关"的可靠传递，不是"网关 → 客户端"

#### 1.4.6 RocketMQ 核心特性与 IM 推送的匹配

| 特性 | 说明 | IM 场景怎么用 |
|------|------|-------------|
| **事务消息** | 消息生产与本地事务原子提交 | MsgServer 写 MongoDB 和发消息原子操作 |
| **延时消息** | 内置 18 个延时等级 | 推送失败后延时重试（5s/10s/30s...） |
| **重试队列** | 消费失败自动进入重试队列，最多重试 16 次 | 在线推送失败自动重试，超过次数进死信队列人工处理 |
| **死信队列** | 重试耗尽进入死信队列（%DLQ%+consumerGroup） | 多次推送失败的消息，人工排查 |
| **消息轨迹** | 记录消息从生产到消费的全路径 | 排查"消息发了但没收到" |
| **Tag 过滤** | 消费者按 tag 选择性消费 | 区分单聊消息/群聊消息/通知，不同 PushServer 消费不同 tag |
| **批量消息** | 一次发送/消费多条消息 | PushServer 批量拉取后做聚合推送 |

#### 1.4.7 IM 推送场景的 RocketMQ 实际设计

**Topic 设计**：

| Topic | 用途 | 队列数 | Tag 划分 |
|-------|------|--------|---------|
| `im_push` | 推送消息 | 16（按用户 hash 路由） | 单聊=tag1, 群聊=tag2, 系统通知=tag3 |
| `im_push_retry` | 推送失败重试 | 4 | 按重试次数 |
| `im_sync` | 多设备同步 | 8 | 已读同步=tag1, 会话同步=tag2 |

**Consumer Group 设计**：

| Consumer Group | 消费哪个 Topic | 作用 |
|---------------|--------------|------|
| `PushServerGroup` | `im_push` | 负责在线推送、离线存储、第三方推送 |
| `SyncServerGroup` | `im_sync` | 负责多设备间的状态同步 |
| `DLQHandler` | `%DLQ%PushServerGroup` | 死信消息人工处理 |

**消息体结构**（Protobuf 序列化）：

```protobuf
message PushMessage {
    int64  msg_id = 1;         // 消息全局 ID
    int64  from_id = 2;        // 发送者
    int64  dst_id = 3;         // 接收者/群 ID
    int32  dst_type = 4;       // 1=单聊 2=群聊
    int32  cmd_type = 5;       // 命令字（4501=聊天 4505=通知 ...）
    bytes  content = 6;        // 消息内容（加密后）
    int32  retry_count = 7;    // 已重试次数
    map<string, string> ext = 8; // 扩展属性
}
```

**消息生产（MsgServer 侧）**：

```java
// MsgServer 写 MongoDB + 发消息到队列，事务保证一致性
SendResult result = producer.sendMessageInTransaction(
    new Message("im_push", "tag1", pushMsg.toByteArray()),
    localTransactionExecutor  // 事务回调：写 MongoDB
);
```

**消息消费（PushServer 侧）**：

```java
// PushServer 批量拉取后聚合推送
consumer.registerMessageListener((MessageListenerConcurrently) (msgs, context) -> {
    // 1. 按 accnodeidentify 分组
    Map<String, List<MessageExt>> grouped = groupByGateway(msgs);
    
    // 2. 对每台网关批量推送
    for (Map.Entry<String, List<MessageExt>> entry : grouped.entrySet()) {
        batchPush(entry.getKey(), entry.getValue());
    }
    
    // 3. 推送失败的消息返回 RECONSUME_LATER 进重试队列
    return ConsumeConcurrentlyStatus.CONSUME_SUCCESS;
});
```

## 二、未读数设计

### 2.1 未读计算公式

**单聊**：
```
未读数 = count(
  msgId > lastReadMsgId AND
  fromId != self AND
  msgState != 4
)
```

**群聊**：
```
未读数 = count(
  cmdType IN [4501, 4505] AND
  fromId != self AND
  msgId > lastReadMsgId AND
  msgState != 4
)
```

### 2.2 关键规则

| 规则 | 说明 |
|------|------|
| `msgState != 4` | 排除撤回消息（撤回不纳入未读数） |
| `fromId != self` | 排除自己发的消息 |
| `cmdType` | 只统计聊天/通知类消息 |
| 已读位置 | `lastReadMsgId` 按设备维护 |

### 2.3 已读/未读实现

```
客户端：
  - 本地维护 lastReadMsgId（用户已读到的位置）
  - 上报已读位置时发送消息状态 (cmd=4005)
  - Ios上报本地未读消息数 (cmd=4011)

服务端：
  - 收到已读上报 → 更新 lastReadMsgId
  - 计算未读数时从个人已读位置开始统计
  - 自己发的消息不纳入未读计数
  - 撤回的消息不参与未读数计算
```

## 四、群聊瓶颈与优化

### 4.1 瓶颈分析

```
1000人群聊，发一条消息：
  写消息表：1次DB操作
  推送给999人：999次推送
  每次推送需要：查连接位置 + 发送

→ 随着群人数增加，推送量线性增长
→ 1000人群消息 P99 延迟 200ms
```

### 4.2 优化方案

| 手段 | 说明 |
|------|------|
| **本地聚合** | 同一连接服务器的用户批量推送，减少网络往返 |
| **写扩散** | 群消息写入每个用户的收件箱（离线场景） |
| **消息序号预分配** | `session_msgseq` 预分配序号段，减少分布式协调 |
| **增量推送** | 只推送增量消息，全量拉取走离线通道 |

### 4.3 性能数据

| 场景 | 吞吐量 | P99 延迟 |
|------|--------|---------|
| 单聊消息 | 50,000条/秒 | 30ms |
| 群聊（100人） | 5,000条/秒 | 50ms |
| 群聊（1000人） | 500条/秒 | 200ms（需优化） |
| 离线消息拉取 | 20,000条/秒 | 20ms |
