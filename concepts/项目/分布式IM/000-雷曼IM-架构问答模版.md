## 一、项目复盘与架构设计

**考察点**：业务理解深度 & 架构设计能力

> **候选项目**：雷漫网络分布式 IM 消息系统（2019.11–2021.4，后台架构负责人）

---

### 🎯 项目背景

雷漫 IM 是一款面向 900 万+ 注册用户的即时通讯系统，覆盖 Web、iOS、Android 三端。我接手时系统存在三个核心问题：

| 问题 | 表现 | 根因 |
|------|------|------|
| **单机连接瓶颈** | 原有 Nginx 方案单机最多 10 万连接，扩无可扩 | 每连接 ~16KB 内存、worker_connections 上限 |
| **群聊消息延迟高** | 1000 人群聊 P99 延迟 200ms+，随人数线性恶化 | 每条消息逐人推送 999 次 RPC |
| **加密通道性能差** | 全链路 RSA 加密，CPU 占用 30%，重连风暴打满 CPU | 每次重连都要 RSA 解密 + DB 查询 |

**目标**：自研 C++ 接入层，单机支撑百万连接，消息 P99 < 50ms，加密 CPU 降到 10% 以下。

---

### 🚧 核心难点

| 难点 | 具体表现 | 我的方案 |
|------|---------|---------|
| **百万连接内存压降** | 默认 TCP buffer 下百万连接吃 ~14GB，16G 机器扛不住 | `tcp_rmem/wmem` min 从 4KB → 1KB，conntrack 扩容 |
| **群消息推送量线性增长** | 万人群在线 3000 人，每条消息 3000 次 RPC | 按网关节点聚合推送，3000 次 → ~10 次 |
| **消息序列号高并发** | 每秒几十万次 msgseq 分配，MongoDB 扛不住 | Redis Lua 原子 INCR + MongoDB 批次预分配 |
| **未读数设计陷坑** | Redis INCR 三大致命缺陷（写扩散/撤回丢失/故障清零） | 已读点 + MongoDB count 方案 |
| **加密通道重连风暴** | 大量用户同时重连，每个都走 RSA 解密（0.5ms/次） | Token + Redis 缓存 sessionkey，重连免 RSA |

**数据流分五条路径**：

| 路径 | 流向 | 说明 |
|------|------|------|
| **🟢 登录认证** | Client → Access → Login → Redis | ECDH+RSA+AES 协商，Token 缓存到 Redis |
| **🔵 消息上行** | Client → Access → MsgServer → MongoDB | MsgServer 写 DB 持久化后即返回 ACK，不持连接 |
| **🟠 消息投递** | MsgServer → RocketMQ → PushServer | MQ 解耦：MsgServer 写完 DB 就投递 MQ，不等推送结果 |
| **🔴 在线推送** | PushServer → Access → Client | 批量拉取 → 查 Redis 在线 → 按网关聚合 → 批量 RPC → 网关本地 fanout |
| **🟣 离线推送** | PushServer → 离线队列 → OfflinePushWorker → APNs/FCM → Client | PushServer 查得离线 → ACK MQ → 投递离线队列（不等结果）→ Worker 异步调 APNs/FCM（50-200ms）→ 用户点通知上线补拉 |

**关键设计决策**：

| 决策项 | 方案 | 理由 |
|-------|------|------|
| **网络模型** | C++ 自研 epoll ET + 多进程 Worker + SO_REUSEPORT | Nginx 每连接 ~16KB 太重；ET 比 LT 减少 60%+ 系统调用；多进程隔离崩溃 |
| **消息存储** | MongoDB 分片集群 | 对比 MySQL 方案：CPU 16:1、内存 16:1、磁盘 3.3:1，IM 写多读少场景 MongoDB 天然优势 |
| **消息队列** | RocketMQ（ASYNC_FLUSH + ASYNC_MASTER） | 比 Kafka 延迟低 1-3ms，内置重试队列+死信队列，事务消息支持 |
| **加密方案** | Token + ECDH + RSA + AES 四层配合 | Token 管效率（重连免 RSA），ECDH 管前向安全，AES-NI 硬件加速 |
| **父子进程通信** | 共享内存队列（替代 Unix socketpair） | 零 syscall、零拷贝、可配置到 MB 级 |
| **未读数方案** | 已读点 + MongoDB count（放弃 Redis INCR） | 避免写扩散、撤回 DECR 丢失、Redis 故障清零三大缺陷 |

### 🔌 RocketMQ 层 · 部署规格与性能模型

> **面试时主动抛出**："我们这层 MQ 看似多了一跳，实际上它承担的职责远不止削峰解耦——没有它就没有 3000→~10 次 RPC 的聚合推送优化。"

#### 📋 核心数据速查

| 维度 | 核心数据 |
|------|---------|
| **四职责** | 解耦（MsgServer 不需知 PushServer 地址）、削峰（瞬时尖峰 MQ 缓冲）、容错（宕机重启不丢消息）、聚合推送（3000→~10 RPC） |
| **增加时延** | **~1-2ms**，但净收益是聚合推送省了 **8970ms**（3000次 RPC×3ms → 10次 RPC×3ms），群聊 P99 从 200ms→50ms |
| **机器/节点** | **4 台** 8 核 16GB 机器，2M-2S 架构 + 2 NameServer（混部） |
| **QPS** | 单 Broker **10万 TPS**，集群 **20万 TPS**，雷漫实际峰值 ~55K（留有 3-4 倍余量） |
| **关键配置** | ASYNC_FLUSH + ASYNC_MASTER、消费线程 20→64 弹性伸缩、消息保留 72h |

---

#### 为什么这一层必需

| 职责 | 说明 | 没有这一层的后果 |
|------|------|----------------|
| **解耦** | MsgServer 不需要知道 PushServer 地址，只管往 MQ 投递 | MsgServer 必须维护 PushServer 路由表，双方强耦合，任一方变动都要联动 |
| **削峰** | 瞬时流量尖峰时 MQ 缓冲，PushServer 按自身能力匀速消费 | 晚高峰群聊 @所有人 瞬时打满 PushServer，超时丢弃，消息丢失 |
| **容错** | PushServer 宕机期间消息不丢，重启后继续消费 | PushServer 宕机时正在推送的消息全部丢失，MsgServer 无重试机制 |
| **聚合推送** | PushServer 批量拉取后按 `accnodeidentify` 分组，同网关消息合并为 1 次 RPC，实现 3000→~10 次 RPC | 每条消息逐人推送，1000 人群 = 999 次 RPC，P99 200ms+，CPU 100% |

> 去掉这层的话，MsgServer 就得同步 RPC 调用 PushServer：**延迟上升**（同步等待推送完成）、**强耦合**（双方地址绑定）、**无削峰能力**、**失去聚合推送机会**，整条链路退化成普通 RPC 调用链。

---

#### ⚡ 聚合推送详解：3000 次 RPC → ~10 次

这是群聊消息推送的核心优化，也是"为什么必须走 MQ"的关键论据。

**问题：群聊消息的"扇出爆炸"**

```
场景：一个 1000 人群，3000 个成员在线（多端登录）

优化前（逐人推送）：
  PushServer 取出消息 → 对每个在线成员逐一调 RPC
  张三（连在网关-A）→ RPC #1
  李四（连在网关-B）→ RPC #2
  王五（连在网关-A）→ RPC #3   ← 同一台网关！重复调！
  ...共 3000 次 RPC，每次 ~3ms

  总耗时 ≈ 3000 × 3ms = 9000ms（串行）/ 200ms+（并行但 CPU 打满）
  P99 延迟 200ms+，PushServer CPU 100%
```

**关键洞察**：多个用户连在**同一台 Access 网关**上，不需要对每个人单独推。把同一台网关上的所有目标用户打包，**一次 RPC** 推过去，网关自己在本地分发给每个连接。

```
优化后（按网关聚合推送）：

  PushServer 批量拉取群消息
    │
    ├─① 查 Redis，获取每个目标用户的 accnodeidentify（连在哪台网关）
    │
    ├─② 按网关分组：
    │    网关-A：1200 个用户 → 打包成 1 次 RPC
    │    网关-B：800 个用户  → 打包成 1 次 RPC
    │    网关-C：400 个用户  → 打包成 1 次 RPC
    │    网关-D：200 个用户  → 打包成 1 次 RPC
    │    ...
    │    共 ~10 台网关 = ~10 次 RPC
    │
    └─③ 每台网关收到后，本地 fanout 给所有目标连接
         （网关注入每个连接对应的 TCP buffer，纯内存操作，微秒级）

  总耗时 ≈ 10 × 3ms = 30ms
  P99 降到 50ms
```

**为什么网关本地 fanout 是零网络开销？**

Access 网关本身就持有所有连到它的用户的长连接（epoll 管理着所有 fd）。PushServer 一次 RPC 把"消息 + 目标用户列表"发给网关后，网关做的事是：

```
for each 目标用户 in 用户列表:
    fd = connection_map[用户ID]      // 查内存哈希表，O(1)
    write(fd, 消息)                   // 往内核 TCP buffer 写，不涉及网络往返
```

整个过程是**纯本机内存操作 + 内核写缓冲**，不产生任何额外的网络往返。这就是为什么 3000 次网络 RPC 可以被压缩成 ~10 次——因为网络开销只在 PushServer→网关这一跳，网关→客户端是本地操作。

**数学换算**：

```
                       优化前          优化后          节省
PushServer→网关 RPC    3000 次         ~10 次          2990 次
每次 RPC 耗时          ~3ms            ~3ms            —
总网络耗时             ~9000ms          ~30ms           8970ms
P99 延迟              200ms+          50ms             -75%
PushServer CPU        100%            30%              -70%

MQ 引入的代价         —               +1~2ms          （净收益 8970ms >> 1-2ms）
```

**为什么必须走 MQ 才能聚合？**

如果 MsgServer 直接 RPC 调 PushServer（不走 MQ），MsgServer 一条一条地投递消息，PushServer 只能一条一条地处理——**没有"批量拉取"的机会**。

```
无 MQ：MsgServer → PushServer（逐条，每次一条消息）
        → PushServer 没法批量分组，只能对一条消息独立推送

有 MQ：MsgServer → MQ（批量堆积）→ PushServer（批量拉取，一次几十上百条）
        → PushServer 拿到一批消息后，按「消息×目标用户」二维聚合
        → 同一网关同一批消息合并为 1 次 RPC
```

**单聊为什么不需要聚合？**

单聊只有一个接收者，MsgServer 直接写 MongoDB + 投 MQ 就完了，PushServer 查到一个在线用户 → 一次 RPC。聚合的收益在群聊场景才会爆发——人数越多、在线率越高，聚合收益越大。

| 场景 | RPC 次数（无聚合） | RPC 次数（聚合后） | 收益 |
|------|-------------------|-------------------|------|
| 单聊 | 1 次 | 1 次 | 无（不需聚合） |
| 100 人群（在线 80 人，3 台网关） | 80 次 | ~3 次 | 96% ↓ |
| 1000 人群（在线 3000 人，10 台网关） | 3000 次 | ~10 次 | 99.7% ↓ |

---

#### 引入 MQ 的代价

| 代价维度 | 具体数值 | 说明 |
|---------|---------|------|
| **增加时延** | **~1-2ms**（端到端） | 消息多经过一次序列化→网络→反序列化。ASYNC_FLUSH 下写入 PageCache 即返回，实际延迟 ≈ 网络 RTT |
| **硬件成本** | **4 台机器**（8 核 16GB） | 2M-2S 最小生产集群。如果复用已有基础设施可省 |
| **运维成本** | **1 人·天/月**（平均） | 关注：堆积告警、消费延迟、磁盘水位、Rebalance。RocketMQ 运维复杂度低于 Kafka（无 ZooKeeper 依赖） |
| **排查复杂度** | **多一层链路** | 出问题时需区分：MsgServer 生产慢 or PushServer 消费慢？→ 通过 RocketMQ 内置消息轨迹 + 消费位点偏移量定位 |

**时延换算**：MQ 增加 ~1-2ms，但聚合推送把群消息扇出从 **3000 次 RPC（每次 ~3ms）= 9000ms → ~10 次 RPC = 30ms**，节省了 **8970ms**，净收益巨大。**这 1-2ms 的代价换来的是群聊 P99 从 200ms 降到 50ms，完全值得。**

#### 集群部署规格

| 项目 | 规格 |
|------|------|
| **集群模式** | 2 Master + 2 Slave（2M-2S），两组主从 |
| **机器配置** | 每节点 8 核 16GB 内存，500GB SSD |
| **总节点数** | **4 个 Broker** + **2 个 NameServer**（NameServer 轻量，可混部） |
| **纯物理机数** | **4 台**（NameServer 与 Broker 混部） |
| **NameServer** | 无状态、可水平扩展，2 节点互为主备 |
| **刷盘策略** | **ASYNC_FLUSH**（写入 PageCache 即返回，后台刷盘） |
| **主从同步** | **ASYNC_MASTER**（Master 写入即返回，Slave 异步复制，吞吐优先） |
| **消息保留** | CommitLog 保留 **72 小时**（磁盘空间够用 + 故障回溯窗口） |

#### 吞吐能力

| 指标 | 数值 | 说明 |
|------|------|------|
| **单 Broker 写 TPS** | **~100,000 条/秒** | ASYNC_FLUSH 下，顺序写 CommitLog，接近磁盘顺序写带宽（~600MB/s）。单条消息 ~1KB 时可达 10万+ |
| **集群总写 TPS** | **~200,000 条/秒** | 2 Master 并行写入，线性扩展 |
| **单 Broker 消费 TPS** | **~100,000 条/秒** | 批量拉取 + MappedByteBuffer 内存映射读，实际接近内存带宽 |
| **雷漫 IM 实际峰值** | **~50,000 条/秒**（单聊最高） + **~5,000 条/秒**（群聊） | 集群能力是峰值的 **3-4 倍**，留有充足余量 |
| **消费线程配置** | `consumeThreadMin=20`，`consumeThreadMax=64` | CPU 有压力时自动弹到 64 线程 |

#### Topic 与队列设计

| Topic | 用途 | 队列数 | Tag 划分 | Consumer Group |
|-------|------|--------|---------|---------------|
| `im_push` | 推送消息（主链路，**唯一 Topic**） | **16**（按 user hash 路由） | 单聊=tag1, 群聊=tag2, 系统通知=tag3 | `PushServerGroup` |

**设计原则：一个 Topic 足够，不搞过度设计。**

| 需求 | 为什么不需要单独建 Topic | 实际怎么解决 |
|------|------------------------|-------------|
| **推送失败重试** | RocketMQ 内置重试机制：消费返回 `RECONSUME_LATER` → 自动进入 `%RETRY%PushServerGroup`，按延时等级阶梯重试（1s→5s→10s→30s…），16 次耗尽进 `%DLQ%` 死信队列。不需要自建 retry topic | 消费失败 return `RECONSUME_LATER`，RocketMQ 自动处理 |
| **多设备同步** | 消息推送本身就是"发到所有设备"——单聊推给双方所有端，群聊推给所有成员所有端。每个设备在 MongoDB 独立维护 `lastReadMsgId`，上线后按自己的位点补拉。不需要单独的 sync topic | 同一推送链路送达所有设备，各端独立管理已读进度 |
| **单聊/群聊/通知区分** | RocketMQ Tag 机制天然支持——生产时打 tag，消费时按 tag 过滤，同一 Topic 内逻辑隔离 | Tag 过滤：`tag_c2c` / `tag_c2g` / `tag_notify` |
| **优先级隔离** | 不同 Tag 绑定不同消费线程池即可（见 §四 优先级管控），不需要拆 Topic | P0 单聊 60% 线程，P3 通知 10% 线程 |

> **面试话术**："我们就一个 Topic，16 个队列按 user hash 路由。重试靠 RocketMQ 内置的 `RECONSUME_LATER`，多设备同步走同一条推送链路、各端独立维护 MongoDB 已读位点，Tag 区分消息类型并绑定不同优先级线程池。RocketMQ 内置能力够用，不搞过度设计。"

#### 面试追问预案

| 追问 | 回答 |
|------|------|
| "为什么不用 Kafka？" | Kafka 吞吐更高（百万级 TPS）但延迟高 1-3ms，且需自建死信队列。IM 场景十万级 TPS 足够，RocketMQ 内置重试+死信+事务消息更贴合推送场景。如果团队已有 Kafka 集群，复用也可以——加 1-2ms 延迟可接受。 |
| "为什么不用 Redis List？" | 小规模（万级连接）可以用 Redis List 做轻量队列。千万级系统需要持久化保证（Redis RDB 间隔丢数据）、消费者组管理（Redis 需自建）、重试机制（Redis 需自建），RocketMQ 开箱即用。 |
| "ASYNC_FLUSH 丢消息怎么办？" | MQ 层丢消息可接受，因为消息在 MsgServer 的 MongoDB 中已持久化。RocketMQ 宕机丢的消息由客户端重传兜底（clientMsgId 去重）。MQ 的职责是"削峰+分发"，不是"永久存储"。 |
| "4 台机器够吗？" | 雷漫 IM 峰值 ~55,000 条/秒，2M-2S 集群有 ~200,000 条/秒的能力，3-4 倍余量。扩容只需加 Broker + 扩队列数，Topic 队列数 16→32 可直接翻倍并行消费度。 |

### 🔄 架构反思

**做得好的**：
- **epoll ET + 多进程 Worker 选型正确**，百万连接压测通过，CPU 空闲 5-10%
- **msgseq 预分配方案**让 99.99% 消息不碰 MongoDB，设计上知道会有 seq 断号但选择接受这个 trade-off
- **统一走 MQ 推送**带来了削峰、解耦、聚合推送、容灾四大收益

**可以优化的**：
1. **MongoDB 单 Primary 写瓶颈**：当前 shard 写 QPS 上限 2-5 万，业务增长到千万 DAU 时需要更多分片或考虑 TiDB 等 NewSQL 方案
2. **万人群带宽爆炸**：在线 3000 人时单条消息出口带宽 3MB，全在线极端情况 10MB/条。需要引入令牌桶限流 + 超载降级（只推 @消息）
3. **长时间离线未读数**：离线半年用户重新登录时 MongoDB count 可能 > 100ms，需要引入快照辅助
4. **seq 断号客户端补拉**：服务重启浪费未用完的 seq 段（最多 10000），触发客户端批量补拉请求增加 MongoDB 读压力。活跃群应动态加大批次到 50000
5. **conntrack 表是个容易被忽略的坑**：百万连接下不调 `nf_conntrack_max` 会直接丢 SYN 包。生产需配置到 2M（详见故障排查故事）

**考察点**：性能优化 & 不停机迁移能力

> 雷漫 IM 是我从零主导架构设计的项目，以下从 **拆分思路 → 扩容策略 → 压测方案 → 平滑发布** 四个维度展开。

---

### 🔧 拆分思路：按职责分离，不是按微服务数量

很多人一上来就拆几十个微服务，我们踩过这个坑。雷漫 IM 拆成了 **4 个核心服务 + 共享基础设施**，每个服务有清晰的职责边界：

| 服务 | 职责 | 为什么不合并 |
|------|------|------------|
| **Access 网关** | 长连接管理、消息加解密、心跳、限流 | 连接管理是 IO 密集型，需要独立扩缩容；与业务逻辑解耦后，业务服务可以随意重启不影响连接 |
| **Login 服务** | 用户认证、Token 签发、Session 管理 | 认证逻辑独立演变（如从密码→短信→OAuth），不应耦合到消息路径 |
| **MsgServer** | 消息校验、写 MongoDB、入队列 | 业务逻辑层，**不持连接**。MsgServer 不知道用户连在哪台网关，只管"消息已安全存储 + 投递到 MQ" |
| **PushServer** | 消费 MQ、查在线状态、推送 | 推送是 CPU 密集型（查路由 + 序列化 + 网络 IO），需要独立扩容。批量聚合推送也在此层完成 |

**拆分原则**：
```
1. 按"变更频率"拆分：Access 网关稳定（只做转发），MsgServer 频繁迭代（业务逻辑）
2. 按"资源类型"拆分：IO 密集型（Access）与 CPU 密集型（PushServer）分开
3. 按"故障域"拆分：PushServer 宕机不影响 MsgServer 接收消息（MQ 缓冲解耦）
4. 不过度拆分：4 个服务够用，不要为了"微服务"而微服务
```

**为什么 MsgServer 不持连接、PushServer 不写 DB**：

```
MsgServer 只做两件事：
  ① 写 MongoDB（消息持久化）
  ② 投递 RocketMQ（将推送任务交给 PushServer）
  
不持连接的原因：
  - MsgServer 扩容不影响连接（连接在 Access 网关上）
  - MsgServer 重启不丢连接
  - 业务逻辑迭代频繁，频繁重启不影响用户

PushServer 不写 DB 的原因：
  - 消息已在 MsgServer 写入 DB，PushServer 只管投递
  - PushServer 故障重启后，消息在 MQ 中不丢
  - 职责单一，性能可预测
```

### 📈 集群扩容策略

**1. 连接预热（Access 网关扩缩容）**

```
问题：新扩容的 Access 节点刚上线就被流量打满，TCP 连接建立超时

方案：渐进式预热
  → 新节点启动后，Nginx upstream 权重设为 0（不分配新连接）
  → 内部预热连接池、加载路由表、建立到后端服务的 gRPC 连接（约 30s）
  → 健康检查通过后，Nginx 逐步上调权重（weight 1→5→10→与其他节点持平）
  → 旧节点缩容时，先标记 draining，等待已有连接自然断开（最长 5 分钟）
```

**2. 容量规划公式**

```
单 Access 节点容量 = 100 万连接（实际运行在 60-70 万，留 30% 余量）
PushServer 容量 = CPU 核数 × 单核推送 TPS（约 5000/核）

扩容触发条件：
  - Access 节点：当前连接数 > 集群总容量 × 0.7
  - PushServer：MQ 消费延迟 > 5s 持续 1 分钟
  - MsgServer：P99 延迟 > 50ms 持续 3 分钟

最小节点数 = 峰值连接数 / 单节点容量 × 2（冗余，一节点故障不影响）
```

**3. 连接池管理**

```go
// 每个服务维护到下游的连接池，避免扩容时新建连接风暴
// PushServer 到 Redis 的连接池配置
redis.NewClient(&redis.Options{
    PoolSize:     100,           // 连接池大小
    MinIdleConns: 10,            // 最小空闲连接（预热用）
    PoolTimeout:  3 * time.Second,
    IdleTimeout:  5 * time.Minute,
    MaxRetries:   3,
})
```

**4. 消息队列的扩缩容**

RocketMQ 消费者扩容需要注意 **Rebalance 风暴**：
- PushServer 新增节点 → Consumer Group 触发 Rebalance → 短暂暂停消费（几百 ms）
- 解决：静态分组分配，避免频繁 Rebalance
- 业务高峰期间**禁止扩缩容**（凌晨 2-4 点操作）

### ☸️ K8s 扩缩容操作（面试高频考点）

> **面试主动引导**："我们的服务全部容器化部署在 AWS EKS 上，利用 K8s HPA + Karpenter 实现了分钟级的自动弹性伸缩。高峰期自动扩容 20+ 节点，低峰期缩容到 5 节点，一个月省 40% 成本。"

#### 1. 三层弹性伸缩模型

K8s 的弹性伸缩从下到上分三层，面试时要能说清楚每层的职责和配合方式：

```
┌─────────────────────────────────────────────────────────┐
│  第一层：Pod 水平自动伸缩（HPA）                          │
│  作用：增减 Pod 副本数                                    │
│  粒度：秒级 ~ 分钟级                                      │
│  指标：CPU / 内存 / 自定义指标（MQ 积压数、QPS）           │
│  命令：kubectl autoscale deployment push-server --min=3 --max=20 --cpu-percent=70 │
├─────────────────────────────────────────────────────────┤
│  第二层：节点自动伸缩（Cluster Autoscaler / Karpenter）    │
│  作用：增减 Worker 节点                                   │
│  粒度：2-5 分钟                                           │
│  触发条件：Pod Pending（资源不足）、节点利用率低            │
│  平台：AWS Auto Scaling Group（ASG）或 Karpenter          │
├─────────────────────────────────────────────────────────┤
│  第三层：Spot Instance 中断处理                           │
│  作用：被回收的 Spot 实例上的 Pod 自动迁移                 │
│  保障：PDB + 多 AZ 部署 + 优先保证关键服务用 On-Demand    │
└─────────────────────────────────────────────────────────┘
```

**面试要点**：不要说"我们用 HPA"，要说"我们 HPA 基于 MQ 积压数的自定义指标做弹性，避免 CPU 指标滞后导致扩容不及时"。

#### 2. HPA（Horizontal Pod Autoscaler）— 弹性伸缩核心

**HPA 工作原理**（面试能画出流程图）：

```
HPA Controller（kube-controller-manager 内）
    │
    ├── 每 15s（--horizontal-pod-autoscaler-sync-period）轮询指标
    │
    ├── 调用 metrics-server 获取 Pod CPU/内存
    │   └── 或调用 custom-metrics-apiserver 获取自定义指标
    │
    ├── 计算期望副本数：
    │   desiredReplicas = ceil[currentReplicas × (currentMetricValue / desiredMetricValue)]
    │   例：当前 10 个 Pod，CPU 使用率 90%，目标 70%
    │       desiredReplicas = ceil[10 × (90 / 70)] = ceil[12.85] = 13
    │
    └── 更新 Deployment/StatefulSet 的 replicas 字段
        └── Deployment Controller 触发滚动更新
```

**雷漫 IM 的 HPA 配置实战**：

```yaml
# PushServer HPA — 基于 CPU + MQ 积压数双指标
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: push-server-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: push-server
  minReplicas: 3          # 最小保底 3 副本
  maxReplicas: 30         # 最大 30 副本（防止过度扩容）
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300   # 缩容稳定窗口 5 分钟
      policies:
      - type: Percent
        value: 10                       # 每分钟最多缩 10% 的 Pod
        periodSeconds: 60
    scaleUp:
      stabilizationWindowSeconds: 0     # 扩容不等待，立即扩容
      policies:
      - type: Percent
        value: 100                      # 每分钟最多翻倍扩容
        periodSeconds: 60
      - type: Pods
        value: 4                        # 每分钟最多加 4 个 Pod
        periodSeconds: 60
      selectPolicy: Max                 # 取两个策略中更激进的
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70          # CPU 利用率超过 70% 触发扩容
  - type: Pods
    pods:
      metric:
        name: mq_consumer_delay         # 自定义指标：MQ 消费延迟（秒）
      target:
        type: AverageValue
        averageValue: "5"               # 平均延迟超过 5 秒触发扩容
```

**为什么用双指标**（面试深度展示）：

| 指标 | 优势 | 劣势 |
|------|------|------|
| CPU 利用率 | 通用、稳定、metrics-server 内置 | 滞后：Pod 启动后 CPU 爬升需要时间；推模型的 PushServer CPU 利用率可能不线性反映负载 |
| MQ 积压数 | 直接反映推送压力，超前指标 | 需要部署 custom-metrics-adapter + 从 RocketMQ Exporter 采集 |
| **双指标配合** | CPU 兜底通用场景，MQ 积压应对突发尖峰 | 两个指标满足任意一个即触发扩容，取最大期望副本数 |

```
实际效果：
  晚高峰 @所有人 消息突发：
    CPU 指标滞后约 30-60s 才感知到负载上升
    MQ 积压指标在 5s 内触发扩容
  两者结合：MQ 积压指标先触发第一次扩容（3→6），
           CPU 指标持续触发后续扩容（6→12→20）
           缩容时 CPU 先降，但 MQ 积压消化完再缩
```

#### 3. K8s 滚动更新策略

```yaml
# PushServer Deployment 配置
apiVersion: apps/v1
kind: Deployment
metadata:
  name: push-server
spec:
  replicas: 10
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 2           # 滚动更新时最多比期望多 2 个 Pod
      maxUnavailable: 1     # 最多允许 1 个 Pod 不可用（保证可用性）
  minReadySeconds: 30       # Pod 就绪后等待 30s 才认为可用
  template:
    spec:
      terminationGracePeriodSeconds: 60  # 优雅关闭等待时间
      containers:
      - name: push-server
        lifecycle:
          preStop:
            exec:
              command: ["/bin/sh", "-c", "sleep 30"]  # 延迟关闭，让新 Pod 先接手
```

**滚动更新流程**（面试必问）：

```
Step 1: 创建新 Pod（maxSurge=2，最多 12 个 Pod 同时运行）
Step 2: 新 Pod 通过 readinessProbe（健康检查 → Nginx 摘流）
Step 3: 旧 Pod 收到 SIGTERM → preStop sleep 30s → 从 MQ 消费组注销
Step 4: 旧 Pod 优雅退出（处理完正在推送的消息）
Step 5: 重复直到所有旧 Pod 被替换
```

**PodDisruptionBudget（PDB）** — 保证缩容/节点维护时不中断服务：

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: push-server-pdb
spec:
  minAvailable: 3           # 至少保持 3 个 PushServer 可用
  selector:
    matchLabels:
      app: push-server
```

#### 4. 优雅缩容（Graceful Shutdown）

Pod 被 K8s 缩容/驱逐时，如果不做优雅关闭，会导致**正在推送的消息丢失**。

```go
// PushServer 优雅关闭流程
func main() {
    // 注册 SIGTERM 信号处理
    quit := make(chan os.Signal, 1)
    signal.Notify(quit, syscall.SIGTERM, syscall.SIGINT)

    // 启动 MQ 消费者
    consumer.Start()

    <-quit // 等待信号

    // Step 1: 停止接受新消息（从 MQ 消费组注销）
    log.Println("开始优雅关闭...")
    consumer.Suspend() // → 触发 MQ Rebalance，其他实例接管分区

    // Step 2: 等待正在推送的消息完成（最多等 30s）
    ctx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
    defer cancel()
    workerPool.Shutdown(ctx) // 等待所有推送 goroutine 完成

    // Step 3: 关闭所有下游连接
    redisClient.Close()
    grpcConn.Close()

    log.Println("优雅关闭完成")
}
```

**优雅缩容时序**：

```
K8s 决定缩容 → 给 Pod 发 SIGTERM
    ↓
Pod preStop hook（sleep 30s）— 给 K8s 一点时间更新 Endpoint，新连接不再路由过来
    ↓
Pod 内部：暂停 MQ 消费 → MQ Rebalance（~500ms）
    ↓
等待正在推送的请求完成（最多 30s）
    ↓
关闭连接 → 退出
    ↓
K8s 确认 Pod 终止
```

#### 2. Karpenter — 新一代节点弹性伸缩

**为什么选 Karpenter 替代 Cluster Autoscaler**：

| 维度 | Cluster Autoscaler | Karpenter ⭐ |
|------|-------------------|-------------|
| **扩容速度** | 慢（依赖 ASG 模板启动实例，3-5 分钟） | **快**（直接调 EC2 API，60-90 秒） |
| **实例多样性** | 单一 ASG 只能用一种实例类型 | **丰富**（自动选择最优实例类型：c5.large / m5.xlarge / c6i.2xlarge...） |
| **缩容策略** | 被动（只在节点利用率低时缩容） | **主动**（持续优化：把利用率低的 Pod 调度到更合适的实例上，然后回收闲置节点） |
| **成本优化** | 需自建多个 ASG 混用 Spot/On-Demand | **内置**（自动混用 Spot + On-Demand，Spot 中断自动迁移） |
| **运维复杂度** | 需要管理 ASG、Launch Template、多个 Node Group | **简单**（一个 Provisioner CR 搞定所有） |

**Karpenter Provisioner 配置**（雷漫 IM 生产配置）：

```yaml
apiVersion: karpenter.sh/v1beta1
kind: NodePool
metadata:
  name: im-node-pool
spec:
  template:
    spec:
      requirements:
        - key: "karpenter.k8s.aws/instance-category"
          operator: In
          values: ["c", "m"]              # 计算优化型 c 系列 + 通用型 m 系列
        - key: "karpenter.k8s.aws/instance-cpu"
          operator: In
          values: ["4", "8", "16"]         # 4-16 核之间自动选择
        - key: "karpenter.k8s.aws/instance-hypervisor"
          operator: In
          values: ["nitro"]               # 只用 Nitro 实例（更好的网络性能）
        - key: "topology.kubernetes.io/zone"
          operator: In
          values: ["ap-northeast-1a", "ap-northeast-1c"]  # 多可用区
        - key: "karpenter.sh/capacity-type"
          operator: In
          values: ["spot", "on-demand"]    # 优先 Spot，不足用 On-Demand
      nodeClassRef:
        name: im-node-class
  limits:
    cpu: 256                               # 集群总 CPU 上限（控制成本）
  disruption:
    consolidationPolicy: WhenUnderutilized  # 缩容策略：资源利用不足时合并
    expireAfter: 720h                       # 节点最长存活 30 天（避免长期运行的节点漂移问题）

---
apiVersion: karpenter.k8s.aws/v1beta1
kind: EC2NodeClass
metadata:
  name: im-node-class
spec:
  amiFamily: AL2                         # Amazon Linux 2
  role: "KarpenterNodeRole-IM"            # IAM 角色
  subnetSelector:
    karpenter.sh/discovery: "im-cluster"  # 自动发现子网
  securityGroupSelector:
    karpenter.sh/discovery: "im-cluster"  # 自动发现安全组
  tags:
    Environment: "production"
    Team: "im-backend"

**Karpenter 弹性伸缩流程**（面试能画出时序图）：

```
HPA 决定扩容 PushServer（3→6）
    │
    ├─ 调度器发现现有节点资源不足 → 3 个 Pod Pending
    │
    ├─ Karpenter 检测到 Pending Pod
    │   ├─ 分析 Pod 资源需求（requests）
    │   ├─ 计算最优实例类型（c5.xlarge = 4核8GB，刚好跑 2 个 Pod）
    │   └─ 决策：需要 2 台 c5.xlarge Spot 实例
    │
    ├─ 调 EC2 API 创建实例（60-90s）
    │   └─ 实例加入集群，节点状态 Ready
    │
    ├─ 调度器将 Pending Pod 调度到新节点
    │
    └─ 启动后：Pod 开始消费 MQ → 积压开始下降
```

#### 3. Spot Instance 成本优化策略

**雷漫 IM 的 Spot 使用策略**：

| 服务 | 实例类型 | 使用策略 | 理由 |
|------|---------|---------|------|
| **Access 网关** | c5.large / c5.xlarge | **On-Demand 100%** | 长连接无状态，但重连代价大，不宜中断 |
| **MsgServer** | m5.large / m5.xlarge | On-Demand 50% + Spot 50% | 无状态，客户端重试容错，Spot 中断影响小 |
| **PushServer** | c5.xlarge / c6i.xlarge | **Spot 80% + On-Demand 20%** | 无状态 + MQ 缓冲天然容错，Spark 中断后消费组 Rebalance 自动恢复 |
| **Login 服务** | t3.medium | Spot 100% | 轻量 + 多副本 + 无状态 |

**成本节省计算**：

```
集群规模：
  日常：5 节点（3 On-Demand + 2 Spot）
  高峰期：20 节点（4 On-Demand + 16 Spot）
  
月成本估算：
  On-Demand 单价：c5.xlarge ≈ $0.17/小时
  Spot 单价（平均）：≈ $0.05/小时（省 70%）
  
  纯 On-Demand：20 × $0.17 × 730h = $2,482/月
  混合策略：日常（3×0.17+2×0.05）× 730h + 高峰期额外实例
          ≈ $1,500/月（省约 40%）
```

# 中断处理机制

#### 4. 多 AZ 高可用部署

```yaml
# 跨可用区部署，避免单 AZ 故障
apiVersion: apps/v1
kind: Deployment
metadata:
  name: push-server
spec:
  replicas: 6
  template:
    spec:
      topologySpreadConstraints:      # Pod 均匀分布在多个 AZ
      - maxSkew: 1                    # 最多相差 1 个 Pod
        topologyKey: topology.kubernetes.io/zone
        whenUnsatisfiable: ScheduleAnyway
        labelSelector:
          matchLabels:
            app: push-server
      affinity:
        podAntiAffinity:              # 同一 AZ 内尽量分散到不同节点
          preferredDuringSchedulingIgnoredDuringExecution:
          - weight: 100
            podAffinityTerm:
              labelSelector:
                matchLabels:
                  app: push-server
              topologyKey: kubernetes.io/hostname
```

#### 6. 面试追问预案

| 追问 | 回答 |
|------|------|
| "HPA 扩容太快把集群打满了怎么办？" | 三层兜底：① HPA maxReplicas 上限（30）；② Karpenter NodePool 的 CPU 上限（256 核）；③ AWS 账户的 EC2 配额限制。同时 HPA behavior 中的 stabilizationWindow 防止震荡。 |
| "Spot 实例被回收，关键服务中断怎么办？" | 依赖三件事：① PDB `minAvailable=3` 保证最少副本数；② Karpenter 自动补充新节点（60-90s）；③ PushServer 无状态 + MQ Rebalance 自动恢复，客户端侧无感知。 |
| "为什么用 Karpenter 不用 Cluster Autoscaler？" | Karpenter 扩容快 3-5 倍（60s vs 3-5min），自动选择最优实例类型（避免资源碎片），内置 Spot 混用策略。Cluster Autoscaler 依赖 ASG 模板，扩容慢且实例类型单一。 |
| "K8s 扩缩容跟 Nginx 摘流怎么配合？" | Access 网关用 Nginx upstream 管理，K8s 用 readinessProbe 控制流量注入。缩容时 preStop sleep 30s + 标记 draining，确保 Nginx 先把流量切走再终止 Pod。 |
| "扩缩容对 MQ 消费有什么影响？" | 扩容时新 Pod 启动 → MQ Rebalance 分配部分分区 → 几百 ms 暂停。为避免频繁 Rebalance，我们使用 `allocateMessageQueueStrategy` 静态分配策略（Sticky Allocator），减少 Rebalance 次数。 |

### 🧪 压测方案

**五步压测法**（我们在雷漫 IM 压测中实际执行的）：

| 步骤 | 内容 | 工具 | 雷漫 IM 实际执行 |
|------|------|------|----------------|
| 1️⃣ 基准测试 | 单接口单机极限值 | 自研压测客户端（同套 C++ Libev） | Access 网关单机 100 万连接、MsgServer 5 万 QPS |
| 2️⃣ 链路压测 | 全链路端到端 | 同上 | 客户端 → Nginx → Access → MsgServer → MongoDB → MQ → PushServer → Access → 客户端 |
| 3️⃣ 混合场景 | 按生产流量比例 | 真实流量回放 | 凌晨低峰拷贝生产流量到压测环境，按比例加速回放 |
| 4️⃣ 极限压测 | 逐步加压到系统崩溃 | 自动化阶梯加压 | 找到第一个瓶颈点（MongoDB Primary 写 QPS 上限） |
| 5️⃣ 稳定性测试 | 持续 72 小时 | Prometheus + Grafana | 观察内存泄漏、GC 抖动、连接数漂移、MQ 积压 |

**压测中发现的真实瓶颈**：

| 发现 | 症状 | 根因 | 修复 |
|------|------|------|------|
| **conntrack 表满** | 50 万连接时间歇性 SYN 丢包 | `nf_conntrack_max` 默认 65536，表满内核丢包 | 扩容到 2M，缩短 established 超时到 600s |
| **MongoDB 写瓶颈** | 消息写入 P99 从 5ms 飙到 50ms | 单 Primary 写 QPS 接近上限 | 分片 + WriteConcern=1（IM 消息可容忍最终一致） |
| **群消息推送风暴** | PushServer CPU 100% | 万人群逐人推送 3000 次 RPC | 按网关聚合推送 + MQ 削峰 |
| **Redis INCR 热点** | msgseq 分配延迟 20ms+ | 纯 Redis INCR 高并发下排队 | 批次预分配（每 10000 条一次 INCRBY） |

### 🔄 滚动发布：IM 系统的平滑升级

IM 系统不能停服，所有发布必须**无损**。分两种场景说明：

#### 场景一：无状态服务滚动重启（PushServer / MsgServer）

这类服务不持长连接，用**原地滚动重启**——同⼀批节点逐个摘流、重启、接回：

```
Phase 1: 摘流（旧节点 A）
  → 从 Nginx upstream / 服务发现摘除节点 A（weight=0）
  → 标记为 draining，新流量不路由到此节点
  → PushServer：MQ 消费者组 Rebalance，分区被其他实例接管（~500ms）
  → MsgServer：Nginx 将新请求路由到其他实例

Phase 2: 原地重启（还是旧节点 A，只是进程重启）
  → 节点 A 上已无流量/连接
  → 停止进程 → 部署新版本包 → 启动新进程
  → 等待 healthCheck / readinessProbe 通过
  → 观察 3-5 分钟：错误率、P99 延迟、CPU/内存是否正常

Phase 3: 重新接入（节点 A 重新上线）
  → 节点 A 重新加入 Nginx upstream，weight 从 0 逐步上调
  → 观察流量恢复是否平滑，无异常则继续下一节点

Phase 4: 重复 Phase 1-3，处理节点 B → C → D ...
  → 每次只操作一个节点，集群整体容量逐步恢复
  → 全部完成后，高峰前留 2 小时观察窗口

发布窗口：凌晨 2:00-4:00
可回滚：任一节点异常 → 立即将该节点摘流，切回旧版本镜像重新部署
```

**关键点**：是**同一批节点的原地重启**，不是新起节点。因为 Phase 1 已经将节点上的流量/连接排空，节点已经是"干净的"，直接重启进程即可。相当于 K8s 的 `RollingUpdate` 策略——逐个 Pod 重建。

#### 场景二：有状态服务蓝绿替换（Access 网关）

Access 网关持有百万长连接，不能原地重启（重启意味着所有连接断开）。用**新节点替代旧节点**的方式：

```
Phase 1: 扩容新版本节点（新节点 A'）
  → 部署新版本 Access 网关节点 A'（新版本镜像）
  → Nginx upstream 加入 A'，weight 从 0 逐步上调
  → 新连接开始路由到 A'（A' 承载新连接）

Phase 2: 摘除旧版本节点（旧节点 A）
  → 从 Nginx upstream 摘除旧节点 A（weight=0）
  → 标记 draining，不再接受新连接
  → 等待旧节点 A 上的已有连接自然断开（心跳超时最长 5 分钟）
  → 5 分钟后确认 A 上无连接 → 停止旧节点 A

Phase 3: 重复
  → 对节点 B → C → D ... 重复 Phase 1-2
  → 每次先加一个新节点（新版本），再摘一个旧节点（旧版本）
  → 集群总容量保持不变（加一个减一个）

Phase 4: 全量完成
  → 所有旧节点替换完毕，旧版本进程全部下线
  → 最终集群节点数不变，但所有节点已升级到新版本
```

**为什么 Access 网关不能原地重启**：

| 场景 | 原地重启 | 蓝绿替换 |
|------|---------|---------|
| **重启期间连接** | 节点重启 → 上面 10 万连接全断 → 客户端重连风暴 | 新节点先接流量，旧节点连接自然消亡，零中断 |
| **重启耗时** | 进程启动 3-5s + 预热 30s → 客户端重连期间消息收不到 | 无感知迁移，连接不中断 |
| **复杂度** | 低（简单粗暴，但客户端体验差） | 高（需多部署临时节点，回滚需清理新节点） |
| **适用场景** | PushServer / MsgServer 等无状态服务 | Access 网关等持有长连接的服务 |

#### 为什么不用双写双读迁移

雷漫 IM 是从零新建的系统，不是从单体迁移，不存在"双写双读"的场景。如果是存量系统迁移（比如把旧 Nginx 方案迁移到新 Access 网关），才会用到：

```
Phase 1: 新老并行
  Nginx(旧) 和新 Access 网关(新) 同时部署
  流量按比例切（1% → 10% → 50% → 100%）

Phase 2: 连接保持
  老连接继续走 Nginx，新连接走新 Access
  Nginx 不接受新连接后，等待老连接自然断开

Phase 3: 全量切换
  所有新连接走新 Access，Nginx 下线
  观察 24 小时无异常后移除旧代码
```

### 💥 场景还原：IM 消息链路级联雪崩

将面试官提供的 `Kafka → Flink → Redis → DB` 链路映射到雷漫 IM 的实际消息链路：

```
用户发消息 → Nginx → Access网关 → MsgServer → RocketMQ → PushServer
                                                          → Redis（在线状态）
                                                          → MongoDB（消息持久化）
                                                          → Access网关 → 用户接收
```

**故障触发**：晚高峰期间，1000 人群聊 @所有人 消息暴增：

| 层 | 故障现象 | 级联影响 |
|----|---------|---------|
| **PushServer** | 消费 MQ 延迟从 5ms 飙到 30s | 消息堆积，用户收不到推送 |
| **Redis** | 在线状态查询 QPS 打满（每次推送都查一次） | 查询超时，PushServer 阻塞等待 |
| **MongoDB** | msgseq 预分配触发 findAndModify 排队 | 新消息无法分配 seq，写入阻塞 |
| **Access 网关** | 大量客户端因收不到消息断开 → 重连风暴 | 新连接 RSA 解密打满 CPU |
| **Nginx** | 连接数打满 `worker_connections` | 新连接被拒绝，用户无法登录 |

### 🚨 分层止损预案（即时应对）

雷漫 IM 的三层限流体系天然构成了分层止损防线。按"从近到远、从快到慢"原则：

#### 第 1 层：iptables 网络层止损（秒级）

```bash
# 防连接风暴：每 IP 60 秒最多 5 个新连接
iptables -A INPUT -p tcp --dport 80 --syn \
  -m recent --name webpool --rcheck --seconds 60 --hitcount 5 -j DROP

# 每 IP 最大并发 10 连接（防止单 IP 重连风暴）
iptables -A INPUT -p tcp --dport 80 \
  -m connlimit --connlimit-above 10 -j DROP

# 紧急情况：直接限到每 IP 1 连接、20 秒 1 次
# 宁可部分用户暂时连不上，也不能让所有用户都连不上
```

**设计原则**：iptables 阈值**最宽**（只挡极端异常），避免误杀正常用户。它是最后一道防线，不是常规限流。

#### 第 2 层：Nginx 接入层止损（秒级）

```nginx
# 紧急限流配置（故障时动态下发）
limit_req_zone $binary_remote_addr zone=api_write:20m rate=5000r/s;
location / {
    limit_req zone=api_write burst=2000 nodelay;
    # 超阈值直接 503，不让请求穿透到后端
}

# 连接数紧急限制
limit_conn_zone $binary_remote_addr zone=perip:10m;
limit_conn perip 20000;
```

**为什么 Nginx 阈值比 iptables 紧**：Nginx 在应用协议层（HTTP/WebSocket），可以返回有意义的错误码（503 + Retry-After），iptables 只能丢包。**前层宽、后层紧**，让用户在离自己更近的地方得到有意义的反馈。

#### 第 3 层：Access 网关应用层止损（10 秒级）

```cpp
// Access 网关的应用层限流（比 Nginx 更精细）
struct RateLimiter {

    // 代价：消息明文转发（仅紧急情况，事后补加密）
}

    // 跳过心跳超时检查，减少 Redis 查询
    // 代价：僵尸连接增多，但保住了核心消息路径
}

```

应急措施（按优先级执行）：

### 🏗️ 架构根治方案（长期修复）

止损之后，我们做了以下架构改造来根治问题：

#### 1. 链路超时根因定位

| 根本原因 | 为什么发生 | 修复措施 |
|---------|-----------|---------|
| **PushServer 逐人推送** | 群消息是对每个成员逐个 RPC 推送，1000 人群 = 999 次 RPC | 按 accnodeidentify 聚合，同网关合并为 1 次 RPC |
| **Redis 在线状态查询热点** | 每次推送都查 Redis，高并发下 QPS 打满 | 一致性哈希路由 + 本地 LRU 缓存（TTL 5-30s），命中率 90%+ |
| **MongoDB msgseq 热点** | 每条消息都调 findAndModify 分配 seq（5-20ms/次） | Redis Lua 原子 INCR 做主路径（< 1ms），额度耗尽时 MongoDB 预分配 10000 条 |
| **重连 RSA 风暴** | 每次重连都要 RSA 解密（0.5ms），大量重连时 CPU 打满 | Token + Redis 缓存 sessionkey，重连只查 Redis（0.1ms），省 90%+ RSA 操作 |
| **连接断开风暴** | 服务端问题导致大量客户端同时断开 → 同时重连 → 雪崩 | 客户端随机退避重连（1s + random(0, 3s)），削峰填谷 |

#### 2. 系统性改进：四层防线体系

```
第一层：限流（接入层）
  iptables → Nginx → Access 三层限流
  前层阈值 > 后层阈值，逐步收紧
  被限流的用户得到有意义的错误响应

第二层：降级（应用层）
  配置中心实时下发降级开关
  - 关闭非关键功能（系统通知、在线状态广播）
  - 降低加密强度（紧急情况下关 RSA，降为 AES only）
  - 跳过心跳检查（牺牲准确性保可用性）

第三层：隔离（架构层）
  关键路径（消息发送）和非关键路径（已读回执、输入状态）独立部署
  故障爆炸半径控制：单 PushServer 实例故障不影响其他实例

第四层：自愈（运维层）
  监控触发自动操作：
  - PushServer 消费延迟 > 总阈值 → 自动扩容
  - Access 节点 CPU > 80% 持续 2 分钟 → 自动摘流 + 重启
  - MongoDB 慢查询 > 100ms → 自动 kill 慢查询 + 告警
```

#### 3. 真实故障故事：conntrack 表满排查（面试最加分项）

这是最能体现 Linux 内核功底的真实故事：

```
现象：压测到 50 万连接时出现间歇性 SYN 丢包，TCP 握手失败

排查过程（按检查清单逐项排查）：
  ① 检查 socket buffer  ← tcp_rmem/wmem 已调到 1KB，正常     ✓
  ② 检查文件描述符      ← ulimit -n 1048576，正常             ✓
  ③ 检查 listen 队列    ← somaxconn 65535，正常               ✓
  ④ 检查 conntrack      ← dmesg: "nf_conntrack: table full,
                            dropping packet"                  ← 找到根因！

根因拆解：
  Linux netfilter 连接追踪表（conntrack）记录每个 TCP 连接状态，
  默认最大 65536 条。50 万连接时表满，内核直接静默丢 SYN 包。
  这个参数非常容易被忽略——大家都知道调 ulimit 和 tcp_rmem，
  但 conntrack 很少有人关注。

修复（/etc/sysctl.d/99-conntrack.conf）：
  net.netfilter.nf_conntrack_max=2097152          # 2M 条
  net.netfilter.nf_conntrack_buckets=524288       # hash bucket
  net.netfilter.nf_conntrack_tcp_timeout_established=600  # 从 5 天→10 分钟
  net.netfilter.nf_conntrack_tcp_timeout_time_wait=30

效果：100 万连接时 conntrack 表使用率仅 60%，不会再满。

每连接内存详细拆解：
  内核层 socket 元数据 + conntrack entry：~3KB × 100万 = ~3GB
  内核层 tcp_rmem/wmem min（调优后 1KB）：~2KB × 100万 = ~2GB
  用户层 Connection 对象 + epoll 事件：~3KB × 100万 = ~3GB
  合计：~8KB/连接 → 100 万连接 ≈ 8GB（16GB 机器剩余 6-7GB）
```

> **面试技巧**：这个故事展示了三个能力——① 系统性排障方法论（逐项检查，不猜）；② Linux 内核深度（conntrack 不是每个人都知道）；③ 数据驱动（每个数字都能拆解）。

### 🔁 幂等性保障

IM 系统中最常见的幂等问题是**消息重复投递**。同一个消息被投递两次，用户会收到两条重复消息。

**雷漫 IM 的幂等方案：客户端生成唯一 ID + 服务端 Redis SETNX 去重**

```
客户端侧：
  → 每条消息生成唯一的 clientMsgId（客户端本地自增序号 + 时间戳 + 设备ID）
  → 即使网络重传，clientMsgId 不变

服务端侧（MsgServer）：
  → 收到消息后，用 clientMsgId 拼 Redis key："msg:dedup:{clientMsgId}"
  → SETNX 写入 Redis，TTL = 5 分钟
  → 如果 SETNX 返回 true  → 首次收到，正常处理（写 MongoDB + 投递 MQ）
  → 如果 SETNX 返回 false → 重复请求，直接返回已有的 serverMsgId
  → 5 分钟后 TTL 自动过期，Redis 内存释放（正常消息 5 分钟内已处理完毕）
```

**为什么用 clientMsgId 而不是依赖 TCP/应用层重传保证**：

| 场景 | 只用 TCP 重传 | clientMsgId + Redis 去重 |
|------|-------------|------------------------|
| 网络瞬断，客户端重发 | ✅ TCP 层自动重传 | ✅ 同样处理，SETNX 防重 |
| 客户端崩溃重启后补发 | ❌ 新 TCP 连接，无法识别重复 | ✅ clientMsgId 不变，SETNX 命中 |
| 服务端处理成功但 ACK 丢失 | ❌ 客户端认为失败，重新发送 | ✅ SETNX 命中，返回已有 msgId |
| MsgServer 写 DB 成功但响应超时 | ❌ 客户端重试，DB 产生两条记录 | ✅ SETNX 命中，不重复写 DB |

### 💥 节点宕机处理

雷漫 IM 的宕机恢复不依赖心跳检测和复杂状态机，而是靠**架构天然容错**：

#### MsgServer 宕机

```
问题：MsgServer 正在处理消息时宕机，消息可能处于"写了一半"的状态

容错机制：
  ① 客户端超时（3s）后自动重试，Nginx 路由到其他 MsgServer 实例
  ② 新实例收到重复请求 → clientMsgId SETNX 去重 → 如果是新消息则处理，重复则返回已有 msgId
  ③ 如果旧实例写了 MongoDB 但没投递 MQ → 新实例 SETNX 判断是新请求，重新写 DB + 投 MQ
  ④ MongoDB WriteConcern=1（写 Primary 即返回），数据不会"写了一半"
```

#### PushServer 宕机

```
问题：PushServer 宕机，正在推送的消息怎么办？

容错机制：
  ① 消息在 RocketMQ 中持久化（CommitLog 磁盘存储），不会丢失
  ② MQ Consumer Group Rebalance 自动触发，其他 PushServer 实例接管宕机实例的分区
  ③ 新实例从上次消费位点（offset）继续消费
  ④ Rebalance 期间短暂暂停消费（几百 ms），消息积压后批量追赶
  ⑤ 推送失败的消息走 RocketMQ 内置重试队列（RECONSUME_LATER）
```

**关键设计：PushServer 是无状态的**。它不存储任何消息本体——消息在 MongoDB 和 MQ 中。PushServer 只负责"从 MQ 拉取 → 查 Redis 在线状态 → 推送"，所有状态都在 Redis/MQ/MongoDB 中，宕机后重启直接继续消费即可。

#### Access 网关宕机

```
问题：Access 网关宕机，上面所有长连接断开

容错机制（客户端侧）：
  ① 客户端检测到 WebSocket 断开 → 等待 1s + random(0,3s) → 重新连接
  ② Nginx 将新连接路由到其他健康 Access 节点
  ③ 客户端携带 Token 恢复会话 → 查 Redis sessionkey → 免 RSA 协商直接恢复
  ④ 重连期间的消息不丢——MongoDB 中已持久化，重连后自动补拉

容错机制（服务端侧）：
  ① Nginx 健康检查探测到 Access 不可用 → 自动摘除 upstream
  ② PushServer 推送时发现目标 accnodeidentify 不可达 → 标记离线 → 走 APNs/FCM
  ③ 用户重新上线后，从 MongoDB 补拉离线期间的消息
```

**宕机恢复时间对比**：

| 组件 | 检测时间 | 恢复时间 | 数据丢失风险 |
|------|---------|---------|------------|
| MsgServer | 3s（客户端超时） | < 1s（Nginx 路由切换） | 无（SETNX 去重保障） |
| PushServer | < 30s（MQ Rebalance） | < 30s（Rebalance 完成后追消费） | 无（MQ 持久化） |
| Access 网关 | 5s（Nginx 健康检查） | 1-4s（客户端随机退避重连） | 无（MongoDB 补拉） |

### ⚔️ 资源抢占与优先级管控

IM 推送场景下，消息量是波动的——晚高峰群聊 @所有人 会产生瞬时流量尖刺。需要优先级管控来保证核心消息路径不被非关键消息挤占。

**雷漫 IM 的优先级设计**：

| 优先级 | 消息类型 | RocketMQ Tag | 消费策略 |
|-------|---------|-------------|---------|
| **P0（核心）** | 单聊消息 | `tag_c2c` | 独立 Consumer Group，预留线程 |
| **P1（重要）** | 群聊消息（含 @消息） | `tag_c2g` | 共享 Consumer Group，按量弹性 |
| **P2（普通）** | 群聊消息（非 @） | `tag_c2g_normal` | 同上，积压时降级 |
| **P3（低优）** | 系统通知、已读回执、输入状态 | `tag_notify` | 独立线程池，CPU 紧张时暂停消费 |

**RocketMQ 侧的优先级实现**：

```java
// PushServer 侧：不同优先级的消息走不同消费线程池
// P0 单聊和 P1 群聊 @消息共用一个高优消费线程池
consumer.registerMessageListener("tag_c2c || tag_c2g_at", 
    highPriorityPool, (msgs, context) -> {
        // 高优处理：立即推送
        return processMessages(msgs);
    });

// P3 系统通知走低优线程池，CPU > 80% 时暂停
consumer.registerMessageListener("tag_notify", 
    lowPriorityPool, (msgs, context) -> {
        if (getCPUUsage() > 0.8) {
            return ConsumeConcurrentlyStatus.RECONSUME_LATER; // 推迟消费
        }
        return processMessages(msgs);
    });
```

**降级开关（配置中心实时下发，无需重启）**：

```
alert_level = normal   → 所有消息正常推送
alert_level = warning  → P3 系统通知暂停，P0/P1/P2 正常
alert_level = critical → P2 非@群聊暂停，只推 P0 单聊 + P1 @消息
                       （用户上线后从 MongoDB 补拉群聊消息，不丢）
```

**资源配额**：

| 资源 | P0+P1 保障 | P2 弹性 | P3 限制 |
|------|-----------|---------|---------|
| PushServer 消费线程 | 60% | 30% | 10%（CPU > 80% 时为 0） |
| Redis 查询 QPS | 70% | 20% | 10% |
| 出口带宽 | 50% | 35% | 15% |

### 📊 编排方式对比

雷漫 IM 的消息推送采用了**事件驱动 + 消息队列解耦**的编排模式。以下是它与中心化调度的对比：

#### 当前方案：事件驱动去中心化编排（MsgServer → MQ → PushServer）

```
┌──────────────────────────────────────────────────────┐
│                   RocketMQ（事件总线）                  │
│                                                      │
│  MsgServer 生产事件          PushServer 消费事件        │
│  ┌──────────┐               ┌──────────┐             │
│  │ 写DB+入MQ │─── 消息事件 ──→│ 拉取消息  │             │
│  │ 即结束    │               │ 查在线状态 │             │
│  │          │               │ 聚合+推送  │             │
│  └──────────┘               └──────────┘             │
│                                                      │
│  双方不直接通信，通过 MQ 解耦                           │
│  MsgServer 不知道 PushServer 的存在                    │
└──────────────────────────────────────────────────────┘
```

**优点**：

| 特性 | 具体表现 |
|------|---------|
| ✅ **解耦** | MsgServer 不知道 PushServer 地址，双方独立演进 |
| ✅ **削峰** | 瞬时消息暴增时，MQ 缓冲吸收，PushServer 按能力消费 |
| ✅ **容错** | PushServer 宕机 → MQ 消息不丢，Rebalance 后其他实例接管 |
| ✅ **独立扩容** | MsgServer 和 PushServer 各自独立扩缩容，互不影响 |
| ✅ **批量优化** | PushServer 从 MQ 批量拉取后按网关聚合，3000 次 RPC → ~10 次 |
| ✅ **顺序保证** | 同一 groupId 的消息路由到同一 MQ 分区，保证同一群聊消息有序 |

**缺点**：

| 特性 | 具体表现 |
|------|---------|
| ❌ **增加延迟** | 消息多经过一次序列化/网络/反序列化（RocketMQ ~1-2ms） |
| ❌ **调试复杂** | 出问题时多一层链路：是 MsgServer 生产慢还是 PushServer 消费慢？ |
| ❌ **运维成本** | 多维护一套 RocketMQ 集群（3 节点起） |
| ❌ **无全局视角** | 没有一个中心节点知道"当前有多少消息在推送中"，监控需要从 MQ 积压指标推算 |

#### 对比方案：中心化调度（假设不用 MQ，由调度器直接 RPC 分配）

```
┌─────────────────────────────────────┐
│        调度器（单点协调）              │
│                                      │
│  MsgServer ─→ 调度器 ─→ PushServer   │
│     │            │           │        │
│     │      (记录每一台 PushServer     │
│     │       的负载，按负载分配)        │
│                                      │
│  所有消息都要经过调度器转发            │
└─────────────────────────────────────┘
```

**对比分析**：

| 维度 | 事件驱动（当前方案）✅ | 中心化调度 |
|------|---------------------|-----------|
| **延迟** | Msg→MQ(~1ms)→Push | Msg→调度器(~0.5ms)→Push，更低但差距小 |
| **吞吐** | ★★★★★ MQ 异步批量，不受单点限制 | ★★ 调度器成为瓶颈（所有消息经过它） |
| **容错** | ★★★★★ PushServer 宕机不影响 MsgServer | ★★ 调度器宕机 = 全链路中断 |
| **扩展性** | ★★★★★ MsgServer 和 PushServer 独立扩缩容 | ★★★ 调度器需感知拓扑变化 |
| **可观测性** | ★★★ 需从 MQ 积压、消费延迟等指标推算 | ★★★★★ 调度器有全局视图 |
| **实现复杂度** | ★★★★ 依赖 MQ 中间件 | ★★★ 纯 RPC，但需自建故障转移 |

**结论**：

雷漫 IM 选择事件驱动编排的核心原因不是"哪种模式更好"，而是 **IM 消息推送场景天然适合事件驱动**：

1. **生产者消费者速率不匹配**：MsgServer 写消息是微秒级，PushServer 推消息是毫秒级。如果不用 MQ 缓冲，生产者必须等消费者——等于让快的人等慢的人
2. **不需要强顺序依赖**：消息 A 和消息 B 的推送没有依赖关系，不需要中心调度器来编排"先推 A 再推 B"
3. **容错高于一切**：IM 系统最不能接受的是"消息丢了"。MQ 的持久化 + Consumer Group Rebalance 提供了最可靠的容错保障

> **反过来看**：如果有强顺序依赖的场景（比如"先生成面试题→用户回答→评分→反馈"），中心化 DAG 编排就更合适。**编排模式没有银弹，取决于任务的依赖关系和容错需求。** 在雷漫 IM 的场景下，事件驱动是最佳选择。

### 🎯 基于雷漫 IM 项目经验的面试五步法

#### 1. 开场定调（前 30 秒）

```
"我在雷漫网络主导设计了分布式 IM 系统。
核心成就是自研 C++ 接入层实现了单机百万连接（8 核 16G，每连接仅 8KB 内存），
群消息扇出从 3000 次 RPC 优化到 ~10 次，消息 P99 延迟从 200ms 降到 50ms。
这中间最核心的挑战是如何在 16GB 内存限制下把每连接开销从 16KB 压到 8KB..."
```

**关键**：第一句就把面试官注意力引到**架构设计**和**性能调优**上——这两个是 50K+ 岗位的核心考核点。

#### 2. 数据说话（必背数据）

| 指标 | 准确值 | 面试场景下的表述 | 被追问时的回答 |
|------|--------|----------------|--------------|
| 单机连接数 | 1,000,000+ | "单机百万连接" | 每连接 ~8KB，16G 机器压测 free 剩 6-7GB，关键是 tcp_rmem/wmem 从 4KB 调到 1KB |
| 单聊 P99 | 30ms | "消息端到端 < 50ms" | 先推送再落库，存储 IO 不在关键路径上；不含移动端网络延迟 |
| 群聊 P99 | 50ms（100人）/ 200ms（1000人，优化前） | "群聊扇出延迟从 200ms 降到 50ms" | PushServer 拉取消息 → 最后一台网关 TCP ACK（不含客户端下行和移动网络） |
| 加密 CPU | 30% → 8% | "加密 CPU 从 30% 降到 8%" | Token + Redis 缓存 sessionkey 是主因（消除 90%+ RSA 操作），ECDH 和 AES-NI 是附加收益 |
| MongoDB vs MySQL 成本 | CPU 16:1, 内存 16:1, 磁盘 3.3:1 | "MongoDB 方案比 MySQL 省 16 倍 CPU 和内存" | IM 写多读少、无复杂事务，MongoDB 分片集群天然适合 |
| 每连接内存 | ~8KB | "每连接仅 8KB" | 内核 ~5KB（socket + conntrack + buffer）+ 用户态 ~3KB（Connection + epoll 事件）|
| RocketMQ 集群 | 2M-2S / 4 节点 / 8核16GB | "RocketMQ 4 节点做削峰解耦，MQ 只增加 1-2ms 但换来聚合推送" | ASYNC_FLUSH + ASYNC_MASTER，单 Broker 10万 TPS，集群 20万 TPS。1-2ms 代价换 3000→10 次 RPC 聚合，净省 8970ms |
| MQ 时延代价 | ~1-2ms | "MQ 这层只增加 1-2ms，但群聊 P99 从 200ms 降到 50ms" | MQ 不在发送方 ACK 关键路径（MsgServer 写 DB+投MQ 即返回），1-2ms 是接收方路径上的增量，但聚合推送净收益远大于此 |

#### 3. 技术深度展示（主动引导）

**不要让面试官猜你的能力边界**，在回答中主动抛出可以深挖的技术点：

```
"说到百万连接调优，我最引以为傲的是 conntrack 表满的问题排查。
大多数人都知道调 ulimit 和 tcp_rmem，但 conntrack 是个很容易被忽略的坑。

我们压测到 50 万连接时出现间歇性 SYN 丢包，
逐项排查了 socket buffer、fd、listen 队列都正常，
最后在 dmesg 里看到 'nf_conntrack: table full, dropping packet' 才找到根因。

默认 conntrack_max 只有 65536，50 万连接时表满，内核直接静默丢包。
修复后调到 2M，同时把 established 超时从 5 天缩短到 10 分钟，
100 万连接时表使用率才 60%。"
```

**面试官心理**：这个候选人不仅会写业务代码，还能深入到 Linux 内核层面排查问题——这正是 50K+ 岗位需要的能力。

**其他可主动引导的深度点**：

| 话题 | 20 秒抛出 | 40 秒深挖（如果面试官追问） |
|------|----------|--------------------------|
| msgseq 预分配 | "我们的 msgseq 方案让 99.99% 消息不碰 MongoDB，但设计上知道会有 seq 断号" | Redis Lua INCR 做主路径（<1ms），MongoDB 批次预分配（每 10000 条），服务重启浪费最多 10000 个 seq，客户端补拉补齐 |
| 未读数方案 | "我们放弃了 Redis INCR 做未读数，因为它有三个致命缺陷" | 写扩散（群聊一条消息 N 次 Redis 写）、撤回 DECR 丢失、Redis 故障清零。改用已读点 + MongoDB count |
| RocketMQ 选型 | "我们选了 RocketMQ 而不是 Kafka，因为 IM 推送场景对延迟和重试有特殊要求" | RocketMQ 比 Kafka 低 1-3ms、内置重试队列和死信队列、事务消息支持 |
| epoll ET vs LT | "我们用 ET 边缘触发，因为 LT 在长连接场景下 CPU 空转严重" | 100 万连接哪怕只有 1% 有数据，LT 也要处理 1 万个重复事件；ET 的坑是必须 while-EAGAIN 读完 |

#### 4. 回答模板：STAR+ 技术深度

```
S(背景)：雷漫 IM 需要支撑 900 万用户，原有 Nginx 方案单机 10 万连接封顶
T(目标)：自研 C++ 接入层，单机百万连接，消息 P99 < 50ms
A(行动)：
  - 基于 epoll ET + 多进程 Worker + SO_REUSEPORT
  - tcp_rmem/wmem 从 4KB → 1KB
  - conntrack_max 从 65536 → 2M
  - 群消息按 accnodeidentify 聚合推送
  - Token + Redis 缓存 sessionkey 消除 RSA 风暴
R(结果)：单机 100万+ 连接，P99 30ms，CPU 8%，存储成本降到 MySQL 的 1/16

+ 技术深度(主动抛出)：
  "这里有一个面试官可能不知道的细节——conntrack 表满的排查故事..."
  
+ 设计取舍(展示权衡能力)：
  "msgseq 预分配有个 trade-off：99.99% 消息 <1ms，但服务重启最多浪费 10000 个 seq，
   我们选择接受这个代价，因为 seq 断号客户端补拉的成本远小于每条消息都走 MongoDB。"
  
+ 复盘反思(展示成长思维)：
  "如果重新设计，我会把未读数做成快照 + 增量，而不是每次都 count。长离线用户（半年没登录）
   重新登录时 count 可能 > 100ms，快照可以把 O(log M+K) 降到 O(1)。"
```
