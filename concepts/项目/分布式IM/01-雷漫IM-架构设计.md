```
         ▼
┌─────────────────────────┐
│  Access网关节点          │
│  (WebSocket网关)        │
└─────┬───────────────────┘
      │
      ├──────────┬──────────┬──────────┐
      ▼          ▼          ▼          ▼
┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐
│Login服务 │ │Msg服务  │ │PushServer│ │  Redis  │
│ (认证)   │ │(消息处理)│ │(消息推送)│ │ (缓存)  │
└─────────┘ └─────────┘ └─────────┘ └────┬────┘
                                           │
                    ┌──────────────────────┴──────────────┐
                    │                                     │
                    ▼                                     ▼
            ┌──────────────┐                    ┌──────────────┐
            │   MongoDB    │                    │    MySQL     │
            │  (消息存储)   │                    │  (业务数据)   │
            └──────────────┘                    └──────────────┘
```

### 1.2 核心组件职责

| 组件 | 职责 | 技术要点 |
|------|------|---------|
| **Nginx** | SSL 终止、WS 反向代理、连接限流 | 单机 65K+ 连接 |
| **Access 网关** | 长连接管理、消息路由、加解密、心跳 | 自研 C++，百万连接 |
| **Login 服务** | 用户认证、Token 验证、Session 管理 | ECDH + RSA + AES |
| **Msg 服务** | 消息处理、持久化、业务逻辑 | 单聊/群聊分发 |
| **PushServer** | 在线推送、离线推送、第三方推送 | 消费队列+状态判断 |
| **Redis** | 登录状态、Token、消息缓存 | Codis 分布式 |
| **MongoDB** | 消息持久化存储 | 分片集群 |
| **MySQL** | 用户/好友/群组业务数据 | MGR 高可用 |

## 二、限流体系

### 2.1 三层限流架构

```
顺序：iptables ＞ Nginx ＞ Access
前层阈值应宽于后层，避免误杀
```

### 2.2 iptables 层（网络层）

```bash
# 限制每 IP 60 秒内最多 5 个新连接
iptables -A INPUT -p tcp --dport 80 --syn \
  -m recent --name webpool --rcheck --seconds 60 --hitcount 5 -j DROP

# 限制每 IP 最大并发 10 连接
iptables -A INPUT -p tcp --dport 80 \
  -m connlimit --connlimit-above 10 -j DROP

# 高配：1 秒 10000 新连接，最大并发 20000
iptables -A INPUT -p tcp --dport 80 --syn \
  -m recent --name webpool --rcheck --seconds 1 --hitcount 10000 -j DROP
iptables -A INPUT -p tcp --dport 80 \
  -m connlimit --connlimit-above 20000 -j DROP
```

### 2.3 Nginx 层

```nginx
worker_rlimit_nofile 65535;
events {
    use epoll;
    worker_connections 65535;
}

http {
    # 按客户端 IP 限制并发
    limit_conn_zone $binary_remote_addr zone=perip:10m;
    limit_conn perip 20000;     # 每 IP 并发连接

    # 按 server 限制并发
    limit_conn_zone $server_name zone=perserver:10m;
    limit_conn perserver 65535;

    # 按客户端 IP 限制请求频率
    limit_req_zone $binary_remote_addr zone=api_write:20m rate=5000r/s;
    location / {
        limit_req zone=api_write burst=5000;
    }
}

stream {
    # TCP 层限流
    limit_conn_zone $binary_remote_addr zone=perip_tcp:10m;
    server {
        limit_conn perip_tcp 5;        # 每 IP TCP 并发
        proxy_upload_rate 200k;        # 每连接上行限速
    }
}
```

### 2.4 Access 层（应用层）

- 单连接总上传次数/秒
- 指定消息类型（如命令字 4501）次数/秒
- 超限记录本地日志 + 监控告警

## 三、共享内存队列（父子进程通信）

### 3.1 背景

Manager（父进程）与 Worker（子进程）原使用 **Unix domain socketpair**：

```
Manager (父进程)
  ├── fork() → Worker[0]  ←→ socketpair (控制流 + 数据流)
  ├── fork() → Worker[1]
  └── fork() → Worker[N]
```

**现有问题**：

| 问题 | 说明 |
|------|------|
| 系统调用开销 | 每条消息 send()/recv()，高频心跳下 syscall 占比显著 |
| 多次内存拷贝 | protobuf 序列化 → 发送缓冲 → socket 内核缓冲 → 接收缓冲 → 反序列化 |
| 内核缓冲区限制 | socketpair 默认 16KB-64KB，高负载时满则丢或阻塞 |

### 3.2 共享内存方案

```
Manager (父进程)                           Worker (子进程)
┌──────────────────────────┐         ┌──────────────────────────┐
│  shm_open → mmap         │ ←共享→  │  shm_open → mmap (同fd)  │
│  写入请求到 SHM Queue    │         │  从 SHM Queue 读取       │
│  写 posix semaphore      │ sem→   │  等待 sem_wait           │
└──────────────────────────┘         └──────────────────────────┘
```

**优势**：
- 零 syscall（除 semaphore 外）
- 零拷贝（mmap 直接映射）
- 共享内存可配置到 MB 级

### 4.2 MongoDB 成本对比

| 资源项 | MySQL | MongoDB | 成本比 |
|--------|-------|---------|--------|
| 集群数 | 64×4=256 套 | 4 分片 | — |
| CPU | 4×256=1024 核 | 16×4=64 核 | **16:1** |
| 内存 | 16×256=4096G | 64×4=256G | **16:1** |
| 磁盘 | 30×4=120T | 9×4=36T | **3.3:1** |

在相同业务规模下，MongoDB 在 CPU、内存、磁盘上的资源消耗均显著低于 MySQL。
