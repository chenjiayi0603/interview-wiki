# 雷漫 IM 登录与加密

> ECDH 密钥协商、RSA+AES 混合加密通道、Token 管理、多设备支持。

---

## 一、加密通道整体流程

### 1.1 混合加密设计

```
客户端                                  服务器
  │                                        │
  │ ① 获取 RSA 公钥（内置/API下发）         │
  │                                        │
  │ ② 生成临时密钥对 (c_priv, c_pub)        │
  │ ③ 随机生成 AES key                     │
  │ ④ RSA 加密 (aeskey + userid + ecdh_pub)│
  │ ⑤ AES 加密 (token + clientTime)        │
  │ ────────── 登录请求 ─────────────────→  │
  │                                        │ ⑥ RSA 解密获取 aeskey + ecdh_pub
  │                                        │ ⑦ AES 解密获取 token
  │                                        │ ⑧ 验证 token 有效性
  │                                        │ ⑨ 生成临时密钥对 (s_priv, s_pub)
  │                                        │ ⑩ ECDH 计算共享密钥 K
  │                                        │ ⑪ 派生会话密钥 SK
  │ ←─────── s_pub + 签名 ──────────────── │
  │                                        │
  │ ⑫ 验证服务器签名                        │
  │ ⑬ ECDH 计算共享密钥 K                  │
  │ ⑭ 派生会话密钥 SK                      │
  │ ⑮ AES-SK 加密认证凭证                   │
  │ ────────── 认证请求 ─────────────────→  │
  │                                        │ ⑯ 验证凭证
  │ ←───── SK 加密的成功响应 ──────────────  │
  │                                        │
  │ ←──── 后续通信使用 SK 对称加密 ────────→  │
```

### 1.2 密钥层次

```
长期密钥（预置/CA下发）：
  - RSA 2048 bits：服务器公私钥对
  - 客户端通过内置或 API 获取公钥

临时密钥（每次登录生成）：
  - ECDH 临时密钥对：密钥协商
  - AES-256：加密登录凭据

会话密钥（登录完成后派生）：
  - 通过 ECDH 计算共享密钥 K
  - 从 K 派生 SK (AES-256 + HMAC-SHA256)
  - 后续消息加密使用 SK
```

### 1.3 各组件分工与设计意图

| 组件 | 算法 | 职责 | 解决什么问题 |
|------|------|------|-----------|
| **Token** | HMAC/签名 | 认证凭证，Redis 缓存 sessionkey | **效率**：重连时免 RSA 解密，直接复用 sessionkey |
| **RSA-2048** | 非对称加密 | 加密传输登录载荷（token + ECDH 公钥） | **第一跳安全**：只有持有私钥的服务器能解密 |
| **ECDH (P-256)** | 密钥协商 | 双方独立生成临时密钥对，计算共享密钥 | **前向安全**：RSA 私钥泄露后历史消息仍安全 |
| **AES-256-GCM** | 对称加密 | 消息内容加密 | **高性能**：AES-NI 硬件加速，500ns/次 |

**为什么 Token 是效率核心**：
- 无 Token 时：每次重连 → 发用户名密码 → RSA 解密（0.5ms）→ DB 查询验证（10ms）→ 重新协商 sessionkey
- 有 Token 时：重连 → 发 Token → Redis 查 sessionkey（0.1ms）→ 复用现有密钥
- **Token + Redis 缓存消除了 90%+ 的 RSA 操作**，是 CPU 从 30% 降到 8% 的核心原因

**为什么 Token 之后还要 ECDH**：
- Token 管效率，ECDH 管安全
- 如果只用 RSA 传输 AES key：攻击者截获后一旦拿到 RSA 私钥，所有历史消息可解密
- ECDH 让双方各自生成临时密钥对，RSA 只传输公钥（非私钥），私钥泄露不影响历史

**各层定位总结**：
```
Token  → 认证提效      （减少 RSA 解密次数）
RSA    → 身份认证 + 初始信道保护（第一跳安全）
ECDH   → 前向安全       （私钥泄露不回溯历史消息）
AES    → 消息加密性能   （AES-NI 硬件加速，几乎零成本）
```

## 二、RSA 公钥管理与分发

### 2.1 公钥获取方式

| 方式 | 说明 | 适用场景 |
|------|------|---------|
| **随 APP 内置** | 编译时固化在客户端代码中 | 推荐，攻击者无法获知私钥 |
| **登录前 API 拉取** | HTTP(S) 接口获取，校验证书 | 密钥可能轮换的场景 |
| **CA 中心下发** | 通过可信链路动态下发 | 极高安全要求 |

### 2.2 公钥轮换策略

- **一般情况下**：RSA 公钥可长期使用不变
- **触发轮换的场景**：
  1. 运维主动轮换（定期或密钥泄露风险）
  2. 私钥疑似泄漏
  3. 算法升级（2048 → 3072）
  4. 安全策略强制要求

## 三、登录缓存模型（Redis）

### 3.1 Token 缓存 (String)

```
Key:   1:1:im:token:userid:${userid}:deviceid:${deviceid}
Value: token 字符串
```

### 3.2 用户登录状态缓存 (Hash) ⭐

```
Key:   1:2:im:status:userid:${userid}
Field: (所有字段带 ${deviceid} 后缀)
```

| 字段 | 类型 | 说明 |
|------|------|------|
| `logintime:${deviceid}` | int32 | 最近登录时间（秒） |
| `clienttype:${deviceid}` | int32 | 客户端类型 0/1/2/3 |
| `status:${deviceid}` | int32 | 0=offline 1=online 2=busy |
| `loginseq:${deviceid}` | int64 | 防重登序列号 |
| `ssidfreshtime:${deviceid}` | int32 | 最近心跳时间（秒） |
| `sessionid:${deviceid}` | int64 | 链路唯一标识 |
| `sessionkey:${deviceid}` | string | 对称加密密钥（32字节） |
| `accnodeidentify:${deviceid}` | string | 网关定位 `ip:port:workIndex` |
| `clientip:${deviceid}` | string | 客户端 IP |
| `platformtype:${deviceid}` | int32 | 1=Android 2=iOS 3=Mac 4=Windows |
| `expire:${deviceid}` | int32 | sessionkey 过期时间 |
| `language:${deviceid}` | string | 语言版本 |

### 3.3 多设备支持

系统完全支持用户多设备同时在线：

```
同一用户可在手机、平板、PC 等多终端同时在线
各设备独立管理：
  - 独立 sessionkey（加密密钥互不影响）
  - 独立 loginseq（防重登）
  - 独立 accnodeidentify（路由到不同网关）
  - 独立 status（可同时在线）

Redis Hash 的 ${deviceid} 后缀实现设备隔离
```

## 四、WebSocket 网关

### 4.1 网关职责

| 职责 | 说明 |
|------|------|
| **长连接管理** | 维护客户端 WebSocket 连接 |
| **消息路由** | 根据消息类型转发到对应服务 |
| **加解密** | 使用 sessionkey 加解密消息 |
| **心跳** | 检测连接存活，更新 `ssidfreshtime` |
| **限流** | 单连接消息频率控制 |
| **协议转换** | Protobuf 编解码 |

### 4.2 连接生命周期

```
客户端连接建立 → WSS 握手 → 登录认证 → 心跳保活 → 消息收发 → 连接断开

关键状态：
  - ssidfreshtime 随心跳刷新（秒级）
  - 路由转发时若 now - ssidfreshtime > N 分钟，会话视为失效
  - 断线后客户端重新建立连接，携带 token 恢复会话
```

### 4.3 连接性能指标

| 指标 | 数值 |
|------|------|
| 单机连接数 | 1,000,000（8核16GB） |
| 每连接内存 | ~8KB |
| 连接建立速度 | 5,000/秒 |
| 心跳处理能力 | 100,000/秒 |
