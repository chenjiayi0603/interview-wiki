## 一、高频面试 Q&A

### Q1: 百万长连接如何实现？每连接开销多少？

**每连接开销 ~8KB**：

| 项目 | 大小 |
|------|------|
| Connection 对象 | 2KB |
| 读缓冲（tcp_rmem min） | 1KB |
| 写缓冲（tcp_wmem min） | 1KB |
| ev_io 结构 | 1KB |
| 内核元数据（socket + conntrack） | ~3KB |
| **合计** | **~8KB** |

100 万连接 ≈ 8KB × 1,000,000 = **~8GB 内存**（8核16GB 实例）。

**关键调优**：
- 使用 epoll（边缘触发 ET）
- 调整 `tcp_rmem` / `tcp_wmem` 最小值（减少每连接缓冲）
- 调整 `net.core.somaxconn`（增大连接队列）

### Q2: 消息推送流程是怎样的？

```
MsgServer 产生消息
  → 写入 MongoDB
  → 推送队列
  → PushServer 消费
  → 判断用户在线/离线
     在线：推送到 Access 网关 → 客户端
     离线：离线存储 + 第三方推送（APNs/FCM）
```

### Q3: 未读数如何计算？

**单聊**：
```
未读数 = count(
  msgId > lastReadMsgId AND
  fromId != self AND
  msgState != 4   -- 排除撤回
)
```

**群聊**：额外限制 `cmdType IN [4501, 4505]`（只计聊天/通知类消息）。

**关键规则**：
- `fromId != self`：自己发的消息不影响未读
- `msgState != 4`：撤回消息不算未读
- `lastReadMsgId` 按设备维护，支持已读上报

### Q4: 加密通道如何设计？

采用 **Token + ECDH + RSA + AES** 四层配合：

| 组件 | 算法 | 职责 | 解决什么问题 |
|------|------|------|-----------|
| **Token** | HMAC/签名 | 认证凭证，Redis 缓存 sessionkey | **效率**：重连时免 RSA 解密，直接复用 sessionkey |
| **RSA-2048** | 非对称加密 | 加密传输登录载荷（token + ECDH 公钥） | **第一跳安全**：只有持有私钥的服务器能解密 |
| **ECDH (P-256)** | 密钥协商 | 双方独立生成临时密钥对，计算共享密钥 | **前向安全**：RSA 私钥泄露后历史消息仍安全 |
| **AES-256-GCM** | 对称加密 | 消息内容加密 | **高性能**：AES-NI 硬件加速，500ns/次 |

**三层加密（不含 Token 层）流程**：
```
RSA 加密传输 AES key + ECDH 公钥
  → ECDH 协商共享密钥
  → 派生会话密钥 SK
  → SK 对称加密通信
```

**为什么要 Token**：没有 Token 时，每次重连都要走完整 RSA 解密（0.5ms）→ DB 查询验证（10ms）。有了 Token，重连只查 Redis（0.1ms），且 sessionkey 可复用，**省掉 90%+ 的 RSA 操作**。

**为什么 Token 之后还要 ECDH**：Token 管效率，ECDH 管安全。如果只用 RSA 传输 AES key，攻击者截获后一旦拿到 RSA 私钥，所有历史消息都能解密。ECDH 让双方各自生成临时密钥对，RSA 只传公钥（不是私钥），私钥泄露不影响历史。

**各层定位总结**：
- **Token → 认证提效**（减少 RSA 解密次数）
- **RSA → 身份认证 + 初始信道保护**（第一跳安全）
- **ECDH → 前向安全**（私钥泄露不回溯历史）
- **AES → 消息加密性能**（硬件加速，几乎零成本）

### Q5: 如何支持多设备同时在线？

Redis 登录状态缓存采用 Hash 类型，所有字段带 `${deviceid}` 后缀：

```
Key: 1:2:im:status:userid:${userid}
     logintime:device_1, logintime:device_2, ...
     sessionkey:device_1, sessionkey:device_2, ...
```

每个设备独立管理 sessionkey、loginseq、accnodeidentify，互不干扰。

### Q6: 群聊瓶颈在哪？如何优化？

**瓶颈**：1000 人群发一条消息需推送给 999 人，每次推送查连接位置 + 发送，P99 延迟 200ms。

**优化手段**：
1. **本地聚合**：同一连接服务器的用户批量推送
2. **写扩散**：群消息写入每个用户收件箱（离线场景）
3. **消息序号预分配**：减少分布式协调
4. **增量推送**：只推送新消息，全量拉取走离线通道

### Q7: 父子进程通信为什么用共享内存队列？

原方案使用 Unix domain socketpair，存在三个问题：

| 问题 | 共享内存方案优势 |
|------|----------------|
| syscall 开销大 | mmap 映射，零 syscall（除 semaphore） |
| 多次内存拷贝 | mmap 零拷贝 |
| 内核缓冲区 16-64KB 限制 | 共享内存可配置 MB 级 |

### Q8: 为什么消息存储选 MongoDB 而不是 MySQL？

| 维度 | MySQL | MongoDB |
|------|-------|---------|
| 集群规模 | 64×4=256 套 | 4 分片 |
| CPU | 1024 核 | 64 核（16:1） |
| 内存 | 4096G | 256G（16:1） |
| 磁盘 | 120T | 36T（3.3:1） |

IM 消息的特点是写多读少、数据量大、无复杂事务，MongoDB 的分片集群天然适合。

### Q9: 限流体系如何设计？

**三层架构**：`iptables → Nginx → Access`

| 层 | 限流对象 | 典型阈值 |
|----|---------|---------|
| iptables | 每 IP 连接数、新建连接速率 | 60s/5次 |
| Nginx | 每 IP 并发、每 server 并发、请求频率 | 20000/ip, 5000r/s |
| Access | 单连接消息频率、指定命令字频率 | 应用层控制 |

**原则**：前层阈值宽于后层，避免误杀。

### Q10: Redis 缓存 Key 如何设计？

```
格式：{分段1}:{分段2}:{模块}:{表/功能}:{key字段}:{key值}
示例：1:2:im:status:userid:100122
       ↑ ↑  ↑  ↑       ↑      ↑
       项目 类型 模块  功能   主键列  值
```

**命名规范**：
- 分段1：项目标识（1=IM）
- 分段2：数据类型（1=String 2=Hash 3=Set 4=List）
- 所有设备字段带 `${deviceid}` 后缀

## 三、STAR 面试故事

### 背景 (Situation)

负责雷漫网络 IM 系统的架构升级。原有系统随着用户增长，面临三个核心问题：
1. 单机连接数瓶颈（原架构 10 万连接封顶）
2. 消息推送延迟高（群聊大时 P99 200ms+）
3. 加密通道性能差（全链路 RSA 加密，CPU 开销大）

### 任务 (Task)

设计新一代分布式 IM 架构，目标：
- **单机支持百万连接**，整体支持千万级
- **消息 P99 延迟 < 50ms**（单聊）
- **加密通道性能提升**，加解密不成为瓶颈
- **多设备同时在线**支持

### 行动 (Action)

1. **接入层优化**：
   - C++ 自研 Access 网关，基于 epoll ET + 共享内存队列
   - 每连接内存优化到 ~8KB（调小 tcp_rmem/wmem）
   - 三层限流（iptables → Nginx → Access）

2. **加密通道重构**：
   - ECDH + RSA + AES 三层混合加密替代全链路 RSA
   - RSA 只用于传输临时密钥，后续通信用 AES 对称加密
   - sessionkey 缓存到 Redis，避免重复协商

3. **消息系统**：
   - MongoDB 分片集群替代 MySQL 存储消息（成本 16:1）
   - PushServer 消费队列，在线直接推、离线存+第三方推
   - 群聊写入扩散 + 本地聚合推送

4. **缓存设计**：
   - Redis Hash 多设备隔离（`${deviceid}` 后缀）
   - Codis 分布式缓存扩容
   - 统一 Key 命名规范

### 结果 (Result)

| 指标 | 优化前 | 优化后 |
|------|--------|--------|
| 单机连接数 | 10 万 | 100 万 |
| 单聊 P99 延迟 | 100ms | 30ms |
| 群聊（100人）P99 | 200ms | 50ms |
| 加密通道 CPU | 30% | 8% |
| 多设备支持 | 不支持 | 支持（手机/平板/PC） |

### 指标详解（面试深挖指南）

#### 1. 单机连接数：10 万 → 100 万

**字面意思**：一台 8 核 16GB 服务器，原来只能维持 10 万条 WebSocket 长连接，优化后能维持 100 万条。

**为什么原来是 10 万**：原架构用 Nginx 做 WebSocket 反代，worker_connections 默认 65535，每连接 ~16KB+，到 10 万时 fd 和内存都吃满了。

**为什么能到 100 万**：自研 C++ Access 网关，每连接内存压到 ~8KB：
- Connection 对象 2KB（C++ 结构体，无装箱开销）
- tcp_rmem 调小到 1KB（内核读缓冲最小值）
- tcp_wmem 调小到 1KB（内核写缓冲最小值）
- ev_io 事件结构 1KB
- 内核元数据 ~3KB（fd + conntrack 条目）
- **合计 ~8KB → 100 万 × 8KB = 8GB**，刚好填满 16GB 实例

**面试追问点**：
- "8GB 给连接，业务逻辑跑在哪？" → Access 网关只做转发和加密，PushServer/MsgServer 是独立进程
- "调小 tcp_rmem 会不会丢包？" → 会，但 IM 有应用层 ACK 重传，TCP 丢包由内核重传处理
- "为什么 Nginx 做不到？" → Nginx 是多进程架构，每连接开销 ~16KB+，且 worker_connections 受限于系统 fd 上限

#### 2. 单聊 P99 延迟：100ms → 30ms

**字面意思**：用户 A 发送到用户 B 的消息，99% 在 30ms 内送达（点击发送→对方收到推送）。

**为什么原来是 100ms**：
- 消息路径：`MsgServer → MySQL 存储(10-30ms) → 查用户在线 → 推送`
- 全链路 RSA 加密的连锁反应：RSA 密钥协商慢、会话 key 有效期短需频繁重协商，高并发下 CPU 排队，消息整体延迟被拉高

**为什么能降到 30ms**：
1. **MongoDB 替代 MySQL**：MongoDB 写入比 MySQL 快 3-5 倍（写多读少场景），分片集群并行写
2. **混合加密替代全链路 RSA**：RSA 只在登录用一次，后续 AES 对称加密（纳秒级，比 RSA 快 1000 倍）
3. **推送路径直连**：`MsgServer → 队列 → PushServer → 在线直接推`，去掉了不必要的 DB 查询

**面试追问点**：
- "P99 30ms，那最慢的 1% 卡在哪？" → 通常是 GC 停顿、内核调度抖动、大消息阻塞写缓冲
- "怎么处理那 1%？" → 消息大小分级（大消息走独立通道）、绑核减少调度抖动

#### 3. 群聊（100人）P99：200ms → 50ms

**字面意思**：100 人群发一条消息，99% 的情况下 50ms 内所有成员都能收到。

**为什么原来是 200ms**：
- 1 条消息推 99 个人 = **99 次推送**
- 每次推送：查 Redis 路由位置(1ms) + 网关写缓冲(1ms) ≈ 2ms
- 99 × 2ms = 198ms → 接近 200ms
- 延迟随人数线性增长

**为什么能降到 50ms**：
- **本地聚合推送**：群成员按网关分组，同一网关的用户批量推送
  - 100 人分布在 4 台网关 → 只查 4 次路由 → 4 次批量推送
  - 99 次 RPC 降为 4 次，延迟从 198ms 降到 ~8ms
- **写扩散 + 消息序号预分配**：离线用户从收件箱拉取，减少实时推送压力

**面试追问点**：
- "1000 人群呢？" → 当前 500 条/秒 P99 200ms，瓶颈在写扩散写入量（1 条消息写 999 个收件箱），优化方向是读扩散 + 本地缓存
- "@所有人 与普通消息区别？" → notifyType 标记不同，推送路径相同

#### 4. 加密通道 CPU：30% → 8%

**字面意思**：整个加密通道（登录认证 + 消息加解密）消耗的 CPU 从 30% 降到 8%。

**RSA 用在哪**：只在登录认证阶段解密 token，**不会每条消息都 RSA 加解密**。消息内容走对称加密。

**为什么原来是 30%**：问题不在 RSA 慢（单次 0.5ms），而在 **每次重连都要完整走一遍 RSA**：

| 场景 | 原方案 | CPU 开销 |
|------|--------|---------|
| 新建连接 | RSA 解密 token + 协商 sessionkey | 0.5ms，仅 1 次可接受 |
| **断线重连** ⭐ | 同上，重走一遍 RSA | 10 万连接 × 高频重连 → RSA 打满 CPU |
| 会话 key 过期 | 重新 RSA 协商新 key | 过期时间短时反复出现 |

10 万长连接下，移动网络波动、切后台、心跳超时导致重连率极高，每次重连都 RSA 解密 0.5ms，纯软件无硬件加速，CPU 堆积到 30%。

**为什么能降到 8%**：核心是 **Token + Redis 缓存 sessionkey**，让重连免 RSA：

| 手段 | 作用 | CPU 节省 |
|------|------|---------|
| **Token + Redis 缓存 sessionkey** ⭐ | 重连接查 Redis 复用 sessionkey，不走 RSA | **省 90%+ RSA 操作** ← 主因 |
| ECDH 替代 RSA 做密钥协商 | ECDH P-256 快 10 倍 | 初次登录协商更快 |
| AES-NI 硬件加速 | AES-256-GCM 500ns/次 | 消息加解密几乎零成本 |
| 会话 key 长期有效 | 存 Redis，避免频繁轮换 | 减少协商次数 |

**核心结论**：30% → 8% 的改善，**Token + Redis 缓存是主因**（消除了高频重连的 RSA 开销），ECDH 和 AES-NI 是安全架构升级带来的附加收益。

**面试追问点**：
- "AES key 传输安全吗？" → RSA 加密 + ECDH 前向安全，即使 RSA 私钥泄露也无法解密历史消息
- "前向安全什么意思？" → 每次登录独立协商 sessionkey，历史密钥不受当前私钥泄露影响

#### 5. 多设备支持：不支持 → 支持（手机/平板/PC）

**字面意思**：用户可在手机、平板、PC 同时在线，各设备互不干扰。

**为什么原来不支持**：账号体系是 "一个用户一个 session"，Redis 里用户状态只有一个字段，新设备登录踢旧设备下线。

**为什么能支持**：Redis Hash 的 `${deviceid}` 后缀实现设备维度隔离：

```
Key: 1:2:im:status:userid:${userid}
Fields:
  sessionkey:device_A   # 手机独立密钥
  sessionkey:device_B   # 平板独立密钥
  accnodeidentify:device_A  # 手机连网关A
  accnodeidentify:device_B  # 平板连网关B
```

每个设备独立管理 sessionkey（加密互不影响）、loginseq（防重登互不干扰）、accnodeidentify（可路由到不同网关）、status（手机 PC 在线状态独立）。

**消息推送逻辑**：遍历用户所有 device 字段，逐个判断在线状态→手机在线推手机、手机关机走 APNs、PC 在线推 PC、PC 离线不推（PC 无第三方推送）。

**面试追问点**：
- "多设备已读未读怎么算？" → lastReadMsgId 按设备维护，手机已读不影响 PC 的未读数
- "手机 PC 同时在线，消息重复提醒怎么办？" → 业务层策略（如 PC 登录时手机静音），架构层只负责按设备推送
