# 服务网格架构设计

> K8s + Istio + Envoy 架构、CRD 灰度发布、Sidecar 性能数据。

---

## 一、系统架构

### 1.1 总体架构

```
                         控制面 (Istiod)
  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐
  │ Pilot    │  │ Mixer    │  │ Citadel  │  │ Galley   │
  │ (xDS下发)│  │ (遥测)   │  │ (证书)   │  │ (配置验证)│
  └─────┬────┘  └──────────┘  └──────────┘  └──────────┘
        │ xDS (CDS/EDS/LDS/RDS/ADS...)
        ▼
                         数据面 (Envoy)
  ┌─────────┐  ┌─────────┐  ┌─────────┐  ┌─────────┐
  │ Pod A   │  │ Pod B   │  │ Pod C   │  │ Pod D   │
  │ ┌─────┐ │  │ ┌─────┐ │  │ ┌─────┐ │  │ ┌─────┐ │
  │ │ App │ │  │ │ App │ │  │ │ App │ │  │ │ App │ │
  │ └──┬──┘ │  │ └──┬──┘ │  │ └──┬──┘ │  │ └──┬──┘ │
  │ ┌──┴──┐ │  │ ┌──┴──┐ │  │ ┌──┴──┐ │  │ ┌──┴──┐ │
  │ │Envoy│ │  │ │Envoy│ │  │ │Envoy│ │  │ │Envoy│ │
  │ └─────┘ │  │ └─────┘ │  │ └─────┘ │  │ └─────┘ │
  └─────────┘  └─────────┘  └─────────┘  └─────────┘

  iptables 规则：inbound 拦截 → Envoy(in) → App → Envoy(out) → 下游
```

### 1.2 核心组件

| 组件 | 职责 | 说明 |
|------|------|------|
| **Istiod** | 控制面 | 将 VirtualService/DestinationRule 转为 xDS，下发给 Envoy |
| **Envoy Sidecar** | 数据面代理 | 拦截 Pod 进出流量，执行路由/熔断/观测 |
| **Go SDK** | 业务接入层 | 封装服务发现、负载均衡、元数据透传（见 02 文件） |
| **Wasm 插件** | 自定义治理逻辑 | 在 Envoy filter 层执行自适应熔断（见 03 文件） |

### 1.3 请求链路

```
客户端 → Ingress Gateway → (Envoy) → Service A Pod
                                          │
                                     Envoy(in) 拦截 (iptables)
                                        ↓
                                    健康检查 → Readiness
                                        ↓
                                    应用进程
                                        ↓
                                     Envoy(out) → Service B
```

**数据面路径**：
```
客户端 → {iptables 拦截} → Envoy(in) → {本地应用} → Envoy(out) → {iptables 转发} → 下游服务
```

## 二、Istio 流量管理

### 2.1 核心配置对象

| 资源 | 作用 | 关键字段 |
|------|------|---------|
| **VirtualService** | 定义路由规则 | hosts, http.route, match, destination.weight |
| **DestinationRule** | 定义目标策略 | subsets, trafficPolicy(loadBalancer/connectionPool/outlierDetection) |
| **Gateway** | 网格入口/出口 | selector, servers.port/hosts |
| **ServiceEntry** | 注册外部服务 | hosts, ports, resolution |

### 2.2 CRD 灰度发布

**自定义资源 AppGroup**：
```yaml
apiVersion: apps.zego.im/v1alpha1
kind: AppGroup
metadata:
  name: appgroup-sample
spec:
  replicaCount: 3
  template:
    selector:
      matchLabels:
        app: appgroup-sample
      containers:
        - image: centos:7
          name: sleep
  original:
    containers:
      - image: centos:7
        name: sleep
  canaryScale: 0         # 灰度比例 0-100
```

**Operator 灰度逻辑**：
```
收到 CRD 变更 → 计算灰度权重 → 修改 VirtualService

originSubset[i].Weight = originSubset[i].Weight * (100 - canaryScale) / weightSum
canaryR.Weight = canaryR.Weight * canaryScale / weightSum
canaryR.Destination.Subset = fmt.Sprintf("canary-%s", canaryR.Destination.Subset)
```

| 操作 | 动作 |
|------|------|
| 增加灰度比例（canaryScale ↑） | 创建金丝雀 Deployment，修改 VS weight |
| 减少灰度比例（canaryScale ↓） | 减少金丝雀 Pod 数量，恢复 VS weight |
| 灰度结束（canaryScale = 0） | 清理金丝雀资源，流量全切到新版本 |

## 三、Sidecar 性能开销

### 3.1 QPS 压测数据

| 场景 | QPS | P99 延迟 | 开销 |
|------|-----|---------|------|
| 无 Sidecar（直连） | 80,000 | 2ms | 0% |
| 有 Sidecar（无插件） | 72,000 | 3ms | ~10% |
| 有 Sidecar（+Wasm 熔断） | 68,000 | 4ms | ~15% |
| 熔断触发时 | 60,000 | 50ms | 部分请求被拦截 |

### 3.2 开销组成

```
开销分布：
1. Envoy 代理转发：+0.5ms × 2（in + out）= +1ms
2. Wasm 插件执行：+0.5ms
3. 统计指标收集：+0.2ms
4. 连接池管理：+0.3ms
总开销约 +2ms，QPS 损失约 15%
```

### 3.3 远程真实环境压测

| 场景 | 平均延迟 | QPS |
|------|---------|-----|
| 直连（无代理） | 110ms | 886.8 |
| 单 Envoy（UDS + iptables × 1） | 139ms | 620.5 |
| 双 Envoy（UDS + iptables × 2 + 路由策略） | 149ms | 581.1 |

**结论**：增加 ~30% 延迟，降低 ~40% QPS（iptables 拦截 + UDS + 代理转发累计开销）。

### 3.4 优化手段

| 手段 | 效果 |
|------|------|
| 连接池调优（HTTP2 复用） | 减少连接建立开销 |
| 精简 Wasm 插件逻辑 | 减少每次请求处理时间 |
| 降采样 Access Log | 减少 IO |
| 启用 gRPC 协议复用 | 减少序列化开销 |
| Sidecar 资源分配 limits | 避免资源争抢 |

## 四、K8s 基础与网格协同

### 4.1 Service / Ingress / Istio Gateway 区别

| 资源 | 层 | 用途 |
|------|-----|------|
| **Service** | L4 | 集群内服务发现与负载均衡 |
| **Ingress** | L7 | K8s 原生七层入口，由 Ingress Controller 实现 |
| **Istio Gateway** | L7 | 网格入口/出口流量管理，配合 VirtualService 实现细粒度路由 |

### 4.2 Deployment vs StatefulSet

| 资源 | 适用场景 | 特点 |
|------|---------|------|
| **Deployment** | 无状态服务 | 副本可替换，滚动更新 |
| **StatefulSet** | 有状态服务 | 稳定网络标识，持久化存储 |

### 4.3 Readiness / Liveness / HPA

- **Readiness**：是否可接流 → 网格场景下更关键，未就绪实例会被 Service 摘流
- **Liveness**：进程是否存活 → 失败触发重启
- **HPA**：根据 CPU/自定义指标扩缩容 → 扩容后需连接预热 + 渐进放量

### 4.4 优雅退出流程

```
Pod 收到 SIGTERM
  → preStop 钩子（发起 /quitquitquit）
  → Readiness 返回失败（Service 摘流）
  → 等待 terminationGracePeriodSeconds
  → 进程退出
```

### 4.5 常见故障排查路径

```
1. Pod 状态和事件：Pending / CrashLoopBackOff / OOMKilled
2. Service Endpoint 是否就绪
3. Istio 路由对象（VirtualService / DestinationRule）是否匹配
4. Envoy 配置与指标（xDS 下发状态、5xx、upstream reset）
```
