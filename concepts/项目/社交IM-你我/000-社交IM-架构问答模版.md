## 一、项目复盘与架构设计

**考察点**：业务理解深度 & 架构设计能力

### 1.1 背景：项目定位与目标

我主导的是 **"你我金融"社交金融 IM 系统**，定位为**金融场景下的即时通讯平台**，承载借贷业务中的沟通、风控、项目协作等核心场景。系统从 0 开始建设，在 3 年半内增长到 **1000 万+ 注册用户，500 万月活，300 万日活**。

核心业务场景包括：
- **金融 IM 通讯**：单聊、群聊（项目群/业务群/讨论组），日均消息量数亿条
- **社交关系链**：好友、关注、粉丝、通讯录匹配，支撑借贷双方的信任连接
- **你我圈（朋友圈）**：类微信朋友圈的社交动态，点赞、评论、转发
- **金融特有场景**：尽调群、借款人/投资人沟通群、风控消息推送、红包转账
- **公众号平台**：系统通知、业务消息推送（如借款进度、还款提醒）

### 1.2 难点：技术与业务上的核心挑战

**挑战一：从 0 到 1000 万的架构演进压力**

系统经历了 4 个阶段的架构演进，每个阶段都有阵痛：

| 阶段 | 时期 | 架构 | 核心问题 | 峰值 QPS |
|------|------|------|---------|---------|
| V1.0 | 2015 | 单体应用 + 单机 MySQL + Redis | 单点故障，扩展性差，QPS 2,000 就告警 | 2,000 |
| V2.0 | 2016 | 垂直拆分（IM/社交/金融），Redis 缓存 | 消息表单表数亿条，查询越来越慢 | 5,000 |
| V3.0 | 2017 | 水平分片（32库×64表），Codis 集群 | 跨库查询需要聚合，缓存穿透严重 | 15,000 |
| V4.0 | 2018 | 服务化拆分 + 消息队列削峰 | 运维复杂度增加，分布式事务难 | 15,000（稳定） |

**挑战二：金融场景的特殊要求**

- **敏感词过滤**：金融平台对合规要求极高，需实时过滤涉赌、涉贷、涉诈骗等敏感词
- **数据安全**：用户手机号加密存储，通讯录匹配需脱敏处理
- **消息可靠性**：借贷相关的聊天记录不能丢失，需永久保存
- **实名制关联**：IM ID 与业务 GUID 映射，支持风控追溯

**挑战三：性能瓶颈**

- 早高峰 8-9 点 QPS 飙升至 15,000，是低谷的 15 倍
- 消息积压导致推送延迟，用户投诉
- 单表数据量达到数亿级别，查询延迟从 ms 级飙升到秒级

### 1.3 收益：最终交付的业务/技术价值

**业务价值：**
- 支撑了公司从 0 到 1000 万用户的业务增长，成为金融借贷场景的核心通信基础设施
- 消息延迟控制在 **50ms 以内**，确保借贷沟通实时性
- 系统可用性达到 **99.99%**（4 个 9），金融业务不中断

**技术价值：**

| 指标 | V1.0（优化前） | V4.0（优化后） | 提升 |
|------|--------------|--------------|------|
| 峰值 QPS | 2,000 | 15,000 | **7.5x** |
| 单表数据量 | 数亿行 | < 500 万行 | **99%+ 缩减** |
| 缓存命中率 | — | 95% | 从 0 到 95% |
| 缓存穿透率 | 极高 | 降低 90% | 布隆过滤器 |
| 高峰期抖动 | 严重 | 降低 80% | MQ 削峰 |
| 分库分表 | 无 | 32 库 × 64 表 | 标准化分片 |

### 1.4 反思：系统设计的缺陷与优化方向

**当前不足：**
1. **C++ 技术栈维护成本高**：自研的 DataProxy + DBAgent 中间件代码量大，新成员上手慢。如果重做会考虑 Go 或 Rust。
2. **分片键单一**：按 user_id 取模分片，群聊消息按 group_id 分片，导致群成员查询需要广播到所有分片。应引入**分片路由表**或 **Elasticsearch** 做二级索引。
3. **冷热分离不彻底**：MongoDB 只做简单的数据归档，没有做生命周期管理（TTL）、数据压缩和检索优化。应考虑 **TiDB** 或 **ClickHouse** 做实时分析。
4. **缺乏配置中心**：分片规则、连接池配置等硬编码在 C++ 代码中，修改需要重启。应用 **etcd/Consul** 配置中心。
5. **监控体系薄弱**：只有基础的 QPS 和延迟监控，缺乏**全链路追踪**（类似 Dapper）和 **SLA 告警**。

**如果重来，我会：**
- 技术栈选型上，核心链路用 C++ 追求极致性能，业务逻辑用 Go/Rust 降低维护成本
- 引入 **Proxy 层（如 ShardingSphere-Proxy）** 透明化分库分表
- 采用 **Kafka + Flink** 做实时消息流处理（替代自研 MQ 组件）
- 补充 **APM（SkyWalking/Pinpoint）** 实现全链路追踪

## 二、性能优化与平滑迁移

**考察点**：性能优化 & 不停机迁移能力

场景：将**单体服务**重构为**支持高并发的微服务架构**。

### 2.1 拆分思路：按业务域拆分解耦

我们采用**垂直拆分 + 水平拆分**两阶段策略：

**第一阶段 - 垂直拆分（V2.0，2016 年）：**
将单体按业务域拆分为 4 个独立服务：

```
原本单体架构：
┌─────────────────────────────────────┐
│  IM Server（登录 + 消息 + 好友 + 动态）│
└─────────────────────────────────────┘

拆分后：
┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐
│ IM 服务   │ │ 社交服务  │ │ 金融服务  │ │ 推送服务  │
│ 单聊/群聊  │ │ 好友/关系 │ │ 借贷/风控 │ │ APNs/个推 │
│ 消息存储  │ │ 你我圈   │ │ 红包/转账 │ │ 短信通知  │
└──────────┘ └──────────┘ └──────────┘ └──────────┘
      │            │            │            │
      └────────────┴────────────┴────────────┘
                     │
            ┌────────▼────────┐
            │ 统一 Da﻿taProxy   │（C++ 自研中间件）
            │ Redis + MySQL   │
            └─────────────────┘
```

**拆分原则：**
- **高内聚低耦合**：每个服务拥有独立的数据库（按业务域分库）
- **接口标准化**：服务间通过 Protobuf + TCP 长通信（自定义协议），HTTP REST 用于外部
- **数据私有化**：每个服务只能访问自己的数据库，跨服务数据通过 API 获取

**第二阶段 - 水平拆分（V3.0，2017 年）：**
对 IM 服务的消息表做**水平分片**：

```cpp
// 分片规则：32 个库 × 64 张表 = 2048 张物理表
int GetShardId(uint64_t user_id) { return user_id % 32; }
int GetTableId(uint64_t user_id) { return (user_id / 32) % 64; }

// 容量验证
// 1000 万用户 × 100 条消息 = 10 亿条
// 2048 张表 → 每表 ~48.8 万条（< 500 万设计目标）
```

**关键设计决策：** 不采用一致性哈希（避免迁移复杂度），直接用 **user_id % 32** 静态分片，配合 **DBRouter 中间件**透明化路由。

### 2.2 集群扩容策略

**扩容方案——按号段 + Group 复制：**

原始设计文档中采用**号段分库**（每 500 万 imid 一个库），实际落地时我们做了调整。

最终采用的 **32 库方案**，在扩容时：

```
扩容前：16 个物理库（16 分片）
扩容后：32 个物理库（32 分片）
迁移策略：在线双写 + 渐进式数据迁移
```

**具体步骤：**
1. 新部署 16 个从库，与老库建立复制关系
2. 配置中心下发新的分片规则，**灰度发布**（先 1% 流量验证）
3. 应用层代码**双写**：新分片规则计算出的新库和老库同时写入
4. 后台**数据校验任务**：比对双写的 16 个新库 vs 老库，修复不一致
5. 读流量逐步切换到新库（灰度 1% → 10% → 50% → 100%）
6. 确认无误后，下线老库

**扩容的关键保障措施：**
- **灰度切流**：按用户 ID 范围灰度，先切内部用户，再切外部用户
- **回滚预案**：一旦发现数据不一致，立即将读流量切回老库
- **一致性校验**：定时任务扫描双写数据，差异报警 + 自动修复

### 2.3 压测方案

**压测模型设计：**

```
压测脚本模拟 4 类典型用户行为：
1. 高频聊天用户（60%）：秒级发消息、收消息
2. 社交活跃用户（20%）：刷好友列表、查看动态、点赞
3. 金融交互用户（15%）：创建项目群、发送借款消息
4. 静默用户（5%）：仅上线、接收推送
```

**压测工具**：自研 C++ 压测客户端（基于实际通讯协议）+ 分布式压测节点

**压测流程：**

| 阶段 | 目标 | 方法 |
|------|------|------|
| 基准测试 | 获取单节点基线 | 单进程单连接，逐步加压到瓶颈 |
| 容量测试 | 找出系统极限 | 逐步增加并发用户数（1K→5K→10K→20K） |
| 稳定性测试 | 72 小时持续运行 | 模拟真实流量曲线（早晚高峰 15 倍波动） |
| 容错测试 | 验证降级/熔断 | 随机杀掉服务/数据库节点，观察系统行为 |

**瓶颈定位与优化（实测数据）：**

| 场景 | 单节点 QPS | 瓶颈 | 优化方案 |
|------|-----------|------|---------|
| HTTP 裸响应 | 23,256 | — | — |
| 写路径（Web→DataProxy→Redis→DBAgent→MySQL） | 1,861 | MySQL 单分片 | 分库分表 + 批量写 |
| 读路径（Web→DataProxy→Redis→DBAgent→MySQL） | 929 | MySQL 单分片 | Redis 缓存 + 布隆过滤器 |
| DataProxy→Redis 读 | 14,658 | 网络带宽 | 连接池 + Pipeline |

**压测阈值设定：**
- CPU > 75% 触发扩容告警
- 单表查询延迟 > 50ms 触发慢查询分析
- Redis 内存 > 80% 触发淘汰策略检查
- 连接池利用率 > 70% 触发扩容

### 2.4 双写双读切换流程

**背景**：从 V2.0 直接升级到 V3.0（水平分片），涉及在**不停机**的情况下将单库数据迁移到 32 库 × 64 表。

**完整切换流程：**

```
Step 1: 准备阶段（T - 7 天）
  ├── 部署 32 个 MySQL 实例，初始化 2048 张分表
  ├── 搭建数据迁移管道（C++ 数据导出导入工具）
  ├── 验证分片规则正确性（全量数据校验）
  └── 部署 DBRouter 中间件灰度版本

Step 2: 全量迁移（T - 3 天）
  ├── 从老库全量导出数据，按分片规则写入新库
  ├── 每迁移完一批数据，做一致性校验（COUNT + CHECKSUM）
  └── 记录迁移断点（支持续传）

Step 3: 增量同步（T - 0 天）
  ├── 应用层开启双写：业务请求同时写入老库和新库
  ├── 增量比对任务持续运行（延迟 < 1 分钟）
  └── 灰度切流策略：
       ├── 第 1 批：内部白名单用户（0.1%），观察 2 小时
       ├── 第 2 批：5% 用户，观察 4 小时
       ├── 第 3 批：20% 用户，观察 8 小时
       ├── 第 4 批：50% 用户，观察 12 小时
       └── 第 5 批：100% 用户，全量切换

Step 4: 回滚预案（随时可用）
  ├── 读回滚：将读流量切回老库（秒级生效）
  ├── 写回滚：关闭双写，回到单库写入
  └── 数据修复：若发现不一致，增量比对任务自动修复

Step 5: 收尾阶段（T + 7 天）
  ├── 关闭老库写流量，保留只读
  ├── 继续运行一致性比对 7 天
  └── 确认无误后下线老库
```

**双写的核心技术要点：**

```cpp
// 双写逻辑伪代码（C++）
void WriteMessage(const Message& msg, uint64_t user_id) {
    // 1. 先写老库
    old_db->Execute(INSERT_SQL, msg);
    
    // 2. 计算新分片
    int shard_id = user_id % 32;
    int table_id = (user_id / 32) % 64;
    
    // 3. 写新库（带重试）
    int retry = 3;
    while (retry-- > 0) {
        if (new_db_pool_[shard_id]->Execute(INSERT_SQL, msg)) {
            break;
        }
    }
    
    // 4. 写失败记录到补偿队列
    if (retry <= 0) {
        compensation_queue_.Push({user_id, msg, shard_id, table_id});
    }
}
```

## 三、复杂故障与分层止损

**考察点**：复杂故障处理 & 架构根治能力

### 3.1 真实故障场景复盘

**场景**：某日早高峰（8:00-9:00），系统整体 QPS 飙升至 15,000，**消息发送链路**出现批量超时，影响用户发消息。

**故障链路**：
```
客户端 → Nginx → IM 服务 → DataProxy → Redis（消息缓存）→ DBAgent → MySQL（持久化）
```

**现象**：
- 消息发送成功率从 99.9% 下降到 95%
- 单条消息延迟从平均 50ms 飙升到 3-5s
- MySQL 的 CPU 使用率 100%，慢查询堆积
- 大量连接超时，导致连接池耗尽

### 3.2 分层止损预案（即时应对）

**第一层 — 客户端（秒级止损）：**

| 策略 | 实现 |
|------|------|
| **客户端重试退避** | 指数退避（1s → 2s → 4s → 8s），最多 3 次 |
| **本地消息缓存** | 消息先写入客户端本地 SQLite，后台异步发送 |
| **降级提示** | 显示"网络繁忙"文案，不阻塞用户操作 |

**第二层 — Nginx 接入层（秒级止损）：**

| 策略 | 实现 |
|------|------|
| **速率限制** | `limit_req zone=im_api 2000r/s`（超出返回 429） |
| **连接数限制** | `limit_conn im_conn 10000` |
| **熔断** | 检测后端错误率 > 10% 时，直接返回降级响应 |
| **IP 黑名单** | 异常流量来源自动封禁 |

**第三层 — IM 服务层（秒级 — 分钟级止损）：**

```cpp
// 熔断器实现（C++）
class CircuitBreaker {
    enum State { CLOSED, OPEN, HALF_OPEN };
    
    bool AllowRequest() {
        if (state_ == OPEN) {
            // 熔断打开，快速失败
            if (time(0) - last_open_time_ > recovery_timeout_) {
                state_ = HALF_OPEN;  // 半开尝试
                return true;
            }
            return false;
        }
        return true;
    }
    
    void OnFailure() {
        failure_count_++;
        // 10 秒内失败率超过 50%，打开熔断
        if (failure_count_ > threshold_ && 
            failure_rate_ > 0.5) {
            state_ = OPEN;
            last_open_time_ = time(0);
        }
    }
};
```

具体措施：
- **服务降级**：关闭非核心功能（如"你我圈"动态推荐、附近的人），释放线程资源给核心消息通道
- **本地队列缓冲**：将消息写入本地内存队列，后台线程批量写入 DB（削峰填谷）
- **限流**：基于令牌桶算法，按用户等级分配配额（VIP 用户优先保障）

**第四层 — DataProxy 中间件层（分钟级止损）：**

| 策略 | 实现 |
|------|------|
| **读降级** | 热点 key 直接走 Redis，不穿透到 DB |
| **写缓冲** | 消息先写入 Redis，异步刷入 MySQL（最终一致性） |
| **连接池保护** | 最大连接数硬限制，防止 MySQL 被打垮 |
| **超时控制** | 单次查询超时 500ms，超时直接返回错误，不重试 |

**第五层 — MySQL 存储层（分钟级 — 小时级止损）：**

| 策略 | 实现 |
|------|------|
| **慢查询 Kill** | 检测运行时间 > 10s 的查询，自动 Kill |
| **读写分离** | 读流量切到从库，释放主库 CPU |
| **连接数限制** | `max_connections=500`，超出拒绝连接 |
| **紧急限流** | 限制批量查询的并发数 |

### 3.3 事后的架构根治方案（长期修复）

**根因定位：**

通过分析慢查询日志和链路追踪，发现三个根因：

1. **缓存穿透**：某用户批量查询不存在的历史消息，Redis 未命中 → 直接打到 MySQL，MySQL 扛不住
2. **热 key 问题**：某大 V 用户在群发消息，导致其所在分片成为热点，该分片 MySQL 成为瓶颈
3. **索引失效**：部分查询未带 user_id 条件，走了全表扫描

**架构根治方案：**

**方案一：布隆过滤器（解决缓存穿透）**

```
请求 → 布隆过滤器 → Redis → MySQL
         ↓（不存在）
        直接返回（穿透率降低 90%）
```

```cpp
// BloomFilter 实现（基于 Redis Bitmap）
class BloomFilter {
    // 使用多个 Hash 函数
    vector<uint64_t> Hash(const string& key) {
        return {fnv_hash(key), murmur_hash(key), city_hash(key)};
    }
    
    bool MightContain(const string& key) {
        auto hashes = Hash(key);
        for (auto h : hashes) {
            int bit = h % bitmap_size_;
            if (!redis_->GetBit(bloom_key_, bit)) {
                return false;  // 一定不存在
            }
        }
        return true;  // 可能存在
    }
};
```

**方案二：MQ 削峰填谷（解决流量抖动）**

```
消息发送 → Kafka → Flink（流处理）→ Redis（缓存）→ 批量写入 MySQL
                                                  ↓
                                            MQ 削峰（波动降低 80%）
```

引入 RabbitMQ 做异步解耦：
- **消息推送**：发送方推到 MQ，接收方异步拉取，不再同步等待推送结果
- **离线消息**：MQ 缓冲离线消息，用户上线后批量拉取
- **日志采集**：MQ 异步落盘，不阻塞主业务逻辑

**方案三：连接池治理**

```cpp
// 动态连接池（自动扩容/缩容）
class DynamicConnectionPool {
    void AdjustPoolSize() {
        if (current_load_ > max_load_ * 0.7) {
            // 扩容
            ExpandPool(min(2 * current_size_, max_size_));
        } else if (current_load_ < max_load_ * 0.3) {
            // 缩容
            ShrinkPool(current_size_ / 2);
        }
    }
};
```

**方案四：读写分离 + 延迟容忍**

- **写路径**：Redis（主缓存）→ MySQL Master（持久化）→ 异步刷入 MongoDB（冷备）
- **读路径**：优先 Redis → 其次 MySQL Slave → 最后 MongoDB
- **最终一致性容忍**：金融场景下，消息的写入延迟 < 1s 可接受

**方案五：全链路超时治理**

| 层级 | 超时设置 | 重试策略 |
|------|---------|---------|
| 客户端 → Nginx | 5s | 指数退避，最多 3 次 |
| Nginx → IM 服务 | 3s | 重试 1 次（幂等接口） |
| IM 服务 → DataProxy | 1s | 不重试（快速失败） |
| DataProxy → Redis | 500ms | Pipeline 自动重试 |
| DataProxy → MySQL | 500ms | 不重试（返回给上游处理） |

## 四、AI 应用与任务编排

**考察点**：AI 技术应用 & 分布式任务编排

> 说明：该项目为 2015-2019 年度的社交金融 IM 系统，当时 AI 应用主要集中在**规则引擎**和**关键词过滤**层面。以下结合项目的实际场景，阐述在搜索、审核、推荐等环节中的类 AI 架构设计。如果面试官追问当前 AI 技术理解，可以结合 Transformer / 大模型的发展趋势展开。

### 4.1 项目中涉及的"类 AI"场景

**场景一：敏感词 DFA 匹配（规则引擎）**

虽然没有用深度学习，但我们实现了**高性能的敏感词过滤引擎**——基于 DFA（确定有限状态自动机）算法，可以视为 **AI 规则引擎的雏形**。

```
敏感词库（Redis Set）→ DFA 编译器（构建 Trie 树）→ 在线匹配引擎
```

| 方案 | 时间复杂度 | 空间复杂度 | 更新难度 |
|------|-----------|-----------|---------|
| DFA（Trie 树） | O(n) | 中 | 低（热更新词库） |
| 正则匹配 | O(n×m) | 低 | 中 |
| AC 自动机 | O(n) | 高 | 高 |

选择 DFA 的原因：在 2015 年没有成熟的 NLP 服务可用，自研 DFA 引擎实现**毫秒级过滤**，并且支持**热更新词库**（运营后台随时增删敏感词）。

**场景二：智能推荐"附近的人"（基于 LBS + 协同过滤）**

虽然算法不复杂，但涉及**召回 → 排序**的经典推荐架构：
```
召回层：Redis Geo 查询附近 1000 人
排序层：按活跃度、信用分、共同好友数排序
过滤层：黑名单过滤、性别筛选、关系过滤
```

**场景三：通讯录好友匹配（类 Embedding 思路）**

用户上传通讯录 → MD5 加密手机号 → 与平台用户做**集合匹配**，本质上可以看作最简单的**向量检索**（手机号作为唯一标识）。

### 4.2 分布式离线任务编排（敏感词库更新）

**问题描述**：敏感词库需要定时从运营后台同步到所有 Redis 节点，涉及**分布式任务编排**。

**实际架构**（2017 年方案）：

```
┌──────────────┐     ┌──────────────────┐     ┌─────────────────┐
│ 运营后台      │     │ 任务调度中心       │     │ DFA 编译集群     │
│ 新增敏感词    │ →   │ (自研 C++ 调度器)  │ →   │ (4 节点并行编译)  │
└──────────────┘     └──────────────────┘     └─────────────────┘
                                                    │
                          ┌─────────────────────────┼──────────┐
                          │                         │          │
                     ┌────▼────┐              ┌────▼────┐     │
                     │ Redis 1 │  ...         │ Redis 16│     │
                     └─────────┘              └─────────┘     │
                                                              ▼
                                                    ┌─────────────────┐
                                                    │ 全量比对 + 告警  │
                                                    └─────────────────┘
```

**任务调度设计：**

| 需求 | 实现方案 |
|------|---------|
| **幂等性** | 每个词条有唯一 ID，编译任务 ID = hash(词库版本 + 时间戳)，重复提交自动去重 |
| **节点宕机** | 调度器心跳检测（3s 超时），宕机节点上的任务自动重新分配给其他节点 |
| **资源抢占** | 每个 DFA 编译节点最多同时运行 2 个任务，超出排队等待 |
| **版本一致性** | 所有 Redis 节点更新后才切换词库版本，原子切换（Redis Lua 脚本） |
| **回滚** | 保留上一版本词库快照，发现问题一键回滚 |

**关键实现：**

```cpp
// 任务幂等性控制
class SensitiveWordTask {
    string GetTaskId() {
        // 任务 ID = 词库版本 + 编译时间戳
        return "dfa_compile_" + version_ + "_" + 
               to_string(timestamp_ / 60);  // 1 分钟内幂等
    }
    
    bool IsDuplicate() {
        // Redis SETNX 检查任务是否已执行
        return redis_.SetNx("task:" + GetTaskId(), "running") == 0;
    }
};

// 节点故障检测
class HealthChecker {
    void Check() {
        for (auto& node : nodes_) {
            auto last = redis_.Get("heartbeat:" + node.id);
            if (time(0) - last > 3) {  // 3s 无心跳
                // 重新分配该节点上的任务
            }
        }
    }
};
```

**编排方式对比：**

| 维度 | 中心化调度（我们当前方案） | 去中心化调度 |
|------|-------------------------|-------------|
| 一致性 | 强一致（状态统一管理） | 最终一致（Gossip 协议） |

| 适用场景 | 任务类型固定、规模可控 | 大规模、高动态场景 |

```
调度器记录任务状态：PENDING → RUNNING → SUCCESS / FAILED
重复提交检查：Redis SETNX + 分布式锁
```

**资源抢占控制：**
```cpp
// 基于优先级队列的资源调度
class ResourceScheduler {
    struct Task {
        string id;
        int priority;  // 1-10，越高越优先
        int cpu_cores;
        int memory_gb;
    };
    
    Task* Schedule() {
        // 按优先级排序，同优先级按等待时间 FCFS
        sort(tasks_.begin(), tasks_.end(), 
             [](const Task& a, const Task& b) {
                 if (a.priority != b.priority)
                     return a.priority > b.priority;
                 return a.wait_time > b.wait_time;
             });
        
        // 检查资源是否充足
        for (auto& task : tasks_) {
            if (available_cpu_ >= task.cpu_cores &&
                available_mem_ >= task.memory_gb) {
                return &task;
            }
        }
        return nullptr;
    }
};
```

### 5.2 常见追问应对

**追问 1："为什么选 C++ 而不是 Go/Java？"**

> **回答思路**：承认历史原因 + 客观分析利弊 + 展示技术前瞻性
> 
> "2015 年选 C++ 有几个原因：1）团队核心成员 C++ 背景，快速出活；2）IM 场景对内存和 CPU 敏感，C++ 性能最优；3）当时 Go 1.5 刚发布，生态不成熟。如果现在重新选型，核心链路还是 C++ 保性能，业务逻辑用 Go 降低维护成本。"

**追问 2："分库分表后跨库查询怎么解决？"**

> **回答思路**：承认痛点 + 给出当前方案 + 展望改进方向
> 
> "分库分表最大的痛点就是跨库查询。我们的处理策略：1）**避免跨库**——90% 的查询都带 user_id，天然路由到正确分片；2）**冗余存储**——群聊消息既按 group_id 存一份，也按 user_id 存一份，空间换时间；3）**聚合查询降级**——后台管理系统的跨库查询走 Elasticsearch 异步索引，不阻塞在线服务。"

**追问 3："Redis 集群为什么用 Codis 而不是 Redis Cluster？"**

> **回答思路**：展现技术选型能力
> 
> "2017 年选 Codis 的原因：1）Codis 支持 1000+ 节点，当时 Redis Cluster 最多 16384 槽，Codis 更灵活；2）Codis 提供 Proxy 层，客户端不需要改代码，对业务透明；3）Codis 支持在线扩缩容，迁移对业务无感。后来 Redis Cluster 成熟了，新项目可以直接用 Redis Cluster。"

**追问 4："你遇到过最严重的线上事故是什么？"**

> **回答思路**：STAR 法则 + 展现反思深度
> 
> "最严重的一次是某次群发通知导致**缓存雪崩**——运营同时给 100 万用户发送通知，所有缓存同时过期（因为设置的 TTL 相同），请求全部打到 MySQL，导致数据库 Hang 了 3 分钟。事后修复：1）缓存 TTL 加**随机偏移**（±20%），避免集体过期；2）Bloom Filter 前置拦截不存在的 key；3）通知推送改为 MQ 异步削峰；4）运营后台加**发送频率控制**，限制单次推送量。"
