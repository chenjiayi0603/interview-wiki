## 一、高频面试 Q&A

### Q1: 千万级用户的架构怎么设计？

**架构演进（4 个阶段）**：

| 阶段 | 时期 | 架构 | 问题 | 峰值 QPS |
|------|------|------|------|---------|
| V1.0 | 2015 | 单体应用 + 单机 MySQL + Redis | 单点故障，扩展性差 | 2,000 |
| V2.0 | 2016 | 垂直拆分（IM/社交/金融），加 Redis 缓存 | 消息表单表数据量太大 | 5,000 |
| V3.0 | 2017 | 水平分片（32 库 × 64 表），Codis 集群 | 跨库查询需要聚合 | 15,000 |
| V4.0 | 2018 | 服务化拆分 + 消息队列削峰 | 运维复杂度增加 | 15,000（稳定） |

**最终架构**：
```
客户端（iOS/Android/H5）
  → Nginx 接入层（负载均衡 + SSL 终结 + 限流）
    → 服务层（IM 服务 / 社交服务 / 金融服务 / 推送服务）
      → 存储层（MySQL 32库×64表 / Codis 16节点 / MongoDB 冷数据）
```

### Q2: 分库分表怎么做？

**分片规则**（C++ 实现）：

```cpp
// 32 个库
int GetShardId(uint64_t user_id) { return user_id % 32; }

// 每库 64 张表
int GetTableId(uint64_t user_id) { return (user_id / 32) % 64; }

// 完整表名
string GetTableName(uint64_t user_id) {
    return "message_" + to_string(GetShardId(user_id))
           + "_" + to_string(GetTableId(user_id));
}
```

**容量验证**：1000 万用户 × 100 条消息 = 10 亿条 → 2048 张表 → 每表 48.8 万条（< 500 万）。

**路由中间件**：`DBRouter` 封装连接池和 SQL 替换，对上层透明。

### Q3: 敏感词过滤怎么实现？

使用 **DFA 算法（确定有限状态自动机）**：

1. 将敏感词列表构建为树形结构（Trie 树）
2. 文本匹配时逐字符遍历，状态转移 O(n)
3. 敏感词库存储在 Redis Set（`2:23:{type}:{subtype}`）

| 方案 | 时间复杂度 | 空间复杂度 | 更新难度 |
|------|-----------|-----------|---------|
| DFA（Trie） | O(n) | 高（构建树） | 低（热更新词库） |
| 正则匹配 | O(n×m) | 低 | 中 |
| AC 自动机 | O(n) | 最高 | 高 |

选择 DFA 的原因：实现简单、O(n) 匹配、支持热更新。

### Q4: Redis 数据结构设计要点？

| 功能 | 数据类型 | Key 示例 | 说明 |
|------|---------|----------|------|
| 用户属性 | Hash | `1:1:{imuid}` | 用户全部属性 |
| 在线状态 | Hash | `1:5:{imuid}` | token + 接入节点 |
| 好友关系 | Hash | `1:2:{imuid}` | frield_imuid → 关系记录 |
| 关注/粉丝 | Sorted Set | `6:15:{imuid}` | 时间有序 |
| 群信息 | Hash | `1:3:{group_id}` | 群属性 |
| 群成员 | Hash | `1:4:{group_id}` | member → 群内信息 |
| 单聊消息 | Hash | `1:1001:{self}:{other}` | 按对话存储 |
| 群聊消息 | Hash | `1:1003:{gid}:{YYYYMMDD}` | 按周分块 |
| 说说列表 | Sorted Set | `6:1014:{imuid}` | 发表/收听分离 |
| 敏感词 | Set | `2:23:{type}:{sub}` | 全量词库 |

### Q5: 缓存穿透怎么解决？

**问题**：查询 Redis 不命中 → 大量请求打到 MySQL。

**方案**：布隆过滤器（Bloom Filter）

- 在 Redis 前加布隆过滤器层
- 不存在的 key 直接返回，不查询 DB
- **效果**：穿透率降低 90%

### Q6: 消息队列用在哪些场景？

| 场景 | 作用 |
|------|------|
| 消息推送 | 削峰填谷，避免推送洪峰打垮网关 |
| 离线消息 | 异步写入，用户上线后拉取 |
| 日志采集 | 异步落盘，不阻塞主流程 |
| 通知推送 | 解耦业务方和推送方 |

## 二、STAR 故事

### 背景 (Situation)

深圳你我金融信息服务股份有限公司的社交金融 APP，2015.9 - 2019.4，用户量从 0 增长到 **1000 万+ 注册用户、500 万月活**。系统初期是单体架构，随着用户增长面临三个问题：

1. **单机 MySQL 扛不住**：QPS 到 2000 就告警
2. **消息表单表太大**：几亿条数据，查询越来越慢
3. **高峰期抖动严重**：早晚高峰 10 倍流量波动

### 任务 (Task)

设计新一代社交 IM 架构，目标：
- **支撑千万级用户**，峰值 QPS 15,000+
- **消息延迟可控**，单聊 < 50ms
- **高可用**，单点故障不影响整体
- **可扩展**，支持按需扩容

### 行动 (Action)

1. **垂直拆分（V2.0）**：
   - 将 IM 服务、社交服务、金融服务拆分独立部署
   - Redis 缓存热点数据，MySQL 读写分离

2. **水平分片（V3.0）**：
   - 消息表 32 库 × 64 表，按 user_id 取模路由
   - Codis 16 节点 128GB 缓存集群
   - 自研 DBROuter 中间件封装分片逻辑

3. **性能优化（V3.0-V4.0）**：
   - 布隆过滤器解决缓存穿透
   - 消息队列削峰填谷
   - 自研 C++ 数据代理层（DataProxy + DBAgent）

4. **冷热分离**：
   - 热数据：Redis + MySQL
   - 冷数据：MongoDB 历史消息归档

### 结果 (Result)

| 指标 | 优化前 | 优化后 |
|------|--------|--------|
| 峰值 QPS | 2,000 | 15,000 |
| 单表数据量 | 数亿 | < 500 万 |
| 缓存命中率 | — | 95% |
| 缓存穿透率 | 高 | 降低 90% |
| 高峰期抖動 | 严重 | 降低 80% |
| 分库分表 | 无 | 32 库 × 64 表 |
