## K1：`rocksdb::FileSystem` 继承 + 路由三后端

**简历原文**：继承 `rocksdb::FileSystem` 实现存算分离，按文件类型路由本地 SSD（热数据）/ 华为 OBS（冷数据）；元数据节点本地 TTL 缓存 + 熔断降级，节点故障不影响整体可用

### 数据支撑

| 后端 | 延迟 P50 / P99 | 路径 |
|------|----------------|------|
| 本地 SSD（热路径） | <0.1ms / <0.5ms | `kLocalPrefix` → posix 文件系统 |
| 元数据服务（gRPC） | 0.5–2ms | `kMetaPrefix` → gRPC 封装 |
| 华为 OBS（冷路径，长连接同 AZ） | 3–12ms / 20ms | `kObsPrefix` → OBS C++ SDK range get/put |
| OBS 含 TCP/TLS 建连（首包） | 8–25ms | 连接池复用后可降至长连接水平 |

热数据路径（热缓存命中率 95%+）整体 P99 <1ms。

### 理论支撑

RocksDB 的所有文件 IO 最终经过 `rocksdb::FileSystem` 抽象层。继承此类，重写 `NewSequentialFile`（顺序读 SST）、`NewRandomAccessFile`（随机读 Block，读路径最频繁）、`NewWritableFile`（写 SST/WAL），即可替换整个 IO 路径而无需修改 RocksDB 上层逻辑。三个后端的错误码统一映射回 `rocksdb::IOStatus`，RocksDB 上层无感知。

RocksDB 原生设计就是为了换底层 IO：`rocksdb::Env::Default()` 本身即是 POSIX 实现，整个框架以 DI（依赖注入）方式传入 Env/FileSystem。

### 业界对标

- **TiKV**：同样基于 RocksDB FileSystem 抽象扩展远程存储（TiFlash 存算分离）
- **Pika / SSDB**：Redis 协议 + RocksDB 底层，落盘路径类似但未做对象存储冷热分层
- **AWS Aurora + S3 存算分离**：计算与共享存储解耦的经典云原生模式

### 追问预案

**Q：三个后端的路由逻辑怎么实现？**
> 根据文件路径前缀分发：`/local/...` 走 SSD posix 实现；`/meta/...` 走 gRPC 封装；`/obs/...` 走 OBS SDK 的 range get/put。路由在 `FileSystem::NewXxxFile` 入口做一次字符串前缀匹配。

**Q：WAL 文件放在哪个后端？**
> WAL 和 L0 SST 文件必须留本地 SSD（`kLocalPrefix`），保证写入延迟 <1ms 且 Compaction 不直接打 OBS PUT 配额。只有 L1+ 的深层 SST 才路由到 `kObsPrefix`。

## K2：LRU 冷热分层（访问频次 × 时间衰减）

**简历原文**：按文件类型路由本地 SSD（热数据）/ 华为 OBS（冷数据）；LRU 缓存

### 数据支撑

| 指标 | 值 | 说明 |
|------|----|------|
| 热缓存命中率 | 95%+ | LRU 在业务热点局部性下的典型水平 |
| 冷请求量 | <5% | 低频路径，整体 P99 主要看热路径 |
| 冷数据 OBS P99 | ~20ms | 含内网 RTT + OBS 鉴权 + 数据 IO |
| 迁移粒度 | SST 文件级 | RocksDB 最小 IO 单元 = SST Block，文件级粒度与实际 IO 模式匹配 |

### 理论支撑

打分公式：`score = access_count / (now - last_access_ts + 1)`，本质是单位时间访问密度。后台扫描线程每分钟跑一次，分数低于全部分数下四分位数的文件标记为"冷"，触发异步迁移。

与标准 LRU（单链表 O(1) 淘汰）的区别：标准 LRU 仅看最近访问时间，一次性线性扫描会错误 evict 真正的热数据（访问时间短但频次低的文件）。我们的方案兼顾频次，防止扫描风暴破坏真实热点。

与 OBS Lifecycle 策略的区别：OBS Lifecycle 是**时间维度**（N 天未操作 → 降级），我们是**热度维度**（访问密度打分）。纯靠 Lifecycle 节省约 30-40%，加上热度打分可到 70%+。

### 业界对标

- **Cassandra Tiered Storage**：SST 文件级冷热分层，与本设计同思路
- **HBase HFile 分层**：冷热数据分层到 HDFS，机制相同
- **RocksDB 自带 BlobDB**：大 value 独立存储 blob file，冷热分离的另一种形式

### 追问预案

**Q：为什么不用 OBS Lifecycle 自动分层？**
> OBS Lifecycle 粒度是整对象 + 按时间，而我们需要 SST 文件 + 按访问热度。3 天前创建但业务热点一直读的文件，Lifecycle 会降级，我们 LRU 打分认为是热的。反过来今天才写但业务不再读的文件，Lifecycle 认为是标准存储，但应该迁到 OBS。纯靠 Lifecycle 节省率约 30-40%，加热度打分可到 70%+。

## K3：元数据 TTL 缓存 + 熔断降级

**简历原文**：元数据节点本地 TTL 缓存 + 熔断降级，节点故障不影响整体可用

### 数据支撑

| 防御层 | 效果 | 说明 |
|--------|------|------|
| 本地 TTL 缓存（第一层） | 命中率 90%+，读路径绕开 gRPC | 元数据高频读但变化少，TTL 内绝大多数请求命中缓存 |
| 熔断器降级（第二层） | 短期读路径可用 | 监控 gRPC 错误率，触发后锁定本地缓存 |
| 恢复后异步对账（第三层） | 最终一致 | 元数据服务恢复后，差量对账修复缓存 |

### 理论支撑

与 etcd watch + local cache 模式一致：元数据服务是远程 KV（gRPC 同步调用），本地 TTL 缓存是 pull 模型的近似优化。三层防御的核心是：**读路径不依赖远端实时可用性**，代价是缓存不一致窗口（TTL 内）。

新建文件时，写操作需要先将元数据写入队列暂存（元数据服务不可用时），等服务恢复后批量提交。写路径在元数据服务故障期间短暂不可用，读路径不受影响。

### 业界对标

- **ZooKeeper + 本地缓存**：分布式协调服务的经典三层防御（ZK → 本地缓存 → 降级默认值）
- **Consul + agent 本地缓存**：服务发现中间层，与本设计结构类似
- **CDN 边缘节点缓存**：源站不可达时继续提供旧版本缓存，同样是可用性 > 一致性的取舍

### 追问预案

**Q：元数据服务挂了最坏情况怎么样？**
> 三层防御：① TTL 缓存默认命中（读路径 90%+ 无影响）；② TTL 过期后熔断器切到本地缓存（短期可用）；③ 恢复后异步对账。最坏情况是写入新文件暂时失败（写操作需要向元数据服务注册新文件），读路径始终不受影响。

## K4：多租户隔离（进程 + OBS 路径 + cgroup）

**简历原文**：每租户独立实例 + OBS 路径隔离 + cgroup 限制，支撑大规模多租户

### 数据支撑

| 隔离层 | 手段 | 效果 |
|--------|------|------|
| 计算层 | 每租户独立 KeyDB 进程 | 进程崩溃不影响其他租户 |
| 存储层 | OBS bucket + 路径前缀 `tenant_id/` | 数据完全隔离，无跨租户访问 |
| 资源层 | cgroup v2 限 CPU + IO 带宽 | noisy neighbor 隔离，防止单租户打满资源 |
| 网络层 | 网络 QoS（带宽限速） | 补充 cgroup IO 限制 |

### 理论支撑

物理隔离（独立进程）是最简单可靠的多租户隔离手段，代价是内存和启动开销（每进程独立 KeyDB 实例，约 100-200MB 基础内存）。cgroup v2 统一资源层隔离，Linux 内核级保证 CPU 和 IO 不超配。

与共享进程 + 逻辑隔离的对比：共享进程实现内存 namespace 或 key prefix 隔离复杂度高且 bug 风险大，独立进程即可利用 Linux 进程隔离保证。适合云服务 PaaS 场景（租户量大但可承受单实例内存开销）。

### 业界对标

- **AWS ElastiCache**：多租户 Redis 以独立实例为基本单元，与本设计完全一致
- **阿里云 Tair**：同样每用户独立实例 + namespace 路径隔离
- **Kubernetes 容器隔离**：cgroup + namespace 隔离是 K8s 基础设施的基础，本设计在进程层直接应用同样机制

### 追问预案

**Q：为什么不用共享进程 + key 前缀隔离？**
> 共享进程里 A 租户的内存问题（大 key、内存泄漏）会影响 B 租户，cgroup 限制单个进程无法精确分摊。独立进程 + cgroup 是最直接的物理隔离，进程间天然互不影响，代价是每租户多 100-200MB 基础内存，在 PaaS 场景完全可接受。

## K5：Compaction rate_limiter + WAL/L0 留本地 SSD

**简历原文**：Compaction `rate_limiter` 限速削峰，WAL/L0 留本地 SSD，规避 OBS 写入限流触发 write stall

### 数据支撑

| 维度 | 本地 SSD | 远程 OBS | 劣化倍数 |
|------|---------|---------|---------|
| 单次 IO 延迟 | 0.1–0.5ms | 5–30ms | 50–100× |
| Compaction P99 抖动 | 5–20ms | 50–200ms+ | 10× |
| OBS 单桶 PUT 配额 | — | 500–2,000/s | 硬天花板 |

Compaction 级联效应：PUT 打满 OBS 配额 → 503 SlowDown → 上传失败重试 → L0 文件堆积 → write slowdown → 极端情况 write stop → 业务写入暂停。

缓解手段：
- Compaction `rate_limiter`：限速到 OBS 配额 70% 以内，大 Compaction 放在业务低峰期
- WAL + L0 留本地 SSD：仅 L1+ 深层 SST 落 OBS，Compaction 输出先写本地再异步上传
- 大 SST 文件（256MB）：减少 HTTP PUT 次数

### 理论支撑

LSM-Tree 写放大（Write Amplification Factor, WAF）：Compaction 过程将 L(N) 的 SST 与 L(N+1) 归并排序，每层数据在生命周期内会被写多次，WAF 约为 10–30×。在存算分离架构中，Compaction 输出直接打 OBS 是致命问题：每次 Compaction 产生的 SST 上传到 OBS 会消耗 PUT 配额，且 OBS 单桶配额是 500–2000/s 的硬上限。

WAL 和 L0 留本地 SSD 的逻辑：WAL 是写入热路径，每次事务必须 fsync，本地 SSD fsync <0.5ms，OBS 延迟 5-30ms 无法承受。L0 文件未经 Compaction，写频率高，同理留本地。

### 业界对标

- **RocksDB 官方文档** §Compaction：`rate_limiter` 是官方推荐的 Compaction 限速手段，`SetBytesPerSecond()` 动态调整
- **Snowflake / Databricks**：Compaction 卸载到独立计算集群（Compaction offload），在线节点只做读写，是更彻底的存算分离
- **TiKV 存储分离方案**：同样采用热数据本地 SSD + 冷数据对象存储，Compaction 处理方式类似

### 追问预案

**Q：write stall 和 write stop 有什么区别？**
> write slowdown 是 RocksDB 检测到 L0 文件数量超过阈值（`level0_slowdown_writes_trigger`，默认 20），主动降低写入速度（sleep 添加延迟）。write stop 是 L0 超过 `level0_stop_writes_trigger`（默认 36）时，业务写入完全暂停直到 Compaction 消化 L0。存算分离场景下 OBS 限流导致 Compaction 卡住，L0 堆积触发这两个阶段。

**Q：rate_limiter 怎么设定具体数值？**
> 根据 OBS 单桶 PUT 配额（500–2000/s × 平均 SST 大小 256MB）计算 Compaction 输出最大带宽，限速在配额 70% 以内。高峰期进一步降低速率，低峰期（凌晨）放开跑大 Compaction。

## K6：存储成本降低 70%+

**简历原文**：存储成本降低约 70%+

### 数据支撑

| 存储类型 | 单价 | 说明 |
|---------|------|------|
| 华为云内存（Redis 类缓存折算） | ~¥2/GB·月 | 内存贵 |
| 华为 OBS 标准存储 | ¥0.099/GB·月 | OBS 便宜约 20× |
| OBS 内网访问费 | 忽略 | 同 AZ 内网无流量费 |

成本计算（1TB 全量，100GB 热内存，900GB 冷数据）：

| 内存单价 | 老架构（全内存） | 新架构 | 净节省率 |
|---------|----------------|--------|---------|
| ¥0.5/GB·月 | ¥500/月 | ¥149/月 | **70%** |
| ¥1.0/GB·月 | ¥1,000/月 | ¥199/月 | **80%** |
| ¥2.0/GB·月 | ¥2,000/月 | ¥299/月 | **85%** |

数据量越大，节省比例越高（热数据受内存容量限制，不随总量等比增长）。

### 理论支撑

核心公式：
```
老架构：Cost_old = N × P_mem
新架构：Cost_new = N_hot × P_mem + N × P_obs
净节省率 = 1 - r_hot - P_obs/P_mem
```
其中 `r_hot = N_hot/N`（热数据占比，~10%），`P_obs/P_mem ≈ 0.099/2 ≈ 5%`，净节省 ≈ 85%。

### 业界对标

- **AWS S3 + EBS 存储分层**：内存 → SSD → S3 三级成本递减，业界存储分层的标准模式
- **阿里云 Tair 冷热分层**：热数据留内存，冷数据落 OSS，原理相同
- **Cassandra Tiered Storage**：Google Cloud Bigtable 的分层案例，冷热存储成本差距在同等数量级

### 追问预案

**Q：70% 怎么算出来的，实测还是估算？**
> 基于公开价格和实际架构推演。华为 OBS 标准存储公开价 ¥0.099/GB·月，内存（云缓存实例折算）约 ¥2/GB·月。代入 1TB 数据（热数据 100GB，冷数据 900GB）：老架构全内存 ¥1000/月，新架构 100GB 内存 + 1TB OBS = ¥200 + ¥99 ≈ ¥299/月，节省率 ≈ 70%。这是业务可推演的估算，实际节省率受热数据比例和具体定价影响。

## R1：同步记录 Key 访问统计（主线程 <1μs）

**简历原文**：在命令处理路径中同步记录 Key 访问统计（规避异步拷贝引发内存暴涨）

### 数据支撑

| 指标 | 值 | 说明 |
|------|----|------|
| 主线程额外开销 | <1μs | Redis 命令本身耗时 1–10μs，<1μs ≈ 增加 1–10% |
| 支撑实例规模 | 万级 | 主从 / 哨兵 / 集群三模式全覆盖 |
| 插桩位置 | `processCommand` 入口/出口 | 与 Redis 模块化设计一致 |

**为什么不用异步拷贝**：异步方案需要将 Key 的 value 数据拷贝到独立队列（或后台线程），大 Key（value 可达 MB 级别）的拷贝会使内存暴涨。同步记录只需记录 Key 名称（字符串引用）+ value 大小（整数），不复制数据本体，开销极低（一次内存写入 ~纳秒级）。

### 理论支撑

Redis 单线程架构（主线程处理所有命令），在 `processCommand` 路径插桩是最直接的方式。同步记录在命令执行完成后立即更新统计结构（哈希表计数器），整个操作是纯内存读写，无锁需要（主线程单线程，天然无竞争）。

布隆过滤器前置：先用布隆过滤器判断 Key 是否有可能是大 Key / 热 Key 候选，命中后才分配计数器，避免为每个 Key 维护状态导致的内存膨胀。

### 业界对标

- **`redis-cli --bigkeys`**（被替代的方案）：遍历全量 Key 的离线扫描，执行期间占用大量 CPU + IO，影响主业务（实测会引起主线程延迟上升）
- **Redis 4.0+ OBJECT FREQ 命令**：LFU 模式下记录访问频次，思路相似但仅限 value 淘汰策略，不支持实时大 Key 检测
- **阿里云 Redis 大 Key 检测**：阿里云 DCS 内置大 Key / 热 Key 统计，实现机制与本方案类似

### 追问预案

**Q：为什么不用 Redis Module 实现？**
> Module 需要独立 .so 加载，每个命令回调会有 Module API 调用的额外开销，且与 Redis 主代码解耦后维护版本兼容性复杂。直接在命令路径插桩是最低侵入、最低开销的方式。

**Q：同步记录会不会因为统计结构本身的内存问题影响 Redis？**
> 布隆过滤器控制内存：100万 Key 仅占 1.2MB（参见 R2）。计数器只为布隆过滤器命中的 Key 分配，实际热 Key 数量远小于全量 Key，计数器总内存可控。

## R2：布隆过滤器预筛（FPR 1%，100万 Key → 1.2MB）

**简历原文**：布隆过滤器预筛，替代原有在线阻塞式 Key 扫描，实现大规模实例大 Key / 热 Key 实时检测

### 数据支撑

| 指标 | 值 | 计算来源 |
|------|----|---------|
| FPR（假阳性率） | 1% | 10 个哈希函数 × 10 bits/key 的标准配置 |
| 100万 Key 布隆过滤器内存 | 1.2MB | 100万 × 10 bits / 8 = 1.25MB |
| 不用布隆过滤器（全量计数器） | 100MB+ | 每 Key ~100 字节计数器 × 100万 |
| 内存节省 | 99%+ | 实际热 Key 约 1% 数量级，计数器仅分配给热 Key |

布隆过滤器周期性重建（每 N 分钟全量重建），防止历史低频 Key 长期占用误报位。

### 理论支撑

布隆过滤器是 m bit 数组 + k 个独立哈希函数，插入时将 k 个哈希位置置 1，查询时检查 k 个位置是否全为 1。假阳性率公式：`FPR = (1 - e^(-kn/m))^k`，取 k=10, m/n=10 时 FPR ≈ 1%。不存在假阴性（false negative）——实际的大 Key / 热 Key 一定会被检测到。

1% 假阳性在业务层面可接受：被误判为热 Key 的低频 Key，在 top N 统计聚合时会因为计数器值极低而自然被过滤，不影响最终输出结果。

### 业界对标

- **Redis 4.0+ RedisBloom 模块**：官方布隆过滤器实现，算法与本方案完全一致
- **BigTable / LevelDB 中的 Bloom Filter**：用于 SST 文件中快速判断 key 是否存在，同样避免不必要的磁盘访问
- **Cassandra 行级 Bloom Filter**：每个 SST 文件携带 bloom filter，读路径优化

### 追问预案

**Q：布隆过滤器 FPR 1% 对结果准确性有什么影响？**
> FPR 1% 意味着低频 Key 有 1% 概率被误判为候选 Key，分配计数器。但因为这些低频 Key 的实际访问计数很低，在 top N 聚合输出时会被真正的热 Key 淘汰。整体大 Key / 热 Key 检测准确率不受 FPR 影响。

**Q：布隆过滤器不支持删除，怎么处理过期 Key？**
> 周期性全量重建（如每 30 分钟），避免历史 Key 长期占用假阳性位。重建期间短暂多分配少量计数器（FPR 略高），不影响业务。如果需要支持删除，可以用 Counting Bloom Filter（每个 bit 改为计数器），内存代价约 4×，但对本场景不必要。

## R3：替代在线阻塞式 redis-cli --bigkeys

**简历原文**：替代原有在线阻塞式 Key 扫描，实现大规模实例大 Key / 热 Key 实时检测

### 数据支撑

| 方案 | 执行方式 | 对主业务影响 | 实例规模 |
|------|---------|------------|---------|
| `redis-cli --bigkeys` | 在线 SCAN 全量 Key，阻塞主线程（Redis 单线程） | 执行期间每次 SCAN 命令占用主线程，P99 上升 | 单实例 |
| 本项目同步插桩 | 命令路径内嵌统计，<1μs 开销 | 无阻塞，主线程额外开销可忽略 | 万级实例 |

`redis-cli --bigkeys` 底层使用 `SCAN` + `OBJECT ENCODING` + `DEBUG OBJECT`，每次 SCAN 批次是一次阻塞，对于 1 亿 Key 的实例可能需要数分钟，期间命令延迟明显上升。

### 理论支撑

Redis 单线程模型：所有命令（包括 SCAN）都在主事件循环中串行执行。`SCAN` 命令每次返回一批 key（count 参数控制批次大小），但每次调用都占用主线程时间片。百万 Key 实例的完整 SCAN 需要数千次调用，总计对主线程的干扰时间可达分钟级。

在线实时检测的核心优势：命令执行完成时 Key 的 value 大小和访问频次天然已知，无需额外扫描。插桩成本 = 一次哈希表查找 + 一次计数器更新，远低于 SCAN 的全量遍历。

### 业界对标

- **阿里云 Redis 控制台**：提供大 Key 分析功能，底层使用 RDB 离线分析（重启后分析 dump 文件），非在线
- **Datadog Redis 监控**：通过 `INFO`, `CLIENT LIST` 等命令采样，非命令级别实时统计
- **美团 Redis 监控**：公开分享中提及在命令路径插桩统计的方案，与本项目思路一致

### 追问预案

**Q：大 Key 的定义是什么？**
> 按类型：String value > 10KB；List/Hash/ZSet/Set 元素数 > 10,000。热 Key：单位时间（如 1s 内）访问频次排前 N（N 可配）。阈值业务侧可配置。

## R4：布隆过滤器周期性重建 + 告警二次确认

**简历原文**：布隆过滤器周期性重建 + 告警二次确认，支撑万级实例稳定运维

### 数据支撑

| 机制 | 参数 | 效果 |
|------|------|------|
| 布隆过滤器重建周期 | 每 30 分钟（可配） | 清理历史假阳性积累，避免 FPR 随时间增大 |
| 告警二次确认 | 连续 2 次独立统计周期均触发 | 过滤布隆过滤器假阳性导致的误报，提升告警精准度 |
| 支撑实例数 | 万级（主从 / 哨兵 / 集群） | 插桩统一嵌入 Redis 进程，单实例开销 <1μs |

### 理论支撑

布隆过滤器随插入元素增多，假阳性率逐渐上升（更多 bit 被置 1）。周期性全量重建能将 FPR 重置到初始水平（1%）。重建时先构建新过滤器，原子替换旧过滤器（指针替换），过渡期间旧过滤器继续提供服务，无停机窗口。

告警二次确认是监控系统的标准抖动过滤手段：单次统计周期内出现阈值超越可能是布隆过滤器假阳性或瞬时流量毛刺，连续两个周期均超越则大概率是真实问题。

### 业界对标

- **Prometheus Alertmanager**：`for` 参数要求告警持续一段时间才触发，原理与二次确认相同
- **SRE 实践**：Google SRE Book §监控：告警需要 "for duration" 避免误报，与本设计理念一致
- **Envoy 熔断**：连续 N 次失败后触发熔断，也是同类"二次确认"机制

## Z2：Envoy Wasm 自适应熔断插件

**简历原文**：自研 Envoy Wasm 自适应熔断插件：滑动窗口错误率统计 + 自动熔断 + half-open 探针恢复

### 数据支撑

| 参数 | 配置值 | 说明 |
|------|--------|------|
| 滑动窗口大小 | 10s | 统计窗口内错误率和 P99 延迟 |
| 错误率阈值 | >50% | 窗口内错误率超阈值触发熔断 |
| P99 延迟阈值 | >1s | 延迟超阈值也独立触发（OR 条件） |
| 熔断持续时间 | 3s | 期间所有请求直接返回 503 |
| half-open 探针间隔 | 1s | 周期性放行少量请求验证 |
| half-open 成功次数 | 连续 2 次 | 成功后关闭熔断 |
| 最短恢复路径 | **<5s** | 3s 熔断 + 1s 第 1 次探针 + 1s 第 2 次探针 |

Wasm vs Native C++ Filter 性能：Wasm 慢约 20%，但熔断逻辑轻量（几十行计数器统计），绝对差值约 0.5ms，被网络延迟（内网 RTT ~1ms）淹没，不是瓶颈。

### 理论支撑

滑动窗口计数器：固定大小时间窗口内统计错误数、总请求数，计算错误率。与固定窗口的区别：固定窗口在窗口边界会出现计数重置导致的短暂误判；滑动窗口每次统计最近 N 秒，避免边界效应。

half-open 状态机：熔断器三态（Closed → Open → Half-open），Closed = 正常，Open = 全部失败，Half-open = 试探恢复。连续 K 次探针成功 → 回到 Closed；失败 → 回到 Open。这是 Hystrix 引入的经典模式，防止服务恢复后瞬间被大流量压垮。

选 Wasm 不选 Native C++ Filter 的三个原因：① 热更新（改阈值不重启 Envoy）；② 沙箱安全（插件 bug 不影响 Envoy 主进程）；③ 跨语言（Go/Rust/AssemblyScript 均可编写）。

### 业界对标

| 框架 | 语言 | 熔断机制 | 热更新 |
|------|------|---------|--------|
| Hystrix（Netflix） | Java | 滑动窗口 + half-open | 需重部署 |
| Sentinel（阿里） | Java/Go | 滑动窗口 + half-open | 规则动态推送 |
| Envoy 内置熔断 | C++ | 连接数 / 请求数上限 | 配置热更新 |
| **本项目 Wasm 插件** | Go/C++ | 错误率 + 延迟双条件 + half-open | `istioctl apply` 秒级生效 |

### 追问预案

**Q：为什么 Wasm 比 Native C++ Filter 慢 20%？**
> Wasm 运行在独立 VM 沙箱（V8 或 Wasmtime），每次插件执行需要跨越 Host↔Wasm 边界（上下文切换 ~1μs），加上 Wasm 字节码解释/JIT 执行比原生机器码略慢。绝对差值：Native ~0.8–1.5ms，Wasm ~1–2ms，差距约 0.5ms。在内网 RTT 1ms 的背景下可忽略。

## L1：Libev C++ 异步网络框架（事件驱动 + 多进程 Worker）

**简历原文**：基于 Libev 自研 C++ 异步网络框架（事件驱动 + 多进程 Worker）

### 数据支撑

| 组件 | 设计 | 效果 |
|------|------|------|
| 事件循环 | Libev（epoll LT 模式） | 空闲连接近零 CPU 唤醒成本 |
| 多进程 Worker | SO_REUSEPORT | 内核负载均衡，避免 accept 锁竞争 |
| 进程数 | CPU 核数（8 核 → 8 Worker） | 利用多核，无线程上下文切换开销 |
| 单跳内部转发延迟 | <5ms | gRPC 同 DC 1–3ms |
| 服务端处理 P99 | <50ms | 不含客户端网络 RTT |

### 理论支撑

Libev 基于 epoll 的 Level-Triggered（LT）模式：只要 socket buffer 有数据就持续触发，编程模型简单，不需要 while-EAGAIN 循环也不会丢事件（相比 ET 模式更安全，代价是多一次系统调用）。

多进程 + SO_REUSEPORT：Linux 3.9+ 内核支持多个进程绑定同一端口，内核按 4 元组哈希均匀分发新连接到各 Worker 进程。相比单进程 accept + 线程池，避免了 accept 队列锁竞争和惊群问题（参考 Nginx 多进程模型）。

### 业界对标

- **Nginx**：同样多进程 + SO_REUSEPORT + epoll LT，是百万连接网络框架的最直接业界参考
- **Memcached**：多线程 epoll 模型，思路类似（多进程改为多线程）
- **WhatsApp Ejabberd**：Erlang BEAM 多进程调度，单机 2M 连接的标杆案例（2012 年）

### 追问预案

**Q：Libev 用的是 ET 还是 LT？**
> Libev 默认使用 LT（Level-Triggered）。LT 模式编程模型简单，socket buffer 有数据就持续触发，不需要 while-EAGAIN 循环。我们选 LT 是因为 IM 消息有严格的保序要求，ET 模式必须在单次触发时读完所有数据，实现复杂度更高，bug 风险更大。LT 的代价是多一次 epoll_wait 返回，对比节省的编程复杂度完全值得。

## L2：单机百万长连接内核调优

**简历原文**：内核参数调优支撑单机百万长连接（压测验证）

### 数据支撑

**机器配置**：单机 8 核 16G，千兆网卡，Linux 4.x（CentOS 7）

**内存拆解**（100万连接 ~8GB 总内存）：

| 层 | 内存 | 说明 |
|----|------|------|
| TCP 内核元数据 | ~3–4GB | `tcp_sock` 结构体 + `sk_buff` 队列，约 3–4KB/连接 |
| conntrack entries | ~300MB | 每 entry ~300 字节，100万 × 300B |
| TCP buffer（调优后） | ~2GB | `tcp_rmem/wmem` min=1KB，100万 × 2KB |
| 用户态应用层 | ~2–3GB | 每连接 `Connection` 对象（fd + 读写 buffer 各 512B + 状态机）~1–2KB |
| **总计** | **~8–10GB** | 16G 机器跑 100 万连接，`free` 剩 6–7GB |

**核心调优参数**：

| 参数 | 默认值 → 调优值 | 作用 |
|------|----------------|------|
| `tcp_rmem/wmem` min | 4KB → **1KB** | 每连接 buffer 从 8GB 降到 2GB |
| `ulimit -n` | 1024 → **1,048,576** | 文件描述符上限 |
| `net.core.somaxconn` | 128 → **65535** | listen 队列 |
| `nf_conntrack_max` | 65,536 → **2,097,152** | conntrack 表容量（百万连接的隐藏雷） |
| `nf_conntrack_tcp_timeout_established` | 5天 → **600s** | 僵尸连接清理 |

### 理论支撑

百万连接最容易忽略的 conntrack：netfilter 连接追踪子系统记录每条 TCP 连接状态，`nf_conntrack_max` 默认 65536 远不够。表满时内核直接丢 SYN 包，业务侧表现为间歇性连接失败，`dmesg` 才能看到 `nf_conntrack: table full, dropping packet`。四条参数协作调优（max + buckets + established timeout + time_wait timeout）缺一不可，只调 max 不调 timeout 会导致僵尸 entry 越积越多。

SO_REUSEPORT 绑定多进程，内核按 4 元组哈希均匀分发，避免 accept 队列成为单点瓶颈。

### 业界对标

- **WhatsApp 单机 2M 连接**（Rick Reed, Erlang Factory 2012）：FreeBSD + Erlang BEAM，同样内核调优
- **C10M 命题**（Robert Graham, Shmoocon 2013）：业界长期讨论的 1000 万连接挑战
- **美团 IM 网关分享**：8–16 核单机百万级，调优手段与本项目一致

### 追问预案

**Q：conntrack 表满为什么不直接用 NOTRACK？**
> 网关层有 iptables 限流和 ACL 规则，依赖 stateful 连接追踪，不能全局 NOTRACK。但内部 RPC 端口（不需要状态追踪的）做了 NOTRACK 跳过 conntrack，优化了内部 RPC 的建连开销。

**Q：压测是自研工具还是开源工具？**
> 单机模拟 50 万连接用自研压测客户端（同套 Libev 框架），多机叠加打满 100 万。辅助 HTTP 网关压测用 wrk，性能瓶颈定位用 perf + FlameGraph 火焰图，协议栈错误统计用 `ss -s` / `nstat`。

## L3：群消息扇出聚合（3000 → ~10 次 RPC）

**简历原文**：群消息扇出：按网关分组聚合推送，将跨节点 RPC 数量级降低

### 数据支撑

| 场景 | RPC 次数 | CPU 消耗 |
|------|---------|---------|
| 老方案（逐成员推送） | 3000 次/条（万人群在线 ~3000） | PushServer CPU 打满 |
| 新方案（按网关节点聚合） | ~10 次/条（网关节点数 ~10） | CPU 大幅下降 |

在线率约 30%（万人群 ~3000 人在线）。网关节点约 10 台，按 `accnodeidentify`（`ip:port:workIndex`）分组后，等效 3000 → 网关节点数（~10）。每条跨节点 RPC 节省 ~0.5–1ms（gRPC 同 DC 1–3ms），总节省 ~1.5–3s CPU 时间/消息。

### 理论支撑

扇出优化的本质是把 **O(N) 跨进程 RPC** 转为 **O(G) RPC + O(N) 本地内存操作**（N=在线成员数，G=网关节点数）。网关本地遍历连接表是纯内存操作（哈希表查找 ~ns），相比跨进程 gRPC（~ms）快 3 个数量级。

新架构：MsgServer 落库 → 写 RocketMQ → PushServer 消费 → 按 `accnodeidentify` 分组 → 批量 RPC 到每个网关 → 网关本地 fanout。引入 MQ 增加约 5–10ms 延迟，但换来的是 PushServer CPU 量级下降。

### 业界对标

- **微信公开架构**：群消息采用"拉模式"（客户端感知到新消息后主动拉取）在超大群，与本方案"推模式"各有适用场景
- **美团实时消息系统**（公开分享）：按接入层节点聚合推送，思路与本项目完全一致
- **Slack 消息路由**：频道消息通过中间 broker 聚合，避免 O(N) 直推

### 追问预案

**Q：如果某个网关节点挂了，这批成员的消息怎么办？**
> 网关心跳检测（10s），挂掉后成员状态从 Redis 中清除（RocketMQ 下线事件）。PushServer 在聚合时跳过这批成员；这批成员在重连到新网关后，会触发拉取离线消息。

## L4：在线状态一致性哈希 + LRU 缓存 + RocketMQ 主动失效

**简历原文**：在线状态一致性哈希 + LRU 缓存 + RocketMQ 主动失效

### 数据支撑

| 方案 | 查询延迟 |
|------|---------|
| 优化前（实时查询 Redis） | 5–20ms |
| 优化后（缓存命中） | **<1ms** |

LRU 缓存 TTL：5–30s（可配）。RocketMQ 主动失效：群成员登录/登出事件实时推送到 PushServer，精确 invalidate 缓存，避免 TTL 内状态不一致。

### 理论支撑

一致性哈希路由：按用户 ID 哈希到固定的 PushServer 节点（虚拟节点 150–200 个/物理节点），查询时直接路由到负责该用户的节点，无需广播所有节点。扩缩容时只影响相邻虚节点的少量 key。

三层组合的必要性：纯 TTL 缓存有一致性窗口（5–30s 内可能读到旧状态）；纯 RocketMQ 主动失效无法处理 MQ 延迟或失序；两者结合：正常情况下 MQ 事件精确失效缓存，MQ 延迟时 TTL 兜底保证最终一致。

### 业界对标

- **IM 在线状态服务**（微信公开 KM、钉钉技术博客）：一致性哈希路由是 IM 在线状态服务的标准架构
- **Redis Cluster 槽位分配**：一致性哈希思想在 Redis 分布式的应用
- **Netflix Eureka + Ribbon**：客户端负载均衡 + 缓存，与本设计同类

## L5：未读数设计（已读点 + MongoDB 联合索引）

**简历原文**：未读数采用已读点 + MongoDB 联合索引，规避大群写扩散

### 数据支撑

| 方案对比 | Redis INCR | 已读点 + count |
|---------|-----------|--------------|
| 发消息写入 | N 次 Redis INCR（N = 群成员数） | 0（仅写消息本体） |
| 撤回处理 | 需 DECR，异步流程可能 DECR 丢失 | 统计时自动排除 `msgState=4`，零操作 |
| Redis 故障 | 计数器清零，所有用户未读数丢失 | 不影响（已读点丢失最多重算一次） |
| 万人群影响 | 1 条消息 1万次 Redis 写 | 1 次 MongoDB 写（消息本体） |

MongoDB `countDocuments` 延迟：
- 正常（索引 `{sessionId, msgId}` 覆盖）：**<5ms**
- 长时间离线（>10万未读）：10–50ms
- 极端（百万级未读，半年未登录）：>100ms（需引入快照辅助）

### 理论支撑

**已读点方案**：每用户存一个 `read_msgid`（已读到的最大消息 ID），未读数 = `countDocuments({sessionId: X, msgId: {$gt: read_msgid}, msgState: {$ne: 4}})`。登录时查一次，在线期间客户端本地维护（收到新消息 +1），零服务端写压力。

联合索引 `{sessionId, msgId}` 保证 O(log M + K)（M = 消息总量，K = 未读数）的 count 性能。B-Tree 索引范围扫描，比全集合扫描快几个数量级。

### 业界对标

- **微信未读数方案**（公开 KM）：采用"增量计数 + 服务端持久化"混合模式，不依赖客户端本地计数，可靠性更高但实现更复杂
- **Slack 未读设计**：基于时间戳 cursor（类似已读点），服务端按 cursor 查询未读，与本方案思路一致
- **MongoDB 官方文档**：`{sessionId, msgId}` 联合索引是 IM 消息系统的推荐索引结构

### 追问预案

**Q：在线期间客户端本地 +1，杀进程丢了怎么办？**
> 下次登录时重查 MongoDB count，重新拿到精确值。IM 场景用户登录频率远低于发消息频率，登录时多一次 count 查询（<5ms）完全可接受。这是"读集中"换"写分散"的取舍，在线期间零开销。

## L6：消息可靠性（Redis ZSet + 指数退避 + APNs/FCM）

**简历原文**：消息可靠性：Redis ZSet 推送状态 + 指数退避重试 + APNs/FCM 离线补偿

### 数据支撑

| 阶段 | 机制 | 超时 |
|------|------|------|
| 在线推送 | WebSocket 直推 | 10s（ACK 超时） |
| 重试策略 | 指数退避：1s → 2s → 4s | 最多 3 次 |
| 离线补偿 | APNs（iOS）/ FCM（Android）厂商通道 | 触发阈值 30s |
| 去重 | Redis SETNX（msgId 为 key，TTL 24h） | 防止重推同一消息 |
| 清理 | 已 ACK 消息从 ZSet 删除（后台扫描） | 减少 ZSet 内存 |

ZSet score = 消息推送时间戳（微秒），排序后可快速找到超时消息（score < now - 30s）。

### 理论支撑

Redis ZSet 作为推送状态队列：`ZADD msgQueue <timestamp> <msgId>`，消息推送成功后 `ZREM`。后台扫描线程用 `ZRANGEBYSCORE` 找到超时消息触发重推或厂商通道兜底。

指数退避（Exponential Backoff）：避免重试风暴。失败后等 1s 重试，再失败等 2s，再等 4s，后续转厂商通道。业界标准是 `wait = base * 2^n + random jitter`，jitter 防止多条消息同时重试造成的锯齿流量。

SETNX 幂等：`SET msgId "sent" NX EX 86400`，同一 msgId 24 小时内只推一次，防止重试导致用户收到重复消息。

### 业界对标

- **微信消息可靠性**（公开 KM）：同样 ZSet 记录未 ACK 消息 + 指数退避 + 厂商离线推送三层
- **APNs / FCM SLA**：厂商通道有 99.9%+ 到达率 SLA，是离线消息可靠性的最终保障
- **AWS SQS 可见性超时**：类似 ZSet 机制，消息被取出后进入"不可见"状态，超时未 ACK 则重新可见

## N2：敏感词过滤（Trie / 多模式匹配）

**简历原文**：敏感词过滤（Trie / 多模式匹配）

### 数据支撑

| 算法 | 时间复杂度 | 典型性能 |
|------|-----------|---------|
| 暴力搜索（遍历词典 × 搜索文本） | O(M×N)，M=词典大小，N=文本长度 | 词典 10万 × 文本 1000 字 = 1亿次 |
| Trie 前缀树 | O(N×L)，L=最长词长度 | 文本 1000 字 × 最长词 20 字 = 2万次 |
| AC 自动机（Aho-Corasick） | **O(N)**，与词典大小无关 | 文本 1000 字固定 1000 次比较 |

AC 自动机实测：10万词典，文本 1000 字，**匹配延迟 <1ms**。构建耗时几百毫秒（启动时一次性构建）。

热更新：新词典构建完整新 AC tree → 原子替换指针 → 旧 tree 延迟回收（等所有进行中的匹配完成）。10万词典重建约 200–300ms，对用户无感。

### 理论支撑

AC 自动机 = Trie 树 + KMP 失配函数 + BFS 构建 fail 指针。在 Trie 树上添加 fail 指针（指向当前模式的最长真后缀对应的节点），使匹配失败时不需要回溯文本指针，保证 O(N) 整体匹配。

相比纯 Trie：Trie 每次失配需要回退文本指针，最坏 O(N×L)；AC 自动机通过 fail 指针一次遍历文本即可找到所有匹配，是多模式匹配的最优解。

### 业界对标

- **Aho-Corasick 算法**（1975 年论文）：多模式字符串匹配的经典算法，广泛用于入侵检测、内容过滤
- **Hyperscan**（Intel 开源）：高性能正则引擎，底层使用 NFA/DFA，比 AC 自动机支持更复杂模式但构建更重
- **各大 IM 平台**：微信、陌陌、字节均采用 AC 自动机或其变体做敏感词过滤

### 追问预案

**Q：简历写的"Trie / 多模式匹配"，和 AC 自动机有什么关系？**
> Trie 是 AC 自动机的基础数据结构，AC 自动机是在 Trie 上加 fail 指针实现的多模式匹配优化。"Trie / 多模式匹配"是对实现的描述，AC 自动机是算法名称。实现时确实用了 AC 自动机，可以展开讲 fail 指针构建和 O(N) 证明。

## N3：MongoDB 2dsphere 地理服务 + TTL 缓存

**简历原文**：MongoDB 2dsphere 地理服务 + TTL 缓存，大幅降低地理查询 QPS

### 数据支撑

| 查询类型 | 延迟 | 说明 |
|---------|------|------|
| 无缓存地理查询（MongoDB） | 10–50ms | `$nearSphere` + 2dsphere 索引 |
| 缓存命中 | <1ms | 热点区域/用户的"附近的人"结果 TTL 缓存 |
| TTL 设置 | 30–60s | 用户位置变化频率低，缓存有效期长 |

2dsphere 支持球面距离计算（haversine 公式），精度比平面距离计算（$near）更高，适合公里级的"附近的人"场景。

### 理论支撑

MongoDB 2dsphere 索引：存储 GeoJSON 格式坐标点，B-Tree 索引按球面坐标区域划分（R-Tree 类似），`$nearSphere` 查询走索引做最近邻搜索，复杂度 O(log N + K)（N=数据量，K=结果数）。

TTL 缓存的业务逻辑：用户位置每分钟更新一次，"附近的人"结果 30–60s 内基本不变。缓存 Key = `user_location_nearby:{userId}:{radius}`，TTL 60s 自动过期。热点区域（市中心、商圈）用户密集，缓存命中率 70%+，大幅降低 MongoDB 查询压力。

### 业界对标

- **微信"附近的人"**：GeoHash + 缓存，业界最知名的地理查询案例
- **MongoDB 官方 2dsphere 案例**：`$nearSphere` + TTL 缓存是 MongoDB 官方推荐的地理服务实现模式
- **Redis GEO 命令**（Redis 3.2+）：内置 geohash，替代 MongoDB 2dsphere 的轻量选择

### 追问预案

**Q："附近的人"分页怎么做？**
> 按距离升序 + `limit/skip`。深分页用 last_distance 作 cursor 优化（`$nearSphere` + minDistance 过滤），避免 skip 大量数据。MongoDB `$nearSphere` 支持 `maxDistance` 和 `minDistance` 参数，直接切 cursor。

## N4：WebSocket + 结巴分词 + 倒排索引 FAQ 客服

**简历原文**：WebSocket + 结巴分词 + 倒排索引 FAQ 客服：关键词命中自动回复 / 未命中转人工，支持会话上下文保持

### 数据支撑

| 组件 | 性能 | 说明 |
|------|------|------|
| 结巴分词（jieba-cpp） | <1ms/句 | 中文 jieba 分词，词典大小 ~25万词 |
| 倒排索引查询 | <5ms | 内存倒排索引，关键词 → 问题列表 |
| 系统响应延迟 | <100ms | 分词 + 倒排查询 + 结果排序整体 |
| FAQ 词库规模 | 数千条 | 金融 IM 场景常见问题集 |

会话上下文保持：用户 session 内维护最近 N 条对话历史，用于处理追问（如"更多详情" → 知道上文问的是什么问题）。

### 理论支撑

倒排索引（Inverted Index）：词 → 文档 ID 列表的映射。查询时对用户输入分词，取各关键词的倒排列表做交集（AND）或并集（OR），BM25 或 TF-IDF 打分排序，取 top 1 结果。与正排索引（文档 → 词）相反，倒排是搜索引擎的核心数据结构。

结巴分词：基于 HMM（隐马尔科夫模型）+ DAG（有向无环图）的中文分词，切词精度高于简单字典最长匹配，适合口语化的用户输入（如"我的账户为什么转不了钱"）。

FAQ 匹配 vs NLP：本系统是**关键词检索/FAQ 匹配**，不是 NLP（无语义理解、无神经网络）。优点：延迟极低（<100ms）、可解释、易维护；缺点：无法理解语义近义词（"提现"和"取钱"需要手动配置同义词扩展）。

### 业界对标

- **Elasticsearch FAQ 检索**：标准倒排索引 + BM25 排序，本系统的轻量版
- **阿里云智能客服**：同样基于倒排 + 同义词扩展 + 意图识别，比本系统多了 NLU 层
- **美团智能客服公开分享**：早期版本也是倒排索引 + 关键词匹配，后续升级为深度学习意图识别

### 追问预案

**Q：结巴分词 + 倒排索引和 NLP 有什么区别？**
> 结巴分词做的是词法分析（把句子切成词），倒排索引做的是关键词精确匹配，两者合在一起是**信息检索（IR）**，不是 NLP。NLP 需要语义理解（同义词、上下文意图），通常依赖神经网络模型（BERT / GPT 等）。本系统是轻量级 FAQ 检索，延迟 <100ms，适合金融 IM 的强合规、强可解释场景。

- AI：DeepSeek（主）+ 阿里云实时 ASR + 备用本地小模型

### 理论支撑

**流式架构的延迟优化**：传统"语音 → 完整识别 → AI 响应"链路延迟 = ASR 完整时长 + AI 推理时长（秒级）。流式架构中，ASR 中间结果稳定后立即触发 AI（不等终态），AI 流式输出（不等完整响应），首字延迟降到 <200ms。本质是"等待"换"投机执行"——可能多算一次（中间结果改变需重算），但延迟显著下降。

**DeepSeek 双模型容错降级**：请求 DeepSeek 同时启动定时器（3s），超时则取消主请求 + 立即转发到本地小模型。前端流式接收，无感切换。降级阈值的设定权衡：太短（<1s）正常请求会误降级；太长（>5s）用户感知到延迟；3s 是 DeepSeek P95 响应时间的合理上限。

**多轮上下文管理**：context window 限制 8K token，超出按 `(轮数衰减系数 × 关键词权重)` 截断。系统提示词永久保留 + 最近 N 轮对话 + 关键摘要（提取每轮关键事实点压缩存储），避免简单 FIFO 截断丢失早期重要信息。

### 业界对标

- **ChatGPT 流式响应**：Server-Sent Events (SSE) 流式输出 token，首字延迟 <500ms，本项目 WebSocket 实现首字 <200ms 已对齐头部产品
- **字节豆包 / 讯飞星火面试模拟**：AI 面试场景的同类产品，技术栈基本一致（流式 ASR + LLM + WebSocket）
- **OpenAI Whisper + GPT-4 streaming**：同类技术组合，本项目用阿里云 ASR + DeepSeek 国内化替代

### 追问预案

**Q：流式 ASR 中间结果不稳定，怎么避免重复触发 AI？**
> 阿里云 ASR 中间结果有 `is_final` 字段标识。我在中间结果连续 N（=3）次相同后才认为稳定，触发 AI。如果用户继续说话改变了识别结果，取消上次 AI 请求，用新结果重新触发。代价是偶发的多余请求（DeepSeek 计费），实测重复率 <5%。

**Q：DeepSeek 和小模型质量差异如何处理？**
> 小模型（Qwen 7B 量化版）只在降级场景用，会在前端展示"AI 服务繁忙，已切换到极速模式"提示用户。质量差异主要体现在长答案的逻辑连贯性上，但对面试模拟的短问短答场景影响小。后续优化方向是给小模型加 RAG（检索面试题库）补足知识。

## P2：Thunder（C++20 分布式集群框架，开源）

**简历原文**：自研 **Thunder** C++20 分布式集群框架（Raft 选主 + Libev + dlopen 热加载，学习型 MVP）

### 数据支撑

| 指标 | 值 | 业界对标 |
|------|----|---------|
| Raft 选举超时 | 150–300ms 随机化 | Raft 论文原文推荐值 |
| Raft 心跳间隔 | 15–30ms | etcd 默认 100ms（更激进） |
| 三节点写确认 | <20ms | etcd P99 在 10–50ms |
| Leader 切换时间 | <500ms | Election timeout 上限 |
| 进程间通信吞吐 | 1–5 GB/s | Unix Domain Socket |
| 进程间通信延迟 | ~0.01ms | 同机 UDP 小包 |
| 项目状态 | MVP 已能跑，开源 | GitHub 链接随时可发 |

### 理论支撑

**C++20 协程对接 Libev**：Libev 注册 fd 事件回调，回调内 `coroutine_handle.resume()` 唤醒对应协程；协程内 IO 操作 `co_await` yield 出来，等下次事件触发。本质是用协程替代回调函数 — **同步语义、异步执行**，避免了 callback hell。C++20 协程是无栈协程（stackless），开销比 Go goroutine（有栈）更小，但需要编译器支持（GCC 10+ / Clang 12+）。

**Raft 选举随机化（150–300ms）**：Raft 论文推荐值，平衡三个因素：
- 故障恢复速度：太长（>500ms）业务感知卡顿
- split vote 概率：随机化范围越大，多个 Candidate 同时发起选举的概率越低
- 心跳开销：心跳间隔取 election timeout 的 1/10（15–30ms）
etcd 默认 1000ms 偏保守，TiKV 默认 100ms 偏激进，Thunder 取中间值便于学习型项目调试。

**插件 dlopen 热加载 + 多进程隔离**：dlopen 本身在同地址空间，不提供进程隔离（插件崩溃会拖垮主进程）。Thunder 的隔离靠多进程 Worker 模型：插件跑在独立 Worker 进程，崩了 Master 检测后拉起新 Worker，主进程不受影响。这是 Apache HTTP / Nginx Worker 模型的同款思路。

### 业界对标

- **brpc**（百度开源 C++ RPC，生产级）：Thunder 不是为了取代它，是把 C++20 协程 + Raft + 插件化串起来深度实践
- **sofa-pbrpc**（蚂蚁开源）：同类 C++ RPC 框架
- **etcd**（Go 实现的 Raft 标杆）：Thunder 借鉴 etcd 的 Raft 实现思路，但用 C++20
- **TiKV**（Rust 的 Raft + LSM）：分布式 KV 存储参考案例

### 追问预案

**Q：跟 brpc / sofa-pbrpc 比有什么区别？为什么不用现成的？**
> Thunder 不是为了取代成熟框架。主要目的是把 C++20 协程 + Raft + 插件化这几个我在工作中没机会一起用的东西串起来深度实践。生产环境我还是建议用 brpc。这个项目定位是**学习性质大于生产性质**，已开源在 GitHub，README 有 quickstart，git clone + make 就能跑 demo。

**Q：Raft 的日志压缩 / Snapshot 实现了吗？**
> MVP 版本没实现 Snapshot，定位是教学型。生产化需要补 InstallSnapshot RPC + 日志截断逻辑。这个我诚实告诉面试官，没做的不硬编。

**Q：协程 + Libev 的写法和原始 Libev 回调比有什么优势？**
> 原始 Libev 是回调风格，多个 IO 串联会形成 callback hell（嵌套深、错误处理分散）。协程版本写起来像同步代码：`auto data = co_await read(fd); co_await write(fd2, data);`，逻辑线性可读。代价是 C++20 协程编译器支持（GCC 10+），且需要理解 promise/awaitable 抽象，学习曲线陡。
