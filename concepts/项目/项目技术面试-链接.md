## 1. KeyDB 存算分离 + Redis 可观测性 — 华为云

### 一句话介绍
KeyDB是华为云的Redis兼容存储服务，我负责存算分离架构的存储引擎改造，基于RocksDB扩展自定义文件系统，数据从本地SSD迁移到远程OBS对象存储。

### 关键性能数据

| 场景 | QPS | P99延迟 | 说明 |
|------|-----|--------|------|
| 纯读（热数据） | **15万** | 1.2ms | 命中Block Cache，内存访问 |
| 纯读（冷数据） | **5万** | 8ms | OBS网络拉取，RTT约2ms |
| 纯写（SET） | **8万** | 2ms | 异步批量提交，攒100条 |
| 混合读写(8:2) | **10万+** | 5ms | 生产环境典型 |

**延迟分布**: P50 0.8ms / P90 2ms / P99 5ms / P999 15ms
**存储成本**: 纯SSD ¥500/月 → 存算分离 ¥200/月（**降53%**，实际生产降约30%）
**可用性**: 99.99%（年停机<53分钟）

### 核心架构要点

```
KeyDB进程 → RocksDB引擎 → 自定义Env插件 → [元数据中心(Etcd) + OBS对象存储]
```

- **热数据**: 本地RocksDB，Block Cache + MemTable，延迟<1ms
- **冷数据**: 超过7天未访问下沉到OBS，拉取延迟5-20ms
- **文件分类**: SSTable(.ldb)写OBS / WAL(.log)本地+远程双写 / MANIFEST存Etcd
- **元数据中心**: gRPC通信，记录文件位置、分片信息，支持快速定位

### 优化历程

| 问题 | 现状 | 优化 | 效果 |
|------|------|------|------|
| 冷数据延迟高 | 8ms | 异步预取+连接池 | 3ms |
| Compaction抖动 | QPS掉50% | 分时段限速 | 抖动<10% |
| 内存占用 | 16GB | 智能缓存淘汰 | 8GB |
| gRPC断连 | 空闲超时 | keepalive心跳30s | 自动重连 |
| 写放大 | 10x | 增大MemTable | 5x |

### Redis可观测性

| 指标 | 数值 |
|------|------|
| 实例规模 | 万级 |
| 大Key阈值 | String>1MB 或 集合>5000元素 |
| 布隆过滤器 | 100万Key仅1.2MB，FPR 1% |
| 热Key检测 | 滑动窗口1分钟，超1000次/分钟标记 |
| 插件开销 | 主线程<1μs，CPU<10% |
| 问题定位效率 | **提升50%**（2h→1h） |

## 2. 服务网格平台 — 即构科技（K8s + Istio + Envoy）

### 一句话介绍
从零搭建K8s+Istio服务网格平台，负责Envoy Wasm插件开发和Go SDK封装，支撑10+业务项目接入，平台总QPS 5万+。

### 关键性能数据

| 场景 | QPS | P99延迟 | 开销 |
|------|-----|--------|------|
| 无Sidecar（直连） | 8万 | 2ms | 0% |
| 有Sidecar（无插件） | 7.2万 | 3ms | -10% |
| Sidecar+Wasm熔断 | 6.8万 | 4ms | -15% |

**Sidecar开销分解**: Envoy转发 +0.5ms×2 + Wasm执行 0.5ms + 统计 0.2ms + 连接池 0.3ms = **总计 +2ms**

### Wasm自适应熔断

- 公式: `k × accepts < total - protection` 则概率性熔断
- k默认1.5（越小越敏感），window默认10s
- **熔断恢复 < 5s**（vs 传统固定阈值30s）
- 组件: Rust编译→Wasm，2MB，热执行0.5ms/请求，CPU 5%

### 架构要点

- **控制面**: Istiod，配置下发
- **数据面**: Envoy Sidecar，代理所有流量
- **SDK**: Go语言封装gRPC/HTTP服务发现、负载均衡，业务无侵入接入
- **瓶颈**: istiod千级服务时配置下发>10s；全量Tracing性能损耗~5%

## 3. 分布式 IM 消息系统 — 雷漫网络

### 一句话介绍
自研C++分布式IM系统，支撑社交APP的900万注册用户和300万日活，实现单机百万连接和消息端到端延迟P99<50ms。

### 关键性能数据

**连接能力**:
| 指标 | 数值 |
|------|------|
| 单机连接数 | **120万**（16核32GB） |
| 每连接内存 | **12KB**（Connection 4KB + 读缓冲4KB + 写缓冲2KB + ev_io 1KB + 其他1KB） |
| 120万连接总内存 | 14.4GB（实际16GB含碎片） |
| 心跳处理能力 | 10万/秒 |
| CPU占用（空闲） | 30% |

**消息吞吐**:
| 场景 | 吞吐 | P99延迟 |
|------|------|--------|
| 单聊消息 | **5万条/秒** | 30ms |
| 群聊（100人） | 5000条/秒 | 50ms |
| 群聊（1000人） | 500条/秒 | 200ms |
| 离线消息拉取 | 2万条/秒 | 20ms |

**消息延迟分解（单聊 20ms）**: 网络传输2ms(10%) + 协议解析1ms(5%) + 路由2ms(10%) + 写DB 5ms(25%) + 写MQ 2ms(10%) + 推送路由3ms(15%) + 网络推送5ms(25%)

### 核心架构要点

```
客户端(TCP/WS) → Libev事件循环(epoll单线程) → gRPC内部RPC → 服务层(消息/用户/群组/推送)
                                                      ↓
                      存储层(MySQL分库分表 / Redis Codis / MongoDB历史消息 / RocketMQ)
```

- **连接层**: Libev单线程epoll，每服务器15万连接，8台共120万。非阻塞I/O + 自定义二进制协议（4字节长度+变长body）
- **分库分表**: 用户ID%32分到32个消息库，每库64张表
- **群消息优化**: 按accnodeidentify合并RPC，从成员数量级压到网关节点数量级（3000次→~10次）
- **msgseq分配**: Redis INCR正常路径<1ms，批次预分配5-20ms（每10000条触发1次）
- **未读数**: MongoDB count替代Redis INCR（避免撤回DECR丢失/大群写扩散）

### 可用性

- 99.99%（年停机<53分钟），实际约40分钟
- 故障恢复 < 30s
- 消息不丢：WAL + 重试机制；消息不重：客户端msgId去重

## 5. Thunder 分布式异步集群框架 — C++20 个人开源

### 一句话介绍
自研高性能分布式异步框架，整合C++20协程、RPC、Raft共识算法和动态插件热加载，空请求200万QPS。

### 关键性能数据

| 指标 | 数值 | 对比 |
|------|------|------|
| RPC空请求QPS | **200万** | gRPC 5万（**40倍**） |
| 10KB请求QPS | **30万** | gRPC 5万 |
| 协程切换 | **50ns** | 线程1万ns（**200倍**） |
| Raft选主 | **<50ms**（3节点） | 原始200ms |
| 单连接内存 | **20KB** | gRPC 50KB（节省60%） |
| 共享内存IPC QPS | **150万** | Unix Socket 50万 |
| 进程间通信带宽 | **1-5GB/s** | — |

### 核心架构要点

**C++20 Stackless协程**: 编译器内置，栈2KB-8KB（堆上分配），vs Stackful 64KB-1MB。50万连接仅需1GB栈内存。
**工作窃取调度器**: 每线程本地队列 + 随机窃取，负载均衡。
**Raft**: 随机化选举超时150ms+random(0~150ms)，批量日志复制100条/批次→10万QPS。
**插件系统**: dlopen+.so热加载，引用计数保护并发卸载，RCU机制。
**多进程Worker**: fork()多进程+Nginx模型崩溃隔离，共享内存ring buffer IPC。

### 与主流框架对比

| 框架 | 空请求QPS | 延迟P99 | 内存/连接 | Raft内置 | 协程 |
|------|----------|---------|----------|---------|------|
| **Thunder** | 200万 | 0.8ms | 20KB | ✅ | ✅C++20 |
| gRPC | 5万 | 3ms | 50KB | ❌ | ❌ |
| brpc | 20万 | 1.5ms | 35KB | ❌(braft) | ✅半同步 |
| thrift | 15万 | 2ms | 40KB | ❌ | ❌ |

### 性能优化历程

```
V0.1 基准10万QPS → V0.2 perf发现瓶颈(内存分配20%+锁15%) → V0.3 对象池→50万
→ V0.4 无锁队列→120万 → V0.5 batch处理→200万
```
